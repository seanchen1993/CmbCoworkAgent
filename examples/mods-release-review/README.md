# 使用现有 Mods API 的发布审核示例

本例验证发布审核这一独立业务：`draft → review → approved`。状态图、可走边、校验时机与
推进操作均由插件的 Function Mod 代码实现，不新增应用专用 API，不修改平台源码。

本目录是开发者教学示例，不是完整的生产发布流程。同一来源代际可续接；来源换代后，
`source-inactive` 状态会触发只读阻断，本例未提供跨代接管入口。长期流程应采用插件自己的
持久化提交器作为主状态来源，例如 AutoBiz 的 `state.json` 与唯一写入脚本，再将平台能力
状态用于展示和同步。不能将测试中固定的来源代际，解释为真实管理器重启后的自动恢复保证。

## 使用

1. 将本目录作为本地插件安装，启用并确认当前源码版本的权限。
2. 在项目工作目录创建 `release-review.json`：

   ```json
   { "description": "本次发布说明", "qualityAccepted": false }
   ```

3. 在会话执行 `/release-review status` 查看实际状态。
4. 执行 `/release-review submit`。插件读取真实产物、请求运行插件自带的 Node 校验脚本，
   发布说明通过后推进至 `review`。
5. 在产物中将 `qualityAccepted` 改为 `true`，执行 `/release-review approve`，推进至
   `approved`。未通过审核时保持原状态，结果中的业务状态为 `blocked`。

本机需要可执行的 `node`。`nodeExecutable` 为可选的作者配置，可改为本机 Node 完整路径；
应用仍会针对实际命令请求原生授权。路径及业务校验规则均由插件提供。

`qualityAccepted` 是示例业务产物中的质量结论字段，不代表平台原生的人工批准凭据。
本例检验字段和状态图是否满足插件规则，不宣称该文件无法被用户或模型修改。

## 机制与适用边界

- `on.capability` 定义动作和输入输出；精确调用真实 QuickJS 回调，错误不会成为成功推进。
- 普通 `on("command.run")` 只负责用户入口，转调同一个业务动作。
- `$.tool.call` 读取工作区真实文件；`$.process.run` 执行插件作者的产物校验脚本。
  用户传入的 `passed: true` 不在输入协议中，不能替代校验。
- `$.platform.publish` 的 `expectedRevision` 保护持久业务状态，动作的 `requestKey`
  防止重复请求再次执行。同一键更改请求会被拒绝。
- `$.state.set(..., { ifVersion })` 保护会话内的并发锁。它是内存状态，不是持久化主状态。
- 此例校验并记录已读取产物的摘要，不宣称文件之后不可修改。严格业务应在实际使用产物时
  重新核对摘要，或由插件自有提交器将校验与写入纳入同一个临界区。
- 动作执行异常可能产生 `unknown`。应检查实际状态及插件自身日志，再决定后续操作；
  同一请求键不会自动重放。插件需要外部副作用或多文件事务时，应自行提供只读对账动作。
- 关闭或更新原插件后，旧来源状态可能需要重新绑定或对账；本例不会把未知状态重置为初始状态。

这说明可执行的状态机本来就能通过现有 Mods 机制实现。平台只提供隔离、权限、工具调用、
版本状态与动作记录等通用能力，发布审核规则始终留在插件内。
