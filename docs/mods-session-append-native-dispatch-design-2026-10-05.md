# 原生会话内容接入已运行的 Mods

日期：2026-10-05。开发目录为 `C:/ai/CmbCoworkAgent-mods-v2`，分支为
`codex/mods-v2`。这是原生消息完整接线中的一段，不是全部入口完成声明。

## 用户将感受到什么

正常提问、模型回答和工具结果保存到对话时，已经在本任务运行的 Mods 可以对这些
内容作处理。没有启用 Mods、没有实际运行的插件实例时，内容仍由同一个正常保存
过程处理，不会为了保存一句话临时启动插件。

例如，一个团队组件可以在保存工具结果前替换其中的敏感文字；代码检查组件可以
保留检查提醒。真实工具编号、调用参数和任务归属仍由原任务提供，不能由显示文字
或者插件声明改变。完整内容保护和实际任务入口接线还须完成各自验收。

## 接线规则

原 `ModsManager.captureFunctionConversationRuntime` 从自身私有记录取出本次实际
任务的会话绑定。返回的处理闭包固定原绑定、原任务权限、原生命周期对象和原
方法；调用前、真实等待后都重新核对这些原对象以及实际追加 Ticket。

原启动位置 `ipc/mods.ts` 将闭包连接到现有
`FunctionModsManager.appendConversation`。该方法只查找已经存在的实例；找不到
实例直接进入 Ticket 的同一个保存过程，不执行插件加载或启动。

没有启用 Mods，或者原生命周期没有追加方法时，闭包也进入同一个 Ticket 保存
过程。已开始的处理如果抛错或等待后原任务失效，必须拒绝，不另开第二次保存。
实际提交已经发生但回执失效时，也不能删除事实或重复调用插件来伪造成功。

这段处理闭包不授予新权限。实际消息生产入口必须先证明本次目标、原生消息、
原位显示记录和工具执行事实；未来接入的入口不能仅凭 `role`、插件名、消息上的
公开标记或同名任务来取得保存权限。

## 评审和验证

Official 和 Latest 两位代理已分别正式通过上述方案。Latest 将在真实 AppDB、
原 Store、原 Manager 和真实 Ticket 上验证：无实例、无方法、已运行处理、处理
提交后抛错、等待期间失效、生命周期替换，以及关闭插件但仍需内容保护的路径。

完整原生入口、流式消息封口、完整内容保护和子任务冷恢复是后续依赖。这段闭包
的测试通过不能代替实际输入、回答和工具结果在真实 Electron 中的使用验收。
