# 让自己的组件接着安排任务

开发分支新增的是：**组件可以把下一件事交给当前聊天真正执行。** 它不只是返回一段建议，也不需要把建议复制进输入框再发送。当前聊天忙时先等待，空闲后开始下一轮；使用这份聊天原来的模型、项目和权限。

## 可以直接试的例子

示例源码在 `resources/mods/queued-review`。把其中的 `plugin.json` 和 `hooks` 文件夹放在 ZIP 根目录，导入“自定义 → 组件”使用的插件包入口。导入、启用后，查看组件并批准当前版本；如果当前聊天已应用 Claw 组合，把这个组件加入组合并重新应用。

1. 打开普通项目聊天，先说明一个具体开发需求，并选好已配置的模型。
2. 聊天输入区上方会出现 **“完成需求并接着检视”**。
3. 点击按钮。组件先发出开发任务；如果原任务还在运行，这条任务会等待。
4. 任务真正完成后，组件再提交一次代码检视，聊天里会出现下一条任务和检视回答。
5. 每条组件任务都有来源标记。检视任务完成后不会无限重复检视。关闭或撤权组件后，不再安排新的后续任务。

这是演示“任务可以接着执行”的例子，不是生产质量门禁。检视是另一个完整任务，**不会倒过来阻止上一轮被标记完成**。如果要求“检视、测试达标才能交付”，应使用已有完成条件或 DIY 流程中的检视、测试步骤。模型是否读到文件、是否真的运行测试，仍要以实际工具记录为准。

把示例的两条任务文字换成自己的要求，就可以体验不同工作方法。例如，第一轮整理需求，第二轮检查遗漏；或者第一轮开发，第二轮只检视，第三轮由另一个已组合的汇报组件处理结果。单独模型分析只给组件结果；这里的提交会在聊天中开启完整工作。

示例用真正的任务编号关联开发与检视，别的任务完成不会触发它。开发提交使用 `asUser: true`，便于准确关联开始时的任务文字，页面仍显示组件来源。如果组合里的其它规则重写这段开发文字，示例会保守地不自动检视，应一并调整关联规则。

示例会保留下游界面，方便和其它组件一起用。如果另一个组件完全替换输入区上方、没有保留下游界面，可能看不到示例按钮；把它改为保留 `next(e)` 返回的内容，或先在仅启用这个示例的聊天中体验。

## 原来的操作怎样迁移

| 原来 | 现在 |
| --- | --- |
| 组件只给建议，自己复制到聊天并发送 | 组件按钮可以直接安排一条聊天任务。 |
| 用独立模型分析，结果只返回给组件 | 仍可这样用；需要当前助手继续执行时，再安排聊天任务。 |
| 执行固定步骤，就点击“运行已保存版本” | 固定流程继续沿用该按钮；组件的自动后续工作不依赖每次手动运行流程。 |
| 普通插件命令返回检查结果 | 保留原命令；要发起下一轮，改成界面按钮或真正完成通知，不能在命令内部直接提交。 |

## 作者要记住的几件事

调用是 `$.prompt.submit({ text: "任务文字" })`。支持 `asUser: true`，仅去掉模型看到的组件来源句，页面和权限仍保留真实组件来源。

- 按钮点击、任务开始/完成通知、定时回调等已支持入口可以提交；运行中的规则不要等待它自己安排的下一轮。示例采用不等待的调用。
- 命令、提交规则、工具调用规则和组装模型输入的规则里不能直接提交。这与核验的官方宿主限制一致；把代码移到真正的完成通知或按钮回调。
- 返回成功的时点是下一轮真正开始，不是回答完成。要处理回答完成，用真正的完成通知。
- 等待中的任务存在内存中。撤权、重载、退出会清理待执行任务，重新批准不会自动重放。改动依赖组件的运行中任务也可能结束，需要重新执行。
- 只支持文字；不能把非空附件、任意会话、人工来源或权限回执塞进参数。文字中的 `/goal`、技能标记和文件引用不会变成人工命令或授权。
- 为防循环，每个组件每个对话最多同时等待8条任务；同项目同组件一分钟最多接纳20条。作者仍需自己避免“每次完成又提交自己”的无限循环。

详尽技术和验收记录见[阶段记录](mods-plugin-prompt-stage-2026-10-04.md)。原生控件嵌入、界面构造器替换等仍继续迭代，当前不宣称任意官方组件都已完全兼容。
