# Mods v2 全面复核与优化方案

日期：2026-09-26。工作树：`C:\ai\CmbCoworkAgent-mods-v2`，分支：`codex/mods-v2`。基于 `e81a634a` 及 9 月 25 日易用性未提交变更。本轮遵循“先方案、两位独立 agent 评审通过、再实现”。本稿已获两位评审明确批准，以下记录在产品代码修改前写入。

## 范围与原则

主要目的仍是让用户可靠地配置完成前检查、自动修复与复检，以及明确选择后的 Autobiz 阶段推进。保持默认关闭、安装不等于授权、应用规则优先、旧证据失效和原生审批边界。此次不扩展 Claude 全量兼容、环境安装器、未知提交自动恢复，也不修改 UAT。

“存量无影响”必须细分：未使用 Mods 的普通用户；已有普通 Plugin/经典 Hook/MCP 用户；使用旧 Mods 状态与卡片的用户；显式开启新完成规则的用户。最后一类的任务完成方式、模型用量和检查耗时改变是预期行为，不应称零影响。

## 已有证据与需解决问题

1. **普通配置与环境进程探测耦合（P2）**：`mods:function-completion-policy` 无条件等待 Git/Python 探测；折叠表单仍挂载，每次全局配置事件重新读取。没有使用 Autobiz 的用户也会启动外部进程，最长等待约 3 秒。来源为 IPC、`FunctionCompletionPolicy` 和实际 probe 实现。
2. **新增保留状态键与旧插件数据冲突（P2）**：`completion-config-source` 的读被截获，写/删被无条件拒绝。已有插件此前可以保存任意同名键，移出 keys 枚举并没有解决真实值不可访问的问题。
3. **公开命令仍暴露内部权限错误（P2）**：`/kanban-mode`、`/kanban-target` 在应用接管后直接写 `completion-config`，需要和 Pane 一样给出可操作提示，不能放开写入权限。
4. **面板局部刷新触发无关读取（P2/性能）**：完成证据、反馈、日志及 legacy 卡片 store 对 `scope: panes` 事件都重新 IPC 读取。Client 每次输入/消息都有可能触发这四类无关工作。现有 `FunctionSite` 已过滤该局部事件，事件合并仍会将全局变更提升为无 scope。
5. **证据读取固定做两次数据库查询（性能）**：`completionEvidence()` 即使没有追加失效记录，仍再次读同一批记录；也对无需检查的记录计算绑定摘要。
6. **外层设置面板异步竞争（P2）**：原 `ModsPanel` 的初始读取有取消标记，`run/refresh` 则未隔离旧项目异步结果。内层规则编辑器已有隔离，并不覆盖外层状态、通知和 busy。

以上由两名 agent 独立静态检视，结合本地代码确认。异步竞争需补动态复现，不能仅凭静态风险宣称已发生用户数据误写。

## 拟实施方案

### A. 分离普通规则读取与按需环境检查

- 恢复 `completionPolicy` 为只读规则快照，读取本身不执行 Git/Python。
- 增加独立、只读的环境检查 IPC/preload 方法，以当前 thread scope 校验调用者，等待结束后再次校验 scope。参数不允许传任意命令或路径；源目录仍由已支持的宿主环境变量决定。
- 规则编辑器仅首次展开时挂载；同项目折叠不销毁草稿。切换项目/插件重置其本地生命周期。
- 环境检查仅在用户选择 Autobiz 检查、已保存规则包含该检查而展开表单，或明确点击“检查 Autobiz 环境”时执行。普通规则加载/保存、全局配置广播不触发外部探测。
- 检查期间或失败/未就绪时，不保存已启用且包含 Autobiz 的规则；允许取消该检查或关闭规则。普通模式可立即编辑和保存。缓存仅在当前编辑器生命周期内保存显示状态；明确重查会重新探测；同时调用继续合并。环境结果不成为授权依据，运行时检查保留。

### B. 保持旧状态命名空间，统一示例反馈

- 删除 `completion-config-source` 特殊读取和写入禁令，恢复这个普通键的 get/set/delete/keys 语义，不迁移或删除已有值。
- 在专用 `completion-config` 的宿主覆盖返回值中附加 `_cmbPolicySource: application`，只供示例 UI 判断归属。新增 `guestValue` 辅助方法仅服务 guest store 读取；原生策略持久值、门禁策略解析、规则摘要继续使用原值。
- 该标记不是权限凭据：guest 伪造标记最多影响自身界面，不能改变宿主规则；真实写入保护仍基于宿主独立设置是否存在。
- Pane 和两个设置命令识别应用归属，直接给出应用设置入口；写入期间被应用接管的竞争继续由宿主拒绝，再转换成友好提示。不得在拒绝后写入 review-mode/review-target 旧别名。

### C. 减少 Client 交互的无关工作

- Evidence、Feedback、Logs、legacy mod-cards-store 只跳过明确 `scope === panes` 的通知；无 scope 的旧/全局事件继续处理，线程过滤保持。
- 保持关闭、撤权、重载、配置变更后的清空与重新读取；检查原生配置订阅是否完整，补齐后须清理监听器，防止重复订阅。
- `completionEvidence` 稳定读取只查询一次；只有确实追加 runtime 失效记录后再次查询。只对相关 PASS/失效记录计算摘要，不改变绑定算法、失效条件、权限检查、顺序、数量限制和中断事实。
- 不改 `host.publish`、assertThread/grant、工具审批、文件指纹与完成门禁，以性能为由跳过任何校验均不在方案内。

### D. 隔离外层设置面板的旧请求

- 按 threadId 给外层解锁设置内容稳定 key；同一项目内用存活状态及读取代次保护异步 refresh/run。
- 原项目已授权操作可以正常完成，但旧响应不得覆盖新项目的 status/notice/busy；不能把原本针对 A 的操作重新发往 B。
- 页面初始读与后续 refresh 使用统一的“最新读取生效”规则；失败提示也需遵守同样生命周期。

## 测试与验收

1. 先失败后修复：旧普通状态键（有/无应用规则及重启）、命令接管（含中途接管）、外层/内层项目切换、probe 慢/失败时普通配置可用、折叠与配置广播零探测。
2. 确定性性能回归：真实 React/Chromium 挂载四种消费者，注入至少 100 次 panes-only 通知，额外无关 IPC 次数为 0；无 scope 事件必须刷新；关闭/换线程/卸载不得遗留旧内容或监听。稳定证据查询 1 次；runtime 变更追加失效后仍能返回新记录。
3. 回归执行：最终 TypeScript、修改行 ESLint、构建；完整 Vitest；展开 npm test 后续独立套件逐条执行并对照旧失败清单（不因首个失败跳过后续）。新增失败须修复或明确隔离原因，不修改旧失败断言。
4. 桌面 E2E：完整 Mods E2E（含 legacy 工具/卡片、默认关闭、经典事件、模型与审批入口）、设置 E2E、实际 utility process 测试；普通构建恢复，检查不得遗留测试专用 bridge。
5. 性能：受控桌面正式 CPU/TTFT/吞吐测试使用既定 5 分钟 × 2 空闲窗口、50 × 2 流式样本，单独执行、不并行构建或其他重测试。指标仍为 CPU 增量 ≤0.5 个百分点、TTFT p95 增量 ≤40ms、吞吐 ≥95%。保留所有样本及失败，不降低门槛。
6. 长稳：本轮用已有 50 条历史/200 次 Client 交互场景与生命周期回归检查所改路径；不能代替既有两小时长稳。没有 retaining-path 证据时不盲改内存逻辑，不宣称解决此前 GC 后堆增长。

## 效果、风险与交付口径

可承诺的代码级效果：普通设置不等待外部依赖；旧任意存储键恢复兼容；局部 Pane 更新不再刷新四类无关数据；稳定检查证据只查库一次；配置异步结果按项目隔离。无法预先承诺正式 TTFT 或长期内存因此达标，需实际测量。

增加独立环境 IPC 是内部应用接口调整，不改变持久化格式。新插件源码更新仍要求原有摘要授权；使用旧已安装示例需要按原机制更新后才获得新的命令/面板提示。若个别优化出现兼容问题，可逐项回退；宿主应用规则和权限边界始终保留。

最终交付包括两位 agent 的方案结论、实现复核、存量影响表、完整测试/失败对照、实际截图和性能结果。未验证的平台和长期稳定性明确列出，不以“全面检视”表示所有可能场景已证明无风险。

## 实施后复核

- 两位 agent 均已明确给出最终代码复核通过。评审过程中发现 `Promise.all` 任一失败会吞掉其他成功字段，已改为 `allSettled` 分项处理；全局状态未知时禁用操作。为保持跨项目全局事实同步，外层订阅原生和 DOM 配置通知，并清理监听。
- 实际 React/Chromium 九项回归已通过：折叠/普通配置零探测、草稿保留、内外项目迟到响应隔离、旧全局操作更新当前视图、部分读取失败、100 次局部 Pane 通知零无关 IPC、关闭压过旧响应及监听清理。
- 真实 Manager/QuickJS/SQLite 规则测试 19 项通过，包括普通旧键的读写/删除/枚举/重启，以及两个旧命令在写入中途被应用接管时不写别名。
- 最终全仓、E2E 与正式性能结果记录在[本轮全面检视报告](mods-v2-comprehensive-review-2026-09-26.md)，保留旧失败及未验收边界。
- 正式性能结果为 CPU/吞吐通过、TTFT 增量 53.1ms 超过 40ms，资格成立但总验收失败。两位 agent 独立复核后均同意本轮不做未经归因的进一步改动，将 TTFT 精调暂缓，先按全面报告的分段定位方案建立证据；此结论不等于性能达标，也不证明剩余工作必然高成本。长期内存问题继续单列。
