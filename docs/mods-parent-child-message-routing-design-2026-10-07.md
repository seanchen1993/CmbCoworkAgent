# 共享子任务的消息如何显示

目标是具备对应的 DIY 能力，不复刻 Claude 的所有内部行为。本次只修复影响实际任务完成的消息路由。

## 问题和用户效果

真实桌面运行两个共享子任务时，子任务已经保存回复与工具结果，父任务却未完成。主进程日志显示，父对话再次收到子任务的实时消息时，因消息属于另一个处理器而拒绝。相同错误至少从 10 月 7 日 00:52 UTC 的运行起已存在，并非最后一处性能调整引入。时间线本身不能证明它与超时的先后因果，因此仍须修复后实际验证。

预期效果：子任务的完整回复与工具结果留在各自的结果页和历史中，父对话收到同一条消息的副本时忽略它，继续执行后续请求并给出最终结果。父任务不会重复显示或保存子任务消息。

## 最小实现

1. 复用真实 Shared admission 已登记的来源和父子关系，把原证明传入既有 Host 和消息归属记录；不另建插件运行时或权限体系。
2. 只有真实主任务收到属于自己的真实共享子任务消息，才可以忽略副本。核对同一数据库、完整父子标识、分支和创建代次，并在父任务的最后一次完整检查之后重新读取原数据库关系。
3. 副本只被忽略，不转换成父任务消息、不取得写入资格。子任务已关闭时，只能判断这条已登记消息的归属，不能恢复子任务权限。
4. 保留消息全文及工具参数核对、父任务取消与关闭检查。其它父任务、兄弟任务、复制证明、伪造标记、过期关系继续拒绝。
5. 原子任务流、保存器、历史恢复、消息验证和跨归属序列化规则保持原路径。

设计与实际生产修改均已获两位独立评审通过；真实来源读取、数据库最新关系核对和关闭后的只读分类均保留。

## 验收

使用真实主任务、两个共享子任务、HTTP 模型和工具，检查完整后续请求、最终结果、各自的历史与保存记录，以及父对话没有子消息副本。再验证关闭子任务后的排队副本、外来消息、伪造证明、父任务取消和同编号任务重建。

复合父任务的功能等待上限为六十秒，后续普通对话仍为三十秒；单独保存实际耗时与是否超过三十秒目标，不能把功能通过写成速度改善。正常单工具链的原五秒性能检查保留。

10 月 7 日真实桌面全链通过：两个子任务分别接收提醒、执行工具、保存独立历史，父任务完成汇总；总计七次模型请求，含后续普通聊天。子任务退出后拒绝新的追加，原按钮正常工作，没有重复执行。首次父任务实际约 40.14 秒，超过三十秒目标。

消息投影完整 64 项及 Shared 的新增真实消息、关闭后副本、外来证明、取消和重建反例已通过。整体兼容回检另见继续实施记录，不以这个局部结论代替全工程验收。
