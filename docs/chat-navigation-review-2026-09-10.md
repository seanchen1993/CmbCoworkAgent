## P1：搜索自动展开整条长回答，重新引入界面卡顿

位置：`src/renderer/src/components/chat/ChatSearchOverlay.tsx:156–160`，调用点 742 行；`StreamingMarkdown.tsx:248`。

`prepareChatContentForSearchHighlight` 会点击当前消息内所有全文展开按钮，即使命中词已经存在于首尾预览的 DOM 中。按钮将完整 `text` 交给 `buildStreamingMarkdownRenderPlan`，继而同步解析和挂载全文。虚拟列表只限制消息行数，无法限制一行内部数万个节点。

用真实 Electron/Chromium、React、StreamingMarkdown 和 Virtuoso，构造 524,008 字符的回答，包含 13,100 个有粗体和内联代码的段落，关键词位于开头：

| 搜索后指标 | 旧基线 | 当前改动 |
| --- | ---: | ---: |
| 全文自动展开 | 否 | 是 |
| 视口子树元素数 | 4,312 | 39,314 |
| 超过 50 ms 的主线程长任务 | 无 | 1,239 / 246 / 87 ms |

数据来自 `PerformanceObserver` 的 longtask 记录。隐藏测试窗口的帧间隔受调度影响，因此不拿帧间隔代替阻塞时长。上一轮长回答夹具主要由连续的 x/y 字符组成，节点很少，没有覆盖这种高节点密度的 Markdown。

影响：共享渲染线程的会话切换、输入框、文件/Git 面板响应都会受影响；主进程和模型请求的业务流程没有因此直接改变，但界面处理会被延后。

建议：搜索只揭示目标附近的有限片段，或者对单条消息内部进行分段渲染；已有首尾片段中的命中应直接定位。全文展开继续由用户显式触发，不能以搜索自动点击全文按钮来绕过性能限制。

## P2：长回答结束后，原本可搜索的尾部消失

位置：`src/shared/chat-search-visible-content.ts:133–136`；`ChatContainer.tsx:3593–3616`。

正在输出时搜索沿用首尾预览；完成后开启 `includeFoldedContent`，只索引原文前 262,144 字符。这改变了搜索覆盖范围，长度超过该上限的尾部仍可显示，却无法继续匹配。

复现输入为 300,026 字符，末尾包含唯一 `TAIL_TARGET`。旧投影包含该词，当前完成态投影不包含。流式内容在 renderer 保留原始字符串，因此驻留内存的长回答可触发此路径；数据库历史加载的字符串另有 120,000 字符限制，不能依靠历史搜索补回这部分末尾。

影响：会话搜索可能出现输出时能找到、结束后找不到最终结论的回退。

建议：保留既有可见首尾区域的搜索覆盖，并让分段索引与 DOM 定位使用一致的范围/偏移映射；不能只扩大前缀截取上限。

## P2：256 Ki 字符限制按块执行，整条消息仍可能同步解析数百万字符

位置：`src/shared/chat-search-visible-content.ts:157–163`；`ChatContainer.tsx:3612–3622`。

数组分支先对全部文本块逐个调用投影，再拼接；每个块都有独立的 256 Ki 字符额度。`buildBoundedChatSearchText` 在这些解析和分配全部完成后才截断结果，因此单文档预算不能限制前面的 CPU 和临时内存开销。已完成多块文本可在 renderer 的搜索建立/刷新路径触发，流式结束时也会重新建立搜索文档。

Node 22 同机四次采样，每块为 320,000 字符的格式化段落，列出最快一次以减轻冷启动/GC 偶然性的影响：

| 块数 | 输入字符数 | 旧投影耗时 | 当前耗时 | 当前中间投影字符数 |
| --- | ---: | ---: | ---: | ---: |
| 1 | 320,000 | 2.4 ms | 9.5 ms | 222,822 |
| 8 | 2,560,000 | 17.0 ms | 78.8 ms | 1,782,583 |
| 32 | 10,240,000 | 69.9 ms | 331.6 ms | 7,130,335 |

这些是合成压力输入及投影函数耗时，不是常见会话的耗时估计。旧实现也有逐块遍历，但本次扩大每块解析范围使这一开销约增至 4–5 倍。

建议：在进入 Markdown 投影前分配整条消息共享的剩余预算，并限制块数、及时停止遍历。限制应覆盖解析输入和中间结果，而不只是最终返回字符串。

## 对其他模块的检视范围

- 虚拟列表只有 `ChatContainer` 这一处生产调用入口；非空列表一直走 Virtuoso，滚动容器在 layout effect 取得。删除前置普通列表没有改变消息气泡、工具审批、编辑、分叉、Goal 或 Hook 回调。
- 搜索投影的两个生产调用点是 renderer 搜索文档构建及数据库历史搜索；没有改变数据库结构、写入格式、IPC 参数或工作流/模型调度代码。
- 历史搜索仍保留 512 KiB 扫描预算，普通关闭搜索的逐 token 路径仍不建立搜索语料。
- 因此没有发现对其他模块业务协议的直接破坏；上面的同步渲染/索引卡顿会影响共享界面的响应，不能说“不会影响其他模块”。
