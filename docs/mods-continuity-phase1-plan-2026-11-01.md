# 第一阶段实施方案：贯通现有页面与能力

状态：architecture_review、delivery_review 两位 agent 已正式逐项评审通过后实施 A/B/C。已完成开发、窄回归和两个全新独立 medium agent 回检，均通过；结果见 [本阶段验收](mods-continuity-phase1-verification-2026-11-01.md)。

## 范围

落实 [既定路线第一阶段](mods-next-iteration-roadmap-2026-11-01.md)。只连接已经存在的页面、试用、配置和运行能力，不增加新 SDK/执行器/授权通道。原项目模式创建、配置、特性/需求管理和执行流程不变；不引入 AutoBiz 分支，不做附件媒体或其他多模态。不构建安装包、不触发 Actions，版本保持 2.0.0。

## 已核对的实际断点及措施

### A. 已安装插件到实际使用入口

1. `InstalledChatPluginUse` 仅以 Function Mod 或 Skill 判断入口就绪，纯传统 Hook/MCP 插件启用后可能显示“未找到聊天入口”，没有返回聊天的按钮。`PluginStartUseReport.chat` 也只投影这两类来源。
   - 在现有精确源码身份检查内补充只读声明摘要：Hook 数量、MCP 服务名称。只说明插件包含哪些规则/工具配置，不返回地址、命令、认证信息，不发起连接或执行。
   - 无 Function Mod 时，已启用、没有待处理 issue 且确有 Skill/Hook/MCP 声明，才能显示原配置入口和返回聊天；没有识别到任何入口时保留准确诊断。
   - 有 Function Mod 时仍要求原有源码授权、组件选择、应用/目录开关全部满足，不允许靠附带 Hook/MCP 绕过原门禁。
2. `InstalledPluginProjectEntry` 的原生项目子入口遗漏 `disabled` 透传；`ModsPanel` 的局部 gate 只覆盖传统项目声明。
   - 透传 busy/disabled，并在获得真实 `host-project`/`plugin-project` 类型后统一遵守既有 projectMode 开关。
   - 原项目创建表单、需求配置和执行命令完全沿用，不另建页面。

### B. 创作、依赖准备、试用和保存之间的衔接

1. 普通聊天功能保存复用后停在 delivery；再次修改生成新待确认候选时，窗口打开但不切到 trial，授权卡被隐藏且普通功能可能没有可达导航。
   - 新的精确审批身份到达时进入已有 trial 页；相同身份的轮询/刷新不抢用户页签。
   - 试用/保存导航在普通聊天功能中仍然可达。只调整页面导航，不代替用户确认或调用新执行器。
2. sourceSet 的 dependencies/needs-review/unknown 没有进入主“下一步”投影，实际依赖待办在 delivery，主区却让用户返回聊天制作；与普通聊天 trial 共存时依赖卡还可能被外层条件整体隐藏。
   - 活跃源码准备始终有可达的原卡，主步骤指向真实依赖安装、配置或原安装结果核对。
   - unknown 仅核对原结果，不自动重装或复用旧确认。
3. sourceSet ready 已经通过现后端形成真实候选及交付记录，但 UI 强制跳到保存，缺少明确的试用去向。
   - 去掉 ready 自动抢占页签。存在真实且当前的候选时，提供跳转既有试用/保存区域的按钮；按钮只导航。
   - 继续按真实 journey、candidateCurrent 和源码身份区分准备成功、试用通过、历史保存。未试用保存的旧规则保留，不新增强制门禁。

### C. 已启用功能到已有页面、侧栏和工具栏

1. 插件使用卡目前只发现 commands/panes；仅声明 platform surface 的插件正确启用后，卡片没有页面入口，只提示按插件说明触发。
   - 基于已经通过原生确认的真实 Function Mod 身份，发现现有 surface 目录。按 `ref.provider` 和 `source.digest` 精确匹配；不能误用整个安装源码的 digest。
   - 创作试用状态未暴露 provider 名时，只能以真实 activeDigest 在宿主目录解析唯一且来源自洽的 provider；有歧义拒绝。点击前再读现有 development.status，核对同一组件、目录和当前生效摘要；不猜 componentId 命名前缀，不增加后端字段或权限。
   - 复用一个前端入口组件：已安装插件的使用卡，以及确有 activeDigest 的创造者试用卡，都能看见本来源的实际页面/侧栏/工具栏入口。
   - 用户点击后，经一次性的、绑定账号/线程/目录/来源身份的前端导航意图进入现有 PlatformWorkspace，再用最新目录的 key/revision/openId 走原打开路径。多入口让用户选择，不能替用户打开任意来源。
   - 若目录冷且需要准备，用户明确点击“查找”后才调用已有 prepare，再读目录；已有目标入口时不因其他来源 canPrepare 而顺带准备。消费打开意图只读取最新目录并匹配原完整 key，不隐式 prepare。不自动启动 session、授权、应用组合或执行业务。没有独立页面时明确指出，保留原聊天/命令路径。
2. 顶部“打开扩展视图”实际只 prepare+refresh；准备后仍无页面时按钮消失，没有明确结果。
   - 按实际动作命名准备/加载入口，并提供无页面或不可用的说明与真实设置/聊天去向，不宣称已打开。
   - 现有 `catalog.errors`/行为目录 errors 不能被空状态隐藏；显示可核对的错误、重新读取和返回创作修复的去向。仅展示宿主已有诊断，不把错误当作授权或自动重试信号。
3. PlatformWorkspace 当前作用域只有 threadId/active，账号或同线程目录变化时旧 frame/目录可能暂留。
   - 让真实账号和工作目录参与前端作用域与挂载身份，失效旧意图及迟到响应。沿用原关闭/清理协议；旧 frame 的清理不能关闭新作用域中的页面。
   - 不把该组件强挂到项目模式、worker 或子会话；这些表面覆盖的扩展属后续独立方案。
4. 在已有按需作者目录补现有公共 surface 的准确 schema/短例，说明注册入口与 Pane 内容的关系及真实打开/关闭动作。只使已存在的能力可发现，不增协议、不把完整开发者底座整理提前到本轮。

## 保持已经正确的路径

设置目前是覆盖层，关闭后保留原聊天/项目详情。Native Feature 已有审批续跑、失败/取消重试、unknown 核对、待答复会话与恢复入口。本轮对这些路径做回归，不另建回退、迁移或运行框架。

## 分工和跨文件接口

- A：静态入口报告、已安装聊天/项目入口与现有 gate；拥有 start-use 相关共享类型、main 投影和 InstalledChatPluginUse/InstalledPluginStartUse/InstalledPluginProjectEntry。
- B：ModsDevelopmentPanel、creator-next-step、CreatorSourceSetCard，负责真实待办导航与状态投影。
- C：现有 PlatformWorkspace、精确来源的表面入口组件与前端导航意图，以及 App 中该组件的作用域接线。不新增 IPC 或 SDK。
- 根代理：协调入口组件接口与 A/B 集成，做跨页面连续场景、原项目流程回归、文档和交付检查。同文件由单一负责人整合，不并行覆盖。

## 必须通过的验证

| 路径 | 验证重点 |
| --- | --- |
| 纯 Hook/MCP、Skill 混合、Function Mod 混合、空插件 | 真实入口及必要设置可达；无连接/执行虚假成功；Function Mod 原授权不能绕过 |
| 聊天复用→保存页→修改→新待确认 | 授权卡可见、原批准接口只调用一次；同身份刷新不抢页签 |
| 源码导入→依赖→配置→候选→试用→保存 | 实际下一步和可点击按钮一致；与聊天 trial 共存不隐藏；unknown 不重装；旧版不冒充当前候选 |
| 已启用平台表面→发现→选择→打开→操作→返回 | 命令/Pane/Skill 为空时也有真实入口；区分准备与打开；无入口有准确反馈 |
| 来源/账号/线程/目录变化、撤权与关闭失败 | 迟到响应不导航/授予/误关新 frame，重开不自动重放未知操作 |
| 原项目和设置覆盖层 | 原创建/需求/配置/执行流程不变，busy 和功能开关有效，关闭设置回到原位置 |

先跑有意义的窄回归、真实 React/CSS 浏览器和类型/lint 检查；不重跑整套业务实现。完成后另启独立 medium agent 回检实现与路径，发现问题修复后复审。真实模型全流程和开发者底座整理按路线留到集中验收阶段；本轮不冒称完成它们。
