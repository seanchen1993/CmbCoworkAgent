## 一、先把 Mods 的意思说清楚

可以把 Claw 理解为“替你工作的助手”，Mods 则是“给助手换工作方法”。

以前，插件常常是一个额外入口：你调用它，它完成一件事。Mods 还可以参与助手原本的工作过程。例如，读项目规范时补充要求、调用工具前检查风险、给检视工作选择模型、完成后整理结果，以及在界面上显示自己的按钮和状态。[官方介绍](https://code.claude.com/docs/en/plugins/mods/overview)。

需要分清三件事：

1. **官方没有承诺“一切功能都已经变成可随意替换的模组”。** 部分内置功能已经采用模组，其他功能仍由产品本身提供。文件授权等重要确认，也不是模组想改成什么样就改成什么样。
2. **“能够定制”不等于“上传任意旧插件，里面的步骤就自动拆出来”。** 模组作者需要把可供选择的能力写出来。没有提供的能力，用户不能仅靠勾选得到。
3. **官方 Mods 不等于我们的 DIY 流程页面。** 官方主要让作者编写工作规则，借助插件安装和启用；我们的组件选择、流程步骤、模型选择和右侧 Claw 面板，是为了让使用者更容易操作而增加的产品设计。[官方制作说明](https://code.claude.com/docs/en/plugins/mods/create)。

因此，目标应是“能完成相同的定制工作，并且更容易使用”，不能只比较页面是不是一样，或者按钮数量是不是一样。

| 继续使用以前的 Plugin 项目模式 | 已做回检 | 本轮相关使用路径、原有任务执行方式、Autobiz 和流程执行均有通过记录。不能据此宣称所有历史功能都没有问题。 |

最容易误会的是：**已经能“给步骤选模型”，不代表已经能“由模组根据每一次工作的情况自动换模型”；已经能“写入检视要求”，不代表已经真的执行了检视和测试。**

## 四、还没有对齐的地方，分别影响什么

### 优先补齐：会影响常见的定制工作

| 差距 | 当前会遇到什么 | 为什么值得补 |
| --- | --- | --- |
| 项目规范的读取过程还不能完整交给模组调整 | 已能选择性调整真正送给助手的规范内容；但模组不能完整决定哪些规范文件怎样读取。 | 想按项目、助手分工使用不同规范时，读取过程的控制还不够细。 |
| 任务中的提醒和补充材料还未完整接入 | 可以改一部分工作规则，不能保证每一条临时提醒和每一类附件都能按组合处理。 | 长任务中新收到的要求，可能没有经过同一套定制规则。 |
| 更广的输入入口和输入建议还不完整 | 普通纯文字发送、执行中追加文字已支持自动检查、改写、补充背景和拒绝；带文件、图片或所选技能的输入、插件代发及远端入口没有按这套新方式接入。 | 需要统一处理富内容、自动代发和实时建议的模组仍需适配，不能只凭安装成功判断。 |
| 独立分析的其他使用选项仍有限制 | 独立分析、分类、利用当前对话进一步分析已经各自经过工作规则处理；仍有材料格式、长度和模型选项的边界。 | 常用文字分析已经贯通，依赖其他格式或特殊选项的官方模组还不能保证原样使用。 |
| 不变内容的重复利用还未完整对齐 | 已有部分工具和项目能力的重复利用；工作规则的复用和改动后及时更新还不完整。 | 长对话、大规则组合可能存在重复准备的开销，但不能预先保证收益大小。 |

已贯通的链路及范围以本轮使用说明为准。接下来优先解决规范读取和临时材料，再扩大常见输入入口；重复准备的开销需在正确性成立后优化。不能为了省时间，让已经修改或停用的规则继续生效。

### 同样需要迭代：会提高使用门槛

| 差距 | 对用户的影响 | 建议方向 |
| --- | --- | --- |
| 内置可选组件还少 | 10 月 3 日时，初次使用主要依赖找插件、上传。当前已提供无需上传的三个 Autobiz 流程，可先按上手说明体验。 | 更多自动参与聊天的组件仍需作者提供；现有项目功能可用，不代表都能拆成组件替换。 |
| 制作模组的引导还不够完整 | 作者仍要理解插件结构，使用者也不容易从一句需求得到可试用的组件。 | 打通“描述需求 → 生成草稿 → 看清作用 → 批准 → 试用 → 修改”的完整过程。 |
| 官方模组的安装兼容仍有边界 | 有的包能识别，但部分能力无法使用；如果只提示安装成功，用户会误以为已经全部生效。 | 安装前说明能用什么、缺什么；常见能力补齐后，降低改造成本。不能保证所有官方包都能直接使用。 |
| 保存、应用、运行几个动作仍容易混淆 | 用户可能保存后以为对话已经改变，或运行一次后以为以后都会自动执行。 | 明确显示“当前对话正在使用什么”，标出本次实际执行了哪些组件，解释没有执行的原因。 |

### 其余未对齐项：先判断是否有真实需求

以下也不是“已经完成”，但不宜压过前面的主要使用问题：

- **高级界面与声音**：终端中的特殊显示、朗读、声音播放，以及新版列出的选中文字能力。
- **更广的设置管理**：模组直接改变更多应用设置，以及像官方那样控制其他模组的加载和执行顺序。当前 Claw 自己的配置功能可用，两者范围不同。
- **更多助手协作方式**：任意自定义助手、更多共享工作方式、向未运行的对话送达消息并自动唤起工作。目前主要支持正在运行的已知助手和对话。
- **更细的模型使用选项**：不同模型的思考强度等选项尚未统一支持，不能把某一款模型的效果当作所有模型都具备。
- **更完整的对话资料处理**：模组参与更多对话记录变化、来源说明、连接状态和统计显示。目前能读取部分信息，不等于能介入全部处理过程。
- **更多外部服务和使用入口**：更多服务组合、图片等返回材料的处理，以及远端使用。当前支持的服务和桌面操作范围较明确。
- **跨项目的模组数据共享与高级扩展**：当前保存范围与官方不完全相同，模组之间的复杂依赖和连续输出也有差距。

完整逐项记录见[功能对照记录](mods-v2-compatibility-matrix.json)。这份记录供开发核对；上面的说明才是面向用户的影响判断。此处没有用一个“对齐百分比”掩盖关键能力是否真正可用。

## 五、哪些不同应当保留

并非每一处不同都需要照搬。

官方说明，模组可以在用户权限下运行，读取文件、环境信息、执行程序和联网；它并不是天然隔离的插件环境。[官方信任说明](https://code.claude.com/docs/en/plugins/mods/overview)。

本工程对文件范围、模型密钥、项目授权和关闭后的停止生效有更严格的约束。这些约束可能让某些官方模组需要改造，但**不应为了安装兼容而让插件直接拿到模型密钥，或越过用户批准的项目范围**。

同时应保留：

- 项目规定的完成条件作为底线，组合不能把它偷偷放宽。
- 没跑测试就显示“没跑”，失败就显示失败，不能用助手的一句“已完成”代替真实结果。
- 我们自己的模型配置和账号管理；它们不需要变成 Claude 的账号体系。
- 适合本工程的图形化组合和右侧面板，前提是用户看得懂、操作顺畅。

对这些差异，应说明原因和替代使用方式，而不是笼统算作“缺功能”。

## 六、接下来的迭代方向

下面是后续方向，其中本轮已完成的部分单独说明；其余仍是计划。

### 方向一：让工作规则贯穿整个任务

本轮已打通普通文字发送前的要求检查、执行中追加文字，以及独立分析自己的规则。下一步补齐项目规范读取、执行中的提醒和补充材料，再逐步扩大带图片、文件等输入的范围。

用户得到的效果：选择“严格检视”，从准备工作到最终结果都能看见它在起作用，不会只改变开场的几句话。

完成判断：更换规范文件、追加要求、停用组件后，后续实际工作立即反映变化；同时不能跳过原有文件授权，不能影响没有启用 Mods 的对话。

### 方向二：让模型和助手按工作内容配合

本轮已经为受支持的子助手打通逐次选择模型，独立分析、分类和利用当前对话进一步分析也已使用自己的规则。下一步补充真实组件示例，让用户无需自己编写判断规则，就能选择何时使用普通模型、何时使用检视模型。

用户得到的效果：同一个 Claw 可以根据实际需要选择普通模型或强模型，而不必把所有情况都预先拆成固定流程。

完成判断：运行记录中的模型与实际使用的模型一致；主助手和子助手分别验证；没有配置或不能使用的模型明确提示，不能悄悄换错模型。是否降低花费，需要实际测量。

### 方向三：让用户少准备，让旧插件更容易加入

增加常用内置组件和可直接体验的组合；为旧插件提供明确的改造说明；导入官方模组时，先检查本工程能否支持它用到的能力。

旧插件并非都必须改造。继续沿用以前的 Plugin 项目模式是一种选择；希望把某个功能放进 Claw，让用户与其他插件自由搭配时，才需要把它作为可选择的能力提供出来。

用户得到的效果：第一次使用就能选“只检视”“检视并测试”“失败后修复”，不用先理解插件内部结构。已有插件只需补充可选择的能力和必要输入，不必全部重写。

完成判断：新用户能从现有示例独立完成一次组合；两个不同插件的能力可以一起运行；缺失能力在安装和应用前说明；升级时保留能继续使用的选项，需要处理的地方逐项指出。

### 方向四：把制作、应用和使用讲明白

完善用自然语言制作模组的引导；统一组合页面和对话侧栏的说明，清楚区分保存模板、应用到当前对话、执行一次流程；在结果中标出哪些能力真的执行了。

用户得到的效果：知道自己改了什么、什么时候生效、怎样触发，以及为什么某一步没有运行。不同组合应该显示出实际行为差异。

完成判断：请未参与开发的人完成“制作或导入 → 组合 → 应用 → 对话中使用 → 修改后再试”，不依赖开发人员口头解释；取消、失败、升级和重新打开应用时也能理解当前状态。

四个方向应一起设计，避免各自形成一套操作方式；实现时先把规则和模型选择的基础做好，再接到页面。之后根据测量补齐内容复用。声音、特殊终端显示等功能先按真实需求安排，不为追求功能数量阻塞主要体验。

## 七、用 Autobiz 看清现在与目标的区别

### 现在就能体验的部分

在“自定义”中导入并启用 Autobiz 示例包，创建 Claw，选择组件和流程，为检视、汇报等步骤分配已配置的模型，保存后应用到当前对话。

然后在聊天输入区选择 **“执行流程”**，发送一个明确目标。可以比较三种组合：

| 选择的组合 | 真正发生的工作 |
| --- | --- |
| 只检视 | 读文件、指出问题，不自动测试或修复。 |
| 检视与测试 | 检视后运行项目测试，失败则停下。 |
| 修复与复检 | 先测试，失败才修复并重新运行同一测试；修复次数有限，仍失败就停下。 |

还可以让另一个插件负责最后的汇报，接收本次有效的检视和测试结果。这已经体现了“不同插件组合、不同模型分工”。操作步骤和示例位置见[用 Autobiz 实际体验 DIY Claw](mods-integrated-hands-on-2026-10-01.md)。示例项目本身仍有既有测试失败，不能把一次运行失败自动归因于 Mods，也不能删弱测试来制造通过。

**“运行已保存版本”是运行该流程一次。保存流程不会自动让所有任务结束后都做检视。** 如果要实现“每次完成都必须检视”，还要配置真的执行检查的组件或完成条件。

### 下一步希望达到的部分

例如创建“团队开发助手”：简单说明用普通模型，发现复杂问题时让子助手改用强模型；新收到的项目要求继续生效；完成前执行配置好的检视和测试，并明确展示结果。用户通过一次组合选择工作方法，普通任务也能按方法工作，只有确实需要固定顺序时才选择流程。

本轮已经打通已接入子助手的逐次选模型，以及普通文字发送和独立分析的规则。其他提醒、规范读取和更省心的制作引导仍要补齐；不能拿一次固定流程演示代表所有自动规则都已完成。

## 八、怎样判断下一版真的完成

验收要看实际工作，至少包含以下几类场景：

1. **组合有区别**：同一个 Autobiz 目标，分别使用只检视、检视与测试、修复与复检，实际行为和结果确实不同。
2. **组合能扩展**：加入另一插件的汇报能力，更换模型，主助手和子助手都按说明生效。
3. **变化能及时生效**：修改项目要求、升级组件、停用组件、重新打开应用后，使用状态正确，没有旧规则残留。
4. **失败说得清楚**：缺模型、缺组件、测试失败、用户取消时，指出原因；不把未执行的步骤写成成功。
5. **原有用户继续可用**：不开 Mods 的普通对话、以前的 Plugin 项目模式、原有任务执行方式和项目授权继续做完整回检。
6. **开销有依据**：用同样的任务比较准备时间和重复读取情况，能证明优化才写进版本效果，不只凭主观感觉。

本轮新增链路已有真实桌面测试通过记录，原有功能和全工程结果单独核对；已有测试与代码规范问题不能写成全部通过。详细结果见[本轮实现与验证说明](mods-devclaw-continuity-delivery-2026-10-03.md)及其中的最终测试记录。

## 九、版本汇报可以怎样说

> 本版本已具备 DIY Claw 的主要操作链：导入能力、组合不同插件、为步骤选择模型、应用到对话，并执行检视、测试和汇报。本轮进一步让组件自动参与普通文字发送和执行中追加要求，打通受支持子助手的逐次选模型及独立分析的工作规则。下一阶段补齐项目规范读取、临时材料和更多输入入口，并降低制作常用组件的门槛。旧 Plugin 用法继续保留，当前不宣称所有官方模组都能直接兼容。
