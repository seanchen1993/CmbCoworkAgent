# Design 网页交互抓取与长对话性能分析

日期：2026-11-13。范围：当前仓库代码审查、真实 Chromium 局部复现、真实 DesignRunManager / DesignSessionStore 压力测试。初次分析未修改功能代码；2026-11-14 的最少改动实施记录见末节。

## 结论

1. 网页导入实现的是当前时刻的静态快照，没有采集原站的交互流程。“基于此页面编辑”和“添加为页面参考”共用抓取结果，因而都有相同限制。
2. 除上述能力边界，还复现了已打开的原生 Dialog / Popover 状态丢失：这是当前可见状态保真不足，可以独立修复。
3. 长对话存在明确的前后端放大链路：逐字输入触发持久化，持久化处理全量历史，再同步完整快照、更新已读并重渲染历史消息。工具记录多时开销明显增加。
4. 以下耗时来自合成夹具，不是用户具体会话的现场性能记录；不能直接当成该会话的输入延迟，也不能把不同夹具的耗时简单相加。

## 一、为什么编辑和参考都丢失交互

### 1. 共用静态快照

`src/renderer/src/components/design/DesignView.tsx:2491` 的 `handleImportUrl` 无论用途，均发送 `source: current-browser`。用途分支发生在抓取之后：编辑把 `captured.html` 作为新设计基线；参考把同一份 HTML 放进附件。当前没有多状态集合、触发动作或状态间关系。

`src/main/services/design/page-capture.ts:70` 直接读取内置浏览器当前 WebContents，不刷新页面。这能保留当前浏览上下文，并不代表复制其运行时。

`src/main/services/design/page-snapshot.ts:49` 克隆当前 DOM，随后在第 178 行清理来源脚本，第 186 行清理 `on*` 事件属性。克隆也不会迁移 `addEventListener` 注册的监听器或框架内部状态。第 242 行的自有运行时只阻止表单提交和链接导航，没有重建弹窗、抽屉、菜单等业务交互。

因此存在三种不同情况：

| 场景 | 当前结果 | 原因 |
| --- | --- | --- |
| 弹窗尚未打开，内容按需挂载 | 无法获得弹窗内容 | 当前 DOM 中没有该内容，也没有执行采集动作 |
| 普通 DOM 弹窗已打开 | 通常能保留外观，按钮交互不迁移 | 当前 DOM / 类名 / 内联样式存在，原站运行时已移除 |
| 已打开的原生 Dialog / Popover | 可能丢失模态、遮罩、层级或整个可见状态 | 浏览器 top layer 状态没有被序列化与恢复 |

项目原方案 `docs/design-url-browser-capture-proposal.md:106` 已将产物定义为“可编辑静态快照”，并要求清理来源脚本。现在的能力与“完整获得页面交互”的用户预期有差距。同时，该方案第 62 行提出保留当前弹窗，原生弹层复现说明这部分还有实现缺口。

### 2. Chromium 实测

使用仓库真实 `extractDesignPageSnapshot` 和 `installSnapshotRuntime`，在独立页面加载快照后检查状态：

| 检查 | 来源页 | 快照页 |
| --- | --- | --- |
| 抓取前未打开弹窗，导入后点击按钮 | 原站按钮可打开 | 无反应，来源脚本已移除 |
| 已打开的普通 DOM 弹窗 | 可见 | 可见 |
| `dialog.showModal()` 的 `open` 属性 | true | true |
| Dialog 的 `:modal` 状态 | true | false |
| 原生 Popover 的 `:popover-open` 状态 | true | false |
| 已打开 Popover 是否可见 | 可见 | 不可见 |

Dialog 保留 `open` 并不等于保留模态展示；依赖 `:modal` 的样式和 backdrop 也需要处理。本次没有对所有组件库、跨域 iframe 或新窗口弹层作覆盖验证。

### 3. 建议实现方向

- 先补齐当前可见状态：采集原生 Dialog / Popover 的打开状态、布局和必要样式，在快照中恢复可见效果，或转换成等价的普通 DOM 弹层。明确哪些行为由快照自有运行时支持。
- 增加用户指定的多状态采集：默认页、打开弹窗、展开菜单、打开抽屉分别保存 DOM / 截图 / 状态名称，并记录触发元素与前后关系。
- 参考用途把状态集合交给模型；编辑用途以其重建本地交互，提供打开、关闭、遮罩、Esc 等可验证行为。
- 不把“保留原站全部 JS”视为直接修复：原运行时还依赖接口、路由、页面内存与资源环境，单独复制脚本不能保证运行。

验收应同时覆盖“当前打开状态可见”和“导入后可执行明确支持的交互”，避免仅以抓到了某段弹窗 HTML 判断完成。

## 二、长对话卡顿的完整路径

```text
textarea.onChange
  → setInputValue
  → updateTs：更新整个 DesignView，并立即排队发送 patch
  → IPC handler：manager.get 再取完整会话
  → manager.patch：再次克隆会话，重新映射所有消息
  → store.save：序列化会话、遍历全部消息并执行 SQL
  → commit：继续克隆完整会话，广播完整快照并返回完整结果
  → renderer：替换会话状态、刷新会话列表、渲染所有消息
  → markRead：再次克隆会话、调用完整 store.save
```

### 1. 输入与高频 UI 状态进入完整持久化通道

- `DesignView.tsx:5107`：每次输入调用 `setInputValue`。
- `DesignView.tsx:1588`、`:1604`：立即更新顶层状态并调用 session client `patch`，没有输入草稿合并保存。
- `session-client.ts:109`、`:169`：按会话串行排队，没有合并待发送的连续草稿。处理慢于输入时，请求会积压。
- `src/main/ipc/design.ts:2897`：处理 patch 前先 `manager.get(id)`，即使只是输入变化也读取并克隆整个会话。
- `src/main/services/design/run-manager.ts:291`、`:350`：patch 再次获取完整会话，并为全部消息创建对象。

缩放、选择元素、画布滚动等状态也使用相同 `updateTs` 通道。并非只有模型输出会触发这些成本。

### 2. 持久化仍遍历完整历史，已读又重复一遍

- `session-store.ts:200`：每次保存序列化完整的非消息 state。
- `session-store.ts:206`：每次遍历全部消息，逐条 `JSON.stringify`，执行 DELETE 和 UPSERT。
- UPSERT 有 `WHERE payload != ...`，能减少未变化数据的实际更新，但不能消除之前的遍历、序列化、SQL 调用和比较。
- `DesignView.tsx:1934`：每次应用新 seq 调用 `markRead`。
- `run-manager.ts:1125`：更新已读也执行完整 `get` / `store.save`，没有专用轻量 SQL 路径。

### 3. 完整快照反复复制与传输

`run-manager.ts:1174` 之后继续克隆完整会话并发布快照，IPC patch 本身还返回快照。当前订阅窗口会收到广播和请求回复；同 seq 的消息可被客户端再次接受并通知，虽然 DesignView 的 seq 检查会挡住重复应用。

已有优化会省略 revision 未变化的草稿 HTML，但历史 messages、executionEvents、正式 HTML 等仍在快照内。只限制可见工具条目数量，不能降低这些数据的复制和传输成本。

### 4. 历史消息没有虚拟化或组件缓存

- `DesignView.tsx:4776` 直接 `ts.messages.map`，挂载全部历史消息。
- `MessageBubble.tsx:515` 是普通函数组件，没有 memo。
- `MessageBubble.tsx:160` 的执行面板每次渲染重新扫描事件、构建结果映射和时间线。
- 每条消息最多显示 60 个工具调用 / 80 个文本事件，这是单条上限，不能限制整段对话的 DOM 总量。
- `MessageBubble.tsx:338` 在详情折叠时仍计算详情文本。
- `DesignView.tsx:1834` 在 messages 变化后读 `scrollHeight` 并滚到底部；完整快照会带来新的数组引用。
- `DesignView.tsx:1519` 订阅整个 `useAppStore()`，其他全局状态变化也可能触发这里重渲染。

单独增加 `memo(MessageBubble)` 可以改善本地输入更新，但后端快照克隆会更换所有消息引用。必须配合增量消息或保留未变化消息引用，才能让缓存持续有效。这里消息正文是普通文本，不能将问题笼统归因为 Markdown 渲染。

## 三、局部性能证据

### 主进程真实 manager / store

Node v24.14.0，内存 SQLite，消息交替为 user / assistant。每条 assistant 含 60 次工具调用及结果，每次结果约 2KB，文本参数使用与生产类似的简短长度摘要。3 次预热，12 次测量，以下为中位数。

| 总消息数 | 单次输入草稿 patch | 随后 markRead | 发布的单份快照约大小 | patch + markRead 的 db.run 次数 |
| --- | ---: | ---: | ---: | ---: |
| 10 | 5.30ms | 3.15ms | 0.70MB | 51 |
| 100 | 62.46ms | 33.80ms | 7.03MB | 411 |
| 300 | 182.81ms | 116.17ms | 21.11MB | 1211 |

这是工具记录较多的压力场景，结果用于证明随历史增长的成本。测试不含 IPC handler 额外 get、Electron IPC、前端渲染和文件数据库 I/O，不能据此报告用户现场的端到端延迟。

### 真实 MessageBubble 的 production React 夹具

独立父组件持有输入值，渲染真实 MessageBubble，消息引用保持稳定；每条 assistant 含 30 次工具调用。使用 `flushSync` 测量输入更新的 React 提交耗时，3 次预热、12 次测量。

| 总消息数 | 当前组件的更新中位耗时 | DOM 元素数 | 仅在夹具包一层 memo 后 |
| --- | ---: | ---: | ---: |
| 10 | 2.8ms | 2148 | ≤0.1ms |
| 50 | 13.9ms | 10708 | ≤0.1ms |
| 100 | 22.1ms | 21408 | ≤0.1ms |

这些数字不含完整 DesignView 工作、IPC、数据库和浏览器绘制。缓存实验只证明未变化消息存在可避免的重渲染，并不证明真实应用只加 memo 就能完成优化。

## 四、修复顺序与验收

### 第一优先级：解除输入与全量历史的绑定

1. 将 composer 输入状态放到局部组件；合并草稿保存，在发送、切换会话等边界显式 flush，并处理旧回复覆盖新草稿的竞争。
2. 已读改成仅更新已读游标 / 元数据的 SQL；游标未前进时跳过。
3. 区分 UI patch 与消息 / 产物更新；只保存变化字段和消息，避免每次草稿变化扫描消息表。
4. patch 返回轻量确认或增量变更，完整快照保留给首次打开和恢复。保持 seq、断线恢复和并发状态合并语义。

### 第二优先级：控制渲染、同步和工具历史体积

1. 使用仓库已有的虚拟列表能力显示可见消息；按消息 ID 保留未变化对象，配合 memo 和局部输入组件。
2. 执行记录默认摘要，详情展开再计算 / 加载。完整输出可独立存储，消息快照只携带摘要和引用，不以删除历史换性能。
3. 同 seq 去重、减少列表通知；全局 store 使用必要字段 selector；仅在用户接近底部时跟随滚动。
4. 生成流已有 100ms 聚合，但每轮仍经过全量成本，应一起改为增量处理，不能只调大节流间隔。

### 弹窗能力并行拆分

先解决已打开 Dialog / Popover 的可见状态，再建设多状态采集与交互重建。这是两个不同验收项，后者涉及模型上下文和产物交互能力，工作量显著大于补一个属性。

### 建议验收场景

- 10 / 100 / 300 条消息，分别覆盖纯文本、工具密集、长输出；记录输入到下一次绘制、主线程长任务、IPC 字节量及 SQL 调用次数。
- 不变历史增加时，草稿持久化和已读更新不再线性扫描历史；普通打字不触发历史消息重渲染。
- 虚拟列表 DOM 数量随可见窗口保持有界，展开详情和向上阅读不被流式更新拉回底部。
- 发送、快速清空、切换会话、停止生成、重新打开和断线恢复均保留正确草稿与消息顺序。
- 弹窗关闭 / 打开两种捕获状态，普通 Portal 弹窗、原生 Dialog、Popover；分别验证外观保留与声明支持的交互。

尚未采集用户具体卡顿会话的 trace 或测试全部网站，不能将某个单独耗时认定为现场唯一瓶颈。代码路径与局部复现已足以确认需要同时处理数据链路和渲染链路。

## 五、最少改动实施记录（2026-11-14）

本次保留现有 IPC、数据库结构、完整快照协议和消息列表布局，只调整 6 个功能文件：

- `page-snapshot.ts`：记录当前打开的原生 Dialog / Popover，快照自有运行时恢复对应 top-layer 状态，也覆盖开放 Shadow DOM 中提取出的弹层。关闭的弹层保持关闭，来源脚本仍然清理。
- `session-client.ts`：连续纯输入 patch 在停顿 300ms 后合并；发送、其他会话操作、显式 flush 和关闭会话前立即排队保存。空字符串也参与合并。对同 seq 的广播 / 请求回复去重，同时允许元数据事件之后补充同 seq 的完整快照。
- `run-manager.ts` / `session-store.ts`：已读只更新游标和 unread 元数据，不克隆历史、不重新保存消息；重复或倒退的游标不写库，写入失败不提前修改内存状态。
- `MessageBubble.tsx`：使用 memo 跳过输入时未变化的历史消息，工具详情只在展开后计算。
- `DesignView.tsx`：订阅必要的全局 store 字段，消息使用稳定 ID，历史消息不再跟随全局 liveOutput 状态切换。

同夹具复测结果：

| 检查 | 优化前 | 优化后 |
| --- | ---: | ---: |
| 100 条工具密集消息：单次已读更新中位数 | 33.80ms | 0.09ms |
| 300 条工具密集消息：单次已读更新中位数 | 116.17ms | 0.10ms |
| 100 条消息、引用稳定的 React 历史区：输入更新 | 中位数 22.1ms | 最大值 0.1ms |
| 客户端连续 30 次输入、最后主动 flush | 30 次 patch | 1 次 patch，保存完整 30 字符 |
| 已打开的原生 Dialog / Popover | 模态丢失 / 浮层不可见 | 模态与浮层打开状态均恢复 |

这些仍是局部夹具结果。单份草稿实际提交时仍走完整快照；模型流式输出时的全量同步、超长列表 DOM 数量也仍存在，本轮没有扩展到虚拟列表和增量协议。

验证：73 项相关单元测试、Node / Web 类型检查和生产构建通过；真实 Electron 登录态抓取、弹层状态、取消、导航竞争和独立离线导出通过；完整 React / Chrome 设计会话回归通过，覆盖导入、完整草稿保留、显式发送、直接编辑、撤销重做、后台恢复、问卷和列表排序。完整回归曾出现一次直接编辑点击等待超时，未修改源码的对照与当前代码复跑均通过，未修改无关编辑逻辑。

浏览器测试原来的异步 `waitForFunction` 并不会轮询等待异步布尔结果；对应草稿检查改为有截止时间的持久化状态轮询，以适配合并保存并避免读取尚未落库的旧值。ESLint 与 HEAD 对照未新增非格式诊断；仓库既有 lint 错误未在本轮扩展处理。

使用新构建后需重新抓取页面，旧快照没有原生弹层状态标记。尚未打开、按需挂载的内容仍需先在来源浏览器中打开；本轮不复制原站业务运行时，也不自动遍历多个交互状态。

## 六、长文本在输入框内编辑时卡顿的补查（2026-11-14）

用户进一步确认，卡顿发生在未发送的文字输入过程中。上一轮合并保存降低了持久化频率，但 `setInputValue → updateTs → setTabStates` 仍在每次按键同步触发整个 DesignView 渲染；技能/设计系统分组、附件信息、预览和其他子组件仍参与更新。输入框也默认启用拼写检查，中文输入法确认键没有单独排除。

本轮只追加修改 DesignView 的输入路径及现有浏览器回归：

- 文字由原生 textarea 即时编辑，最新值同步写入已有草稿 ref，并沿用 300ms 合并保存。普通文字增删不再触发工作区重渲染。
- 只有空白/非空状态变化、`/` 技能搜索变化时，才刷新依赖输入的界面。发送、技能选择、会话切换和恢复等外部更新仍会同步输入框。
- 普通发送和绘制标记发送均读取最新草稿，避免因减少渲染而发送旧文字；删除会把旧 React 状态覆盖回草稿 ref 的冗余 Effect。
- 关闭该输入框的拼写检查；输入法正在组词时，Enter 不触发发送。正常的 Enter 发送与 Shift+Enter 换行继续保留。

对照使用真实 DesignView、production React 和精简的宿主 API，分别测试约 900 字和 90000 字、分行与连续单行文本。每组执行 8 次输入：旧路径均触发 8 次工作区渲染，新路径均为 0 次，文本完整保留且没有页面异常。原生 textarea 与普通 React textarea 也作了对照；空白会话下约 9 万字没有复现明显的长停顿，因此不能据此把用户原始会话的严重卡顿完全归因于单一因素，也不报告端到端固定提速比例。

完整 React/Chrome 回归通过，并新增约 4 万字的实际编辑检查：连续输入不刷新工作区，光标保持在末尾，输入法确认不发送或清空草稿；立即发送读取最新文字。原有技能筛选、附件与模型选择、草稿携带/重开、直接编辑、撤销重做、后台恢复和排序均通过。Node/Web 类型检查、生产构建、差异检查通过，ESLint 与 HEAD 对照未新增非格式诊断。
