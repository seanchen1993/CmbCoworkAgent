# Mods 业务组装通用化实施与验证报告

日期：2026-10-19。开发范围：`codex/mods-v2` 本地工作树。本文承接《Mods 平台实现复核报告》，说明本轮业务组装边界调整。旧报告中“业务组装仍依赖 legacy 与 AutoBiz”的限制由本轮新增的 Host 组装路线继续补齐，旧报告其他结论不据此自动升级。本轮联合验收已完成，代码已先行提交推送，结果及限制见第六节。本轮继续暂缓 S6 阶段快照、隔离调试、回退及中间阶段重跑。

## 一、结论与实施范围

本轮将业务组装分为公共组装底座和受审执行适配器。公共底座复用来源校验、依赖闭包、资源打包、配置声明、扩展组合、安装事务和原生执行约束；AutoBiz 的组装投影、上下文生成、选择策略及特定协议识别归入适配器。新增“供应商准入”独立场景验证公共契约，不增加供应商或数仓名称分支。

本轮不是删除全部历史 AutoBiz 实现。既有 `harness-board` 服务、原 Python 执行协议和历史项目数据仍保留兼容职责；本轮重点是让公共创作与组装入口无需调用这些业务语义，也不将旧服务另行复制为新的通用执行器。

本轮提供两条明确的执行路线，不将既有业务名称替换描述为通用化，也不承诺任意流程引擎均已支持。

| 层次 | 本轮职责 | 明确边界 |
| --- | --- | --- |
| 公共组装底座 | 来源与独立插件身份、依赖顺序、资源闭包、配置合并、Skill/Function 扩展、冲突检查、组装锁与交付 | 不解释业务结论，不执行作者自定义的原生适配器 |
| `host-linear-v1` | 将业务 Mod 的阶段、产物、检查、动作与环境声明投影至原 Host 执行器 | 使用既有状态、检查、动作锁和审批；不实现任意 DAG |
| `autobiz-v1` | 保留既有 AutoBiz Python 执行、动态流程、上下文与必需校验 | 仍须通过原受审实现及资源准入，标签不能代替实际源码 |
| 业务插件与 Mods | 定义业务步骤、知识、配置、产物含义、前后依赖和具体规则 | 作者应定义有效检查和人工责任；静态声明不能证明业务正确性 |

适配器采用封闭静态注册，不允许插件通过文件路径注册任意宿主执行代码。旧 catalog 未声明 runtime 时保留兼容默认；未知适配器拒绝。已受审 AutoBiz 内核不能通过改标 Host 绕过旧规则。

## 二、平台公共底座调整

### 1. 公共组装不再解释 AutoBiz 流程

`business-mod-assembler.ts` 负责通用选取、依赖、资源、身份、配置、扩展和锁。公共注册表只选择适配器、检查身份冲突并提供运行模式元数据；board 投影、必需 Hooks 和已验证产物导出协议由 AutoBiz 适配器负责。

Host Mod 的 `host` 字段复用既有 `ProjectRuntimeManifest` 解析与校验，不另建执行状态机。阶段 ID 使用 Mod ID，Skill 使用真实入口完整路径；未绑定检查、未检查的必需产物、冲突引用及不受支持的旧 validators/guards 会被拒绝，避免组装后静默丢失原保证。

### 2. 资源贯穿创造者与交付链

受检查的 Host 候选通过完整路径清单与文件摘要核对后，进入原项目创作会话和原生试用入口。附加知识、引用和配置资源随草稿持久化、开发快照、重启恢复、试用快照及 ZIP 导出保留。这里的快照是既有源码冻结机制，不是暂缓的 S6 阶段状态快照。模型不能自行扩大由主进程授予的资源读取清单。

公共 catalog 支持具体文件和目录前缀；目录在包内有界展开，缺失或空声明拒绝。路径穿越、敏感文件、链接及硬链接继续拒绝。创造者文本资源捕获继续采用原限制：32 个文件、单文件 64 KiB、总计 256 KiB、深度 8、遍历条目 128。这是该捕获入口的范围，不是所有 catalog 或来源快照的统一容量；本轮不将其扩展为任意二进制资源打包。

来源改变、文件缺失或候选摘要不符时拒绝试用。准备试用仅生成待确认请求，实际启动继续使用原生批准；重启恢复源码和来源记录，不恢复旧执行权限。Host 试用保留创造者候选来源关联，不先安装候选，也不另建执行器。

### 3. 消除文件名触发业务语义

复查发现：旧准入逻辑可能仅凭 `board_core/board_config.json` 存在便套用 AutoBiz 规则。现依据有效运行声明、旧上下文桥接契约及显式适配器声明区分路线。普通 Host 插件可以包含同名普通资源，不会被解释为 AutoBiz；既有 Python entry 上下文、旧执行路径和显式 AutoBiz 规则仍受原检查保护。

无运行声明的历史包仍保留保守上下文保护，该兼容回退不授予受审协议权限。完整、有效的 Host 业务 catalog 可以在尚未生成执行清单时识别为 Host 来源；非法运行声明不能回退到 catalog 绕过准入。所有声明的流程入口均参与校验，默认 Host 入口不能掩盖第二个 legacy 入口。

同步安装与异步快照检查复用相同分类语义；异步检查只解释同一份受观察源码，避免重新读取磁盘将不同版本混用。普通资源的存在性探测保留原路径、链接、文件描述符和父目录身份检查，不为分类读取整份业务内容。

项目阶段 Skill 的隔离标记与旧 board 项目入口分别处理：Host 阶段仍属于项目 Skill，但不会因此出现旧“新建此插件项目”按钮，也不会进入旧适配器注册表。旧服务的直接创建及已有绑定同样检查实际执行协议，界面隐藏不能代替后端校验。合法的 Python entry 知识提供器仍可独立保留其 board 上下文。

安装后的组装与衍生面板复用入口识别组件，依据实际安装信息和原生模板选择路线，不依赖预览结果猜测。Host 插件引导至既有“本地项目任务”，旧插件保留原项目入口；卸载、停用、模板失效或会话范围变化时不得继续跳转。该调整复用原项目能力，不增加业务执行器。

通用流程目录中的 AutoBiz 阶段候选属于可选发现来源。该状态文件损坏时显示有界诊断，其他动作与流程仍可配置；原生阶段准备、校验、提交和会话范围锁继续严格执行，不将可选发现失败转化为执行放行。

## 三、AutoBiz 连贯性与校验保留

| 关注点 | 本轮处理 | 保证范围 |
| --- | --- | --- |
| board 配置与环境替换 | 原上下文实现迁入适配器，保留完整配置克隆、部署单元、`DEVCLAW_*` 环境和原 Python 调用 | 不将原 board 简化为普通提示词，不丢弃未被投影的配置 |
| 知识库 | 保留外部知识只读绑定、宿主管理的可变缓存、必需知识及来源检查 | 文件存在不等于已加载；来源变化后旧执行身份失效 |
| Hooks | 保留原 Hook 身份、必需 Hook 要求及实际原生运行 | 模型自报成功、静态预览和适配器名称不能替代 Hook 结果 |
| 产物衔接 | 保留原 validators、guards、必需输入、checkpoint 及可验证产物协议 | 声明的上下游依赖与原业务校验继续适用，不自动推断任意新步骤语义 |
| 完成证据 | 通用捕获接收可信内部调用方明确提供的引用；AutoBiz 适配器提供自身状态布局 | 文件指纹不等于业务 PASS；未新增无限制公开 Guest 文件引用 API |

原上下文实现迁移后的词法序列已与基线核对，原 legacy preflight 函数体保持等价。旧原始受审资源与锁的校验未放宽：新增显式 runtime 仅接受精确 AutoBiz 声明，额外字段及其他适配器不能被宽泛忽略。

本轮新增的 Host 业务组装适配器明确拒绝仍依赖 board 的旧 `contextProvider.entry` 和旧已验证产物输出选项。既有支持 entry 上下文的原生包仍保留原准入与保护，不因本轮改动而放开。普通 Host 业务可通过声明资源、原配置工具和原文件工具消费知识；不能借用旧声明获得隐含权限。

## 四、独立场景：供应商准入

示例源码位于 `examples/vendor-onboarding-mods`，用户自定义资格审核 Mod 位于 `examples/vendor-qualification-mod`。两者使用公共 `host-linear-v1` 契约，不依赖 AutoBiz 研发阶段、部署单元或 checkpoint。示例刻意包含普通业务资源 `board_core/board_config.json`，其内容采用供应商资料格式，用于验证同名文件不会触发 AutoBiz 解析；该资源与真实知识规则均须完整保留。

基础插件由“资料整理→最终报告”组成。加入资格审核 Mod 并明确顺序后，形成“资料整理→资格审核→最终报告”。普通 Function Mod 提供原生用户配置读取；规则文件随包保留。资料阶段产生 `dossier.json`，审核阶段实际读取资料并产生 `qualification.json`，最终阶段实际读取前序文件形成报告。

源码集成测试同时验证基础与增强版本的依赖闭包、检查、安装、原编译器发现、导出和源码往返。包级用例进一步检查配置工具的真实结果、知识规则规范化全文、实际文件读取与写入、原生批准、原 Host Schema 凭据及错误产物阻断，最终新包执行结果见第六节。资格审核失败时不得推进，冻结 Mod 源码保持不变，重试当前失败阶段并修正错误产物后再继续；这属于既有失败重试，不是 S6 回退或修改 Mod 后从中间阶段重跑。

依赖不等于数据映射语言。插入新步骤后，作者仍需声明依赖、消费者实际读取位置和有意义的检查；平台不会自动判断不同业务文档是否语义一致。

### 新业务接入时分别修改什么

| 责任方 | 接入工作 | 本轮独立场景中的实际落点 |
| --- | --- | --- |
| 业务作者 | 定义内核版本、模块、资源和配置，选择现有执行契约 | `examples/vendor-onboarding-mods/mods/business/manifest.json` |
| Mod 作者 | 提供真实 Skill、依赖、阶段声明、产物及检查；按同版本 `kernelRef` 加入 | `examples/vendor-qualification-mod` |
| 知识与策略维护者 | 维护随包规则及配置含义，明确人工审核责任 | `knowledge/admission-policy.md`、普通 Function Mod 的 `policyTier` 配置 |
| 组合使用者 | 选取模块、核对顺序和依赖、检查并生成独立插件，按目标环境重新配置和授权 | 业务 Mods 组装、原生安装与本地项目任务 |
| 平台维护者 | 维护公共契约、安全边界和执行能力；仅当现有通用能力确实不足时扩展底座 | 本例不新增供应商专用状态、工具、分支或执行器 |

因此，已有线性执行契约能够表达的新业务，主要改变插件与 Mods 源码。新增全新执行引擎、未支持的动作语义或任意 DAG，仍需要公共能力设计及审查，不能通过一个业务标签自动获得支持。具体字段与接入步骤见[业务 Mods 组装开发指南](sparks/business-mod-assembly.md)。

## 五、实际收益与仍有的限制

1. 新线性业务可复用公共执行、配置、权限和交付能力，不再被迫模拟 AutoBiz。业务作者的主要工作转为编写 Mods、Skill、声明资源与检查，而非增加平台业务分支。
2. AutoBiz 保留既有业务保证，通用化不以删除校验换取“可组合”。公共机制与旧业务适配的责任可以分别审查和演进。
3. 创造者候选的知识和其他资源可随保存、试用与导出保留，减少因打包遗漏造成的环境差异。配置值、密钥、安装身份与批准不随导出迁移，跨机器须重新配置和授权。
4. 显式输入、实际工具结果和检查凭据提高执行过程的可核对性，但不证明真实业务判断正确，也未建立 token 节约或全局性能提升的量化结论。

仍有明确边界：适配器由平台受审维护；任意新 Python 引擎尚不能仅靠标签接入；Host 仅覆盖现有执行器支持的线性合同；动作仍需原动作锁与实际授权；文本资源仍受原有界限制；可选 AutoBiz 本地 Git 来源策略仍存在于兼容适配器。独立示例随仓库和本地验证产物提供，本轮未新增面向所有业务的模板市场或自动语义迁移能力。

### 历史记录与复验原则

新增 Host 集成用例首轮超出默认 5 秒。拆分用例后，最后一个覆盖四次真实 Host 操作及数据库、快照、输入核对的新用例采用明确的 15 秒预算；其他新用例仍采用默认期限，生产期限和既有测试期限未延长。这是集成测试范围的说明，不是性能改善结论，原失败记录保留。

首次完整回归发现旧能力目录用例仍要求明确 Host 插件因同名 board 资源而被禁用，与本轮修复目标冲突。确认原因后停止该轮并保留失败日志，将旧拒绝断言的 fixture 明确设为 legacy，另增 Host 同名资源可用的正例。修正后 3 文件、27 项专项通过。该次调整仅涉及测试文件，当时核对的生产源码及包字节未变。

第二轮完整回归期间，扩大入口复查又确认安装兼容性、旧项目列表与直接服务入口、可选流程目录等位置仍有同类耦合，因此主动停止该轮。该轮未作为完整通过记录。后续已统一修复生产代码并复验对应专项；最终新包的两条实际流程与完整回归均已通过。专项还发现旧目录缓存的大批量测试超时，以及两个新增 fixture 不完整，分别核查实际读取开销和 fixture 契约，不延长既有测试期限。

目录修复仅共享单页内的协议观察，跨页仍重新核对；有界枚举超限时回退至原安全读取，大小写与目录变化另有回归。安全 board 探测延迟至选中行的缓存与解析之前，避免对每页全部候选重复打开文件。专项中原大批量用例从先后 9.6 秒、5.6 秒降至 3.2 秒，并在原 5 秒期限内通过；该数据只代表此回归环境，不外推为整个应用性能提升比例。

中间打包曾因复查发现同名资源耦合而主动停止，未作为验收通过记录。最终普通构建与 NSIS 打包已在新目录完成；编译输出与 ASAR 的主进程、preload 一致，21 个技能文件的清单与字节一致，未包含测试桥接入口。两条实际包流程及最终完整回归均已通过；未覆盖现有安装目录。

第三轮完整回归发现既有兼容性测试将可变 `HEAD` 的解析器当作旧客户端解析器，而该版本已支持新配置迁移标记，导致原拒绝断言失效。停止本轮并保留日志后，改为保存、核对字节数及 SHA-256，并通过原 VM 执行迁移能力引入前的真实历史源码。原有拒绝和接受断言均保留，测试不再依赖本地 Git 历史。此次仅变更测试与溯源 fixture，生产源码、构建产物和已验证 ASAR 保持不变；专项通过后重新启动完整回归，取消轮次不计为通过。

第四轮完整回归已结束，1,506 个文件通过、8 个失败、8 个跳过；15,020 项通过、15 项失败、56 项跳过，源码前后摘要一致。14 项为原时限内的超时失败，其中一项还出现超时后的临时目录清理占用；不能仅凭运行较慢就排除问题。记录到 Silent 电源方案及 CPU 频率计数后，用户切换为 Turbo，已记录变化；因环境变化与运行阶段交织，尚不能据此断言全部超时的原因。

另一项失败明确定位为本轮生产校验顺序回归：完整受审库存检查前移，遮蔽了旧包缺失必需 agent 的原诊断。旧 12 ZIP、原集成测试和受审规则保持不改；本轮独立测试和静态检查结束后，已应用独立静审的最小修复。所有入口元数据仍先验证，必需 agent 闭包随后检查，完整受审库存仍严格拒绝未受审包。新增四项同步/异步回归，与前轮全部失败组及相关契约检查合计 12 文件、232 项在原时限内通过；这属于修复及运行条件变化后的专项复验，不将原失败记录抹除，也不据此认定全部超时的原因或宣称应用性能改善。修复后的新包、两条实际 SDK 流程及不筛选的完整 Vitest 均已通过；其余最终检查结果见上表。
