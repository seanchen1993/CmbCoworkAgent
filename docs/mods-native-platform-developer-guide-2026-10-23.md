## 这次改造解决什么问题

以前，插件需要同时教模型完成业务、调用脚本查询进度、写状态文件、检查产物、等待用户确认，并处理执行中断。每个插件容易重复实现这些控制逻辑。用户看到模型说“完成了”，还需要确认文件是否真的生成、状态是否写入、下一个步骤能否读取。

现在，插件声明每个阶段使用哪个 Skill、消费什么产物、生成什么文件、运行哪些检查、何时需要用户确认。平台根据实际执行记录和文件内容推进任务。Mods 可以通过统一接口读取运行状态、提供业务检查和知识筛选、发起受控工作流，以及定制展示。

例如，在 AutoBiz 前面加入“需求转换”：作者增加一个模块，声明转换结果的格式，再把 PRD 模块的输入指向它。通用编译器检查引用和契约，平台执行转换、检查结果并将真实产物交给 PRD。作者仍需说明“转换正确”的业务标准；平台不会从阶段名称推断需求是否完整。

## 平台和插件分别负责什么

| 事项 | 平台负责 | 插件负责 |
| --- | --- | --- |
| 执行任务 | 权限、取消、执行身份、错误和结果记录 | Skill 中的专业方法与任务要求 |
| 阶段推进 | 校验当前版本、真实检查记录及审批，再保存状态 | 阶段顺序、输入输出、业务完成条件 |
| 产物检查 | 安全读取实际文件，运行声明的检查，保存检查对象和结果 | 文件结构、需求覆盖、业务规则及反例 |
| 知识加载 | 授权目录、配置隔离、读取范围、变更核对 | 哪些资料适用当前任务，如何筛选和组织上下文 |
| 多工作树协作 | 原有工作流、资源身份、取消恢复及合并审批 | 角色、任务拆分、批次依赖和评审方法 |
| 执行时限 | 保存原开始时间、核对实际命令启动、阻止过期结果提交 | 何时开始计时、首次执行时限、总时限和单条命令时限 |
| 运行展示 | 提供授权后的状态与运行事实 | 展示哪些指标、怎样组织视图 |
| 插件生成 | 编译、诊断、试用与交付接口 | 模块和规则的具体内容 |

公共执行代码不依赖 AutoBiz 的业务阶段名称、知识库目录规范或业务字段。新路径使用统一作者契约。既有兼容适配代码保留，用于原插件入口；这不意味着历史适配器已全部移除。

## 状态到底由谁推进

以“需求说明完成”为例：

1. 平台记录本次执行的项目、阶段、插件版本和输入身份。
2. Skill 引导模型读取前序产物，生成真实需求文件。
3. 平台读取文件，运行声明的结构检查和业务检查。
4. 阶段要求人工确认时，用户确认的是这一版实际成果。文件变化后，旧批准不再适用。
5. 条件全部满足，平台在原状态存储中提交阶段变更。重复请求、旧版本请求和过期检查不能再次推进。

模型可以提出继续请求，但不能用一句“已完成”代替检查。Mod 通过公开接口请求操作，也不能直接写平台数据库或代替用户批准。Skill 不再需要调用旧外层脚本修改 state.json。

业务对象仍可以由插件维护，例如需求条目、测试分类和部署单元。平台只拥有通用运行状态，不把每种业务对象都内置到主程序。

## workflow 阶段的公开动作与失败边界

显式声明为 workflow 的 Host 阶段仍通过同一公开动作入口加载上下文和执行检查。主进程仅在原 action scope 活跃、线程与项目/操作绑定精确匹配且当前授权检查通过后，将传给动作选择器的 metadata 复制视图投影为 normal；原线程 metadata 与模型模式仍为 workflow。普通 workflow 会话、跨线程请求、remote/parent 等限制没有放开，插件无需改为普通模式绕行。

上下文 provider 的“已尝试派发”标记现在紧邻原 startSaved 调用之前设置。selection、材料或定义准备失败且尚未尝试派发时，只有通过原权限、精确 owner 和物理退休守卫才记录 failed；一旦尝试 startSaved，或退休不能确认，仍保留 unknown。此修复只影响新的执行，不追改旧 unknown，也不授权模型自动重放。

## Mod 怎样请求当前项目继续执行

已授权 Mod 通过 `native.project-runtime` 的 `project` 能力操作当前会话绑定的任务。调用顺序是 `inspect` 读取状态与检查记录，`preflight({kind: "continue"})` 核对条件，再把返回的 `planId` 交给 `request({planId})` 打开原生确认。取消和结果核对分别使用 `cancel`、`reconcile`。

预检计划绑定原调用方、工作区和任务版本，有效期为五分钟，并按一次性请求处理。获得 `planId` 不表示已经获准执行；Mod 不能通过传入其他项目编号、任意路径或状态值改变目标。成果批准、输入回答、版本迁移和旧项目导入仍使用各自的原生界面。

公开接口复用原执行器、权限和存储。插件作者不需要再创建第二套工作流引擎、任务状态库或合并审批系统。

阶段的 `executionMode` 默认是 `normal`。需要模型使用原工作流工具的阶段必须显式声明 `executionMode: "workflow"`，并经冻结声明、来源绑定及原权限核对；普通阶段不会因此自动获得该工具。后台工作流完成后，由原 Host 核对实际运行身份和物理结算通知，在同一操作、同一来源下续接结果模型轮。工作流启动后的提问只支持原 live 续接，不承诺应用重启后自动重放已经发生的副作用；无法证明结算时仍保留未知。

材料接口只服务当前 Host 上下文准备过程，普通 Mod 不能据此随意读取用户目录。工作流资源使用平台已经授予的工作区引用；资源间合并限同一运行、同一仓库，并保留原生审批。目前不支持将资源直接转交另一阶段，也不会自动重试结果不明的外部操作。

合并后检查使用原运行的工作树标识与实际合并提交，而不是接受插件任意指定目录。平台在进入检查、用户批准后和发布成功结果前核对仓库身份、提交及已跟踪文件是否变化。已经封存的工作树不会因此重新获得代理写入权限；检查期间发生变化时，平台拒绝把结果记为成功。这样，多仓库插件可以分别验证各仓库成果，同时继续使用同一套公共权限和结果记录。

执行时限也区分公共机制和业务策略。插件声明一个预算的首次命令时限、总时限和单命令时限，平台将开始时间保存在原工作树记录中。重新打开任务或重复声明同一预算不会重新计时；真正的进程启动回执才能证明已经开始执行，模型说“开始测试”不能代替它。到期后停止新增副作用并拒绝迟到的成功提交，查询、失败结算和清理仍可进行。AutoBiz 的具体分钟数写在插件工作流中，平台不识别 AutoBiz 的阶段名称。

原生审批等待与执行总预算是不同边界。可信审批及受控队列等待可以暂停所属 Guest 调用链的软期限，同一祖先链累计最多 15 分钟；这不延长 CPU 配额、进程执行超时、Flow 总预算或工作树绝对期限。Flow 的总时限仍包含等待确认，长时间未处理审批可能在进程启动前耗尽预算，并使检查结果保持 `unknown`。进程启动数为零只能证明该子进程未启动，不能证明整个检查动作没有其他副作用，也不能据此自动重跑。

## AutoBiz 插件具体怎样变化

新源码位于 `resources/native-compositions/`。业务规则、知识选择和 Code 编排仍在插件资源中，不写进通用 Host 服务。

| 插件文件 | 用途 |
| --- | --- |
| `autobiz/composition/source.json` | 描述模块顺序、输入输出、检查、配置和成果确认；这是作者主要编辑的组合源 |
| `autobiz/modules/*/SKILL.md` | 说明每个阶段如何完成业务，不负责修改外层平台状态 |
| `autobiz/workflows/native-code.workflow.js` | 定义 Code 内部工作流和协作顺序 |
| `autobiz/knowledge/` | 随插件分发的方法资料；组织知识通过用户配置绑定 |
| `autobiz-rules/mods/main.ts` | 将业务规则暴露为可授权、可调用的 Mod 动作 |
| `autobiz-rules/checks/provenance.json` | 记录提取规则的原始文件与摘要，支持核对迁移来源 |
| `autobiz-knowledge/mods/main.ts` / `selector.ts` | 入口按当前阶段选择方法资料，选择器按部署单元与资料边界筛选组织知识 |
| `devclaw.source-set.json` | 在集合根目录声明项目源码和独立依赖目录，使使用者通过一个入口完成准备；不携带开发机安装身份或批准 |

编译产物中的 `devclaw.project-runtime.json`、`devclaw.project-actions.lock.json` 和 `composition/lock.json` 由编译器生成。作者修改源契约后重新编译，避免同时手工维护多份顺序和引用。

Hooks 需要按作用分别处理。原来负责外层状态推进的 Hook 由平台阶段事务替代；检查业务产物的规则变成声明式检查或检查 Mod；知识加载改为上下文提供器；工具调用前的写入限制仍需在实际工具执行边界约束。不能把任意 Hook 删除后称为已迁移，也不能认为把脚本包进 Mod 就自动保留了原事件语义。

## 普通用户怎么使用

1. 在创造者工作区的“保存为插件并复用”区域点击“选择作者源码目录”，选择带有 `devclaw.source-set.json` 的完整源码集合。AutoBiz 对应本仓库的 `resources/native-compositions` 目录。
2. 界面逐项显示依赖名称与版本；点击“安装此依赖”，再通过各依赖原来的使用入口完成启用和权限确认。权限不能由源码集合替用户批准。
3. 点击“核对权限并准备模板”，系统使用本机实际安装和授权身份编译项目，随后在交付卡确认安装模板并点击“开始使用”。不需要填写内部 Mod ID 或复制开发机锁文件。
4. 从项目入口选用已安装模板，填写任务目标和工作目录。组织知识及其他目录在配置入口绑定，不带作者电脑的默认路径。
5. 在项目内的权限与配置卡核对主包及各项检查、动作和上下文依赖。完成必填配置，逐项勾选确认并批准所需依赖；全部就绪后再启动任务，查看当前阶段、真实检查结果及下一项待办。
6. 使用“连续执行至下一确认点”执行允许自动继续的阶段。系统会在需要输入、批准、出现失败或结果不明时停下。
7. 需要补充信息时，在阶段会话中回答输入卡片。支持续接的执行保留原问题、回答和操作身份，避免从头重复已经完成的工作。
8. 需要成果确认时，查看实际文件和检查后接受或拒绝。需要修订时先填写“修改意见”再拒绝，随后显式点击“按修改意见重新执行”。拒绝不会推进阶段。

### 在当前项目补齐依赖权限

项目权限卡分别展示主包与当前保留动作锁声明的依赖，包含名称、来源摘要、动作和所需权限。仅含配置的主包不运行 Function VM，但它依赖的检查或知识 Mod 仍可能需要单独授权。主包就绪不能代替依赖就绪；必填配置、全局与当前工作区开关、各项依赖授权均满足后，界面才允许继续启动。

需要授权的依赖逐项确认，配置沿原配置入口保存；批准只适用于主进程核对的精确来源及当前工作区。依赖缺失、停用、源码变化或无法编译时，卡片说明原因，不自动安装、启用或批准另一份源码。先经原安装或设置入口解决问题，再回项目核对。切换项目、版本或来源后，旧界面的迟到响应不能使新项目变为就绪。

**批准依赖、批准具体命令、接受阶段成果是三件不同的事。** 依赖授权不代替随后进程的原生许可、Git 集成确认或成果审核。源码集合准备时的授权也不能保证另一工作区已获授权。该项目内补齐入口已通过真实后端和浏览器夹具回归，当前新增界面的构建后实际应用验证仍以动态验收记录为准。

### 拒绝成果后按意见修订

修改意见最多 4,000 个 UTF-16 代码单元，随原拒绝记录保存；接受成果无需填写。已保存的拒绝决定和意见只读展示，不能用第二次点击改写。未保存文本随项目、阶段或操作切换清空。

“按修改意见重新执行”仅适用于已成功结算但成果被拒绝的当前操作。它先沿原取消入口结束这次操作，再准备并启动新的操作；原成功检查、拒绝意见和历史记录保留，不被覆盖。新操作仍需通过全部检查及必要审批，意见只是修订输入，不增加权限。未知结果不能使用这个按钮重跑；导入后仅验证已有字节的阶段也不提供这一重写入口。

### 失败阶段的下一次尝试需要额外说明时

当前阶段最新操作已明确 failed、且没有活动或 unknown 操作时，可填写“本次阶段补充说明（可选）”，再显式点击“开始当前阶段”。最多 4,000 个 UTF-16 代码单元，后端同时限制 16,000 UTF-8 字节。填写非空说明后，连续执行和仅检查入口禁用，避免漏传；没有说明时保持原使用方式。导入后仅验证已有字节的阶段不提供该输入。

说明通过原 `prepare.stageInstructions` 随新操作保存，历史记录可只读查看；准备失败保留输入，确认准备成功后清空。切换项目、版本、阶段或失败操作会清空未提交文本。说明不附加到旧失败记录，不改任务 goal、来源、审批或检查；新操作仍须按原流程执行。unknown 不能借此强制重试。说明仅交给主阶段作为本次修订要求，不成为子代理自动继承的目标。

此入口已通过针对性后端、真实 React 浏览器夹具、官方 Node/Web 类型检查及正常构建。实际项目已通过界面向新的 Design 操作提交并冻结 972 字符说明，旧操作未变；模型已据此修订测试方案，第三次 Design 完成原生审批及两项原检查，经人工接受后推进。Plan 后续因完整文件35,909字节超过原28,000 UTF-8字节上限，在输入捕获时停为 unknown、terminal=null；输入成功、单阶段通过与完整流程须分别核对，完整流程及独立 HTTP 验收仍未通过，详见动态验收报告。

Plan 作者须按公开 Skill 的精确枚举和结构编写，生产任务与独立测试作者分工不混用，首批必需的 POM 入口不能拖到后续批次；每个内文≤20,000 UTF-8字节，完整 bundle≤28,000字节。补齐后的教学例、原 checker/命令策略与通用输入边界4文件120项及真实 React 输入准备界面已通过；R4 新作者版前五阶段已由真实模型及原检查推进；Plan 曾因模型服务余额不足、验收引用格式错误而失败，模型修正后通过。Code 入口的 workflow 动作作用域问题已修复，但原 unknown 不因此解锁或转为成功；增强后的混合八阶段及独立供应商 2/2 通过；这不改变 R4 的真实 unknown，也不代表在线模型完成 Code。

### 主阶段与受委派子任务的边界

Host 主执行者接收当前阶段目标、产物要求和修订意见。通过 `task` 委派的子代理只继承冻结的项目背景、知识和约束，并执行该次明确的委派；不会把“完成整个阶段、写全部产物、修复全部反馈”自动当成自己的目标。系统提示与 Mods 的任务上下文两条通道均遵守这个边界，普通非 Host 会话维持原行为。

这不取消 AGENTS、必需上下文、来源及工具权限限制。只读 Explore 子代理仍不能写文件，也不能通过更换命令参数获得被禁止的执行能力；需要写入或运行测试时，应由具有相应权限的执行者按原流程完成。子代理的文本结论不能代替检查回执、成果批准或阶段推进。

源码集合入口正在接受本轮联合验证。已有插件继续使用原安装与项目入口；熟悉作者工具的开发者也可分步安装依赖、编译和试用，然后按上述第 4—8 步使用。

作者在集合根目录提供以下声明即可沿用这一准备流程；目录名是示例，不是平台内置业务标识：

```json
{
  "protocol": "devclaw.project-source-set/v1",
  "title": "我的业务模板",
  "goal": "按照声明的阶段与检查交付业务成果",
  "project": "project-template",
  "dependencies": ["quality-rules", "knowledge-selector"]
}
```

项目目录保留统一组合源；依赖目录各自是正常的 Function Mod 插件。当前最多八个依赖，依赖源码累计不超过 32 MiB；项目仍使用原作者源大小限制。此入口不接受含 MCP、Hooks、Skills 等其他注册类型的依赖包，也不取代任意旧插件的首次模块化适配。

AutoBiz 需要规则 Mod 和知识 Mod，再编译组合源。源码集合把这些步骤放在同一入口中处理，仍逐项确认安装与权限；依赖缺失或存在多个不明确的提供器时，编译器给出诊断。安装或编译通过不表示业务验收通过。

准备过程中断时，已安装依赖保留。结果不明的项显示“核对实际安装结果”，不会直接重装；重新打开后需核对保存的来源身份与现有权限。结束准备也不会自动卸载已经安装的依赖。源码集合只接受所选目录下声明的相对目录，不能使用它下载未知依赖或导入本地连接配置。

更换电脑时，先安装并授权这两个依赖，通过创造者的 `project_actions` 读取当前机器实际可用动作，再保存作者源码并执行 `project_compile`。然后绑定知识目录等必填配置，执行真实试用。不能复制开发机的安装身份锁来代替重新绑定；`project_doctor` 和 `project_test` 通过也不等于业务动作已经执行成功。

## 已有任务怎样采用插件修改

安装插件新版本不会静默替换正在运行任务保留的版本。先在创造者工作区修改源、检查和试用，再到原任务的“任务配置与版本”核对是否可采用新步骤。

系统会比较已完成阶段、产物、业务检查和知识绑定。可以安全更新的后续步骤由用户确认后采用；已完成阶段被改写、活动资源未结束或历史依据无法保持时会阻止更新。当前迁移只允许保持历史依据的未来步骤更新。改写已完成业务需要另行重新验收，本文不承诺原项目的任意回退或重放入口。

旧项目导入使用独立目标目录，限已纳入平台执行管理、接入导入声明的稳定检查点。界面读取目标插件声明的导入方式，用户填写特性标识等参数；主进程读取实际旧检查点、原材料和摘要，列明哪些步骤要重跑、哪些产物只需重新检查。确认后冻结平台管理的旧执行入口。历史成功和历史批准只作为来源资料，不计作新任务的成功凭据。

AutoBiz 的文档适配器已通过兼容与不兼容路径验证：需求转换、PRD、规格阶段重新执行，设计锁及 Plan 中的原摘要保持原值再检查，不能为使检查通过而重算旧锁。重新生成的前序产物若与原设计或 Plan 不兼容，会明确阻断。缺少可核验历史版本的 `UI_CONTEXT` 不会被猜测为某一阶段的正确输入。

导入确认时，完整方案和原目标目录随冻结记录保存。关闭窗口或重启后，在导入入口选择已冻结旧项目，点击“核对并恢复上次导入”，重新核实原依据后继续同一方案。已复制且摘要一致的文件可续传，不覆盖变化文件，也不自动解冻。早期只有摘要、未保存完整方案的冻结记录不能自动恢复，需要维护者核对。

导入范围内的阶段全部重新验收前，不能更新计划或创建调试分支绕过检查。完成后可以修改和调试后续阶段，但尚不支持把调试起点退回导入范围内；该限制同时在执行入口和存储提交处检查，不依赖隐藏按钮。

未登记的原始插件、未纳入平台管理的外部脚本，不具备该安全冻结边界。当前入口不能直接把任意原始目录转换成已管理项目；需要先完成来源与运行入口适配。已经成功导入的任务从本地任务列表继续使用，不重复导入。

## 插件开发者怎样衍生一个新流程

创造者可以使用 `native-modular` 模板创建组合源，也可以读取自己拥有的未受保护作者源码后修订。受保护市场包不能通过作者入口读取、编译、试用或导出源码，仍可通过原安装运行入口使用并进行只读诊断。开发者主要维护以下内容：

- **模块方法：** Skill 描述专业任务、缺失信息如何询问、实际产物写在哪里。
- **输入输出：** 给产物明确标识、路径和契约版本，后续模块引用实际前序输出。
- **业务验收：** 为每个输出提供检查；复杂规则使用已安装授权的动作提供器，并准备失败样例。
- **配置与知识：** 声明需要用户绑定哪些资料，哪些普通字段可以交给知识 Mod；敏感字段和目录权限不通过提示词隐式传递。
- **协作资源：** 有 Code 工作流才声明角色和工作区绑定。普通文档流程不需要 Git、工作树或多代理配置。

“前插需求转换”需要同时修改新模块和 PRD 的输入。只在 Skill 文本里增加一句“先转换需求”，平台无法据此建立独立阶段和可验证的产物衔接。

创造者的编译和契约测试能发现错误引用、缺少资源、不兼容输入输出以及不符合结构的样例。真正的业务质量仍需要隔离试用、业务反例及必要的人工确认。权限不足、凭据缺失、外部执行结果不明时，不能通过删除检查来自动修复。

## 哪些需求以后只改插件即可

| 需求 | 通常修改范围 | 条件 |
| --- | --- | --- |
| 调整某一步的写作或开发方法 | Skill 与验收样例 | 输入输出仍兼容；运行中任务需要核对版本 |
| 插入、删除或重排未执行阶段 | 组合源及受影响的输入契约 | 下游仍能获得所需产物；必要业务检查保留 |
| 加入组织特有的业务检查 | 检查 Mod 与组合源 | 所需执行能力已公开并获授权 |
| 改变知识筛选规则 | 知识 Mod | 在授权材料范围内完成，不自行读取其他目录 |
| 展示各工作树进度 | 视图 Mod | 公共运行接口已提供需要的事实；展示不能替代执行权限 |
| 接入全新外部系统并要求可恢复提交 | 插件适配器，必要时补公共接口 | 必须有真实授权、结果核对和取消或补偿能力 |

判断标准是平台是否已经开放所需能力及可靠的执行边界。Mods 提供扩展方式，不会让平台尚未提供的底层能力自动出现。

## 性能和可靠性有哪些实际收益

新路径读取阶段状态直接查询平台存储，不再为一次外层状态查询启动 Python，也不需要让模型决定应调用哪个状态查询脚本。固定工作流动作可以由确定性节点执行，模型负责需要判断的业务任务。

知识按声明和当前阶段加载；查询任务状态不触发知识准备。执行、检查和状态提交仍核对相关输入是否变化，不能用省略这些检查换取更快的表面响应。

可靠性的收益是“成功”有明确对象：哪个版本执行、检查了哪些文件、用户批准了哪一版成果、哪些资源尚未结束。失败后可以围绕这些记录决定继续、修复或人工核对，减少凭聊天文本猜测状态。

这些机制有机会减少纯调度的模型轮次、重复知识注入和重复执行。具体 Token 和耗时节约比例需要相同样例、模型和环境的对照测量。聊天滚动、闪屏是渲染链路的另一类问题，不能用状态查询变快来宣称已经根治。

本机机制对照使用相同的项目编号、阶段序号和状态结果，分别测量“启动 Python 读取小型 JSON”与当前 Host 服务的 SQLite 状态读取。Windows、Node 22.22.2 下得到以下观察值：

| 查询方式 | 样本数 | p50 | p95 | 每次查询的子进程数 |
| --- | ---: | ---: | ---: | ---: |
| 启动 Python 并读取 JSON | 20 | 86.49 ms | 93.47 ms | 1 |
| 当前 Host 服务读取状态 | 200 | 0.077 ms | 0.158 ms | 0 |

该对照只说明去掉进程启动的局部收益，没有运行旧 AutoBiz 的完整 CLI，也不包含模型、网络、业务检查或页面渲染，不能外推为整个任务的加速比例。另一个实际服务回归检查了 200 次“项目及操作列表”读取，确认没有进入包检查、知识准备或执行器。

上线分支合并后的八项聊天性能浏览器回归已通过。其中，真实滚动条拖动测试使用 400 条混合高度消息，观察到的空白帧为 0、同时挂载的消息行最多 21；侧栏拖动预览期间没有触发应用整体重渲染，释放时提交一次。测试包含真实滚动列表和事件路径，但不能替代安装包在用户实际历史消息、硬件及网络条件下的体验验证。

## 使用范围与验收边界

公共能力使用独立供应商准入流程验证通用性；AutoBiz 作为复杂业务接入，不作为平台内置分支。模型产出夹具的集成测试验证控制链、文件和真实执行器，不代表任意模型都能一次生成合格业务成果。

当前 AutoBiz Code 支持 `backend_only` 的受限路径；多仓需要显式声明仓库绑定，各仓按依赖串行执行、分别审批和提交，不具备跨仓原子性。完整 frontend 路线与原并行多工作树合并列车尚未等价迁移。CICD 只生成并检查发布准备材料，不执行真实外部发布；组织知识仓库的同步与沉淀也尚未完成。不具备外部结果核对协议时，未知状态不能视为成功。复杂阶段恢复只有在配置、上下文、检查和资源都满足恢复条件时开放。

以下为原实施记录核对时点的结果：当时完成的是源码环境下的业务集成、浏览器操作和回归验证，应用尚未打包。使用模型产出夹具的 AutoBiz 八阶段、独立供应商、多仓串行及失败修复链集成测试通过；源码集合交付与原生插件复制亦分别通过实际服务和界面验证。完整回归发现的两组测试支架问题已修复并复验，分轮日志保留，不宣称单次命令全绿。静态检查仍有格式警告，未以整库格式化扩大功能改动。上述结果不能代替安装包、实际用户数据及在线模型的业务质量验收。
