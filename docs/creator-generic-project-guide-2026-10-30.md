# 用创造者维护通用项目插件

本轮沿用原生项目组合的创建、派生、编译、试用和交付流程，增加阶段提示词编辑。平台依据插件自己的声明工作，不识别 AutoBiz 的名称或业务阶段。

## 通用职责边界（2026-10-31 续作确认）

| 层次 | 负责的内容 |
| --- | --- |
| 平台 | 作者草稿和版本、阶段/产物/依赖契约、权限确认、通用运行与证据校验、试用和交付入口 |
| 创造者 | 理解用户目标，选择或派生模板，发现可用能力，修改阶段、输入输出、提示词和配置，编译并组织重新试用 |
| 插件及开发者 | 业务阶段含义、行业验收规则、组织知识、企业接口、专用算法和复杂执行策略，通过实际公开契约接入 |

用户可以要求资料整理、供应商评审、运营报告或研发交付等不同流程。创造者依据目标组织阶段；模板中的阶段数、名称、编码/Git/部署步骤都不是平台默认要求。增加、移除或替换阶段时，使用已有组合作者声明和精确补丁，同时更新相关输入输出、检查和资源，再重新编译试用。当前正文编辑器只负责阶段正文，结构调整仍在创造者对话中完成。

结构调整还要检查依赖提供器的公开配置契约：有些配置按阶段 ID 或产物 ID 引用知识范围、验证对象或执行能力。新增阶段时应保留旧映射，按契约补齐新阶段必要配置；不能一概要求“所有配置一字不变”，也不能顺手新增用户未要求的配置入口。平台只负责通用契约和流程，提供器自身校验具体配置含义。编译成功仍需真实试用，不能据此推定新增阶段的业务配置可运行。

能力目录没有合适实现时，创造者应明确缺少什么以及插件开发者需要实现的契约。简单缺项可在现有 SDK 范围内编写；复杂个性化需求交由开发者实现，不能为了单个业务把定制逻辑移入平台，也不能承诺任意需求均能自动生成。AutoBiz Lean 仅用于验证这套流程的一个参考样例。

## 新建与派生

- 从零创建：在已绑定工作区的创造者对话中说明目标、阶段、输入输出与验收要求，让创造者以原生组合模板建立项目草稿。
- 从原生插件派生：选择支持派生且保留作者源的已安装项目插件，由创造者创建独立草稿。也可以再次派生已保存的新插件，走相同流程。
- 从老插件迁移：先人工整理作者源、资源、公开依赖与检查契约，再导入。旧 AutoBiz 不会因选择“派生”而自动转换，旧运行状态也不会迁移。

AutoBiz Lean 是已有的受限研发参考脚手架；通用资料模板用于验证同一创作流程可以服务其他业务。Lean 的规则、知识与交付能力仍是独立依赖，安装授权和配置沿现有流程完成。完整业务范围见其 README，不能将参考脚手架当成原 AutoBiz 的全功能替代品。

## 修改某个阶段的提示词

1. 在创作工作区打开“阶段提示词”，选择项目草稿和阶段。尚未试用的原生项目草稿也可编辑。
2. 核对该阶段的输入、输出与检查，修改“阶段提示词正文”，再点击“保存草稿”。也可以点击“让创造者修改”，在对话中说明期望。
3. 保存成功会产生新修订。点击“编译并从头试用”把明确的草稿身份交给创造者，继续原有编译、检查和原生试用确认流程。
4. 真实试用通过后，再沿交付卡确认保存插件，并从普通项目入口使用。

如果旧修订已经保存为插件，新修订需要另存时，在交付卡的“新插件标识”填写未被安装插件使用的独立标识。名称冲突会明确阻止保存；不能把旧插件的安装记录当成新修订已交付。保留旧插件可让现有项目继续使用固定版本，新项目再选择新保存的插件。

正文编辑只替换阶段声明指向的作者 Skill 正文；原 YAML 元数据、其他文件、检查、配置及依赖保持原样。实际阶段上下文还包括需求、上游产物、知识和工作流，正文不是全部提示词。变更检查或流程结构时，应在对话中明确提出，并重新编译验证。

多个阶段共用一个作者 Skill、作者源缺失或格式损坏时，编辑区会说明原因并保持只读。由创造者先明确影响范围或修复源码，不能通过正文编辑器暗中修改多个阶段。生成的 `skills/native-*` 不是编辑对象。

## 冲突与试用

- 模型或其他入口修改了草稿后，旧版本保存会被拒绝，当前文字保留。先复制需要的内容，再放弃本地修改并刷新，核对新版本后重做修改。
- 切换阶段或草稿前，未保存正文需要显式放弃。文字会尽力暂存在当前窗口并按账号修订、聊天和工作区隔离；这不是永久备份。缓存失败会提示用户保存或复制，关闭窗口前仍应保存。
- 达到现有草稿/修订预算时，回到创造者对话走续作流程；不会扩大预算或自动删除历史。
- 保存草稿、编译检查、真实试用、保存插件是不同状态。旧成功不能证明新修订成功。正在运行的旧试用继续绑定旧源码；未知结果按原恢复入口核对，不能标记成功绕过。
- 本轮修改后从头重新试用，不提供中段回退、旧运行状态迁移或外部操作撤销。

## 老插件重构的影响

精简提示词或移除不再需要的 Hook，只要原生作者声明、输入输出、公开动作和验收契约仍有效，就作为插件自身的新源码候选处理。平台不需要针对 AutoBiz 增加适配。如果删除了实际承担校验、产物写入或旧状态推进职责的 Hook，须把必要行为映射到原生声明、Skill 或提供器并重新验证；阶段推进仍由 Host 统一负责，插件不重建一套旧状态机，不能将删文件等同于兼容完成。

已派生的插件是独立源码副本，已有项目固定其运行版本，不会自动跟随脚手架更新。需要吸收上游重构时，由创造者明确修改当前草稿，再走编译、试用和保存流程。

实施范围与验证要求见 [本轮方案](creator-generic-project-iteration-plan-2026-10-30.md)。受控测试通过只证明各自覆盖的代码与界面行为，不能代替真实模型完成用户项目。
