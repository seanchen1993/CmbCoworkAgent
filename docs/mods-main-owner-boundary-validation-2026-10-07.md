# 主版本稳定：确认两次状态检查的作用

前一轮已排除简单更换文件读取方式的明显收益。当前先验证任务内容保护链路，
确认其中的重复检查各自承担什么责任，再判断是否值得修改。

源码显示，插件运行层先确认 Mods 仍开启，之后还会核对授权与插件状态。
这些后续操作可能执行其它代码。聊天宿主随后再确认开启状态和会话所属项目，
因此中途关闭 Mods 时，后一次检查仍有实际作用，不能直接删除。

## 本轮方案

新增独立回归文件，使用实际组件管理器、真实插件编译和运行、实际会话协调器与数据库。
接收管理器原样产出的会话所有者，沿原入口注册，不手工构造一个成功检查的替身。
计数只围绕准备完成后的单次检查；准备阶段的多次核对不能冒充同一次检查。

先验证正常路径的两处开启检查，再验证授权检查或插件状态读取结束后关闭 Mods。
还需验证取消真实会话，以及会话编号与创建时间相同、实例标记已经更换的情况。
失败必须发生在真实保存路径，核对原生写入委托次数、数据库记录、聊天显示与回执，
不能只因旧对象已失效就宣称没有保存。

原来的通用、包装回调和未知读取来源保留全部检查。新增测试不为生产代码增加接口，
不保存开启结果，不删除等待后的权限检查，不改交付包。

两位独立方案及源码评审后运行新增回归，再运行相邻保护链路回归。
真实桌面采用既有同包共享任务；如需读取次数诊断，只能在隔离设置文件的固定开关上
计数并完整还原原方法。诊断不能当作无改动的速度基线，原 39.015 秒记录继续保留。

新增六项回归已通过。准备完成的实际目标单次核对，确实先经过组件运行层，
再经过聊天宿主，各读取一次开启状态。正常提交时，记录、聊天显示和对应回执均实际保存。

授权核对结束后关闭、插件状态读取结束后关闭、真实会话取消，以及实例标记更换四种
情况均拒绝提交，原生写入委托次数为零，独立数据库查询的记录、显示和回执均为零。
实例测试保留相同会话编号和创建时间，只更换实例标记；没有把它冒充为删除后重建。
测试的项目边界采用实际会话和工作目录检查，没有声称执行完整桌面 IPC 处理器或 SDK 调用。
