# 慢请求不耗规则自身时间：实现与验证

工作目录为 C:/ai/CmbCoworkAgent-mods-v2，开发分支 codex/mods-v2；没有改 UAT、提交或发布。参考已经核对的 Claude Code 2.1.288。整体对齐继续进行，不在本阶段结束。

## 用户实际得到什么

组件调用模型、读取文件或等下游规则时，不会再因为外层处理函数自身时间不足而提前失败。普通规则有10秒处理时间，恢复处理有独立1秒。等待这些请求时暂停自身计时，主动睡眠仍占自己的时间。作者可以直接读取 `next.budget` 看自己的剩余时间，不需要发查询请求。

用户仍用原导入、选择组合、批准和聊天流程。启动分析在首次启动或明确重载时执行；普通保存不偷偷分析。真实桌面用两个组件调用已配置的本地HTTP模型，模型实际等待11.2秒，第一次和新参数重载都成功。回到聊天执行命令读取已有结果，不另发请求。原参数保存、停止后修正与普通连续聊天继续通过。

处理规则自身预算和宿主总等待分别控制：常规模组链总等待最多120秒，明确的更短期限保留。启动仍共用整次120秒，单次模型仍60秒，CPU和内存限制不放宽。取消或到期时调用者结束等待；底层实际操作若不响应取消，仍被跟踪至真正结束，不能为了显示空闲重复执行或提前重载。

## 两位评审发现与修复

- 同步阻塞使 timer 没机会执行，过期结果仍可能接纳：改为单调时钟同步核验，并验证实际阻塞反例。
- 恢复前、保留下游及清理等待可能永不结束：总期限覆盖这些等待，下游不重放。
- 内容保护还在等待却被误认为空闲：同样持有实际活动至真实 finally，迟到结果只清理。
- 免费请求开始时可能给已经耗尽的规则续命：先同步结算和判过期，再停钟；每个并行请求只能关闭自己的回执。
- 一个合法CPU片段内耗尽后直接返回，可能赶在下次检查前成功：接纳返回前再次检查。
- 总期限已过但恢复规则先进入：初次和恢复入口均同步核验，反例确认恢复次数0。
- 预算里的Infinity被普通JSON变成空值：直接用实际VM数值创建只读快照；旧帧读取不能复活。

两位独立最终静态复审通过。评审没有替代运行测试；广域结果保留实际状态。
