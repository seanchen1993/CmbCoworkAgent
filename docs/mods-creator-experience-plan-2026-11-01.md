# 创造者体验、上下文预算与能力开放纠正方案

日期：2026-11-01。状态：两位 agent 实施前评审通过，已完成开发及两位独立 medium agent 回检；回检发现的旧版本误标 P2 已修复并复审关闭。详细结果见 [验收记录](mods-creator-experience-verification-2026-11-01.md)。

## 用户目标和固定边界

用户用自然语言创作、调整和组合 Mods；插件是保存、安装和分发这些能力的一种载体。项目插件继续进入既有项目创建、配置、需求管理和执行流程。平台不内置 AutoBiz 的业务步骤，不新增并行执行器，不将配置、试用、保存和实际执行混为一谈。

版本固定 2.0.0；保留当前工作区已有修改。本轮不生成安装包、不触发 Actions。先经两位 agent 审阅具体方案，再开发；开发完成另由多个 agent 以 medium 强度回检。

## 已确认的问题

1. 本机当次模型窗口 128000，配置输出上限 81920、安全余量 1000，压缩触发和输入预算只有 45080。五次 context-compaction 发生在连续模型步骤间。该输出值来自配置，平台默认值是 8192；不能将其描述为默认设置错误。
2. 最终模型边界按 Hook 后的提示词及工具计数，但前置摘要按更早输入计数。精确的 MODS_MODEL_INPUT_BUDGET 未被已有 overflow 恢复路径识别。不能仅增大窗口、静默改用户配置、忽略错误或无限压缩。
3. 创作工作区把阶段提示词编辑放在试用/保存流程之外；已经发送到真实对话的修改请求仍提示继续输入，导致重复入口和状态误解。普通灵件试用确认藏在高级区，项目“开始试用”实际只准备环境。
4. 聊天侧栏把有资格使用的来源显示为正在使用；可用依赖不构成执行证据。“结果”混合插件交互面板、命令记录与产物；公共插件设置导航显示在每个分页上方。
5. 固定指引主要介绍控件位置，缺少当前状态的下一步、示例需求、试用和保存的实际边界。Mods 被缩减为“组合几个插件”的文案。

## 开发方案

### A. 上下文预算和故障恢复

- 统一实际 step 模型、输入、工具和最终 Hook 的预算口径；精确识别本地输入预算异常，只在尚未调用模型、未执行工具时进入已有有界摘要恢复。
- 校验恢复是否实际减少输入；相同输入不能反复压缩重试。固定指令/工具负载本身超限时明确指出，保留聊天和草稿，不把不可压缩系统内容当历史删掉。
- 显示模型窗口、输出预留、实际可用输入的区别；高输出配置有明确解释。错误展示可采取的下一步，不仅暴露内部错误码。
- 本轮保留用户明确配置的输出上限及实际发送参数；不引入可能影响推理协议的动态裁剪。修复恢复、摘要目标和可见预算后再以证据决定是否需要请求级动态输出策略。
- 回归：128K/81920 场景、最终 Hook 增量、小窗口 step 模型、工具固定负载、摘要无进展、严格重试次数、用户取消及非预算错误不误重试。

### B. 一个创作对话，一个可理解的试用工作区

- 默认在外部创作对话提出修改；工作区“返回对话修改”携带当前插件/阶段上下文。原提示词直接编辑保留在折叠的高级区，不能成为普通用户的必经步骤。
- 主区基于现有真实状态显示当前版本和下一步：制作中→待准备→可试用→待配置/确认→环境已准备→执行中/待确认→通过/失败/未知→已保存。
- 主要操作沿原 API；不增新状态机，不把安装或保存称为已运行，不复用旧版本的试用通过记录。普通灵件原有授权入口提升为清晰的试用步骤；项目试用区明确准备环境和开始执行的区别。
- 保存后明确使用位置：项目插件进入原项目入口，聊天功能进入对应聊天；未试用但按原规则允许保存时如实标注。
- 页面采用简明的版本概览、顺序操作和按需展开细节；窄窗口可滚动，不让源码和诊断淹没主操作。
- 回归：三类插件、首次/修改后/保存后状态、试用失败与未知、修改请求只发送一次、未发送正文保护、保存后正确入口、账号/线程/目录/迟到响应隔离。

### C. 任务侧栏与术语

- 主区只陈述当前选择/可用功能，不能以“已安装/已授权/依赖启用”推断“正在运行”。项目插件及其依赖显示真实归属，但不改既有继承和权限规则。
- 任务输出、插件提供的交互面板、技术记录分清来源和用途；插件面板不当作验收成功证明。管理已安装插件只在配置区保留一个名称明确的导航入口，不与结果链接混淆。
- 默认移除长篇技能/MCP/模型教学说明，具体配置在按需展开区查看；缺配置、不可用原因与必要操作仍可见。
- 创造者入口说“创建或调整 Mods 功能”，涵盖界面、工具、事件规则和流程，组合现有能力只是其中一种；移除 AutoBiz 默认示例及插件组装的狭义表述。
- 回归：只选技能、空组合、默认继承、共享依赖、禁用/失效来源、纯项目组件、原实际运行记录、链接导航不授予权限、窄屏和键盘可达性。

### D. 有实质帮助的指引

- 给“想实现什么→如何描述→在哪里试用→看到什么算通过→如何再次使用”完整路径和可复制示例，不替用户自动授权或执行。
- 根据当前创作阶段解释下一步；普通用户主路径不包含快照、源码、恢复策略等高级步骤。
- 指引可关闭重看，保留原草稿、焦点和账号隔离。增加示例与完成标准时不自动覆盖输入或发送消息。

### E. 对齐 Claude Code Mods 的公开能力

- 从官方 registry 与公开分发包核实最新版本；本机现有 CLI 不原地升级，检查副本放独立临时目录。审计公开 SDK、事件和 UI render sites，不以搜索缓存代替版本证据。
- 对照本平台实际 SDK 和原生渲染点列出已开放、确实缺少和不适用部分；“UI 开放”不等于开放任意 Electron/DOM 或权限确认界面。
- 本轮只实现有明确契约、可验证归属/生命周期和现有权限支持的通用缺口。每个新增面单独经两位 agent 确认实现措施，再落代码；不能为追求方法数量伪造空实现。
- 已核实本轮 UI 优先范围是 Box/Text 等现有声明组件的安全布局、样式和宿主映射，补可发现的类型/用法，复用当前 pane、toolbar、sidebar、page 渲染路径。具体属性白名单须与校验器、原生渲染器和测试同时补齐；不开放任意 CSS/DOM/Electron。ToolProgress、audio、MCP 连接等独立契约在审计表中明确状态，不伪造支持。
- 复杂业务、多仓库策略、企业接口和专用交互由插件开发者基于公开能力实现；平台提供统一权限、会话、事件、模型、持久化与界面基础。

## 验收和交付

先跑有意义的窄测试和真实组件浏览器，再 Node/Web 类型检查与修改文件 lint。用 AutoBiz 及非 AutoBiz 的来源验证公共路径，没有业务名称分支。执行正文受控的测试与真实模型端到端分开记录，不把模型环境问题或 Git 环境混报成功/失败。保存可核对的浏览器截图、版本/源码证据和验收说明。

本轮完成后，新的 medium 强度评审 agent 独立检查上下文/权限边界、创作主流程、文案事实及能力对齐，发现阻断则修复后复审，不以开发者自评替代。
