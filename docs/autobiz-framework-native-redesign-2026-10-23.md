## 1. 设计决策

**从任务和业务契约重新设计 AutoBiz，复用平台的执行、授权和运行记录，将旧插件中有价值的知识、专业方法和校验规则提取为可组合能力。**

以下决定作为实施约束：

1. 选择原生流程运行时的新路径，由平台持有外层阶段执行事实和唯一推进权。插件声明业务流程、输入输出、质量条件和人工决策点；不再用 Skill、工具 Hook 和状态脚本分别推进同一阶段。该选择不强制推广到所有 Mods。
2. 一个用户任务关联全部阶段会话、子 Agent、Workflow、产物和反馈。物理会话可以隔离，用户无需在不同页面拼接执行过程。
3. 模块按可独立复用的业务能力划分。一个 Mod 可以同时提供 Skill、检查器、知识选择器和界面扩展；不要求一个文件或一个 Hook 对应一个 Mod。
4. 需要组合的插件只维护一份组合源声明。系统为流程插件编译版本固定的执行计划、运行声明和展示投影；简单 Mod 仅注册所需能力。生成文件不作为第二份可编辑事实来源。
5. 固定调度、查询和状态提交调用确定性服务；模型负责需求理解、内容生成和专业判断。平台不硬编码 AutoBiz 阶段名、知识目录或产物格式。
6. 新插件与旧插件并存，但同一项目执行绑定不能由两者同时写入。迁移保留业务语义，不承诺原样保留所有旧脚本和状态文件。

这里的“平台持有阶段状态”不等于平台决定业务。就像数据库负责事务而业务定义规则，平台确保符合已声明、已授权、已验证的推进条件；AutoBiz 决定什么是合格需求、设计和交付。

### 1.1 三项通用性硬约束

**约束一：流程运行时按需接入。** 简单工具、界面扩展、工具调用统计等 Mod，可以只注册自身所需能力，不必创建项目、阶段、审批或产物记录。只有需要持久流程与可靠交接的插件才选择原生流程运行时；系统根据真实声明诊断所需能力，不让普通用户选择内部运行模式。本文后续阶段对象和提交协议仅适用于接入该运行时的路径。

**约束二：平台管理执行事实，插件定义领域规则。** 平台负责某次执行是否发生、输入与检查是否仍有效、是否具备授权以及提交是否成功。业务模块负责组织业务步骤、判断业务质量并声明决策条件。公共类型不得包含 AutoBiz 的阶段枚举、PRD 格式或专属知识目录；插件领域状态不能形成第二套外层阶段写入者。插件若自持领域状态，必须明确所有权、并发与恢复协议，不能假定普通 KV 已提供业务事务。

**约束三：特殊资源通过可选提供器接入。** 通用资源协议只定义身份、归属、授权、租约和生命周期核对；Git 工作树提供器负责仓库、base/head、候选和清理语义。没有 Git 需求的插件不加载工作树能力。提供器按所支持的生命周期操作声明能力，不要求所有资源都有合并、封存或回滚。插件不能靠自报能力获得主进程权限，也不能把任意路径声明成已授权资源。

通用性需要正反两类验收：独立流程插件能复用运行协议，简单 Mod 也能在不启用项目运行时的情况下正常使用。若新增业务需要增加平台专有分支，或一个简单工具必须填写大量阶段配置，均视为设计不通过。

## 2. 用户最终如何使用

### 2.1 普通使用：一个目标、一个任务入口

例：“根据这份业务描述完成订单查询功能。”

1. 用户选择 AutoBiz 模板或由会话推荐，带入当前项目、目录和已有配置，只选择一次。
2. 平台先诊断能力和环境，再集中询问缺失的业务资料、知识绑定及必要授权。已有有效配置直接复用。
3. 展示简明计划：将交付哪些内容、哪些位置需要用户确认、将使用哪些外部资源。源代码摘要、模块版本等放在展开详情。
4. 在同一任务持续执行。有效输入、检查、授权均满足时自动进入下一个非人工阶段；需要业务输入、审批或结果核对时明确停下。
5. 用户从任务里查看成果、修改意见和 Code 子任务进度。完成后直接查看交付物或继续修改，不再重复打开插件、选择模板和建立无关联会话。

默认任务界面只保留：**当前工作、待我处理、结果**。阶段列表用于解释进度；细节面板显示证据、日志和资源。技术性的“Mod 状态”不承载整个业务流程。

### 2.2 创造：修改业务方案，而非手工维护多份配置

例：“在 AutoBiz 前加入需求转换，输出统一格式，再交给原需求分析。”

1. 系统读取已安装插件的真实组合契约，向创造者展示业务变化及影响范围；用户无需理解契约文件。
2. 优先复用已有需求转换 Mod；缺少时生成它的实现和契约。不满足类型或语义衔接时，生成显式转换能力，不能仅把两个路径连接起来。
3. 展示用户可理解的差异：新增什么、原步骤接收什么、哪些规则保留、需要补什么配置、哪些旧结果需重验。
4. 在同一创作任务中准备隔离试用。用户可以边看结果边反馈“转换丢了性能要求”，系统修改对应能力并重验受影响范围。
5. 保存新模板后直接“开始使用”；分享时导出插件包。内部 ID 和建议版本自动生成，作者可在高级信息中修改。

草稿保存、样例验证通过、真实业务验证通过是不同状态。允许保存未验证草稿；不能把安装成功或 JSON Schema 通过显示为业务已经验证成功。

自然语言创作者只需描述目标、提供业务资料/样例并判断结果。实现、契约、依赖、ID、建议版本和编译产物由系统生成维护，源码编辑是可选入口。保存形成唯一可定位的插件版本及其模板/能力入口，附验证范围；“保存草稿”“安装使用”“导出分享”明确区分，不以一句“保存成功”掩盖尚未安装或尚未验证。

### 2.3 现有界面的收敛

| 现有控制面 | 目标处理 |
| --- | --- |
| 安装后再找入口、再选同一模板 | 安装交付卡提供“开始使用”，携带模板身份和上下文直达任务创建/已有任务绑定预检。 |
| 常用搭配、步骤管理、从 Mods 组装 | 普通入口合并为“创建或修改模板”；步骤编辑成为创造者的高级视图，不再要求普通用户配置顺序。旧入口保留迁移提示。 |
| 聊天任务模板与项目流程 | 界面按“轻量任务”“有产物和验收的项目任务”解释用途，底层通过不同执行适配器接入同一任务视图，不宣称执行语义相同。 |
| 创作区常驻、指引与日常使用混合 | 会话可切换创造者模式；仅创作任务展示创作工作区。首次指引锚定真实按钮/icon，可关闭、跳过和重新打开。 |
| 多个阶段会话分散展示 | 阶段会话关联到任务；待输入卡和结果聚合在任务中，仍可打开原会话排查。 |
| 配置及功能开关分散 | 统一能力入口展示应用、项目和插件绑定的有效状态及阻断原因；不能用新的总开关隐式授权其他插件。 |

### 2.4 操作入口与易用性验收

任务“待我处理”是输入、业务审批和恢复的主要展示入口；原会话、插件视图及通知引用同一请求 ID 和同一受控服务，不各自保存可写决策。原生权限确认仍由可信确认界面承接。旧入口只跳转或展示历史，不能留下另一套独立推进按钮。

从任一视图处理后，其他视图同步为已处理；重复点击只产生一次有效操作，过期请求显示失效原因与当前入口。聚合权限按任务及子运行分别检查，关联任务不扩大插件可读取的会话范围。

从 D1 起执行两条固定 UI 验收路径：首次安装后启动、已有配置项目再次使用。已有目标/模板/目录不重复填写；无人工决策且已授权阶段之间的机械推进点击为零；业务输入、审批和结果可从当前任务完成；重启恢复无需重新描述目标。预检一次列全当时可确定的缺项，后续动态发现的问题就地补充，不承诺执行前预知所有缺项。

## 3. 平台、插件、Mods、Skill、Hooks 的边界

| 层 | 应负责 | 不应负责 |
| --- | --- | --- |
| 平台执行底座 | 操作身份、权限、并发版本、持久运行状态、检查凭据、提交、取消、未知结果核对和资源归属 | AutoBiz 的七阶段枚举、PRD 内容标准、专有知识选择和测试策略 |
| 插件组合声明 | 选择模块、输入映射、配置绑定、交付目标、审批和执行策略 | 复制底座事务、通过提示词绕过检查 |
| 业务 Mod | 注册专业动作、Skill、检查器、上下文提供器或视图；声明依赖与版本 | 把任何脚本当成可直接拥有全部权限的扩展 |
| Skill | 在已给定输入和上下文中执行专业工作、产生业务结果 | 手改 checkpoint、获取租约、同步多个状态文件 |
| Hooks | 运行边界防护、生命周期适配、必要的调用前后处理 | 隐式决定业务阶段完成、重复定义流程图 |
| Workflow | 组织需推理的子 Agent、并发工作和子运行结果 | 让模型反复执行固定状态查询或资源管理命令 |

Mods 的价值是让插件作者通过公开协议替换、扩展和组合这些能力。例如增加一个“数仓质量规则”Mod，即可带入其输入要求、检查动作和结果视图；平台不需要理解数仓业务。平台尚未开放的资源或生命周期能力仍需平台开发，不能由插件绕过安全边界补出。

### 3.1 按能力选择运行协议

| 使用形态 | 最小接入要求 | 不强制引入 |
| --- | --- | --- |
| 单个工具、界面或观测 Mod | 原有注册、权限、生命周期及作用域协议 | 项目、阶段计划、产物审批、工作树 |
| 独立持久动作 | 按副作用需要使用操作身份、核对和取消协议 | 为一次动作虚构完整项目流程 |
| 原生可靠流程插件 | 组合契约、计划、阶段操作及所需输入输出检查 | Git、Code、固定阶段数量 |
| 旧插件或自持领域运行时 | 明确所有权，通过现有入口或适配器观察、调用和交接 | 在没有迁移协议时自动转成 Host 状态 |

这是能力组合，不新增四套互斥产品模式。平台可复用共同的操作基础，但不能为了形式统一而先重构所有执行器。独立动作的公共恢复协议尚需逐项核实；未实现时明确报告边界，不将它强制转成项目。

## 4. 状态模型：一个权威写入者，不要求只有一张表

### 4.1 对象与归属

| 对象 | 内容与权威 |
| --- | --- |
| 任务执行绑定 | 平台绑定工作区/资源范围、安装身份及执行计划。项目/Feature 是现有项目适配器的身份，不要求其他插件向用户暴露 Feature 概念。 |
| 领域对象 | 插件持有订单状态、风险等级等业务事实及转换规则，通过受控动作更新并返回可核对结果；不能直接改写平台阶段，平台也不能仅由领域值推断阶段已通过。 |
| 计划版本 PlanRevision | 平台保存不可变编译结果：模块及代码身份、步骤、输入映射、知识/配置要求、策略和依赖。 |
| 阶段操作 StageOperation | 平台持有准备、授权、执行、验证和提交状态，并关联输入指纹、父运行及结果。 |
| 产物版本 ArtifactRevision | 平台记录位置、内容身份、生产者和消费关系；格式及业务意义由插件定义。 |
| 检查凭据 CheckReceipt | 平台保存检查器身份、输入/产物摘要和结果；插件给出业务断言。 |
| 上下文快照 ContextSnapshot | 平台固定本次运行的知识来源、选择规则和配置绑定版本；业务模块定义选择方法。 |
| 子运行 | 复用已有运行身份与生命周期，平台维护父操作关联、取消、恢复及可核对结果；插件定义领域载荷和完成规则。Code 子运行是 AutoBiz 的业务称呼，不新增专用平台状态机。 |
| 界面投影 | 由上述事实计算；不是第二套可写流程状态。 |

以上为接入流程运行时的目标逻辑对象，优先扩展现有 Host 记录；不要求新建同名表或再造一套通用事件存储。独立 Mod 不因此创建阶段记录。唯一写入者约束针对同一执行事实，不禁止插件管理独立领域状态；插件状态事务必须有真实的一致性实现，不能把平台 KV 的能力夸大为业务数据库。

### 4.2 阶段推进

逻辑链路：准备输入 → 诊断与授权 → 执行 → 固定输出版本 → 检查 → 必要业务审批 → 条件提交 → 决定是否继续。

- “模型回答结束”“文件存在”“工具调用返回”均不等于阶段通过。
- 提交必须核对计划版本、输入/输出身份、审批绑定及当前检查凭据；检查后修改产物会使相关凭据失效。
- 授权与业务审批分开：允许写文件，不等于用户批准设计方案。执行策略不能覆盖原生权限确认。
- 等待用户输入是可恢复等待，不能当成失败或重新启动一轮。请求绑定任务、操作、会话和请求 ID；重复回答幂等，旧请求明确失效。
- 响应丢失或外部结果不明进入 `unknown`。先核对事实，再决定提交、明确未执行后的重试或交由用户处理；不得把 unknown 清空后重跑。
- 同一执行绑定的外层提交串行。首期沿用当前工作区互斥；资源彼此隔离的任务才可并行。后续由提供器声明读写范围并统一检测冲突，再按资源缩小锁范围，共享目录、目标分支与外部对象不能因 Feature 不同而绕过互斥。

连续执行由有界协调器完成：一次推进后重新预检下一阶段，在审批、输入变化、权限变化、失败、unknown、取消或预算边界停下。不得通过无限工具调用或自动点击替代协调器。

**成果审批是新增协议。** 当前 Host 的批准主要发生在执行前并绑定输入。目标中的输出后审批需独立记录，绑定计划、操作、产物摘要、检查集合和审批策略。拒绝保留已经发生的执行事实；修改成果生成新版本并使旧成果审批失效，不能复用执行前的批准代替成果验收。

**可恢复待输入是新增协议。** 持久记录请求 ID、问题结构、计划与操作身份、答案及消费位置。相同请求和相同答案返回已有结果，冲突答案拒绝；关闭卡片只隐藏显示，取消请求才改变执行状态。恢复后重新验证权限和输入身份，从受支持的续执行位置继续；执行器不能安全续接时保持待处理，不能重放等待前的副作用。取消、迁移或撤销使旧请求明确终结，已消费记录仍用于去重和审计。

### 4.3 修改步骤和局部重跑

启动前选择可选步骤，编译成完整计划；不固定七阶段。首个实现复用已有线性执行能力。

运行中修改必须生成新计划版本，不能原地改活动计划。系统计算依赖影响，暂停受影响操作，核对外部副作用后迁移。未受影响且证据仍有效的产物可以复用；审批仅在其绑定对象、范围及策略均未改变时保留。

迁移先保存候选及影响报告，再冻结受影响操作的新派发，处理待输入并等待副作用到达可核对边界。用旧计划版本和迁移代次作条件提交，原子更新活动计划引用与复用关系；失败时旧计划引用仍有效，但冻结不能自动解除，须核对后显式继续。迟到结果只能追加到原计划，不能推进新计划。重启恢复迁移意图和当前进度。现有隔离分支创建不是活动计划迁移；尚不支持安全切换时保留原任务并创建明确关联的隔离分支。

局部调试使用隔离运行与新的输入/产物版本。接受调试结果前重新验证，不能“回写初始状态”掩盖已提交代码或外部发布。任意动态图不作为首个版本的隐含承诺；不能表达的动态语义应阻断或继续兼容路径，不能偷偷降级为线性。

### 4.4 插件变更、撤销和外部副作用

活动运行固定代码与契约快照；正常更新用于新绑定，已有运行采用新版本必须经过计划迁移。保留旧快照不等于保留执行权：停用或卸载立即阻止新的操作及副作用授权，对进行中的动作请求取消并核对结果。无关插件变化不应使当前任务整体失效。

旧输入请求与迟到回调不能推进当前任务，但已发生副作用的迟到结果仍应写入原操作的核对记录，不能丢弃事实。运行历史和恢复所需快照/资源归属保留至核对及保留策略允许清理；会话仍可读、可继续普通对话。核对与资源处置走独立的最小权限入口，不通过重新启用插件来恢复全部权限；缺少可信核对能力时明确保持 unknown。

对于多外部副作用动作，增加按需使用的子操作清单：每项记录稳定操作键、目标身份、参数摘要、请求意图、外部回执与核对证据。相同键不同参数拒绝复用。分别保存已发生、明确未发生、未知事实；远端不支持幂等时，不承诺恰好一次。只有证明确未发生才允许重试对应子项；补偿/前向修复属于新的受授权操作。

取消不是回滚，业务检查失败也不是外部动作未执行。父操作的汇总状态不得抹掉子操作的真实结果。unknown 阻止相关冲突写入，不因租约到期认定副作用未发生；可复用资源采用递增租约代次，过期 owner 的普通回调和提交不能改变新 owner 的状态。对仅有只读计算的 Mod，不强制建立外部副作用清单。

## 5. 模块契约与插件作者体验

### 5.1 最小作者工作

作者只声明实际提供的能力及必要契约：工具声明调用输入输出，界面声明视图入口和数据需求，统计能力声明观察来源和权限，上下文提供器声明来源与选择规则。被组合进可靠流程后，才增加步骤输入映射、产物、检查和审批绑定，由流程适配器诊断附加条件。平台提供适用的默认展示和诊断，作者无需手写公共事务日志、试用控制器及重复运行配置。

下面是**设计示意，不是当前可直接安装的 API 或最终文件格式**：

```yaml
module: requirements.convert
version: 1.0.0
inputs:
  request: { contract: business-request/v1 }
outputs:
  requirements: { contract: normalized-requirements/v1 }
executor: { skill: normalize-requirements }
checks:
  - requirements-schema
  - source-coverage
context: [business-glossary]
effects: [workspace-artifacts]
```

组合源声明只表达模块选择和连线，例如 `需求转换.requirements → 需求分析.requirements`。编译器解析实际契约、默认值和代码身份，生成计划与展示；不能由模型填写“已通过检查”的凭据。

### 5.2 启用相应能力后必须验证的契约

| 维度 | 规则 |
| --- | --- |
| 输入来源 | 指定用户资料、上游产物或显式上下文；必填输入缺失即阻断，不从聊天中静默猜测替代。 |
| 输出 | 指定结构、版本、生产者及定位规则；路径解析受工作区授权约束，不能以同名文件认定同一产物。 |
| 兼容性 | 声明支持版本并检查实际结构；语义差异由转换动作和样例验证，结构兼容不等于业务等价。 |
| 依赖 | 发现缺失、循环、冲突及不满足的前置条件；界面给出可执行修复入口。 |
| 知识/配置 | 声明所需角色、范围、必填项及绑定策略，敏感值只传受控引用。 |
| 副作用 | 区分只读检查、报告写入和外部变更；声明不等于授予权限。 |
| 检查与审批 | 保留必须业务门禁，作者改动显示影响；不能为使试用通过自动删掉不通过的断言。 |
| 运行结果 | 结构化成功、失败、待输入和未知结果，带可追溯操作身份。 |

### 5.3 新插件的建议源码组织

```text
plugin.json                  插件说明、版本与公开能力
composition/                 作者维护的组合源与配置契约
modules/
  requirements/              专业方法、检查器、输入输出契约
  specification/
  design/
  delivery/
knowledge/                   选择策略与可分发知识，不包含凭据
tests/                       业务样例、断言与异常场景
compat/                      可选旧数据导入器，正常新路径不依赖它
```

该目录是作者组织建议。安装包继续服从平台已公开格式，新增协议先做版本化兼容；编译生成内容由工具管理，不要求用户同时编辑 catalog、board 配置与 Host manifest。

## 6. AutoBiz 的重新拆分

| 业务能力 | 保留的价值 | 新路径变化 |
| --- | --- | --- |
| 需求理解/转换 | 原始要求、术语、约束、需求来源和覆盖检查 | 输出结构化需求，原文可追溯；可替换转换器，原需求分析消费明确产物。 |
| 规格与设计 | 规格完整性、架构约束、人工确认 | 检查动作显式执行；确认绑定实际设计版本。详细设计是可选依赖能力，不由固定编号决定。 |
| 计划 | 工作拆分、依赖、验收和资源需求 | 产出可消费的实施计划；业务 DAG 可以在 Code 子运行内部表达，不另写外层阶段。 |
| 代码交付 | 多 Agent 实现、评审、编译/测试分离、候选接受与合并规则 | 作为 Code 子运行，以公共资源句柄管理工作树；结果通过证据进入外层验收。 |
| 发布与归档 | 发布条件、知识沉淀、最终证据 | 外部发布独立授权并可核对；归档消费已确认交付结果。 |
| 知识能力 | 原 board 配置的变量解析、范围选择、提示词模板和沉淀规则 | 迁移为配置解析和上下文提供器，生成版本化快照；不在每次新会话中全量运行查询脚本。 |

不再把“状态机 Mod 包装旧 writer”作为新 AutoBiz 的核心卖点。新外层执行状态由公共运行协议管理；插件可以自定义领域状态机，通过受控动作与可核对结果交接。领域状态并不必须隶属于平台阶段，但不得再写一份同义的外层执行状态，不能由两个控制器重放同一副作用。

原 `state.json` 保留在旧项目和导入边界。新任务的状态直接读平台投影；`STATE.md` 可按需导出供人阅读，不要求它与数据库共同成为事务写目标。

## 7. 知识、配置与 Hooks 不丢失的做法

### 7.1 配置与知识绑定

配置分为插件默认值、项目覆盖、运行参数和凭据引用；优先级固定，关键覆盖须可见。旧环境变量不能直接当成另一台机器的有效配置。

知识快照至少绑定：来源身份、内容版本/摘要、选择规则版本、相关配置指纹和范围。缓存按身份与版本命中，读取请求单飞；知识变更显式失效，不能只按文件路径缓存。敏感值不得写入普通日志、导出包或可反推的明文摘要。

阶段准备时获取快照，执行期间固定该版本；外部知识无法固定时标明其时效和不可复现边界。后续新阶段按策略采用新快照，已经通过的结果不能静默替换上下文。只有实际依赖变化知识的下游结果进入重验范围。

换电脑安装只携带配置 Schema、默认值和可分发资源；缺少知识目录、模型连接或凭据时统一预检并引导重新绑定。导入的旧原包仍需检查嵌入秘密，不能因平台不导出托管凭据就认定原包安全。

### 7.2 Hooks 逐项归类，而非全部机械转成 Mods

| 原 Hook 类型 | 目标归属 |
| --- | --- |
| 产物结构、内容完整性、证据校验 | Mod 的显式只读检查动作；保留结构化失败原因和证据。 |
| 需求/设计等业务审批 | 阶段声明的人工决策点，绑定产物版本。 |
| 越权路径、工具/执行边界保护 | 保留在可信平台或受控 Hook 边界，不能因阶段检查存在而移除。 |
| 变量替换、知识注入 | 配置解析与上下文提供器，按版本准备并复用。 |
| 自动更新 checkpoint | 新路径取消，交由平台条件提交；旧兼容路径继续按原协议运行。 |
| 同时校验和修复/同步状态 | 拆成检查与显式修复动作；修复后产生新产物身份并重新验证。 |
| 通知、进度和审计 | 消费持久运行事件，按权限投影，不能监听回调就认定副作用成功。 |

为每个旧 Hook 建立映射：触发条件、输入、读写、副作用、失败语义、新归属、验证样例和迁移状态。没有归属或未验证的必要 Hook 是迁移阻断项。纯 Python 校验器可以继续使用，替换语言不是验收标准。

## 8. Code 与工作树进度

本节只适用于 AutoBiz 代码交付按需启用的 Git 能力。目标执行关系：外层阶段操作 → 通用子运行（AutoBiz 称 Code 子运行）→ 批次/子 Agent → 通用资源引用 → Git 工作树提供器。子运行完成与父阶段通过是不同事实，由父阶段声明的检查和审批条件决定是否提交。

通用资源层只持有资源身份、提供器身份、授权范围、owner、父操作、版本和生命周期记录。Git 提供器实现授权仓库、base/head、租约、跨步骤复用、封存、候选核对和清理。公共层控制是否允许操作并记录执行事实，提供器完成实际操作并返回可核对证据；同一资源只有一个实际操作 owner。

工作树可在实现、评审、测试间复用；脏工作树或结果不明时保留并提示处理，不能直接删除。未启用 Git 提供器只阻断依赖它的 Code 路径，不影响需求生成、独立业务流程或简单 Mod。首期抽取现有工作树能力的最小适配接口，不建设通用资源市场；提供器不支持的生命周期操作明确返回不支持，不能虚构成功。

Workflow 的确定性节点调用受控动作完成资源准备、查询与结果登记；模型节点负责实现和专业评审。动作与父运行持久关联，重启时先核对，不能把一次模型输出缓存当成外部动作恰好执行一次的证明。

进度展示由插件侧视图 Mod 消费授权后的通用运行/资源快照，展示各工作树的任务、阶段、检查、耗时及待处理项。平台负责可靠事件与权限，插件决定呈现方式。仅当公共协议已有所需信息时，新增这种展示才无需平台改代码。

过渡期可将旧 Code 执行器封装为一个受控子运行，但必须禁用其外层 checkpoint 推进，并明确它仍持有的资源及核对方式。只有完整复用、多仓库、取消、重启和合并验收通过，才移除旧控制面。

## 9. 创造者的可靠闭环

统一过程为：识别意图 → 发现能力 → 提议变更 → 生成候选 → 静态与执行前诊断 → 隔离试用 → 汇总证据 → 对话修改 → 保存/使用/导出。

- **能力发现：** UI、模型工具和插件声明使用同一机器可读能力描述，分别返回可直接做、有条件可做、缺少能力及解决入口。存在工具名称不等于任意插件都可使用。
- **受控修改：** 插入阶段、修改 Skill、修改检查分别计算影响；保留源身份和必需规则，禁止模型自动删除保护来消除错误。
- **自修复：** 可修复生成源码、引用、格式和可重现样例失败；权限、凭据、业务决策及无法判明的外部结果必须转为明确待处理项。限定修复轮数并显示剩余问题，不能承诺任意旧插件自动转换成功。
- **原始插件首次模块化：** 先生成资源及 Hook 语义清单，再建议契约和映射；无法识别的动态脚本保留兼容执行或要求作者提供适配，禁止靠静态猜测宣称等价。
- **交付对账：** 安装以候选身份、安装注册和实际文件身份核对；导出核对目标文件及包摘要。明确未发生方可重新准备，部分发生进入修复，无法判断保持 unknown。重试不能覆盖不相关用户文件。
- **直接使用：** 保存成功定位唯一交付物，进入绑定预检并复用有效配置；聊天扩展进入会话，项目模板进入任务，不让用户猜入口。

整个闭环共享任务 ID、候选版本、试用运行和交付记录，保留底层独立身份。为了视觉连贯而把所有运行共用一个会话或取消隔离并不合理。

| 状态存储 | [会话状态](../src/main/mods/v2/named-state.ts)、[持久 store](../src/main/mods/v2/state-store.ts) | 不将现有会话状态或普通 KV 当成跨会话业务事务；首期使用 Host 专用协议，不先造通用数据库框架。 |
| 交付 | [项目交付服务](../src/main/mods/devtools/creator-project-delivery.ts) | 沿用确认和未知态保护，核验各交付路径都有对账与可恢复入口。 |
| 使用入口 | [已安装插件入口](../src/renderer/src/components/customize/InstalledPluginProjectEntry.tsx)、[本地项目面板](../src/renderer/src/components/harness-board/LocalProjectsPanel.tsx) | 关联统一任务，带入模板、目录与配置，消除重复选择和机械推进。 |

新协议的命名、IPC 和数据库迁移在各实施阶段确定。应用版本继续固定 2.0.0；协议版本和插件版本独立管理，不能因为应用版本不变而静默改变安装包语义。

当前 [Host 状态定义](../src/shared/project-runtime/host-types.ts) 尚无持久等待用户输入状态；[用户输入服务](../src/main/services/user-input.ts) 的内存请求不能直接视为重启恢复。[Host 存储](../src/main/harness-board/project-runtime/host-store.ts) 当前按工作区约束活动操作。上述新增协议须同时更新 Schema、持久化迁移、IPC、执行器、UI 和恢复测试；版本不兼容必须在执行前诊断，不能让新 UI 配旧后端静默降级。

## 11. 实施顺序与不可省略的验收

| 阶段 | 交付 | 完成门槛 |
| --- | --- | --- |
| D0 业务与协议基线 | 旧规则映射、真实样例、三项硬约束及协议增量清单 | 必需语义都有目标归属；固定最小契约与兼容策略，旧项目可继续使用；记录性能基线。 |
| D1 最小原生闭环 | 最小契约编译、产物/检查身份、需求转换 → PRD → 规格 → 设计确认、统一任务入口 | 不调用旧外层 writer；输出后审批、输入等待续接、并发提交和重启核对通过；已配置路径无机械推进。完成一次非 Code 的修改→试用→保存→使用。 |
| D2 业务覆盖与通用验证 | 知识版本、配置绑定、必要 Hooks 显式检查、交付对账、更新/撤销策略 | 保留已映射必要规则；换机和知识/契约变化通过；独立供应商流程、无项目运行时的简单 Mod 均通过。卸载后会话可读、无关运行不受影响。交付对账和直接使用不等待 Code 改造。 |
| D3 Code 可选资源支线 | 确定性 Workflow 动作、Git 提供器、跨阶段工作树、父子凭据 | 多仓库与批次依赖、实现/评审/测试、取消、恢复、合并冲突和响应丢失通过；无双 owner；无 Git 插件不受影响。 |
| D4 计划演进与复杂调试 | 运行中计划迁移、受影响范围重验、复杂子运行调试与接受 | 中途插步、修改 Skill/检查后不消费过期凭据；活动资源核对完成后才迁移；安全边界不支持的情形明确阻断。 |
| D5 迁移与交互收敛 | 稳定边界导入旧项目，旧入口迁移，帮助与文档 | 历史记录不冒充新凭据；迁移可核对，既有项目不被改写；普通用户无需理解 Mod ID 和运行类型。 |
| D6 性能与联合验收 | 热路径测量、优化及完整回归 | 业务、安全、跨平台、UI 连续任务和包内路径通过；提供优化前后数据及剩余限制。 |

依赖顺序为 D0 → D1 → D2；D3 的接口设计与 D2 可并行，完整 AutoBiz 交付依赖 D2、D3 均通过。D4 的纯产物计划变更依赖 D2，涉及 Code 资源的调试另依赖 D3。D5 的旧项目迁移必须等待其实际使用的全部能力通过。D6 每阶段累积验证，最终联合验收，不把风险发现全部留到最后。

可并行分工：平台契约/执行、插件业务提取、统一任务 UI、独立验证。先固定共享类型与样例，划分文件所有权，避免多个 agent 各建一套契约。每个里程碑交付可独立验收的范围，不要求首个简单插件等待全部复杂资源能力。

独立业务验证使用供应商准入流程：资料归一化 → 合规检查 → 风险评估 → 人工批准 → 归档。它使用相同契约、上下文、审批和恢复协议，平台代码中不得出现供应商或 AutoBiz 专有分支。数仓衍生另外验证专业模块复用，但不能单凭 AutoBiz 衍生包证明平台通用。

另外验证一个只读工具 Mod 和一个观测/界面 Mod：未启用项目运行时、未配置 Git 提供器时仍可安装、授权和使用。创造者验收只给出“插入需求转换”和一个丢失需求的反例，不手改 YAML、ID 或 Host manifest，必须完成修订、试用、保存及启动新任务。

最低异常集合按实际启用能力执行：公共层验证授权撤销、版本错配、重复调用和作用域隔离；流程层验证缺失/变化/恶意路径输入、并发提交、过期凭据、审批后产物变化、输入卡关闭/重复回答/重启续接、计划迁移迟到结果；交付层验证部分安装/导出、凭据缺失及跨机器绑定；外部动作验证多子项部分成功、取消后结果到达和重启 unknown；Git 提供器另外验证脏工作树、合并冲突、资源代次及旧项目副作用核对。Git 专项不作为普通 Mod 的门槛。

## 12. 性能和业务效果的验收方式

新路径状态读取直接查询平台投影，目标是不为一次外层状态查询启动 Python。固定调度动作不调用模型。知识采用版本缓存与单飞；上下文按阶段依赖加载，详细记录留在可查询证据中，避免每次将全量历史注入提示词。

记录状态读取 p50/p95、上下文准备耗时、子进程数、重复读取字节、纯调度模型轮次及 Token、任务总 Token、用户重复输入与机械操作数、取消到资源稳定时间。相同样例、模型、硬件及缓存条件下比较；没有测量前不承诺具体节约比例。

业务效果看需求覆盖、缺失拦截、产物来源正确性、审批对象正确性、重复副作用和可恢复性。减少 Token 不能以丢失关键知识或删除真实校验为代价。

聊天滚动和闪屏属于渲染性能专项：单独测量长会话滚动帧、布局变化和渲染次数，复用既有优化工作。流程重设计能减少状态轮询及重复注入，但不能据此宣称根治渲染问题。

## 13. 迁移与完成边界

只在无活动操作、无 unknown、无未确认合并及无归属不清资源的稳定边界迁移。先保存旧项目与安装身份，明确旧 checkpoint 对应的新计划，重新验证将被消费的历史产物；历史成功和审批保留来源，不伪造新运行成功。

切换后旧 writer 和旧恢复循环对该绑定停止写入；新流程不双写旧 state.json。没有新副作用时可撤销新绑定；已有新产物、Git 提交或外部发布时，先核对再通过受检查的导出或前向迁移处理，不能用覆盖状态文件实现“回滚”。

**最终完成标准：普通用户在一个任务中交付完整业务；创造者可通过通用协议衍生并验证插件；AutoBiz 的必要知识和规则有执行证据；独立业务场景同样成立；旧项目有明确迁移路径。** 文件变少、改写语言、测试数量或打包成功都不能单独代表该目标完成。

三个子 agent 独立评审，首轮各提出六项意见，内容有重叠。主审结合源码合并修订后，三者复读更新稿，均确认各自审查范围内没有阻断定稿的矛盾。评审只验证设计一致性，不替代运行测试，也不证明方案在所有业务下最优。
