# 工作区批量删除修复

基线：`origin/UAT`，`d49494b5`。分支：`codex/fix-workspace-deletion`。

## 原因与修改

1. 批量删除的 `requireIdle` 复用了 `isThreadForkBusy`。复制会话需要稳定的结果边界，
   因而会拦截未确认的 worker/workflow 通知，也会把缺少工作区路径的旧模式会话视为忙碌。
   这些条件不等于任务正在执行。删除现在通过独立检查查询前台运行、外部运行所有者、
   workflow 和 worker 的实际运行状态；取消中的前台运行仍等待结束并重新检查。
2. 旧检查会恢复 coordinator 历史状态、读取待通知 workflow 结果，并为部分终态 worker
   加载输出、生成快照。删除不需要这些消息内容。新检查完全绕过这条历史恢复路径。
   批量处理继续在任务之间让出事件循环，失败分支也让出；进度更新限制为约每 100 ms
   一次，并确保最终计数送达，避免每个快速 IPC 都触发侧栏刷新。
3. 原循环在首个删除错误处返回，前端还会因组内任一运行任务禁用整组删除。
   现在每个失败项保留并继续处理后续任务，返回的剩余列表仅包含失败项。
   工作区、项目组、特性组入口均允许执行，实际运行状态由后端逐项判定。
   对话框显示已处理、已删除、已跳过数量，并允许重试剩余项。
4. 复检发现：缺少工作区路径的 workflow/coordinator 任务不能直接放行，否则后续依赖路径的
   工作树检查会被跳过。现在批量和单独删除都会在清理开始前返回明确的路径错误，保留任务；
   普通模式的未关联工作区任务仍可删除。
5. Electron 性能测试捕获 1 万条消息删除时主进程停顿 288 ms，CPU profile 指向 SQLite
   删除和 COMMIT。对至少 1000 条消息的任务，保留原有原子删除事务，但暂时禁用该事务的
   自动 WAL checkpoint，提交后由后台 Worker 执行 PASSIVE checkpoint。连接策略在 finally
   中恢复，Worker 启动失败、崩溃或超时不会将已提交的删除变成失败；小任务不启动 Worker。

## 保留的边界

- 删除仍逐项提交；仅对后端已确认删除的任务清理前端状态。
- 会话 incarnation、分组归属、外部运行所有者检查仍保留。
- 未合并、未丢弃或清理异常的 workflow worktree 仍由独立持久化检查保护。
- 删除事务和检查点文件清理仍保持现有顺序，后台 WAL checkpoint 只改变提交后的维护位置。
  仍有同步 SQL 删除成本；性能结果来自隔离测试数据，不代表所有历史数据规模。

## 复检后的 Electron E2E 和性能回归

命令：`npm run test:workspace-deletion:e2e`。使用隔离 HOME、APPDATA、SQLite 和工作区，
真实构建的 Electron、preload、IPC、React 侧栏和数据库，不替换删除处理器，不调用模型。

- 单独和批量 IPC 都拒绝缺失 workflow 工作区的删除。
- 真实侧栏批量删除保留失败项，删除其前后的成功项，重试只处理剩余项。
- 创建实际 workflow run JSON 和未合并文件，确认已知/缺失路径时任务与文件均被保护。
- 小历史 100 条消息、大历史 10000 条消息，每条 2048 字符。大历史重复 3 轮。
- 真实侧栏删除 20 个任务、2000 条消息，其中包含一个空闲 coordinator 任务。
- 性能预算：单任务删除小于 5 s，主进程定时器最大间隔及渲染帧最大间隔均小于 250 ms；
  20 任务批量小于 10 s。实际测量包含 IPC 和磁盘清理。

最近一次完整 E2E 结果：

| 数据规模 | 删除耗时 | 主进程最大间隔 | 渲染帧最大间隔 |
| --- | --- | --- | --- |
| 100 条消息 | 152.5 ms | 33 ms | 7 ms |
| 10000 条，第一轮 | 413.2 ms | 158 ms | 7 ms |
| 10000 条，第二轮 | 399 ms | 156 ms | 7.1 ms |
| 10000 条，第三轮 | 382.7 ms | 150 ms | 7.1 ms |
| 20 任务、2000 条消息 | 3261 ms | — | — |
