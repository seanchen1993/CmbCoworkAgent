# UAT 1.5.2 聊天跳动与闪屏排查

日期：2026-09-14。源码基线：UAT，`4dedee74`。

已在真实消息组件和用户提供的 Windows 安装包中确认两个布局问题，并在工作区修复：虚拟列表漏算消息行间距；长思考区在虚拟滚动卸载、重挂载后丢失展开状态。长思考内容会放大它们造成的高度变化。

这足以解释一部分消息上下跳动、内容突然收缩或闪动，但不能据此断言所有用户的整窗口闪屏都由同一个原因造成。

## 1. 虚拟列表漏算每行 16px 的间距

位置：`src/renderer/src/components/chat/ChatMessageVirtualList.tsx`，`VirtuosoMessageListWrapper`。

原实现给 Virtuoso 的 List 容器设置 `space-y-4`。Tailwind 将其转换为直接子元素之间的 16px 外边距，直接子元素恰好是 Virtuoso 测量的消息 item。

实际浏览器测量：普通消息 item 的边框盒高度为 66.75px，Virtuoso 记录约 67px，但下一行实际还相隔 16px。这 16px 没有进入它的虚拟位置计算。虚拟列表切换渲染范围时，已挂载 item 的数量变化，实际内容高度与虚拟 padding/offset 的偏差也随之变化。

`ChatContainer` 又会在内容高度变化时执行底部跟随。因此，错误高度测量、虚拟位置修正和底部跟随会作用于同一个视口，表现为回跳或位置不稳定。长思考区增长、折叠、重挂载时，更容易触发范围变化。

修复：将间距移到 item 内部，使用 `[&>[data-item-index]]:pb-4`。保持消息间的视觉间距，同时让这 16px 成为测量高度的一部分。每个 item 的 padding 固定，不随它是否成为当前渲染窗口的最后一项变化。

修复后实测：普通 item 高度为 82.75px，Virtuoso 记录约 83px，item 外边距和盒子之间的未测量间隙都为 0。

这与 [Virtuoso 官方排查文档](https://virtuoso.dev/react-virtuoso/troubleshooting/) 对动态高度和 item 外边距的说明一致。

## 2. 思考区的状态和消息组件生命周期绑定

位置：`src/renderer/src/components/chat/MessageBubble.tsx`。

原实现使用本地 `useState(false)` 保存展开状态，另用两个 `useEffect` 在流式思考开始后展开、正文或工具调用出现后收起。用于判断是否已经自动展开/收起的 ref 也保存在消息组件内部。

虚拟列表会卸载离开渲染范围的消息，因此可以稳定复现：

1. 展开一条含 150 段思考内容的历史消息。
2. 滚到对话顶部，使该消息被卸载。
3. 再滚回这条消息。
4. 原实现重新以收起状态挂载，`aria-expanded` 从 `true` 变为 `false`。

对于流式思考，重挂载还会先提交收起状态，再在 effect 中打开。这个额外的短行到长行变化会干扰虚拟列表的测量。思考越长，重挂载时的高度差越大。手动收起的流式思考也会在重挂载后被重新自动展开。

修复：

- 新增 `reasoning-expansion-context.ts`，在当前会话列表的生命周期内保存自动阶段与手动选择。
- 缓存上限为 500 条思考区状态，切换会话时使用独立缓存。
- 在提交 DOM 前解析自动展开/收起状态，避免先提交错误行高再通过 effect 更正。
- 保存手动选择和自动操作是否已经执行的标记，同一阶段的后续 token 和虚拟重挂载不重复覆盖用户操作。正文/工具调用首次出现时，仍按原行为自动收起一次。
- 保留自动行为：纯思考输出开始时展开；开始正文/工具调用时自动收起；只有思考内容的完成事件保留已展开状态。

缓存只保存少量布尔值和阶段标记，不保存思考文本，也不修改数据库或持久化消息。

## 3. 为什么长思考更容易暴露问题

聊天内容按消息进行虚拟化。一条消息内的长思考仍然是一个高度较大的 item。它的展开、收起或重新挂载，会改变远大于一个视口的高度，放大错误测量和状态重置的后果。

另外，`StreamingMarkdown` 对累计内容节流，且在内容超过 64 Ki 字符时切换为头部、折叠提示和尾部预览。这些是现有的性能保护措施，也会带来真实的内容高度变化。本次没有修改该策略，未将其单独判定为已证实根因。超过该阈值的复杂 Markdown、真实模型交错工具输出和不同显卡仍是后续 UAT 覆盖项。

## 5. GPU 与整窗口闪屏的边界

在当前受限自动化环境中，默认 GPU 模式启动诊断副本时，GPU 子进程反复以 `-1073741515`（`0xC0000135`）退出，最终出现 `GPU process isn't usable`。该状态常见于依赖加载失败，但本次没有确定具体缺失的依赖，也不能将测试环境现象归因于最终用户的显卡驱动。

因此上述 Electron 对照使用 `--disable-gpu --in-process-gpu` 完成。这证明消息布局缺陷无需硬件加速也能出现，修复在该模式下有效；没有验证受影响用户的原生 GPU 路径，也没有在产品中全局关闭硬件加速。

如果修复后仍出现整窗口闪屏，应结合受影响机器的应用日志区分 `render-process-gone` / 自动重载和 GPU 进程错误，并在相同数据、相同窗口尺寸下对照开启/关闭硬件加速。该步骤需要受影响机器上的证据。
