# DevClaw 内置能力与项目插件平台实施方案

本方案在 Mods_v2 工作树推进 DevClaw 自有内置能力、轻量插件开发和项目模式扩展。借鉴 CC 的功能划分、事件组合与测试思路，在本工程现有实现上独立开发。AutoBiz 是复杂项目插件的兼容实例，通用接口同时服务其他开发者的插件，不把 AutoBiz 的阶段、目录或 Python 实现写成平台规则。

工作树为 `C:/ai/CmbCoworkAgent-mods-v2`，分支为 `codex/mods-v2`。方案基于 2026 年 10 月 12 日的工作树内容，包括现有未提交实现。用户已授权持续实施，实际完成情况与未验收项见同目录实施账本；不以本方案目标描述代替交付证据。各阶段完成必须有独立验收记录，已有项目能力包交付记录不代替本方案验收。

## 目标与交付边界

交付三条可以分别使用的路径：

| 使用者 | 开发方式 | 平台承担的工作 |
| --- | --- | --- |
| 只需要命令、工具或界面的开发者 | 继续使用 Skill、MCP 或灵件，不要求接入项目流程 | 安装、权限、命令、界面、诊断 |
| 开发简单项目流程的开发者 | 使用轻量项目模板，声明阶段、输入、产物和校验 | 默认看板、会话入口、项目状态、审批、运行记录 |
| 已有复杂项目插件的开发者 | 保留原适配器、Skills、Hooks、验证器和状态存储，逐项增加能力声明 | 通用控制台、标准动作接口、证据展示、可选流程编排 |

第一批目标是让独立开发者完成一个两阶段项目包时，无需自己编写看板、IPC、状态数据库和恢复页面。复杂业务规则仍由插件负责。已有项目保持当前路线，启用新界面不改变执行规则。

项目模式使用过程也要减轻：项目身份、当前阶段、工作区、插件版本由宿主提供；只让用户填写任务目标和必要业务参数。平台展示推荐下一步和实际阻塞原因，不再要求用户在多个面板重复填写 Feature、路径和阶段。

当前项目创建类型含 `projectCode`、`projectFromLean`、`systemId`、`systemName` 等企业字段。轻量本地项目应采用新的基础创建输入，企业关联作为可选扩展；不让第三方作者填写假系统 ID，也不放宽企业项目原有校验。旧持久化记录由兼容投影读取，新旧类型使用明确的项目类别区分。

本方案不要求完整复刻 CC API，不自动翻译任意 Python，不自动拆解紧耦合业务阶段，不把单文件模型检视当成完整项目验收。在线插件市场、任意循环工作流、跨机器执行恢复放在后续扩展，不阻塞首版。

## 当前基础与需要打通的地方

| 当前模块 | 已有能力 | 本方案增量 |
| --- | --- | --- |
| `src/main/agent/agents-md.ts` | 规范文件加载、来源、预算与本地覆盖 | 统一的规范查看、冲突解释和生效范围 |
| `src/main/mods/`、`src/main/mods/v2/` | 隔离运行时、授权、事件、界面和 SDK | 自有内置目录、项目能力桥接、兼容性声明 |
| `src/main/mods/devtools/` | 检查、类型、创作、试用、安装与版本回退 | 模板生成、项目诊断、隔离开发运行、统一契约测试与打包 |
| `src/main/harness-board/` | 插件适配、项目与 Feature、托管、人工门禁 | 通用项目运行接口和协调层；保留现有服务路径 |
| `src/shared/project-capability.ts` | 严格的 `devclaw.project/v1` 静态说明 | 保持协议不变，另加可选运行声明 |
| `ProjectCapabilityPanel.tsx` 与 controller | 阶段说明、产物诊断、原会话准备 | 一次配置、项目动作、证据有效性与恢复入口 |
| `src/main/mods/flows/` | 动作组合、部分项目上下文与恢复 | 在已验证项目协议内运行阶段动作，统一执行归属 |
| `src/main/mods/v2/autobiz-*` | 固定旧来源的特定验证与状态提交 | 保持版本边界；新复杂插件通过通用适配器接入 |

已确认的限制：项目能力 v1 的 `before`、`after` 是说明文字；创作检查尚无通用依赖注册表；部分 Flow 原生配置拒绝未覆盖的项目策略；托管运行重启后会失败而非继续执行。代码版本回退已有实现，但业务状态回退不是它的承诺。

## 六项自有内置能力

六项均为本方案正式交付范围；名称与 ID 为建议，最终名称统一后记录映射。下表描述目标，不代表六项当前已全部实现。随应用提供，普通用户无需自行下载、导入或组装才能使用；普通聊天可使用通用能力，绑定项目后增加阶段、批次与原验证链的上下文。

2026-10-12 核对 [Claude 官方内置条目说明](https://code.claude.com/docs/zh-CN/plugins/mods/overview)：官方界面使用 `cc-plugin-*` 名称；`plugin-authoring` 提供 Skill，本身没有 Mod 代码；`you-should-know` 为默认关闭的侧边 Agent；`telemetry` 为分析记录能力。DevClaw 对应提供本产品的创作、项目建议和运行度量，不把六个名称都解释为六份相同形态的运行模块。

内置身份由宿主注册，上传包不能通过名称或 manifest 声明获得内置权限。展示名称使用 DevClaw 名称；现有 `cmb.*` 协议和数据键不因品牌改名而批量迁移。普通内置增强可关闭，组织强制约束依旧由宿主执行。

| CC 条目 | 内置能力与建议 ID | 现有落点与新增模块 | 交付行为与验收 |
| --- | --- | --- | --- |
| `agents-md` | 项目规范 `devclaw-project-instructions` | 复用 `agent/agents-md.ts`、`context-sources.ts`；新增规范投影与查看界面 | 展示来源、层级、作用范围及已注入/截断/未加载原因；与实际请求一致，不重复注入，不改变既有优先级 |
| `diff` | 变更审阅 `devclaw-change-review` | 复用 Git 服务、现有 diff 展示；新增 `mods/builtins/change-review.ts` | 支持明确的分支、会话、需求、阶段或批次基线，并关联对应检查；缺少基线时明确不可用，已有未提交修改不冒充本次修改 |
| `sec-default` | 组织策略 `devclaw-policy` | 复用 `mods-policy.json`、runtime authority 和工具权限宿主；新增只读解释器 | 展示实际命中规则、来源、范围与处理办法；关闭灵件仍保留强制约束，用户包无法提升权限 |
| `telemetry` | 执行度量 `devclaw-observability` | 复用 trace、`services/event-reporter.ts`、`harness-board/managed-run-telemetry.ts` | 串联阶段耗时、返工、失败、用量与审批等待；区分事实/估算/未知；本地可用，外发沿用现有配置与脱敏 |
| `plugin-authoring` | 扩展开发助手 `devclaw-extension-authoring` | 扩展现有 authoring tool、模板、CLI、Skill 与离线教程 | 自然语言或模板创建，复用公开动作，检查、隔离试用、安装与回退；当前版本的 API 能力来自真实类型与兼容目录 |
| `you-should-know` | 项目提示 `devclaw-project-advisor` | 项目事实规则与可选侧边 Agent，共用建议记录 | 规则提示缺产物、失效证据、待审批与下一步；侧边分析长任务中的遗漏和风险，默认关闭、限频限额、不自动执行建议 |

新增 `src/main/mods/builtins/registry.ts` 汇总固定身份、版本、真实提供器、能力和状态；扩展现有宿主内置身份机制，包括 `builtin-context-meter.ts`，不建立第二套权限或安装系统。可扩展命令、事件与界面使用既有灵件组合链；必须执行的约束继续在宿主边界生效。内置能力随应用版本交付，已实现部分可逐组开放，未实现部分不得标记 ready。侧边 Agent 可以默认关闭，但实现及验收属于最终范围；仅交付规则提醒不能标记第六项完整完成。

### 用户入口与默认行为

| 用户要做的事 | 统一入口与默认表现 | 防止增加操作负担 |
| --- | --- | --- |
| 知道本次遵循哪些要求 | 项目/聊天详情中的“项目规范”，按需展开 | 沿用原加载设置；展示开关不改变注入，语义冲突的模型判断标注为建议，不冒称已裁定 |
| 看这次改了什么 | 现有差异入口中的“变更审阅”，默认当前任务的有效基线 | 清楚区分全部工作区改动与本次改动；无 Git 仓库提供明确说明，不生成虚构差异 |
| 明白为什么被拦住 | 审批或失败处的“为什么需要确认／为什么不能继续”，详情进入运行过程 | 提供对应原审批/配置入口；无命中不常驻警告；组织管理数据只展示用户可见内容 |
| 看进度、结果与成本 | 现有“运行过程”，技术事件折叠 | 不再新增“可观测性”独立页面，不向聊天插入计量消息，不逐事件整页刷新 |
| 自己制作或复用功能 | 灵件中的“自己制作”，可选择描述需求、模板、新建项目模板或复用已有步骤 | 共用检查、试用与安装向导；保存不执行，试用范围和正式安装区别清楚 |
| 得到值得处理的提醒 | 项目页的“下一步”及运行过程中的“建议” | 规则不调用模型；模型建议默认关闭，长任务中不挤占输入框，不抢焦点或重复弹窗 |

规范、审阅、策略解释和本地度量按需可用；制作由用户进入或提出制作请求触发。可选展示与建议使用已有设置管理，普通使用不增加六个前置开关。规则展示可以收起，原审批门禁不能因此失效。

### 六项专项验收

1. 项目规范：从实际注入结果投影来源与预算，不另跑一遍文件发现充当事实。覆盖父子目录、工作区切换、子任务、截断、文件变更和重复来源。无法自动解释的自然语言冲突显示“需要核对”，可选模型分析不更改规范。
2. 变更审阅：启动任务时捕获可解释的工作区基线，包含已跟踪及未跟踪文件的适用范围；阶段和批次继承明确的快照关系。覆盖预先脏工作区、重命名、删除、二进制、子模块及缺少历史快照。差异关联真实输入指纹和测试范围；改动归属不能仅凭时间或 Git HEAD 推断，存在并行编辑时标明归属不确定。
3. 组织策略：解释来自真实决策结果，覆盖普通工具、灵件工具、Skill/Hook、托管与已开放 Flow。用户包伪造内置名称、关闭展示或改写提示不能绕过原批准/拒绝。组织强制、项目规则及可选建议分别展示；普通 AGENTS 内容不自动晋升为组织强制规则。
4. 执行度量：复用现有事件和账本作统一投影，关联事件具备版本、稳定 ID、宿主身份、时间、结果和来源；去重、分页、有界保留，不能另造一份完成状态。区分总用时、执行及审批等待；并行子任务耗时不能直接相加当作总用时。缺模型价格或用量时显示未知，估算标注依据；本地查看与是否允许外发相互独立。
5. 扩展开发助手：内置版本匹配的制作 Skill，提供“从零创建”和“复用已有步骤”两个完整案例。用户描述需求后经历生成、检查、隔离试用、修正再试用、应用；运行调用固定旧版本，空闲边界更新。验证缺依赖、类型错误、权限变化、试用失败、安装及回退；不能把仅提供五个 CLI 命令当成自然语言创作已交付。官方创作参考见 [创建一个 mod](https://code.claude.com/docs/zh-CN/plugins/mods/create)。
6. 项目提示：规则与模型建议分开标明。建议绑定项目、阶段、运行和事实指纹，状态变化失效、同一事项去重，支持忽略和关闭。侧边 Agent 只获所需读取能力，无提交阶段/自动审批/修复写入工具；有并发上限、调用/用量预算及取消机制，收费未知时不能声称硬金额限额。关闭、切项目或主任务结束时停止其后续调用，失败不阻塞主任务，不形成自我触发循环。最终演示长任务发现遗漏、用户查看依据、选择处理或忽略的完整路径。

### 复用清单与兼容边界

| 现有基础 | 本方案使用方式 |

## 降低插件开发负担

### 区分作者成本和业务执行成本

作者当前需要连接多种 manifest、平台命令、Skill、Hook、状态协议、组件、动作和打包步骤。新方案由模板与通用运行时接管重复部分。用户当前需要安装、授权、绑定项目、选择组合、保存应用再运行；新向导把这些步骤整合为一条可见过程，仍明确区分保存配置和开始执行。

业务执行采用插件明确支持的路线：简单文档任务可以只有“起草、验收”两阶段，代码任务可以使用“实现、检视验证”模板。AutoBiz 的标准、精简、动态路线由自身工作流编译器决定；平台仅呈现已支持选项，不根据任务看起来简单就移除原门禁。已有 Feature 不自动换路线。

### 轻量项目模板

新增 `examples/project-docs-lite`，作为真正可安装、可执行的非 AutoBiz 项目插件。初版作者只需维护插件元数据、两阶段声明和一个 Skill 文件；通用文件存在性、JSON Schema 等检查由宿主提供，需要专业检查时才增加自定义校验器。只验证文件存在时明确显示检查范围，不宣称内容质量合格。

推荐目录如下，文件名中的运行声明为本方案新增协议，当前版本尚不支持：

```text
project-docs-lite/
  plugin.json
  devclaw.project-runtime.json
  skills/draft/SKILL.md
  tests/project-contract.json
```

测试样例由脚手架生成。默认看板、状态存储、项目创建、阶段会话、产物预览由宿主提供。帮助文本可由运行声明生成到内部展示结构，作者无需重复维护 `devclaw.project.json`；已有 v1 文件继续使用原解析器，二者同在时明确帮助文案的覆盖规则，执行规则只读运行协议。

轻量初版支持线性阶段、显式人工审批、本地校验、成功推进和修复后重试。不支持作者自定义无限循环、动态并行调度和任意状态写入；这些需求走完整适配器路线。每个新项目明确记录状态所有者，轻量项目由宿主管理，旧插件项目由原插件管理。

### 开发工具与一条预览路径

沿用当前 `openwork plugin check|inspect|types`，新增以下命令作为拟议开发接口；完成对应阶段前，教程不得写成可用命令。可以增加 DevClaw 品牌入口别名，但保留原命令兼容。

| 拟议命令 | 输出与边界 |
| --- | --- |
| `plugin init <dir> --template command|project-lite|legacy-adapter` | 新目录、模板、声明类型、最小测试；不覆盖已有文件 |
| `plugin doctor <dir>` | 声明、依赖、运行时、平台、Skill 引用、动作输入输出、缺失能力诊断；不默认执行业务脚本 |
| `plugin dev <dir>` | 隔离项目与预览会话、当前源码版本、日志；只对明确开发会话生效 |
| `plugin test <dir>` | 生产协议校验与契约测试；默认隔离文件和可控外部服务，真实服务需明确测试配置 |
| `plugin pack <dir>` | 可安装包、版本与摘要、依赖清单、测试范围、排除凭据的检查报告 |

开发会话保存源码后，在空闲边界加载新版本；运行中的调用固定旧快照。权限扩大或新外部写入能力需要按现有授权规则处理，不能用开发模式绕过。正式项目依然使用安装版本，编辑本地文件不改变正在交付的插件。

UI 提供“创建功能／创建项目模板／接入现有项目插件”三种入口。项目向导自动从当前项目填入身份和工作区，一次展示插件版本、环境缺口、能力范围和将要应用的组合，最后提供“保存配置”与“开始任务”两个明确动作；已有有效授权按现有规则复用。

## 通用运行协议与模块划分

### 可选运行声明

保留严格的 `devclaw.project/v1` 原样解析。新增独立的 `devclaw.project-runtime.json`，协议名建议 `devclaw.project-runtime/v1`。插件安装器通过明确能力声明选择运行适配器，不能仅根据包名判断项目类型。

运行声明应包括协议版本、插件身份、状态所有者、模式 `host` 或 `legacy`、阶段或阶段提供器、公开动作、产物、校验器、审批要求、所需运行环境及恢复能力。通用字段不包含 `dev.code`、`.autobizdevops`、发布单元或公司知识平台的固定含义。

轻量包使用 `host` 模式；复杂插件使用 `legacy` 模式，由适配器返回实际工作流。旧 `board_core/board_config.json` 未增加声明时自动使用旧适配器，行为保持。新运行声明损坏时新能力不可用，但原项目查询和恢复入口保留；如果项目已采用新强制规则，不能靠回退旧入口绕过这些规则。

### 项目能力接口

拟新增 `src/shared/project-runtime/` 和 `src/main/harness-board/project-runtime/`。前者定义有版本的数据协议，后者实现宿主协调器、轻量适配器和旧适配器桥接；避免继续把所有职责堆入 `harness-board/service.ts`。

| 接口 | 输入与结果 | 执行规则 |
| --- | --- | --- |
| `describe` | 阶段、动作、校验、所需环境与实际支持能力 | 读取声明不执行插件代码；动态检查作为独立明确操作 |
| `snapshot` | 当前阶段、产物、版本、有效证据引用 | 由绑定项目的适配器提供，不信任界面自报状态 |
| `prepareAction` | 动作引用、参数、状态版本，返回执行计划或缺口 | 只准备；不写状态，不启动模型，不自动批准 |
| `startAction` | 已核对计划与宿主运行身份，返回运行记录 | 重新检查授权、状态、审批和并发归属，经原工具与 Hook 链执行 |
| `validate` | 校验器 ID、输入与运行范围，返回结构化结论 | 校验可能运行命令或产生报告；标明副作用类型，不假装只读 |
| `requestTransition` | 目标转换、期望状态版本、证据引用、幂等键 | 校验完成与审批后调用唯一转换路径，不允许直接改状态文件 |
| `cancel`、`reconcile` | 运行身份或未知操作，返回真实状态 | 按适配器声明执行；不支持恢复时明确要求人工处理 |

宿主派生 projectId、featureId、workspace、pluginId、插件摘要、stageId 和 threadId，插件只能提出动作请求。未支持的接口返回明确的 unsupported，不能把执行失败降级为成功。强制规则、可选建议、产物存在、校验通过分开建模。

为灵件增加受限桥接 `src/main/mods/v2/project-sdk.ts`，先开放读取和动作准备，再按阶段开放执行。IPC 复用 `src/main/ipc/harness-board.ts` 边界并补 preload 类型。Renderer 不持有通用 shell 执行入口。

### 状态与证据

新建标准证据记录，至少包含：插件与验证器版本、项目与阶段身份、运行与动作身份、代码及输入指纹、检查范围、结果、产物引用和时间。结果区分通过、失败、阻塞、未知、过期和仅供参考。时间新不等于证据有效；输入或规则变化需重新判定。

旧插件适配器只报告自己能证明的范围。仅有历史日志的结论标为历史记录；没有指纹则有效性未知，不能伪装成当前验证通过。原验证器支持延期、例外或受控跳过时保留其业务语义并展示依据，不在宿主另造更宽松或更严格的隐式规则。

宿主保存动作账本与证据索引；旧插件继续保存业务状态。不得新增一份可独立修改的 AutoBiz 阶段状态。轻量宿主项目使用单独的版本化状态服务，并具备事务更新和并发冲突检测。

### 执行归属和恢复

统一关联项目、Feature、阶段、ManagedRun、Flow、会话和审批。对同一受控转换只允许一个执行者持有当前状态版本；同一幂等键返回已记录结果，另一个过期请求必须冲突退出。操作账本本身不能保证第三方写入恰好一次，仍需适配器的幂等或核查接口。

执行协调器不能只锁新面板。开放前列清原会话、工具、托管、Flow、审批与插件脚本的实际写入路径，确认均进入原子版本检查/唯一提交边界。适配器逐项声明并验收版本条件提交、幂等与结果核查能力；不满足的操作保留原入口或明确不支持。仅新增宿主锁而旧脚本仍可独立写入时，不宣称全入口防重已实现。

托管运行负责项目推进，Flow 可以作为某阶段内部动作的执行方式。一个任务只能有一处修复重试预算；原插件批次调度和平台 Flow 不同时指挥同一批次。先保留当前拒绝未验证项目策略的检查，覆盖相应契约后才逐路径解除。

重启后的处理按能力分级：只读可重新执行；可证明幂等的动作使用原操作身份恢复；结果未知的写入先核查；缺少核查能力的旧插件继续人工恢复。审批记录持久化，但批准是否仍适用要核对动作、输入与状态版本，不能把旧批准套到新请求。

## AutoBiz 适配的具体边界

兼容基准固定为增强包使用的 `504e327d2f9a4d9e30e9f541c4432accf8000ad5`、版本 `1.0.87`。宿主现有原生适配固定 `8db1ec937d6ed3d271cb9dc540310d6633c91e70`，保留独立路径。不能只更换常量就接管新版业务。适配包记录明确支持的源版本和摘要，上游变化重新运行契约验收。

下表的 AutoBiz 路径来自该固定提交；它们是保留与调用的边界，不表示需要修改外部仓库。

| AutoBiz 模块 | 保留内容 | 新平台增加的适配 |
| --- | --- | --- |
| `board_core/board_config.json`、`inspect_state.py` | 项目与 Feature 状态、原 nextAction、平台命令配置 | 将原查询结果转为通用 snapshot；节点 ID 与参数含义不变 |
| `board_core/workflow.py`、`workflow_compiler.py`、`hooks/inspect_workflow_templates.py` | 标准、精简、动态阶段和跳过规则 | 展示实际可选路线；创建时固定版本；既有 Feature 不重编译成默认路线 |
| `hooks/init_workspace.py`、`render_collected_session_context.py` | 项目初始化、工作区、知识和项目上下文 | 环境诊断、参数自动填充；缺业务依赖明确阻塞，不编造上下文 |
| `skills/autobiz/`、`skills/autodev/`、其他原 Skills | 原任务指导和角色协议 | 用标准动作引用准备原 Skill 会话，避免重复复制提示词 |
| `hooks/hooks.json`、`state_checkpoint.py`、`stage_gate.py` | Hook 时序、阶段前后条件、阻断语义 | 将原失败映射为定位明确的诊断，初期只包返回值，不改变原脚本 |
| `human_gate_design_done.py`、宿主 Human Gate | Design 完成前的真实确认 | 通用面板展示并跳转原审批；新按钮不能直接执行脚本绕过 PreToolUse |
| `task_runner.py`、`code_execution_guard.py`、`frontend_route_write_guard.py` | 任务运行身份、文件范围、前端路线、Code 校验限制及原受限编译例外 | 动作界面按真实角色开放；原允许/拒绝判断均保留 |
| `workflows/code-batched-execution.workflow.js`、`parallel_batch_*`、`parallel_merge_train.py` | 批次依赖、Review、UTest、合并和最终验证 | 展示子步骤状态和证据；批次调度仍由原插件负责 |
| `evidence_kernel.py`、`evidence_store.py`、`verified_digest_guard.py` | 证据来源、摘要、新鲜度和失效规则 | 只读转换为通用证据结构；保留原验证器最终判断 |

重点场景：固定版本的 `code_execution_guard.py` 限制活动 Code task worktree 的验证命令，同时保留其严格识别的后端 production-only compile 例外；其他验证遵循 Review 后 UTest 的原判断。平台必须沿用原 guard 的全部允许/拒绝语义，不扩大编译例外，也不把合法例外一并禁掉。通用项目质量灵件在 AutoBiz 项目中尊重原执行角色和阶段，不擅自插入额外自动检查。

第一阶段只导出状态、诊断、产物读取和原会话准备。第二阶段仅对验证过的动作开放执行。`requestTransition` 若无法完整经过原 Hook、审批及写入链，就继续指向原会话；不为了补齐 API 数量单独调用 Python 提交脚本。

专用打包器继续保留上游原文件摘要核对。增强层放在本工程 `examples/autobiz-fullstack-mods`，通用适配层放在宿主新目录；外部原库修改另作版本化交付，不混入首次平台升级。

## 旧插件兼容约束

| 插件类别 | 默认行为 | 可选升级 |
| --- | --- | --- |
| 只有 Skill、MCP、传统 Hook 的插件 | 安装、启停、原调用不依赖项目能力或灵件授权 | 增加独立灵件或标准动作 |
| 只有旧 board_config 的项目插件 | 保留原适配器、原项目记录、原运行链 | 自动得到基础只读控制台，逐项声明新能力 |
| 已有 devclaw.project/v1 的项目插件 | 静态帮助、阶段说明与原入口照常 | 增加独立运行声明，不改 v1 解释 |
| 自定义 Node 或 Python 工作流插件 | 保留自己的状态与领域校验 | 以适配器返回标准数据，无需重写全部代码 |
| 新建轻量项目包 | 宿主管理阶段与状态 | 后续显式迁移到完整适配器，不能原地换状态所有者 |

兼容要求包括插件缺失、禁用、卸载后项目数据保留；恢复正确版本后可重新读取。新增声明错误局部显示，不能让旧合法详情整体失效。运行期间固定插件版本属于本方案需补齐的基础，不能笼统视为已有：普通插件的 `installPluginFromDirLocked` 会替换原目录并删除成功安装后的备份，创作者版本库另走专用路径。P2 在新项目执行前建立完整包快照及引用保留，或对仍依赖可变安装目录的运行明确延后更新；P3 对复杂适配器同样验收。仅记录版本号或摘要不足以固定后续读取的 Skill、Hook、脚本和资源。卸载与回退不删除业务产物。

新项目绑定稳定插件身份与版本摘要，避免同名插件混淆。历史按名字匹配的兼容路径先保留并提示有歧义，不能未经迁移一次性删除。平台安装目录中的内置身份与用户插件 ID 分开。

跨包复用以明确导出的动作、输入输出 schema 和版本约束为边界，不允许直接 import 别人的内部文件。现有同包组件 `dependsOn` 不扩展为含糊的跨包依赖；新增单独的包依赖协议与锁定结果。缺少依赖、版本冲突或 schema 不匹配在运行前说明。

## 分阶段实施与验收

### P0 固定基线与兼容样本

改动：增加契约样本、差分测试和本方案验收账本。记录当前工作树及涉及文件摘要，不整理无关改动。选择 AutoBiz 固定版、至少一个其他开发者维护的真实项目插件，以及传统 Skill／Hook／MCP 包作为基准；本地 fixture 用于自动化，但不能代替真实第二插件的适配验收。

真实第二插件先记录实际名称、版本、可用环境及负责人；未取得样本时可推进轻量包与通用读取基础，对应真实适配验收保持未完成，不虚构第二插件，也不阻塞不依赖它的能力。

2026-10-12 用户补充：没有其他真实插件可提供，要求自主探索类似数据开发场景，并保护存量功能。因此本轮不再等待该输入；使用本地真实 AutoBiz 精简/完整变体与独立轻量文档包验证不同阶段结构，合成数据开发案例只作为通用契约样本。下文“真实第二插件/真实业务环境”的原目标保留为扩大兼容声明的条件，当前交付不得声称已经验证不存在的第三方样本或未接入的业务服务。

验收标准：

- 原入口完成、阻断、审批拒绝、取消和重复操作的轨迹可以复现，记录 Hook 次序及外部副作用次数。
- 两类项目插件的节点、状态路径、语言和审批需求存在差异，通用协议能表达而无需包含 AutoBiz 固定字段。
- 记录原失败和环境缺口，不把既有全仓测试结果标成本轮通过。

验收标准：

验收标准：

- 新作者按教程从空目录生成、预览、打包、安装一个两阶段项目；无需编写 Electron、IPC、数据库或 React 看板。
- 扩展开发助手完成自然语言制作、失败修正再试用和应用；复用公开动作的示例不复制他人内部文件、不绕过被调用插件的授权和检查。项目用户只需选模板、填目标、开始任务，即可在运行过程查看结果；不反复填同一身份或路径。
- 样例包含正常推进、缺失输入、校验失败、审批拒绝、重试和关闭重开后状态读取；真实生产路径运行，不只测 JSON。
- 作者必填项限定为包身份、阶段、Skill 引用、产物与适用检查；模板默认不要求 Python 或企业服务。
- 纯本地项目无需企业项目编码、系统 ID、发布单元或企业登录即可完成；企业项目原有字段、关联与授权检查通过回归。
- 保存源码只更新隔离开发会话的空闲版本；正式项目与正在运行调用保持原快照；能力变化按实际授权处理。
- doctor 不隐式执行插件脚本；pack 产物能经现有正式安装入口运行，不能只从源码目录启动。
- 记录新作者首次跑通耗时、手工文件数和应用操作数，目标为两阶段样例 30 分钟内跑通；这是验收目标，尚非现状指标。由未参与实现者按文档操作。

### P3 旧适配器执行桥接与真实证据

改动：增加 legacy adapter、执行协调器、证据协议、受限 project SDK；连接原工具编排、Skill 生命周期和 Hooks。AutoBiz 增强层及专用打包脚本增加适配声明，至少再适配一个真实第三方项目插件。

验收标准：

- 同一隔离输入经原入口和新入口，关键业务状态、产物、Hook 顺序和副作用次数一致；只读对比可双读，写入比较必须用独立项目副本。
- AutoBiz Design 未批准不推进；Code 原受限生产编译例外仍允许，其余验证按原 guard 和 UTest 边界拒绝或允许；标准、精简、动态节点、受控跳过保留原结果。
- 原 Hooks、Skills、校验器和工作流源文件摘要保持；新增包装仅进入增强层，确需改原文件时转为独立版本变更。
- 缺产物、失败校验、过期指纹、重复提交、并发请求和错误项目身份均不能误标完成。
- 旧日志仅显示历史证据；关闭新灵件不关闭原校验。没有新声明的旧包无需重打包仍可运行。
- 第二真实插件不依赖 AutoBiz 文件名、固定节点或 Python；它的合法失败、状态提交和取消同样通过。

### P4 阶段内 Flow 与恢复

改动：连接 `mods/flows/harness-context.ts`、`native-host.ts`、项目执行协调器、`managed-run-controller.ts`、`managed-run-recovery.ts`、`human-gate-service.ts` 和通知账本。逐项开放适配器已验证的执行／恢复能力。

验收标准：

- 对已通过原子提交契约的适配器，原会话、托管、Flow 和界面同时请求同一转换时，只有一个获得执行权；其余明确复用或冲突，不重复启动。未支持的适配器保留明确能力限制，不以新面板锁冒充原脚本受控。
- 在准备完成、执行前、外部写入后、结果落账前、待审批时分别中断并重启，得到可解释的恢复或核查状态。
- 可证明幂等的写入不重复提交；无法证明的写入停在 unknown，绝不靠自动重跑判断成功。
- 拒绝、取消和批准仅作用于对应动作版本；Feature 切换与旧审批不能串用。
- 阶段内部模型分工和修复预算可追踪，原批次调度器与平台不形成双重重试循环。
- 不支持恢复的旧插件仍显示原有失败与人工继续入口，不能因新平台上线而失去可恢复的历史记录。

### P5 流程减负与能力包发布

改动：在P1/P2已有向导、运行版本固定及最小复用基础上，扩展默认组合、跨包动作schema映射、依赖锁定、升级兼容报告和回退指引；完善开发助手，交付默认关闭的侧边项目建议Agent及预算/取消机制，补齐执行度量的返工、审批等待与可用成本关联。组织签名与集中分发可作为后续独立批次，不阻塞本地能力包交付。

验收标准：

- 已安装插件的项目配置在一条向导中完成，身份和工作区不重复填写；保存不会开始执行，运行入口含义明确。
- 普通命令插件无需项目配置；轻量项目无需 AutoBiz；复杂插件能选择自身支持的精简路线而不丢必需门禁。
- 缺依赖、版本不兼容、动作输入输出不匹配在运行前定位；自动接线不能猜测或丢弃必填字段。
- 更新不改变正在运行的版本；回退恢复代码并检查数据兼容，不能宣称撤销外部操作。
- 用相同样例比较改造前后的作者耗时、手工配置数、用户操作数和错误定位耗时；门禁通过条件及失败拒绝结果保持。
- 六项专项验收全部有真实证据：项目提示包括规则及侧边Agent两种模式，扩展开发助手包括自然语言制作与复用路径。默认关闭的可选模型能力同样需要实现和验收，不能用“可选”代替未完成。

### P6 发布回归与推广

改动：完善兼容矩阵、迁移指南、离线文档和诊断导出；将已验收的能力分别开放，保留旧路径与项目数据。

验收标准：

- 按仓库要求，新增行为先跑窄回归，再完成 Node／Web 类型检查、范围 lint、build 和完整 `npm test`；失败保留原记录并逐项归因，不能弱化断言。
- 生产 Electron 安装包中完成插件安装、创建项目、阶段运行、审批、失败、恢复、更新、卸载；Renderer 同时覆盖窄屏和键盘操作。
- 六项能力与三个官方示例共同启用时，覆盖冷启动、切换项目/组合、原生最小化恢复、源码热更新、重复点击和流式回答期间打开面板；检查闪屏、旧内容回闪、重复回答、输入草稿丢失及上下文串用。每个模块提供实际例子，至少一条完整失败、排查、修复、再验证导览；初次使用者能说明当前进度、阻塞原因和下一步。
- AutoBiz 与真实第二项目插件完成约定的端到端场景；外部服务未连接的部分明确未验收，不能用模拟服务代替真实业务交付声明。
- Windows 为首个完整验收平台；未实际运行的平台明确为未验证，只有补齐相应路径／进程／打包回归才扩大支持声明。
- 发布记录列出实际插件版本、应用版本、协议、支持动作、恢复能力、检查范围和已知限制。

## 兼容与失败测试矩阵

各阶段选择所改路径的相关组合；发布前覆盖全矩阵的必需场景，避免每个小改动机械重复全套。

| 维度 | 必需样本 |
| --- | --- |
| 插件 | 传统 Skill／MCP／Hook、旧 board、v1 说明增强、AutoBiz 固定版、另一真实开发者插件、新轻量包 |
| 功能开关 | 新增强关闭、启用但未授权、已授权、策略拒绝；传统插件行为按原权限机制保留 |
| 项目状态 | 未开始、进行中、待审批、失败、完成、跳过、历史未知、当前证据失效 |
| 调用入口 | 原阶段会话、新面板、灵件动作、托管、允许的 Flow、桌面／现有 IM 审批 |
| 生命周期 | 安装、升级、代码回退、禁用、卸载、插件缺失、重启、版本被运行引用 |
| 故障 | 模型错误、进程超时、校验失败、取消、双击、状态变化、外部写入结果未知 |
| 数据边界 | 跨 Feature、跨工作区、路径链接、外部产物 grant、旧状态 schema、损坏声明 |

测试分四层：协议与纯逻辑、真实适配器集成、生产 Electron 交互、配置真实依赖的业务验收。每条记录写清层级，不能以静态解析通过代替业务执行通过。

## 实施组织与首批范围

阶段编号用于追踪验收，不要求每个小改动单独全量回归。按三个连续交付组推进，每组中关联功能连续实现，边界窄测按需要进行，组末集中检视和回归，最终P6统一验收；不等待用户提醒才推进下一组。

1. 第一组：P0可用基线与P1，统一现有项目入口，交付规范、审阅、策略解释、本地度量和规则提示。真实第二插件暂缺仅保留该项未验收。
2. 第二组：P2及P5最小复用前置内容，完成轻量项目、自然语言制作、版本保留、已有动作复用和傻瓜式案例教程。
3. 第三组：P3/P4及P5余项，接入复杂插件原验证链、统一受控执行和恢复，完成侧边建议Agent、度量关联及发布兼容，再进入P6。

P3复杂插件写入须等协议、原链基线、完整版本与身份边界验收；P4不得抢先绕过原执行链。三个交付组分别由两名中等思维强度子agent交叉检视实际实现和使用体验，修复已确认P2及以上问题后再交付；不能用方案评审代替代码或实包验收。保持单一职责增量改动，不整体重写Harness service。

所有阶段在 Mods_v2 工作树增量开发。已有混合改动先记录并保留；不自动提交、不覆盖外部插件仓库、不迁移真实业务数据。后续验收账本使用 `docs/mods-v2-project-platform-progress-2026-10-12.md`，仅在开始实施时创建并按真实结果更新。

## 稳定性与性能优先补充要求（用户追加）

暂停新增功能，先关闭对话卡顿、运行时丢失、超时、重复回答和闪屏中的已确认问题，再恢复后续批次。功能最终能完成不能代替过程可用性验收。

- 用同一隔离生产包和本地协议模型对比普通模式、Weather、Replay、组合模式；每组至少连续五轮并保留累计历史，包含持续流式输出、输入操作及最终回答唯一性。
- 记录主进程事件循环阻塞、真实 IPC 延迟、运行进程退出原因，以及全过程可见内容缺失和占位；按准备、切换、稳定阶段分别报告，不只测最后几秒。CPU 分析与正式时序采样分开解释，构建和其他重测试不与性能测量并行。
- 区分已确认根因与日志线索；主进程长时间未运行不直接归因于某段代码。修复不能仅隐藏提示、扩大超时、无限重试、绕过授权或自动重放结果未知的业务操作。
- 首次打开、长历史连续使用、三个官方示例、组合切换、最小化恢复、源码热更新及关闭重开均进入最终稳定性验收。发现过程空白或超时即保留失败证据并继续排查，不以功能断言通过覆盖体验失败。
- 此后的每一组功能变更都检查是否增加热路径同步 I/O、重复读取、无关全局刷新或无界排队；必要时增加上述对照测量。继续保护 UAT 原路径和 AutoBiz 原审批、Hook、阶段验证链。
