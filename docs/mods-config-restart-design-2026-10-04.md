# 已保存参数的明确重新加载

这是配置阶段之后继续实施的方案，不表示功能已经交付。

## 用户要解决的问题

普通参数可以在空闲时自动应用。但有些插件在启动时要保存状态、打开界面或启动后台服务，不能在旧实例仍存在时尝试一遍这些操作。现在这类插件会如实显示“参数已保存，应用未完成”，旧实例保留。下一步提供“重新加载当前组合”，让用户在原参数表单里完成这件事，不必重启整个应用或反复关闭开关。

DevClaw 的多个组件共用一个当前会话处理链，因此这次重新加载的范围是当前对话的已启用组合。按钮旁明确写出：会重新启动这些组件，关闭本次组件界面；保存的参数和插件持久数据保留。新启动可能执行作者的启动操作，原写文件、工具和进程批准仍需正常通过。

## 实际执行顺序

1. 仅原生界面控制入口提供重新加载，不新增插件 SDK 控制自己的重启。传入原项目、插件、代码摘要和已看到的保存版本，并保留原窗口与会话的所有者检查。使用单独控制入口，不占用等待自己释放的活动令牌。
2. 有物理任务、逻辑任务或真实插件调用/流/进程清理时立即返回仍待应用。不会中断当前任务，也不预约一次以后可能脱离原窗口的有副作用启动。
3. 真正空闲时同步暂停旧处理链，并由原宿主 `claimLocalThreadRunLease` 抢占独立 `mods` 物理运行租约。租约不能移交或偷取。原桌面、IM、调度和命令入口将正常识别该实际占用；重新加载完成或失败都按原精确 owner/runId 释放。
4. 新增宿主私有重启守卫，检查原所有者、取消、租约、会话、项目、批准及逻辑任务。它进入独立宿主上下文，退出旧 SDK 回执和写租约；不能继承正在执行的模型身份。后续每个启动调用仍经过实际权限与效果入口，不能因重新加载得到未批准的文件或工具能力。
5. 关闭旧实例之前先只读编译全部原选中包，解析真实参数，核对代码批准、组合选择与所有保存版本。最后同步复核全包来源；任何不匹配都保留旧实例并显示失败，不执行启动效果。
6. 预检通过才关闭旧实例的资源并退休。整个重启持续保留原物理租约与控制守卫；新普通请求等待同一个宿主控制过程。随后从已预检、批准的不可变代码与参数快照构建完整的新处理链。构建不能重新读可变源码再悄悄换包。
7. 新启动允许原有操作，但使用严格错误处理：作者捕获了失败的启动操作、处理函数恢复、匹配器异常或非法结果，都不能假装启动完成。正常匹配器返回 false 是合法跳过。只在实际完整注册、所有启动处理结束及最后授权/版本/来源复核后显示“已应用”。当前阶段的私有自动候选继续只允许本地注册与只读操作；两种启动方式明确区分。
8. 旧实例已关闭之后，新启动若失败，应显示“重新加载失败，当前组合已停止”，保留参数；不声称旧实例仍可用，不自动重复可能已经执行过的启动效果。宿主记录当前对话的失败控制状态，阻止普通入口隐式重试。用户可以修复后明确重试；禁用 Mods 仍沿用原普通聊天路径。
9. 切项目、关闭对话、撤权和应用关闭使重启守卫失效并取消新实例。失败控制状态独立于运行实例缓存：普通 invalidate、closeThread（组合变化也会调用）、源码/批准/保存值变化都保留停止标记。仅明确重试能重新执行启动效果；真实应用退出结束它。禁用 Mods 不受此标记影响普通聊天，重新启用后仍需要明确重试。旧回调不能靠新的控制状态继续操作。

重启取得自己的租约之后，守卫不再使用包含自己的 configurationBusy 判断；它复核精确 mods/runId 租约和单独的逻辑任务状态。旧实例的 close/后台清理必须真正完成，新实例才启动；清理失败同样进入停止状态。重启守卫不把原运行缓存失效当作许可恢复。

## 长期后台服务的边界

自动应用继续以全部真实活动数为准，后台进程也算忙。明确重新加载则区分前景调用与当前实例自己的长期资源：进程打开和批准等待仍算前景，实际 started 确认后，手工资源令牌和后台等待结果的令牌都标为可关闭的长期资源。实际 SDK 调用、process pull/read/write、处理函数、Flow、子助手和清理仍算前景，不能因拥有进程而被忽略。仅前景、物理任务和逻辑任务全为空才同步暂停新的进入；随后在原重启租约下关闭自己的资源并等待真实完成。清理开始把原资源令牌提升为前景，直到实际 finally 释放。

资源管理增加仅重启使用的严格关闭回执：等待所有清理完成后，任何 rejected 都报告失败，不能把当前 closeAll 的 allSettled 当作成功。普通关闭和撤权保持已有尽力清理行为。必须用实际启动且不结束的后台进程验证：确认后可以明确重载，backend.close 延迟前新启动为零，完成后才启动；打开、pull 等前景活动期间返回等待；backend.close 真拒绝则停止且没有新 load/start。

暂停后仍存活的长期资源令牌不得继承原前景令牌的续行豁免：由资源唤醒的新 SDK、RPC、pull 或处理函数只能等待或在退休后取消，不能在预编译等待期间执行新效果。只有已入场的前景调用允许续行，而明确暂停的前提就是前景为空；宿主清理提升是独立私有操作。清理管理保留正在关闭的真实 Promise 和第一项清理失败，直到严格退休核验，即使条目此前已经删除、失败被作者捕获或普通 abort 清理吞掉，也不能在后来空列表中误报清理成功。反例包含先关闭失败、条目移除后再重新加载仍零新 load/start。

后台标记只能由真实 backend.started 的宿主确认建立；处理中合成的首帧及现有 stream.started 的 Promise.race 都不能证明进程已经启动。关闭回执还要等待原后台任务实际收尾，不能释放后留下旧效果继续运行；实现时避免 task.catch→close→等待同一 catch 的循环。

## 代码组织与验证

提取小的宿主重启租约适配器和控制状态帮助类；复用已有源码证明、参数解析、完整构建与原效果处理链。完整构建显式接收经过预检的包/参数快照，不复制另一套 SDK 运行器。初始化阶段区分普通加载、私有自动候选、用户明确重启，错误严格性与效果许可独立表示。

验证包括：启动保存状态的实际插件、启动后 UI/后台服务、启动捕获拒绝与恢复、只读预检失败零效果、运行中点击零重启、保存版本/源码/选择/批准变化、原窗口丢失、真实物理租约冲突、清理延迟、失败不自动重放、明确重试、无配置变化的普通 Plugin/Harness 路径。实际 Electron 验证表单按钮、权限提示、真实新注册参数、失败文案与普通聊天。两位方案和实现评审通过后交付，再继续敏感、多值和文件选择参数及其它未对齐能力。
