## 为什么不能直接复用旧打包器

旧脚本固定取旧提交，并替换 `hooks/hooks.json`。当前分支该文件包含写入、执行、证据和人工确认等约束，替换会改变原业务。

当前分支的 Feature 使用选定节点等动态流程信息；旧看板助手遇到 `workflowNodes` 就拒绝，不能用固定七种旧流程假称完整支持。

宿主原 Autobiz validator 和阶段提交仍固定旧来源。本次不替换这个核心，不把新分支交给旧版本验证器自动批准或推进。

## 实施范围

1. 新增专用打包器，从已解析的目标分支 Git 提交导出完整 tracked 文件，记录来源提交及原文件摘要。保留原 Skill、MCP、agents、workflows、board_core、Python、测试和经典 Hook。
2. 只增量添加 native Mods 清单和模块；修改包装清单的名称、适配版本、描述与 `mods` 入口，原其他字段保留。不得覆盖原 Hook／角色／工作流文件。
3. 四个明确组件：真实状态、项目看板、单文件模型检视、跨插件检视输入。看板声明状态依赖。状态必须经安装包中该分支原 `read_state_json.py` 的只读规范化入口取得，使用受审批的 `process.run`，当前选定项目目录明确提供只读脚本所需的工作区参数。不使用会修写状态的 `inspect_state.py`，不让模型直接读受限 state／日志。记录展示包含 checkpoint／stage／选定节点，不推断已完成，不执行阶段提交。
4. 导出可等待的“准备检视输入”动作：明确指定实际 Feature 和文件，经原状态入口取得必要的规范化字段；拒绝未知 Feature 和受限状态／日志文件，结果交给独立 Review 插件。汇报动作使用已有“本次执行结果”输入方式，不把 Review 的字符串冒充下游所需对象。模型检视与原生项目测试仍分开。
5. 提供一个完整、无活动 Code／Batch 的源码副本，原用例不修改，增加显式检查配置运行 tests 根目录的 unittest 可发现用例。integration 子目录、顶层脚本式测试和 Node 测试分别按原命令执行并记录；不把一个 discover 范围称为整个分支全量。另用原分支初始化器创建演示 Feature；不手工把阶段跳到 Code／Review，不伪造业务产物通过。
6. 演示流程由用户公开界面选择插件动作、汇报及人工确认；两个只读 Agent 使用 A／B 展示模型分工。若另演示实际修改，只允许独立副本中的明确演示文件，不声称完成原活动 Code Workflow。测试环境的控制模型只用于检查调用、数据和真实工具，不冒充客户模型质量。

## 明确边界

新看板显示的是项目实际状态和记录，不代替当前分支的动态语义校验器。原业务流程和门禁保留，通过原 Plugin 入口使用；新增 Mods 增强选择、交互和跨插件调用。

普通本地新增 Mods 体验与原 Plugin／Harness 的完整业务模式分开。原模式依赖真实项目／Feature 绑定、PLUGIN_WORKSPACE／PROJECT_DIR 等上下文及原协议；不能把普通 Agent／Function 演示说成整套原业务门禁已生效。状态只读命令使用当前项目目录，不能由插件任意指定其他项目或伪造运行角色。环境预检与原 Hook 拒绝均如实处理，不关闭原保护来过测。

这版不启用新分支的宿主自动阶段推进，不声明旧版本 validator 能验收新分支。最终指南区分演示来源、实际执行项、原分支基线失败、控制模型以及尚未完成的业务验收。
