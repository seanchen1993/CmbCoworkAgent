## 预算和功能边界

| 项目 | 实施限制 |
| --- | --- |
| 单消息原文及投影 | 各不超过 256 Ki 个 UTF-16 单元；正文与工具摘要共享 |
| 内容块 | 至多检查 128 个正文候选块及 128 个工具调用；超出部分标记不完整 |
| 界面及 Worker 语料 | 保留最多 500 条、4 Mi 单元；Worker 允许额外一条临时验证文档，随后释放 |
| 活动上下文 | 同时一处；关键词最多 256 单元，前后文各最多 80，合计最多 416 单元 |
| Worker 传输 | 原文按 8,192 单元分包，单包序列化小于 64 KiB；串行确认 |
| 历史搜索 | 512 KiB 扫描、128 KiB 响应；每消息坐标额外限制 48 KiB，计入完整响应 |
| 结果 | 界面最多 1,000 项，内部保留一项哨兵以显示截断状态 |
| DOM 映射 | 最多 256 Ki 文本单元及 8,192 个 TextNode |

搜索超限时显示范围不完整，不承诺任意长度消息的无界全文检索。对无法在预算内完整确认语义的用户、系统或 think 包装块，跳过并标记不完整，避免把截断后的隐藏内容当正文。Worker 失败显示失败/不完整状态，不在界面线程同步回退到全文扫描。

搜索上下文独立于原始消息，不写回数据库或模型输入。复制、编辑仍读取原文；手动“展开全文”继续保留，用户主动展开超大正文仍有原有渲染成本。

## 性能对照

Windows、Node 22.23.2、同一安装的 Electron/Chromium，使用独立测试用户目录及受控流式生产者。实际应用通过 UI 提交、真实 preload/IPC/SQLite 和历史加载 Worker 运行；没有调用外部模型。性能运行期间不并行执行构建或测试套件。

基线由 Git 导出原始源码构建，只增加相同的 `data-chat-thread-id` 测量标记，并把构建用 skills 输入指向同一物理资源目录。业务逻辑保留基线版本。就绪时间在页面内测量：点击事件至目标行有布局且可见的动画帧；自动化定位器等待另行记录。

每版执行 40 次交替切换，每个方向各 20 个样本；中位数取标准中位数，P95 取最近秩次。

| 场景 | 基线中位数 / P95 / 最大值 | 修复后中位数 / P95 / 最大值 |
| --- | ---: | ---: |
| 切入 80 条历史消息 | 5,520.65 / 5,577.0 / 5,625.6 ms | 278.3 / 294.4 / 295.0 ms |
| 返回正在输出的会话 | 294.95 / 378.1 / 378.6 ms | 262.4 / 394.0 / 460.5 ms |
| 两方向合计 | 2,935.35 / 5,560.6 / 5,625.6 ms | 277.35 / 377.8 / 460.5 ms |

切入历史会话的 P95 降低约 94.7%。返回运行会话的 P95 增加约 4.2%，低于方案的 10% 门槛，但最大样本约 461 ms，高于基线最大值；这里不能推导出每次切换都更快。第一轮每方向 10 个样本出现较大波动，后续两版均补足每方向 20 个，保留了第一轮数据，没有只选择最快样本。

高密度正文使用真实 Markdown 与 Virtuoso：524,008 字符，包含 13,100 个格式化段落。20 次搜索定位的结果为：DOM 元素数 4,305 → 4,305；定位中位数约 15.8 ms、P95 22.2 ms、最大约 22.9 ms；未记录到超过 50 ms 的搜索长任务。二次检视的自动展开路径曾达到约 39,314 个元素及 1,239 ms 长任务，此项没有再现。

32 块、约千万字符输入执行 20 次冷 Worker 索引：实际入选 262,144 单元，界面准备 P95 约 0.4 ms，Worker 启动/传输/投影/匹配总等待约 22.7–30.2 ms，实测最大分包 8,745 字节。返回 5 个已覆盖片段命中，并标记范围不完整。

1/80/100/101/128 条消息的首次提交回归均为 0 次正文渲染，框架提交约 0.2–1.5 ms。此指标只衡量 Virtuoso 接管前的提交，不代替上面的实际切换时延。

隐藏测试窗口的动画帧调度曾造成约 873 ms 的读数，最终压力数据改用前台窗口；隐藏运行数据单独保留，没有混入上述结果。内存约束通过输入/缓存/传输上限、连续冷索引、Worker 终止和异常恢复测试验证；未完成长时间整进程堆快照及 GC 归因，不能声称已经证明长期无内存泄漏。
