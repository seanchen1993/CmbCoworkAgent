# Mods v2 宿主调用基础复核

实施分支：`codex/mods-v2`。本批基线：`aa97b145`，不在 UAT 上开发。
这是当前代码的架构约束与后续接入顺序，不代表全部 Claude Mods 能力已经交付。

## 本批修正的基础问题

此前模型 SDK 与自定义工具各自维护准入、记账、撤权和发布流程，原生 SDK 又通过 v1
引擎执行。三个入口存在身份与账本细节不一致：模型 SDK 使用虚构轮次并固定为 main；
队列未传递 agent/turn；原生 SDK 生成了一个未落账的父调用编号，最终发布仍引用该编号。
模型已返回但用量写入失败时，也可能被记为 unknown，混淆执行事实与后处理失败。

新增真实嵌套模型场景后，截图复检还发现 LangChain 隐式继承外层模型回调，导致内部
模型原始 token 提前进入主对话，尽管 SDK 返回值已经过滤。本批将内部模型的完整流读取
放进独立 LangChain 上下文，清除外层回调、graph 配置及 trace 继承，同时保留本工程
授权与调用账本上下文。回归同时检查父调用流事件、界面文本、持久消息和下一次模型输入。

现在 `src/main/mods/v2/host-call.ts` 提供两个明确边界：

- `functionCallIdentity` 从宿主异步上下文生成身份，保留实际 turn/agent/parentCallId；
  当前调用仍绑定自己的插件授权。过期、跨项目、跨会话或冲突的代理身份拒绝进入。
- `runFunctionHostCall` 固定准入、预约、执行、结算、发布的顺序，模型和自定义工具共用。
  模型的限流、持久预算及用量记录仍由模型适配器负责，工具参数仍由工具 schema 负责。

原生 SDK 继续使用已经接通文件、Shell、MCP 和 classic hooks 的 `ModEngine`，只复用身份
来源并修复实际账本编号。不把通用包装层再套到原生执行外面生成第二份执行记录。
这是本工程的独立宿主设计；参考 Claude 的宿主准入、调用标识与取消传播机制，不能宣称
Claude 使用了相同的 SQLite、AsyncLocalStorage 或状态机实现。

## 必须保持的执行顺序

```mermaid
flowchart LR
  A[宿主作用域和授权复核] --> B[强制策略准入]
  B --> C[再次复核并原子预约账本/预算]
  C --> D[执行一次]
  D --> E[先记录实际执行结果]
  E --> F[记录用量及校验结果]
  F --> G[复核授权并保护输出]
  G --> H[再次复核后返回]
```

| 发生位置 | 执行账本 | 发布结果 |
| --- | --- | --- |
| 准入拒绝、预约失败 | 不创建成功执行记录 | 不发布，不调用工具/模型 |
| 已预约，但实际调用前撤权/取消 | not_started | blocked |
| 已开始，调用抛错或失去回复 | unknown | blocked，不自动重放 |
| 工具返回 deny/isError | failed | 经策略保护后可返回工具错误 |
| 实际返回后撤权、用量记录或输出校验失败 | 保留 succeeded/failed | blocked |
| 正常完成 | succeeded/failed | 经策略保护后发布 |

授权复核发生在异步边界两侧。排队只转移已受理调用的租约，保留 agent/turn；调用方
作用域已经结束的遗留任务不能重新获得写权限。子代理的原生 SDK 调用暂明确拒绝，
不得回退借用 main 的后端。子代理模型 SDK 使用其真实身份记账，仍受同一插件预算。

本批不增加数据库表或迁移，沿用已有 scope、parentCallId、执行状态及 publication 字段。
宿主修订提升到 `desktop-host-call-v11`，旧快照授权自然失效，需要在项目 Mods 页面批准。

## 后续能力的接入顺序

1. **工具解析与绑定。** 建立宿主工具描述和解析接口，分别由 native、MCP、registered
   适配器提供真实 schema、稳定目标和作用域校验。目录元数据只用于展示，不能当作调用
   授权；不能根据 `mcp__` 前缀猜提供者，因为自定义工具也使用该前缀。绑定必须核对
   workspace/thread/agent/turn 与失效代次。优先解决 MCP SDK 和目录快照的真实可调用性。
2. **权限查询与实际执行。** 从现有文件/命令/MCP 权限入口提取无副作用的声明式查询。
   `tool.check` 使用这些查询；不运行工具、不弹审批、不执行 classic PreToolUse。
   实际调用仍在最终参数经过 classic 改写后执行宿主强制校验和审批。不能用静态“读工具
   allow、写工具 ask”作为正式实现，也不能把可选 Hook 返回 allow 当作绕过强制权限的凭据。
3. **再开放权限事件和 MCP SDK。** 先验证真实适配器的查询/执行一致性，再接通固定字段、
   origin、多次 next、取消和撤权契约。无真实宿主对应行为的分支保持明确不支持。
4. **子代理与委托。** 有了按代理绑定的目录和真实权限查询后，再开放子代理注册/调用及
   跨插件能力委托。父子审计记录只表达归因，本身不授予父插件或 main 的权限。

上游 `tool.check` 的语义依据是已冻结的 2.1.273 声明 `ToolCheckArgs/Input/Result`：
查询无 tool_use_id，真实调用由宿主提供该字段，tool/input/id 均固定；返回 allow/ask/deny。
见 [兼容设计](mods-v2-parity-design-2026-09-16.md) 的版本、哈希与本机还原证据索引。
基础批交付时尚未开放 `tool.check` 或 MCP SDK；随后 MCP SDK 已按上述执行边界接入，
见 [MCP SDK 实施复核](mods-v2-mcp-sdk-2026-09-17.md)。`tool.check` 仍待真实权限查询适配。

验证结果与性能边界记录在 [实施记录](mods-v2-implementation-2026-09-16.md)。
