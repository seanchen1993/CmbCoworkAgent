# Mods 控制存储启动：保持完整恢复，减少重复落盘

状态：两位独立 agent 设计评审通过，生产与真实数据库测试待源码检视和执行。

## 原因和范围

当前启动先设置 WAL 和 FULL，再逐项建表、补列、建索引、写版本和恢复中断记录。
这些写入各自提交。新的性能采样显示这里存在开销，但不能保证这一项优化就能让
尚未通过的三个原五秒检查通过。正式时间限制保持不变。

只修改 `src/main/mods/control-store.ts` 的构造函数，新增独立回归文件。
不修改 Peer 存储、普通业务写入、文件检查、查询次数、权限或任何已审来源关系。

## 实现约束

1. 原 WAL、FULL、连接超时和打开方式完全保持；两条 PRAGMA 在事务外执行。
2. PRAGMA 成功后，以原 SQLite 连接执行一次 `BEGIN IMMEDIATE`。只有实际成功后
   才记录本构造函数拥有未提交事务；不根据报错真假判断。
3. 原建表、版本拒绝、补列、数据回填、索引、FunctionStateStore 创建、版本写入、
   中断调用/证据/任务恢复，以及原任务保留数量和逐项保存顺序全部保持。
4. 最后执行一次实际 `COMMIT`，成功后才清除拥有事务的状态并返回实例。不使用
   缓存或跳过恢复；成功启动仍把 running 调用变为 unknown，把证据变为 interrupted，
   把 queued/running 任务分别变为 cancelled/unknown。
5. 任一步失败后，拥有事务时尝试实际 `ROLLBACK`；连接关闭单独尝试，不能因为
   回滚失败而跳过。保留首错误，包括 undefined 和 null；只有一个错误时原样抛出，
   多个错误按首错误、回滚、关闭顺序聚合。拒绝或清理失败不会发布可用实例。
6. 不将本模块的事务成功当作模型调用、共享读取、插件权限或流结束的证明。

事务失败会让这次迁移与恢复完整回退。旧构造函数失败时可能留下部分修改，新的
行为会减少这种不完整状态；这是明确的行为变化，必须以真实数据库验证。数据库
已有内容不裁剪，不用新的结构替代旧版本夹具。原动态方法调用仍原样执行，不把
未知回调改为私有固定函数；若确有依赖独立提交的旧调用者，先评估而不是隐瞒。

仓库当前没有构造时重写这些方法并独立提交的调用者。本方案不承诺任意外部修改
构造方法后的行为等价：自行开启事务会保留原调用并失败；未知代码若已经提交事务，
不能声称它仍被回滚。分别通过真实嵌套事务失败和实际提交后异常验证这些边界。

## 必须通过的实际检查

- 完整新库创建和再次打开：原表、索引、版本、WAL、FULL、全部字段和正常写入保持。
- 真实旧版本库：完整原审计、任务、证据、设置数据迁移与原恢复结果一致。
- 中段真实失败：用独立 Node SQLite 连接打开旧库，固定失败点之后完整 schema、
  行、字段和原始 JSON 与迁移前一致；不只是检查返回错误。
- 晚期任务恢复失败：先真实执行原 running 恢复，再在真实原任务保存位置失败；
  原调用、证据、任务和版本全部回退。恢复后正常启动只执行原恢复，不重新执行任务。
- 提交、回滚和关闭异常：保持真实委托，独立观察资源清理，精确保留 undefined 等
  首原因；外部连接再次打开可用。没有自造 SQLite 成功结果。
- 原控制存储、状态、Manager 及相关恢复回归保留。运行原四个五秒检查；另加冷启动
  对照采样，仅作定位，不替代正式门槛。若没有明确收益，保留记录并重新判断优化。

## 用户效果

用户操作不变。预期是插件状态库启动时减少重复提交，失败后不留下半完成的迁移。
实际速度以测量为准；这不表示其它尚未完成的 Mods 能力已经交付。
