## 1. 先说结论

**现在可以组合不同插件的动作、Skill、MCP 工具和模型，保存成自己的 Claw，并在对话中执行。**
尚未做到任意 Claude Mod 原样导入、所有 Hook 任意拆分，以及替换整个 Agent 内核。

存量 Plugin **不需要为继续原来的使用方式全部改造**。原有 Skill、MCP、传统 Plugin 项目模式
仍有各自入口。需要改造的是新增要求，例如把原来的一个命令变成“能接收前一步数据、执行完后
把结果交给下一步”的可组合动作。

以前写一个 Skill 或 MCP 插件，并不需要自己实现 IPC、进程隔离、凭据管理等整套基础设施。
现在的价值是：对于需要介入运行过程的扩展，宿主提供统一的 Function Hook 和执行边界；
对于需要固定业务顺序的任务，Claw/Flow 提供来源选择、模型绑定、步骤执行及结果记录。
不能把“过去普通插件也必须修改主工程”作为这次改造的价值依据。

### 几个容易混淆的概念

| 名称 | 实际是什么 | 例子 |
| --- | --- | --- |
| Plugin | 安装和分发的包，可以包含不同种类的能力 | Autobiz 插件里同时有 Skills、MCP、脚本和 Function 模块 |
| Skill | 给助手使用的任务说明及关联资料；执行效果依赖模型和工具 | 需求分析、代码评审方法 |
| MCP | 外部工具服务；可以保留已有服务实现 | 查询需求、读取仓库、调用业务系统 |
| Function Mod | 可执行的扩展模块，按事件参与运行，也可注册命令、工具等 | 完成前检查、模型调用拦截、自定义命令 |
| 插件动作 | 作者显式导出的、带输入输出契约的 Function Mod 操作 | Autobiz 准备文件 → Review 检视文件 |
| 我的 Claw | 保存所选来源、模型和流程副本，并应用到当前对话 | “研发 Claw”“只读检视 Claw” |
| DIY 流程 / Flow | 按保存的顺序和条件执行步骤 | Skill 分析 → MCP 查询 → 插件动作 → 测试 → 人工确认 |

**包已安装、能力已授权、组合已应用、任务已执行，是四个不同状态。**
勾选一个插件不会让它在每次回答中都运行，也不会自动改变回答风格。

## 2. 没有对齐的能力，会影响哪些实际功能

以下分两类列出：第一类是 Claude API 兼容差异，第二类是本工程 DIY 产品边界。
第二类不能反过来证明 Claude 官方已经提供相同的可视化流程页面。

### 2.1 Claude API 兼容差异

| 差距 | 哪种插件或需求会受影响 | 目前可以怎么做；不能据此声称什么 |
| --- | --- | --- |
| 完整 `skill.prompt` 正文扩展尚未接入 | 在所有 Skill 生效前统一改写最终正文、附加动态规则的 Mod，不能原样移植 | 维护自己的 Skill 内容，或在 Skill 任务中填写目标；已有 Pre/PostSkillUse 不等于完整正文拦截 |
| `prompt.read/edit/fill/submit/suggest/section/context/attachment` 等未提供 | 自动读取/填充输入框、管理附件、提示词片段、由插件替用户发消息 | 使用现有输入框、显式命令或流程任务入口；它们不能替代完整的编辑器 API |
| `tool.describe` 未提供 | 动态改写已有工具对模型展示的描述、schema 或约束 | 可显式注册自己的工具；已支持的 `tool.call`/`tool.check` 不等于改写工具定义 |
| `model.complete` 的 `effort` 未支持 | 同一模型按步骤精确改变推理强度的官方 Mod 会报不支持 | 可选不同模型和显式输出上限；选模型不等于设置 effort |
| 2.1.284 的模型调用第二参数 `options.signal` 未支持 | 插件想单独取消其中一个模型请求、保留同一任务的其他工作 | 新结果协议支持 `timeoutMs`；父任务取消、撤权仍有效，但不等于独立 AbortSignal |
| 模型协议、输出额度、fork 语义仍有边界 | 假定所有插件都返回新版对象、要求超大输出或完整 Claude 缓存上下文的插件 | 旧插件默认保留字符串/旧 fork；新插件显式选 `result-v1`。模型输出默认 256、最大 4096 tokens，单次宿主时限 60 秒；fork 使用经过清理的宿主文本快照 |
| `env.set`、`config.set/list/describe` 未提供 | 插件运行时修改会话环境、改变后续 MCP 进程配置、调整 Claude 原生设置 | 在应用或 MCP 配置入口设置；不能用写全局 `process.env` 冒充隔离的会话环境 |
| `ui.copy/panes/blit`、音频及部分终端 UI 能力未提供 | 依赖剪贴板、多终端面板、像素绘制、语音输出的 Mod | 使用本工程已有面板、日志和通知子集；普通聊天/现有插件面板不因此不可用，但原版 UI 不能保证照搬 |
| 部分会话、归因和第一方能力未接入 | 依赖 `session.measure/end/attach/detach`、`plugin.register`、`attribution.text`、`telemetry.*` 等的插件 | 使用现有宿主入口及记录；不能把插件注册成功当作这些事件已接上实际业务 |
| 部分 `classic.*` 只定义了事件结构 | 把 PermissionRequest、ConfigChange、WorktreeCreate 等当作 Function 事件观察的插件可能没有真实触发点 | 逐项检查事件兼容报告。这里说的是 Function 兼容层，不表示所有传统 Hook 或宿主审批失效 |
| HTTP、进程、凭据仍按本工程边界执行 | 依赖 Claude 专用 credential handle、Unix socket、多层压缩，或精确进程截断语义的插件 | HTTP 已支持单层 gzip/deflate/br；传输和解压后各有 256 KiB 上限。使用本工程批准的请求/进程入口；旧 Node 脚本不能直接当 Mod 装载 |
| 依赖类型聚合、部分测试/作者 API 未全量适配 | 依赖其他 Mod 自动贡献类型、完整官方测试库的插件 | 可生成本工程支持的作者类型并做本地检查；类型通过不证明运行时和依赖提供者全部兼容 |

完整事件清单见 [compatibility-catalog.ts](../src/shared/mods/v2/compatibility-catalog.ts)。
其中 `bounded` 是“已有有界适配”，`metadata` 是“有结构定义但未接业务触发”，
`unavailable` 是“没有生产提供者”，不能把三者合计为已实现数量。
`ui.resolve` 的事件提供者与同名辅助函数也不是一件事。
这里核对的是 Function Mods 的 Claude 兼容接口，不是旧 `cmb.mods/v1` 的事件体系。
例如旧声明中出现 `prompt.context`，并不表示已经实现 Claude 同名接口，两套语义需要分别核对。

### 2.2 DIY 组合仍有的产品边界

| 当前边界 | 对使用的影响 | 当前建议 |
| --- | --- | --- |
| 插件内部任意函数、Hook 不自动变成节点 | 安装旧插件后，动作下拉框可能仍为空 | Skill/MCP 用原生步骤；代码操作由作者导出 `claw.actions` |
| 选动作仍会加载提供者的整包 Hooks | 想只用其中一个动作，其他自动 Hook 仍可能触发 | 作者拆成独立包，或给自动行为增加明确配置；不能把选择动作当作其余 Hook 已被卸载 |
| Flow 仍需一个已授权的“所属 Mods” | 只有 Skill/MCP 的流程，目前也不能完全取消 Function Mod 授权来源 | 保留一个已批准的流程归属包；这是当前限制，不是 Skill 本身必须改写 |
| 来源选择、模型绑定按对话；完成规则仍按项目共享 | 两个对话能用不同组合，但不能假定各自有独立完成门禁 | 变更完成规则前核对同项目影响；强制门禁不能通过删掉 Flow 检查来绕过 |
| MCP 在 Claw 中按服务选择，使用共享连接池 | 普通聊天不能通过该列表只开放某服务的一个工具，也不保证每个 Claw 独立进程 | Flow 的 MCP 步骤可指定单个工具；不要把调用范围选择当成连接隔离 |
| MCP 节点只支持受限 schema 和结构化输出 | 复杂 schema、图片/二进制处理链可能不能直接编排 | 工具目录会显示不可用原因；先适配成受支持的对象输入与 text/structuredContent 输出 |
| 基础参数已有表单，复杂配置仍以 JSON 和对象路径绑定 | 不支持通用表达式、任意字符串拼接或数组映射 | 简单字段直接填写，前步对象路径可选择；固定输入覆盖同名字段，复杂值保留高级 JSON |
| Flow 限普通本地项目会话 | 不能在传统 Plugin 项目模式、Harness、远端或定时任务中直接套用这套流程入口 | 这些模式继续使用各自原有路径；要体验 DIY 请新建普通本地项目会话 |
| 失败、取消、重启不是全业务事务 | 已发往远端的写操作不能保证撤回；中断流程不自动续跑 | 核对产物后重跑；MCP 不自动重发，也不能配置跨过 MCP 步骤的失败回退 |
| Agent 内核未完全模组化 | 不能通过勾选组件替换整个推理循环、权限引擎、沙箱或存储 | 将现阶段定位为“可组合能力与有界运行扩展”，不是任意内核可插拔平台 |

Skill 选择固定来源身份与 `SKILL.md`，不是整个技能目录的内容快照，也不是操作系统文件隔离。
MCP 配置摘要不保证远端服务实现始终不变。切换 Claw 不会抹掉历史消息中已经出现的内容。

### 2.3 对存量用户是否有影响

- **没有使用新 Claw 的用户**：传统 Plugin 项目模式、Harness、普通技能/MCP 路径保留。
  上轮真实 Electron 对传统 Plugin/Harness 的 7 组回归通过；这不等于任意第三方插件都已验证。
- **应用了 Claw 的用户**：所选 Skill/MCP、默认模型和 Function Mods 会改变当前对话可用能力。
  “仅使用所选”且空选，会关闭本类宿主能力；“沿用已启用来源”则保留动态来源行为。
- **开了完成规则的项目**：会多出评审/测试耗时、模型费用，严格规则可能阻止完成；这属于配置的效果。
  完成规则项目共享，不随切换某一对话组合自动恢复。
- **升级包的用户**：相关源码、声明或协议改变后，旧摘要授权和旧组合引用可能失效，需要重新核对并应用。
- **混合新旧模型协议的作者**：互不拦截的插件可以共存；若同一模型操作的观察器与调用者协议不一致，
  系统在请求前拒绝，需统一这一条调用链的协议，不能跳过观察器掩盖冲突。

## 3. 存量 Plugin 到底要不要改，改哪部分

| 现有内容 / 新要求 | 是否必须改代码 | 具体做法 |
| --- | --- | --- |
| 保持传统 Plugin 项目模式及现有业务用法 | 否 | 按旧入口继续使用，先做项目回归，不强制迁移 |
| 已有 `SKILL.md`，想参与 Claw 或固定步骤 | 通常不需要 | 安装并启用原 Skill，在 Claw 选中，在 Flow 添加“Skill 任务” |
| 已有 MCP 服务，想参与 Claw 或固定步骤 | 通常不需要 | 保留服务，配置并启用；Claw 选服务，Flow 加“MCP 工具”，选择具体工具；不支持的 schema 需适配 |
| 已有 Function Mod，只想整体选进 Claw | 通常不需要 | 安装、批准，在 Claw 选中；仍按原事件/命令触发 |
| 旧 `cmb.mods/v1` 声明式扩展，想变成 Function Mod/动作 | 需要按新契约适配 | 保留原功能的回归基线，迁移入口、事件处理和返回值；不能只把 apiVersion 改成 v2 |
| 已有 slash command，想成为可等待、可传数据的步骤 | 需要适配；除非它已符合动作协议 | 增加动作声明和 handler；等待真实完成，返回经过 schema 验证的对象 |
| 只有传统 shell/Python Hook，想实现运行中拦截、状态/UI | 需要新增 Function 模块 | 保留业务脚本，按需通过受控进程或 MCP 调用；不要把所有脚本重写成主工程代码 |
| 从 Claude 直接搬入 Function Mod | 需要兼容核查，未必能零修改 | 检查事件提供者、SDK 用法、模型协议、import、运行额度及 UI；通过校验后再做真实执行验证 |
| 一个大插件希望每项自动行为都能单独开关 | 需要作者拆分或配置化 | 拆成独立 Plugin，或显式读取配置；现有动作选择不会自动拆卸同包 Hooks |

不要仅改文件夹名字或加一个 `mods` 标签，就把普通插件描述成已适配 Function Mods。
也不要为了组合 Skill/MCP，先给它们套一层没有业务价值的 Function wrapper。

### 3.1 保留原包，再增量加模块

常见混合包可以保留如下结构；按原插件实际清单合并，不是要求重建所有目录：

```text
my-plugin/
├─ plugin.json                    # 或现有 .claude-plugin/plugin.json
├─ skills/.../SKILL.md             # 原有技能继续保留
├─ .mcp.json                      # 原有 MCP 配置继续保留
├─ scripts/...                    # 原有业务脚本继续保留
└─ hooks/
   ├─ hooks.json                  # 增加 modules 声明
   └─ actions.ts                  # 新增 Function 模块
```

`hooks/hooks.json` 中的模块路径相对该文件所在目录，例如：

```json
{ "modules": ["./actions.ts"] }
```

上面只是 Function 部分。**已有经典 Hook 时不要直接覆盖整个文件。** 先盘点旧 Hook 的事件、
脚本和副作用，决定保留、合并或迁移哪个行为；同一门禁不要在经典 Hook 与 Function Hook 中重复执行。
Autobiz 打包器的具体策略是备份原配置到 `hooks/classic-hooks.json`，把实际入口改为 Function modules；
这是 Autobiz 的显式迁移决定，不是所有插件必须采取的规则。

Function 代码运行于受限运行时，不是完整 Node.js。现有 `node:fs`、`child_process`、动态 import
或任意 npm 依赖不能原样假定可用。可使用宿主 `$.fs`、`$.process`、`$.mcp` 等受支持入口，
也可保留已有 MCP/外部脚本实现；纯业务逻辑按装载器支持的相对模块方式组织。

### 3.2 把一个命令改成可组合动作

以已经可安装的 [Review 示例包](../examples/mods-review-agent/README.md) 为完整参考：

1. 在实际插件清单中增加 `claw.actions`。每项声明 `id`、名称、自己注册的 `command`、
   `inputSchema`、`outputSchema`。参考 [实际清单](../examples/mods-review-agent/plugin.json)。
2. 在 `session.start` 注册该命令，在 `command.run` 中处理它。多模块的 session.start 使用显式
   `{}` matcher；增加新模块时保留已有 modules 列表。
3. 从 `JSON.parse(event.args)` 取得宿主动作 envelope，校验 `version === 1`。
   业务参数在 `request.input`，配置在 `request.config`，本次目标在 `request.task`。
4. `await` 实际工作。成功返回 `{text, output}`，其中 output 是 JSON 对象；失败抛错。
   只返回“已启动后台任务”不能证明检视结束；`passed:false` 也不是当前动作协议的失败信号。
5. 给下游需要的数据声明稳定字段。例如 Review 接收 `path/source/context`，输出 `path/review/model/scope`。
6. 本地检查、安装、重新批准，再将提供者加入当前 Claw，最后在 Flow 里选择此动作。

实际实现见 [hooks/action.ts](../examples/mods-review-agent/hooks/action.ts)。不要直接在聊天中向
这个隐藏动作命令传普通字符串；它是接收宿主 JSON envelope 的入口。
该包原有 `/claw-review strict working` 则是用户命令，启动后台检视后用
`/claw-review-status` 查询，不适合不经适配就作为“等待检视完成”的流程步骤。

当前限制：每包最多 32 个导出；输入、输出根必须是对象；输入 envelope 和返回对象各最多
28000 UTF-8 字节；text 最多 8000 字符。Schema 是受限子集，不做自动类型转换或填默认值。
动作必须属于该插件，不能在声明里指向另一个插件的命令。详细契约见
[动作作者协议](mods-claw-action-authoring.md)。

`claw.actions` 是**本工程扩展**，并非 Claude 官方同名协议。

### 3.3 新旧模型接口怎么选

旧插件保持当前行为时，不加选项即可。旧 `$.model.complete()` 继续返回字符串，
现有 Review 示例就使用这个模式。

若要使用新版 `isAnswered/text/usage`，在实际使用的清单中增加：

```json
{ "cmbCompatibility": { "modelProtocol": "result-v1" } }
```

同时改调用代码和观察器，不能只改清单；`claw.actions` 本身不要求新版模型协议。
例如原来的字符串判断要改成先判断 `reply.isAnswered`，成功再读 `reply.text`，失败处理 reason。
原生 `mods/manifest.json` 与包装清单不能重复声明该选项。改变协议后重新批准并更新 Claw 引用。
此选项也是本工程扩展。完整迁移示例见 [模型协议作者说明](mods-model-result-v1-authoring.md)。

### 3.4 本地校验与升级清单

在开发工程根目录，使用 `.nvmrc` 要求的 Node 22、npm 10+；CLI 读取已构建的 main：

```powershell
Set-Location C:\ai\CmbCoworkAgent-mods-v2
npm run build
node bin/cli.js plugin check examples/mods-review-agent
node bin/cli.js plugin inspect examples/mods-review-agent --strict-compatibility
```

实际改造时将末尾包目录换成自己的目录。TypeScript 作者可使用 `plugin types` 导出宿主支持的类型，
按其类型改好签名后使用 `plugin check <目录> --types`；未经类型化的旧示例不应直接宣称通过严格类型检查。
`--out` 只写新文件，完整用法见 [作者工具](mods-v6-authoring-tooling-2026-09-28.md)。

`valid: true` 是装载/注册检查结果，不是项目授权、业务验收或所有 SDK 语义完全兼容。
`--strict-compatibility` 检查已注册事件的提供者，不会证明全部分支都能执行。

每个正式迁移包至少核对以下结果：

- 旧的 Skill、MCP、命令仍能完成原任务；没有因更新 hooks.json 丢掉原行为或重复跑门禁。
- 新动作在正常输入、缺失输入、权限拒绝、模型错误和取消时，结果与状态一致。
- 前一步输出确实到达下一步；没有把后台“已启动”或模型的“建议通过”当作实际测试 PASS。
- 更新包后旧引用能明确失效，重新批准、重新选择来源、保存并应用后可运行。
- 模型范围、读写权限、实际费用和耗时符合业务预期；保持失败记录，不吞掉异常。

## 4. 用户从安装到对话使用的完整流程

### 4.1 上传和授权

1. 从开发目录启动应用，打开带业务项目目录的**普通本地会话**。不要把插件包目录当业务工作目录。
2. 打开“自定义 → Function Mods”，选择“上传 Mods（ZIP）”或“从文件夹安装”。
   ZIP 保留完整包结构，常见做法是将 `plugin.json` 放在 ZIP 根目录；不能只上传一段 `.ts`。
   仅有 Skill/MCP 的旧插件按原 Plugin/技能/连接器入口安装配置。
3. 开启应用级和项目级 Mods，核对该包声明与摘要，点击“授权以上能力”。当前没有管理密码，
   运行授权仍保留，具体文件/工具操作也可能有原生审批。
4. 更新包、源码、动作声明或模型协议后，重新核对授权。旧组合不会自动信任同名新版本。

### 4.2 DIY 自己的组合

1. 右侧“Claw 工作台 → 配置 → 编辑我的 Claw”，为组合命名。
2. 勾选已授权 Function Mods。在“技能 Skill”“外部工具 MCP 服务”选择沿用来源，或仅使用所选。
   后者可混选不同插件来源；空选的含义是这一类不提供能力。
3. 设置“主助手默认模型”，按需绑定 implementation/review 等角色。只保存模型引用，密钥留在宿主设置。
4. 需要固定步骤时，到“DIY 流程”选择或创建流程；为流程选择一个已授权“所属 Mods”。
   添加 Agent 任务、Skill 任务、MCP 工具、插件动作、真实检查或人工确认。
5. Skill 步骤选实际技能和目标；MCP 步骤主动“加载 MCP 工具目录”，选择服务和工具、填写 JSON 参数。
   加载工具目录会连接服务。常见参数可直接用表单填写，复杂值保留高级 JSON。插件动作选择其真实提供者及导出动作。
6. 后续插件动作/MCP 可“接收前置步骤输出”：路径留空取完整 output，`/structuredContent` 可取 MCP
   结构化对象；所取内容必须是对象。固定 JSON 输入覆盖同名字段，不是任意模板表达式。
7. 保存流程；回“我的 Claw”选择该已保存版本；点击“保存能力组合”，再点“应用到当前对话”。

修改模板不会改掉已应用副本。修改流程后，需要重新选择新版本、保存组合、再次应用。
同一项目两个普通对话可以绑定不同组合；但同项目显式 Flow 互斥，完成规则仍项目共享。

### 4.3 在对话里到底怎么触发

| 想做什么 | 具体操作 | 实际效果 |
| --- | --- | --- |
| 日常使用选择的能力和模型 | 输入框选“聊天”，发送正常任务 | 使用当前 Claw 能力范围；Hook 只在对应事件触发，不保证每个能力都被调用 |
| 调一个插件查询/命令 | 发送插件文档中的 `/命令 参数` | 执行该命令，是否后台执行以命令契约为准 |
| 每次任务完成前自动检视 | 在 Function Mods 对应插件的“完成检查规则”选择报告/阻止/修复模式并保存 | 完成阶段调用该插件提供的评审及所选检查；仅选中 Review 名称不能自动获得门禁 |
| 按 DIY 步骤处理本次需求 | 当前对话应用已绑定流程的 Claw，输入框选“执行流程”，输入本次目标并发送 | 按版本快照执行，侧栏查看每步结果和人工确认 |
| 执行固定模板目标 | DIY 流程页点击“运行已保存版本” | 立即按保存的目标执行一次，不是安装、发布或生成聊天命令 |
| 解释刚才的执行结果 | 点击“带运行摘要追问”，编辑后发送 | 切回普通聊天，附带运行摘要，不重新跑流程 |

“运行已保存版本”与“执行流程并发送本次目标”是两种启动方式，通常选一种即可，避免重复执行。
关闭侧栏不等于取消；需要停止时使用取消操作。

## 5. Autobiz：看得见差异的实际例子

目标：**Autobiz 读取真实 Feature 和文件 → 独立 Review 插件检视 → 人工确认**。
这条流程不要求先实现所有未对齐 API，也不要求把 Autobiz 全部重写。

### 5.1 准备两个不同的插件

本机本次核对存在 `C:\ai\autobiz_kanban`，没有发现此前提到的 `C:\ai\autobiz\_kanban`。
请区分“上游插件源码仓库”和“你要交付业务的项目目录”；下面前者用于生成包，后者在应用中作为会话目录。

在开发工程根目录生成 Autobiz 包，输出目录必须尚不存在：

```powershell
git -C C:/ai/autobiz_kanban cat-file -t 8db1ec937d6ed3d271cb9dc540310d6633c91e70
node scripts/package-autobiz-mods.mjs C:/ai/autobiz_kanban output/autobiz-mods-migration-demo
node bin/cli.js plugin check output/autobiz-mods-migration-demo/AutobizDevOps_Plugin_Kanban_Mods
```

第一条应显示 `commit`；缺少该对象时先修复源码仓库准备，不能仅把参数换成不相干目录。
打包需要 Git、Python 及项目依赖；固定提交是经过适配的上游版本，不是直接取最新 HEAD。
再次演练应换一个新的输出目录，不要删掉此前业务数据来凑路径。

安装生成的 `AutobizDevOps_Plugin_Kanban_Mods.zip`，再从文件夹安装
`C:\ai\CmbCoworkAgent-mods-v2\examples\mods-review-agent`。前者的 examples 目录只是覆盖模板，
不能单独装；后者是完整独立包，可以直接装。两包分别授权。

业务项目须有真实 `.autobizdevops/state.json`、已存在的 Feature，以及一个非空、不超过 4000 字符的
项目文件。下例 `order-export` / `order-export.cjs` 是示例值，要换成该项目实际 ID 和相对路径；
不要为了演示手工伪造状态文件。准备动作不支持动态 workflow.d 覆盖，有此配置会明确拒绝。

### 5.2 配置流程和模型

在“我的 Claw”选两个 Function Mods，设置可用默认模型；如果 Review 要用另一个模型，将其加入
角色模型允许集合。然后在 DIY 流程配置：

| 顺序 | 步骤 | 填写内容 | 预期证据 |
| --- | --- | --- | --- |
| 1 | 插件动作：Autobiz「准备单文件检视输入」 | 输入 `{"feature":"order-export","path":"order-export.cjs"}` | output 有真实 feature/checkpoint/path/source/context |
| 2 | 插件动作：Review「独立 Review：检视前一步文件」 | 选择第 1 步输出，路径留空，固定输入 `{}`；配置先用 `{}` 沿用默认模型 | 等到模型真实返回，output.review 有检视内容，scope 为 single-file-no-tests |
| 3 | 人工确认 | “核对检视结果及检视范围，确认后结束” | 流程停下等待同意或拒绝 |

需要 Review 使用指定模型时，它的动作配置可填 `{"model":"custom:实际模型ID"}`，同时在 Claw 中
允许这个模型。**这是此 Review 动作约定的参数，不是所有插件动作的通用保留字段。**
Agent/Skill 步骤可直接选模型或角色；不能假设给任意插件动作选择角色就会自动改写它内部的模型调用。

保存流程 → 在 Claw 选择此流程 → 保存组合 → 应用到当前对话 → 输入框切换“执行流程”，发送：

> 检视订单导出文件的正确性、边界和失败处理。报告具体问题与依据，不修改文件，不宣称执行过测试。

在右侧核对第 1、2 步的提供者确实不同，Review 的结果真实存在，最后等待人工确认。
若要运行测试，再加“真实检查”，要求项目具有相应脚本/环境。若要推进业务阶段，另加 Autobiz
验收/阶段推进并满足宿主校验与审批；此双插件示例本身不会推进阶段。

### 5.3 怎么确认这是 DIY，而不只是换了文案

1. 将 Review 的请求模型改为另一个已配置且被允许的模型，重新保存并应用，核对宿主实际请求记录。
   动作 output.model 是请求模型引用；若另有 Mod 路由覆盖，最终模型以宿主记录为准。
2. 插入一个来自其他插件的 Skill 任务，或一个只读 MCP 查询步骤，核对来源和步骤结果。
   MCP 结果传给下游时，要匹配后续动作要求的字段，不能把任意文本当 Review 的 path/source。
3. 在独立演练项目中把输入改成不存在的文件，预期第 1 步失败，第 2 步不应仍显示检视成功。
4. 仅保存新模板而不应用，当前对话应继续用旧副本；应用后才使用新版。

这里的收益是：换执行者、换模型、加检查或调整顺序，有相应的真实执行变化和记录。
它不承诺模型一定找到所有问题，也不把一次单文件检视等同于全仓回归。

### 5.4 如果需要“普通任务结束后自动代码检视”

不要只保存上面的显式 Flow。对已经实现完成评审处理器的 Autobiz Mods，在“完成检查规则”先选
“仅报告 + 本次代码改动 + 代码评审”，保存项目规则，再在普通聊天执行有真实代码改动的任务。
查看任务底部“完成检查证据”。需要失败阻断时，再选择“阻止完成”或“自动修复并复检”，并配置预算。

安装、打开 `/kanban`、勾选组合，都不会自动开启此门禁。其他任意 Review 插件如果没有完成处理器，
也不能靠勾选“代码评审”就自动补出实现。规则与显式 Flow 可并存，部署前核对是否重复检视、重复计费。
完整语义见 [完成规则](mods-v2-application-completion-rules.md)。

## 6. 常见问题与定位

| 现象 | 先看什么 |
| --- | --- |
| Plugin 能安装，动作列表却没有内容 | 是否真的导出 claw.actions；Skill/MCP 直接用相应原生步骤；是否已批准当前版本 |
| 切了组合，普通回答没变化 | 该能力是否只有命令/事件触发；组合是否应用；不能用回答文案判断执行 |
| 保存后发送任务没按顺序跑 | 是否重新绑定保存的流程并应用；输入框是否选“执行流程” |
| 插件更新后组合不可用 | 重新批准、重新选动作/来源/流程版本、保存并应用；不按同名绕过摘要 |
| 没有可选“所属 Mods” | 应用/项目开关、完整 Function 包、项目授权；仅安装 Skill 不能提供 Flow 所属 Mods |
| Skill 在斜杠菜单里却无法发送 | 菜单仍可能列全局来源，但当前 Claw 未选择它；实际发送按身份校验 |
| MCP 有服务却没工具节点 | 主动加载目录；检查连接和 schema 支持范围，加载失败不代表原服务已卸载 |
| 模型调用协议冲突 | 调用者和同一模型操作的观察器是否同属 legacy-v1 或 result-v1；同时核对新摘要 |
| 某节点失败但脚本/远端已写入 | 取消/失败不等于回滚；核对实际产物再决定重跑，不能自动重放未知副作用 |
| 找不到这里的新页面 | 是否误开 UAT/旧安装包，是否普通本地项目会话，Mods 是否开启 |

要退回原使用方式，移除当前对话的 Claw 覆盖，检查并单独调整项目完成规则；
“保存空组合”不是“恢复原配置”。恢复配置也不会撤销已经写入的文件或远端操作。
