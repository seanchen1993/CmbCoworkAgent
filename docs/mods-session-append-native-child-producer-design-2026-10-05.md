# 子任务的原生消息接入（方案草稿，等待两位评审）

## 用户可感受到的效果

主任务派发给子任务后，Mods 的消息处理也能作用于子任务实际产生的回复和工具结果。
子任务后续请求会继续使用处理后的完整消息。重开记录时显示同一份已确认内容，多个
并行子任务各自保存，不会混入主任务或另一个子任务。取消时等待实际工作结束。

本草稿先闭合回复与工具结果的真实来源及保存，子任务初始输入仍保留原框架行为。
初始输入改写、流式事件和其他输入入口随后单独落实实际地址，不能称为已经对齐。
这些是继续实施项，尚没有框架无法实现的证据。

## 已确认的工程事实

- `runtime.ts` 的真正 string-prompt 子任务工厂已经使用
  `createFunctionConversationSharedAgent`，保留原 `createAgent` 初始化和任务调用。
  当前子任务只安装会话通道中间件，没有主任务的原生消息宿主。
- 实际共享检查点读取分配子任务命名空间。`FunctionConversationSharedNativeRead`
  是私有对象；初始化、恢复和并行预留已经有完整实际 Saver 流程，不能按公开名字猜测。
- `registerSharedChild` 已建立原子任务登记、真实目标和独立显示位置。
  `completeFunctionConversationSharedActive` 在登记完成后固定实际目标与显示位置。
- `ModsManager.captureFunctionNativeConversationRuntime` 和原生规则来源注册目前仅允许
  主任务的 `FunctionConversationNativeRunProof`。共享子任务不能复制主任务运行证明。
- 同一个已创建的子任务图可以并行调用。每次直接安装新的节点宿主会替换方法并产生
  竞争，因此实际图的方法只安装一次，每次运行选择自己的私有实例。

## 提议的最小基础

1. 在真实 `SharedActive` 完成之后，由原工厂产生新的私有子任务生产来源对象。
   私有记录绑定原 Active、SharedNativeRead、实际 Saver、实际 authority、invocation、
   scope、已登记 target、原 parent 及精确 destination。拒绝克隆、同名、相同配置和
   已关闭对象。调用实际原 family、预留、源与显示位置核验后，末尾纯核所有地址、
   当前数据库、物理身份及取消状态，不能只比较公开命名空间。
2. 原共享子任务登记只增加宿主内部取得该对象的接点，复用其已登记的真实 target。
   不新建另一个 family、显示位置或 owner；关闭子任务只退该子任务，不能关闭父 owner。
   Coordinator 保持 SDK 会话的既有主任务视图，原生子任务生产者独立使用真实子目标。
3. Manager 保存同 authority 的该真实登记，建立独立原生运行对象。`run` 是该原工厂
   固定的 invocation 地址，数据库、signal、binding、target 和 destination 均来自
   上述来源。新增规则来源注册只能接收这个真实对象，不能把 Main-only 注册变成接受
   普通 callback 的通用接口。每次核原 authority、绑定、规则及部署值；关闭和撤权后
   不复用上次规则正确性的结果。
4. 实际子任务图工厂一次安装稳定的原节点包装与原模型回调来源。每次调用使用独立
   私有运行域；实际 scope 准入之后创建该域的原生宿主。节点开始、完成、取消清理
   与显示处理都绑定同一真实域和原 task/address。不得仅在完成时按当下域追认来源。
   未获得当前实际域的原图调用保留真正普通调用路径，不能获得新原生保存证明。
5. 完整模型与工具结果经过原 Protector、Keeper、Store、显示凭据和 Saver 成员索引。
   模型/工具只执行一次。保留主任务已实现的最终纯数据核验、完整返回容器核验、
   同次存档以及最后真实 drain。原图命令、工具参数、关联与原控制字段不重造。

## 在评审前必须明确的接点

- 原 Coordinator 返回的真实 child target 与 owner 如何只由该登记对象取得。
  不以公开 `binding.target` 作为运行权限。应由同一登记私有表关联读取。
- 共享工厂的稳定节点包装如何在原 Runnable 首次运行前固定 invocation，并在所有
  实际异步完成阶段保持一致；并行调用不得临时替换图方法或共享一个可变 currentHost。
- 原模型调用来源对同一 model 实例的并行使用如何保持 Attempt 地址和真实回调实例。
  不能按 agent 名字或 provider run ID 等值拼接。
- 当前调用返回和 scope 关闭前，如何先等待原生宿主及原框架的真实清理结束。
- 子任务恢复时保留原显示位置与已有完整消息；不能创建新记录把缺失证明修成成功。

## 真实来源接点的修订

原共享读取对象在 `getTuple` 的 `admit` 返回后即从私有表删除，不能将它当作长久权限。
生产来源必须在原 `completeSharedActive` 与原登记仍在该准入调用中时生成，私存当时
已认证的原读取视图、原 config、namespace、Saver 与 scope。之后调用固定原视图的
守卫，并核 Active 预留、真实登记、target、destination、数据库及原物理身份；不会
重新读取已删除的凭据，也不会延长原读取对象的有效期。

Coordinator 的原登记应返回新的私有登记对象，仅在其自己的表中关联既有 target、
父 owner 与 destination。Manager 读取这一对象并核原 Active，不能按公开 binding
再登记另一个主任务。恢复准入沿原 Saver 与完整成员索引，在当次完成登记后建立新的
私有运行域；旧运行域和旧输出始终无效。

稳定包装需在实际节点的任务 latch 安装后、第一个来源回调之前固定本次运行域与宿主。
Work 和 slot 保存固定的真实 runtime 与宿主回调快照。Tools 原包装从同一个实际 Work
取得该 runtime，真实 request 再固定它；不能永久使用图安装时的另一个 runtime。
模型来源每域独立，实际首 Start 回调在原 Calls 私有域中固定 Attempt，再合并本域
原 callback；相同 model 对象或重复 provider ID 不建立跨域关系。

全图只安装一次。关闭一个运行域不能关闭整图节点或整图 Tools 表，必须按真正 Work
归属停止本域的新工作、等待该域 Keeper/Tools/节点工作及原 scope 全部结束，再释放
authority 与 namespace 预留。无当前共享域时保留原普通调用；它没有原生保存资格。

上述修改解决了原读取短寿命和 Tools runtime 等值错误。全图一次包装与逐域宿主的
具体只读登记接口仍需两位评审确认，不能用一般的可变 currentHost 或公开回调替代。

## 实际回归要求

使用真实 Manager、共享 string-prompt 工厂、ToolNode、Saver 和实际数据库，而不是
只用一个普通闭包或伪造 checkpoint。至少覆盖：

- 真父任务派发子任务；子任务模型回复和工具结果改写，下一次子任务模型拿到完整
  处理结果，工具只执行一次，父任务使用原工具返回并继续自然执行。
- 同名并行兄弟、同一子图重复调用与不同 invocation，分别核实际目标、显示位置、
  保存凭据及模型请求；复制 metadata/config/ID 和晚到事件不能跨域。
- 真实关闭、取消、撤权、规则变化及同名物理会话重建，不发布旧结果、不重复执行。
- 首次保存、真实重开/恢复及已有显示位置丢失时拒绝；源守卫在末尾改变正文或凭据
  时，原图存档和下一请求都不接收错误结果。
- 无 Mods 的原子任务路径和原 Plugin/项目/Harness 回归保持；完整正文与原测试
  时限保持，性能另行独占测量。类型、构建、实际桌面流程与两次独立源码检视均需完成。

## 当前实施与验证状态

基础方案已通过两位独立设计与源码评审。真实共享登记、原生产来源和独立 Manager
运行对象已经实现，基础回归 88 项通过。稳定子任务图、逐次运行域和逐域清理已经
实现，第一次独立源码评审通过；第二次发现 Host 内部还需启动并观察全部清理组，
相关窄修见 `mods-session-append-native-child-current-design-2026-10-05.md`。

新产品并行用例尚未通过原 5 秒时限。实际统计发现约 14.6 万次重复查询，正在设计
固定读取语句优化。基础通过不等于整个子任务产品通过；模型/工具改写、下一次实际
模型请求、冷恢复、撤权和完整桌面流程仍须逐项验证。没有框架无法实现的证据。
