# DevClaw 2.0.0：可组合插件的创造、修改与使用

## 1. 版本与职责

DevClaw 应用版本固定为 **2.0.0**，不同构建通过 Git 提交、Actions 运行编号和文件摘要区分。AutoBiz 的插件版本独立管理，不能用应用版本代指插件版本。

本轮 AutoBiz 插件为 **1.1.0**：基础版保留原主流程，需求转换版在需求讨论前加入转换步骤。需求转换版的产物要求当前 Feature、非空需求列表和整数 `revision`；最终交付样例采用修改后的规则 `revision >= 2`，技能名为 `requirements-convert-v2`。创建自己的衍生流程时，由业务需要决定这些规则，不是平台统一要求所有插件采用这一格式。

本次改造将三项职责分开：

| 层次 | 职责 |
| --- | --- |
| 平台创造者 | 读取实际插件、形成修改计划、诊断依赖、保存独立草稿、生成候选、安排试用和原生安装确认 |
| 插件可组合契约 | 声明步骤、技能入口、输入输出、必要校验、配置和资源依赖 |
| 状态 Mod 与原执行器 | 根据实际生效流程决定下一状态，执行原校验，通过原有唯一写入器提交，再读取真实结果 |

通用改造接口不识别“需求转换”“供应商”等业务名称。AutoBiz 保留既有兼容适配器；其知识库、Python 校验器、Hooks 和状态写入方式仍由插件提供。本次没有将 AutoBiz 的阶段数量或新增业务步骤写入平台逻辑。

## 2. 一句话提出改造需求

在已启用创造者模式的聊天中选择新版可组合 AutoBiz 来源，输入：

> 基于这个 AutoBiz 插件，在需求讨论之前增加“需求转换”步骤，将原始需求转换为结构化需求。要求包含当前 Feature、非空需求列表和版本字段；需求讨论必须读取这份产物并保留来源。自动补齐产物校验、上游依赖和状态衔接，保留原知识库、Hooks、配置和必需校验。先给出修改预览，再申请独立试用，通过后保存为独立插件。

创造者需要读取真实源码和契约后生成 Skill、必要校验实现及结构化修改，不能只增加一句提示词或一个界面节点。业务含义不明确、没有可用执行器或原始流程无法安全映射时，应说明缺项，不能臆造兼容性或成功结果。

模型负责理解和编写业务内容；平台保证的是来源绑定、结构化校验、受控保存和执行验证。这不构成“任何旧插件都能一次自动转换成功”的承诺。

AutoBiz 1.0.5 内的旧状态 Mod 固定七阶段；安装新版 DevClaw 不会自动改写已安装插件里的代码。请使用本轮交付的新版 AutoBiz，或先在独立候选中更新状态扩展并重新试用。组合时保留知识扩展与状态扩展，不能只选择主干步骤后宣称保留了原完整插件。

## 3. 新步骤如何衔接

以新增需求转换为例：

```text
原始需求 → 需求转换 → NORMALIZED_REQUIREMENTS.json → 原需求讨论 → 原后续步骤
```

新增步骤声明产物路径、结构和校验器；下游同时声明对该产物的必需输入及上游步骤依赖。组装器重新计算顺序、入口、相邻转换和界面操作。原快捷入口不能绕过新增的必经前置步骤。

AutoBiz 的状态 Mod 读取原编译器针对当前 Feature 得到的实际流程，使用其中的合法边和摘要进行决策。状态提交前重新检查源文件、实际流程、产物和原 Hooks；写入时再次验证，并同步维护 `state.json` 与 `STATE.md`。不再在状态 Mod 中固定七个主阶段。

本轮该状态提交适配器面向 Windows 本地 NTFS，依赖原业务运行环境。DevClaw 其他平台安装包可用，不等于这一插件适配器已经具备跨平台状态提交能力。新电脑需按环境说明重新检查 Python、Node、Git、业务构建工具和知识配置。

原 Skill 的业务正文保留。插件侧通过公开的技能生命周期接口补充当前状态控制规则，要求使用当前插件的 `state_read`、`state_preflight`、`state_advance` 和 `state_reconcile`。原初始化、新建 Feature 仍使用原插件入口，并按新流程初始化；这不表示所有旧 CLI、任意文件写入或历史状态都被平台全面接管。

## 4. 修改中间技能或步骤

可以继续在同一创造者聊天中提出：

> 保留开发阶段的原验收规则和知识资料，修改开发技能，使其先输出变更计划再执行。生成新候选，重新验证，不覆盖原插件或复用旧试用结论。

或者：

> 修改需求转换步骤，新增 revision 最小值要求，并让下游保留该版本信息。检查所有输入输出版本和必要校验，生成新的试用候选。

每次修改绑定原来源摘要、当前工作流摘要和草稿版本。旧摘要不能覆盖新草稿；替换原步骤必须明确指定原来源及替换来源，普通同名模块仍会被拒绝。

原必要校验、产物要求、人工审批、动作引用、配置及知识资源不能在改写中隐性删除。需要更改实现时，应编写独立的新资源并明确引用，不能通过修改原必需校验器使测试通过。

保护基线取自重新核对的原插件，不能由模型自行指定。用户尚未发布的新步骤、自己追加的产物结构和衔接规则可以继续对话调整；平台重新检查整个流程的一致性，并使旧预览、试用和确认失效。这样既能修改自己的草稿，也不能借多轮修改逐步删除原插件的必要约束。

对于已声明 Hooks 的原业务技能，本轮允许保留技能名称修改正文；直接改名会被拒绝，提示先明确迁移 Hook 名称绑定。新增加的草稿技能和没有 Hooks 绑定的 Host 技能可以按契约改名。平台不会用保留一个未再命中的旧 matcher 来冒充 Hooks 已保留。

原步骤的 checkpoint 标识也可能被原业务校验和 Hooks 引用，因此保留其身份，只重算步骤之间的相邻转换。新增步骤可以声明自己的状态；修改历史状态名称需要独立迁移，不能隐含在一次技能改写中。

较大的原技能资源通过只读摘要引用保留，生成候选时重新核对原文件，不占用新增作者源码的单文件和总大小预算。

**修改后的候选需要重新验证。** 已运行项目使用其绑定的包快照；编辑安装目录不会安全地热替换正在执行的代码。若实际执行源或步骤契约发生变化，状态 Mod 拒绝继续使用旧证据。应重新生成候选、申请新试用，再按原生确认流程更新或安装。

本次不以“把旧项目直接改为任意新状态图并接着运行”作为已完成能力；历史状态迁移需要独立的明确映射与恢复验证。

## 5. 知识、Hooks 和配置如何保留

1. 共享内核继续绑定实际来源及精确资源，不由模型替换为占位实现。
2. 原知识资源、上下文提供器和配置声明进入生成包的资源闭包。原脚本、校验器和知识文件保持原摘要；新增功能使用自己的命名空间。
3. 用户实际配置值和密钥不随源码导出。安装到新电脑或创建新试用时，仍需绑定该电脑的知识路径、环境和必要凭据。
4. 原 Hooks 继续按其真实事件和条件执行。SDK 的进程调用不会自动重放普通工具的全部 Hooks；状态 Mod 显式复用原生命周期、产物、业务校验和候选代码摘要规则。候选决策文件和真实代码摘要在准备、持锁检查及提交确认后重新核对，变化即阻止写入；不在状态锁内执行原 Hook 的回退副作用。不能把所有 Hooks 简化为无条件成功回调，也不能用 Mod 的“允许”替代原产物校验。
5. 文件存在、编译通过、进程退出码为零或界面显示安装成功，均不能单独证明业务完成。必须核对实际业务校验、提交回执和提交后的状态读取。

## 6. 失败与未知结果

| 情况 | 行为 |
| --- | --- |
| 必需产物缺失、结构不符、校验失败 | 不推进状态，修复产物后重新检查 |
| 上游文件在检查后发生变化 | 拒绝使用旧输入证据，重新检查 |
| 来源、技能或流程摘要变化 | 不复用旧试用、旧确认或旧提交证据 |
| 草稿版本冲突 | 保留现有稿，重新读取后修改 |
| 安装、导出或状态提交结果未知 | 先只读对账，不自动重复执行 |
| 新电脑缺少知识路径或配置 | 明确补齐本机绑定后再运行 |

这类失败应产生可定位的错误与下一步操作，不能以长期等待或伪造成功掩盖。

## 7. 验证标准与使用顺序

完整验证应分别覆盖：实际包准入和编译、正常输入、缺失产物、错误结构、上下游版本、校验后改动、源代码变更、重复请求、原 Hooks 失败以及状态双文件一致性。

本轮 AutoBiz 示例另外包含插件侧需求传递校验：PRD 必须保留归一化需求原文及其来源。只生成结构正确的 JSON，或只在提示词中要求“读取上一步”，都不足以通过此项业务验收。此类业务规则由插件提供，平台负责声明、绑定和调用，不内置需求文档的判定逻辑。

AutoBiz 本轮新增的严格产物衔接限定为不超过 256 KiB 的普通文件，并检查路径及链接。目录或更大产物需要额外的受限收集和摘要协议，当前明确拒绝；不能将此示例概括为任意体积、任意类型的业务数据都已支持。

独立供应商插件使用同一套工作流修改和组装入口，在原 Host 执行器中验证“需求转换 → 资料整理 → 准入决策”。AutoBiz 使用原 Python 内核和状态 Mod 执行器。两者状态写入方式不同，通用性体现在共享的改造、依赖、资源保护、保存和交付规则，不要求把所有插件改成同一个业务执行器。

用户使用顺序为：选择来源 → 对话提出修改 → 核对实际预览 → 确认独立试用与配置 → 查看真实校验结果 → 保存/导出 → 原生确认安装 → 创建或选择绑定该插件版本的项目。

自动化测试可以控制模型输出以复现业务边界，同时执行真实脚本、校验器、状态写入和快照。此类测试不能代替远程模型质量、企业知识库连接或用户电脑环境的实际验收。

## 8. 开发者接口

`mod_business` 增加：

- `read_workflow`：读取实际来源或当前草稿的流程、输入输出和摘要。
- `transform_workflow`：以 `insert`、`replace_step`、`replace_skill` 提交有版本约束的结构化修改，保存独立草稿并使旧执行证据失效。

修改后继续使用既有 `preview`、`request_trial` 和 `request_review`。这些模型工具不能替用户批准安装、授权、试用或恢复。缺少执行器和真实契约的原插件仍需先完成源码分析及模块化适配，不能仅凭通用修改接口宣布迁移成功。
