# DevClaw 创造者能力与操作边界说明

核对日期：2026-10-23。适用范围：Mods-v2 分支当前实现。应用版本固定 2.0.0，插件版本独立管理。本文作为能力支持、操作路线和后续验收的跟踪依据。

本文区分源码实现、本地验证、持续集成和可下载安装包四种交付状态。首次提交 `4ddda76780d903a47d1dd3b5a54d014bb6ec8e67` 的持续集成在 Windows 临时目录短路径测试夹具处失败；随后的夹具修复已按工作流原参数完成本地 16 文件、147 项复验，生产安全边界未改变。新 Windows 包是否完成，仍须核对修复提交对应的最终构建编号及附件摘要。自动化验证不能替代远程模型、真实企业知识库和业务效果验收。

## 一、能力范围与职责

创造者已经可以读取实际插件、提出结构化改造、生成 Skill 与校验源码、保存多轮草稿、组合为独立候选、安排隔离试用，并在原生确认后安装或导出。任意旧插件的语义识别、全部状态迁移及外部系统恢复仍需明确适配和验证。

模型负责理解需求和编写业务实现；平台负责来源、契约、资源、版本、权限、保存和真实执行证据的约束。模型的文字答复、文件生成、编译成功、进程返回 0 和插件安装成功，是不同事实，不能相互替代。

### 1.1 能力支持矩阵

| 能力 | 当前类别 | 实际支持与必要条件 | 不能据此承诺 |
| --- | --- | --- | --- |
| 在聊天中切换创造者 | 已实现 | 普通本地聊天可直接点击输入区“创造者模式”；缺少工作目录时按提示选择目录 | 不必先去设置开启创造者；但权限、目录与应用灵件启用仍需明确确认 |
| 读取实际安装插件 | 已实现 | `mod_business` 取得真实来源身份、文件和摘要；只读取准许范围 | 不能凭插件名字或过时目录猜接口，不能读取或输出密钥 |
| 从零制作 Function Mod | 已实现，需检查与确认 | 提供脚手架、源码保存、编译诊断、试用和正式复用入口，按实际能力授权 | 纯函数试用不等于完整业务插件已经迁移或业务运行通过 |
| 生成状态 Mod 骨架 | 条件支持 | `scaffold(kind:state-extension)` 生成可执行决策骨架及迁移计划；需绑定真实状态读取、原写入器和检查 | 默认保守决策，不会自动识别未知业务边或生成真实提交成功回执 |
| 原始标准 Host 插件首次模块化 | 条件支持 | 已有明确阶段、Skill、产物和检查声明，可生成保留原文件的独立候选，用户确认后继续组合和试用 | 静态候选不代表业务成功、已安装或状态控制已迁移 |
| 只有 Skill 或动态脚本的原始插件 | 需作者/创造者明确适配 | 分析真实入口、Hooks、状态读写、知识和配置；编写完整 catalog、执行映射、必要附加源码和真实检查；平台校验后另行确认 | 不能从目录顺序或描述自动猜出全部状态图、外部副作用和业务含义 |
| 转换错误后的对话修复 | 条件支持 | 按原生诊断的路径、错误码及缺项，修改本次迁移计划或新增源码后重新请求确认 | 不保证模型一次修好；不得删除原必要检查、变更原身份或重放结果未知的操作 |
| 业务步骤与常驻 Function Mods 组合 | 条件支持 | 通过依赖和资源声明组合步骤、知识、状态及界面扩展，检查命名空间、配置和 provider 冲突 | 常驻扩展不能作为业务阶段排序；多个任意来源不保证协议或执行器兼容 |
| 基于新版可组合 AutoBiz 1.1.0 前插步骤 | 条件支持 | 使用实际来源与摘要，生成真实技能、产物和校验；原下游显式依赖输入；保留知识及状态扩展；重新试用 | 安装新应用不会自动改写旧 AutoBiz 1.0.5 的固定七阶段状态 Mod |
| 跨业务复用改造机制 | 条件支持，已有独立验证 | AutoBiz 与供应商准入来源使用相同流程修改、资源保护、预览和交付接口，实际执行分别服从原执行器 | 不表示任意插件均兼容，也不要求将所有业务迁移到同一个状态写入器 |
| 修改原中间 Skill 正文 | 已实现，受基线保护 | 保持原检查、Hooks、知识、配置与必要资源，保存新草稿、重新生成候选和试用 | 不能修改原必需校验器使其无条件通过，不能复用旧业务成功结论 |
| 修改自己新加、尚未发布的步骤 | 已实现 | 可继续改 Skill、输出 schema、输入、依赖及新增检查；全流程需继续一致 | 上下游 schemaVersion 不兼容不会自动忽略，旧契约的生产回执不能继续用 |
| 原步骤必要契约保护 | 已实现 | 原真实来源是保护基线；原必需输入输出、检查、动作引用、人工审批、资源与身份不能隐性弱化 | 模型不能指定“空保护基线”或通过多轮编辑逐步删除原约束 |
| 原 Skill 改名 | 部分支持 | 没有原 Hooks 绑定的 Host 来源、新增草稿步骤可按契约改名 | 已有 Hooks 的原业务 Skill 改名需要显式迁移映射，本轮拒绝隐性丢 matcher |
| 原 checkpoint 改名 | 当前变更入口不支持 | 保留原身份，允许组装器重算邻接边；新步骤可声明自身状态 | 历史状态名称迁移不能隐含在一次 Skill 改写中 |
| 保留大原始资源 | 已实现 | 原资源以路径和 digest 只读引用，生成候选时重新验证原字节，不挤占新增源码预算 | 不能通过引用读取任意宿主路径、替换原脚本或隐藏知识变化 |
| 多轮草稿保存 | 已实现，有额度 | 同聊天最多 4 份业务草稿，每份最多 8 个版本；revision/CAS 防陈旧覆盖 | 不提供无限自动历史、随意删除旧稿或自动换聊天规避额度 |
| 应用重启后继续创作 | 部分实现 | 草稿和交付记录有持久化，重新进入创造者后读取真实记录，重新检查来源和生成必要预览 | 内存 inspection、待确认迁移和旧授权不自动恢复；看不到旧面板不等于草稿被删除 |
| 隔离试用与原聊天关联 | 已实现 | 试用有独立项目/执行会话，原聊天汇总候选、阶段、产物、检查、会话和反馈 | “一个用户聊天”不等于所有阶段共用一个物理 agent 会话 |
| 自动判断试用成功 | 条件支持 | 使用真实产物、检查及业务证据；候选、契约和运行必须一致，证据截断会提示缺口 | 不能仅凭“模型说完成”、聊天终止或程序退出 0 判业务全部通过 |
| 配置和知识绑定 | 已实现，需用户环境 | 配置 schema 随插件；宿主管理的敏感值和本机目录由原生入口输入；新项目和新电脑重新绑定和预检 | 宿主管理的密钥、本机绑定路径和执行授权不会自动随导出插件迁移；原来源已有连接配置仍需作者分发前核对 |
| 保存为新插件 | 已实现 | 已检查候选在原聊天产生原生交付卡；用户分别确认安装或导出 | 草稿保存、生成候选、试用通过和安装完成不是同一动作 |
| 安装、导出未知结果对账 | 已实现 | 只读核对实际安装内容或 ZIP 的精确身份；已发生、未发生、冲突、未知分别处理 | 不能因回调超时自动重复安装、覆盖文件或重放状态提交 |
| 保存后直接使用 | 已实现 | 交付卡“开始使用”核对实际包，按聊天扩展/Host 项目/插件项目定位入口，可就地补配置 | 打开入口不等于授予执行权限或跳过配置预检 |
| 同名已安装插件更新 | 条件支持 | 组合交付可能为仅导出；导出更新 ZIP，再走原插件安装确认，保留 UUID 与配置，权限变化重新确认 | create-only 安装器不能假称直接覆盖已安装版本 |
| 运行期间修改安装目录 | 不保证安全热替换 | 运行绑定来源快照和 digest；改动后需要新候选、新试用或受控 reload | 不能保证正在运行的会话无缝采用任意新代码，也不能继续使用旧授权和证据 |
| S6 Host 阶段隔离调试 | 条件支持 | 真实阶段进入快照、原运行已结算、兼容候选、受控输入和新原生确认；支持 stage/downstream | 不是任意插件、MCP、外部动作、Git 或数据库状态回退 |
| AutoBiz 插件自有阶段恢复 | 平台条件能力，当前附件未提供 | 需包声明有效恢复适配器，原试用与进程已结算，再复制独立输出、调用原回退脚本并重新验证接管 | 当前r13两份1.1.0包均未携带`devclaw.stage-recovery-adapter.json`，不能直接按恢复入口操作；也不支持任意Git、worktree或外部仓库恢复 |
| Python 查询与知识加载性能优化 | 目前只有部分基础机制 | 已有配置缓存、归因缓存/单飞、Worker 和防抖；真实知识正文仍可在每轮前运行 Python/Node | 未实现完整的通用 provider 跨轮缓存、知识版本失效及进程池，不能声称新插件必然更快 |

支持口径依据：[创造者能力声明](../src/main/mods/devtools/creator-support.ts)、[业务插件工具](../src/main/agent/tools/mod-business-tool.ts)和[Mod 创作工具](../src/main/agent/tools/mod-authoring-tool.ts)。该矩阵中的“条件支持”不应在界面或报告中简化为普遍支持。

## 二、原始插件与可组合插件的机制变化

| 事项 | 原始插件常见方式 | 新版可组合插件 |
| --- | --- | --- |
| 阶段组织 | Skill 提示、CLI 或脚本内部约定顺序 | catalog 显式声明步骤、Skill、依赖和输入输出，受执行器支持范围约束 |
| 状态推进 | Skill 调脚本改 state，流程图可能散落脚本 | 状态 Mod 根据当前 Feature 实际编译流程判断合法边，复用唯一原写入器提交；Host 插件仍保留 Host 权威 |
| 新增前置步骤 | 人工改多个脚本、提示和入口，容易遗漏 | 创造者提交结构化 insert，统一重新计算入口与相邻边，并要求显式下游输入和真实检查 |
| 修改中间技能 | 常直接改安装目录，再从头运行 | 独立草稿和候选，可多轮改正文；来源、原契约、资源及证据受保护，重新试用 |
| 产物衔接 | “下步读取上一步”依赖提示自觉 | producer、输入路径/版本、schema、validator 和真实执行证据共同核对；业务语义仍由插件提供 |
| Hooks | 按 Skill/工具/生命周期规则执行 | 原规则继续存在；状态 Mod 明确复用原必要门禁，不能用 SDK 进程调用假称自动触发全部普通工具 Hooks |
| 知识和配置 | board 配置、环境变量、脚本加载 | 原配置和上下文路径保留进资源闭包；本机值由原生绑定，候选与运行核对身份 |
| 保存与团队复用 | 人工拷目录、改文件、打 ZIP | 预览、独立试用、确认安装或导出，有精确摘要和未知结果对账 |

新版继续复用 Skill、Python、Hooks 和原状态文件，将可组合边界表示为机器可读契约，并为生成、修改、验证和交付提供统一机制。任意脚本接入仍需明确执行入口、输入输出、权限和校验语义。

## 三、推荐的实际使用路线

### 3.1 第一次安装和确认入口

1. 安装最终构建成功的 DevClaw 2.0.0，核对构建来源；安装新版 AutoBiz 基础插件 1.1.0。不要仅按应用版本判断插件内容已更新。
2. 在“灵件与使用设置 → 我已添加”查看实际插件、启用状态、来源及权限。包含 Function Mods 时，按当前聊天提示明确启用“应用和当前项目灵件”，再核对权限；打开设置不会自动授权。
3. 在目标普通本地聊天选择实际工作目录，然后点击聊天输入区“创造者模式”。无须先去设置切换。输入区“使用指引”仅在创造者模式出现，可再次打开；“创作工作区”按实际创作任务显示。
4. 如果使用手动组合入口：“灵件与使用设置 → 对话创作 → 高级：手动组装、源码与历史版本 → 从 Mods 组装”；工作台另有“从 Mods 组装新插件”。它面向已经有 Mods 契约的来源，不会仅通过勾选自动完成复杂原始插件首次迁移。

UI 依据：[聊天中的创造者入口和指引](../src/renderer/src/components/customize/ModsDevelopmentPanel.tsx)、[灵件管理页](../src/renderer/src/components/customize/ModsPanel.tsx)、[工作台组合入口](../src/renderer/src/components/customize/ClawPanel.tsx)和[使用设置入口](../src/renderer/src/components/customize/ModsUsageSettingsEntry.tsx)。

### 3.2 可直接复制的一句话需求

> 请读取我已安装的 AutoBiz 1.1.0 实际源码和可组合契约，在需求讨论前新增“需求转换”步骤，将原始需求生成 NORMALIZED_REQUIREMENTS.json，包含当前 Feature、非空需求列表和整数 revision；需求讨论必须读取并保留这些需求原文和来源。请同时生成真实 Skill、产物 schema 和校验实现，补齐下游输入、依赖、入口及状态衔接；完整保留原知识、配置、Hooks、必需校验和原唯一写入器，不修改原插件。先给真实修改预览，再申请独立试用，展示每阶段实际检查和状态结果；我确认后再保存、安装或导出为独立插件。无法安全映射的部分请明确列出，不要猜测或报告未发生的成功。

工具实际路线是：`inspect` → `read_workflow` / `read_mod` / `read_asset` → `transform_workflow` → `preview` → `request_trial` → 原生确认与试用 → `request_review` → 原生安装或导出。工具可由创造者调用，用户无需手写这些参数，但应能看见真实预览和确认卡。

### 3.3 原始插件尚未模块化时

直接说明：“请先检查这个原始插件，列出真实阶段、状态写入器、Hooks、配置、知识和必需产物；能安全自动拆分就生成独立迁移候选，不能确定的地方明确要求适配，不覆盖原插件。”

实际路径是 `inspect_raw` → 读取原资源与迁移 schema → 明确 catalog/必要附加源码 → `request_modularization` → 原生确认创建独立源候选 → 再进入普通组合和试用。当前允许有界附加文本文件，不允许改写原文件、身份、凭据路径或用新增文件覆盖原资源。原始来源变化时要重新检查。

标准 Host 声明可直接形成静态候选；任意 Python 业务状态机、动态 Hooks 或私有外部系统需要作者补明确映射及运行验证。平台拒绝不明映射是可靠性边界，不应删除原校验来“修复转换错误”。

### 3.4 继续对话修改

修改原开发技能：

> 保持开发阶段 Skill 名称、原 checkpoint、必需产物、原校验器、Hooks 和知识资源不变，只修改正文为“先给出变更计划，再分步实现和验证”。保存新候选并重新试用，不覆盖原安装包。

修改刚新增的步骤：

> 将我在本聊天新增且尚未发布的需求转换步骤改成 revision 最小值为 2，并同步修改真实 schema、校验实现及下游版本声明。再将这个新 Skill 改名为 requirements-convert-v2，检查引用完整性，生成新候选和新试用，废弃旧预览及旧通过证据。

这些修改可以在同一草稿基础上继续，不必每次重新从原插件创建。但已有 Hooks 的原 Skill 不能直接改名；需要保留旧名改正文，或由作者先提供明确 Hook 映射迁移。原必要 contract 仍以实际原插件为保护基线，用户自己的新增规则可以调整，平台继续检查一致性。

### 3.5 如何知道试用确实成功

1. 核对原聊天中的候选摘要、试用目录、项目及当前版本；确认创建隔离试用仅分配副本，尚未运行业务。
2. 按试用入口重新绑定知识和配置，核对精确来源和权限，再启动原执行器。
3. 从原聊天或试用旅程查看每阶段的真实执行会话、产物、检查项和状态。等待用户输入不等于失败；模型说完成不等于检查通过。
4. 至少测试：正常输入、缺产物、坏 schema、上下游版本不符、检查后修改文件、修改 Skill、修改新步骤、原 Hooks 拒绝、状态提交未知及重试对账。
5. AutoBiz 需求转换示例还要检查 PRD 实际保留需求原文和来源，不能只生成格式正确的 JSON。修改契约后必须重新执行生产者，旧输出和回执不能跨契约复用。
6. 检查全部通过后，再判断业务效果是否满意；不满意在原聊天提交反馈，生成新候选和试用，不把旧试用的“通过”标签套给新版本。

旅程关联见[试用旅程投影](../src/main/mods/devtools/creator-trial-journey.ts)；AutoBiz 会话续接的关联与线程身份核对见[业务试用会话关联](../src/main/mods/devtools/creator-business-trial-sessions.ts)。每阶段可有独立物理会话，原聊天是统一创作与验收入口。

### 3.6 保存、更新、导出与开始使用

1. 让创造者为通过验收的精确候选准备交付卡。草稿“保存”只保存创作源码，不等于已经安装新插件。
2. 核对名称、插件版本、资源和权限变化。由用户原生确认安装，或选择 ZIP 导出路径；模型不能自己替用户确认。
3. 已安装同名目标可能进入“仅导出”路径。导出更新 ZIP 后，通过原有插件安装确认更新；这样才能核对实际 UUID、配置和权限，不应声称创建新插件已覆盖旧版本。
4. 安装或导出结果未知时，使用卡片的核对入口，只读确认实际结果。确认未发生后重新准备和确认；冲突或不可读继续保留未知状态，不重放写操作。
5. 安装成功后点击“开始使用”，系统重新核对实际安装摘要并区分聊天扩展、Host 项目或插件项目。缺少配置可就地填写后重新检查，进入对应项目创建或聊天配置。
6. 新建或选择绑定该实际插件版本的项目。旧项目不会因安装新包自动完成任意状态图迁移；不要直接编辑旧项目的 state.json 跳过验收。

原生入口依据：[安装后使用入口](../src/renderer/src/components/customize/InstalledPluginStartUse.tsx)、[使用前来源核对](../src/main/plugins/plugin-start-use.ts)；未知交付对账见[项目交付服务](../src/main/mods/devtools/creator-project-delivery.ts)与[业务创造者服务](../src/main/mods/devtools/creator-business.ts)。

## 四、额度、重启和恢复的真实能力

### 4.1 8 个版本与 4 份草稿

业务草稿额度是每个聊天最多 4 份、每份最多 8 个版本，见[业务草稿保存与恢复提示](../src/main/mods/devtools/creator-business-draft.ts)。达到上限不会自动删除历史、覆盖旧候选或抛弃已安装插件。

单稿 8 版已满且仍有空草稿槽位：先读取完整 files/catalog，重新检查原共享内核，用新草稿 id 和 revision 0 保存；保留业务 Mod ID、Skill 名称、资源与扩展，然后用新返回版本预览。原稿和旧检查候选保留。

4 份槽位都满：仍可读取源码，已有可组装版本可继续预览和原生确认导出。继续编辑需先完整保留源码及未提交变更，由用户指定新创造者聊天或个人源码副本，再重新检查来源并导入。不会自动跨聊天搬迁全部试用、授权与恢复记录，也不能将尚未保存修改描述为已保存。准确恢复提示见 `creator-business-draft.ts:34`。

### 4.2 重启后

重新选择原聊天、工作目录并进入创造者模式，再读取持久草稿、交付和原生试用记录。inspection 和内存预览可能需要重新生成；原生审批不会仅凭历史文字恢复。安装目录或原来源已变更时，先重新检查来源，旧候选不得借相同版本号继续生效。

## 五、阶段调试与插件恢复的适用范围

### 5.1 Host 阶段隔离调试

入口为创作工作区的“阶段隔离调试”。先“刷新阶段调试记录”，选真实阶段进入快照、最新兼容候选及 stage/downstream 范围，再“准备阶段调试方案”，核对后“确认创建隔离调试分支（尚不执行）”，之后逐阶段重新批准。

适用前提：原运行及物理执行已结算，受控文件快照存在，目标候选保持必要 contract 和输入身份。配置、知识和上下文需要冻结绑定；Hooks 与脚本 provider 需要声明兼容恢复政策和新的确认。MCP、外部动作、副作用检查、非配置共享 Mods 等仍可能拒绝，不能删依赖绕过。

恢复范围是受控工作区文件；数据库、网络、整机或 Git 状态不在此协议内。单阶段通过不代表下游或完整插件通过。依据：[阶段调试准入](../src/main/mods/devtools/project-stage-debug-admission.ts)与[阶段调试界面](../src/renderer/src/components/customize/ProjectStageDebugPanel.tsx)。

### 5.2 AutoBiz 插件自有恢复

这条路径使用插件声明的 `devclaw.stage-recovery-adapter.json` 及原 `hooks/rollback_stage.py`，不将 AutoBiz 的 checkpoint 语义写进 Host 调试器。只有实际包携带有效适配器并满足原运行结算条件，才显示可执行恢复能力。

**当前附件中的r13基础版和需求转换版AutoBiz 1.1.0均未携带该恢复适配器声明，不能直接按本节操作。** 原回退脚本保留、状态Mod的`adapter.py`存在，都不代表已提供阶段恢复协议。下面说明平台的条件能力：作者需显式声明并携带恢复适配器，重新生成完整资源锁，完成恢复专项测试后再生成新包；不得向现有已锁定ZIP直接追加未经验证的脚本。

试用中的“插件阶段恢复” → “检查阶段恢复条件” → 选原流程起点和恢复状态 → 明确批准规划脚本 → “准备插件阶段恢复方案” → 核对影响和批准 → “确认创建恢复后的独立试用（尚不运行）”。随后重新核对配置、知识、工具权限和业务检查，再明确运行。

参考恢复适配器保留业务代码，不恢复 Git；存在 `.git`、非空 worktree/并行记录、外部仓库映射等会阻断。应用恢复结果未知时先读取保存记录，只在原生证据满足条件且用户重新批准后运行只读 verify 并接管，不重放 apply。已恢复副本仍需业务验收，不能将“恢复成功”当成“阶段完成”。

当前状态提交适配器面向 Windows 本地 NTFS；应用其他平台可打包不等于该插件适配器已跨平台验证。依据：[插件恢复适配说明](../resources/mods/autobiz-stage-recovery/README.md)、[恢复实现](../resources/mods/autobiz-stage-recovery/adapter.py)和[恢复界面](../src/renderer/src/components/customize/PluginStageRecoveryCard.tsx)。

## 六、人工转换检查列表

自动转换缺少语义时，由作者完成以下内容；可让创造者协助整理和编写，但必须由真实执行验证，而不是只改名称和目录。

- [ ] 留存原插件副本和精确摘要；分离用户配置值、凭据、缓存和运行状态，确认不进入导出包。
- [ ] 列出全部入口：Skill、CLI、工具、Hooks、项目初始化、新建 Feature、状态推进、知识同步和用户输入续接。
- [ ] 找到唯一状态写入器；列出每 Feature 的动态流程、可选边、checkpoint、运行持锁和未知结果读回方式。
- [ ] 将阶段写成明确模块：Skill 入口、输入产物、输出 schema/版本、所需上下文、检查器、依赖和可选条件；不要用文件夹排序推断业务边。
- [ ] 原检查和 Hook 事件、matcher、脚本、动作引用、人工审批保留；Hook 命名迁移必须显式映射，不能保留一个永远不命中的旧 matcher。
- [ ] 配置与知识声明明确用户、机器、工作区和运行生效层次；环境变量替换仍由原实际入口完成，不能用占位知识替代成功。
- [ ] 完整声明资源闭包，包括 Skill 脚本、知识、上下文 provider、子 agent 配置、workflow 与恢复适配器；原资源摘要保护，新增实现使用独立命名空间。
- [ ] 使用现有支持执行器，或由插件编写明确适配器。若制作状态 Mod，必须实现真实读取、准备、校验、唯一写入和对账，不得返回伪 committed。
- [ ] 定义真实失败案例与业务验收样例，覆盖缺文件、坏 schema、旧摘要、上游变化、并发、Hook 拒绝、用户输入续接和状态双文件一致性。
- [ ] 在独立候选和试用目录运行，不原地改安装目录；成功后生成新插件 ZIP，再原生确认安装和使用。

AutoBiz 本轮严格新产物衔接只支持不超过 256 KiB 的普通文件；目录或更大产物需额外受限收集与摘要协议。这个限制不能概括成平台所有业务数据均无大小和类型限制。
