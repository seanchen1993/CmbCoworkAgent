能力是否可用以当前 catalog、静态检查、运行时授权与真实作用域共同决定，不能仅凭此表申请执行权。超出首批范围的现有高级能力可以说明其实际入口和额外条件，但不作为 S1 自动成功承诺。

不支持需求的固定处理：保留当前运行版、已保存草稿及可用组合；返回具体缺口、支持范围和可验证的替代方案。需要用户决定缩小需求时再询问，不擅自删掉功能、关闭别的 Mod、创建同名假能力或改写宿主。能保存的部分明确标为草稿，不能显示“已应用”；未知动作先核对，不能为了修复再次执行。

首批场景：天气与真实工具计数；不依赖 AutoBiz 的文档审查与结果展示。每个场景均覆盖新建、组合、局部修改、必要确认、真实观察、命名保存/套用、撤回和失败恢复。

## 2. 安全切换必须满足的条件

| 环节 | 对候选允许的操作 | 对旧运行版必须保持的性质 |
| --- | --- | --- |
| 保存候选 | 新增不可变源码修订，不覆盖运行中的源码目录 | 原 activation、授权、运行 generation、现有调用与显示 owner 仍有效，旧 SDK 调用可完成。 |
| 编译与启动检查 | 隔离编译/候选启动、受控只读检查、候选失败后真实清理 | 不签发运行权，不退休旧实例，不因草稿状态更新触发来源/作用域失效。 |
| 等待确认与排队 | 记录精确来源、能力和所属轮次；新增权限等待用户确认 | 旧调用、订阅与可用界面继续工作；`queued` 不代表已切换，不修改旧调用捕获的权限范围。 |
| 准备应用 | 原制作轮物理结算，原运行器报告可切换；持有原配置租约并重新验证源码、目标与权限 | 候选检查或 CAS 失败时继续保留旧版；仅因保存/检查/排队不得产生 `MODS_CALL_SCOPE_CHANGED`。 |
| 退休与激活 | 冻结新准入，等待旧物理工作排空，在同一原生事务内替换 | 只有明确进入退休或真实撤权/删除/作用域变更时才使旧 owner/调用失效；退休后失败记为 unknown，不伪称已回滚。 |

正向验证在各环节持有真实旧版 SDK 调用、显示 owner 和来源守卫，核对 generation 与实际结果；同时覆盖后台资源和前台忙碌。反向验证撤权、删除、项目切换和实际退休仍会拒绝旧调用，不能通过放宽守卫来“修复”作用域错误。
