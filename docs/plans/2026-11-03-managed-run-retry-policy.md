# 托管运行失败与重试策略

## 已确认的行为

- 模型调用失败优先处理，不得因为阶段已完成而新建会话推进。
- 即使特性已经满足完成条件，本轮模型错误也先处理；其他执行异常同样结束托管，不记为完成。
- 根据接口状态码和结构化错误分类，认证失败、权限不足、余额不足等不可重试错误直接结束托管；临时模型服务故障在原会话按 5 秒、30 秒、120 秒退避，最多重试 3 次。
- 托管原会话重试与 Runtime 共用已有的同模型 HTTP 判断规则：`408`、`409`、`429`、网关限流 `432/433` 和 `5xx`。没有状态码时复用 `classifyApiError` 对网络、限流、服务异常和空响应的既有识别。此次无需新增错误码，普通模型切换重试保持原规则。
- 阶段切换，或阶段从未完成进入完成、归档、跳过状态，才属于正常推进。
- 首次执行和正常推进不计入重试。同一次托管累计最多执行 5 次模型服务或业务重试，包括人工确认的业务重试；换会话、阶段切换和某次成功不清零。
- 仅实际发起重试时计数，等待、取消和展示决策不计数；发起前保存计数。达到上限后仍需重试时，结束托管并保留原因。
- 用户已确认：历史记录保持可读，缺失累计重试次数字段按 0 处理，新托管从 0 开始。
- 无法识别的模型错误直接停止，日志记录分类结果，不通过猜测文案新增错误码。历史执行结束事件缺失 `retryable` 时沿用有限重试，仍受局部和累计上限约束。
- 新会话重置局部模型重试次数，原会话继续保留局部次数；累计次数始终保留。等待期间不增加任何执行次数，面板分别显示已执行次数和计划重试序号。
- 新建会话的模型选择由调用方从运行快照显式传入。选择 Ultra 时仍保存为该会话模型，托管结束后继续该会话仍使用 Ultra，不自动回退。

## 实施与验证

1. 执行结束事件携带可重试标记，invoke、resume、interrupt 复用现有错误分类逻辑，日志保留该标记。
2. 修正决策优先级与阶段推进条件，集中定义累计上限规则。
3. 运行记录保存累计次数；原会话模型重试、人工确认原会话继续、人工确认新会话重试共用计数入口，复用现有 Feature 执行互斥。
4. 验证结构化 403/434 不重试、临时错误最多 3 次、阶段已完成不循环开会话、累计第 5 次可执行而第 6 次禁止、取消不计数、正常推进与成功不清零、旧记录缺失字段可读。
5. 运行相关单元测试、前后端类型检查和仅改动文件 lint；不进行浏览器或截图验证。
6. 包装异常保留原始 `cause`，复用已有状态码和错误分类；重试前重新读取运行快照，终止时复用已计算的决策，不重复检查 Feature。
7. policy 是局部上限判断的唯一入口，并向执行层返回退避计划。缺少会话或计划、收到无法执行的定时器决策时，明确结束托管，避免只记日志而留下无定时器的运行状态。
8. 错误分类日志使用 `AutoMode` 标签；计数更新仅刷新执行次数，其余事实仍为原决策时快照。重试种类必须显式传入，累计字段继续保留历史记录缺失时的可选语义。
