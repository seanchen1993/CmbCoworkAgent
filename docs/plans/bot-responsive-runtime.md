# Bot 前台响应与后台任务

实验原始记录及后续留档入口：[Bot 主对话与异步任务实验档案](../experiments/bot-dispatch/README.md)。该档案保留成功、失败和中间轮次；下文的迭代结论应结合对应原始记录使用。

## 目标与边界

主 Bot 负责沟通和协调，简单工作可以直接处理；持续执行优先交给独立任务或已关联的 Feature。用户补充要求继续原任务、原目录和原受众。普通对话、Bot 和项目运行共用安全边界注入，不用整轮取消实现正常补充。

保留 Beta 的普通对话、Team、Workflow、技能、审批、记忆范围、群聊归属和结果回传。等待提问时的新消息仍沿用现有跳过/转向行为。执行器只在 App 运行期间工作，重启不自动重做可能产生副作用的操作。

## 实施清单

- [x] 接收：复用 current-run-message-queue，稳定消息标识、持久化接收回执和安全边界消费；正常补充不取消执行。
- [x] 前台：保留短工具，连续重操作受前台预算约束，超预算交接剩余工作；工具已完成的副作用不重放，任务目录不变。
- [x] 调度：任务控制和状态查询不等待工作目录写锁；文件、Git 和浏览器继续按资源归属串行。
- [x] 状态与通知：运行、等待输入/审批/浏览器、后台依赖、异常及业务完成分开；重要交互沿原受众和既有 IM 回执传播。
- [x] 电脑：主对话可切换查看本受众独立任务的浏览器，显示任务来源；只轮询当前可见页面，接管/归还仍操作原任务。
- [x] 界面：紧凑任务列表，关注项优先、完成项折叠；任务顶部集中返回、状态、完成和更多操作；补充消息有接收状态。
- [x] 本地验收：覆盖直接回答、异步交办、运行中连续补充、问题等待、停止、结果回传、群隔离、历史重载及 UI 切换。

## 实施细节

### 前台执行与交接

私聊与真实 IM 主 Bot 用户轮保留短查询和小操作工具，优先通过 `bot_work_create` 交办持续工作；进度查询只读取状态，后续修改通过 `bot_work_send` 继续原任务。独立任务执行与自动汇报轮不套用前台预算；App 多 Bot 群的参与和消息交付规则沿用既有实现。

前台单个物理运行允许最多 4 次普通执行工具调用，从首次执行工具起超过 30 秒后不再准入新的普通执行工具。任务管理、记忆、提问等协调工具不计数。主用户轮不再提供同步 `task`、`workflow`；预算层也保留对恢复的旧调用的异步交接指引，避免主 Bot 等完整子任务。独立任务仍可使用这些执行方式。

预算拒绝发生在工具及工作目录锁之前，工具回执明确说明本次调用未执行。主 Bot 需要提供目标、约束、目录、已有结论、命令回执及剩余工作，并取得新的成功交办回执后才能正常结束。交办失败沿用有限次完成校验，不无限重试，也不伪报成功。长 shell 通过既有沙箱的前后台转交机制保留同一进程，每 10 秒尝试让出，人工审批等待期间不转交。

这是工具边界预算，不是硬性 30 秒响应承诺：正在等待的模型响应或浏览器操作不会被强行中断。用户中途补充在原运行的下一个安全边界被处理。

### 补充、持久化与恢复

普通会话、Bot 主会话、独立任务及运行中的 Feature 会话共用 `steerAgentRun`。按线程和物理运行标识隔离，消费前重新校验归属；Feature 同时校验 Bot、项目会话及原群绑定版本。正常补充不取消工具或子代理；停止仍是独立操作。

修复两处实际 App 测试发现的消息错序问题：队列接收事件只结算草稿，由有序流发布前一条助手快照和补充消息；afterModel 返回新的助手消息对象，使 checkpoint 保存稳定 ID，避免重开后出现重复助手回复。撤回、停止和归属失效的补充有明确失败回执。

复测中发现 SQLite 的延迟读事务在后台连接提交后无法升级写事务，造成结果汇报失败。消息 upsert 改为短 `BEGIN IMMEDIATE` 事务，并在事务内读取计数和旧消息；锁只覆盖消息落盘，不覆盖模型执行或人工等待。

Feature 补充依附实际活跃的根运行。根运行已结束、仅 Team/Workflow 子运行还在工作时，保留现有忙碌保护，不向任意子代理注入，也不另起重叠执行。重启后沿用已有中断/结果待核对状态，不自动重放外部副作用。

### 任务界面与浏览器

任务顶部保留返回、实际状态、当前适用的完成/继续按钮，其余操作收进更多菜单。右侧默认展示 6 条，搜索按需展开，关注项优先、已完成项折叠；普通任务与 Feature 仍在同一任务目录中。

主 Bot 的电脑页可以选择同一受众的独立任务浏览器；当前只挂载一个预览。需要接管时，主对话展示任务来源和原请求的接管卡片，打开/归还仍使用原任务页面及请求代次。独立任务页面固定显示自身浏览器，Feature 的原有项目会话浏览器入口保留。

运行状态复用现有投影，包含等待提问、审批、浏览器、后台依赖和失败；仅“已回复”不等于业务完成。真实 IM 通知复用既有原群/私聊投递链路，本次未修改 IM 网关、接口或数据库结构。

## 验收标准

1. 简单问答不会被强制拆成任务；较长工作不因多次短工具无限占用主对话。
2. 主对话与后台任务可以同时交流。同一任务的补充按接收顺序应用，不重复显示、不丢失、不重做已完成命令。
3. 等待用户、浏览器接管、审批和执行失败能被主 Bot 与原群感知；普通群成员作答权限与本人操作审批边界不变。
4. 工作目录共享时，创建/查询/补充任务仍可立即响应，写入和浏览器控制不会跨任务串扰。
5. 从主对话、右侧任务和普通会话打开同一任务，仍是同一个 thread 和工作目录。

## 沟通角色与原始交办（2026-11-16）

### 提示词与工具分工

App 私聊、招乎私聊和群聊的直接用户轮使用独立的 `BOT_COMMUNICATION_PROMPT`，替换通用编码执行提示词。主 Bot 先判断整个交付过程，非简单工作优先异步交办；日常回答、短改写、单步事实查询、明确的小修改和短 Shell 仍能直接处理，用户明确要求主对话完成时予以尊重。没有增加一次额外的分类模型请求。

去掉主用户轮的通用 `write_todos` 执行规划提示和同步子代理提示，避免模型一边被要求保持沟通，一边被要求自己规划并逐步执行。主 Bot 保留技能目录；复杂技能流程交给执行任务读取和应用，简短设置、定时任务等仍可直接完成。执行器继续使用普通 Runtime 的完整提示词、仓库指令、技能、审批和工具。自动汇报轮保持只读结果、不开执行工具；例行任务、内部协作和 App 多 Bot 群沿用原有执行合同。

设计参考 Grok 0.18 重建源码的 dispatcher 身份、短轮沟通及异步结果收尾，以及 DeepSeek Super-agent 原型的独立 Router、宿主传递原始请求和简短路由说明。没有照搬 Grok 的群内全部直接执行规则，也不要求每个请求都委派。前台预算仍是兜底，并非严格的整轮响应时限；模型生成、已有工具和人工等待不能被表述为固定 30 秒内结束。

### 原始请求与继续处理

- `bot_work_create` 的 `goal` 可省略或仅写简短目标；宿主保存当前原始请求、已经应用的补充消息及所选历史来源，执行器无需依靠主 Bot 重新抄写完整需求。
- `bot_work_send` 复用同一个任务和目录，同样传递本次原始修改要求。正常运行中的补充仍走安全边界注入；模型输入带来源上下文，聊天界面保留简洁的交办文本。
- 来源按 Bot、原 thread、任务归属、受众以及实际注入关系校验。未应用的排队消息、其他群、其他 Bot、自动通知不成为本轮用户指令。旧任务没有新来源标记时沿用原执行指令，不追溯拼接最新聊天。
- 首屏最多 8 条、每条最多 4,000 字符、合计最多 12,000 字符，明确提供分页位置。执行器通过只读 `bot_work_input` 取回剩余文字；长补充携带自己的 `assignmentId`，分页不能误读初次交办。来源查询按捕获的 ID 批量读取，每批最多 64 个，不扫描完整会话。
- 来源明确区分当前请求、已应用修正和历史参考。原始用户约束和后续修正优先于 Bot 的简述；历史用户消息也只是参考，其展示位置不表示发生得更晚。同一请求拆出的多个目标只执行各自交办的部分。
- 任务状态快照增加已有的业务版本号，完成后修改时用真实版本重新打开；冲突继续要求刷新，不猜版本。

当前原文自动传递适用于独立会话任务的创建和补充。Feature 保留原有项目工具和项目上下文，工具消息仍需包含完整的执行要求；本次没有声称已将 Feature 的交办协议也改为原文引用协议。

## 真实案例复测（2026-11-16 晚）

继续使用用户已有的 `deepseek-v4-flash` 配置，只读凭据，在隔离 Electron 配置和虚构工作目录执行。实际模型自主选工具，工具执行、文件写入及通知均走 App Runtime；没有用决策桩代替路由。

| 初始场景 | 实际路线 | 验证结果 |
| --- | --- | --- |
| 日常问答、短文改写、读取单文件事实、修改一个时间 | 主对话直接处理 | 约 2.1–7.5 秒；修改内容实际落盘 |
| 多材料活动方案、自然要求后台推进方案 | 独立任务 | 校验费用、90 分钟流程、交付文件及回传；两次执行期间另问简单问题，主对话均约 1.7 秒回复，后台任务当时仍在执行 |
| 跨文件对账、修复折扣代码 | 独立任务 | 对账合计/差异正确；实际运行代码测试，未仅凭模型陈述判断 |
| 从零实现 CSV 对账工具 | 独立任务 | 实际调用交付的 CLI，复核整数分合计及差异，再运行生成的测试；初次端到端约 205 秒，主 Bot 占用约 52 秒 |
| 用户明确要求主对话完成多材料分析 | 主对话直接处理 | 约 6.3 秒，不创建任务、不写文件 |
| 简单通知但用户明确要求独立任务 | 独立任务 | 约 14 秒完成并回传 |
| 单条耗时命令 | 后台命令 | 初次观察模型主动放后台；补测覆盖运行时自动转后台，原命令完成后收到 `CHECK_OK`、退出码 0 和完成通知 |

两组方案各继续执行“修改 → 查询状态 → 完成后重开修改”：均保持原 work、thread、工作目录，查询状态不重启任务，每次修改结果回传主对话。任务记录 active 与实际运行结束能够区分。

效果判断：12 类初始场景均跑通，但不能据此认为模型已经稳定主动委派。5 个复杂工作中，4 个先尝试前台执行，再由预算阻止下一次操作并促成交接；明确要求后台推进的案例自主交办。初次复杂请求的前台占用约 16–52 秒，模型生成时间及交接说明仍占用前台。新增 `mainSeconds` 单独记录前台占用，`seconds` 记录执行及汇报全部结束，避免混用。样本结果不代表稳定命中率或生产延迟。

复测发现并修正：

- 自动预算转后台复用了“用户发来新消息”的旧命令回执，真实模型因此追问不存在的新消息。改为仅陈述“前台等待结束、同一命令继续后台执行、完成后自动通知”；新构建实测约 17.8 秒收到最终结果，不再出现该误导。底层 23 项预算/进程交接回归通过，包含原生进程持续执行、停止及完成回执。
- 多案例测试重复进入已打开的 Bots 工作区，第二次截图误等待已隐藏的模式入口。测试改为检查当前工作区后再切换。首次报错发生在业务断言全部通过后的截图步骤，不是任务执行失败。修正后两组方案、6 个后续操作和后台命令共 9 轮定向补测通过，任务页截图正常；后台执行时插入简单问题分别在 1.9 秒、1.3 秒内回复。
- 后台命令测试原先只等主轮结束。现根据实际后台线程和通知回执继续等待完成，并识别自动转后台，避免把模型没有显式传 `run_in_background` 误记成前台执行。

同时重跑：实际 App 的普通会话、Team、Workflow、Bot 主会话和独立任务连续补充两条消息（实时、落盘、重载一致，28 次模型夹具调用）；群私聊隔离、草稿编辑/删除/重试、指定目录附件与审批等待（16 次模型夹具调用）；浏览器 50 次打开/卸载及原任务接管；202 项队列、引导与并发定向测试均通过。渠道仍为本地模拟，没有连接真实招乎。

## 沟通提示词分离后的复测

实际 Electron + `deepseek-v4-flash`，仍用上述虚构案例、隔离配置和真实工具执行；主 Bot 没有预置“必须委派”的用户角色。除明确后台、明确主对话和明确任务三个对照组外，用户交办没有要求创建独立任务。
