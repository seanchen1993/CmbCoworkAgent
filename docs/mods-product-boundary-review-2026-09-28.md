# Mods 产品定位与 Claude 对照复核

> 本文记录分析阶段的状态。后续落实情况见 [本轮交付记录](mods-claw-delivery-2026-09-28.md) 和 [操作指南](mods-claw-hands-on-2026-09-28.md)。

日期：2026-09-28。按用户“先分析”的要求，暂停继续添加聊天连接实现。本报告区分官方事实、已有实现和产品建议，不把草稿列为完成。

## 结论

用户把 DIY Claw 理解为“安装/选择自己的能力，在同一个对话里按自己的方式工作”，方向合理。
把这进一步理解为“Claude Mods 已经自带任意组件拖拽、步骤换序、发布助理及聊天选择的一整套页面”，现有证据不支持。

本工程的插件运行与宿主边界有复用价值；固定步骤流程也有明确业务用途。但是把两者合称为“Mods 已完成/与 Claude 已对齐”不准确。
目前四类流程节点、流程库、业务运行账本和 Autobiz 阶段提交，是本产品设计，并非复刻已证实的 Claude 官方流程编辑器。

## 当前设计需要修正的地方

### 1. 固定工作流与持续行为增强没有分清

“任何编码任务结束前自动评审”属于对既有 Agent 的行为增强。
“严格执行分析、实现、评审、测试四步”属于一个显式业务工作流。二者可以共存，但不能让用户以为配置其中一个就得到了另一个。

### 2. 选择了 Mods，不等于流程执行了该插件的能力

`FlowDefinition.plugin` 当前绑定一个插件；`prepareFlowScope` 校验该插件的已授权快照并维持运行身份。
四类步骤由宿主执行，Agent 列表来自 `loadAgentProfilesAsync`。没有通用的“插件声明组件 → 组件出现在库中 → 节点调用对应插件能力”契约。

授权与运行身份有真实安全作用，应保留边界；但让用户为了运行普通流程先安装一个无关查询插件，作为长期产品使用方式不合理。
后续应明确区分宿主内置步骤的权限与插件能力的依赖/授权，而不是移除所有检查，或把一个插件授权视为所有组件的授权。

### 3. 聊天入口不能把每句话都当成重新执行工作流

“开发订单导出”可以是新任务；“刚才为什么失败”“只修第二个问题”可能是追问或修改当前任务。
刚开始编写的聊天连接草稿主要做的是把普通文本作为新流程任务，它尚不能代表“定制了一个能够连续对话的 Claw”。不应在未解决语义区分前将其交付为完整能力。

### 4. 配置方案尚不是可分享的插件包

当前保存的是宿主流程定义，不会自动导出成 Claude 或本工程通用插件包。流程、角色、模型、插件配置和依赖需要独立的版本/作用域模型。

## 建议的产品方向

先明确三个层次，名称仅为建议：

1. **Mods 能力**：开发者提供 Hook、命令、工具、角色、面板；保留权限、取消、重载与支持范围。
2. **我的 Claw 配置方案**：用户选择哪些能力生效，配置参数，指定作用于哪个项目/会话；每次普通对话依然由原有 Agent 处理，匹配的能力参与执行。
3. **显式工作流**：需要固定顺序时，选择步骤并明确启动；成为配置方案可选的一项能力，不强迫每次问答都跑全流程。

Autobiz 示例的目标使用效果：用户选择“Autobiz 研发助手”，配置规范、评审、测试和阶段推进策略，随后在聊天中提出业务任务。普通追问保持普通对话；任务准备结束时执行已配置检查；用户明确要求标准交付流程时再执行固定步骤。阶段推进单独受真实验收和人工确认约束。

这是建议目标，不是本工程或 Claude 当前已全部具备的现成产品能力。

## 后续实现前的验收边界

- 同一输入在切换配置后，能通过实际调用、检查记录和策略差异证明不同，而非仅输出不同文案。
- 所有行为扩展清楚说明触发条件、适用范围、依赖和权限；不以安装即授权。
- “启动新任务”“追问结果”“补充要求”“取消”“批准”有确定路由，追问不意外触发写代码或推进阶段。
- 自定义组件必须显式声明输入输出和可调用入口；有稳定能力标识，失效或撤权时不得换成别的实现继续执行。
- 配置绑定版本与项目/会话；修改只影响约定的下一次执行，不能在运行中悄悄更换授权对象。
- 验证普通聊天、传统 Plugin、Harness 不受新增选择器或订阅的额外影响。
