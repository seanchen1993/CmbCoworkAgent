# 周期任务遇到一次错误后继续：实施方案

上一阶段退出适配已验证，见 mods-session-end-stage-2026-10-04.md。本阶段只解决一个已确认的使用差距：一次查询失败不应让后续定期检查永久消失。

## 原版依据

[官方 API 指南](https://code.claude.com/docs/en/plugins/mods/api)说明周期回调错误写入调试记录，下一周期继续。固定并校验的 Claude Code 2.1.288 实际 plugin test 两项通过：第一次 every 回调抛错，第二次成功，明确 cancel 后不再运行；after 抛错只运行一次。证据为 output/claude-code-2.1.288-alignment-analysis-2026-10-03/timer-error-probe-result.json 和 timer-error-probe.log。时钟由原测试工具 mock.clock 推进，只证明回调/取消语义，不证明真实等待或回调预算。

普通回调处于事件之外，不强加注册 Hook 的 10 秒自身预算。仍保留现有 120 秒宿主期限、VM CPU/内存边界和每组件最多八个并行回调。外围 clock.every 事件继续按注册 Hook 规则计时。

## 改动边界

1. 在 FunctionSession.openTimer 的真实 guest.invoke 周围捕获每周期回调错误。只有 every、VM 未销毁、真实资源归属及原宿主身份复核通过，才记录错误并返回，让原调度循环继续。不能按组件提供的错误文字或错误码判断权限是否有效。
2. 原周期调度错误、周期被拒绝、八个并行回调入口上限、外围新调用或宿主守卫失败、资源取消、会话关闭、权限撤销、组合或执行身份变化、共同退出期限过期仍走原关闭路径。开始回调前的原生守卫不放在普通错误恢复范围内。回调里普通 SDK 业务错误属于本次失败，可以在下一周期重新检查；不声称能从组件异常文本辨别所有底层传输故障。VM 暂时达到 32 帧时，本周期拒绝入场，下周期可再次尝试，不能冒称它和八回调入口上限是同一位置。
3. after 仍为一次任务，出错后关闭。cancel 不重复执行回调；当前已进入的回调不会因此被重放。资源句柄、计数、实际后台占用与 finally 保留原实现，不提前释放实际未结束工作。
4. 普通回调调试记录固定 MODS_TIMER_FAILED，不采用组件可构造的异常码或文字，不记录用户文本、模型凭据。调试记录本身同步抛错或异步拒绝均不能中止周期，也不能制造后台未处理拒绝。
5. 本阶段不增加自动模型调用、发送新聊天或上传步骤，用户沿用 $.clock.every 和 cancel，不需要学习新的控制方式。更新宿主版本并按原批准流程处理已有组件。

## 验证

先补真实 QuickJS 集成回归并在修复前确认普通每周期错误用例失败。覆盖首次同步错误、异步错误、多周期恢复、cancel、一次回调、撤权、VM 销毁、会话关闭、周期拒绝、容量与退出期限，确认普通聊天仍可用、计数与残留活动归零。

真实 Electron 通过安装、批准、任务入口和 utility process 运行“第一次失败、之后写日志、取消后日志不再增加”，保留原进程、HTTP、后台任务等邻近场景。检查真实错误是否进入调试记录，不用测试替身代替生产回调通道。类型和本阶段 lint、冻结受控广域回归、有限吞吐样本再完成两位独立实现复审。
