# 需求：招乎侧交互式决定（工具审批与结构化补充输入）

> 期次：第二期
> 来源：从[远程接入分阶段方案](./chatx-im-remote-control-staged-plan.md) §2.11、§2.12 抽出独立成文
> 涉及方：桌面客户端、Java 网关、双边契约
> 说明：本文是需求与契约要求，详细设计由实施方完成。

## 1. 背景

Agent 执行过程中有两类必须由人给出决定的场景：

1. **工具调用审批**。写文件、执行 shell、提交代码等操作在执行前需要用户批准。
2. **结构化补充输入**（`request_user_input`）。Agent 需要用户在若干选项间选择，或补充一段信息。

当前两者都只能在桌面完成。带来两个问题：

- 用户在招乎侧发起的任务，遇到这两类场景就停住，必须回到桌面，纯移动场景走不通；
- 第三期允许从招乎驱动 Coordinator 与 Workflow 后问题会放大，这类会话通常带多道审批门，每一道都要回桌面。

本需求让这两类决定可以在招乎侧给出。

## 2. 现有机制

两者在主进程里的形状一致，客户端侧接入成本很低：

| | 注册表 | 决议入口 |
| --- | --- | --- |
| 审批 | `pendingApprovals`（`src/main/agent/runtime.ts:342`） | 直接 `resolve(decision)` |
| 补充输入 | `pendingUserInputs`（`src/main/services/user-input.ts:28`） | `submitUserInputResponse(response)` |

两个 Map 都在主进程，不需要经过渲染进程，也不需要新的 IPC 通路。都是内存态，进程重启即失效。

现有渲染进程通路（`ipcMain.on("sandbox:approvalDecision")`）必须保留。招乎侧决议要做成**并行的第二条决议路径**，复用同一套校验，不得替换，也不得另写一份校验逻辑。桌面行为基线测试已锁定这条通路的存在。

## 3. 两个交付层

同一能力做两层，卡片是增强而非前提。

### 3.1 层一：文本（不依赖契约变更，可先行交付）

**审批**

推送时附一次性短码：

```
【支付网关改造 / 对账单导出】需要批准
写入文件 src/billing/export.ts

/批准 7F3A   或   /拒绝 7F3A
```

**补充输入**

提问以编号列表推送：

```
【支付网关改造 / 对账单导出】需要你确认
导出格式用哪种？

1. CSV（兼容性最好）
2. Excel（带格式）
3. JSON（便于程序读取）

回复 /回答 <编号>，或 /回答 <编号> <补充说明>
```

短码与编号上下文随请求过期，进程重启后失效。

**该层是长期的降级形态，实现卡片后不得移除。**

### 3.2 层二：卡片（需要网关配合）

- **审批改用招乎审批 2.0**（`/robot-service/single-message/send-audit-beta`）。同意与拒绝按钮直接产生上行回执（`updateAudit` 事件）。
- **补充输入使用自定义卡片表单组件**（列表选择器、输入框、提交按钮），回执走 `CustomCard` 事件。
- 决定给出后按平台 msgId 更新原卡片，把"待处理"改为"已处理"。outbox 已持久化 `platformReplyId`，可直接使用。

卡片相对短码的收益不只是体验：**按钮点击在协议层是独立事件类型，与普通文本消息结构上不同**，因此"自然语言误触发决定"这一风险从根本上消失，不必依赖短码去防。

## 4. 审批分级规则

卡片只改变决定的采集方式，不改变可批准范围。

| 操作类别 | 招乎可批 | 说明 |
| --- | --- | --- |
| 工作区内 `write_file` / `edit_file` | 是 | 必须展示目标文件路径（相对工作区） |
| `execute`（shell） | 是 | 命令原文完整展示，不截断 |
| `git_commit` / `git_push` | 否 | 见下方结构性限制 |
| `save_code_exec_tool` | 否 | 等于永久扩权 |
| 工作区外的任何写入 | 否 | 与现有沙箱边界一致 |

**结构性限制。** `ApprovalDecision` 的 `commitResult` / `pushResult` 按其定义是"渲染进程执行完提交或推送之后回填的结果"（`src/main/types.ts` 中 `ApprovalDecision`）。这两类审批的批准动作本身包含由桌面实际执行提交，远程返回 `{ type: "approve" }` 而不带这些字段，会产生"已批准但提交从未发生"的状态。

要放开必须先把 commit/push 的执行从渲染进程搬到主进程，**不在本需求范围内**。

不可远程批准的类别推送到招乎时只通知"需要在桌面确认"，不附短码，卡片也不带可点击的批准按钮。

**只允许一次性批准。** `ApprovalDecisionType` 有 `approve` / `approve_session` / `approve_permanent`，招乎侧只开放 `approve` 与 `reject`，不开放会话级与永久豁免。同时必须尊重每个请求自带的 `allowed_approval_types`。

## 5. 结构化补充输入

`UserInputQuestion { header, question, options: [{ label, description }] }` 与卡片表单组件基本一一对应，可直接映射。

支持两种回答形式：选中某个选项，或在选项之外补充自定义内容。答案进入 Agent 的方式必须与桌面回答完全一致。

**关于开放理由的更正。** 本需求的早期版本把 `request_user_input` 排除在远程之外，理由是"结构化补充输入是让 Agent 获得内容，与批准一个已知操作不是一回事"。该理由不成立：用户本就能从招乎发任意文本驱动会话，回答一个提问不新增任何能力通道。真实障碍只是纯文本无法呈现结构化表单，而这一层已由本需求解决。

## 6. 契约要求（网关侧）

### 6.1 归一化必须发生在网关

卡片回执是**第一件带渠道特有结构的上行数据**。此前判定"客户端不需要渠道抽象层"的依据，正是客户端拿到的事件已被网关归一化为纯文本。

因此要求：网关把 `updateAudit` 与 `CustomCard` 回执转换成契约中的结构化决定事件，客户端拿到的仍是渠道中立载荷。**不得让卡片回执的原始 JSON 透传到客户端。**

### 6.2 事件形态草案

在 `RemoteImEventV1` 之外扩出决定事件，或在其 `message` 上扩出新的 type。字段命名可调整，语义不可省：

```ts
interface RemoteImDecisionEventV1 {
  schemaVersion: 1
  eventId: string
  platformMessageId: string
  principalId: string
  conversationKey: string
  conversationSeq: number
  deviceEpoch: number
  occurredAt: string
  lease: { id: string; expiresAt: string }
  /** 客户端下发卡片时生成的不透明引用，网关原样回传，单次有效 */
  requestRef: string
  decision:
    | { kind: "approval"; verdict: "approve" | "reject" }
    | {
        kind: "user_input"
        answers: Array<{ questionId: string; optionLabel?: string; text?: string }>
      }
}
```

`requestRef` 由客户端在发送卡片时生成并携带，网关只负责原样回传，不需要理解其含义。这样网关不持有任何本地审批或会话信息，与既有的"网关不保存本地目标信息"约束一致。

需要与网关团队确认：招乎审批 2.0 与自定义卡片是否支持一个可往返的自定义标识；若不支持，则由网关维护 `平台 msgId ↔ requestRef` 的短期映射，映射随请求过期。

### 6.3 决定事件必须走控制通道，不进执行队列

**这是最容易做错且后果最严重的一条。**

审批决定必须在入站临界区内处理，与控制指令同级，**不得进入会话执行队列**。原因：执行队列此刻正被那个等待审批的 Turn 占用，如果决定事件排在它后面，就是死锁，审批永远等不到答案。

### 6.4 幂等与异常

- **重复回执**：用户重复点击按钮、平台重投，都必须按首次决定处理，后续回执为空操作并给出友好回复，不产生第二次决定；
- **过期请求**：决定到达时该请求已因 TTL 取消或运行已结束，回复"该请求已过期"，不做任何决议；
- **载荷解析**：API 参考明确指出各类回执的 `msgContent` 常以 JSON 字符串而非 JSON 对象返回。网关侧解析必须做二次解析与异常保护，畸形载荷按无效决定丢弃并记录，不得抛给客户端；
- **越权决定**：越过 `allowed_approval_types` 或指向不可远程批准类别的决定，一律拒绝并说明原因。

## 7. 降级与版本

自定义卡片要求招乎 APP/PC V6.6+，Markdown 容器 V6.14+，AI 内容 V6.15+。

需要先摸清目标用户的客户端版本分布。能力不足时自动退回层一的文本形态，**不得报错，不得让用户卡住**。

单聊卡片 `content` 上限 15,000 字符，超出需截断并提示到桌面查看完整内容。

## 8. 安全约束

1. 决定只能通过卡片按钮或带一次性短码的显式指令给出，自然语言永不构成决定。用户发"同意""可以"按普通消息处理。
2. 短码随机生成、单次有效、随请求过期，不得可从 requestId 推算。
3. 远程决定能力是独立的全局开关，默认关闭。关闭时行为与现状完全一致。
4. 该开关不并入会话的"接入招乎"开关：接入决定哪些会话暴露，远程决定的是用户愿不愿意在手机上做授权判断，属于另一个轴。
5. 每一次远程决定都记录来源，并在桌面对应会话中可见。
6. 审批请求的展示内容需要脱敏：路径用相对工作区形式，不含绝对路径、环境变量与凭据。

## 9. 非目标

- 不放开 `git_commit` / `git_push` / `save_code_exec_tool` / 越界写入的远程批准；
- 不放开 `approve_session` / `approve_permanent`；
- 不把自然语言解析为决定；
- 不让卡片回执原始 JSON 透传到客户端；
- 不实现群卡片、千人千面、图表组件与 AI 流式卡片；
- 不改变审批与补充输入在桌面侧的现有交互；
- 不移除文本降级形态。

## 10. 验收

**文本层**

1. 不具备卡片能力的客户端上，审批与补充输入均可通过 `/批准`、`/拒绝`、`/回答` 完成。
2. 短码单次有效：同一短码第二次使用被拒绝；短码不可从 requestId 推算。
3. 并存多个请求时，短码各自指向正确对象，不会决议错对象。
4. 自然语言"同意""批准"仍按普通消息处理，不产生决定。
5. `/回答` 支持选项与自定义内容两种形式；答案进入 Agent 的方式与桌面回答一致。

**卡片层**

6. 卡片按钮与表单可完成同样的决定；实现卡片后文本指令仍然有效。
7. 客户端能力不足时自动退回文本形态，不产生错误提示。
8. 决定给出后原卡片被更新为已处理状态。
9. 客户端收到的决定事件是契约中的结构化类型，不含任何渠道特有的原始 JSON。

**分级与安全**

10. 不可远程批准的操作，其推送不附短码、卡片不含批准按钮，且无法用任何指令决议。
11. 招乎侧只能给出 `approve` / `reject`；越过 `allowed_approval_types` 的决定被拒绝。
12. 全局开关关闭时，行为与现状完全一致，招乎侧不出现短码与卡片。
13. 远程决定在桌面对应会话中可见，且标明来源为远程。
14. 审批展示内容不含绝对路径、环境变量与凭据。

**并发与异常**

15. 审批决定不排在执行队列之后：一个 Turn 正等待审批时，决定事件仍能及时到达并解除等待。
16. 重复点击或平台重投同一回执，只产生一次决定。
17. 请求已因 TTL 取消或运行已结束时，决定被拒绝并提示已过期，不做任何决议。
18. 畸形回执被网关按无效决定丢弃并记录，不抛给客户端。
19. 渲染进程原有的审批决议通路保留，桌面行为基线测试全部通过。

## 11. 需要外部确认的事项

1. 招乎审批 2.0 与自定义卡片是否支持一个可往返的自定义标识，用于承载 `requestRef`；若不支持，改由网关维护短期映射。
2. `updateAudit` 与 `CustomCard` 回执的完整字段契约、是否可能重复投递、是否保证顺序。
3. 卡片更新接口的调用频率限制与失败语义。
4. 目标用户的招乎客户端版本分布，用于决定卡片层的覆盖范围与降级比例。
5. 审批 2.0 的卡片状态机（原文提及状态 0～6）与本需求的请求状态如何对应。
