# 项目完成检查规则

在项目任务中打开「自定义 → Function Mods → 对应插件 → 完成检查规则」。先解锁管理设置并明确开启 Mods；解锁本身不会启用执行。规则按项目和插件保存，重启继续生效，插件不能覆盖应用保存的规则。

## 配置与执行

- 关闭：移除此插件的完成门禁；其他插件分别受自己的规则控制。
- 仅报告：记录检查结果，不因该规则阻止完成。
- 阻止完成：所选检查失败、证据过期或超时，会阻止正常完成。
- 自动修复并复检：在原 Agent 完成循环内申请修复，重新捕获文件证据并执行检查。修复次数同时受应用规则和原完成循环限制。

范围可选当前文件、当前 diff、Feature 或整个项目。当前文件须填写相对路径；Feature 须填写 ID。检查可选代码评审、单元测试、E2E 和 Autobiz validator。代码评审需要插件处理器；项目测试使用现有 npm scripts 或已安装的受支持 runner，不自动下载依赖。缺少能力会明确失败。

最大修复次数、最长时间和模型输入加输出总预算是共同约束。时间预算使用单调时钟；墙钟校时不延长运行。取消、撤权、关闭和替换 runtime 会撤销原运行的执行权限。证据绑定任务、轮次、运行、插件摘要、runtime generation、配置、diff、需求和文件指纹，旧 PASS 不会在修改后沿用。

## 可选的 Autobiz 阶段推进

这是应用扩展，不是 Claude Mods 的同名 API。选择「阻止完成」或「自动修复并复检」、勾选 Autobiz validator 后，会出现「自动推进阶段起点」。留空只检查；填写时必须指定 Feature ID。起点示例为 `requirements_eval_in_progress`，实际合法值由该 Feature 的 workflow 决定。

宿主调用固定版本 workflow compiler 推导阶段终点，不接受插件指定推进目标。只有所选检查、真实上游 validator 和证据复核都通过，才在原 FunctionSession、runtime authority、run lease 和原生文件权限下申请推进；原审批拒绝会阻止写入。阶段已到终点时重复完成只复检该阶段，不继续进入下一阶段。关闭、仅报告或取消 validator 会移除自动推进设置。

当前适配依赖 Windows 本机 Git 仓库 `C:\ai\autobiz_kanban` 的固定提交 `8db1ec937d6ed3d271cb9dc540310d6633c91e70`，以及 Python。宿主通过 Git archive 读取固定对象，不执行该仓库未提交的 Python 修改。用户最初给出的 `C:\ai\autobiz\_kanban` 在当前环境不存在；不会静默创建或改写它。缺少依赖会报告失败，普通 Mods 和未启用该检查的任务不受影响。

## 查看证据与恢复

任务底部的「完成检查证据」显示采集、检查、修复、validator 和 checkpoint 推进记录，以及失败原因和下一步。采集完成只是步骤结束，不是测试或业务通过。文件改变后重新检查；进程重启后中断的步骤保留，不能恢复成 PASS。

checkpoint 使用宿主提交日志和状态文件竞争检查。提交结果未知时应先核对操作编号、宿主日志、state.json 与 STATE.md，不直接重放推进。当前不承诺对整个工作区所有文件建立原子事务，也尚未提供未知提交的完整自动恢复界面。

现有自动阶段测试使用真实固定 compiler/validator、真实 Electron 和原生权限，但模型及业务产物是契约夹具，不构成真实业务验收。真实项目的代码、测试、业务验收产物仍需分别验证。安装包由 GitHub Actions 构建。
