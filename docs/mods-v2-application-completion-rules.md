# 项目完成检查规则

在普通本地项目会话中打开「自定义 → Function Mods → 对应插件 → 完成检查规则」。当前没有管理密码；需要明确开启 Mods 并完成当前项目的插件授权。规则按项目和插件保存，重启继续生效，插件不能覆盖应用保存的规则。完整组合与使用流程见 [使用与迁移指南](mods-compatibility-impact-and-plugin-migration-2026-09-29.md)。

## 配置与执行

- 关闭：移除此插件的完成门禁；其他插件分别受自己的规则控制。
- 仅报告：记录检查结果，不因该规则阻止完成。
- 阻止完成：所选检查失败、证据过期或超时，会阻止正常完成。
- 自动修复并复检：在原 Agent 完成循环内申请修复，重新捕获文件证据并执行检查。修复次数同时受应用规则和原完成循环限制。

初次配置可选择「只给检查报告」或「修复后再完成」模板，再点击「保存项目规则」。前者对本次代码改动做评审，后者做评审和单元测试，并在失败时申请修复。模板不会自动提高时间或模型预算，也不自动开启阶段推进。

范围可选指定文件或目录、本次代码改动、指定功能（Feature）或整个项目。指定文件须填写项目相对路径；Feature 须填写 ID；无关输入会隐藏。检查可选代码评审、单元测试、E2E 和 Autobiz 业务验收。代码评审需要插件处理器；项目测试使用现有 npm scripts 或已安装的受支持 runner，不自动下载依赖。缺少能力会明确失败。

应用保存规则后，`/kanban` 显示规则来源和只读摘要，不再提供会保存失败的编辑控件。`/kanban-mode` 和 `/kanban-target` 也会提示回到应用设置修改。请统一在应用设置修改，并在看板点击「刷新真实状态」。仅使用旧插件配置且尚未保存应用规则时，看板和命令仍支持编辑。已安装的旧示例需更新并重新授权，才能获得这些提示。

最大修复次数、最长时间和模型输入加输出总预算是共同约束。时间预算使用单调时钟；墙钟校时不延长运行。取消、撤权、关闭和替换 runtime 会撤销原运行的执行权限。证据绑定任务、轮次、运行、插件摘要、runtime generation、配置、diff、需求和文件指纹，旧 PASS 不会在修改后沿用。

## 可选的 Autobiz 阶段推进

这是应用扩展，不是 Claude Mods 的同名 API。选择「阻止完成」或「自动修复并复检」、勾选 Autobiz validator 后，会出现「自动推进阶段起点」。留空只检查；填写时必须指定 Feature ID。起点示例为 `requirements_eval_in_progress`，实际合法值由该 Feature 的 workflow 决定。

宿主调用固定版本 workflow compiler 推导阶段终点，不接受插件指定推进目标。只有所选检查、真实上游 validator 和证据复核都通过，才在原 FunctionSession、runtime authority、run lease 和原生文件权限下申请推进；原审批拒绝会阻止写入。阶段已到终点时重复完成只复检该阶段，不继续进入下一阶段。关闭、仅报告或取消 validator 会移除自动推进设置。

当前适配需要 Git、Python 3 和 Autobiz 源码中的固定提交 `8db1ec937d6ed3d271cb9dc540310d6633c91e70`。默认源码目录为 `C:\ai\autobiz_kanban`；其他机器可设置环境变量 `CMB_AUTOBIZ_SOURCE` 为实际目录后重启应用，Python 路径可用 `CMB_AUTOBIZ_PYTHON` 指定。宿主通过 Git archive 读取固定对象，不执行源码工作树中未提交的修改。

首次展开规则时才读取配置。普通规则不会启动 Git/Python 探测；选择启用的 Autobiz 检查时自动预检，也可手动点击「检查 Autobiz 环境」。尚未检查、检查中或检查失败时，不能保存启用的 Autobiz 规则，但可以取消该检查或关闭规则。依赖缺少时给出修复提示，普通代码检查仍可保存和运行；修复依赖后再次点击「检查 Autobiz 环境」。「重新检查配置」只重读规则，不重新探测环境。这个预检不代表项目已通过验收，也不会安装软件、授权执行或代替运行时的权限、产物与磁盘检查。自动推进仍仅支持 Windows 本地固定 NTFS 磁盘。

## 查看证据与恢复

任务底部的「完成检查证据」在折叠状态先显示结果摘要、修复请求轮数或下一步；展开后查看采集、检查、修复、validator 和 checkpoint 推进记录。单项检查或插件意见不会被摘要写成整轮通过，重复阶段确认会说明「未重复写入」。采集完成只是步骤结束，不是测试或业务通过。文件改变后重新检查；进程重启后中断的步骤保留，不能恢复成 PASS。

checkpoint 使用宿主提交日志和状态文件竞争检查。带操作编号的推进记录提供「核对 checkpoint 恢复证据」按钮，通过 SQLite 只读日志与有界文件读取，对比 state.json、STATE.md 的提交前、预期写入和当前 SHA-256。界面区分两文件未变、符合预期、部分写入、外部修改及不可读，并给出下一步。核对不改变日志、状态文件或业务结论；关闭模块会拒绝核对，切换任务或失效后的迟到结果不会恢复界面。

提交结果未知时先核对操作编号和文件，保留现场，不直接重放推进。即使当前内容符合预期，也不能据此重新获得 PASS。当前不承诺整个工作区原子事务，也不提供未知提交的自动回滚或自动重放；完成业务修复后仍须重新执行完整检查。

自动阶段回归测试中的模型及业务产物是契约夹具；另已完成[真实模型订单导出演示](mods-v2-real-business-demo.md)，包含原 Agent 修复、真实测试、固定 validator 与项目外独立业务断言。单个示例通过不替代其他项目的业务验收。安装包由 GitHub Actions 构建。
