## 先分清两个入口

| 入口                   | 在这里做什么                                          | 做完以后怎么使用                                         |
| ---------------------- | ----------------------------------------------------- | -------------------------------------------------------- |
| 自定义 → Function Mods | 安装你写的扩展包，查看能力、开启和授权                | 命令在聊天里调用；Hook 在相应事件发生时执行              |
| 自定义 → DIY 流程      | 组合 Agent 任务、真实检查、人工确认、Autobiz 阶段推进 | 保存后在本页点击“运行已保存版本”，查看步骤结果和人工确认 |

当前“上传自己的 Mods”和“新增自定义流程节点”不是同一个能力：上传的命令、Hook、面板不会自动出现在步骤组件库。流程的“所属 Mods”用于校验运行授权，不表示这个包的命令会被当作流程步骤调用。

## 第一次体验：上传一个自己的 Mods

1. 使用项目要求的 Node 版本，在上述开发目录执行 `npm run dev`。
2. 打开一个带项目目录的**普通本地会话**。先在设置里配置可用模型；后续 Agent 步骤需要它。
3. 打开“自定义 → Function Mods”，在“添加能力”里展开“如何上传自己的 Mods？”。
4. 点击“下载最小 Mods 模板”，保存 `my-claw.zip`。这是能实际安装、执行的完整包。
5. 点击“上传 Mods（ZIP）”，选择刚下载的 ZIP。也可解压后通过“从文件夹安装”选择插件根目录。
6. 开启“启用 Mods 功能（应用级）”和“启用项目 Mods”，在 `my-claw` 卡片核对能力后点击“授权以上能力”。安装不等于授权或执行。
7. 回到该项目聊天，发送 `/my-claw-info`。预期返回“我的 Claw 已就绪，当前项目：…”及实际项目路径。

模板目录如下；打包时保留相对路径，最稳妥的方式是让 `plugin.json` 位于 ZIP 根目录：

```text
my-claw/
├─ plugin.json
├─ README.md
└─ hooks/
   ├─ hooks.json
   └─ register.ts
```

`plugin.json` 是名称与版本；`hooks.json` 声明模块；`register.ts` 写你的命令和事件行为。
可以先把 `register.ts` 返回的“我的 Claw 已就绪”改为“团队研发助手已就绪”，重新安装并授权新摘要，再次执行命令观察差异。
这一步验证自己的代码确实被加载。单个 `.ts` / `.js` 文件不能直接当完整包上传。

模板仅查询项目路径，不修改文件、不调用模型；它也不会自动执行下面的代码检视流程。

继续编写自己的命令、状态或 Agent 行为时，可参考 [作者类型与本机校验工具](mods-v6-authoring-tooling-2026-09-28.md) 和 [代码评审 Mods 示例](../examples/mods-review-agent/README.md)。这些是扩展代码的开发资料；日常调整流程顺序、角色和模型直接在页面完成。

## 第二步：DIY 一条代码检视流程

1. 保持选中刚才的项目会话，进入“自定义 → DIY 流程”。
2. 点击“新建代码检视流程”。这会创建“检视代码 → 确认检视结果”两步，不要求 Autobiz Feature 或测试脚本。
3. 将“所属 Mods”选为已授权的 `my-claw`。将流程名称改为“团队发布前检视”。
4. 填写“任务目标”，例如：

   > 检视当前项目的未提交改动，重点检查权限、失败处理和兼容性。列出有代码依据的问题及文件位置。只检视，不修改文件，不编造测试结果。

5. 点击“检视代码”步骤卡片。修改步骤目标，选择已有的只读评审角色及可用模型，或使用会话默认值。
6. 点击“确认检视结果”卡片，修改最后需要人确认的说明。
7. 点击顶部“保存流程”，再点击“运行已保存版本”。运行中的任务使用保存时的版本，之后修改草稿不会改变这次执行。
8. 页面滚动到“运行与历史”。查看步骤结果；出现“人工成果确认”时，阅读结果再点“同意并继续”或“拒绝并停止”。

模板中的“只检视”是任务指令。如果需要强制只读，请选择确实配置了只读工具权限的 Agent 角色；不要把提示词当作权限隔离。

## 第三步：加入你自己的组合

组件区有四个明确入口，点击添加后会直接展开该步骤：

| 组件             | 可以改什么                           | 实际效果                                           |
| ---------------- | ------------------------------------ | -------------------------------------------------- |
| Agent 任务       | 目标、角色、模型、顺序、条件与路线   | 单独调用所选角色和模型完成这一步                   |
| 真实检查         | 单测、E2E 等检查类型                 | 使用项目脚本或对应验收器执行；需要项目具备相应环境 |
| 人工确认         | 确认说明、位置                       | 停下来等待你的决定                                 |
| Autobiz 阶段推进 | 关联真实 Feature，放到最后启用的位置 | 校验产物并推进一个合法阶段，失败则停止             |

用每张卡片上的上下箭头调整顺序，用“启用步骤”决定是否参与执行。点击卡片只展开当前步骤，复杂配置收在“条件、成功路线与失败回退”里。

例如可以做成：

```text
编码与修复 → 独立代码评审 → 单元测试 → 人工确认
     ↑             │             │
     └──── 业务不通过时回退 ───────┘
```

具体操作：新增一个 Agent 步骤并命名“编码与修复”，将它移到评审前；新增“真实检查”选择单元测试，将它移到人工确认前。在评审和单测步骤的高级配置中，将“业务不通过时”设置为“编码与修复”，限制最多失败转向次数，例如 2 次。

回退会重新执行步骤，不会撤销已经改过的文件。权限拒绝、取消和宿主错误不等于可自动重试的业务失败。存在依赖的步骤不能任意调换；保存前出现校验错误时，先修正引用、路线或步骤位置。

流程里的 Agent 角色来自项目可用角色列表，不是 Mods 通过 `$.agent.register` 动态注册的角色列表。

## 以 Autobiz 使用

1. 打开你的实际 Autobiz 项目的普通本地会话，并安装、开启、授权适用的 Autobiz Mods。
2. 进入 DIY 流程，点击“从 Autobiz 模板创建”。项目阶段设置会自动展开。
3. 先启用“编码与修复、独立代码评审、单元测试、人工验收”，填写具体业务目标，为 Agent 步骤选择可用角色和模型。
4. 如果需要 E2E，确认项目已有对应脚本与依赖后启用该步。
5. 如果需要推进状态，在“项目阶段与运行限制”选择实际 Feature，再启用末尾“Autobiz 验收并推进阶段”。只运行普通步骤时不必选 Feature。
6. 保存并运行。关注运行记录中的步骤顺序、真实测试结果和失败回退；需要原生工具审批时，点击返回当前任务处理原有审批卡片，再回来看进度。

更完整的业务用例见 [Autobiz DIY 操作与边界](mods-v3-diy-flow-hands-on-2026-09-27.md)。其中旧的“管理设置解锁”描述已过时：当前没有管理密码，运行授权仍保留。

## 做完后如何复用，以及按钮为什么不能点

- 下次在同一项目会话进入 DIY 流程，在“我的流程”里选择已保存版本，再点击运行。也可以“复制当前流程”，改成另一套步骤。
- 普通聊天不会自动触发你保存的流程；可以在流程页运行，或在聊天选择已保存版本后明确点击“启动流程任务”。关闭页面也不等于取消任务。
- “运行已保存版本”不可用：先检查是否还有草稿未保存、定义错误、未授权 Mods，或当前会话已有活动流程。
- “所属 Mods”里没有可用项：回 Function Mods 完成安装、应用/项目开关及当前摘要授权，再点“刷新项目状态”。
- 项目已有强制完成规则时，关掉流程里的某个检查不会免除宿主强制验收。
- 当前入口支持普通本地项目会话；Harness、远端和子线程尚不支持在这里编排执行。传统 Plugin/Harness 的原有使用方式参见 [存量功能回检](legacy-full-regression-2026-09-28.md)。
- 重启后保留流程版本和运行记录；未完成任务不会自动重放有副作用的动作。先核对产物，再决定重跑。
