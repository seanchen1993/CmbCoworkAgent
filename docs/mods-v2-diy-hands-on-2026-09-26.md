## 1. 启动并打开练习项目

在 PowerShell 启动最新开发版本：

```powershell
cd C:\ai\CmbCoworkAgent-mods-v2
npm run dev
```

在应用中新建一个普通本地会话，选择一个可用模型，关联项目目录：

```text
C:\ai\claw-diy-lab-20260926
```

这是独立于工程 Git 工作树的练习目录，已经准备好，不用 `npm install`。实现故意错误：订单总金额没有乘数量，并错误包含已取消订单。`requirements.md` 写明要求，`order-total.test.cjs` 包含四项断言。

可先在另一终端确认基线：

```powershell
cd C:\ai\claw-diy-lab-20260926
npm test
```

预期 **4 项、2 通过、2 失败，退出码 1**。这是演示的起点，不是环境安装失败。

## 2. 安装一个自己的 Mods

1. 在已关联练习目录的会话进入「自定义 → Function Mods」。
2. 确认「作用目录」是练习目录。当前无需管理口令或解锁，开关和插件版本批准分别设置。
3. 点击「从文件夹安装」，选择 `C:\ai\CmbCoworkAgent-mods-v2\examples\my-delivery-claw`。不需要先去普通「插件」页，也不要用「安装示范 Mods」代替——该按钮安装的是另外三个示例。
4. 勾选「启用 Mods 功能（应用级）」和「启用项目 Mods」。确认「作用目录」是练习目录。
5. 在 `my-delivery-claw` 条目检查摘要后点击「授权以上能力」，看到「已授权」。不必给这个练习项目授权其他 Mods。

回到对话，逐条发送：

```text
/my-claw name 我的质量助手
/my-claw rule 交付前确认真实测试结果，列出未完成事项。
/my-claw preview
```

预期能看到改过名字和提醒内容的交付卡，也可以输入 `/my-claw` 打开面板。这里的 `rule` 只修改提醒文字，不会自行执行代码评审、测试或约束模型；下面另外配置的完成规则才会触发真实检查。

## 3. 配置真实完成规则

回到「自定义 → Function Mods → my-delivery-claw → 完成检查规则」：

| 配置项 | 本次填写 |
| --- | --- |
| 检查范围 | 整个项目 |
| 执行检查 | **仅勾选单元测试** |
| 代码评审、E2E、Autobiz 业务验收 | 都取消勾选 |
| 最大修复次数（高级预算中） | 2 |
| 最长时间（秒） | 300 |
| 模型总预算（tokens） | 200000 |

`my-delivery-claw` 本身没有代码评审处理器，所以本例不勾选「代码评审」。宿主能根据应用保存的规则执行项目 `npm test`，不需要插件重新实现测试进程。也不需要 Python、Autobiz 源码或 Feature 配置。

预算是上限，不是固定消耗；对话与修复使用当前模型，会按实际请求产生用量。保留原有权限检查，出现审批时核对目标为练习项目、命令为项目测试或对 `order-total.cjs` 的修改，再决定是否批准。

## 4. 同一条消息，比较四种行为

每轮开始先在练习目录执行 `npm run demo:reset`，然后改变「完成模式」并点击「保存项目规则」。复位只重写 `order-total.cjs`，不会关闭规则或删除任务历史。按 A → B → C → D 测试；时间有限可以省略 C。

每轮都发送同一段话：

```text
这是完成检查规则的对照测试，现在先只回复“申请完成”，不要主动读取、修改代码或运行测试。
只有随后收到宿主完成检查要求修复的反馈时，才按 requirements.md 修复 order-total.cjs，并运行 npm test 后再次申请完成。
不得修改 requirements.md、order-total.test.cjs、package.json 或 reset-demo.cjs，不得通过删除或放宽测试来通过检查。
```

| 轮次 | 完成模式 | 正常预期 | 你应核对什么 |
| --- | --- | --- | --- |
| A | 关闭 | 本插件不发起完成测试，Agent 可以直接结束 | 手工 `npm test` 仍为 2 个失败；本轮没有该规则的新检查记录 |
| B | 仅报告 | 宿主实际运行测试，记录失败，但该规则允许结束 | 「完成检查证据」有单元测试失败/退出码；代码仍错误，不能把“允许结束”当成通过 |
| C（可选） | 阻止完成 | 实际测试失败，宿主拒绝正常完成 | 有失败和阻断证据；不会由此规则自动申请修复 |
| D | 自动修复并复检 | 测试失败 → 宿主要求原 Agent 修复 → 再测 → 满足条件后完成 | 代码改变，证据有修复申请和复检结果；成功时手工 `npm test` 为 4/4 |

首段出现“申请完成”不等于整个过程已结束。等生成/工具执行结束，再看任务底部「完成检查证据」最后结果。交付卡上的提醒或模型声称“测试通过”，都不能替代测试命令和证据。

模型并不保证每次修复成功。审批被拒、预算耗尽、超时或代码仍错时，正确结果应是停止并明确原因，而不是伪造通过。如果 A/B 轮模型自行主动修复，说明没有遵守对照提示，这轮不能证明完成规则差异；复位后重新测试。

## 5. 怎么判断这次真的 DIY 了

最有说服力的对照是：**同一工程、同一模型、同一条消息，仅改变项目规则，结束流程从“直接结束”变成“报告失败”，再变成“失败后申请修复与重新测试”。** 无需修改主工程或反复在每条业务需求中提醒它执行测试。

建议各截一张图：B 的失败证据、D 的修复与复检证据、D 完成后终端的 4/4。你的汇报可以写：“为这个项目配置了测试通过才能完成的交付流程；检查由宿主强制执行，修复由原 Agent 在预算内完成。”不要写“改了提醒后模型就学会自动检视”或“已与 Claude Code 全量等价”。

`/my-claw off` 只关闭交付卡，不关闭应用保存的完成规则。退出实验时到「完成检查规则」选择「关闭」并保存；也可以关闭这个项目的 Mods。无需卸载插件或关闭应用全局 Mods。

## 卡住时按这个顺序检查

- 命令找不到：确认打开的是 ModsV2 开发版；插件已经安装，应用/项目开关开启，当前项目摘要已授权。
- 四轮没有区别：确认作用目录正确、每轮都保存规则并复位代码；不要只执行 `/my-claw rule`。检查是否给错误插件保存了规则，或有其他完成规则同时生效。
- 提示 `code-review` 能力不可用：本例只保留「单元测试」，不要套用后忘记取消模板默认的代码评审。
- 显示缺少脚本：会话目录必须是练习目录，且其中 `package.json` 包含 `test` 脚本。
- 修复因为预算或审批停止：先看证据中的具体原因；不要把安全停止误认为设置没有生效，也不要依靠无限放大预算证明成功。

准备验证：本轮仅在本地验证练习代码的 2 失败基线，以及另一临时目录中正确实现的 4 通过对照，没有替你调用模型或修改应用配置。本次手动演示的真实模型执行结果以你实际运行和证据为准。夹具验证记录为 `output/mods-v2-validation/2026-09-26-diy-demo-fixture-check.json`。
