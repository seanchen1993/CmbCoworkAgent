# Mods 剩余能力：用户影响与实现可行性评估

日期：2026-09-29。基于 `codex/mods-v2` 当前代码与此前已验证的 Claude Code 2.1.284 差距。
本文保留评估时的完整建议，不是对新版本 Claude 的重新核验。后续已完成基础参数表单、可选 configSchema、
对象输出路径选择及草稿保护，见 [增量交付](mods-flow-forms-delivery-2026-09-29.md)；其他建议不能据此视为已实现。
2026-09-30 的 [宿主独立流程迭代](mods-host-flow-delivery-2026-09-30.md) 又补齐了普通本地新建流程
不必选择“所属 Mods”的能力。下文相关条目保留原评估背景，组件粒度及其他后续建议仍待实现。
现状及使用操作见 [迁移与使用指南](mods-compatibility-impact-and-plugin-migration-2026-09-29.md)。

## 判断

影响最大的不是还差多少 API 名字，而是用户能否顺利完成：
**装入原有能力 → 选择需要的组件和模型 → 接好输入输出 → 执行 → 看懂结果 → 下次复用。**

这条基本链路已有实现，但配置成本、组件边界和工作模式仍有明显限制。
大多数高价值缺口可以在现有基础上补齐，不需要推翻运行时；有几项需要先升级授权与快照契约。
不能承诺把任意第三方插件自动变成独立组件，也不能保证复制 Claude 私有运行上下文。

以下影响等级是基于操作链路的工程判断，不是用户遥测统计。成本分低、中、高，指相对改动范围，
不作为工期承诺；上线前仍需详细设计、两位独立评审及回归/E2E 验证。

## 1. 最值得优先解决的实际使用问题

| 项目 | 用户遇到什么 | 可行性与建议实现 | 成本 / 风险 |
| --- | --- | --- | --- |
| 参数和前后步骤连线仍要写 JSON | 非开发用户不知道 path/source 是什么，也不会填 JSON Pointer；包能安装，却接不成流程 | **可实现，最高优先级。** 基于现有 inputSchema 做基础表单、字段提示、前步输出选择与类型检查，保留 JSON 高级入口。未声明 configSchema 的动作不能凭空生成可靠配置表单，需新增可选作者契约 | 中；后端必须继续独立验证，页面校验不能替代权限和 schema 校验 |
| 只想用 Skill/MCP，却必须选择“所属 Mods” | 用户没有 Function 包也要先装一个，难以理解，阻断最简单的组合 | **可实现，优先补基础。** 新增宿主管理的 Flow 执行主体，原生节点使用流程租约与各来源授权；插件动作仍验证真实提供者。旧有所属 Mods 流程继续兼容 | 中高；不是删掉必填项或塞一个虚假授权包，涉及运行、撤权、审批与持久化 |
| 只选一个动作，整包其他 Hooks 仍参与 | 想要 A 插件的读取功能，却连带触发自动评审、路由或其他行为；难以做到“按组件 DIY” | **对显式声明组件可实现，应作为核心迭代。** 作者声明稳定组件 ID、入口、依赖和配置；绑定、授权、加载、撤权按同一组件快照处理。旧插件默认仍整体加载 | 高；不能靠隐藏 UI 或按事件名字随意过滤，初始化和共享状态可能有依赖 |
| 已在传统 Plugin 项目模式工作的用户不能直接运行 Flow | 需要另开普通会话，原工作习惯与新功能割裂 | **本地 Plugin 模式可以做适配，但需先完成接口验证。** 复用原模式的 runtime factory、工具、技能及完成处理器，再接 Flow 的运行契约；不在后台偷偷切成普通模式 | 高；插件上下文、审批、Harness 完成循环和取消必须各自保持语义。远端、定时任务另评估 |
| Claw 分对话，完成规则仍项目共享 | 一个对话想“只报告”，另一个想“必须复检”，配置却相互关联 | **可实现。** 区分项目强制底线与 Claw 附加规则；运行时生成有效规则快照，UI 展示来源。旧规则先保留原语义，不自动把强制项降成可选项 | 中高；需定义重复检查去重、冲突、预算和切换时机，不能简单复制一份配置 |
| 更新插件后，用户要手工找出哪些引用失效 | 修改一个包后组合不能运行，不知道应重选哪些步骤 | **可实现，收益高。** 增加版本差异与受影响节点列表、引导重选和重新批准；兼容字段可保留输入草稿，但不能静默信任新摘要 | 中；必须继续按来源身份匹配，不能仅靠同名替换 |
| 已选/未选能力与菜单显示不一致 | 菜单中能看到 Skill，发送后才说当前 Claw 不允许 | **可实现。** 用真实来源 ID 过滤或标注菜单，给出为什么不可用以及去哪里调整；运行时守卫保留 | 中；同名技能不能按名称合并，不能用前端列表代替宿主校验 |
| MCP 工具存在却无法加入流程 | 高级 schema、复杂输出超出支持子集，用户不清楚原因 | **可分步实现。** 先核对实际工具与已有子集的差异（已有受限本地引用），再补有业务证据的缺口和字段级诊断。图片/文件用受控产物引用另建契约 | 中到高；不开放无界外部引用解析，不把二进制直接塞进步骤 JSON |

前三项最贴近用户最初的“每个步骤可以灵活选择”。其中“组件级选择”需要作者配合，
没有声明边界的任意旧插件不能保证自动拆分；这不是多做一个解析器就能解决的问题。

## 2. 确实影响插件迁移，但不阻断基本 DIY 的兼容缺口

| 能力 | 谁会直接受影响 | 能否实现与必要条件 | 建议顺序 |
| --- | --- | --- | --- |
| 完整 skill.prompt | 想在 Skill 使用时动态补充团队约定、业务背景或转换正文的插件作者 | **可实现，成本中高。** 建立“解析来源 → 固定完整正文 → 扩展 → 保护 → 交付”的统一路径，显式激活、模型主动读 Skill、分页读取和 Flow 子任务必须看到一致版本。不能只在一个激活回调里改字符串 | 第二阶段，优先于低价值 UI API |
| tool.describe | 想在运行时定制模型看到的工具说明/schema 的作者 | **有界实现可行，成本中高。** 在模型工具目录构建处适配；描述变化不能改变真实工具身份。若允许 schema 变换，还需定义参数到原执行器的映射及校验；仅修改展示不能声称完整兼容 | 与 Skill 正文链一起设计 |
| prompt.read/fill/edit 等 | 想提供“填入任务模板、编辑草稿、附带资料”按钮的作者 | **可实现，成本中。** 绑定 thread ID、草稿版本和附件权限；先填草稿并由用户发送，再按明确授权扩展 submit。不能覆盖用户正在输入的内容或改到另一个对话 | 在表单、使用引导之后 |
| model.complete 的 effort | 想给代码评审配置更高推理强度的作者 | **部分后端可较快补齐，成本中。** 当前独立 complete 解析器拒绝 effort，但 Agent 模型边界已有部分 DeepSeek 映射。应建立模型能力表、显式值映射、费用和配置快照；不支持的供应商明确拒绝，不静默丢参数 | 可独立补齐，不必等待整个组件重构 |
| 独立模型 options.signal | 一个插件有多个请求，只想取消其中一个 | **可实现，成本中高。** 通过 guest 取消句柄关联宿主单请求控制器，与父任务取消组合；覆盖调用前已取消、执行中取消、晚到结果与句柄释放。不能直接把 AbortSignal 当普通 JSON 传 IPC | 中等优先；已有父任务取消和 timeoutMs 可覆盖部分需求 |
| 模型输出额度与时限配置 | 大文件评审、较长报告可能遇到截断/超时 | **有界配置可实现，成本中。** 区分宿主最大预算、项目配置与单次请求，保留硬上限和真实结算，清楚显示截断原因；实际痛点需按模型和文件大小测量 | 与模型配置一起补，不直接取消额度 |
| 更多 classic 事件提供者 | 依赖权限/配置/工作树等事件观察的迁移插件 | **按事件可实现，成本不一。** 必须在真实业务触发点交付一次有效事件，定义异步时序、异常和取消语义；没有对应宿主能力的事件不能凭空补空回调 | 由实际迁移插件需求驱动 |
| 依赖类型聚合和迁移诊断 | 维护多个互相依赖 Mod 的开发者 | **可实现，成本中。** 按版本锁定依赖、限制声明文件解析，校验运行时真实提供者；首先输出可操作的差距清单 | 普通用户收益间接，晚于主要使用链路 |

本表“可实现”不是“完全相同”：例如本工程使用多模型后端，无法让不支持推理强度的供应商
凭空获得 effort；也不能把现有文本快照 fork 宣称为 Claude 内部缓存会话的复制。

## 3. 可以做，但应由明确业务需求推动

### 会话环境与 MCP 隔离

`env.set` 对需要“这个 Claw 用测试环境，另一个用生产环境”的工作流有价值，但当前 MCP 使用共享连接池。
只增加环境赋值 API，会让已连接服务继续使用旧值，甚至造成跨对话影响。

可行方案是不可变的会话环境覆盖层、包含配置/环境/权限身份的连接池键、进程生命周期和凭据引用隔离。
同一会话变更环境后如何处理旧连接也必须明确。成本高，适合有真实多环境需求时建设；
基础 DIY 不应被这项阻塞。简单区分服务时，可先显式配置不同 MCP 服务。

### 故障后的恢复执行

长流程用户确实需要“从失败处继续”，可以实现受限恢复：只读操作可重新执行；有幂等键且提供查询能力的
写操作可核对后继续；其他副作用操作要求先确认真实状态。需将步骤意图、提交状态和结果证据持久化。

成本高，不能承诺任意 shell、外部业务系统和文件写入的统一回滚，也不能把重跑节点称为恢复原事务。
先完善失败定位、产物展示和明确重跑入口，再补业务范围明确的恢复协议。

### MCP 单工具选择与连接隔离

单工具允许列表可基于现有服务选择继续扩展，成本中，适合“只读 Claw”这种明确需求。
它与独立进程/连接隔离是两件事。要防止同服务其他工具参与调用，应检查普通模型工具目录、
显式 MCP 调用和 Flow 节点全部入口；不能只从下拉框隐藏工具。

## 4. 暂缓，不作为这一轮主要目标

- **完整终端像素/多 pane、音频和第一方遥测接口**：个别插件需要，普通代码检视和跨插件业务流程
  不依赖它们。剪贴板等小功能可以按实需单独做，不必为了它重建终端 UI。
- **任意 Agent 内核、沙箱、存储和权限引擎替换**：技术上可设计新的扩展体系，但不是现有 API 的小补丁，
  需要另立架构项目和可信边界，不适合作为本次 DIY 交付的完成条件。
- **Claude 私有凭据句柄、内部缓存会话的完全等同实现**：外部程序的身份及内部资源不能直接复用。
  可提供本工程自己的受控等效入口，但应明确差异。
- **任意旧插件自动拆分、任意副作用自动回滚、所有未来 Claude API 零修改兼容**：无法给出可靠的通用保证，
  不应写成可验收承诺。使用作者契约、版本范围和具体业务用例作为边界。

## 5. 建议的实施顺序与验收目标

### 第一批：让用户真正能自己组合

先评审并确定 Flow 执行主体、组件身份与版本、组件依赖、参数 schema 和授权关系；
据此实现无强制所属插件的原生流程、组件显式选择、表单化参数和前步字段选择。
同时加入配置诊断和升级引导。旧包默认行为保持不变，新增作者声明才能获得细粒度组合。

验收：一个不写代码的用户，用现有 Skill、MCP、两个插件动作和不同模型组成流程；
不需要占位包，不需要手写 JSON；明确知道哪些 Hook 会参与。模型、来源和数据传递有真实执行记录。
没有足够 schema 的第三方动作明确保留高级配置入口，不能保证所有旧包自动表单化。

### 第二批：让迁移和日常使用更完整

完成 Skill 正文链、工具描述契约、草稿填充、effort 和独立取消；
建立项目强制规则与 Claw 附加规则的合并快照。根据实际 MCP 工具补齐常用 schema。

验收：有真实依赖上述 API 的测试插件，不能只验证注册成功；双对话不能串草稿、串规则或串取消；
重新应用后能复用明确版本，旧 Plugin 和无 Claw 会话回归通过。

### 第三批：扩展存量模式和高级运行

先验证本地 Plugin/Harness 与 Flow 的适配契约，再在保留其原有运行语义的前提下接入。
多环境隔离、断点恢复、远端和定时流程按业务需要独立推进，不捆绑到前两批。

如果用户的主要项目全部处于传统 Plugin 模式，应将其**可行性原型**提前到第一批设计期间，
避免前两批完成后才发现主工作模式无法承接；但不为赶原型放松其权限与完成检查。

每批都需包含旧定义迁移、双会话隔离、撤权/取消、真实业务失败、重启行为、旧 Plugin/Harness 回归、
Electron E2E 和适度性能对比。主指标应是业务任务完成与配置成本，不能拿 API 数量作为完成度。
