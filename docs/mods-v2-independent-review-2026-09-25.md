## 2. 已确认的交互问题

### P2：原生设置保存后，插件面板仍允许编辑，但保存必然失败

复现步骤：

1. 在“自定义 → Function Mods → 完成检查规则”保存应用规则。
2. 打开或刷新 `/kanban` 面板。
3. 在仍然可操作的“完成行为”下拉框选择另一个模式。
4. 界面显示 `未保存：MODS_COMPLETION_POLICY_HOST_OWNED`，生效规则没有改变。

本次使用真实 FunctionSession、QuickJS、Pane、SQLite 和应用策略覆盖层复现。专用测试通过的含义是“确认存在这个失败行为”，不是问题已修复。

根因：应用设置成为权威来源后，宿主正确拒绝插件写入 `completion-config`；面板却仍执行旧的写入路径，也没有展示设置归属。

- 宿主保护：[application-completion-policy.ts](../src/main/mods/v2/application-completion-policy.ts)，`assertGuestWritable`。
- 面板保存及报错：[pane.tsx](../examples/autobiz-kanban-mods/hooks/kanban/pane.tsx)，89–106 行。
- 始终可编辑的模式控件：同文件 173–178 行。

建议：应用规则生效时，面板显示“由应用设置管理”，将相应编辑控件设为只读，提供跳转入口。未被应用接管时才保留插件内编辑。**不能通过放开插件写权限来解决此问题。**

### P1（面向其他机器交付前）：Autobiz 依赖固定开发机路径，界面缺少就绪检查

[autobiz-source.ts](../src/main/mods/v2/autobiz-source.ts) 第 8 行固定为 `C:\ai\autobiz_kanban`，并要求固定 Git 对象存在；调用还需要 Git、Python。安装应用及 Mods 包本身不足以准备这个业务能力。

当前规则表单可以直接选 Autobiz 验收和阶段推进，用户执行任务后才会遇到依赖失败。这影响 Autobiz 示例的可移植交付，不代表所有 Mods 都不能在其他机器使用。

建议：提供受校验的适配器交付方式，或允许选择源码目录并验证固定版本；配置页面预检依赖、项目结构、阶段和可用测试入口。未就绪时说明原因、给出修复入口，禁止把不可用能力显示为已经就绪。保留固定版本校验，不能改成任意本地脚本即可执行。

## 3. 静态检视发现的异步风险

### P2：保存请求的旧响应可能覆盖切换后的项目表单

[FunctionCompletionPolicy.tsx](../src/renderer/src/components/customize/FunctionCompletionPolicy.tsx) 的读取 Effect 有 `live` 保护，但 245–259 行的异步保存没有检查响应是否仍属于当前 `threadId/plugin`。父界面按插件保留组件时，项目切换可能复用这个组件。

风险时序：项目 A 保存尚未返回 → 切到项目 B 并加载其规则 → A 的响应返回，直接覆盖 `view/draft/notice`。第一次请求仍写入 A；风险在于 B 页面显示了 A 的设置，后续用户再次保存时可能写错配置。

这是代码路径上的静态发现，本次没有动态复现这段竞争，不应当说已经观察到跨项目误写。

建议：为加载和保存共同绑定项目、插件及请求代次；组件身份改变后丢弃旧响应。增加延迟 IPC 的切换回归，验证表单、提示和 busy 状态均不会被旧请求污染。

## 4. 用户体验还需要的优化

### 将配置流程变成用户能理解的选择

目前需要理解管理解锁、全局启用、项目启用、权限授权、规则来源等多个状态，再填写文件路径、Feature ID、checkpoint 和预算。安全开关有必要，但页面应将其组织为一条明确的就绪流程。

建议先提供三种业务模板：“完成后给我检查报告”“不通过就修复后再检查”“验收通过再推进看板”。模板映射现有宿主规则，授权仍由用户明确完成；高级预算、检查组合和诊断放入展开项。

“当前文件”实际需要手填路径时，应改称“指定文件”或提供文件选择器；Feature 和起始阶段从项目读取并选择，避免要求用户记内部状态名。对整个项目检查隐藏无关输入，同时清楚说明哪些设置按项目保存。

### 预算应给出解释和可操作的反馈

默认修复 token 预算为 8192；历史真实业务演示累计约 110945 tokens，且记录过更低预算失败。这不意味着所有场景都应提高到相同数值，但说明默认值不能保证复杂示例开箱即用。

应说明预算包含哪些请求和上下文，显示已用/剩余量；耗尽时展示已完成的检查、剩余步骤，以及由用户决定的继续方式。模板可使用分级预算并清楚展示成本约束，不能为了演示静默放开上限。

### 结果先给业务摘要，证据保留在详情

已有真实演示截图中，大量步骤记录、英文内部值和重复边界说明占满对话区域。用户仍需自己判断“到底修好了没有，是否推进了，哪里需要我操作”。

建议首屏只呈现类似：“发现 2 项问题 → 修复 1 轮 → 单测和验收通过 → 阶段 A 已推进到 B”，再提供时间、用量和展开证据。失败、等待审批、预算耗尽、证据过期各自给出明确下一步。哈希、内部事件和恢复诊断放入高级详情。

## 6. 建议的下一步及验收条件

1. **先修交互正确性**：统一应用设置与 Pane 的规则归属，处理保存响应竞争；添加相应回归和 Electron 操作验证。
2. **再补开箱可用流程**：依赖预检、业务模板、文件/Feature/阶段选择、明确的生效状态和业务结果摘要；在没有固定开发机目录的环境中验证安装、配置、失败修复及推进。
3. **完成性能收敛**：对照原门槛解决 TTFT、慢帧与堆增长，再按原样本量复测；不能通过降低验收标准宣告完成。
4. **若仍要求最初的全面对齐**：继续以兼容矩阵逐项关闭 partial/unsupported，并绑定行为证据；不能仅因核心示例跑通就关闭这部分计划。

面对普通用户的最终验收，应要求用户不读内部架构文档即可完成：选择模板 → 看见依赖和授权是否就绪 → 保存并知道生效范围 → 运行任务 → 从摘要辨认发现、修复、复检和推进结果 → 失败时知道下一步。当前版本还未达到这个体验标准。
