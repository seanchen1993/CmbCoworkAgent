- 横向参考：`C:\ai\opencode`、`C:\ai\claude-code`、`C:\ai\hermes-agent` 等

目标洞见：

1. 工具返回结果动态字段投影和裁剪。
2. 技能/工具执行错误熔断与调试模式 fail fast。

## 1. 结论摘要

| 洞见 | 价值 | 难度 | 性价比判断 | 推荐动作 |
|---|---:|---:|---|---|
| 工具返回结果动态字段投影和裁剪 | 高 | 中低 | 最高 | 先做 MCP/deferred tool MVP，再扩展到通用 ToolResultProjection |
| 错误熔断与 fail fast | 高 | 中低 | 很高 | 复用现有 ToolFailureSignal，增加 failure fingerprint 与阈值策略 |

两个洞见都适合第一批做。原因是它们不要求重写 Agent 主循环，却能直接改善长链路工程交付的稳定性、token 成本和调试体验。

推荐第一阶段目标：

1. `invoke_deferred_tool` 支持 `required_fields` 和 `max_result_chars`。
2. MCP 结果统一经过 projection/bounding 层，记录裁剪元数据。
3. 工具失败进入统一 failure fuse，调试模式首错即停，普通模式同类错误重复 N 次熔断。
4. Trace/日志记录原始大小、裁剪后大小、失败指纹、熔断原因。

## 2. 洞见 1：工具返回结果动态字段投影和裁剪

### 2.1 当前工程现状

当前 MCP 结果处理集中在 `src/main/mcp/result-utils.ts`：

- `normalizeMcpInvocationResult` 负责把原始 MCP 结果标准化。
- `getUsefulMcpResultData` 的优先级是 `structuredContent`、JSON 文本、普通文本、contentBlocks、raw。
- `toEagerToolResponse` 直接把文本或 contentBlocks 返回给模型。
- `toCallResult` 把 `getUsefulMcpResultData` 放入 `{ ok: true, data }`。

关键证据：

- `src/main/mcp/result-utils.ts:201-220`：当前只是提取“有用数据”，没有按调用方字段需求投影。
- `src/main/mcp/result-utils.ts:222-270`：eager MCP 和 call result 仍以完整 text/data 为主。
- `src/main/agent/tools/tool-search-tool.ts:489-502`：`invoke_deferred_tool` 直接 `JSON.stringify({ ok: true, data: getUsefulMcpResultData(result) })`，没有 `required_fields`。
- `src/main/mcp/capability-service.ts:253-265`：MCP 调用后立即 normalize，没有 projection/bounding 层。

当前工程已有可借鉴的“结果裁剪 + 完整结果 sidecar”思路，但只用于 Workflow：

- `src/main/agent/workflow/engine.ts:217-235`：Workflow final result 超限时写 `<runId>.result` sidecar。
- `src/main/agent/workflow/engine.ts:1497-1522`：`boundResultWithSidecar` 将 run.json 中的结果裁剪，完整 JSON 可写 sidecar。
- `src/main/agent/workflow/types.ts:50-56`：workflow tool final result 约 8K 字符预览，完整结果可另存。

现状判断：

当前能力是“提取 + 截断”，不是“按场景投影”。缺少：

1. 调用方声明字段需求的入口。
2. JSON 结构字段白名单裁剪。
3. 裁剪元数据，例如原始大小、裁剪后大小、缺失字段、是否截断。
4. MCP 普通工具结果的完整结果 sidecar。
5. 对数组、分页、搜索结果这类大结果的语义化摘要策略。

### 2.3 目标设计

核心原则：

1. 模型默认只看“必要字段 + 有界预览”。
2. 完整结果不丢，但不直接塞进上下文。
3. 工具调用方可以声明需要的字段。
4. 平台层必须有最终大小兜底。
5. 先做低风险入口，再扩全链路。

建议新增模块：

```text
src/main/mcp/result-projection.ts
src/main/mcp/result-projection.test.ts
```

核心类型建议：

```ts
export interface ResultProjectionOptions {
  requiredFields?: string[]
  maxChars?: number
  maxArrayItems?: number
  mode?: "auto" | "fields" | "bounded" | "raw"
}

export interface ProjectedResult {
  data: unknown
  metadata: {
    projected: boolean
    truncated: boolean
    originalBytes: number
    projectedBytes: number
    missingFields?: string[]
    omittedFields?: string[]
    fullResultRef?: string
  }
}
```

字段路径先支持 JSONPath 子集即可：

```text
id
name
items[].id
items[].status
data.records[].customerId
data.records[].score
```

不建议第一版引入完整 JSONPath 引擎。原因是字段路径越强，安全和性能边界越复杂。第一版支持对象路径、数组通配、数组前 N 项即可。

### 2.4 实施方案

#### Phase 1：MVP，覆盖 `invoke_deferred_tool` 的 MCP 分支，并明确 saved tool 边界

改动范围：

1. `src/main/mcp/result-utils.ts`
   - 将 `getUsefulMcpResultData(result)` 拆成两步：
     - `extractUsefulMcpResultData(result)`
     - `projectMcpResultData(data, options)`
   - 保持原函数默认行为不变，避免破坏旧链路。

2. `src/main/agent/tools/tool-search-tool.ts`
   - 给 `invoke_deferred_tool` 增加可选参数：
     - `required_fields?: string[]`
     - `max_result_chars?: number`
     - `max_array_items?: number`
   - 同步增强 `inspect_tool(caller="invoke_deferred_tool")`，让模型可靠知道可选字段：
     - 当前 `inspect_tool` 已返回 MCP `output_schema`。
     - 建议新增 `field_hints`，从 `output_schema` 推导常用 field paths。
     - 对已存在的 stored result example，不直接暴露完整历史样例；只派生脱敏后的 `example_field_paths` 和 top-level keys。
     - 当前 stored example 主要在 `caller === "code_exec"` 时返回，建议为 `invoke_deferred_tool` 增加轻量字段提示，避免 `required_fields` 靠猜。
   - 返回结构从：

```json
{ "ok": true, "data": ... }
```

升级为：

```json
{
  "ok": true,
  "data": "...projected data...",
  "_projection": {
    "projected": true,
    "truncated": false,
    "originalBytes": 120000,
    "projectedBytes": 3000,
    "missingFields": []
  }
}
```

3. 对缺失字段不直接失败：
   - 返回已有字段。
   - `_projection.missingFields` 标记缺失。
   - 如投影为空，回退到 bounded preview，并提示可用 top-level keys。

4. 明确 saved tool 分支行为：
   - `invoke_deferred_tool` 入口会先处理 saved tool，再处理 MCP lazy tool。
   - MVP 不能静默忽略投影参数，否则同一工具接口体验不一致。
   - 建议 saved tool 始终支持 `max_result_chars` 的通用 bounded preview。
   - `required_fields` 对 saved tool 只做 best-effort：当 `parseCodeExecOutputValue(result.output)` 得到 JSON object/array 时尝试字段投影；当输出是普通文本时不报错，但在 `_projection` 中标记 `requiredFieldsIgnored: true` 和原因。
   - 后续若 saved tool 增加 output schema，再升级为与 MCP 一致的严格字段提示。

验收标准：

1. 不传 `required_fields` 时，旧行为保持不变。
2. 传 `required_fields` 后，返回只包含声明字段。
3. 超过 `max_result_chars` 时有明确截断标记。
4. 数组结果可限制 `max_array_items`。
5. `inspect_tool(caller="invoke_deferred_tool")` 返回 `field_hints` 或 `example_field_paths`，模型不需要凭空猜字段。
6. saved tool 分支识别投影参数；至少支持 `max_result_chars`，对无法执行的 `required_fields` 明确返回 `_projection.requiredFieldsIgnored`。
7. 单测覆盖对象、数组、嵌套、缺失字段、非 JSON 文本、循环结构、saved tool JSON/文本输出。

预计难度：2-3 天。

#### Phase 2：MCP eager 工具和 server proxy 统一兜底

改动范围：

1. `src/main/mcp/langchain-tool.ts`
   - `toEagerToolResponse` 前增加 bounded projection。
   - 不修改 MCP 原始 input schema，避免把 `required_fields` 误传给真实 MCP server。
   - 只做默认上限和语义提示。

2. `src/main/mcp/server-proxy.ts`
   - 如外部调用也需要保护，可让 `toCallResult` 支持 projection options。

3. `src/main/agent/runtime.ts`
   - MCP hook context 中记录 projection metadata，便于 Hook/Trace 观察。

验收标准：

1. 直接暴露的 eager MCP 工具不会因为大结果污染上下文。
2. 原 MCP server 不感知 projection 控制字段。
3. Hook 和 trace 能看到裁剪前后大小。

预计难度：3-5 天。

#### Phase 3：完整结果 sidecar / managed result store

建议新增：

```text
src/main/tool-results/result-store.ts
```

设计参考本工程 Workflow sidecar 和 opencode ToolOutputStore：

1. 模型可见结果只保留 bounded preview。
2. 完整结果写入受控目录。
3. 返回 `fullResultRef`，后续通过专门工具读取片段或搜索。
4. 不直接给模型一个任意文件路径，避免扩大权限。

目录建议：


验收标准：

1. 完整结果可追溯。
2. 结果文件有 TTL 或清理策略。
3. 读取完整结果必须经过专用工具或权限控制。
4. Trace 中只记录摘要，不默认上传完整敏感数据。

预计难度：1-2 周。

## 3. 洞见 2：错误熔断与调试模式 fail fast

### 3.1 当前工程现状

当前工程已经有多个局部保护，但没有一个跨工具的同类错误熔断器。

已有能力：

1. 工具失败检测：
   - `src/main/hooks/tool-failure.ts:44-99`：识别工具返回中的 `success:false`、`is_error:true`、`error`、非 0 `exitCode`、命令失败字符串。
   - `src/main/hooks/tool-failure.ts:105-128`：把 thrown error 转成 `ToolFailureSignal`。
   - `src/main/hooks/tool-failure.ts:131-157`：基于 `tool_call_id` 做 PostToolUseFailure dedupe。

2. Hook halt：
   - `src/main/hooks/halt.ts:37-44`：`continue:false` 会抛出 `HookHaltError`。
   - `src/main/hooks/runner.ts:1321-1369`：PreToolUse/PreSkillUse/UserPromptSubmit 可阻断或停止。
   - `src/main/hooks/runner.ts:1456-1499`：PostSkillUse 可 halt 或要求 revision。

3. PostToolUseFailure：
   - `src/main/agent/runtime.ts:4575-4604`：工具失败信号会触发 PostToolUseFailure hook。
   - `src/main/agent/runtime.ts:964-982`：MCP `isError` 也会触发 PostToolUseFailure。

4. 模型/API retry：
   - `src/main/ipc/agent.ts:2758-2768`：根据路由模式限制每个模型的最大 fetch attempts。
   - `src/main/ipc/agent.ts:4773-4808`：failover loop 尝试候选模型。
   - `src/main/agent/failover.ts:161-198`：判断哪些 API 错误值得 retry。

5. Workflow 防 runaway：
   - `src/main/agent/workflow/engine.ts:392-400`：agent invocation ceiling 超限直接报错。
   - `src/main/agent/workflow/engine.ts:513-519`：abort 后 park forever，避免死脚本热循环。
   - `src/main/agent/workflow/subagent.ts:170-194`：subagent 最多跑 2 次。
   - `src/main/agent/workflow/types.ts:58-62`：结构化输出最多 5 次，subagent fresh run 最多 2 次。

6. MCP transport retry：
   - `src/main/mcp/capability-service.ts:164-185`：terminated/disconnected/ECONN 只重试一次。

缺口：

1. 没有把同一类工具错误跨多次调用聚合。
2. 没有“同类错误重复 N 次后停止本轮”的默认策略。
3. 没有 Skill 调试模式下“首错即停”的平台开关。
4. PostToolUseFailure 目前偏观察/扩展 hook，不是默认熔断策略。
5. 用户只能看到工具失败，无法看到“为什么平台判断继续重试无意义”。

### 3.2 C:\ai 横向参考

#### claude-code：连续失败 circuit breaker

`C:\ai\claude-code\src\services\compact\autoCompact.ts` 是最直接的参考：

3. 阈值不宜过高，3 次足够证明路径大概率无效。
4. 熔断要输出明确 reason，不能静默跳过。

本工程 Workflow 已有“超过调用上限直接失败”的原则：

- `src/main/agent/workflow/engine.ts:392-400`：超过 agent invocation ceiling 后不报告 completed，而是 fail loudly。

可借鉴点：

1. 熔断后不能伪装成功。
2. 错误信息要告诉用户如何重构任务或缩小范围。

### 3.3 目标设计

建议新增模块：

```text
src/main/agent/failure-fuse.ts
src/main/agent/failure-fuse.test.ts
```

核心类型：

```ts
export type FailureFuseAction = "observe" | "warn" | "strong_warn" | "halt"

export interface FailureFuseInput {
  threadId: string
  turnId: string
  toolName?: string
  toolCallId?: string
  toolArgs?: unknown
  signal: ToolFailureSignal
  mode: "off" | "warn" | "debug"
}

export interface FailureFuseDecision {
  action: FailureFuseAction
  fingerprint: string
  count: number
  threshold: number
  reason: string
}
```

指纹建议包含：

1. `toolName`
2. `signal.kind`
3. `signal.errorType`
4. 标准化后的错误文本
5. 可选的参数摘要，例如命令主语、MCP tool id、文件路径类别

错误文本标准化规则：

1. 去除绝对路径中的用户目录。
2. 数字行号、时间戳、UUID、hash 用占位符替换。
3. 保留 exit code、错误类型、关键异常名。
4. 文本最多取前 500 字符。

阈值建议：

| 模式 | 条件 | 动作 |
|---|---|---|
| debug | 任意工具失败 | 首错 halt |
| off | 任意工具失败 | 不记录、不提醒、不 halt |
| warn | 同一 turn 同一 fingerprint 第 1 次 | observe |
| warn | 同一 turn 同一 fingerprint 第 2 次 | warn，给模型提示不要重复同路径 |
| warn | 同一 turn 同一 fingerprint 第 3 次及以后 | strong_warn，不 halt |
| warn | 用户取消/Abort | 不计入提醒 |
| warn | 网络/限流类模型 API 错误 | 交给现有 retry/failover，不进入工具失败提醒 |

### 3.4 实施方案

#### Phase 1：MVP，基于 ToolFailureSignal 做 turn 内熔断

改动范围：

1. 新增 `src/main/agent/failure-fuse.ts`
   - 提供 `recordToolFailure(input): FailureFuseDecision`。
   - 内部使用 `Map<threadId, Map<turnId, Map<fingerprint, state>>>`，或等价的复合 key：`${threadId}:${turnId}:${fingerprint}`。
   - state 包含 count、firstSeenAt、lastSeenAt、lastToolCallId。
   - 设置最大容量和 TTL，避免内存泄漏。
   - 同一 turn 结束时清理该 turn 的状态；跨 turn 只保留聚合统计，不直接参与 MVP 熔断。
   - 同一 fingerprint 后续出现成功结果时重置本 turn 计数；跨 turn 统计采用 TTL 衰减，避免旧失败长期累计造成误熔断。

2. 接入 `src/main/agent/runtime.ts`
   - 熔断决策必须进入 awaited 控制流，不能只挂在 fire-and-forget 观察链路。
   - `onToolFailureSignal` 当前是 toolErrorMiddleware 的观察回调，注释已说明 fired-and-forgotten；它可以继续用于 PostToolUseFailure 通知和日志，但不能作为 halt 的唯一入口。
   - MCP `isError` 当前触发 PostToolUseFailure 时使用 `.catch(...)`，也是观察链路；普通工具结果检测在 `local-sandbox.ts` 中同样 fire-and-forget。上述链路只能记录，不能稳定停止本轮。
   - MVP 推荐接入两个 awaited 控制点：
     - MCP awaited 路径：`service.invoke(...)` 返回 `result` 后、`PostToolUseFailure` fire-and-forget 前，若 `result.isError`，同步构造 `ToolFailureSignal` 并调用 `recordToolFailure`；decision 为 `halt` 时直接抛 `FailureFuseHaltError`。
     - 通用工具 awaited 路径：优先接 `createToolHookMiddleware` 的 `const result = await handler(...)` 之后、PostToolUse hook 之前；对返回结果调用 `detectToolFailure`。decision 为 `warn` 时把提示作为 PostToolUse 反馈返回给模型，decision 为 `halt` 时抛 `FailureFuseHaltError`。
   - fire-and-forget 的 `PostToolUseFailure` 仍保留，用于安全/观测 hook；但它不承担熔断控制职责。
   - 当 decision 为 `warn`，向模型注入短提示：

```text
同类工具错误已重复出现 2 次。不要继续用相同参数重试，请先改变策略或向用户报告阻塞原因。
```

   - 当 decision 为 `halt`，终止本轮：

```text
同类工具错误已重复出现 3 次，平台已停止自动重试，避免继续消耗 token 或制造副作用。
```

3. 新增错误类型
   - 推荐新增 `FailureFuseHaltError`，不要滥用 `HookHaltError`。
   - 在 `src/main/ipc/agent.ts` catch 中仿照 `HookHaltError` 处理：
     - pause active goal
     - tracer.finish("cancelled", reason)
     - 发送 renderer custom event，例如 `failure_fuse_tripped`

4. 调试模式开关
   - 第一版先支持 env/config：

```text
CMB_AGENT_FAIL_FAST=1
```

   - 后续再接到 Skill 开发 UI 或线程设置。

验收标准：

1. 同一 turn 内同一工具同一错误重复 3 次，本轮停止。
2. debug 模式下首次工具失败即停止。
3. 用户 abort 不触发熔断。
4. 同一工具不同错误不误聚合。
5. 同类错误第 2 次有明确提示，第 3 次有明确停止原因。
6. 不同 turn 的旧失败不会直接累计触发本轮熔断。
7. 某 fingerprint 后续成功时，本 turn 对应失败计数重置或标记 recovered。

预计难度：3-5 天。

#### Phase 2：跨 turn / skill 级熔断

第一阶段只做 turn 内，避免误杀。第二阶段可以扩展：

1. thread 级短期记忆：同一 fingerprint 在 10 分钟内多轮出现，直接 warn。
2. skill 级调试：某个 skill 开发期间开启 fail fast。
3. 高风险工具策略：写文件、发布、浏览器点击、外部 API 调用可以更严格。
4. UI 显示“熔断卡片”：包含 fingerprint、失败次数、最后错误、建议动作。

预计难度：1 周。

#### Phase 3：与 Harness/SkillOps 联动

1. Harness run 中记录失败指纹。
2. Skill Eval 把重复失败纳入评分。
3. SkillOps 自动聚合高频失败模式，生成候选修复建议。
4. 错题本按 fingerprint 聚合，而不是按原始错误文本聚合。

预计难度：1-2 周。

## 4. 两个方案的依赖关系

这两个洞见可以并行做，但存在一个正向耦合：

1. 工具结果投影减少上下文污染。
2. 错误熔断减少无效重试。
3. 两者共同提升长链路 Harness 交付稳定性。

建议优先级：

1. 先做 `failure-fuse.ts` 核心单测，因为它不依赖 MCP schema。
2. 同时做 `result-projection.ts` 核心单测。
3. 先接 `invoke_deferred_tool`，验证字段投影收益。
4. 再接 MCP awaited `isError` 和 `createToolHookMiddleware` 的 awaited result 控制点，验证错误熔断收益。
5. 最后加 trace/metrics。

## 5. 推荐里程碑

### M0：设计确认

产出：

- projection 字段路径语法确认。
- failure fingerprint 规则确认。
- debug fail fast 开关确认。

### M1：核心库和单测

产出：

- `failure-fuse.ts`

耗时：2-3 天。

### M2：接入 deferred MCP 和 awaited 熔断控制点

产出：

- `createToolHookMiddleware` 的 awaited result 路径接入 failure fuse。
- `onToolFailureSignal` 和 PostToolUseFailure fire-and-forget 链路保留为观测通知，不承担 halt 控制。

耗时：2-3 天。

### M3：Trace/日志/配置

产出：

- projection metadata 写入 trace 或 debug log。

- `CMB_AGENT_FAIL_FAST` 或本地配置开关。

耗时：1-2 天。

### M4：灰度和评估

灰度策略：

1. 默认只对 lazy/deferred MCP 开启显式 projection。
2. 默认只对同 turn 同 fingerprint 3 次触发 halt。
3. debug fail fast 只在显式开关下启用。

观察指标：

| 指标 | 目标 |
|---|---|
| MCP 结果平均注入字符数 | 下降 30%-70% |
| 长任务工具失败后重复调用次数 | 明显下降 |
| 因同类错误导致的 token 消耗 | 下降 |
| 误熔断反馈 | 可解释、可配置豁免 |
| Harness run 成功率 | 上升 |

耗时：1 周。

## 6. 风险与规避

| 风险 | 表现 | 规避 |
|---|---|---|
| 投影字段漏掉模型后续需要的信息 | 模型需要再次调用工具 | 缺失字段不失败；保留 top-level keys 和 full result ref；允许 fallback raw |
| 字段路径语法过强导致复杂度高 | JSONPath 实现和安全问题 | MVP 只做简单路径和数组通配 |
| 直接改 eager MCP schema 破坏真实 MCP 调用 | 控制字段传给外部 MCP server | 第一版只给 `invoke_deferred_tool` 加控制字段；eager 只做默认 bounding |
| 熔断误杀可修复错误 | 模型第二次修改参数即可成功 | 第 1 次 observe，第 2 次 warn，第 3 次 halt；debug 才首错停 |
| 错误指纹过粗 | 不同错误被当成同类 | 指纹包含 toolName、kind、errorType、标准化 message、参数摘要 |
| 错误指纹过细 | 同类错误无法聚合 | 去除路径用户段、UUID、时间戳、行号等噪音 |
| 完整结果 sidecar 泄露敏感数据 | 大结果写入可读文件 | Phase 3 做受控目录和专用读取工具；默认 trace 不上传完整结果 |

## 7. 推荐最终落地顺序

第一周建议只做最小闭环：

1. `result-projection.ts`：字段投影 + bounded preview。
2. `invoke_deferred_tool`：新增 `required_fields`、`max_result_chars`。
3. `failure-fuse.ts`：失败指纹 + 计数 + 阈值决策。
4. MCP awaited `isError` 和通用 tool awaited result：接入 failure fuse。
5. 单测和日志。

第二周再做增强：

1. eager MCP 默认 bounding。
2. 跨 turn / skill 级熔断策略。
3. debug fail fast UI/配置。
4. trace metadata。
5. sidecar/managed result store 设计评审。

## 9. 总体判断

这两个洞见都是高性价比。

工具结果投影的关键价值是让模型只看当前任务需要的信息，减少上下文污染；错误熔断的关键价值是让平台能识别“继续重试已经没有意义”的状态，及时停下来并给出可解释诊断。

从工程实现看，当前 CmbCoworkAgent 已有足够多的基础件：MCP result-utils、Workflow sidecar、ToolFailureSignal、PostToolUseFailure、Hook halt、Workflow retry cap。真正要补的是一个统一的 projection 层和一个统一的 failure fuse 层。两者都可以低侵入落地，适合先做 MVP，再扩展到完整 Harness/SkillOps 闭环。
