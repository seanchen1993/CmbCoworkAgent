# Mods 公共底座与创造者收敛最终方案

日期：2026-10-29。适用分支：`codex/mods-v2`。应用版本固定 `2.0.0`。

本文是对两份输入文档的合并评审与实施建议，不代表新增能力已经实现，也不授权立即实施全部新增范围。当前已授权的修复和真实使用验收继续进行；新增公共能力按本文分期实施。

评审输入：

- `C:/ai/新建文件夹/mods-creator-platform-plugin-hooks-transformation-plan-2026-10-16.md`
- `C:/ai/新建文件夹/platform-mods-batch-navigation-requirements.md`

## 1. 最终结论

两份文档的基本方向合理，应合并为一套方案，而不是叠加为两个重构项目。

第一份文档用于约束创造、组合、配置、知识、校验、状态和交付的完整性；其中不少原计划能力已经有实现，必须更新现状，不能再次从零建设。第二份文档提供了明确的公共能力验证场景：任务持续运行时，通过 Mod 选择插件自有目录，查看相对固定起点的真实代码变更。该场景应作为下一轮底座补齐的首个完整交付。

当前问题不宜表述为“Mods 大部分基础能力尚未开放”。更准确的分类是：

1. 已有并开放：执行、文件、模型、工具、事件、Mod 状态、公共能力调用与订阅、Surface、部分项目检查与恢复等。
2. 平台已有但缺少合适的 Mods 公共入口：部分 Git 查询、IDE 打开、项目与 Feature 的丰富只读查询。
3. 必须补充的公共机制：运行期间受宿主约束的只读视图交互、外部目录与仓库引用、跨版本代码检查的生命周期。
4. 已开放但创造者使用不可靠：能力引用错误、旧说明选择兼容路线、诊断不足、候选与执行结果混淆。
5. 合理的插件责任和安全边界：业务状态图、调度、唯一 writer、未知脚本语义、外部副作用恢复，不能通过增加 SDK 名称自动解决。

不增加 Batch 或 AutoBiz 专用平台 API，不建立第二套任务执行器、业务状态机、权限系统或插件安装器。

| 为创造者改造普通项目模式交互 | 不采用 | 创造者输出标准插件；普通项目模式继续选择插件并执行任务。 |

## 4. 统一架构与责任

沿用一条公共链路：**插件/Mod → 既有 platform 与 Surface → 宿主作用域和权限 → 公共服务 → 原生预览或原执行器**。

| 层次 | 必须负责 | 不应负责 |
| --- | --- | --- |
| 平台公共服务 | 来源与版本、授权、执行域、取消、只读查询、状态提交边界、必需检查、实际操作事实 | 解释 Batch/Feature 的业务状态图、业务字段和知识含义。 |
| Mods | 界面、观测、变换、公共动作、能力组合；按权限调用宿主服务 | 凭名称或普通 JSON 绕过检查、替另一插件提交业务状态。 |
| 插件 | 模块选择、业务流程、配置声明、知识规则、产物含义、业务校验、唯一 writer 和适配器 | 向平台塞入特定业务硬编码，或把成功显示文案当作事实。 |
| 创造者 | 理解目标、发现真实能力、生成或修改源码、检查影响、组织原生试用与交付 | 代用户批准、发明接口、复用过期授权、重放未知副作用。 |
| 普通项目模式 | 选择插件、填写必要配置、开始任务、查看结果和必要确认 | 要求用户掌握模块清单、协议版本、源码目录或内部组装工具。 |

原生 Git 面板与 Mods 预览可以共用提取后的查询服务和展示组件，权限和目标由各自入口绑定。不能直接把一个按主聊天 cwd 执行的旧 IPC 暴露给外部目录。

## 5. 只读交互执行域

### 5.1 查询与执行分开

在既有平台能力机制内增加明确、可校验的 query 语义。现有 effect action 默认行为保持不变，不因升级自动变成免队列。

- query：宿主认可的只读查询或在同一受限域内执行的界面回调，不申请业务线程运行 lease，不等待 Workflow 结束。
- effect：进程、模型、业务写入、任务控制等，仍进入原队列、授权及检查链。
- query 的短期去重与取消不等于业务动作的持久幂等账本；界面每次筛选不能生成一条业务任务或安装操作。

协议版本和方法名称在实施阶段冻结；本文不把拟议名称标为已可调用接口。旧严格解析器不得接收未经版本协商的新字段。

### 5.2 可允许和必须拒绝

只读域允许：已授权且纳入该域的文件读取、宿主查询服务、筛选和选择、重绘、关闭，以及当前视图私有的少量偏好。偏好复用现有存储后端，但作用域由宿主强制隔离，不能整体放开 `store.set/state.set`。

只读域拒绝：通用进程、模型、MCP、任意工具、业务文件写入、业务状态发布、启动/取消任务、Git 写入及未适配的能力调用。拒绝后不得自动改走有副作用的通道。

约束必须沿直接调用、间接 `platform` 调用、异步续接和取消信号传递。静态扫描和作者的 readonly 声明只能用于检查，不能代替运行时限制。原生目录授权、复制或打开 IDE 等用户意图型操作另有窄入口，不借 query 获得任意系统操作权。

## 6. 公共代码检查服务

新增一个公共宿主服务，承载目录绑定、变更列表、单文件内容与 patch、原生预览等职责。经既有 capability 桥开放，必要时增加类型化薄封装，不建设平行权限或执行框架。

### 6.1 外部目录与仓库身份

用户显式操作后，由原生授权入口签发不透明的只读引用，绑定实际会话、Mod 来源、授权代次、规范化目录身份和真实仓库身份。

- 插件提供的路径、manifest 或 Workflow 参数不是授权。
- 已有匹配且有效的授权可以复用；不向其他插件、其他聊天隐式扩散。
- linked worktree 的 commonDir 可在工作目录之外。宿主读取查询必需的 Git 元数据，不向 Guest 开放 commonDir 或其他 worktree 的任意文件权限。
- 原 fs 的工作区边界保持不变；目录引用不登记平台管理 worktree，不切分支，不修改主会话 cwd。
- 目录替换、junction 转向、撤权或来源变化使引用失效。正常提交导致 HEAD 变化只改变比较版本，不应每次都要求重新授权目录。
- 引用及本机绝对路径不进入可移植插件，换电脑须重新绑定。

### 6.2 首期比较范围

首期完整支持：**冻结 baseline commit → 当前 working 的已跟踪累计变化，另列未跟踪文件**。

baseline 由插件提供，宿主验证它可在授权对象库中解析为 commit 后固定为实际对象标识。缺失或不可读时明确报错，不猜 main、不悄悄改用 HEAD、不自动 fetch。合法比较不必强制 baseline 是当前 HEAD 祖先。

列表和预览明确显示目录、比较模式、baseline、实际 HEAD、读取时间和完整性。未跟踪文件不混入普通 diff 的统计；新增、删除、重命名、类型变化、冲突和二进制各有明确状态。冲突可显示当前内容和限制，不能伪装成普通完整 patch。

后续再开放 `base-to-head`、`head-to-index`、`index-to-working`。未支持模式明确拒绝，不降级到另一个模式。

### 6.3 安全查询与有界内容

宿主使用固定 argv 和受控 Git 可执行程序，不接受作者提交的 shell 或任意 Git 参数。禁用外部 diff、textconv、fsmonitor、交互、可选 index 刷新等可能执行程序或写入的行为；不执行 checkout/add/commit/merge/reset/clean/fetch。

查询只处理当前选中目录和文件，异步运行，有时间、条目和编码后字节边界；重命名分析也需有界。首期列表分页、单文件惰性读取、大内容明确截断；patch 的复杂跨页定位后续单独设计。截断不是“没有其他变化”，二进制不是解码失败后的空文本。

文件名用无歧义格式解析，覆盖中文、空格、引号、换行与不同大小写语义；读取版本文件同时约束路径和符号链接，不能由 Guest 直接拼 Git 元数据路径。

working、baseline、HEAD、index、历史对象内容与 patch 的每个入口均复用已有文件访问和敏感路径/内容策略。目录授权不覆盖已有明确拒绝；不能通过 Git 输出、重命名旧路径或历史版本绕过文件权限，也不能只过滤工作目录当前文件。

预览只使用受限文本/代码/Diff 组件，不接受任意 HTML。源码和 patch 默认不进入模型上下文，用户显式引用时另走原上下文权限与容量规则。

### 6.4 一致性、取消与生命周期

结果绑定视图实例、目录引用、比较身份和请求序号。比较身份包含实际仓库、baseline、HEAD，以及该次读取能验证的 index/working 变化信息；不声称获得了整仓库事务快照。

翻页、单文件 patch 和版本读取必须校验比较身份。变化则返回过期或要求刷新，不能把不同时刻的页拼成完整结果。加载失败、无变化、目录消失、权限不足和内容截断分别表达。

关闭面板、切聊天、换目录、停用插件或撤权时立即撤销旧结果发布权，停止发起后续读取，并向后端取消。底层进程必须受期限约束并尽力物理停止；不能只在前端忽略回包，也不能承诺任意 OS I/O 立即消失。

P0 使用手动刷新。可见期间低频刷新、退避和合并在 P1 交付，避免首期引入多仓库扫描与监听风暴。

普通刷新失败时可保留标明过期的旧内容。撤权、来源失效、跨会话或目录身份失效则必须清除该视图已呈现的受限正文并使相关敏感内容缓存失效，不能仅禁止迟到回包、继续展示旧内容。必要审计保留操作身份与拒绝事实，不借缓存恢复旧读取权。

### 6.5 清理后的阅读

live directoryRef 随目录清理失效，首期显示目录不可用，不重建目录、不恢复任务。

P1 如需阅读已提交版本，单独建立明确授权的 repository/object 引用。仅当原对象库仍存在且对象可读时进入标明来源的历史模式；对象缺失就报错，不自动 fetch。历史阅读权不从过期的 live 引用偷渡获得。

## 7. 项目投影、知识与检查覆盖

这些能力与代码检查共享来源、版本、新鲜度、取消等公共约束，但使用各自的 schema 和原服务，不形成万能 JSON 接口。

### 项目与 Feature 只读投影

从原权威项目服务开放精简查询、筛选、分页和订阅。优先当前授权项目，跨项目查询必须显式授权；不能让 Mod 以提供他人 threadId 的方式访问。状态仍由原 writer 持有，投影不能独立推进阶段。

### 版本化知识与 provider 缓存

只对实际受约束的只读 provider 实施有界缓存和并发单飞。缓存键至少包含来源摘要、有效配置修订、目标身份、角色、知识版本和输入；权限或版本变化必须失效。

没有可靠版本的可变 provider 不承诺长期缓存，可采用明确新鲜度策略并记录降级。脚本不能因自称只读而进入免 lease 查询域；失败、取消、unknown 不缓存为成功。

展示缓存不能替代阶段提交前的产物摘要、必需检查和原 writer 读回。上下文装载回执只证明交付事实，不证明模型理解或遵守。

### 检查覆盖报告

明确普通工具、Mod 进程、Host action/check 三条链分别覆盖哪些平台限制、业务 Guard 和普通 Hooks。复用已有必需检查与 StageCheckReceipt，不再创建另一套业务成功凭据。

最终参数变化后检查，必需检查在可短路扩展链之外执行。异常、超时、缺项、取消和未知都不等于通过。普通 Hook 的成功不能提升为不可绕过检查。

## 8. 创造者、插件与配置的统一闭环

普通用户路径为：**描述目标 → 看到候选 → 必要配置或确认 → 直接试用 → 对话修改 → 保存插件 → 开始使用**。能力目录、模块 ID、版本锁和源码工具是创造者的内部工作，不要求用户先选择技术路线。

1. 发现只返回真实实现及当前限制，区分已安装、已授权、需配置、缺能力和不支持。
2. 创造者使用完整真实引用：能力的 provider/id/version 与 action id 不混同，不能从插件版本猜协议版本。
3. 原创项目优先当前原生可组合源码；兼容格式用于已有来源，不由旧技能说明将新项目导向另一套格式。
4. 编译诊断包含受限文件、字段位置与具体原因，不回传凭据、完整源码值、堆栈和任意异常文本；未知错误不机械重试。
   工具输入应按动作提供足够窄的结构与必填项，返回当前精确草稿身份、修订和下一步参数；避免用一个包含大量无关可选字段的工具让模型反复猜测。参数缺失可以返回可读候选供重选，不能擅自补成另一个目标并执行。
5. 候选、试用、组合、业务运行、保存与导出分别保留原服务事实，以操作 ID 和精确源码版本关联展示，不另建能覆盖业务成功的状态机。
6. 保存确认、结果和“开始使用”在主流程显示；高级记录按需展开。已保存旧版与未保存的新草稿必须区分。
7. 局部修改按依赖影响复验。修改进度显示不重跑业务；修改契约、输入、校验或 writer 必须复验关联阶段和下游失效。
8. 源码热替换遵守已有安全切换点；模块变量重载、试用数据与正式数据的关系必须明确。需要保留的数据由插件按声明持久化，不承诺自动迁移任意 JS 内存。
9. unknown 只允许核对实际结果、明确未发生后的重新准备、或用户确认的后续处理；重启不能恢复旧执行权或自动重放副作用。

配置使用原值、敏感项与表单服务。插件定义业务字段与默认策略，创造者提出变更，用户绑定环境和秘密；平台校验作用域、必需项、覆盖权限和冻结版本。普通值按声明的默认/用户/项目/单次覆盖规则解析，强制约束单独校验。数组、空值和删除不采用未经声明的深合并。导出不携带凭据、本机授权和活动会话。

Hooks 按平台强制限制、必需业务 Guard、普通事件处理分别保留；不要求把旧脚本全部改写成 Mod。旧流程由适配器明确其状态图、知识、产物和 writer，未知语义不能靠模型推断后宣布转换等价。

## 9. 分期实施与放行条件

| 阶段 | 交付范围 | 依赖与放行条件 |
| --- | --- | --- |
| P0-A：基线与协议 | 当前能力/限制清单；query/effect 执行语义、只读拒绝集合、协议兼容与错误模型 | 既有项目、插件、Surface 和原队列回归不变；不重复建设已有底座。 |
| P0-B：服务底座 | 目录授权引用；固定只读 Git 查询；比较身份、取消与有界结果 | 越权、目录替换、错误仓库、baseline 缺失、特殊文件名、冲突和大文件反例通过。 |
| P0-C：运行中视图 | query act、必要的受控 Surface 冷启动、通用预览；保留原 open/view 基础 | 真实业务 lease 持有期间仍可打开、选择、看 Diff；嵌套副作用被拒绝。 |
| P0-D：创造者接入 | 真实目录发现、完整类型与可复用示例；生成或组合导航 Mod；准确诊断与原生确认 | 不虚构 API；不要求技术管理页；保存后普通用户可直接使用。 |

| P1-C：历史对象阅读 | 明确授权的 repo/object 引用与历史预览 | 清理后 live 引用失效；对象授权、缺失和 GC 路径明确。 |
| P2：复杂适配 | 按真实需求扩展恢复、旧插件迁移与外部动作适配 | 明确资源支持范围和唯一 writer；不承诺任意插件一键恢复。 |

## 10. 验收矩阵与性能预算

### 必须通过的真实链路

Workflow 持续运行 → 打开 Mod 导航 → 选择插件自有仓库/Batch → 首次必要目录授权 → 查看变更列表 → 查看单文件 Diff/内容 → 文件发生真实变化 → 手动刷新 → 切 Batch → 关闭。其他任务不中断，原项目模式继续可用。

同一协议至少接入两个独立场景：一个为多仓库开发批次导航，一个为不含 Batch/AutoBiz 数据结构的目录变更审阅 Mod。AutoBiz 可作为复杂兼容案例，不能是唯一证明。

### 正反例

- 两个目录有同名文件、100 次快速切换且故意倒序回包，旧内容覆盖新选择为零。
- 已提交、暂存、未暂存、未跟踪、删除、重命名、冲突、二进制与超长行有准确状态；仅对已交付模式作保证。
- baseline 不可读不替换；路径越界、跨会话、跨来源、junction/目录替换与撤权均拒绝。
- 运行中变更使比较或游标过期；旧结果可标过期保留，不拼成完整新结果。
- 关闭、停用、撤权后旧请求完成，不发布、不复活视图、不持续刷新；撤权或身份失效还清除当前受限预览并使相关缓存失效。
- 只读回调经同步、异步、间接能力尝试进程、模型、MCP或业务写入，均在实际边界拒绝。
- 目录被清理只显示不可用；不自动创建、checkout、fetch 或恢复任务。
- 预览前后原任务状态、业务 manifest、lease、阶段凭据和 Git index 不因预览改写；不能把并行业务自身变化误算成预览写入。
- 保留必需 Hook 拒绝、坏 schema、上游输入变化、unknown 对账、重启恢复与普通输入/停止操作的既有回归；本期新增查询、引用和预览的相应反例必须通过。不把所有历史链路新增适配列为代码检查 P0 前提。
- 保留独立 Mod、多个 Mods 组合、非 AutoBiz 项目创建修改三条既有创造者链的回归；P0 新增验收聚焦代码导航 Mod 的发现、生成/复用、试用与保存，编译夹具不能代替真实运行。

### 首期拟定预算

以下是待基线验证的验收预算，不是已测得收益。测试报告记录 OS、CPU、内存、磁盘、Git 版本、源码和构建摘要、样本规模与并发数。

- 本地选择反馈及加载态 p95 不超过 150 ms，不等待业务 lease。
- 约定的 2,000 个变更文件压力样本，冷/热首屏分别统计，首屏 p95 目标 2 s；不以遗漏文件达标。
- 列表建议首屏 100 条；每页编码后字节和总在途内存上限须与现有 IPC/QuickJS 桥容量联合确定，预留 JSON 编码余量。总文件量不因分页被伪装成全部结果。
- 每个视图最多一个列表读取和一个当前文件读取；重复刷新合并，新选择取消旧文件读取，不扫描全部 Batch。
- 关闭后立即失去发布权，1 秒内停止发起新查询；后端取消和超时的物理收敛单独记录。
- Electron 主线程不执行同步 Git/目录扫描。记录排队、Git I/O、返回字节、渲染、取消和过期率，避免只报总耗时。
- P0 的重复查询必须单飞合并；P1-A 对适用的版本化 provider 再验收 20 个相同输入并发请求最多执行一次，版本、配置或授权变化后不得命中过期成功结果。后者不作为代码检查 P0 的新增前提。
- Token 收益由同目标的模型请求数、重复上下文与重试前后对比测得，不承诺固定节省比例；代码预览不默认注入模型。

mock 用于可控错误、长内容和回包顺序；真实 Git、目录权限、原生预览、业务 lease 与保存使用链必须由实际运行验证。

## 11. 兼容与发布

应用版本保持 `2.0.0`，协议版本独立演进。由于应用版本固定，**不能只靠“最低应用版本 2.0.0”判断新能力是否存在**；必须使用实际能力/协议发现、构建身份和安装/执行兼容检查。

旧 Surface 与普通 action 保留原语义；新 query 语义按明确版本开放。对必需新语义，旧客户端必须在安装或执行前拒绝，不能假定它会理解旁挂文件或未知字段；无法证明拒绝路径时，不分发要求该语义的包。

新增服务先按能力开关小范围启用，迁移到共享服务的原生 Git 面板单独回归。回退关闭新入口，不迁移业务状态、不恢复旧执行授权、不自动重放操作。发布和构建仍须遵守当前用户指令；本文本身不触发构建、安装包或 GitHub Actions。

## 12. 实施完成的判断

最终目标不是增加接口数量，而是：用户能在不理解内部协议的情况下，通过创造者做出可用扩展，安装后直接使用；开发者通过公共服务实现界面、观测和组合，无需为每个业务功能修改主程序。

对本文首期场景，只有真实任务运行期间的导航、外部目录授权、变更列表、Diff、刷新、取消和隔离全部通过，才能宣布“Mods 已支持运行中查看插件自有仓库变更”。当前已有执行、状态或 Surface 能力不能替代这项结论；反过来，这项专项尚未完成也不意味着既有 Mods 底座全部未开放。
