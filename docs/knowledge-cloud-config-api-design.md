## 1. 知识库身份与配置

- `id_key` 是不可变的知识库内部标识，用于项目绑定、本地状态与目录定位。不得复用已分配给其他知识库的标识；服务端与 APP 校验其可安全用于目录，不得包含路径分隔符、`.`、`..` 等非法目录值。
- `name` 是全局唯一的业务名称，数据库使用 `UNIQUE(name)`，不再使用名称加分支的联合唯一约束。名称不能为空，不允许首尾空白，大小写不同视为重名；数据库以当前 `utf8mb4_general_ci` 的实际比较规则为最终约束，不另建客户端判重算法。
- 一期人工维护 SQL 时提供符合要求的名称。查询接口只校验，不 trim、不改写数据库、不改写返回名称；客户端直接使用返回名称，不做 trim、大小写转换或其他额外处理。不符合规则的数据报配置错误。
- 同一仓库不同分支可配置成不同知识库，分别使用不同 `id_key` 和名称。例如“支付研发知识库”对应 `main`，“支付研发知识库（试验版）”对应 `develop`。不增加仓库加分支唯一约束。
- 同一 `idKey` 可以修改名称、仓库地址及分支，项目绑定不变。客户端始终按最新成功查询得到的配置执行更新，不维护两套来源定义，也不持久化来源哈希或 commit。
- `gitRef` 表示分支；沿用现有空值回退 `main` 的约定，服务端统一返回有效的非空分支，客户端不再另行推导服务端组织规则。
- 时间均采用 GMT+8 `YYYY-MM-DD HH:mm:ss`，不用 ISO T 格式。

## 2. 服务端过滤与查询接口

`POST /devclaw/knowledge-config/query`，请求头 `Content-Type: application/json`、`Accept: application/json`。

APP 通过现有 `getUserInfo()` 取得 `userinfo-models.json` 对应身份，只发送以下三个字段，不上传整个身份文件或登录令牌：

```json
{
  "sapId": "00012345",
  "pathName": "总行/信息技术部/a组",
  "originPathId": "root-id/it-id/team-a-id"
}
```

三个字段均为字符串，字段值按现有身份信息传递，缺失值传空字符串。服务端负责组织匹配，客户端不做组织过滤。初始服务端规则沿用完整组织路径段精确匹配；后续可以在服务端调整而不改 APP 请求结构。无有效组织路径时只返回全局库。请求中身份字段本身不替代企业服务已有的身份认证机制。

成功返回的是**当前用户可见知识库的完整快照**，不是数据库全量、不是增量。响应不返回 `enableOrg`、`devopsId`、`devopsKey` 或其他未约定列。字段白名单及完整契约见服务端接口定义。

```json
{
  "code": 200,
  "message": "success",
  "data": {
    "items": [
      {
        "idKey": "kb-payment-main",
        "name": "支付研发知识库",
        "description": "支付业务知识",
        "repoUrl": "https://git.example.com/payment-knowledge.git",
        "sshUrl": "git@git.example.com:payment-knowledge.git",
        "gitRef": "main",
        "ownerName": "示例发布人",
        "ownerId": "example-owner",
        "customConfig": "{}",
        "createdAt": "2026-10-21 10:00:00",
        "updatedAt": "2026-10-21 10:00:00"
      }
    ]
  }
}
```

业务结果均返回 HTTP 200，只有 `code=200` 且完整数据合法才算成功。空表或当前身份没有匹配记录返回 `items:[]`，这是明确的空配置。请求超时、传输失败、HTTP 非 200、非 JSON、非成功业务码、响应字段无效，都不得覆盖上次有效配置或标记记录失效。

| code | 含义 | APP 行为 |
| --- | --- | --- |
| 200 | 成功，包括空配置 | 接受当前身份的完整可见快照 |
| 40001 | 请求格式错误 | 保留状态，记录错误 |
| 50001 | 读取配置失败 | 保留状态，等待正常定时更新或手动操作 |
| 50002 | 配置无效或超过响应限制 | 不接受部分快照，保留状态 |

服务端不分页、不截断、不增加 revision 或增量协议；响应限制复用服务现有统一配置。过滤结果中只要有无效记录就整次报错，不能偷偷跳过，否则客户端会误认为对应库已失效。

## 3. 本地状态与双目录

状态文件仍为 `<getCmbCoworkAgentDataRoot()>/knowledge-state.json`，默认 `~/.cmbcoworkagent/knowledge-state.json`。仅登记曾对本机用户可见的库，不保存所有组织配置、组织匹配规则、令牌或 DevOps 凭据。

每个知识库维护两个独立 Git 克隆，仓库和目标分支均使用该记录的最新云端配置：

```text
<数据根目录>/knowledge/<idKey>/read/     普通会话读取与默认内容预览
<数据根目录>/knowledge/<idKey>/write/    知识沉淀会话工作区
```

路径由框架计算，不写入项目元数据，不允许云端直接指定本机路径。两个目录独立更新，不在本机互相复制内容。

目标状态结构如下。`workspaces` 必须是数组，每种 `role` 恰好一项；不得依赖数组顺序：

```json
{
  "schemaVersion": 1,
  "knowledgeBases": [
    {
      "idKey": "kb-payment-main",
      "type": "public",
      "name": "支付研发知识库",
      "description": "支付业务知识",
      "repoUrl": "https://git.example.com/payment-knowledge.git",
      "sshUrl": "git@git.example.com:payment-knowledge.git",
      "gitRef": "main",
      "ownerId": "example-owner",
      "ownerName": "示例维护人",
      "visibility": "visible",
      "lastSuccessfulSyncAt": "2026-10-21 10:00:00",
      "workspaces": [
        { "role": "read", "status": "success", "lastError": null },
        { "role": "write", "status": "blocked", "lastError": "存在未提交或未推送的本地改动" }
      ]
    }
  ]
}
```

- `ownerId`、`ownerName` 保存查询接口返回的维护人编号与姓名，分别对应数据库的 `owner_id`、`owner_name`；配置刷新时更新，历史不可用记录保留最后可见时的信息。卡片显示一个“维护人：姓名/编号”tag，只有一项有值时只显示该项，都没有时不显示。
- `type` 是知识库级别的必填字段，目前仅支持 `public`。服务端下发的知识库由客户端写入 `"type": "public"`；该值表示知识库类型，不代表全员可见，可见范围仍由服务端过滤决定。接口和数据库无需增加此字段，历史不可见记录也保留该类型。
- `visibility` 仅为 `visible` 或 `unavailable`。成功接受快照后，本次返回的记录为 `visible`，本地原有但本次未返回的记录为 `unavailable`，统一展示“已不在可用”，不区分删除和组织变化。不可见记录保留最后可见配置及本地文件，停止自动和手动同步。
- 目录 `status` 为 `not_downloaded`、`success`、`failed`、`blocked`。每个目录只有一个状态；`lastError` 只补充原因，不另建失败布尔值。`blocked` 表示本地未提交、未推送改动或冲突等导致同步暂停。
- `syncing` 与运行中的会话占用仅在内存维护，不落盘；不持久化 commit 或来源哈希。状态文件的最新同步结果供界面展示，下一轮仍统一处理全部当前可见库，不按失败状态创建额外调度任务。
- `lastSuccessfulSyncAt` 是知识库级别的最近成功更新时间，使用 GMT+8 `YYYY-MM-DD HH:mm:ss`。只有同一次操作的 read/write 都成功（包括完成检查后确认已是最新）才写入；部分成功、失败或暂停均保留原时间。没有成功记录时不写此字段，卡片显示“暂无成功更新”。配置刷新、来源变化及变为不可见不清除已有时间。
- 最新配置的仓库或分支变化时，对受影响目录先取消旧 `success` 状态，再尝试同步；不得出现新配置仍配旧成功状态。失败时保留文件但写入 `failed`，遇到本地改动写入 `blocked`。成功才写 `success` 并清除错误。
- 文件由框架统一读写并保留现有原子写入方式。单个目录同步结果只修改对应记录的对应 workspace，不覆盖另一目录结果或最新配置。

状态文件 `schemaVersion` 固定为 `1`，直接使用上述结构。不考虑旧格式兼容，不实现状态迁移、旧字段适配或版本升级逻辑；不自动搬迁或删除原有本地目录。

## 4. 统一更新与手动重试

1. APP 启动或身份就绪后后台更新一次，之后沿用 90 分钟周期。身份更新复用现有刷新入口。网络和 Git 异步执行；云端查询 5 秒超时，上一轮未结束则跳过本轮，退出时停止定时器。
2. 一轮更新先查询、校验完整快照，再按 `idKey` 合并最新配置和可见性，然后分别同步所有可见库的 `read`、`write`。若配置查询失败，保留配置，仍可按上次有效配置执行本轮 Git 更新；没有有效配置时不启动 Git 更新。
3. 复用现有 Git 远端检查、异步 clone、HTTPS 20 秒超时和 SSH 兜底。按最新记录的仓库、分支检查实际 Git 目录，不能仅因 `idKey` 相同就认为内容已是最新。无变化且可复用时返回成功；有变化时在临时目录 clone，成功后替换对应目录。
4. 两个目录分别检查本地未提交变更、未推送提交及冲突，存在时暂停该目录更新，保留文件并记录 `blocked`，不得自动 stash、merge、rebase 或覆盖。不论一个目录失败还是暂停，都继续处理另一个目录及其他库。
5. `write` 有正在运行的沉淀任务时，复用现有 Thread 运行状态暂停它的更新，`read` 仍正常更新，包括普通会话正在运行时也允许更新 `read`。不引入锁、队列或另一套调度系统。运行占用属于临时状态，不改写为持久化失败。
6. 更新失败保存标准用户提示，原始错误去除凭据及终端控制字符后仅写日志，等待下一轮正常更新；没有错误专用定时器。“检查全部更新”走同一完整流程；每个知识库只提供一个“拉取更新”按钮，点击后按最近有效配置依次尝试该库两个目录，不额外拉取云端配置，不触发其他库同步，不提供分目录更新或重试按钮。
7. 操作完成后用一条结果文案说明两个目录的更新情况。均成功时显示“知识库更新成功”；一个成功、一个失败时，例如显示“读取内容更新成功，沉淀工作区更新失败：<原因>”；存在本地改动时显示对应目录暂停更新的原因，不影响另一个目录结果。只有两个目录都在本次完成远端检查且无需更新时才提示“已是最新”。目录失效应显示未下载或目录不可用，不因落盘状态为成功就直接使用。

## 5. 项目选择与普通会话读取

- 创建、编辑项目的界面仅允许单选知识库，也可以暂不选择；下拉框只列出可用知识库，选择后替换当前选择并关闭，提供“清空选择”按钮。底层仍支持多库绑定和参数传递，已有多库绑定不会因打开或保存表单而自动清空。项目元数据仍为 `knowledgeBaseIds: string[]`，仅保存稳定 `idKey`；未配置的旧项目按空数组处理，不自动推导或补绑。
- 创建、编辑项目的选项只展示 `visibility=visible`、`read.status=success` 且读取目录有效的库。下载失败、未下载和历史失效等状态只在公共系统约束 Tab 的对应卡片展示。
- 编辑项目不把不可用绑定加入可选列表，也不在那里展示历史状态。用户未主动更换知识库时保留原 ID，不得因为选项列表缺失就自动清空。
- 解析已有绑定时，不要求当前可见，但要求状态文件存在该 ID、`read.status=success` 且读取目录有效。按项目选择顺序逐项解析，跳过不满足条件的库；全部不可用时返回 `[]` 并显示 toast“项目绑定的知识库当前不可用，本次会话未加载知识库”；部分不可用时显示“部分项目知识库当前不可用，本次会话仅加载可用知识库”，不阻断会话。不回退旧文件、插件目录或其他库；未绑定时不显示该提示。
- `session_context_inject` 模板包含 `${knowledgePath}` 时，框架传入 JSON 数组，每项为 `{ "id": "服务端idKey", "name": "知识库名称", "path": "read目录绝对路径" }`。数组按项目选择顺序包含所有可用绑定，整个数组作为 `--knowledge-path` 的一个参数，使用现有参数数组执行方式；模板无占位符则不追加参数、不另行注入。
- 插件未配置占位符时保留现有兼容性提示，不阻止项目创建和编辑。插件解析多个知识库的清单和具体内容，不同知识库的同名系统或部署单元均保留，框架不推导或更新 `supported_deploy_units`。

## 6. knowledge_config 知识沉淀会话

知识沉淀使用插件现有 `knowledge_config.sync_type=invoke_session` 与 `nextAction`，但工作目录统一由框架按项目绑定解析：

```text
项目只有一个绑定时直接使用；多个绑定时在沉淀对话框选择目标 idKey
  → 本地 knowledgeBases 中对应 idKey
  → workspaces 中 role=write 的记录
  → <数据根目录>/knowledge/<idKey>/write
  → createThread({ workspacePath: write绝对路径, ... })
```

- 目标必须属于项目绑定，不能静默使用第一个知识库；同步中的目标不可选择，其他有效目标仍可使用。
- 未绑定知识库时阻断并提示“请先在项目设置中配置知识库”。不会使用插件此前同步的旧路径、`inspectCommands.<platform>.knowledge_path`、项目代码目录或空工作区作为替代。
- 沉淀目录首次未下载、无效，或没有可用的已完成克隆时阻断，提示前往公共系统约束 Tab 下载或处理；不能把临时克隆目录传给会话。
- 每次发起新的沉淀会话前，针对实际 `write` 工作区检查未提交变更，包括暂存、未暂存、未跟踪文件及未解决冲突。存在时先 toast 提示“知识沉淀工作区存在未提交的变更，本次会话将继续使用该工作区”，然后照常创建会话，不要求确认，也不清理改动。
- 此规则允许因本地改动而同步暂停的有效 `write` 目录继续用于沉淀。`write.status=blocked` 不单独成为阻断理由；只要原工作区仍有效且不是正在替换，就按上述提示继续。仓库或分支尚未更新成功时不再增加来源不一致的阻断规则；Tab 展示当前同步状态和错误，沉淀会话使用现存工作区，提交目标仍是它实际的 Git 分支，不增加配置分支与实际分支不一致的提示。
- 非本地改动导致的同步失败，只有仍存在此前完成克隆的有效 `write` 工作区时才可继续使用；未提交变更检查照常执行。检查异常应提示具体原因，不伪报工作区干净。
- `write` 正在同步替换时沿用现有忙碌提示，不排队；创建前和实际执行时复用现有入口检查。沉淀任务运行期间只暂停该库 `write` 更新。
- write 的本地变更由用户在沉淀会话现有 Git 面板处理，Tab 不新增打开沉淀目录入口。本期不改提交、push 或凭据管理流程。`read` 通过下一轮正常更新或用户手动同步取得远端内容，不将 `write` 未提交内容复制给 `read`。
- 不增加多个沉淀会话之间的互斥，不增加恢复旧沉淀会话时的工作区重检查。未提交变更提示只在创建新沉淀会话前执行。
- 普通插件读取的 `${knowledgePath}` JSON 数组与沉淀的 `workspacePath` 是两种不同参数，分别指向 `read` 与 `write`，不可混用。

## 7. 公共系统约束 Tab 与反馈

- 主列表展示本地状态文件中的全部知识库，以 `idKey` 为卡片标识。名称右侧同一行以小 tag 展示配置分支、汇总状态、最近成功更新时间及不可见标记；名称过长时省略。两个目录都成功时只显示一个“已下载”，状态不一致时显示“部分更新失败”“暂停更新”等汇总状态，具体错误保留在下方，相同原因只显示一次。标题下不展示知识库数量；标题右侧复用通用提示图标及 Tooltip，文案为“知识库将定时自动拉取，可见的知识库由你所在的组织管理。”。
- 默认内容预览读取 `read`，复用现有扫描和 Worker，限制可读范围；提供打开对应 `read` 本地目录的入口。预览不提供单独刷新按钮：每次展开重新读取，单库、全部及定时同步完成读取目录的处理后，展开中的预览自动刷新。使用内存中的预览修订计数通知界面，不落盘，不因本地列表每 3 秒轮询就重复扫描。
- 每张知识库卡片只提供一个“拉取更新”按钮，统一更新 read/write；通过结果文案说明部分成功、失败或暂停，不增加分目录操作按钮。`unavailable` 卡片显示“已不在可用”，悬停提示“该知识库对您所在组织不再可用”，只允许查看或打开已有本地内容，不提供同步；不删除本地文件。绑定项目仍按各用途的目录可用规则解析。
- Git 异常优先根据明确的系统错误码识别；退出码不能区分原因时，结合 Git 固定错误信息，转换为认证、权限、仓库不可访问、分支不存在、网络、证书或本机目录等标准提示。HTTPS 与 SSH 均失败时只采用第一个底层异常，不拼接两次原因。卡片和 toast 使用相同提示，不展示命令、临时路径或终端输出；read/write 提示相同时合并显示一条，不同时分别说明。每张卡片展示一个最近成功更新时间。
- 无配置缓存时区分“配置获取失败”与“配置尚未就绪”；成功空快照显示“暂无可用知识库”。后台失败不重复弹窗，错误在页面展示；用户主动操作时明确反馈结果。
- 沿用当前界面打开期间每 3 秒读取本地状态的方式，关闭或卸载时停止；轮询不触发网络或 Git、不弹轮询错误提示。
- 特性创建不再提供拉取公共系统约束按钮，插件更新不触发知识库同步。框架不再读取 `pull_knowledge`，不改插件配置和发布单元列表。

## 8. 本期边界与实施前确认项

本期不实现管理端、插件修改或旧插件内部读取行为验证、增量接口、失败专用重试、自动清理、状态文件兼容与迁移或旧插件目录回退。现有数据库重名数据的处理，需要在获知实际数据后单独确认。DDL 是目标基线，不是线上自动迁移脚本。
