# 启动时独立分析：继续对齐方案

前一阶段：敏感参数。工作目录仍为 `C:/ai/CmbCoworkAgent-mods-v2`，开发分支 `codex/mods-v2`，不改 UAT。整体持续目标不因本阶段完成而停止。

## 用户得到什么

插件可以在开始工作时先做一次独立分析，例如判断项目类型、选择工作方式，再注册自己的命令。新安装后的首次启动和用户明确点击“重新加载当前组合”都可使用这条链。独立分析仍使用用户已配置的模型、原有批准和内容保护。

自动应用参数保持原来的限制：它不会为了试用新参数花费模型额度或执行外部操作。需要启动分析的组件提示用户明确重载，避免后台重复分析或重复副作用。

## 已确认问题

本地 Claude Code 2.1.288 声明同时提供 session.start 和 model.complete/classify/fork，已有模型能力不能仅因调用发生在启动回调里失效。DevClaw 的真正障碍是自己的初始化等待环：

- FunctionModsManager.buildEntry 等待 FunctionSession.start 完成。
- 启动回调调用模型；FunctionModels 为实际请求准备自己的规则。
- 规则再次进入同一 manager.classicEvent，等待尚未完成的 buildEntry；FunctionSession.promptComposition 也会再次等待 start。
- 明确重载目前用 MODS_CONFIG_RELOAD_REENTRANT 立即拒绝，避免死锁，但仍是可适配缺口；首次冷启动也需要处理。

依据是本地 v2/manager.ts、v2/session.ts、v2/models.ts、ipc/mods.ts、v2/model-prompt-frame.ts 和现有真实重载回归。不能简单删掉等待或关闭规则，否则分析会借用旧实例或绕过组合。

## 实现边界

1. 宿主在实际 session.start 调用期间保留私有启动作用域，固定本次 SessionEntry 和会话对象、项目、对话、代码、参数和批准。只覆盖实际启动 Promise，结束即关闭。SDK 输入不能创建这个作用域。
2. FunctionModels 的实际 prepare 已建立私有 independentPromptFrame。通过新增宿主独立模型规则入口，只有这个真实活跃帧、同一启动作用域及实际项目/对话同时匹配，才能进入当前新实例的规则处理。
3. 新入口只接 prompt.compose/section/context/attachment，不重新进入 manager 的普通操作链，不等待原 buildEntry/start，不调用旧实例。其他启动时重入继续明确拒绝。
4. FunctionSession 提取共用的内部规则处理；宿主专用启动入口只在实际启动中使用。普通入口继续等待 start。保留输入/输出校验、内容保护、固定事实、取消、真实批准及来源/参数复核。
5. 启动期间每次模型请求前后核对全部准备的源码与保存版本，不能等待分析回来后才发现另一组件已升级。模型端点、批准 epoch、项目和窗口仍由原模型/重载守卫负责；任何已失效请求不得触发新的 provider 调用或接纳结果。
6. $.prompt.compose 在真实独立分析的活跃帧内读取本次真实提示快照。若原调用没有原生任务身份，只允许这次私有帧和当前处理上下文提供访问；不伪造主任务身份、不缓存到无身份的 WeakMap、不借用旧主任务快照。具有原运行身份时继续核对同一身份。
7. 处理完毕关闭规则帧；过期异步后续不能继续读取该快照。模型规则里再次发起独立模型请求仍触发既有递归拒绝，不能无限调用。新启动回调之后的正常后台资源沿原新鲜入口执行，不保留启动特殊待遇。
8. 只在原允许执行的首次启动和明确重载开放这条适配。自动只读候选仍在 SDK 入口拒绝 model.complete/classify/fork，零 provider 请求；错误保持粘性，不能靠 catch 假装候选可接纳。
9. fork 仍要求真实可复制对话；没有历史就按原结果返回无内容可分析，不创造历史。旧 legacy-v1 与 result-v1 返回形式不改变。
10. 启动分析没有自动重试。明确重载失败沿用“组合已停止”和用户明确重试的规则；普通模型请求的账本、计量、并发与额度界限沿用 FunctionModels。

## 验收

- 首次真实加载、明确重载都能从实际 session.start 完成一次 complete/classify；provider 请求确实包含新实例规则，并且只调用一次。
- 两个组件组合时按新组合的真实顺序处理，旧实例规则不参与；$.prompt.compose 读到本次实际请求，规则改写反映在 provider 输入。
- 具有真实对话快照的 fork 保留原角色和捕获端点；无快照结果仍真实。
- 自动参数应用仍零模型调用；嵌套独立分析、普通重入、旧 startup/frame、取消、撤权又重授、源码或参数变化都验证拒绝和清理。
- 真实 Electron 从导入、填参数、批准、启动到明确重载验证，不用 mock model callback 冒充 provider 通路；回归原重载、参数、普通任务、输入保护和连续任务。
- 两位独立设计评审及实现复审；类型、受控广域、真实桌面和性能证据另写交付账本，然后继续生命周期与其他剩余能力。

本方案已实现，两位独立实现静态复审通过；真实桌面27检查点、受控广域360文件3074项均通过。范围见 mods-startup-model-stage-2026-10-04.md。目前没有认定框架限制。

实现复审补充：原启动处理外层只有5秒总等待，独立模型虽有60秒上限也会先被外层取消。两位评审认可阶段内有界适配，要求整次共享 deadline，不能仅扩大每个 Hook 的等待。实际 start 在 engine.build 前建立独立120秒期限，build 与全部启动回调及派生SDK共享合并信号。到期必须返回明确 MODS_STARTUP_TIMEOUT，不能静默绕过后接纳；不取消原父作用域。QuickJS 的50ms执行片段、5秒窗口累计500ms CPU、内存上限和原取消仍不放宽；没有调用模型的未完成异步启动也在120秒结束。每个启动 frame 同用120秒上限以避免先被5秒中断，整链仍受唯一共享deadline。真实模型请求仍逐次最多60秒，不提供自动重试。实际超过5秒的HTTP响应、原CPU/取消、未完成Hook与build共享超时已经通过。后续继续官方“SDK/下游等待不消耗处理函数自己的预算”的完整等待计量，不宣称两者完全一致。

实现复审发现并已修复：冷启动和静默发现后的首次启动也拒绝同链普通重入；prompt发布后及下一处理函数实际进入前复验私有启动凭据；模型返回后的处理链仍消费完整守卫；来源失效保持粘性，作者捕获错误不能继续写入或接纳旧快照；启动成功返回前再次核验全部事实。新鲜后台入口清除Manager与Session两层启动作用域。真实128个源码文件约1.83MiB的完整启动/重载中位7335.51ms、最大7813.35ms，包含本地HTTP但没有界面绘制；保留完整源码核验，明确记录此成本，不将它说成5秒自身预算对齐。

两位独立评审要求以下实现硬条件：专用入口保留主 manager 的保护与发布链；无原运行身份只匹配本次frame和启动回执；全包守卫必须传入 FunctionModels 的整个请求生命周期，在 provider 调用和结果发布前后继续核对；新增异步 Session 方法纳入 session-facade 活动分类，新鲜后台资源不继承启动特权。还必须覆盖 registrationOnly 冷发现之后 session() 的真正首次 start，不能只包 buildEntry 一处。私有模型帧固定实际请求身份，启动规则回执匹配 exact entry/session/frame/request；prepare结束后关闭frame，provider阶段仅使用已捕获的全生命周期守卫，不假复活规则帧。
