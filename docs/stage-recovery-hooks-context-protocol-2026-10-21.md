# 阶段恢复的 Hooks、配置与上下文协议

## 适用范围

本文说明 Host 管理状态的项目阶段恢复。平台保留原项目的阶段输入，在独立分支中执行，经重新批准后验证实际结果；不会把原会话的批准、执行权限或成功状态复制到新分支。

插件自行管理状态的项目还需要插件恢复适配器。业务检查点、看板状态、仓库快照、worktree 对应关系属于该适配器的职责；不能仅凭 Host 阶段快照推断这些业务状态已经恢复。平台代码不按照 AutoBiz 名称选择恢复逻辑。

## 保留的原始语义

- 保留插件、Skill 和 Hooks 的准确资源版本。不会通过删除非空 Hooks 使准入检查通过。
- 原有必需 Hooks 仍进入原生 Hooks 执行流程，保留前后校验、阻断、执行回执和必需校验失败结果。
- 阶段输入绑定配置、知识和上下文的私有快照。配置重新绑定到新工作区；敏感字段由原生配置服务重新密封，旧授权不转移。
- 原项目、原工作区和冻结输入在受限执行时作为只读资源；新分支使用独立工作区和私有可变上下文目录。
- 新分支的产物仍通过原生阶段检查。命令正常退出、Hook 结果对账成功，都不等于业务阶段通过。

含行为的 Shared Mods、MCP、公开动作、外部动作校验等，不在当前通用 Host 恢复准入范围。只包含原生配置元数据的包可以使用配置恢复能力，不需要制造一个无业务意义的可执行 guest。

## 插件声明

`devclaw.stage-recovery.json` 是插件资源的一部分，随保留包参与资源身份核对。

仅提示词 Hooks 使用如下声明：

```json
{
  "apiVersion": "devclaw.stage-recovery/v1",
  "hookExecution": "prompt-only",
  "externalEffects": "deny"
}
```

需要执行命令 Hooks 或上下文脚本的 Windows 包采用以下声明：

```json
{
  "apiVersion": "devclaw.stage-recovery/v1",
  "hookExecution": "windows-sandbox",
  "externalEffects": "network-requires-confirmation",
  "contextProvider": {
    "protocol": "devclaw.context-text/v1",
    "args": ["--stage", "${stageId}", "--workspace", "${workspace}"]
  }
}
```

`contextProvider` 仅在插件原有扩展契约声明了 `context.provider.entry` 时使用。平台执行保留版本中的该脚本；声明不会增加新的任意入口。参数是独立 argv，支持 `${workspace}`、`${stageId}` 和 `${goal}`，不经过 shell 插值。

该协议不是“任何原脚本都已安全”的证明。命令 Hooks 必须符合当前准入约束，例如同步执行、阻断式失败处理；HTTP Hooks、未审查脚本以及需要其他未支持能力的插件会被阻止，并提供缺项诊断。

## 上下文脚本的数据接口

通用脚本通过 UTF-8 标准输入读取一个对象：

```json
{
  "schemaVersion": 1,
  "projectId": "本次项目标识",
  "operationId": "本次阶段操作标识",
  "configuration": {
    "audience": "已解析的普通配置值",
    "selected": ["warehouse", "api"]
  },
  "stageId": "draft",
  "workspace": "本次独立工作区",
  "goal": "本次任务目标"
}
```

`configuration` 只包含冻结时已解析的非敏感保存值和默认值，保留布尔、数值与数组类型。敏感字段和敏感默认值均不传给脚本；知识目录配置字段映射到同次私有知识副本。

脚本还可读取 `DEVCLAW_PLUGIN_DATA_ROOT`、`DEVCLAW_KNOWLEDGE_ROOT` 和 `DEVCLAW_KNOWLEDGE_READONLY`。私有可变上下文目录与冻结输入分离。已有 board 配置的包复用现有上下文适配语义，冻结后再复制到本次执行的可变目录；普通 provider 不需要伪造 board 文件。

平台以隔离 Python 模式执行入口，要求输出非空 UTF-8 上下文文本。输出长度、整体输出量、运行时间和取消均受控。文本通过原有原生上下文发布路径进入模型，并保留任务数据与系统指令的边界；不把脚本输出提升为平台指令。

## 用户确认与实际执行

1. 首次试用时，准备阶段会展示本次上下文脚本策略和精确摘要。即使阶段原本无需人工审批，也会停在确认卡片。
2. 用户单独勾选本次脚本的网络与外部效果说明，再点击“批准并执行”。审批绑定本次 operation、项目版本、保留源码和策略摘要。
3. 创建命令恢复分支时，需要再次确认该分支的精确恢复策略。阶段自己的上下文脚本批准仍独立存在。
4. 更换阶段操作或策略摘要后，确认框恢复为未勾选。旧批准不能沿用；“只检查已有成果”也不能绕过必需上下文脚本。
5. 阶段失败时保留实际失败事实与校验回执。取消必须等待真实受控进程结束；不会把取消显示成外部效果已撤销。

当前实际命令隔离使用应用内置 Codex Windows sandbox 和原生 Job 控制器，拥有独立 TEMP/TMP 与执行目录。沙箱不可用时明确失败，不退化为普通进程。Windows 文件权限保护与网络隔离是不同保证：当前机制不能保证所有网络访问均被 OS 拒绝，因此需要明确单独批准，不能宣传“完全无网络副作用”。

## 未知结果的处理

每次真实命令执行前，平台持久化精确执行意图，绑定分支、阶段操作、源码、Hook 摘要和策略。真实物理结束后，平台先独立持久化本地终态事实，再发布公开回执。

如果进程已经正常结束，但公开回执发布失败，冷启动后的本地对账可以读取原生终态事实恢复该回执。该操作只读本地事实，无需网络批准，不执行原命令，也不把阶段直接标记为通过。随后仍需原生操作终态核对与产物校验，才能结束旧分支并重新准备、批准和执行新分支。

真实取消、断连、输出截断等不能证明外部效果已结束的情况仍保留未知状态，阻止自动重放。外部结果核实必须经过可信插件适配器和相应新批准；Renderer 提供的任意 JSON、产物存在或人工猜测不能替代执行事实。

## 验证边界

回归覆盖真实 Windows 受限命令、原工作区与冻结知识的写入拒绝、真实 stdin 配置消费、取消与进程回收、必需 Hooks 阻断、配置密封重绑定、上下文发布、丢失成功回执的冷对账，以及重新批准后的新分支实际执行。

这些验证证明通用协议在受支持路径中可执行，不代表任意历史插件都已完成恢复适配。插件自行拥有的复杂工作流必须通过自身恢复适配器完成业务检查点与 worktree 的映射和核实，不能用平台通过代替业务验收。

## 插件自行管理状态的恢复适配

平台同时提供 `devclaw.plugin-stage-recovery/v1` 适配协议。其职责是核对已物理结束的原生试用所有者、复制受限范围内的完整项目产物、绑定配置和私有知识、执行审批及持久意图、核对真实结果，再向原有试用控制器注册新的独立项目。业务阶段与检查点的解释仍由插件脚本负责。

首次执行前，原生检查返回保留包、适配器和输入的准确摘要。准备操作必须携带这三项摘要与单独的网络效果批准；后续应用操作还必须确认本次计划摘要。Renderer 不能指定资源路径、伪造所有者 incarnation，或提供一个声称“已成功”的结果来恢复操作。

AutoBiz 适配器实际调用原有 `hooks/rollback_stage.py` 的计划和应用命令，再用原状态解析器及 workflow 契约验证结果；保留原 `stage_gate.py` 对产物的要求。恢复到某阶段后，缺少该阶段产物仍然阻断进入下一阶段。新项目注册复用原有控制器的所有权体系，不再运行会覆盖恢复结果的项目和需求初始化命令。

当前采用 `private-output-copy` 隔离和 `codeSource=keep`。这表示恢复业务状态与产物副本，保留开发源码；不表示已经具备 Git 源码自动回滚能力。包含 Git 元数据或指针、非空工作树目录、活跃任务租约、外部或未解析仓库映射的项目会被明确阻止，不能把原仓库或活跃 worktree 误认成独立副本。支持这些情况需要插件提供私有仓库克隆、工作树重绑定及业务事实核实的适配能力。

未启动的环境准备失败与执行后的未知效果严格区分。平台在沙箱准备成功、真实启动之前持久化执行意图；确定尚未启动的准备失败不制造执行回执，可以修复环境后重新批准。已经启动的取消或结果不明继续保留未知状态，阻止覆盖旧恢复入口或自动重复应用。
