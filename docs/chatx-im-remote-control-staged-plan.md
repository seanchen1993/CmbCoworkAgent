# 方案：把内置机器人从"托管助手"扩展为"桌面远程控制"

> 代码基线：`fff99227`
> 性质：分阶段产品能力扩展方案，供实施前评审。
> 关系：不替代 [V1 实施规格](./chatx-unified-bot-v1-implementation-spec.md)，是它之后的增量。V1 的安全边界、租约模型、持久化纪律全部继续有效。

>
> 期次对照：本文的阶段 1、阶段 2 对应[技术方案简报](./chatx-unified-bot-technical-brief.md)中的第二期、第三期。简报的第一期是本文之前已定义的统一机器人与托管收件箱。

## 0. 先更正一个技术判断

先前评审中有一条结论是错的，如果按它做设计会走偏，这里更正：

**错误结论：** coordinator 会把 worker 派生到其他 Thread，因此打破"一个 Thread 一个执行 owner"的不变式，需要把租约扩成运行树。

**实际情况：** worker 的 id 是合成的（`${parentThreadId}__worker__${workerId}`，`coordinator-worker-manager.ts:1310`），不创建 DB thread 行，不申请任何本地运行租约，并且跑在父 run 的 `abortSignal` 之下。父线程那把租约天然覆盖整棵运行树。**租约模型不需要任何改动。**

真正的阻塞在另一处，见阶段 2。

## 1. 目标与总体顺序

要达到的产品形态：用户在桌面已有的会话，可以在招乎里指定并对话；本地会话执行完成后主动推送到招乎。

分两个阶段，必须按序：

| 阶段 | 内容                                  | 是否改桌面主路径 |
| ---- | ------------------------------------- | ---------------- |
| 1    | 会话接入招乎（双向：推送 + 远程驱动） | 否               |
| 2    | 解锁 coordinator / workflow           | 是（唯一一处）   |

阶段 1 不碰桌面执行路径，符合既定的"第一版桌面行为零回归"。阶段 2 是唯一需要动桌面的，放在最后，此时 IM 侧其余部分已跑通并有测试，回归风险是孤立且可二分的。

## 2. 阶段 1：会话接入招乎

### 2.1 单一开关

一个会话上只有一个开关，语义是"把这个会话接入招乎"。打开后同时获得两件事：执行结果自动推送到招乎，以及可以从招乎给它发指令。

**这里推翻了本方案早期版本的一条约束。** 早期版本要求把"推送"和"远程驱动"拆成两个独立开关，理由是推送单向、驱动双向带写权限。该理由不成立：推送会把执行结果的正文自动、持续地发到 IM 平台，是实打实的内容外泄；驱动是按需的、需要人主动发指令。两者一个偏保密性、一个偏完整性，严重程度相当，不存在"推送安全、驱动危险"的梯度。而拆开的产品代价是实的：用户在手机上收到结果想追一句，却发现能看不能回，这个状态很难解释。

保留知情同意，靠文案而不是靠开关数量。开关旁必须写明两个后果：

> 打开后，这个会话的执行结果会自动发送到你的招乎，你也可以从招乎给它发指令。

这个决定是可逆的。将来若确实需要分离，把一个开关拆成两个、存量默认都开，成本很低。

### 2.2 授权对象有两类

**会话授权**：允许从招乎驱动这一个已有会话，并接收它的结果。开关在会话上。

**Feature 授权**：允许从招乎在这个 Feature 下新建会话。开关在 Feature 详情里（实施规格 §6.5 已规划该位置）。

两者范围不同，UI 文案必须区分，不能都写成"允许远程访问"：会话授权是一次性的，Feature 授权是常设授权，意味着 IM 之后可以在该项目工作区里反复开新会话。

### 2.3 统一列表，不区分项目模式

`/会话` 一个指令、一套编号，同时列出已授权的会话和已授权的 Feature：

```
可用目标：
1. 重构登录模块（会话）
2. 季度报告整理（会话）
3. 支付网关改造 / 对账单导出（功能，新建会话）
```

选会话条目则绑定该已有线程；选 Feature 条目则在该 Feature 下新建一条 Project Mode Thread。

`/项目` 和 `/功能` 两级导航退休，暴露哪些 Feature 已经在桌面决定完，不需要在 IM 里逐级浏览。两级 selection context 收敛为一级。

**列表条目去重：** 某个 Feature 已有活跃远程会话时，它在列表里的条目直接变为那条会话，同一个 Feature 永远只占一行，状态在"新建会话"与"已有会话"之间切换。目的是避免重复点击攒出一串废线程。

**统一的是选择界面，不是执行语义。** 线程是不是项目模式由它自己的 metadata 决定，`getHarnessAgentContext` 本来就从 metadata 推导。项目模式会话仍须获得完整 harness context、插件注入、额外工作区、当前流程节点，并且仍然不注册 scheduler tool。不得以"不区分项目模式"为由简化执行侧。

### 2.4 桌面会话如何知道推给谁

IM 建的线程有 `imDeliveryContext`，桌面自建的没有。需要"本机当前用户的推送目标"这一概念：

- 来源是网关为该 `principalId` 建立的 conversation route，也就是用户至少和机器人说过一次话；
- 未建立路由时开关置灰，提示先在招乎向机器人发一条消息；
- 按 route 当前的 `conversationKey` 与 `deviceEpoch` 投递，沿用现有 `expectedDeviceEpoch` 校验；设备被接管后旧设备的推送必须被网关拒绝，与定时提醒规则一致。

从 IM 侧创建的会话天然已接入，开关默认打开。

### 2.5 推送基础设施

已经存在，收件箱的定时提醒走的就是这条路：`buildImProactiveReplies` → `enqueueProactiveReplies` → `replyClient.sendPending()`（`src/main/services/im/inbox-scheduler.ts:192-200`）。本阶段是把同一条通路接到桌面 Turn 的完成点上。

### 2.6 与已删除旧行为的区别（必须写进实现说明）

Clean cut 删掉的旧 `chatxRobotChatId` 隐式外发不得以任何形式复活。差别要在代码注释和 PR 说明里写清楚，否则会被误判为回退：

|          | 旧实现（已删除）            | 本阶段                            |
| -------- | --------------------------- | --------------------------------- |
| 触发     | Thread 元数据存在即自动外发 | 用户逐会话显式打开                |
| 通路     | 客户端持凭据直发平台 HTTP   | 经网关，客户端无凭据              |
| 幂等     | 无                          | 稳定 `deliveryId` + outbox 幂等键 |
| 失败处理 | 静默                        | outbox 状态机，含 `unknown`       |

### 2.7 每轮执行前的校验

沿用 `capability-guard` 的模式，每次执行前重新校验，任一不满足则 suspend 而不是静默降级：

1. 该会话或 Feature 的接入授权仍然打开；
2. 工作区目录仍存在且可访问；
3. Thread 仍存在且元数据与 target snapshot 一致；
4. conversation route 仍固定在本设备与当前 `deviceEpoch`；
5. 本阶段仍限 `agentMode === "normal"`，非 normal 一律拒绝并提示回桌面。

选中 Feature 条目新建会话时，`validateImFeatureTarget` 那套校验一条都不能省：项目 active、目录存在、harness adapter 兼容、Feature 未归档、工作区可安全解析、项目约束与插件上下文可加载。解析不出工作区必须阻止创建，不允许回退到应用根目录、最近目录或用户输入目录。

### 2.8 授权发生在桌面，不在 IM

不能做成"IM 发指令列出全部最近会话"。原因有两条，都不是显而易见的：

**一，会话标题会外泄到 IM 平台。** 项目名和 Feature 名是人工命名、可控的；Thread 标题是从用户第一句话自动生成的，可能包含任意敏感内容。把全部近期会话列到招乎，等于把一批未经审查的字符串推到 IM 平台上。先前评审中"列项目清单可接受、不必做脱敏别名"的结论**不适用于会话标题**。

**二，工作区是任意目录。** 收件箱是托管沙箱，Feature 经校验，而任意已有会话指向用户机器上任意路径。

两个问题由"授权发生在桌面"同时解决。"最近 24 小时活跃"可以作为桌面侧的排序或筛选辅助，帮用户找到要授权的会话，但不能作为自动授权规则。

### 2.9 收件箱保留

收件箱是零配置入口，也是任何授权发生之前唯一可用的目标，继续作为默认目标存在。不得以"统一"为由把它一并去掉。

### 2.10 设置项收敛

授权已经是逐对象的，`remoteAccess: "inbox-only" | "inbox-and-features"` 这个全局分级失去意义，可以退休。建议保留一个全局总开关作为兜底（一键停止本设备的全部远程接入），但不再分级。

### 2.11 从招乎批准工具调用

本节推翻实施规格 §14.1 与验收第 28 条"远程审批只在桌面完成"。理由是纯 IM 用户在审批门前无路可走，而阶段 2 的 coordinator 几乎必然撞上审批门。

机制上很便宜：`pendingApprovals` 是主进程里的 Map，直接持有 `resolve`（`runtime.ts:342`）。IM 侧拿到 requestId 即可决议，不经渲染进程，不需要新的 IPC 通路。

#### 2.11.1 结构性例外：git_commit / git_push 不可远程批

`ApprovalDecision` 的 `commitResult` / `pushResult` 按其定义是"**渲染进程执行完**提交/推送之后回填的结果"（`src/main/types.ts` 中 `ApprovalDecision`）。也就是说这两类审批的批准动作本身包含由桌面 UI 实际执行提交或推送，不是单纯返回一个决定。

IM 返回 `{ type: "approve" }` 而不带这些字段，runtime 会拿到"已批准但提交从未发生"的状态。这不是加个指令能绕过的。要放开必须先把 commit/push 的执行从渲染进程搬到主进程，**不在本阶段范围**。

这两类恰好也是后果最不可逆的，留在桌面不算勉强。

#### 2.11.2 协议：一次性短码，不解析自然语言

审批请求推送到 IM 时附带一个随机短码：

```
【支付网关改造 / 对账单导出】需要批准
写入文件 src/billing/export.ts

/批准 7F3A9C   或   /拒绝 7F3A9C
```

- 短码随机生成、单次有效、随审批请求一同过期；
- 不复用 `/重试` 的短码派生方式，不得可从 requestId 推算；
- 多个审批并存时，短码是唯一的指向依据。

规格 §14.1 中"IM 文本不构成批准"这条**仍然成立**：变化是新增了带短码的显式指令，而不是开始把自然语言解析为审批决定。用户发"同意""可以"仍然按普通消息处理。

#### 2.11.3 按 operation 分级

`ApprovalRequest.operation` 是枚举，天然可作分级依据：

| 操作类别                            | IM 可批 | 说明                               |
| ----------------------------------- | ------- | ---------------------------------- |
| 工作区内 `write_file` / `edit_file` | 是      | 必须展示目标文件路径（相对工作区） |
| `execute`（shell）                  | 是      | 命令原文必须完整展示，不截断       |
| `git_commit` / `git_push`           | 否      | 见 2.11.1                          |
| `save_code_exec_tool`               | 否      | 等于永久扩权                       |
| 工作区外的任何写入                  | 否      | 与现有沙箱边界一致                 |

不可远程批的类别推送到 IM 时只通知"需要在桌面确认"，不附短码。

#### 2.11.4 只允许一次性批准

`ApprovalDecisionType` 有 `approve` / `approve_session` / `approve_permanent`。**IM 侧只开放 `approve` 与 `reject`**，不开放会话级和永久豁免：在手机上点一下就给出长期授权，风险与收益不成比例。

同时必须尊重每个请求自带的 `allowed_approval_types`，不得给出该请求不接受的决定类型。

#### 2.11.5 独立全局开关，默认关闭

远程审批**不并入**会话的"接入招乎"开关。接入决定的是哪些会话暴露，远程审批决定的是用户愿不愿意在手机上做授权判断，是另一个轴。

做成一个全局设置"允许从招乎批准工具调用"，默认关闭。关闭时行为与现状一致，审批只在桌面。

#### 2.11.6 留痕

每一次远程批准都要记录来源，并在桌面对应会话中可见。这类授权最需要的是事后可查。

#### 2.11.7 交付分层

本节描述的短码协议是**文本兜底层**，不依赖任何契约变更，可独立交付。卡片形态见 2.12，它是同一能力的增强层，两者共存并按客户端能力降级。

### 2.12 卡片增强与结构化补充输入

> 本节已抽出独立需求文档：[招乎侧交互式决定](./chatx-im-interactive-decision-requirement.md)。该文含完整的契约要求、验收与待确认事项，实施以该文为准，本节保留概要。

#### 2.12.1 更正：`request_user_input` 应当开放

本方案早期版本把 `request_user_input` 排除在远程之外，理由写的是"结构化补充输入是让 Agent 获得内容，与批准一个已知操作不是一回事"。**该理由不成立**：用户本就能从招乎发任意文本驱动会话，回答一个提问不新增任何能力通道。真实障碍是纯文本无法呈现结构化表单，而卡片消除了这个障碍。

结构上契合度很高：`UserInputQuestion { header, question, options: [{ label, description }] }` 与自定义卡片的表单组件基本一一对应。客户端侧同样便宜：`submitUserInputResponse` 与 `pendingUserInputs` 是主进程 Map（`src/main/services/user-input.ts:28`），与 `pendingApprovals` 同一形状，拿到 requestId 即可回填。

#### 2.12.2 两个交付层

**层一：文本兜底（不依赖契约变更，与 2.11 同期交付）**

- 审批：`/批准 <短码>` / `/拒绝 <短码>`，见 2.11.2；
- 结构化补充输入：提问以编号列表推送，用户回 `/回答 <输入短码> <编号>`，或用
  `/回答 <输入短码> 其他 <自定义内容>`。多道问题逐题生成新短码，已用短码立即失效。

该层在任何客户端版本上都可用，是卡片不可用时的降级形态，不得因为实现了卡片就删除。

**层二：卡片（需要网关与双边契约配合）**

- **审批改用招乎审批 2.0**（`/robot-service/single-message/send-audit-beta`），同意与拒绝按钮直接产生上行回执（`updateAudit` 事件）。这比短码更优的地方不只是体验：按钮点击在协议层就是独立事件类型，与普通文本结构上不同，"自然语言误触发审批"的风险从根本上消失，短码退化为老客户端兜底。
- **结构化补充输入使用自定义卡片表单组件**（列表选择器、输入框、提交按钮），回执走 `CustomCard` 事件。
- 卡片可按平台 msgId 更新，用于把"待处理"改为"已处理"。outbox 已持久化 `platformReplyId`，可直接使用。

#### 2.12.3 归一化必须发生在网关

卡片回执是**第一件带渠道特有结构的上行数据**。此前"app 侧不建渠道抽象层"的判断，依据正是客户端拿到的事件已被网关归一化为纯文本。

因此要求：**网关把 `updateAudit` 与 `CustomCard` 回执转换成契约中的结构化决定事件**，客户端拿到的仍是渠道中立的载荷，不得让卡片 JSON 直接透传到客户端。这需要在 `RemoteImEventV1` 中扩出结构化事件类型，属于双边契约变更，须与网关团队同期排期。

#### 2.12.4 实现约束

- **回执载荷需二次解析。** API 参考明确指出各类回执的 `msgContent` 常以 JSON 字符串而非 JSON 对象返回，网关侧解析必须做异常保护，畸形载荷按无效决定丢弃并记录。
- **客户端版本碎片。** 自定义卡片要求招乎 APP/PC V6.6+，Markdown 容器 V6.14+，AI 内容 V6.15+。需要先摸清目标用户的版本分布；能力不足时自动退回层一，不得报错。
- **卡片单聊 `content` 上限 15,000 字符**，超出需截断并提示到桌面查看。
- **分级规则不变。** 卡片只改变决定的采集方式，不改变 2.11.3 的可批准范围：git 提交与推送、保存执行工具、越界写入仍限桌面，其卡片不带可点击的批准按钮。
- **一次性语义不变。** 卡片按钮只提供单次批准，不提供会话级与永久豁免。

### 2.13 指令集

| ------------------------- | --------------------------------------------------------- |

### 2.14 三项待确认的产品决策

以下三项在需求层有多种合理取法，不同取法产品不同，不得由实现者临时决定。此处给出建议值，确认前按建议值实施。

**一，`remoteAccess` 退休后存量用户的 Feature 如何处理。**
建议：**不自动继承**。已设为 `inbox-and-features` 的用户升级后，其 Feature 不自动获得远程新建授权，改为提示一次"远程访问方式已变更，请重新选择要开放的功能"。理由是自动继承等于把一个旧的全局设置静默换成一批新的逐项授权，属于静默扩权；宁可让用户重选。

**二，推送的粒度。**
建议：**每轮推送，但桌面窗口处于前台时不推**。人在桌面前连续做短对话时不产生手机通知，离开后自动开始推送，不需要用户额外操作。若认为该条件过于隐晦，退而求其次是无条件每轮推送，行为简单可预期。

**三，撤销接入时正在执行的那一轮如何处理。**
建议：**让它跑完并正常推送结果**，撤销只对之后的消息生效。中途掐断会留下半成品状态，而这一轮本来就是用户自己发起的。

### 2.15 非目标

- 不推送中间过程、工具调用、流式片段，只推送最终结果（审批请求除外，它必须实时推送）；
- 不推送失败堆栈、绝对路径、环境变量（沿用现有脱敏规则）；
- 不允许 IM 指定任意路径或未授权对象；
- 不自动列出、不按活跃度自动授权；
- 不允许 IM 修改接入授权状态，授权与撤销只在桌面；
- 不开放 `git_commit` / `git_push` / `save_code_exec_tool` 的远程批准；
- 不开放 `approve_session` / `approve_permanent`；
- 不把自然语言解析为审批或回答决定；
- 不让卡片回执的原始 JSON 透传到客户端，归一化必须在网关完成；
- 不实现群卡片、千人千面、图表与 AI 流式卡片；
- 不支持非 normal 模式（阶段 2 才放开）；
- 不做群发、不做推给他人。

### 2.16 验收

1. 未在桌面授权的会话，IM 列表里看不到，也无法通过任何编号绑定到。
2. 授权后可在 IM 绑定并对话，执行语义与桌面同一会话一致。
3. 已授权 Feature 可从 IM 新建会话，新会话获得完整 Project Mode 上下文，且不注册 scheduler tool。
4. 同一 Feature 已有活跃远程会话时，列表只出现一行且指向该会话。
5. 打开接入的桌面会话执行完成后，招乎收到结果，内容与桌面最终回复一致；关闭后不再推送。
6. 未建立 conversation route 时开关不可用且有明确提示。
7. 推送使用稳定 `deliveryId`，重复投递不产生第二条消息。
8. 撤销授权后，后续 IM 消息被拒绝，binding 进入 suspended，不静默切回收件箱。
9. 工作区被删除或移动后 binding suspended，报错不含绝对路径。
10. 非 normal 模式会话即使被授权也被拒绝，提示回桌面。
11. 设备被接管后，旧设备的推送被网关拒绝。
12. IM 列表不包含未授权对象的标题。
13. 全库不存在依据 Thread 元数据自动外发的路径。
14. 远程审批全局开关关闭时，行为与现状完全一致，审批只在桌面且 IM 不出现短码。
15. 开启后，工作区内 `write_file` 与 `execute` 的审批可从 IM 批准并继续执行；`execute` 的命令原文完整展示，未被截断。
16. `git_commit` / `git_push` / `save_code_exec_tool` 的审批推送到 IM 时不附短码，只提示回桌面确认；IM 无法用任何指令决议它们。
17. 自然语言"同意""批准"仍按普通消息处理，不产生审批决定。
18. 短码单次有效：同一短码第二次使用被拒绝；短码不可从 requestId 推算。
19. 并存多个审批时，短码各自指向正确请求，不会批错对象。
20. IM 只能给出 `approve` / `reject`；越过 `allowed_approval_types` 的决定被拒绝。
21. 远程批准在桌面对应会话中可见，且标明来源为远程。
22. 审批 TTL 到期后事件取消，短码同时失效。
23. 文本兜底层可独立工作：在不具备卡片能力的客户端上，审批与结构化补充输入均可通过 `/批准`、`/拒绝`、`/回答` 完成。
24. `request_user_input` 可从招乎回答，包含选项与自定义内容两种形式；答案进入 Agent 的方式与桌面回答一致。
25. 卡片可用时按钮与表单可完成同样的决定；实现卡片后文本指令仍然有效，未被移除。
26. 客户端能力不足时自动退回文本形态，不产生错误提示。
27. 不可远程批准的操作，其卡片不含可点击的批准按钮。
28. 畸形或重复的卡片回执被网关按无效决定丢弃并记录，不产生第二次决定。
29. 客户端收到的回答与批准事件是契约中的结构化类型，不含任何渠道特有的原始 JSON。

## 3. 阶段 2：解锁 coordinator / workflow

### 3.1 真正的阻塞点

`agentMode` 确实是 `createAgentRuntime` 的入参（`runtime.ts:3958`），执行侧是选项驱动的，worker 派生和工具门控都在 runtime 内部，这部分不用动。

问题在**围绕 runtime 的编排**：`src/main/ipc/agent.ts` 中有 64 处 `coordinatorWorkerManager.` / `workflowRunManager.` 调用，而 IM 路径与共享核心中是 0 处。characterization 测试专门锁死了这一点（`testAdvancedDesktopModesStayInsideTheExistingHandler`，断言 `restoreWorkersForThread`、`findPendingNotification`、`runCompletionHooksWithRevision` 必须留在 handler 内）。

所以 IM 的执行器没有跑 coordinator turn 的代码。

### 3.2 绝对不能只拿掉闸门

**不得**单独移除 `capability-guard.ts` 中的 `agentMode !== "normal"` 判断。那样 IM 会把 coordinator 线程当普通线程跑：worker 不会被恢复，workflow 待处理通知不会被消费，完成钩子走另一套。这正是整个设计一路在防的"第二套执行语义"，而且作用在用户已有真实产物的会话上，后果远重于收件箱出错。

### 3.3 需要抽取的范围

比"整个 `agent:invoke`"小得多，限定为三块：

1. 模式分发（`effectiveAgentMode` 判定与分支入口）；
2. worker 恢复（`restoreWorkersForThread` 及其前置状态读取）；
3. 通知与完成处理（`findPendingNotification`、`runCompletionHooksWithRevision`）。

桌面 stop / replace / steer / goal 的所有权**不在本次范围内**，继续留在 handler。

抽取过程中桌面行为必须保持不变，由现有 characterization 测试守护。测试中断言"必须留在 handler 内"的那几条需要相应改写为"必须由共享核心提供且桌面与 IM 共用"，这是本方案中唯一允许修改既有断言的地方，改写需在 PR 中单独说明。

### 3.4 长任务语义

coordinator / workflow 一轮可能远超网关执行许可的续期节奏。IM 侧采用：立即回"已启动"加事件短码，执行期间维持许可续租，完成后经阶段 1 的推送通道返回结果。因此阶段 1 必须先完成。

### 3.5 即使做完仍然受限的部分

要在产品文案里写清楚，避免用户预期落空：

- **部分审批仍只在桌面。** 按 2.11.3 的分级，`git_commit` / `git_push` / `save_code_exec_tool` 与工作区外写入无法远程批准。coordinator 与 workflow 撞上这几类时仍会进入 `waiting_desktop`，超过 TTL 即取消。由于 coordinator 常以提交收尾，这个限制在本场景下会比较明显，需在产品文案中说明。
- **IM 不能创建** coordinator / workflow 会话，只能驱动桌面已建好并授权的会话。IM 在已授权 Feature 下新建的会话是普通模式。
- **中间过程不推送**，只有最终结果与审批请求。

### 3.6 验收

1. 桌面已建好并授权的 coordinator 会话，可从 IM 发送消息并正确执行，worker 恢复、通知消费、完成钩子与桌面完全一致。
2. workflow 会话同上，节点流转正确。
3. 桌面 characterization 测试全部通过；改写的断言有单独说明。
4. 同一消息分别从桌面和 IM 进入同一 coordinator 会话，执行链路一致（不比较模型自然语言输出）。
5. 遇到审批时 IM 收到等待提示，TTL 到期后取消该事件且不影响绑定。
6. IM 无法创建非 normal 模式的新会话。

## 4. 跨阶段必须守住的不变式

1. 同一 Thread 任一时刻只有一个 Runtime owner，IM 让位桌面。两个阶段都不改这条。
2. 客户端不持有平台凭据，`principalId` 由网关决定。
3. 所有对外确认前 `flushStrict()`。
4. 远程输入标记为不可信；错误外发不含堆栈、绝对路径、环境变量、凭据。
5. 接入授权与撤销只发生在桌面，IM 侧无法给自己提权。远程审批是对单次已知操作的一次性决定，不改变任何长期授权范围。
6. 统一的是选择界面，不是执行语义；项目模式会话在执行侧仍享有完整 Project Mode 上下文。
7. 自然语言永远不构成授权决定，审批只接受带一次性短码的显式指令。
