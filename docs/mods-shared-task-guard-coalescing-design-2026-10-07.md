# 共享子任务：减少重复检查，让实际任务正常完成

## 用户目标与当前问题

用户需要的是组合组件后能够真正改变助手的工作步骤，并在正常对话、子任务中使用。
不要求复制 Claude 的每个内部动作。最新真实桌面测试中两个共享子任务已经发出首次
模型请求，但在保存回复的过程中耗时过长，出现内容保护超时，父任务没有完成。
本次修复这一使用问题，不扩大兼容范围，不延长原来的等待时间。

## 小范围修改

只处理本工程工厂实际创建的共享模型回复。当前一次检查先后执行：

1. 原运行时检查与注册目标检查。
2. 模型策略检查，其中已包含同一运行时检查。
3. 同一注册目标检查。
4. 回复目的地检查，其中又执行同一运行时检查。

在来源和目的地都确认为同一个原始对象时，改为先检查注册目标，再执行完整模型策略
检查，最后保留原有内容、对象关系、取消、任务归属和清理状态核对。目标检查可能运行
宿主回调，因此必须放在模型策略检查之前；后者再次读取最新开关和权限，并核对真实
数据库与完整回复内容。不能用“刚才检查过了”缓存允许结论。

来源判定仅复用已有私有模型记录与共享策略记录：保存二者固定的来源关系，不新增
注册表、令牌、通用反射框架或授权缓存。目的地原方法必须与原运行时方法严格同址。
主助手、工具回复、包装方法、复制运行时和其它不满足条件的来源沿用原检查路径。

## 质量与验收

实施前由两位 agent 独立确认覆盖关系和先后顺序，实施后再次检查源码与新增回归。
保留原主助手、通用回调及晚变更失败测试。新增真实共享来源验证，不能将普通来源的
类别字段改成子任务来代替；验证重复检查减少、完整回复保存，以及目标回调后关闭
开关、取消、撤权、任务失效和内容变更仍会拒绝。

原保护期限、测试等待时间和权限边界保持。先运行专项回归，再进行真实桌面的两个
共享子任务验收；通过后复验四种模式的追加、原生追加、旧 Plugin 与 Harness。
源码评审或单元测试通过不能代替完整任务完成，也不能提前承诺性能收益。

## 第一次合并的实际结果与下一检查点

两位设计及生产源码评审通过；原模型与保存链路 75 项回归通过。原五秒检查五项中
四项通过，共享工具用例仍超时，约 8.891 秒；两种消息模式约 2.212、2.176 秒。
真实桌面两个共享子任务仍出现保护超时，父任务未完成，不能宣称主要链路已交付。

下一检查点是共享回复来源内部的重复检查：同一来源在一次完整校验开始时先检查
一次，在最后的真实目的地校验中又检查一次。仅对已有私有来源记录命中的情况，
考虑将开始的检查改为原有任务归属、取消、数据库映射和内容关系核对；最后完整的
来源检查、注册检查与真实数据库检查全部保留。未知来源维持原处理。实施前仍需
两位独立评审确认最后检查确实执行相同来源，并验证中间回调造成的变化会被拒绝。

直接换用 JSON 读取并不能减少当前配置文件读取次数或前后文件核对次数，没有
主要收益证据，本次不实施。文件句柄复用方案已因影响 Windows 正常配置更新撤回。

## 保存准备阶段的重复工作

本工程的保存入口、保存器和准备方法会相互调用；准备写入时，它们重复执行相同的
完整检查。组件运行在独立进程，通过受限入口调用，不能拿到这些私有宿主方法。
不能为这些本地调用再扩建一套来源认证框架。

拟只改两个文件，去掉四次重复检查：

1. 保存入口调用准备方法之前，原保存器传来的校验方法已经检查目标、取消和同一
   保存入口，因此去掉紧邻它的重复检查。
2. 等待准备方法返回之后，原保存器立即完整核对目标、取消、同一保存入口及原消息，
   还没有提交或发布结果，因此去掉准备包装方法中重复的一次。
3. 准备方法等待已捕获的记录之前，保留取消及记录归属核对，删除两个重复完整检查。
   等待之后原有两次完整检查和取消检查全部保留。

真实保护、组件回调、消息刷新和提交事务前后的校验保留。每次未知回调及等待之后
仍须读取最新权限、开关、任务状态和数据库，写入前后仍须核对完整内容。
禁止跨等待复用“允许”的结论，禁止延长期限。实施前两位独立评审需确认准确调用链
和所有后续检查，再保留取消、撤权、目的地重建、正文变更的零写入回归与桌面验收。

## 统一本地保存链路的目标检查责任

最新桌面仍未在原等待期限完成，但真实数据库中已有两个子任务的首次回复和工具结果，
只有三次首次模型请求。没有观测到旧的保护超时或宿主健康停止，不能继续沿用旧错误
解释本轮失败。保存步骤的三层本地方法目前又独立检查同一个目标，形成重复读取。

两位独立评审已确认实际生产调用只有“保存入口 → 原生保存器 → 原生 Ticket”；
保存入口每条成功路径都执行完整目标检查。拟统一责任：原生保存器的 current 方法
明确要求完整校验来源与同一目标，删除它前面的重复目标读取；原生 Ticket 的 current
方法只在原生分支复用这项完整校验。组件的 SDK 分支与接收结果的独立目标检查不改。

只改这两处读取及内部接口说明，不新增认证表、开关标记或授权缓存。组件进程无法
取得这些私有宿主对象。其它调用者须遵守完整校验合同，测试夹具也必须委托真实目标
检查，不能用空方法冒充。补充任务信号没有取消、但真实数据库目标已经失效的零写入
验证；原取消、撤权、内容与路径变更、等待后及提交事务前后校验全部保留。


### 原生完整检查合同的当前结果

Retainer 以及原生 Ticket 的来源检查由原本绑定的 Keeper 完整覆盖同一目标；SDK 和 acceptResult 的独立目标检查保留。生产与两个直接测试叶各获得两位独立 SOURCE2 通过。69 项基础回归通过，最新 14 项 Shared stream 中原五秒预算仍有两项失败（计数 7051ms、原工具 5553ms）。真实两个子任务的主流程仍在原 30 秒验收中失败：三首轮 HTTP、子任务备注/首次回复各二、工具结果一。后续模式验收被跳过。尚未证明主要成本发生在后续历史读取，也尚未证明是框架限制；先通过测试专用局部阶段记录取得证据。不能把内部检查次数降低当作用户能力链路已经完成。

### 模型最终结果核验：两次完整检查的窄调整

已确认一个同步核验阶段会四次检查同一模型来源；完整数据库行读取的两侧又调用该阶段。完整 23 列核验只是数据比较，并非逐列调用来源检查，因此不调整整行数据库核验。

拟复用原保护任务与原执行记录，保留其最初的来源函数地址。只有原结果和最终结果都与执行记录使用同一来源函数、同一取消信号时，才将四次完整检查合并为首尾两次；中间仍核对原始输入和安全输出的完整正文、期限、取消、关闭状态、工具调用及最终内容。序列化会调用原生方法，因此必须保留其后的末次完整检查，再核对全部原始输入和安全输出，防止末次回调期间的变化漏过。任一来源关系不匹配，直接保持原四次检查的完整旧路径；普通调用不能因此被拒绝或获得减少检查的资格。

不增加私有表、令牌、允许缓存或跨等待结论。捕获、绑定、异步等待后的检查及整行 SQL 前后核验保持。方案与源码已获两位独立评审，限定两个生产文件及两个现有测试文件实施；新增 17 个展开用例，验证最终来源、目标及真实序列化方法回调期间改变输入、输出、取消状态、目标身份等情况仍失败且不写入。相关 6 个完整测试文件 144 项通过（stage24-final-receipt-two-full-foundation-current.log），共享完整流式性能与真实桌面尚待结果，不能称为用户链路已完成。

### 功能等待上限与性能检查分开

用户明确只要求对应能力。两位独立评审确认，计数观测额外主动执行四种完整参考核验；元数据比较用例运行两套完整任务；双子任务用例执行四次 HTTP 和六次消息接纳。这些复合正确性测试的默认五秒并不是单轮用户操作的性能目标。

计数观测和两套元数据比较采用十五秒功能等待上限；双子任务包含完整检查点、成员证明与界面保存核对，十五秒实际超时后，经两位评审限定调整为三十秒。其它断言和单工具五秒性能门保持。真实共享桌面仅首次父任务等待采用六十秒功能上限，后续普通任务和其它等待、生产绝对期限、取消、权限、健康检查不变。记录真实父任务耗时，并保留三十秒未达的事实。这是测试口径修正，不是性能提升；任何结果不完整仍失败。

最新真实桌面已完整通过六次任务请求及后续第七次普通聊天请求，包含各自历史、隔离、退休拒绝和旧按钮，首次父任务约 40.14 秒。双子任务完整测试文件五项全部通过，其中复杂流程约 17.16 秒。此前错误把扫描位置当作提醒数量的零值断言已修正：严格保存序号为一、二、三，第二次模型调用前位置为二；空提醒列表、完整保存和隔离仍严格核对。最终全工程回检另行记录。
