# 会话结束时的处理：下一阶段方案

工作仍在 C:/ai/CmbCoworkAgent-mods-v2，codex/mods-v2。流式阶段全部验收后继续本阶段；整体目标保持进行中。

## 用户看到什么

用户退出应用、删除已运行的对话时，已启用的组件可以收到一次“这个对话正在结束”的通知，用于整理自己的状态。所有组件共同使用1.5秒的期限，组件多、网络慢都不能把这个通知变成长时间退出等待。原来插件的退出处理和任务清理保留。

组件重新加载、切换页面、普通任务回答完毕和撤销组件授权，不等于对话结束，不能误报。未真正启动的组件不会因为退出而首次运行。

## 已核对的依据与真实落点

固定 Claude Code 2.1.288 声明10350–10400：session.end携带实际reason、sessionId和resume.id，结果只回显sessionId。整个链默认1.5秒，SDK等待也消耗这个期限。6193–6223要求next.budget同步读取实际共同期限，后面的组件只剩前面留出的时间。

设计时本工程只识别该名字，兼容说明还标无法运行；本阶段已补实际通知。真正退出在src/main/index.ts的before-quit（已有停止任务和经典SessionEnd），真正删除在src/main/ipc/threads.ts的原fireSessionEnd之后；will-quit已经太晚。固定声明4144–4146明确顺序是经典SessionEnd设置链先完成，再通知Mods。组件重新加载和撤权继续直接清理并即时撤权，不能新增可执行窗口。

## 共同时间基础

退出期限由主进程生成，不能每到一个组件就重新给1.5秒。实际宿主期限继续有总等待切断和取消。私有FunctionInvocation增加宿主生成的共同单调截止信息；不能放进作者事件、SDK参数或公开API。native预算读取和发起RPC之前同时检查自身时间、共同期限与原取消；在本阶段共同期限不会因SDK/模块通道等待而停钟，恢复也只能用剩余共同时间。

不同进程的performance.now起点不同，不能直接相减。本阶段采用本机系统单调计数的纳秒期限（私有十进制字符串），每个进程在native层读取process.hrtime.bigint并计算剩余。Node说明该计数与日期无关；Windows libuv实际用QueryPerformanceCounter。已在实际Electron39.8.10主进程与utility process中取得8次采样，每个子进程读数均在父进程前后读数之间，Node22.22.1/libuv1.51.0；原始记录见output/mods-validation/e2e-shared-clock/shared-monotonic-clock.json。Mac/Linux尚未实际验证，不能泛称Node保证所有进程起点相同。[Node官方说明](https://nodejs.org/api/process.html#processhrtimebigint)、[libuv Windows实现](https://github.com/libuv/libuv/blob/v1.x/src/win/util.c)。这是依据实现和本机实验确认的Windows适配；若实际环境不能证明同源，拒绝伪造共同预算并设计带校准的保守替代，不能无声退化为每帧重置。

native在帧真正开始时把ms设为自身配置与共同剩余的较小值；remainingMs每次读取不超过该共同剩余。已过期不允许进入新组件/恢复或启动SDK。普通规则、流式规则仍用已经验收的SDK停钟方式，不改变正常任务120秒等既有期限。

## 实际结束通知

- FunctionSession新增明确end入口，独立于retire：第一次保存私有结束Promise，重复结束沿同一回执，不重播。实际sessionId/resume.id固定为原$.session.id对应的threadId，结果是观察性回显，不允许组件更改宿主结束事实。
- 接纳闸门与通知分开：主进程在首次await前同步捕获已有实际实例、阻止新的普通入口，已有任务沿原流程取消；先完成原经典链，随后才在这个精确实例上创建Mods共同1.5秒期限。不能从结束入口调用session()/withEntry去加载或自动应用。经典退出桥接若需要同一实例，使用此次宿主结束回执的明确阶段，不能让普通请求冒充。
- FunctionModsManager只取已有、已启动、批准仍有效的实际会话，不加载候选、不执行session.start。通知前后保留代码摘要、保存版本、授权和epoch检查。结束期间拒绝新的普通入口，不能有取消后重新开模型/任务的路径。
- 退出应用：实际任务停止后先await经典fireSessionEndAll，再开始Mods共同期限，最后原will-quit清理。经典原5秒不塞进Mods1.5秒，也不与Mods并跑。即使只有Mods命令创建了会话，也不能被现有“无活跃经典会话”快捷路径漏掉。多个对话并行等待，不能每个串行增加1.5秒。
- 删除对话：现有拒绝活跃任务/工作树等前置检查之后，接纳结束意图并捕获原实例，先原经典fireSessionEnd，再await该实例Mods通知，继续原remote撤权、最终数据库校验及清理。通知表示已接纳的删除意图，不证明数据库已删除：remote撤权和最后CAS仍可能失败。之后无论删除成功或失败都退役已通知的这个原实例，锁存仅属该实例，不能永久锁threadId；不回滚或重播end，不自动跑startup。失败后存活对话的普通聊天仍可用，下一次显式用户操作可依原加载流程建立新的组件实例。保存参数和现有对话记录保留，后台不偷偷重启。前置拒绝、过期批量选择不触发通知。新增remote失败和最后group/incarnation检查失败的恢复反例。
- reason按真实业务选择并与原经典入口保持一致；本阶段不把删除对话宣称为Claude /clear原地更换sessionId，也不假造DevClaw未提供的CLI恢复命令。resume.id只是实际记录标识，删除后不能承诺记录可恢复。
- 结束通知不授予新的写工具/模型或用户身份。SDK仍通过原作用权限和实际拥有者；没有有效拥有者的操作照原规则拒绝。end-only私有共同证明须覆盖nested SDK及实际module RPC：仅本次结束活帧的模块调用使用moduleController和该共同cut取消信号的交集，cut到期令在途调用signal真实abort，宿主等待前后都核验。普通模块/其他普通frame及原已脱离命令的进程仍保留原独立生命周期，不全局abort moduleController。已经结束cut帧保留私有终态证明，迟到旧scope不能退化成普通后台身份再发pull/UI等请求；原资源close等清理例外保持。晚到回执只清理，真实host activity持有到实际finally，不能用通知超时伪造清理完成。
- 配置重载、源码更新、撤权、未启动候选和实例替换使用原即时retire，不额外触发session.end。真正应用关闭/删除已经收到end，再retire只做清理。

## 验收与后续

删除与应用退出重叠时，共享经典阶段不能无限等待。两位独立追加方案评审均通过：只有全应用退出进入经典阶段时建立一次原有5秒共同期限，已进入及后来接纳的经典阶段均复用其剩余时间；单独删除保持原来的脚本期限和取消信号。宿主阶段保存真正的Promise，已在等待的通知也能被随后附着的退出期限唤醒，到期直接离开等待，然后各实例并行开始1.5秒通知。已开始的原脚本保留自己的权限和信号，不重播，真实活动仍等到finally才释放。过期的阶段证明继续拒绝迟到SDK和首次core，不能退化为普通调用；会话本身也保存退出校验，覆盖不继承Hook环境的模块通道。结束通知使用自己的期限，已有资源只允许原拥有者执行关闭、取消打开、释放打开三种清理。

原命令/HTTP SessionEnd内部原本已有5秒总等待，缺的是外部Mods经典处理链和重叠请求的共同等待。本修复不改原脚本取消信号，不把原删除解释为无限等待。实际桌面验收还发现原脚本输入漏了reason，本阶段仅对SessionEnd补上实际clear/logout，未提供原因时为other，其它事件输入不增加该字段。等待加载的旧实例在会话构造后、启动前同步继承已有退出期限，晚到加载也不能越过截止。

真实QuickJS两个组件：前者等待SDK、后者读到减少的共同预算；两个实例各自独立、不因恢复重置；clock等待也减少；总期限后SDK/恢复调用0。主进程与真实utility process共同计数采样、延迟IPC不扩大期限，原模块等待仍不能停这个共同钟。重复end一次、修改宿主事实无效、无Hook不新增等待、未启动不执行、撤权/重载无通知。

实际Electron：用户真实聊天/Mods命令创建对话后删除，观测收到实际ID/原因一次；多个组件总耗时有界；退出应用前能收到通知，挂起组件不阻塞退出。原Plugin SessionEnd、项目模式、配置重载、连续聊天、IM/Goal/Harness邻近回归及广域、类型、lint、性能全部确认。两位独立方案通过后实施，发现实际边界先修方案再执行。

完成后继续私有回调/完成检查、消息附件及能力矩阵中其他仍能适配的入口；目前没有确认的新框架限制。
