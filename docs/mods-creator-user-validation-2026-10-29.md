# 通用 Mods 创作、业务校验与连续创作验收说明

本文记录 `codex/mods-v2`、应用版本 `2.0.0` 的实际使用验收。验收采用隔离用户目录、真实 Electron 界面和已配置的远端模型；通过界面确认安装、文件与命令操作，不用测试入口代替项目创建和阶段执行。本轮不制作安装包、不触发 GitHub Actions。

## 一、普通用户的三条使用路径

| 路径 | 实际操作与结果 | 保留的证据 |
| --- | --- | --- |
| 创建独立 Mod | 从空白聊天描述“显示本会话成功读取文件次数”；读取实际文件后由 0 变为 1；对话修改显示名称，保存并在新聊天再次使用 | `independent-real-read-build29.png`、`independent-dialogue-edit-build29.png`、`new-chat-formal-evidence-build29.json` |

证据位于本地 `output/ordinary-user-20261029/run-H8UOX7/`，不将用户目录、会话日志或模型配置提交到仓库。三个路径使用真实操作；业务异常的系统性覆盖另由针对性测试完成，二者不能相互替代。

正式项目生成 `facts.json`、`verification.json`、`report.json`。两条来源分别为服务不可用时段、设备告警时段；产物保留原文和缺失依据，不把时间重叠写成因果结论。此项目原有门禁主要验证结构，不能据此声称任意引用或推理都已经过业务规则验证。

一次早期试用受验收转发器请求数限制而中断，其未知结果和工作目录予以保留。后续使用独立试用和正式项目重新执行；没有删除中断证据，也没有把未知结果直接改为成功。

## 二、业务验收作为普通 Mod

新增独立 `evidence-validation` Function Mod，源码位于 `resources/native-compositions/evidence-validation/`。创造者可通过真实依赖目录发现、准备安装、等待原生确认，再读取实际公开动作并编译绑定。平台负责文件范围、权限、输入指纹和原始校验回执，业务规则放在 Mod 中。

提供两个动作：

- `check-citations`：引用的来源 ID 必须存在，引文必须是对应来源文本的非空逐字子串。
- `check-report`：复核引用，并要求报告的 `summary`、`citations` 与真实上游摘要文件一致。

摘要步骤声明来源输入；报告步骤声明来源和摘要输入。动作读取 Host 提供的产物引用，沿用原项目门禁；产物写入 `passed:true` 或模型口头声称通过均不能替代原始执行回执。输入变更后，旧回执不得用于阶段提交。

范围必须明确：这不是事实真实性、因果推理或摘要质量的通用判定器；不证明模型整理的来源文件与外部原件一致；报告额外的 `body/content` 等字段不在一致性规则内。展示完整报告或引用外部材料时，应另行声明对应输入及规则，不能把字段一致扩大为全文或事实可信。

实际界面验收已完成“资料摘要报告”：从空白聊天提出上述自然语言需求，创造者发现并复用 `evidence-validation@1.0.0`，经原生安装确认后生成三步项目及实际动作绑定；隔离试用逐步写入 `sources.json`、`summary.json`、`report.json`，摘要和报告均经过结构检查与独立业务动作检查，最后人工接受成果并完成项目。证据为 `business-validator-completed-build33.png/.json` 以及原创作会话只读状态 `business-validator-creator-ready-build33.json`。

重启应用后，通过记录和候选源码仍可读取；从原会话保存为 `summary-report-custom@1.0.0` 成功，默认名与原草稿关联。点击“开始使用”后普通新建项目页自动选中该插件，显示“整理来源 → 生成摘要 → 交付报告”。证据为 `business-validator-saved-build34.png`、`business-validator-start-use-build34.png`。

此次真实界面运行证明正向发现、绑定、执行与推进链路。错误来源、伪造引文、改写摘要、伪造通过字段、公开结果篡改和校验后上游变化的失败阻断，由实际 QuickJS、Flow 与 Host 的集成回归覆盖；这些负例使用受控产物，不冒充模型自然产生的错误。

## 三、连续创作

- `project_continue` 使用草稿 ID、版本与源码摘要确认基线，复制源码到新草稿继续修改；不复制试用成功、安装许可或执行权限。
- `project_versions` 返回真实保留的源码版本；旧存储没有历史时明确标记不完整，不补造历史。
- `project_compare` 返回实际变更文件，按需分页读取文本；文本窗口不是逐行对齐的补丁。
- `project_archive` 释放可归档草稿的活跃名额，同时保留源码历史和已有试用证据；运行中或结果未确定的草稿不得通过归档绕过限制。
- 公共 Mod 的依赖影响根据已安装插件及当前创作聊天的明确声明生成，并出现在原生复用确认界面。动态 JavaScript 调用、其他创作聊天、外部副本及所有已绑定项目不构成完整可发现依赖图；“未发现依赖”不能解释为“没有影响”。

源码存储采用内容去重，仍保留有限版本、活跃草稿与总容量限制。续作不意味着无限存储；容量不足应显示准确原因，不自动删除旧证据。已绑定动作摘要的调用者不会悄悄跟随公共 Mod 新版本，应重新编译、绑定并验收。

可以直接对创造者说：“保留当前插件和试用记录，从最新版本继续修改”“比较这次修改与上一个版本”“检查更新这个公共灵件会影响哪些已安装插件”。创造者应调用上述工具读取实际记录；版本比较不是业务效果比较，依赖报告也不是所有运行项目的完整清单。达到活跃草稿上限时，可归档已能证明不再运行的旧草稿；归档不释放历史存储字节或会话容量。无法证明试用已结束时，不能用归档绕过保护。

## 四、本轮实际问题修复

1. 原生审批等待纳入可信等待管理；用户等待不再直接耗尽 Mod 的普通执行时限。局部操作取消后同步清理审批，迟到的批准不能复活已取消操作。真实文件审批记录相隔约 155 秒后仍成功继续；计算时间、继承硬截止和等待上限仍然有效。
2. 中断后的结算保留原始未知原因，避免失效权限把取消误写成“输入已变化”；真实输入变化仍会被拒绝。未知外部效果仍需原生对账，不能默认重试或自动判成成功。
3. 工具参数 JSON 错误提示增加错误位置附近片段，引导将过长编辑按完整模块分批提交，不自动修复后偷偷执行。
4. 续作工具返回紧凑基线和下一步，避免把全部源码重复塞入模型上下文。
5. 保存插件优先采用可辨识的候选名或派生草稿标识，仍保留同名版本冲突检查和用户手动编辑。
6. 成功完成的试用不再统一显示“已失效、重新准备”，而是提示回制作会话查看结果及保存选项；未完成、失效的旧试用仍保留禁止继续执行的提示。
7. 项目结果区区分文件检查、结构检查和业务校验，避免同一文件多个检查显示成无法区分的重复“通过”。
8. 保存新插件导致运行实例重建时，已完成依赖的提示区分“运行尚未确认就绪”和真正的安装未知结果；前者提供“核对运行状态”，不要求重复安装或授权。
9. 统一工具说明、容量错误提示与项目创作 Skill 的续作指引，不再让模型手工转写全部源码到新草稿。
10. 依赖影响查询兼容平台已认可的大小写、下划线、点和数字开头的提供方身份，保持大小写精确匹配。创造者新建纯源码包仍使用原有小写连字符命名规则，本轮没有放宽安装边界。

真实业务试用中还观察到服务端较快返回、应用消费流式响应与收尾明显延迟的情况。同期完整回归运行、可用内存较低；已排除该试用目录被旧计数或清洗 Mod 授权干扰。新增有限次数的原生处理耗时诊断用于区分流读取、每帧权威检查及收尾，未移除任何校验。功能完成证据不能作为性能已经根治的证明。

已修正一处确定的重复工作：项目、操作和最近绑定操作三类热读取复用已编译 SQL，仍逐次读取数据库并完整验证状态。回归确认其他连接的取消、改名及状态篡改立即可见，返回对象被修改也不会污染后续读取。该优化减少重复 SQL 编译；尚不能据此认定分钟级流式延迟已经解决。

## 五、使用方式

在空白聊天切换“创造者模式”，描述需要的功能、输入和完成标准。独立 Mod 准备好后试用，再保存复用；项目插件在创作工作区试用，通过后保存，点击“开始使用”进入普通项目创建入口。

修改已有步骤时，说明保留哪些输入、知识、配置和检查，以及要替换的行为。创造者读取实际源码后修改；试用成功属于具体版本和实际执行，不会因为新版本编译通过而自动继承。

需要引用校验时，可描述：“摘要引用必须逐字来自来源，报告必须原样沿用摘要和引用；复用现有校验灵件，作为项目推进条件。”系统发现依赖后显示原生安装确认；确认后继续创作并运行真实项目验收。
