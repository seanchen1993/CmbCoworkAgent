# Mods 响应性与创造者续作修复（2026-11-03）

适用开发分支：`codex/mods-v2`，应用版本保持 `2.0.0`。

## 用户可见变化

- 打开普通聊天或项目会话时，不再因为存在未登记的插件源码而显示“查找可用插件界面”。实际插件页面仍从原使用入口打开，不增加项目模式步骤。
- 创造者取消累计 32 次操作、3 次候选修复、10 分钟总时长、64 次模型调用以及 32 轮原生续作限制。记录累计用量，不以这些固定配额终止正常创作。
- 已保存的旧默认 64 次模型记录可继续使用。恢复作者对话和直接恢复原试用的路径均处理旧记录，保留已发生的请求与 Token 统计。
- 创作工作区显示实际操作、候选和模型请求次数，不再显示固定的候选分母；未知历史用量继续标为不完整，不伪造零消耗。

单次模型超时、模型上下文容量、用户取消、权限、源码校验、并发版本检查和未知副作用的停止规则仍生效。宿主显式配置的模型策略保留；当前生产创造者没有配置固定模型次数策略。记账存储仍受字节容量保护，这与操作次数配额不同。

## 卡顿修复依据

1. 面板绘制通知原先还触发平台页面目录和行为目录刷新；冷目录查询进一步同步枚举插件来源。现在绘制通知只刷新已打开的页面，聊天目录查询只返回已登记的能力，实际来源发现保留在插件使用入口。
2. `FunctionPanes` 原先收到反馈、卡片等无关通知也重新查询，且允许请求并行堆积。现在过滤无关通知，同一会话只保持一次面板读取，合并连续更新并丢弃过期响应。
3. 展示快照原先为每个面板重复扫描全部 DOM 区域。现在一次收集后复用，保留原有可见性、焦点和模态窗口判定。

受控生产 React 浏览器用例的工作量结果：

| 场景 | 修复前 | 修复后 |
| --- | --- | --- |
| 40 次反馈通知触发面板读取 | 40 次 | 0 次 |
| 40 次连续面板通知触发读取 | 40 次 | 本次采样 7 次，最大并发 1 |
| 同组面板通知触发页面/行为目录读取 | 各 40 次 | 各 0 次 |

这些数据说明重复工作减少，不代表用户整机速度按同一比例提升。真实 Windows 包的交互回归与全量测试单独记录。

## 新发现：新增项目会话绕过插件流程

用户确认入口是“项目里新增会话后直接发送需求”。代码核对发现：`buildNativeDiscussionContext` 将这种会话明确标为“普通讨论”，阶段技能作为业务参考，而正式执行只在原 Host 入口中启动。因此不是需求过于简单导致平台切换模式，而是新增会话的讨论路径与插件执行入口尚未贯通。上述性能观测不能证明此问题已修复。

建议的通用修复边界：

1. 项目会话始终绑定真实插件版本、Feature、当前阶段及其指令，不能根据需求复杂度解除绑定。
2. 优先复用现有斜杠技能选择机制：新增项目会话展示并预选当前阶段技能，普通用户无需记忆命令；正式运行已支持 trustedExplicitSkill，可将用户发送的执行请求接回原 Host 执行器。斜杠仅提供入口，不能只展开为提示文字。主进程解析真实身份及版本，不接受模型自由指定插件、阶段跳转或批准；澄清与解释仍允许对话。按需加载当前技能，替换重复注入而非继续堆叠提示词，验证压缩及续作后的绑定。
3. 讨论路径不能直接使用写文件、执行实现命令或子代理等能力绕开阶段；权限限制须实际覆盖工具和子代理，不仅靠提示词。
4. 使用原运行、检查、等待输入及成果确认机制；没有当前版本的真实检查收据不能推进，不能因需求简单省略阶段，也不能把所有问题自动变为整条托管执行。
5. 使用 AutoBiz 与非 AutoBiz 两个插件验证：短需求、澄清提问、开始实施、重复发送、阶段变化、失败检查、等待输入、取消与恢复。旧插件入口和普通聊天保持兼容。

这部分属于后续项目聊天与执行的衔接工作，尚未作为此次配额和性能修复实现或验收；不能用增加一句强提示词声称已经解决。
