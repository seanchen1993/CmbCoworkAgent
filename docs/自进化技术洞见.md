# 自进化技术洞见

# 一、痛点描述

当前，我司作为银行科技能力建设与交付主体，正在将大语言模型及智能体（Agent）能力逐步引入研发提效、运维辅助、文档处理、知识问答、系统巡检等金融科技场景。随着智能体从“单轮问答”演进为“多工具、多步骤、长链路”的自动化执行系统，大量真实执行过程开始沉淀在本地会话、工具调用、代码修改与用户反馈之中。

但在传统智能体架构中，上述执行经验大多停留在单次会话上下文内，任务结束后即被遗忘，无法形成可复用、可审计、可持续优化的能力资产。结合金融行业对安全可控、流程留痕、知识复用及生产稳定性的要求，当前自进化体系主要暴露出以下三方面系统性痛点：

**1. 复杂任务经验无法体系化沉淀，重复试错造成资源与人力浪费**

在研发交付、生产排障和内部工具建设过程中，Agent 往往需要通过多轮文件读取、命令执行、错误定位、补丁修改和测试验证才能完成一个复杂任务。若这些执行路径无法在任务结束后转化为可复用 Skill，后续遇到同类场景时仍需重新探索工具调用顺序、项目约定、合规边界和质量门禁，导致 Token、工具调用、人工等待时间及算力资源持续重复消耗。

**2. 缺乏基于真实 Trace 的效果评估与责任归因机制**

传统提示词优化大多依赖人工复盘或少量样例，缺少对真实执行链路的持续观测与量化评估。系统难以判断某个 Skill 是否真正提升了任务成功率，某次失败究竟源于模型能力不足、工具调用异常、上下文缺失、权限边界不清，还是金融业务规则未被正确注入。若没有统一的 Trace、模型调用、工具调用、Token、结果质量、代码采纳和异常告警数据底座，自进化将停留在“经验性调参”阶段，无法支撑金融级智能体平台的精细化运营。

**3. 能力写回缺乏审批、分发与回滚机制，生产级复用风险较高**

Agent 自进化的本质是将运行过程中的经验反向写回能力层，其风险属性更接近“生产配置变更”而非普通文本生成。如果缺少候选审阅、Diff 对比、版本标记、审批发布、灰度采纳和本地备份回滚，错误 Skill 可能在后续多个研发或运维场景中被重复触发，放大自动化执行风险。同时，个人会话中沉淀出的有效经验若无法经过治理后进入共享通道，也难以转化为团队级、部门级乃至全行级能力资产。

# 二、影响分析

在银行科技体系强调安全、稳定、合规、可审计的客观约束下，上述架构痛点若不加以解决，将对智能体规模化落地与组织能力沉淀产生如下负面影响：

**1. 智能体执行成本居高不下，复杂任务吞吐能力受限**

缺少“经验复用层”时，系统只能依赖大模型在每次会话中重新推理任务流程。大量高频流程性任务持续消耗模型上下文、工具调用和用户等待时间，导致同类问题反复支付探索成本。随着研发、运维、测试、文档等场景并发扩大，单次任务链路越长，资源浪费越明显，最终限制智能体在更多业务条线和科技团队中的推广规模。

**2. 组织知识沉淀断层，金融科技最佳实践难以规模化复制**

银行科技公司在核心系统研发、渠道系统建设、数据平台治理、监管报送、生产运维等领域沉淀了大量隐性流程与规范。若这些知识只能通过口口相传、手工文档或单次会话上下文维系，优秀实践难以被新项目、新成员和新 Agent 会话稳定复用。长远看，智能体无法形成“越用越懂业务、越用越贴合流程”的正向飞轮，系统能力会长期停留在通用模型调用层。

**3. 能力演进缺少治理闭环，自动化执行风险难以收敛**

自进化如果没有可观测、可审批、可回滚的治理设计，可能将偶发成功路径、错误经验或过窄的文件级处理方案沉淀为 Skill，进而在未来任务中被错误触发。对于代码生成、生产脚本辅助、系统配置排查、业务文档处理等高风险场景，这类错误复用会放大模型幻觉和自动化副作用，影响系统稳定性、审计可追溯性与合规可控性。

# 三、建议措施

为保障智能体在金融科技场景下安全、稳定、可持续演进，建议基于本项目已有的 Trace、Skill、Optimizer、云端自进化和审批面板能力，建设“采集-评估-生成-审批-分发-回滚”的闭环式自进化架构。具体工程落地实施方案如下：

**1. 建设以全链路 Trace 为核心的经验采集与评估底座**

自进化的前提不是让模型随意改写自身，而是将每次真实执行过程沉淀为可分析、可审计、可归因的数据资产。建议将 Agent 每轮执行统一记录为结构化 Trace，覆盖用户意图、模型调用、工具调用、Token 消耗、执行耗时、最终结果、错误节点、已使用 Skill、进化版本来源、组织信息及应用版本等关键字段。

**全链路执行观测：** 对每次 Agent Run 记录 LLM 节点、Tool 节点、Tool Result 节点和终态节点，形成可回放的执行树。通过工具调用次数、重复调用、失败重试、命令验证和最终响应质量，识别哪些会话具备沉淀价值，哪些会话存在稳定性或合规风险。

**技能效果归因：** 将 Trace 中的 usedSkills、evolvedSkills、技能版本、作者、组织信息与代码采纳事件关联，建立 Skill 维度的成功率、过程分、结果分、采纳率和异常告警指标。只有能够被度量、被追溯、被横向比较的 Skill，才适合进入持续优化链路。

**安全数据上传：** 对 Trace 中的用户输入、模型上下文、工具参数、工具结果和错误信息进行长度截断、二进制识别与超大 Trace 压缩，并保留上传超时与失败静默降级机制。通过“本地完整留存、云端受控上传”的方式，确保自进化分析既具备数据基础，又符合金融场景下的数据安全与最小必要原则。

**2. 构建在线沉淀与离线优化并行的双通道进化机制**

针对不同类型的经验来源，建议同时保留在线会话级沉淀和离线 Trace 批量优化两条通道，分别覆盖“即时发现”和“集中挖掘”两类演进诉求。

**在线沉淀通道：** 在普通会话成功完成后，根据工具调用阈值判断是否具备沉淀价值。对于复杂任务，可支持“直接触发”和“模型判断”两种模式：前者在达到阈值后进入 Skill 沉淀流程，后者先由模型判断该流程是否具备通用性，再决定是否向用户推荐。推荐后必须经过用户意图确认、Skill 草稿生成、详情确认，最终才能写入本地技能目录。

**离线优化通道：** 针对本地或云端积累的历史 Trace，通过兴趣评分筛选高价值会话，例如高工具调用、反复修正、错误恢复、领域流程探索等。优化器基于 Trace 摘要和已有 Skill 内容，生成“创建新 Skill”或“修补已有 Skill”的候选，而不是直接覆盖生产能力。

**控制技能碎片化：** 当 Trace 已经使用过某个 Skill 时，优先将经验归入该 Skill 的 patch 候选，而不是生成大量相似新技能。对于未使用 Skill 的高价值会话，再抽象为新的通用任务族 Skill，避免形成“一次任务一个技能”的资产膨胀，保障组织级技能资产的可维护性。

**3. 建立人机协同的审批、分发与回滚治理体系**

自进化能力必须坚持“模型生成候选，人工决定采纳”的治理原则。建议将所有 Skill 变更纳入候选态管理，提供 Diff、版本、来源 Trace、推荐理由、评估分数、审批状态和操作人信息，确保能力写回过程可解释、可追溯、可审计。

**本地候选审批：** 离线优化生成的候选保持 pending 状态，用户可在自优化面板查看来源 Trace、生成理由和完整 SKILL.md 内容。只有审批通过后，系统才写入自定义 Skill 目录，并自动刷新 Skill 缓存，避免模型直接修改运行时能力。

**云端进化分发：** 对已上传到技能市场的 Skill，可由云端 Trace Evolver 基于大量真实 traces 生成优化版本，经作者或管理员审批后发布到自进化更新通道。本地客户端拉取已发布候选后，可展示云端版本、本地版本、文件 Diff、评估分数和变更说明，支持一键安装，将个体经验转化为可控共享的组织能力。

**版本标记与回滚保护：** 进化产生的 Skill 需要写入明确标记（如 evolved-by），并记录 sourceVersion、targetVersion、candidateId 和来源 Trace。安装云端进化版本前，必须先备份本地旧版 Skill；安装失败时自动恢复，采纳后也可手动回滚或导出旧版备份，确保任何能力升级都具备可逆性。

**4. 将自进化指标纳入运营看板，驱动持续校准**

自进化不是一次性功能，而是一套长期运营机制。建议在 Dashboard 中持续跟踪 Skill 使用量、过程质量、结果质量、代码采纳率、进化版本使用占比、候选通过率、候选拒绝原因、回滚次数等指标，形成“数据发现问题-生成候选修复-审批发布-再观测效果”的持续校准回路。

在此基础上，可进一步将高质量 Trace 沉淀为评测集，把 Skill 更新前后的执行表现进行对照，筛选真正能降低工具调用次数、提升成功率、减少用户纠错、提高代码采纳的进化版本。最终目标是让 CMBDevClaw 不仅能完成单次任务，更能从每一次真实任务中提炼金融科技组织经验，逐步形成面向银行业务场景的可复用、可治理、可审计的智能体能力资产。
