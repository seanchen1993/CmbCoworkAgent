# DevClaw 插件与项目模式：Mods 整体优化分析与实施边界

日期：2026-10-23。核对范围：`codex/mods-v2` 当前代码；应用版本固定为 2.0.0。

本文区分现有能力、本轮开发内容和后续建议。代码审查可以定位结构性重复工作，不能代替性能测量，也不能据此承诺固定的耗时或 Token 降幅。

## 1. 结论与需要纠正的方向

Mods 适合承载插件的业务策略、流程组合、知识选择、业务校验和界面展示。平台需要提供稳定的数据和动作接口，并管理来源、权限、生命周期及执行结果。扩展机制的价值应体现在新增业务能够通过插件交付，而不是持续修改平台业务分支。

目前可组合流程和一致性检查已有较多实现，但项目模式的数据读取、知识准备、界面投影和创造交付还没有完全使用同一套公共协议。此前侧重逐条打通功能，尚未将这些热路径整体收敛；继续按单个问题增加缓存、脚本入口或专用页面，会扩大重复实现。

应先统一以下四条链路，再决定具体模块如何实现：

1. **读取链路**：同一状态版本形成一份只读快照，供原生界面、Mod 面板和模型上下文消费。
2. **执行链路**：策略生成计划，原执行器执行必要检查并通过唯一写入器提交，再读取结果和对账。
3. **上下文链路**：知识、配置与动态状态分别版本化，按任务选择，变化时失效，保留必需知识加载证明。
4. **创造链路**：来源检查、改造、配置、试用、验收、交付和开始使用共享同一候选与操作身份。

## 2. 当前架构事实

### 2.1 项目模式有两类状态权威

| 类型 | 当前入口及状态权威 | 合理改造方式 |
| --- | --- | --- |
| 原插件自有项目，如 AutoBiz | `harness-board/service.ts` 调用插件命令；原 Python、Hooks 和业务文件管理真实状态 | 插件提供状态与知识适配，Mod 组织策略、组合及展示，继续调用原合法写入器 |
| 标准 Host 项目 | `ipc/project-runtime.ts` → `HostProjectService`，由原生 SQLite 状态和操作票据管理 | 通过原 Host 服务读取和执行；Mod 不直接修改数据库 |

跨单元组合协调已有执行器，不应再产生第三份同名业务状态。公共接口可以统一，底层存储和执行器不必强制相同。

### 2.2 已有底座不能重复建设

当前 SDK 已提供 `platform.list/read/subscribe/poll/publish/act/status`、受控文件和进程、工具与命令注册、配置、store/state、会话及界面能力。方法是否可调用仍取决于作用域、授权和调用生命周期。

已有配置和目录缓存、阶段归因缓存、请求合并、Worker、取消、防抖、受限传输、提示事件缓存。未知交付结果对账、原会话试用关联和保存后“开始使用”也已有实现。下一步应收敛这些实现及入口，而不是把它们重新列为完全缺失。

当前原生公开 provider 已覆盖 workflow 观测等能力，但**尚没有统一的项目与 Feature 只读 provider**。存在通用调用机制，不等于所有项目业务数据已经开放给 Mods。

## 3. Python 查询和知识准备的实际问题

### 3.1 不只是新建聊天时加载

`standard-thread-turn.ts` 的标准轮次在进入模型请求前等待 `buildHarnessFeatureAgentContext`。选择插件上下文时，它继续调用知识渲染命令。当前核对路径未形成按完整输入版本复用知识正文的跨轮结果缓存。

知识 provider 启动 Python，原知识模块还可能启动 Node 收集器。现有单调用 3 秒、总收集预算 8 秒是失败与取消边界，不是缓存。全局并发限制为 2，也不等于相同请求只执行一次。

因此，慢请求可能重复支付排队、来源准备、Python 启动和导入、Node 启动、文件扫描、知识收集、序列化和提示组装成本。将同一条命令改成由 Mod 调用，并不会消除这些成本。

### 3.2 读取与写入应采用不同策略

| 场景 | 优化方式 | 一致性要求 |
| --- | --- | --- |
| 项目、Feature、产物状态展示 | 批量只读快照、按版本复用、事件触发失效、可见时订阅 | 可展示明确标记为刷新中的旧快照；不能伪称最新 |
| 当前阶段归因 | 复用已有 30 秒缓存、进行中请求合并、dirty 和失败退避 | 不能把失效后的阶段错误归到已开始的调用 |
| 稳定知识正文 | 按知识内容、配置、选择范围及插件版本缓存或预计算 | 必需知识变化或加载失败时不得使用过时成功结果 |
| 当前 Feature、用户输入和步骤状态 | 从当前运行快照按需构造小型动态上下文 | 必须与当前项目、Feature 和运行身份一致 |
| 状态推进、业务验收和审批 | 原执行器执行真实预检、必要 Hooks 和提交前复核 | 不能用显示缓存替代真实文件、状态、产物或审批检查 |

### 3.3 需要通用的 provider 协议

后续只读 provider 应声明输入、输出 Schema、作用域、依赖版本、是否可缓存、最大结果、取消方式及必需性。平台统一管理同键请求合并、容量、失效、超时、失败退避和生命周期；插件声明知识语义及选择策略。

缓存身份至少应覆盖插件及包摘要、工作区、项目、Feature、配置版本、所选知识单元、知识内容版本和权限代次。不能仅用插件名称或 TTL 作为身份，也不能将缓存授权视为仍然有效。

内容版本应在知识同步、实际文件变化或配置提交时维护；不能为了判断每次缓存是否可用，又在每轮请求前完整扫描同一知识库。观察丢失或来源不确定时应明确失效并补读，执行验收仍核对真实输入。

先用原服务实现适配，再逐步支持插件自有只读实现。Python 可以保留在业务计算和校验路径；如果测量证明有必要，再提供通用受管理 provider worker。不能先默认每个插件常驻一个 Python 服务。

## 5. 三个代表性场景

### 5.1 AutoBiz 衍生需求转换流程

本轮开发的通用创造者可读取实际来源、插入新步骤、修改技能或步骤、校验依赖并保存独立草稿。新版 AutoBiz 状态 Mod 从原编译器读取实际有效流程，调用原校验与写入器，保留知识和配置。

新增需求转换必须同时定义结构化产物、必要校验和下游输入。PRD 的插件侧业务断言要求保留上游需求及来源；只新增一个目录或提示词不能证明衔接成立。契约变化会使旧回执失效。原来源的必要校验受保护，作者尚未发布的新步骤允许继续对话修改。

这些内容解决可组合性和执行一致性，**没有自动消除原状态读取和知识准备的 Python 调用**。性能读链路需要按第 3 节单独收敛。

### 5.2 独立供应商插件

独立供应商场景使用同一套通用改造与组装入口，在原 Host 执行器中运行需求转换、资料整理和准入决策。它没有复用 AutoBiz 的 Python 状态存储或业务适配器。

该例验证公共改造、输入输出及资源保护规则可以跨业务复用；不能据此宣称任意未知旧插件均可一次自动转换。缺少可执行契约的旧插件仍需明确映射及实际校验。

### 5.3 workflow 工作树进度展示

已有公开 workflow provider、分页与订阅可作为数据来源。插件可用 Pane / surface 展示每个工作树及 agent 的阶段、状态、分支和清理进度，不需要平台为每个业务写一张专用看板。

平台继续提供真实 Git 与运行事实、操作身份、取消批准和清理结算。目录数量不能推算完成率；看得到进度也不代表可以任意恢复或删除工作树。

## 6. 性能、Token 与运行效果应分别验收

| 收益 | 可采用的机制 | 必须测量或保留的条件 |
| --- | --- | --- |
| 减少首字前等待 | 只读结果复用、后台预计算、相同请求合并、稳定知识缓存 | 冷/热准备耗时、进程次数、队列等待、失效正确性；不能跳过必需知识 |
| 降低本地资源占用 | 批量查询、共享订阅、增量投影、关闭后停止观察 | CPU、内存、I/O、IPC 字节、进程数量；不能每个面板新增扫描器 |
| 减少输入 Token | 稳定知识与动态状态分层、按阶段注入、来源摘要、按需检索 | 同一任务的输入量与完成质量共同对比；进程减少本身不等于 Token 减少 |
| 改善 Harness 效果 | 明确下一步、输入输出、必需检查、回执、失败与恢复 | 真实错误是否被阻断，重试是否重复副作用，模型是否使用正确知识 |
| 提高插件创造效率 | 公共契约、模块复用、统一诊断、原会话试用和版本比较 | 新增第二业务是否无需改平台，失败是否可定位，原业务语义是否保留 |

稳定提示前缀可能有助于模型服务端缓存，但实际命中和计费取决于模型供应商及请求内容，不能保证。必需知识、权限、产物验收和提交检查不能作为节省 Token 的删除项。

## 7. 统一实施顺序与验收门槛

### P0：先统一读取和上下文协议

1. 建立公共项目/Feature 只读 facade，适配现有 Host 与插件自有执行器，不创建新状态库。
2. 建立版本化只读 provider 与上下文结果缓存，分开稳定知识、选择目录和动态 Feature 状态。
3. 增加同一请求的来源准备、排队、进程、收集、渲染、模型及界面计时，记录命中与失效原因。
4. 将来源、契约、知识、配置、权限和实际运行身份用于统一诊断；继续复用已实现的对账与开始使用能力。

**验收**：相同输入的连续读取不重复执行相同冷计算；并发等价请求只执行一次；知识、配置、选择、来源、权限或阶段变化后准确失效；必需项失败不复用旧成功结果；不影响普通聊天及其他项目。

### P1：统一项目视图与创造交付体验

1. 原生项目页和 Mod 面板共用公共投影与订阅，增加明确扩展槽位。
2. 统一检查覆盖、输入输出和回执语义，业务实现留在插件。
3. 收敛原始转换、配置、试用、反馈、对账、保存和开始使用的状态与主要操作。
4. 用 AutoBiz 和独立 Host 业务同时验证，新增业务不得改平台业务分支。

**验收**：用户不需要理解多个内部状态框即可完成创造与使用；各页面对同一版本和结果的判断一致；改技能、改步骤、改知识和输入卡续接均有新的有效证据；公共回执保持兼容，插件私有元数据不扩散到公共 Schema。

### P2：观测、效果评测与复杂恢复

1. 复用 workflow 观察补齐项目/阶段/子 agent 关联，形成插件可 DIY 的进度与用量面板。
2. 根据测量结果决定是否需要受管理的长驻 provider；支持取消、卸载、崩溃及来源失效清理。
3. 逐类开放复杂调试恢复，明确文件、Hooks、工作树、外部动作的差异。
4. 将用户目标转为业务样例，比较版本间效果及成本。

**验收**：真实用户路径有可复现基线；每项优化同时满足功能、一致性、隔离和资源门槛；未知外部副作用不能自动重放或声称任意回滚。

以上为完整后续方案。本轮正在验收的可组合改造不应被描述为上述全部性能和界面收敛已经完成。
