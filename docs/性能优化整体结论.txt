整体结论

仓库已经做过一轮有效优化，尤其是消息查找、拖拽更新、文件监听器数量、扫描去重和组件懒加载。不过仍有三条主要性能瓶颈：
- 主进程卡顿：同步日志、sql.js 全库导出、同步 Git/文件操作。
- 长会话卡顿与内存增长：ThreadContext 全局刷新，历史线程状态和数据库常驻。
- 流式响应卡顿：每次 token 更新都重新解析完整 Markdown。
这些问题确实存在，不只是理论风险。

====================================================================
最高优先级
====================================================================

1) 同步日志阻塞 Electron 主线程  —  属实
   src/main/logging.ts:86-90 的 writeLine 每条日志都会执行 rotateIfNeeded（内含 existsSync + statSync，见 logging.ts:6-10）和 appendFileSync，全部同步。
   src/main/index.ts:106-110 代理了全部 console.*（log/info/warn/error/debug）。仓库约有 500 处日志调用。
   src/main/services/workspace-watcher.ts:344 还会在防抖之前记录每一个文件事件。执行构建、安装依赖或切换分支时，会产生大量同步磁盘写入。
   （注：原文档引用的 logging.ts:82 是 joinArgs；真正的同步写盘在 86-90 行。）
   建议：日志改成内存队列，异步批量写入；生产环境关闭 debug 日志；删除或采样 watcher 单文件事件日志。这是低成本、高收益优化。

2) ThreadContext 导致大范围重复渲染  —  属实
   src/renderer/src/lib/thread-context.tsx:1077-1079 的 ThreadProvider 把所有线程状态放进单个 useState<Record<string, ThreadState>>。
   src/renderer/src/lib/thread-context.tsx:3905 的 contextValue 会随线程状态变化而更新，多个消费者（Chat、RightPanel、Sidebar、Harness 等）可能重新渲染。
   后台线程的一次状态变化，也可能触发当前重型页面执行。
   建议：按线程建立 external store，使用 useSyncExternalStore 或 Zustand selector；拆分 actions/state context；组件只订阅当前线程需要的字段。

3) 访问过的线程长期占用内存  —  属实
   src/renderer/src/lib/thread-context.tsx:3613 的 initializeThread 会保留每个访问过的线程及其消息、文件列表、内容和子代理记录；3837 的 cleanupThread 基本只在删除线程时调用。
   主进程 src/main/agent/runtime.ts:1745 的 checkpointers 是无上限 Map（注释明写 "Per-thread checkpointer cache"）。sql.js 会把整个 SQLite 文件载入 WASM 内存。
   本地实测：373 个线程数据库，总计 128.75 MB，最大单库 17.57 MB。
   建议：渲染层和主进程都增加 LRU，当前运行线程固定保留，其余只保留最近 5～10 个；只读 checkpoint 查询结束后立即关闭数据库。

4) sql.js 每次保存都导出整个数据库  —  属实
   src/main/db/index.ts:32-33 在防抖后调用 db.export()，再用 writeFileSync 写完整数据库。src/main/checkpointer/sqljs-saver.ts:195 也采用同样模式。
   对当前 4.14 MB 主库实测：全库导出平均 1.41 ms，同步写盘平均 5.28 ms，单次最大约 11 ms。
   这些工作都在主线程，数据增长后会进一步恶化。
   短期可延长防抖并在 worker 中导出和写盘。长期建议迁移到支持 WAL 和增量写入的原生 SQLite，并放入 worker/utility process。

5) 流式 Markdown 累积接近 O(n²)  —  属实（比原描述更严重）
   src/renderer/src/components/chat/MessageBubble.tsx:718 每次流式更新都会把完整文本传给 StreamingMarkdown。
   src/renderer/src/components/chat/StreamingMarkdown.tsx 每次都重新执行 ReactMarkdown、GFM 和代码高亮。
   ⚠️ 关键事实：isStreaming 虽在接口声明（第 9 行），但组件体内（第 114 行）根本没有解构使用——它完全无效，比"没有改变解析策略"更彻底。
   ✓ 已做的优化：插件已提到模块作用域（第 72-73 行 REMARK_PLUGINS / REHYPE_PLUGINS），避免每次重建插件数组。剩余问题是全量解析仍每 token 触发。
   建议：流式期间以 30～60 ms 或 requestAnimationFrame 节流；暂时关闭代码高亮；结束后再执行完整 Markdown 和 highlight。长回答会有明显改善。


====================================================================
次高优先级
====================================================================

6) Dashboard 一次刷新产生多个 ES 请求  —  属实
   src/renderer/src/components/dashboard/use-dashboard.ts:1903 的 fetchAll 用 Promise.all 并发调用 5 个 IPC，主进程进一步拆成约 7 次 ES 查询。
   "旧请求不会真正取消"准确：只有 id !== fetchIdRef.current 的 stale-guard（第 1912 行），没有 AbortController，底层 ES 查询仍会跑完。
   建议合并为 snapshot IPC，使用 ES _msearch、15～60 秒共享缓存、in-flight 去重和 AbortController。

7) Trace 查询扫描全部历史文件  —  属实
   src/main/agent/trace/collector.ts:835 的 listTracedThreads 列出全部目录；848 的 readThreadTraces 读取并解析某线程全部 jsonl，无索引。
   当前本地有 296 个目录、756 个 JSONL、共 23.41 MB。建议维护轻量全局索引，查询时只读取最新候选文件。

8) 工作区首次加载  —  ⚠️ 部分过时，核心问题仍在
   原文档引用的 src/renderer/src/models.ts:3005 已不存在：递归枚举已重构进主进程的 loadWorkspaceFilesDeduped（带去重 + 后台加载，见 thread-context.tsx:2031），"渲染层递归枚举"的描述已被淘汰。
   但核心问题仍成立：扫描结果仍按线程常驻在 thread state 的 workspaceFiles 字段（thread-context.tsx:2041，状态定义见 413/561）。
   src/renderer/src/components/panels/RightPanel.tsx:1962 的 buildFileTree 随后复制、排序并构建整棵树。
   建议改为目录展开时按需读取，并增加条目上限、取消信号和非活动线程文件树回收。

9) Sidebar 没有虚拟化  —  属实
   src/renderer/src/components/sidebar/ThreadSidebar.tsx:375 订阅整个 threads 列表，无虚拟化。线程数量达到数百后，任何状态更新都可能触发列表分组和大量节点更新。
   建议使用最小状态 selector、React.memo 和列表虚拟化。

10) 部分同步 Git 操作可冻结 UI  —  属实
   src/main/services/adoption-tracker.ts:1338 使用 execFileSync 执行 git rev-parse，1349 执行 git diff --cached，均为同步、5s 超时。最长等待可达数秒。
   建议改异步执行并限制并发。


====================================================================
优化方案（按"收益/成本"排序，分三批落地）
====================================================================

总体策略：先做"低成本、立即可感知"的主进程与流式两条线，再做架构性的状态/内存改造，最后做存储底座迁移。每一步都可独立合入、独立回滚。

──────────────────────────────────────
第一批：低成本快赢（建议本周内，预期投入 1～2 天）
──────────────────────────────────────

P0-A 异步日志队列（对应问题 1）
  方案：
   - logging.ts 引入内存环形队列 + 定时 flush（如每 200ms 或累计 64 条），用 fs.appendFile（异步）或 fs.createWriteStream 落盘；rotateIfNeeded 改为按字节累计计数，避免每条 statSync。
   - index.ts 的 console.* 代理只入队，不直接写盘。
   - 增加 CMB_LOG_LEVEL 环境变量（显式设置即严格生效）；生产环境对 DEBUG 采样降频（默认保留 1/20），而非整段丢弃，既压低高频突发量又保留排障线索；INFO/WARN/ERROR 始终保留。
   - workspace-watcher.ts:344 的单文件事件日志降级为 console.debug：dev 全量、打包构建走上面的 1/20 采样。
  风险：低。日志丢失窗口仅为 flush 间隔，进程退出时主动 flush 一次即可。
  验证：构建/切分支时观察主线程不再有成片同步写盘；对比优化前后日志文件内容一致性。

P0-B 流式 Markdown 节流 + 流式期间关高亮（对应问题 5）
  方案：
   - StreamingMarkdown 接受并真正使用 isStreaming：流式中用 REMARK_PLUGINS 但跳过 REHYPE_PLUGINS（rehypeHighlight），渲染纯文本/无高亮；isStreaming=false 时再走完整管线。
   - MessageBubble 侧对传入文本做 rAF 或 30～60ms 节流，避免每 token 触发 ReactMarkdown。
   - 组件用 React.memo + 自定义比较，仅当节流后的文本变化才重渲染。
  风险：低。仅影响渲染节奏，不改数据。
  验证：长回答（>5KB）流式过程中测 FPS / 输入响应；结束后高亮正常出现。

P0-C 同步 Git 改异步（对应问题 10）
  方案：adoption-tracker.ts 的 execFileSync 改 execFile（promisify），captureStagedSnapshotsForCommit 整体 async 化；对并发 git 调用加 p-limit（如并发 2～4）。
  风险：中。需确认调用方都能 await；rev-parse/diff 的时序依赖要保持。
  验证：大仓库提交时 UI 不冻结；快照内容与同步版本一致。

──────────────────────────────────────
第二批：架构性状态与内存（建议 1～2 周，需要测试护栏）
──────────────────────────────────────

P1-A 线程状态 external store + selector 订阅（对应问题 2）
  方案：
   - 把 threadStates 从单个 useState 迁出到 external store（Zustand，或 useSyncExternalStore + 手写 store）。
   - 拆分 actions context（稳定引用，不随状态变）与 state 订阅（按 threadId/字段 selector）。
   - 25 个消费者改为只订阅自己需要的切片，后台线程变化不再触发当前页重渲染。
  风险：中高。改动面大、消费者多，建议分组件渐进迁移，先迁 Sidebar/RightPanel 这类高频重渲染者。
  验证：用 React Profiler 对比"后台线程刷新时当前 Chat 的 commit 数"应降到 0。

P1-B 渲染层 + 主进程线程 LRU（对应问题 3）
  方案：
   - 渲染层：维护访问顺序，超过保留上限（当前线程固定 + 最近 5～10 个）即对其余线程调用 cleanupThread，释放 messages/workspaceFiles/子代理记录。
   - 主进程 runtime.ts checkpointers 改 LRU；只读 checkpoint 查询用完即 close() 释放 WASM 内存。
  风险：中。需保证被回收线程再次进入时能正确重建；正在运行/流式的线程永不回收。
  验证：连续访问 30+ 线程后测渲染进程与主进程内存曲线应趋于平稳而非单调上升。

P1-C 工作区文件树按需加载 + 非活动回收（对应问题 8）
  方案：目录展开时才向主进程请求该层文件；workspaceFiles 加条目上限与 AbortController；非活动线程的文件树随 P1-B 的 LRU 一并回收。
  风险：中。RightPanel 树构建逻辑（buildFileTree）需适配增量节点。
  验证：超大工作区首屏加载时间与内存占用下降；展开/折叠交互正常。

──────────────────────────────────────
第三批：存储底座（建议作为独立里程碑，风险最高）
──────────────────────────────────────

P2-A sql.js 导出/写盘移出主线程（对应问题 4，短期）
  方案：延长防抖（如 100ms→300～500ms 合并写）；db.export() + writeFile 放到 worker_threads / utility process，主线程只传 buffer。
  风险：中。需处理 worker 与主库的一致性与退出时 flush。
  验证：保存高峰期主线程不再出现 5～11ms 的同步停顿。

P2-B 迁移原生 SQLite（对应问题 3/4，长期）
  方案：用 better-sqlite3 / 原生 SQLite（WAL + 增量写）替换 sql.js，彻底消除"全库载入 WASM"和"全库导出"，并天然支持增量写入。
  风险：高。涉及数据迁移、打包原生模块、跨平台编译。建议先在分支做兼容层与一次性迁移脚本。
  验证：内存不再随库大小线性增长；写入为增量；旧库可平滑迁移。

P2-C Dashboard snapshot IPC（对应问题 6）与 Trace 索引（对应问题 7）
  方案：
   - Dashboard：5 IPC 合并为 1 个 snapshot IPC，主进程用 ES _msearch 一次发出；加 15～60s 共享缓存、in-flight 去重、AbortController 真正取消旧请求。
   - Trace：维护轻量全局索引（threadId → 最近 N 条的文件/偏移），listTracedThreads/readThreadTraces 只读最新候选文件，避免全量扫描解析。
  风险：中。需保证缓存失效与数据新鲜度平衡。
  验证：Dashboard 刷新网络请求数下降、切换时间区间不再叠加重复请求；Trace 取最近 20 条耗时与文件数解耦。

落地与度量
──────────────────────────────────────
- 度量基线：以"主线程长任务（>50ms）数量""渲染进程内存峰值""长回答流式 FPS""Dashboard 刷新请求数"为四个核心指标，每批前后各采一次。
