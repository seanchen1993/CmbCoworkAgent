# Mods 轻量插件重构说明

日期：2026-10-30。面向：普通使用者、插件作者、平台开发者。

**阅读状态：修订架构已完成三方独立复审，核心修正已实现，主要联合路径已验证。本文分别说明设计、已验证能力和适用边界；本轮测试不代表任意业务、任意框架或真实模型产出质量均已验证。**

详细技术约束与验收要求见 [修订方案](./mods-lean-architecture-revision-2026-10-30.md)。本轮只修改 Mods-v2，应用版本保持 2.0.0，不打包、不触发 GitHub Actions。

## 一、这次要解决什么问题

目标是：**用较少的重复上下文和操作，保持原有业务要求，并让某项能力可以独立替换。**

原 AutoBiz 已能完成需求、规格、设计、代码与交付工作，也有知识加载、Hooks、产物检查和多工作树执行。问题在于，这些职责分散在 Skill、脚本、配置和 workflow 中。改一个环节，作者需要追踪多个文件，模型也需要反复阅读许多操作说明。

本次不以“把原脚本改名为 Mod”作为完成标准。需要重新明确每个部分的职责，让平台管理运行事实，让插件管理业务方法，并把可替换的边界写成明确契约。

例如，公司希望更换交付文档规范，应该修改或更换业务规则 Mod，重新生成并验证插件。不能表面换了规则，下游交付 Mod 又偷偷运行一份旧规范。这正是本轮独立评审发现并要求修正的问题。

## 二、各部分分别做什么

| 部分 | 通俗理解 | 具体作用 |
| --- | --- | --- |
| 平台公共能力 | 负责运行秩序和记录的基础设施 | 确认用的是哪个版本、允许做什么、实际运行了什么、输入是否变化、检查是否通过，再提交阶段状态 |
| Mod | 可以独立开发和替换的功能部件 | 选知识、检查业务产物、执行与核验测试、展示工作树变更等 |
| Skill | 对模型说明这一阶段怎样完成工作 | 输入是什么、要形成什么结果、遇到不明确问题如何处理 |
| workflow | 一次任务内的确定性执行顺序 | 创建工作树、调子代理、编译、测试、处理有限修复、请求合并批准 |
| 插件 | 可安装使用的一套完整方案 | 把阶段、Mods、Skills、资源、配置和 Hooks 组合在一起 |
| 创造者 | 帮作者完成组装和修改的助手 | 理解要求，发现或编写能力，更新组合与依赖，试用、修改，生成插件 |

Mods 本身不是新的大模型，也不自动理解全部业务。它的价值是让确定性功能成为正式扩展：有入口、有参数、有权限、有版本、有真实运行结果，可以被其他插件复用。

### 为什么平台仍然需要开发

插件可以决定“订单需求必须有超时场景”，但不应自己宣称“我有权修改任意文件”或“我已获得用户批准”。平台必须提供可信的权限、输入和执行记录，插件才能安全地使用这些能力。

本轮平台增加的是通用能力，例如把已安装提供器的真实身份固定给检查器、将已声明 workflow 的实际摘要自动绑定、向需要的检查提供原始请求的来源元数据。元数据包含项目身份、字节数和摘要，检查器用它核对基线产物中保存的原文。它们也适用于文档审批、数据处理和其他项目插件，不涉及 AutoBiz 专用阶段名。

## 三、普通用户会怎样使用

普通用户仍然选择插件、填写必要的项目与知识配置、提出任务。无需理解 Mod 源码，也无需自己编辑状态文件。

新版默认流程分为五步：

1. **确认需求基线。** 模型整理需求、澄清和范围。系统保留原始请求，用户确认整理结果。
2. **形成需求与验收定义。** 生成需求说明、规格和验收场景，对照已确认基线检查。
3. **形成设计与实施方案。** 生成设计、任务和批次依赖，完成方案检查与成果接受。
4. **实现并验证代码。** workflow 调用子代理，在工作树中实际编译、测试、检查，再通过原生合并确认。
5. **准备交付并归档。** 生成交付说明和可追溯证据，保留原始产物。未经明确要求，不把“交付准备完成”表述为已经远程发布。

增加需求确认是有意的取舍。若用户要求“查询必须两秒内返回”，模型不能在实现困难后同时删除需求清单和规格中的“两秒”，再用二者一致证明合格。需求基线先被独立接受，后续作者不能在本阶段一起改掉它。

需求确实变化时，需要明确修订并重新接受，受影响的方案、代码和交付证据重新验证。系统不能把聊天中一句普通补充自动当成已经批准的新基线。

本轮默认代码执行路线限于后端项目：Node 的受支持 JavaScript 源码，或 Maven 编译 Java、再由 Python unittest 验证的路线。独立的 Python doctest 执行与证据 Mod 已有真实运行验证，但使用时需要明确更换组合声明和提供器。前端构建、任意语言和任意测试框架尚未承诺通用支持。

### 用户怎样知道成功

成功需要区分层次：

- 文档格式或业务检查通过：表示对应规则已经检查实际产物。
- 编译或测试通过：表示原生执行器真的运行了对应命令并记录结果。
- 阶段完成：表示该阶段必需检查和成果接受全部满足，平台已经提交状态。
- 项目完成：表示声明的各阶段都完成；不自动意味着已经上线或发布。

界面和报告应直接给出当前阶段、结果、阻断原因与下一步，不要求用户阅读模型的“我已经完成了”来判断。

## 四、业务效果怎样保持

### 1. 知识不靠反复粘贴保留

知识 Mod 读取用户绑定的组织知识，按照明确的部署单元和阶段映射选择材料，同时保留来源和摘要。未标注资料不被静默丢弃，最近的 AGENTS 约束继续保留。

前插“需求转换”或后接“E2E”时，创造者需要补齐新阶段知识映射；不应为此修改平台，也不应因为阶段名称不在旧清单中就无法运行。

大知识库当前通过 `knowledgeRoots` 明确绑定目录范围，每次重新扫描所选子目录，再读取相关正文，避免缓存文件清单漏掉新增资料。未实现通用知识索引绑定；只扫描所选目录时也不会声称已经完整搜索整个知识库。

### 2. Hooks 不会因为重构消失

现有安全 Hooks 和必要业务约束保留。是否把某条 Hook 迁入规则 Mod，取决于职责，而不是为了统一名称：

- 对整个工具执行都有效的安全约束，继续使用相应 Hook 或公共运行边界。
- 对某阶段业务产物的判断，适合成为规则 Mod 的检查动作。
- 每个阶段都必须满足的提交条件，由平台的必需检查机制执行。

迁移时需要保留触发时机、输入、失败效果和证据。只复制脚本却没有接回触发入口，不算完成迁移。

### 3. 规则检查与执行检查分别负责

规则 Mod 判断“需求、设计、交付文档是否满足业务规范”。执行与证据 Mod 判断“运行是否真实、输入是否对应、测试统计是否完整、合并是否有原始记录”。

两者缺一不可，平台要求全部必需检查通过。交付 Mod 不再复制全部业务规则，因此可以真正更换业务规范；但它仍会验证自己需要的字段、实际文件摘要和执行证据。

### 4. 减少上下文不等于删掉必要约束

每个子代理收到本批任务、依赖批次规格、引用的决策正文、来源位置和设计约束。依赖通过程序计算，不由模型随意决定省略什么。

用户在基线中确认的补充决定，也必须原样进入下游定义，并映射到关联需求的真实需求条目与验收场景。最终 E2E 作者按仓库取得各批次所需材料的合并结果，不能只收到任务名称和规格编号。这种映射保证来源和结构可追踪，仍需业务验收判断语义是否真正实现。

例如第二批依赖第一批的权限模型，即使第二批只修改查询接口，也必须拿到权限规则。决策编号本身不够，必须能取得该编号对应的正文。缺少定义时应阻断并定位缺项。

不相关的完整历史和操作说明可以减少；无法可靠拆分的必要内容仍应保留。

## 五、作者如何修改一个插件

### 场景 A：在前面增加“需求转换”

作者向创造者描述输入和输出，例如：“先将客户需求表转换为统一需求清单，再进入确认与规格阶段。”

创造者需要完成的工作包括：

1. 发现已有转换 Skill/Mod，或生成所需能力。
2. 声明新产物和检查规则。
3. 将产物加入下一阶段的真实输入依赖，补齐角色与知识映射。
4. 保留原需求来源和确认边界，不让转换产物替代用户批准。
5. 试运行，并验证转换失败会阻断、转换结果修改会使下游旧结果失效。
6. 保存为新的插件版本，安装后从普通项目入口使用。

“只插一行阶段名称”不足以完成这种改造。创造者的作用正是帮助作者补齐这些必要连接，并把缺项具体展示出来。

### 场景 B：替换某个业务规则

例如将中文交付模板换成公司的英文模板，产物结构和运行证据保持兼容。替换规则 Mod 后，编译器从实际已安装能力中解析身份并固定；workflow 及交付检查只接受这个固定提供器的真实结果。

无需同步修改另一份隐藏的旧规则。若新规则改变了产物结构，则还需显式适配消费方契约，不能以“可组合”为由忽略不兼容。

### 场景 C：更换测试框架

执行与证据作为完整 Mod 替换。新的提供器必须公开测试输入格式、执行方法和证据格式。workflow 使用这些契约，而不把 Node、Java 或第三个框架名称写死。

首轮已有 Node 和 Java/Maven 路线；第三框架必须通过实际运行验证后才能宣称支持。只改下拉框、复制包名或返回一份 `passed: true` 都不算支持。

当前 Python doctest 提供器已跑通真实编译、批次测试、最终测试及原始证据核验。它验证了完整提供器可替换；并不表示任意填写一个框架名字，系统就会自动具备该框架能力。

### 场景 D：增加工作树 Diff 界面

独立界面 Mod 使用平台通用 Git 读取和 workflow 观察接口，展示目录、基准和文件变更。它既可以读取 workflow 提供的工作树，也可以让用户选择有权限的仓库和基准。

这种界面能力可以被 AutoBiz 或其他插件使用。平台补齐一次通用接口后，作者可以继续调整展示方式；平台无需为每个插件分别开发一套 Diff 页面。

| 位置 | 改动及作用 |

| `resources/native-compositions/autobiz-lean/project/composition/source.json` | 声明五步流程、输入输出、角色、知识映射、必需检查和执行绑定 |

## 七、评审要求保留的限制

1. **测试通过不能证明所有业务都正确。** 还需要明确业务样例、场景核对、独立审查与代表性的错误实现验证。
2. **本轮不允许模型自动削弱失败测试。** 确认为生产代码问题时可进行有限自动修复；诊断为测试问题时保留失败记录，提示审查测试变更，再进入新运行。旧失败不回写为成功。
3. **换 Mod 需要重新编译和验证。** 旧源码的批准和成功记录不能自动转移到新源码。
4. **接口开放不等于任意脚本自动成为 Mod。** 脚本仍需声明入口、参数、权限及结果契约，接入真实调用位置。
5. **减少材料不等于已经省下相同比例的 token。** 子代理、工具读取、修复轮次都可能产生额外消耗，需要完整计量。
6. **组合有明确大小边界。** 单次产物检查最多覆盖 8 个文件，包含当前产物和上游输入；编译阶段会提前拒绝超限。较大的原规则提供器可通过完整 source-set 导入，其他符合单 Mod 作者预算的提供器可独立准备、检查和安装。
7. **本轮 Lean 插件尚不能直接从另一个项目身份继承需求基线并从中段调试。** 基线绑定原项目身份，新建调试分支具有新身份，会被来源检查拒绝。当前应重新从基线开始；未来需补明确的跨项目分支来源协议，不能通过改写已接受基线或取消身份检查绕过。

## 八、当前证据能说明什么

已有受控验证覆盖了原生 Host、真实 workflow、Git、Node/Java 编译测试、来源摘要与 Hooks；独立 worktree Diff 也做过桌面验证，长会话做过滚动与拖动测试。这些成果会保留并继续回归。

本次独立评审表明：固定模板运行成功，仍不能替代规则替换、前插后接、需求基线和必要上下文的验证。新增用例已覆盖这些变化，后续修正仍需经过最终联合复验。

当前固定样例重新测得：编译后 Skill、知识正文和必读契约合计从 **89,485 降至 33,595 UTF-8 字节**，减少约 **62.46%**；这一测量范围内的材料操作从 50 次降至 33 次。新版已经包含独立需求基线和新增必读契约。此前 25,211 字节是评审前版本的历史值，不再作为当前结果使用。

上述数字不包含 Host 消息封装、产物正文、workflow、子代理提示、工具返回和重试，更不是总 token 或费用下降比例。确定性测试检查了必要约束的保留与错误阻断，尚未证明在同一模型下所有真实项目的产出质量都不降低。

最终报告需要分别给出功能兼容性、业务验收结果、父子代理完整消耗、延迟与桌面体验。受控模型输出用于验证确定性执行链时会明确标注；真实模型质量尚未比较的部分不会声称已经证明。

本轮可复查的结果如下。原生 Host、SQLite、QuickJS、workflow、Git、编译和测试使用实际实现；模型写作及用户确认决定由测试提供。

| 验证 | 本轮结果及范围 |
| --- | --- |
| 完整项目链 | 3 条通过：英文规则替换并后接独立检查、Java/Maven 路线、真实 Node 失败后仅修生产代码；均推进至项目完成 |
| 后接步骤 | 英文规则场景完成五阶段后，由独立 Mod 检查资料引用与摘要衔接；先失败阻断，再修订、接受、完成。该附加检查不替代代码 workflow 内的真实应用 E2E |
| 前插和独立业务 | 需求转换前缀组合、非 AutoBiz 报告流程分别通过；覆盖来源变化失效及末尾检查失败后修订 |
| 第三执行框架 | Python doctest 真实编译、批次测试、最终测试、重放和 `code.verify` 通过；没有把这一项表述为第三框架的五阶段 Host 全链 |
| 测试问题 | 真实测试失败后诊断为 `test_bug`，保留失败测试和回执，不改断言、不重跑、不合并 |
| 创造者与项目入口 | 6 个项目入口脚本、18 个创造者流程脚本全部通过；覆盖配置、确认、复用、恢复和结果审查 |
| 工作树和聊天 | 工作树 Mod 10 项回归通过；聊天性能 9 个脚本通过，400 条混合高度消息拖动用例中可见空白帧为 0 |

## 九、后续开发如何组织

方案先通过独立评审，再按文件职责并行实施。公共编译绑定、需求基线与规则、知识与创造者发现分别开发；workflow 和跨模块证据由主代理整合。

联合验收不仅重跑原样例，还要实际更换规则、前插需求转换、追加失败与成功的 E2E、更换执行提供器、在非 AutoBiz 场景复用能力，并检查输入变化和授权撤销能否正确阻断。

只有这些验证完成，才能把“架构合理”进一步表述为“实现可用”。
