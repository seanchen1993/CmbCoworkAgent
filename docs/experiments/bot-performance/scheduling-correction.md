# Bot 调度修正：保持并行能力 · 2026-11-17

用户要求：不要通过限制并行任务数来通过性能测试，保留当前架构的高吞吐能力。

已撤销上一轮新增的「4 个执行名额 + 2 个沟通名额」。生产入口恢复 `Number.POSITIVE_INFINITY`，没有新增 Host 同时运行数上限；同 thread 租约、资源锁、原有队列规则继续生效。只限制每次调度循环连续占用主线程的时间，不等待已有任务结束才启动下一批。

原方案和原始数据保留在[首轮优化记录](optimization.md)，并标明已撤销。只启动 4 个、让 496 个排队的耗时不能作为 500 并发任务的性能改善证据。查询、定向刷新、Feature 分页和记忆缓存四类优化继续保留。

最终验证：**134 个文件、2,585 条 Bot 定向回归通过**，Node 类型检查通过；500 个模拟工作及其 500 次结果回传完整通过。仍保留一组计时长尾样本，详见下文，不宣称延迟稳定达标。

## 实现

- [生产入口](../../../src/main/bots/local-service.ts) 恢复原并发配置，删除新增 admission 模块及执行/沟通名额分类逻辑。
- [Host](../../../src/main/bots/host.ts) 按约 8 ms 的调度时间片通过 `setImmediate` 让出事件循环，后续继续启动所有可运行任务。没有固定「每批只运行 4 个」的规则。一个同步 SQL/回调不能被时间片抢占，8 ms 不是用户响应 SLA。
- 已有回调提前调用 wake，也必须遵守这次让出；不会被微任务连续唤醒绕过。主对话仍沿用原来的队列优先级，结果仍排队，不变成 Steer。
- 跨时间片只保留未取得 runtime 租约的线程，避免反复探测不可用资源。每个时间片重新判断正在运行的线程；runtime 可用事件允许重新尝试。
- [任务队列](../../../src/main/bots/store.ts) 新增 queued-only 的 `bot_tasks_admission` 优先级索引，匹配原有排序及 rowid 同时间戳顺序，避免为每次 LIMIT 1 选择重新排序整个待办队列。群聊范围、授权、同线程互斥及命令/Workflow 可运行条件均保留。索引和 SQL 复用同一优先级表达式。

仅修改 Bot 相关调度和测试，没有改变普通对话/项目模式的原生执行器，也没有改 IM 网关或 ES。此次新增的是 Bot 本地 SQLite 索引。

**保留长尾，不选择性报好看的结果：**完整套件记录到一次 1,684.01 ms 的事件循环 tick 间隔；隔离诊断最大间隔 45.66 ms，没有重现该长停顿。隔离诊断 GC 日志中有数十毫秒停顿，但没有原轮次的 GC 证据，不能把原来的 1.68 秒直接归因于 GC，也不能据此声称已经修好。旧完整基线启动 500 个任务为 648.56 ms；当前两轮存在明显波动且新增了启动期间消息，因此不宣称稳定的总体延迟/吞吐提升。已确认的是并行能力未被减少、用户消息可以在批量启动期间被处理、全部结果可以返回。

8 项快速场景在第一次定时器执行前已全部启动；没有采到启动期间 tick 的最大间隔记为 `null`，不是 0 ms。

## 集中完成时发现并修复的边界

首轮完整压测在 500 个任务全部启动后，完成与回传队列排空超时。单独复测一度通过，说明不能仅靠再次运行掩盖时序问题。

增加可控时间片回归后稳定复现：主对话和一批后台任务在两个调度片之间结束，但跨片缓存仍把主对话 thread 当作运行中而排除，后续 `work_result` 留在队列。模拟 runtime 不额外发送 onAvailable 时，没有新的唤醒来解除排除。

修复为只跨片保存 acquire 返回 null 的线程；正在运行的线程每片重新计算。回归同时验证 32 个任务的 32 次回传全部执行、同 thread 互斥保留、不可用资源不轮询、runtime 可用后重新尝试。没有增加轮询或降低并发来绕过该问题。
