# Bot 性能评审与本地压测 · 2026-11-17

> 后续状态：查询、刷新、Feature 和记忆优化已落地；执行调度按用户反馈改为保持原有并行能力，只优化调度开销与事件循环让出。见[调度修正记录](scheduling-correction.md)及[首轮优化结果](optimization.md)。以下保留优化前的评审原文，数值与问题描述代表当时版本。

本轮确认五类可优化的性能问题：任务查询没有充分使用范围/排序索引、无关变更重复刷新已加载任务、Feature 列表/详情请求叠加、执行调度缺少主机级并发约束、记忆准备重复同步读取。生产代码未修改；查询优化仅在隔离测试数据库中对照验证。

## 目的与范围

用户要求全面 review 和测试 Bot 模块性能。覆盖主 Bot 调度、独立任务、技能交办、Steer、结果回传、Feature/Team/Workflow 状态、群聊、附件、浏览器、记忆、资源锁和运营统计。

本轮不把“功能断言通过”当成“性能达标”。性能数字为单台开发机合成负载观测，没有生产 SLA 阈值；没有真实模型、招乎服务端或生产 ES 压测。未更改普通对话、项目模式或 IM 网关行为。

## 主要发现

### P2 · 任务目录的工作量随总任务数、命令数及单任务历史增长

位置：[列表 SQL](../../../src/main/bots/store.ts#L1011)、[状态投影](../../../src/main/bots/store.ts#L898)。

`(? IS NULL OR w.audience_key=?)` 让查询计划只能按 `bot_id` 使用 `bot_work_owner` 索引，不能直接按会话范围和 ordinal 取前 40 项，需要临时排序。每个候选还会计算相关子查询；`background_busy` 对命令表扫描，`execution_state` 对同一任务历史按状态重新排序。

| 输入 | 实际列表 API 中位数 | 输出大小 |
| --- | ---: | ---: |
| 5 万历史轮次、2,000 个任务、0 个后台命令 | 12.77 ms | 22,333 B |
| 同上，100 个 accepted 后台命令 | 83.41 ms，样本 p95 86.62 ms | 22,333 B |

测试只替换首屏 SQL 的精确 audience 谓词，保持其他逻辑和现有索引不变：0 命令时 **11.25 → 0.48 ms**，100 命令时 **80.98 → 2.04 ms**。全部返回列值一致，计划变为 `(bot_id, audience_key, ordinal)` 范围检索。这是测试中的 SQL 对照，不能称为已落地的 API 提升。

同一个任务的历史从 100 轮增长到 1 万/5 万轮，`getWork` 从 0.18 ms 增长到 6.25/30.98 ms；输出仍约 690 B。5 万轮读的定时器延迟 31.54 ms，说明小结果并不等于小查询成本。

建议：有/无 audience 分别构造明确条件，先按正确索引选出页内 ID，再计算状态；后台命令归属批量聚合；“活跃状态”和“最近一次结果”分开按索引读取，避免扫描全部历史求状态。保留 Team/Workflow、等待输入、未汇总结果等状态语义及所有分页数据。

### P2 · 无关事件会重刷已加载的全部任务

位置：[全局快照订阅](../../../src/renderer/src/components/bots/use-bots.ts#L43)、[额外任务刷新](../../../src/renderer/src/components/bots/use-bot-works.ts#L46)。

除记忆事件外，任何 Bot 事件都刷新全局快照；revision 又使当前任务目录刷新。加载更多后，`extra` 中的任务每 40 个串行查询摘要；合并使用循环中的 `find`，任务数增加后还有二次复杂度的比较成本。

在已加载 2,000 项、面板当前仅展示 6 行的场景，一个其他 Bot 的表情事件产生 **1 次 snapshot + 1 次 list + 49 次 summaries**。模拟每次 IPC 10 ms，请求跨度 **685.4 ms**。10 次间隔 20 ms 的事件产生 10 次快照、10 次列表和 57 次摘要请求，跨度 886.2 ms。单次最多 40 项、同一目录只保留一条刷新链，这些限制有效，但不能避免总量放大。

建议：按 Bot/群/任务 ID 定向失效；只刷新变化的任务及当前可见页。展开历史保持稳定游标，需要时刷新，不能为了减负静默丢掉已加载数据；摘要合并用 ID Map。避免把每个附件进度事件变成整个控制面刷新。

### P2 · Feature 刷新缺少跨轮并发合并，列表缺少有效分页

位置：[详情 effect](../../../src/renderer/src/components/bots/BotFeaturePanel.tsx#L174)、[Feature 列表 hook](../../../src/renderer/src/components/bots/BotFeaturePanel.tsx#L283)、[列表查询](../../../src/main/bots/feature-store.ts#L152)。

详情的 `pending` 是 effect 局部变量，revision 改变后重新初始化；清理只忽略旧结果，不取消或等待旧请求。列表也只通过 `current` 防旧结果落地。150 ms 合并可以处理密集事件，但不能处理持续变更期间的慢请求。

实际组件测试：10 个同范围事件间隔 180 ms，列表/详情每次模拟 600 ms，产生 **10 次列表 + 10 次详情，峰值 8 个请求同时在途**。单次详情内部限制 4 个会话状态读取，但这个限制无法约束多次详情请求叠加后的总 I/O。

另一个问题是 UI `taskRows` 默认 `limit=-1`。2,000 个 Feature、每个 50 条操作历史时，返回 **487,591 B**、中位 **33.20 ms**。仅加 `LIMIT 20` 仍需 **28.09 ms**；计划在操作选择和外层列表排序处都有临时 B-tree，说明只加 UI 限量不足以解决查询成本。

建议：同一 Feature 的请求跨 effect 保持单飞和 dirty 合并，切换后真正停止无用读取或复用已有请求；列表使用可续读分页和匹配排序的索引，再对选中页投影状态。会话历史保留，不以截断旧 Feature 换速度。

### P2 · 生产调度没有主机级执行并发上限

位置：[生产配置 Infinity](../../../src/main/bots/local-service.ts#L299)、[同步接纳循环](../../../src/main/bots/host.ts#L2009)、[运行租约](../../../src/main/bots/runtime-adapter.ts#L578)。

租约保证同一 thread 不重复运行，但不同独立任务可同时获得执行资格。队列 500 的限制约束等待数，任务一启动就释放等待名额，不约束在跑数。

| 队列独立任务数 | 同时活跃的独立任务 | 本轮接纳耗时 |
| --- | ---: | ---: |
| 8 | 8 | 5.71 ms |
| 32 | 32 | 19.05 ms |
| 100 | 100 | 69.47 ms |
| 500 | 500 | 648.56 ms |

以上使用保持未结束的模拟租约，没有发出 500 个模型请求；停止后均释放完毕。接纳完成后发送主对话 ping，调度耗时 2.31–3.01 ms。这个结果证明线程隔离有效，**不证明真实模型/CPU/网络过载时主对话仍然快**，也没有测接纳循环中途到达的用户请求。

建议：执行任务有可调并发与排队；沟通/必要通知单独预留资源，不能用一个全局池把主 Bot 又堵在后台任务后面。大批启动分批让出事件循环；目录写入、Git、浏览器仍按资源范围加锁，不能把所有任务串行化。

### P2 · 每轮记忆准备先全量同步读两遍，再丢弃超预算内容

位置：[记忆读取](../../../src/main/bots/memory.ts#L63)、[提示构建](../../../src/main/bots/prompt.ts#L72)、[运行前调用](../../../src/main/bots/runtime-adapter.ts#L1163)。

`list()` 先读全部 Markdown 做校验，又读一次做解析与 hash；`forPrompt()` 再 stat/排序。提示构建对每条内容做 JSON 序列化后才检查 4,000 字符预算。

| 输入 | 同步读取中位数 | 读取并构建提示中位数 |
| --- | ---: | ---: |
| 20 条、合计 82,800 字符 | 0.83 ms | 1.01 ms |
| 200 条、合计 828,000 字符 | 6.18 ms | 7.70 ms |
| 200 条、合计 9,360,000 字符，接近单文件上限 | 16.44 ms | 35.77 ms |

本夹具单条均超过 4,000 字符，最终只生成约 1.46 KB 的规则/省略提示，没有内容条目；这个特殊输入用于证明“内容不入提示，读取和序列化成本仍然发生”，不能代替正常短记忆的效果评估。

建议：一次校验读取复用解析结果，按 Bot/作用域/版本缓存必要数据，先做长度筛选再序列化。缓存必须响应用户编辑、文件外部修改、权限范围和删除，保留文件/符号链接校验，不改变记忆隔离。

## 建议实施顺序

1. 任务查询与定向刷新一起优化。两者会相乘放大，优先解决“一个事件触发多批慢查询”。用本次 SQL/IPC 计数作对照，保留分页和状态语义。
2. Feature 请求合并、有效索引和分页。只改 Bot 侧读取，不更改项目模式执行逻辑。
3. 执行并发与事件循环分批，并给沟通保留独立容量。再用真实模型验证后台高负载下用户消息响应，不以模拟租约 3 ms 代替该结论。
4. 记忆读取/提示构建优化；附件跨群公平性、磁盘配额作为下一阶段专项。保持接管、消息回执、权限及历史文件可用性。

内网验证还需要：Windows 真实库/杀毒软件下磁盘耗时、真实模型 TTFT/上下文缓存、多个任务并发时主对话响应、真实招乎上传/回执、长时间运行内存曲线、ES 大数据与多用户并发。当前没有这些生产数据。
