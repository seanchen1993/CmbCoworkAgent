# 招乎投递保序：复用会话表和发件箱

2026-11-22，Asia/Shanghai。App 基于 `codex/merge-uat-into-bot-beta@d26a05a77`，网关基于 `master@913b5e9`，含本轮工作区改动。此前复现过同群重试时后发先至，以及一个慢群拖住另一群。本轮沿用相同的用户侧验收，另加一项数据库约束：升级前后的常驻表清单完全相同。[上一轮保序回归](2026-11-22-zhaohu-delivery-fifo-regression.md)

## 设计与验收

已有会话在原会话行上分配出站序号，发件箱在同一个短事务中保存序号和消息。入站游标仍单独维护。工作线程提交认领事务后才访问招乎，平台请求或退避期间其他会话可以投递。自动重试沿用原序号及平台请求 ID。

绑定前的通知还没有会话行。网关先写入通知自身的发件箱记录，再在当前收件人的唯一索引上取得队列位置。事务一起提交。不同收件人可以各自取得第一个位置。原回调完整回滚时，网关用同一消息标识重新执行入站去重与落库。新卡片按会话、卡片的顺序取锁，让桌面重连时对同一张卡的重放也能读到已提交的结果。

MySQL 5.7 升级脚本使用一张临时表为旧记录排序，回填后立即删除。对 V5 留下的无会话键直接通知，收件人只有随机密文可用，迁移沿用逐条独立的位置。新通知按收件人排队。

## 中间失败与修正

- 初版尝试解析数据库错误文字来区分队列位置竞争与业务重放。MySQL 5.7 驱动的报错格式与 H2 不同，实库用例失败。最终拆开「插入业务回执」和「分配位置」，只有后一个操作的唯一键冲突需要尝试下一位置。
- 首笔事务回滚时，多名写入方可能收到 InnoDB 1213。曾试过让首条出站记录兼任互斥行，实测出现其他收件人等待超时，已弃用。最终仅在数据库完整回滚后重试整个回调事务，上限 3 次。
- 实库暴露了应用写入的重试时间与数据库判断到期所用时钟不一致，原定 30 秒的退避可能立即结束。现由数据库同时负责计算和判断到期时间。
- 纠正时钟后，一次常规联调在等待平台消息时超过 20 秒。网关日志显示两个首发会话同时获取同一机器人的凭据，正常的刷新竞争套用了 30 秒发送故障退避。该情况现单独排入 1 秒重试，真实发送故障沿用原退避规则。
