# 招乎按会话投递回归

2026-11-22，Asia/Shanghai。App 基于 `codex/merge-uat-into-bot-beta@d26a05a77`，网关基于 `master@913b5e9`，均带本轮未提交改动。此前同群分段在重试和双实例下都实测出现 B、A。另一个群曾因前一群的一秒慢请求多等 1026 毫秒。[修改前的复现记录](2026-11-22-zhaohu-delivery-order.md)

## 验收和环境

判定依据是平台发送接口实际收到的顺序。让群 A 的第一条暂时无法成功，在它解除阻塞前检查群 B、Bot 私聊、普通机器人是否已经完成发送，再解除阻塞并检查群 A 的内容和次数。分段、卡片、文件的身份和幂等键沿用原值。人工重新投递一份已明确失败的附件算一次新的排队请求。

App 采用 Node 25.5.0、Vitest、原生 SQLite 和仓库普通 IM 测试脚本。网关采用 JDK 17、MyBatis、H2 事务并发测试以及 MySQL 5.7.24 联调。WSS 链路使用真实 App 客户端和 Java 网关，招乎 HTTP 服务及任务执行使用本地替身。本轮没有使用内网账号或调用模型。

## 实验结果

| 用例 | 注入条件 | 观察结果 |
| --- | --- | --- |
| 群、私聊和普通会话 | 群 A 首条发送悬挂，其他目的会话稍后入队 | 其他三个目的会话均先送达，群 A 的后续回复仍未发送 |
| 群内分段自动重试 | A 首次明确未送达，等待重试时切换网关工作实例 | 同群分段和另一条回复均保留顺序，重试间隔未被后续轮询提前结束 |
| 双实例同时发送 | 第一实例已认领 A 并暂停平台请求，两实例再次轮询 | 平台收取顺序为「另一个群、A、B」，同群没有重复调用 |
| 并发入库 | 首次事务持有群 A 的序号直至手工放行 | 同群后续事务不能提前发布序号，另一私聊可提交和认领 |
| 乱序分段请求 | 先提交长回复的第 2 段，再补第 1 段并重发第 2 段 | 第一次返回可重试的前段缺失，最终只存两段 |
| 两个 App 数据库与提问卡 | Bot 正文进入退避，再申请交互卡和同群普通通知，另一个群发送文字 | 实际顺序为「另一个群、Bot 正文、提问卡、同群通知」 |
| 会话切换卡 | 主体文字成功，附属切换卡第一次失败，然后同会话再来一条消息 | 其他私聊照常发送。卡片重试成功后才发送同会话的后续文字，卡片更新也会等待其首次发送 |
| 附件 | 同群两份文件中的第一份暂时失败。两个群又在同一桌面连接上交错上传 | 同群尝试顺序 A、A、B。新网关的两个上传独立；旧网关单路传文件时其他会话的文字仍可发 |
| 结果未知与人工重试 | 普通机器人首条进入可恢复的 UNKNOWN，同时人工重投一个已明确失败的文件 | 普通会话保留队首，人工重投的文件排到所属会话队尾 |
| 历史数据升级 | V5 数据库中，第 2 段早于第 1 段落库，中间还有另一条消息 | 在 MySQL 5.7 实际执行 V6 后，顺序恢复为「第 1 段、第 2 段、另一条消息」，后续序号从正确位置递增 |

## 复现与证据

- App 定向命令为 `npx vitest run src/main/services/im src/main/bots/{im-channel,im-wire,mock-channel}.test.ts --maxWorkers=3`。15 个测试文件、289 个用例通过。`npm run typecheck:node` 和单独的 WebSocket 协议测试通过。
- 网关命令为 `mvn -f tools/bot-channel-tests/pom.xml test`。9 个测试类、91 个用例通过，跳过 0 个。首次并发探针的 mock 将「无 Bot 路由」返回为空 Map，生产返回 null；测试据此修正后复跑。该次失败不计入通过数。
- 扩展运行 `npm run test:im-v1`，另单跑因串行脚本中止而未执行的 WebSocket、原机器人本地联调和 clean-cut。两项静态检查仍失败。在只含上述 App 基线提交的临时目录中分别重跑，复现同样的源码断言：`im-remote-thread-ui` 期待工作区名称常量在原文件中直接赋值；`im-clean-cut` 统计到 52 处渠道字面量，断言预期为 2。其余 17 个脚本通过。
- 普通联调用 `APP_REPO=<App源码目录> python3 tools/bot-channel-tests/run-local-journey.py`；设置 `BOT_IM_MEDIA_ONLY=1` 后单独测试图片及附件。常规联调覆盖两个机器人身份、同 ID 隔离、私聊与群的交办、续办、回传、解绑；附件联调用 PNG、DOCX、XLSX 验证文件内容、受众、去重和上传失败提示。
- 中间一次常规联调中，出站 24 条全部 SENT，入站为 11 个 COMPLETED、1 个 FAILED，后者的回执是 EVENT_OUTCOME_UNKNOWN。另一次媒体联调结束采样时还有 1 个入站事件为 ACCEPTED。两者均按实际状态记录，不算入「出站送达」或声称所有入站任务成功。

最后一次联调把主动解绑和结束采样放到 App 发完入站终态回执之后，并直接断言网关没有未送达的出站记录。普通联调得到 12 个入站 COMPLETED、24 个出站 SENT；媒体联调得到 6 个入站 COMPLETED、29 个出站 SENT。两次均通过 V5 有数据升级 V6 的断言，进程退出码为 0。调整的是测试的采样时点，出站顺序、附件内容与成功数量的要求沿用前轮。19 个原机器人脚本也已逐个复跑，结果仍为上述 17 通过、2 个基线静态断言失败。

## 生效条件

停止所有旧网关写入和发送实例，执行 `V6__reply_conversation_order.sql`，随后启动新网关和新版 App。旧数据中没有会话键的直接通知，因收件人只保留随机密文，迁移时各自保留独立位置。空闲网关按配置轮询，默认 1 秒；同一会话发生临时失败时，后面的消息会共同等待队首。平台限流、网络延迟、招乎客户端实际渲染顺序不在本地测量范围内。
