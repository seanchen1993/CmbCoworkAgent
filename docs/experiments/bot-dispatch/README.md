# Bot 主对话与异步任务实验档案

本档案记录主 Bot 从执行任务转向沟通调度的迭代过程，用于后续创新文档中的问题、设计、验证和局限说明。2026-11-17 已从临时构建目录回收 **23 次真实模型运行、140 条测试轮次**。实验发生于 2026-11-16；140 条包含修改、查状态、重开等后续轮次，不是 140 个独立样本。

本轮观察到：只增加委派偏好，主 Bot 仍可能长时间自行执行；独立沟通提示词、清理执行规划冲突、宿主传递原始请求联合调整后，最后完整轮的 5 个复杂场景均主动委派，后台执行期间的新问题在 1.1–1.9 秒得到回复。样本较少、迭代中同时改变多个因素，不能据此声称某一句提示词带来稳定命中率或已经超过其他产品。

## 问题与设计假设

用户希望后台工作期间仍能与同一个 Bot 交流。原有主 Bot 拥有完整执行工具和编码规划提示，即使能调用 `bot_work_create`，仍经常自行读文件、写代码、验证，导致主对话被持续占用。

本次借鉴的机制是主角色与执行角色分离、短交办说明和事件驱动回传。设计假设是：让主 Bot 先按整体交付结果选择处理位置，移除相互矛盾的执行规划提示，并由宿主传递原始请求，能减少主 Bot 先自行研究再转交的情况。简单回答、小修改和短 Shell 保留在主对话；模型仍可判断，用户明确指定主对话时优先尊重。

这些实验测的是我们自己的实现。没有使用 Grok 或 DeepSeek Super-agent 产品作为受控性能对照，外部产品的机制参考与本地实测结论应分开表述。

## 代表性迭代结果

所有以下案例使用实际 Electron Runtime 和 `deepseek-v4-flash`，每个初始案例使用新建隔离 Bot、虚构材料和临时目录。工具真实执行，产物落盘。没有连接真实招乎；隔离配置使用测试授权的 YOLO，正常审批另由回归覆盖。

| 阶段 | 可追溯观察 | 应如何理解 |
| --- | --- | --- |
| 主 Bot 仍自行执行 | [早期 CLI 案例](runs/20261116T041334Z-import-5b80f4ed/record.json) 未创建独立任务，整轮 205.1 秒 | 该旧轮没有单独前台计时，不把整轮时间等同交办延迟 |
| 角色分离的中间轮 | [18 条业务记录](runs/20261116T123543Z-import-e2ac294b/record.json) 中 5 个复杂场景最终委派，3 个靠预算兜底；其主轮为 18.2、20.2、74.4 秒 | 最终创建任务不等于主动委派；套件末尾另有旧提示词标记检测失败 |
| 清理规划冲突并强化原文交办 | [完整复测](runs/20261116T130059Z-import-17a1f0a7/record.json) 中 5 个复杂场景全部主动委派，4 个没有要求任务或后台；交办 2.5–4.8 秒，主轮 4.0–6.5 秒 | 18 条业务结果未记录错误；末尾误把完成通知轮纳入主沟通检查，套件仍失败，原记录保留 |
| 最终构建定向确认 | [4 类复测](runs/20261116T131018Z-import-bdb5b5d6/record.json)：短 Shell 直接执行；修代码、CSV CLI 主动委派，主轮 6.1/8.0 秒；后台命令 4.0 秒让出 | 重跑实际 Node 测试 8/13 项、执行 CLI、核对原 CSV 未修改；确认了业务产物，而非只采信模型回复 |

最后完整轮中，5 个复杂任务执行期间分别插入简单问题，回复延迟为 **1.9、1.5、1.1、1.9、1.3 秒**，都观察到后台任务仍在工作。两组方案的修改、状态查询、完成后继续保持原 work、thread 和目录。最终定向复测的两次并行回复为 1.9/1.5 秒。

## 失败与反例

失败记录也属于创新材料的证据，不能只摘取最后的成功轮。

- [中途反例](runs/20261116T125435Z-import-b7b8b4b1/record.json)：模型在正确回答 `5` 后附加一句后台状态，被当时严格的格式断言中止；CSV CLI 另一次修改了样本输入，导致合计 44000 与预期 43000 不符。后续分开记录答案格式与调度成功，并明确保留输入、校验文件不变。
- [截图失败](runs/20261116T113816Z-import-f0697610/record.json)：完成业务后重复查找已隐藏的模式入口超时。属于测试导航问题；旧报告的 error 字段仍保留。
- [最终完整轮的套件失败](runs/20261116T130059Z-import-17a1f0a7/record.json)：后台命令完成通知保留执行工具，却被算入主用户轮，触发 `mainPlanner=1`。统计范围随后修正；不把该轮整体标成全绿。
- 早期还记录到浏览器关闭和完成后重开状态不符，详见历史索引。无法确认原因的情况不推断成模型问题或脚本问题。

## 指标口径

| 指标 | 定义 |
| --- | --- |
| 主动委派 | 实际路线为独立任务，且明确记录 `budgetHandoff=false`。还要分别标记用户是否已经要求任务或后台 |
| 预算兜底 | 运行时拒绝继续前台执行后转交；与主动委派分开统计 |
| `dispatchSeconds` | 用户发送后到宿主创建任务的时间，不是首字延迟 |
| `mainSeconds` | 主用户轮任务记录的创建至结束时间，反映该轮占用，不含全部后台执行 |
| `seconds` | 该案例执行、等待和结果回传的整体耗时 |
| `responsiveness.seconds` | 后台工作期间插入另一个问题，到这次回复结束的时间 |
| `overlapObserved` | 测试查询时观察到后台工作仍活动，不能单凭快速回复就认定并行成立 |
| `exactFormat` | 简单回复是否完全符合只答数字；不与业务执行或调度成功混为一个指标 |
| 业务校验 | 实际读取产物、执行命令/测试、检查同一任务和目录、确认结果回传；与路线偏好、截图、套件元数据校验分开 |

旧报告中的指标缺失、启动筛选参数与进程退出码无法完整恢复；构建产物指纹仍可核对，但不能伪造当时的源码提交号。历史 `status=no-failure-recorded` 只表示留存内容未发现失败，不能解释为确认退出码为 0。历史原始报告已脱敏，`originalReportSha256` 指向脱敏前字节；不宣称脱敏文件与该哈希字节一致。

## 后续每次实验如何留档

`tests/bots-task-routing-app.spec.ts` 现在自动创建 `runs/<UTC时间>-<随机标识>/`，开始时即写入，逐轮更新，结束记录 passed/failed。若进程被强杀，最后的 running 记录和阶段会保留，复盘时应标记为未完成，不能计为成功。不同重跑不覆盖；截图按案例命名保存在同一个目录。

每次目录包含：

- `record.json`：实验时间、平台、模型、用例选择、阶段、实际输入/回复、工具、关键延迟、校验及完整错误；不保存完整网络请求、个人资料库或用户历史。
- `summary.md`：自动生成的逐项结果表，方便阅读。
- 构建信息与关键源码：实际构建 SHA256、构建时提交/分支/脏状态、提示词和相关工具源码快照，其他关键执行文件指纹。使用旧构建时保留“构建源码未知”，不会用当前源码冒充。
- 测试脚本快照，以及各角色第一次实际请求的系统提示词、工具名和请求中的模型参数。第一次请求不代表后续每轮配置都一样；参数未发送时留空。
- 任务返回/继续界面截图（适用案例），与结果共目录。凭据、网关地址和本机用户路径不入档。

运行方式仍为：

```sh
node --import tsx scripts/run-bot-integration-e2e.mjs --build-only
# 使用上一步打印的隔离构建路径；凭据仅从已有配置读取，不写进命令或报告。
BOT_TEST_APP_OUT="<隔离构建目录>" \
BOT_ROUTING_MODEL_PROFILE="<本地模型配置目录>" \
BOT_ROUTING_MODEL_ID="<模型ID>" \
node --import tsx tests/bots-task-routing-app.spec.ts
```

`BOT_ROUTING_CASE` 可选，逗号分隔筛选案例。记录器会记下筛选范围，定向补测不能冒称全量通过。历史回收脚本为 `scripts/archive-bot-experiments.mjs`，只用于补救旧临时目录；新实验无需额外复制。

每轮完成后，还应补充一句“本轮改变了什么、为何改变、结果是否支持假设、下一步”。手工实验或其他测试入口按 [记录模板](../实验记录模板.md) 留档，真实模型、模拟模型、单元测试分别记录。全量/抽样、失败与未运行项目必须明确；变更输入或验收标准时保留前后差异。

## 可用于创新文档的结论边界

当前证据可以支撑“通过主角色分工、原文交办和事件回传，减少前台持续执行，样本中后台期间可继续交流”。不支撑跨模型稳定成功率、生产 SLA、因果单因素提升比例或优于 Grok/DeepSeek 的性能结论。后续要形成更强论据，需在固定输入和验收标准下重复运行，并增加旧 Bot 长历史、并发任务、真实内网与 Windows 样本。

留档机制已做本地离线检查：启动 checkpoint、失败保留、重跑隔离、旧构建来源区分和敏感字段脱敏通过。本次归档没有再次调用真实模型，也没有修改 App 的运行逻辑。
