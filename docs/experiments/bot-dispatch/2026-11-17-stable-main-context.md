# Bot 主会话稳定前缀与结果排队

日期：2026-11-17（Asia/Shanghai）。在已有未提交的 Bot 浏览器边界、交办反馈和预算分类改动上继续开发，没有提交、推送或修改 IM 网关。

## 设计与范围

用户确认不再增加独立轻量汇报器；任务结果必须排队，不能 steer，改动只对 Bot 生效。

- 沟通、初始化和独立任务结果汇报使用同一主 Bot 角色、系统提示与工具定义。结果作为原主会话的新事件进入，保留历史和原受众。
- 当前时间、记忆、任务状态、来源和停止记录附在本轮输入末尾；已经进入 checkpoint 的历史消息不重新生成。动态开场提醒也放在当前请求尾部，不再改写系统提示。
- 汇报请求发送 `tool_choice: none`，另有宿主工具拦截：即便供应商忽略该参数，也不能执行工具或进入工具 hook。汇报不运行用户提示 hook、显式技能启动或普通用户消息触发的任务状态逻辑。
- 结果沿用持久化 outbox 和主会话队列；正在回复用户时不注入、不取消、不让出。新用户消息先于待汇报结果执行。原有实际用户消息 steer 行为不变。
- 原结果回执仍由 Bot 界面展示为任务跳转入口；动态上下文不写入可见聊天正文。独立执行器、普通对话、Team、Workflow、Feature 的执行提示和时间策略不采用本次主 Bot 分支。招乎群直接回传原任务结果的链路保持原样。

macOS arm64、Node 22.23.5；隔离构建和一次性 Electron profile；虚构文件与任务。真实模型为已有配置中的 `deepseek-v4-flash`，凭据只读，不修改用户模型配置。没有连接生产招乎、ES 或实际业务网页。

App 失败过程没有删除：

1. 第 1 次：测试夹具仍从系统提示读取实时状态，改为读取当前事件后继续。
2. 第 2、3 次：把结果标为完全隐藏的内部通知，导致任务导航入口丢失；恢复独立的可见回执边界，同时保持内部事件的运行语义。
3. 第 4 次：测试的宽泛按钮选择器同时匹配交办与结果入口，改为精确选择交办入口。
4. 第 5 次旧断言通过，但截图复查发现第二次结果入口缺失。第 6 次增加“每个结果都有独立入口”的断言后失败；两个回执都在数据库中，界面仅有一个。第 7 次诊断的重载等待又超时，不计通过。
5. 使用统一的“任务结果”占位文字会触发现有展示对相同消息的合并。最终保留原本不同的结果回执内容与请求 ID，由现有 Bot presenter 渲染链接，不改通用消息展示。第 8 次加强后的断言通过；[连续回传截图](supplementary/2026-11-17-stable-main-context/result-navigation.png)可见两次独立入口。

已知基线问题的对照日志为 `bot-stable-context-head-baseline.log` 和 `bot-stable-context-head-stream-baseline.log`，均在证据目录。四个既有失败是一个查询计划断言、两个源码架构断言、一个流式 ID 基线断言；没有宣称整个仓库测试全绿。

后续：[技能首回复与既有失败检查修复](2026-11-17-skill-feedback-baselines.md)已定位并修复这四个失败入口。Bot 查询存在实际性能问题，其余为过时测试合同；本页历史失败数据与原日志保持不变。

## 性能与局限

- 不新增轮询和汇报代理调用；一次结果仍在原主会话汇报。动态快照按轮附加，不按 token 追加；记忆文本继续使用现有长度上限。
- 系统和工具前缀稳定为缓存复用提供条件，不保证供应商实际缓存命中。`tool_choice`、模型配置、技能/插件配置变化及上下文压缩都可能影响供应商缓存。
- 结果轮保留工具定义会增加未命中时的输入；历史中会保留每轮动态快照，需由现有上下文压缩机制处理。未做大规模长会话、生产缓存或 Windows 包实测。
- 技能案例出现一次预算兜底，作为后续委派改进材料保留；本轮没有另改路由策略来掩盖该反例。
