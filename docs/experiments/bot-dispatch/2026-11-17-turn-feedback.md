# 首次回复、任务交办和预算续办的统一反馈

2026-11-17，分支 `codex/merge-uat-into-bot-beta`，基线 `0f13fc512b6bfe4a7a37399882c8e2704c473d8d`，App 1.5.6，macOS arm64 / Node 22.23.5。使用未提交工作区构建，包含前一轮主 Bot 浏览器边界修复。各构建的源码快照和指纹独立记录，不能只用基线提交复现实验。

## 问题与假设

此前提示词要求执行前说明一次、交办后再说明一次；预算回执又标为工具错误。于是同一个请求可能先看到“我来看看”，随后是英文预算 ERROR，再看到“已交给它处理”。招乎的 opening 和 final outbox 还会分别投递两段同义确认。

假设：用当前用户请求统一确认状态，把成功交办当作本轮沟通的结束事件；预算作为内部续办控制事件，真实失败保持错误。这样用户只收到必要的一次回应，后面直接收到结果或需要处理的事项，同时少一次仅生成交办措辞的模型请求。

## 实现与验收口径

- 主 Bot 首次说明使用同一助手口吻，例如“我来核对今天的数据，整理好后发给你。”；已有首答时，不再复述技能流程、预算或交办过程。
- 模型通过 `finishTurn: true` 明确这一批交办已覆盖全部要求。宿主在处理新 steer 后验证所有回执，确认任务被接纳才结束主轮，不再请求一次模型生成交办尾句。新建、继续原任务和执行类 Feature 操作使用同一规则。未声明结束、混合批次、缺少回执、部分失败和新补充仍走正常处理。
- 没有任何首答的成功交办，宿主补一句“我会继续处理，结果会发回这里。”；不伪造“已执行完成”。App 显示紧凑的任务入口。
- 预算回执明确本次工具未执行，不是工具错误。默认聊天不显示内部控制信息；执行详情可查中性说明。真实错误保留原始错误回执与可理解的失败消息。
- IM 对成功交办复用原 opening 投递记录，保留重试；没有 opening 或已失败则发送最终确认。后续任务结果、错误和附件保留。没有新网关协议、DDL 或 ES 查询。

## 实际 Electron 与受控模型

不是静态页面桩：启动实际 Electron、preload、IPC、SQLite 和 Runtime；模型返回固定步骤，以确定性地触发边界。招乎使用本机 WebSocket 网关夹具，不连接生产服务。

| 场景 | 实际验收 |
| --- | --- |
| 群聊直接交办 | 主模型 1 次请求，交办接纳后不再请求确认尾句；opening 1 条，实际任务结果 1 条。 |
| 预算续办 | 前 4 条不同的 `echo` 实际执行；第 5 条返回 `executed: false`，未执行；第 6 次模型请求发起独立任务并结束，无第 7 次确认请求。App 无红色预算错误，IM 无英文内部指令或 JSON 泄漏，只有 1 条开场与 1 条结果。 |
| 真实失败 | 指定不存在的目录，`bot_work_create` 保留错误回执；App/IM 均显示目录不存在、任务未创建的具体说明，执行详情保留红色工具失败。 |
| 首答之后有新发现 | 实际短命令得到行数夹具，交办前说明“输入有 24 行，其中 3 行重复”。开场、新发现和任务结果各送达一次；不重复开场，也不为了去重而漏掉新信息。主轮 2 次模型请求，无额外交办确认。 |
| 无首答的创建与继续 | 宿主各补一次确认；真实文件写入、附件导出、人工批准、结果回传通过。修改继续使用原 work/thread，第二版文件再次交付，模型夹具禁止交办后额外确认请求。 |
| 多目标、steer、重复投递 | 真实 LangChain 图及单元检查完整批次、部分失败不结束、运行中注入优先处理；IM 私聊/群聊重复结算不重复投递，缺少 opening 时有回退。 |

最新 App/IM 定向轮耗时 11.929 秒；任务创建/修改定向轮 13.019 秒。这是完整夹具时长，不是生产投递时延。

## 所有失败及复测

[验证清单](supplementary/2026-11-17-turn-feedback-validation.json)保存 26 次本地命令的退出码、耗时、脱敏完整日志和构建指纹，包含失败轮次；真实模型另有各自独立记录。

1. 初次图测试 6 通过、1 失败，及首次 Node 类型检查失败：测试误用了不存在的消息队列 helper 名称，中间件分支缺少明确返回值；修正后通过。
2. 首次 App/IM 构建没有指定 `--handoff`，缺少既有 e2e bridge，尚未进入业务断言；按现有构建方式补齐并重跑。
3. 两次任务 App 测试失败涉及旧夹具合同：原始请求现在应进入执行器上下文；该检查只适用于首次执行，不应要求每轮都重复；旧交办尾句已收敛为任务入口。更新断言后，真实文件、审批和第二次结果交付通过。私聊无关历史仍必须隔离。
4. 第二次 IM App 测试误在简化群转录中寻找原生工具错误分组；改为同时验证用户可见失败、原生错误回执及执行详情。没有隐藏真实错误来让测试通过。
5. 真实模型第二轮的新 Bot 欢迎问题导致 6 分钟初始化超时，Shell 案例尚未发送。夹具改为只取消初始化阶段的欢迎提问，并留存取消记录；正式案例中的提问和审批不自动回答。第三轮初始化没有提问，取消数为 0；Shell 用例实际通过。
6. 单元首轮实际为 7 文件 / 556 项；命令另带了不存在的 `bot-work-receipt.test.ts`，该选择器未运行，不能计为通过。后续分别为 5 文件 / 80 项、6 文件 / 429 项，及增加新发现保护后的 4 文件 / 364 项，存在重叠，不相加为独立样本。紧凑任务入口在 Electron 测试中实际点击和校验。
7. 最终新发现回归初次使用带分号的引号内 `echo` 文本，既有命令策略要求审批；夹具未作答，等待任务结果超时。保留[审批日志片段](supplementary/2026-11-17-turn-feedback/app-im-05-approval-diagnosis.txt)。改用简单 `echo rows24_duplicates3` 后复测通过，没有放宽产品审批规则。

主进程及渲染端类型检查、最终隔离构建通过。早期包装脚本没有逐命令保存源码或精确开始时间：清单明确置空，不用最终源码倒填。构建 manifest 和真实模型记录保留各自的源码捕获时刻；JSON 文件时间只代表观测到的记录写入时间。

真实模型三轮基于 build-02 / build-03。随后复查增加了“保留首答后的新发现”保护，build-04 已通过实际 App/IM、364 项定向回归和主进程类型检查；这项补充没有再计入新的真实模型样本。

## 结论与边界

单次确认、接纳后结束主轮、预算中性续办及真实错误保留已打通。去重使用实际任务回执和稳定 outbox ID，不根据文本相似度猜测；没有新增模型分类请求或全局锁。IM 判重按既有主键查询，不扫描全会话。没有生产性能数据。

模型不设置 `finishTurn`、有混合批次或尚需回答时仍继续正常模型流程；不为强行去重而截断用户要求。无首答时可能到成功交办才出现宿主确认，首字时延仍受模型和先行读取影响。少量真实模型样本不代表稳定措辞或固定响应时限。没有验证 Windows 打包版本、真实内网招乎投递或真实 WPS 登录。
