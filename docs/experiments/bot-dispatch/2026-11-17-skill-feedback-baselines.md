# 技能首回复区分新建与续办，以及既有失败检查修复

日期：2026-11-17（Asia/Shanghai）。延续 `codex/merge-uat-into-bot-beta` 的未提交改动，本轮未提交或推送。

## 问题、范围与实现

用户要求先处理两项：主 Bot 的技能首回复要区分新建和继续原任务；确认此前四个失败检查是否属于 Bot，并修复相关问题。

- 成功技能回执中的 `task.origin.dispatch` 决定措辞，不依赖模型填写的 `workId` 或任务名称。因此按名称续办、恢复已完成任务、重放同一回执都不会被误称为新建。
- 新建：“已新建任务，我会按所选技能处理，结果发回这里。”
- 续办：“我会在原任务中继续处理，结果发回这里。”
- 仍在成功接纳后只回复一次，不增加模型调用。失败仍说明真实阻塞；无法证明操作类型的旧回执保持中性措辞。
- 生产代码只改 Bot 反馈与本地任务查询。普通会话、项目模式和共享流式运行代码未改；相关文件改动仅限测试。没有 IM 网关、ES 查询或数据库结构变更。

## 四个失败入口的实际归属

| 失败入口 | 原因 | 本次处理 |
| --- | --- | --- |
| `work-projection.test.ts` | Bot 的真实查询性能问题：优先任务查询反向遍历任务历史；最新结果查询选择 `injected_into=NULL` 索引，可能遍历几乎全部历史 | 命令先按归属反查任务；限定未解绑工作以使用现有线程索引；最新结果明确按工作 ID 使用历史索引。保留所有结果、权限、游标和待通知记录 |
| `desktop-agent-invoke-characterization.spec.ts` | 共用入口的源码断言仍检查旧阶段解析函数名 | 改为检查现有 `resolveHarnessExecutionStage(binding.projectId, binding.slug)`，阶段准备顺序继续验证 |
| `standard-thread-turn-architecture.spec.ts` | 共用入口断言写死元数据解析函数恰好出现 10 次，新增守卫后已是 12 次 | 改为分别验证 invoke、resume、interrupt 和原有归属守卫使用共用解析器，不再以全文件调用次数代替边界检查 |
| `stream-message-ids.spec.ts` | 共用流式测试漏掉完成快照自定义事件，错误地只读取消息增量 | 使用真实 Electron 流消费者验证完成快照替换、稳定 ID、补充顺序和所有中间帧无重复；后一条同类断言同步更新为快照协议 |

因此，这不是四个 Bot 生产逻辑缺陷。Bot 查询存在性能缺陷，其余三个入口存在测试合同失配。最初的流式脚本在第一个失败处停止；修正后暴露的第二条同类断言也保留了失败记录。

## 条件与真实模型复测

macOS arm64、Node 22.23.5、隔离 Electron 构建及临时 profile。沿用 `deepseek-v4-flash` 与虚构图书借阅技能、材料，不连接生产招乎、ES 或业务网页。新建场景增加确切首回复断言，再次选技能的续办增加单次调用、接纳后回复、原任务措辞断言，原文件与技能校验标准不变。

运行命令：`node --import tsx tests/bots-task-routing-app.spec.ts`，选择 `BOT_ROUTING_CASE=slash-skill-natural,slash-skill`；模型和构建仅通过本地环境变量指定，凭据不留档。

[真实运行原始记录](runs/20261117T120837Z-4750e7d1/record.json)：

| 场景 | 主轮 / 全流程 | 首回复与结果 |
| --- | --- | --- |
| 只选技能，未要求创建任务 | 6.7 / 27.6 秒 | “已新建任务……”；技能激活、脚本校验、文件交付与结果回传通过 |

四轮主轮都只有一次模型请求；其中两个是后续修改，不能算作四个独立路由样本。此次自然输入比上一轮慢，不能宣称措辞调整使响应更快。结果支持无额外模型调用以及交办类型准确，不代表生产延迟承诺。

## 本地查询性能证据

[执行计划及同数据对照](supplementary/2026-11-17-skill-feedback-baselines/projection-plan-final.json)使用内存 SQLite、45 项工作、25,000 条无关私聊历史和一个后台命令。分别执行两页列表、对应优先项、单项详情、三项摘要，共六次查询；每次查询的结果与原 SQL 逐字段相等。没有增加查询数、缩小历史范围或改变原分页。

- 修复后的计划不再全扫任务/工作历史，也不再以 `injected_into=NULL` 搜索最新工作结果。
- 单查询各运行 7 次，首屏列表中位数约 144.5 → 0.5 毫秒，优先项约 160.8 → 1.0 毫秒。
- 这是同机虚构数据的局部查询对照，存在其他测试负载；不是生产 ES 耗时或整个 App 的响应时间。
- 回归额外验证直接任务、协作任务的后台命令，以及已结束但待通知的命令仍进入优先项；不相关私聊与其他群的结果不混入。
