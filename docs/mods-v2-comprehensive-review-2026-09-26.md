## 发现与已实施的修正

| 问题 | 实际影响 | 本轮处理 |
| --- | --- | --- |
| 虚拟 `completion-config-source` 与普通存储键碰撞 | 已有插件的同名数据被遮蔽，写入/删除遭拒 | 恢复普通键完整读写、删除、枚举和重启兼容；来源提示仅附在专用配置读取结果上 |
| 应用接管后旧命令仍走写入路径 | `/kanban-mode`、`/kanban-target` 返回内部错误，用户不知道去哪里修改 | 两个命令提前说明应用设置入口；中途接管也给相同提示，不写旧别名；宿主保护不放开 |
| 每次读取规则都启动环境探测 | 普通配置和广播刷新可能等待 Git/Python；折叠规则也产生读取 | 首次展开才挂载编辑器；独立 IPC 按需检查环境；普通读取/广播不探测；折叠保留草稿 |
| 局部 Pane 变化刷新四类无关数据 | 增加 IPC、证据查库、序列化与渲染工作 | 证据、提示、日志、旧卡片仅跳过明确 `scope=panes` 的事件；保留全局事件和原生配置广播 |
| 稳定证据读取重复查询数据库 | 每次刷新都多查一次 | 稳定读取一次；真正追加失效记录后才再次读取，不省略失效校验 |
| 设置面板旧请求污染项目切换 | 迟到结果、错误或 busy 状态与当前项目不一致 | 内外面板按项目隔离，读取代次和存活状态校验；旧全局操作结束仍通知当前视图 |
| 并行读取中某项失败丢掉其他成功值 | 项目状态失败时可能误显示应用总开关关闭 | 分项接收成功结果；全局状态未知时禁止操作，显示对应错误 |

`_cmbPolicySource` 仅为界面提示。宿主执行策略、存储和证据指纹不包含这个提示；插件不能靠伪造它获得授权。探测前后仍检查 IPC 项目作用域；权限、输出保护、文件指纹、取消和生命周期检查没有为提速而移除。

## 对存量用户的影响

| 使用方式 | 变化与风险边界 |
| --- | --- |
| 未启用 Mods 的普通用户 | 默认仍关闭，不自动安装/授权/改变任务行为；主执行路径保持关闭短路。界面仍有少量有界状态 IPC，不能声称绝对零开销 |
| 普通 Skill/Plugin、旧 Hook、MCP 和原生工具 | 未变更它们的声明、安装入口或授权协议；全仓与集成回归检查相关路径，不能据此证明所有第三方插件绝对兼容 |
| 已使用旧 Mods 配置 | 用户保存应用规则前继续使用插件配置，不新增迁移或重置；普通状态键得到恢复 |
| 已保存应用级项目规则 | 继续由宿主拥有；插件命令和 Pane 转为清楚提示，改规则应使用应用设置。已有旧插件包不会自动更新，需更新源码并重新批准摘要 |
| 只做代码评审/测试 | 无需 Git/Python 环境探测即可编辑和保存普通规则；实际 diff 检查仍要求项目支持相应范围，测试仍需可用 runner |
| 使用 Autobiz 验收 | 未检查、检查中或失败时不能保存启用的 Autobiz 规则；可以取消该项或关闭规则。部署仍需 Git、Python 3、固定源码对象；不自动安装依赖 |
| 多项目来回切换 | A 的授权操作仍在 A 完成，不重发到 B；迟到结果不能填进 B；应用范围的安装/开关变更会让当前页面重读最新事实 |
| 仅报告模式 | 允许结束任务不再被界面解释成“全部检查通过”；实际结果和证据仍保留 |

没有持久化格式迁移。新增环境 IPC 需要配套主进程和 preload/renderer，交付时应使用完整构建，不能只替换某个旧进程文件。

## 剩余 TTFT 的评审结论与后续方案

正式失败后，同两位 agent 再次独立核对数据及已有诊断。两位均同意：本轮核心功能可交付，但 TTFT 精调暂缓，性能失败保持不变。目前没有具有当前分段归因证据的安全低成本直接修复；这不等于已证明剩余工作必然很大，也不等于对用户无影响。既有授权语句复用、经典空处理器优化、checkpoint 保留查询优化已经落地，不能重复列为新收益。

按用户“主要目的优先，复杂边缘项可暂缓”的范围，本轮不凭猜测继续改动受保护执行路径。下一阶段先建立证据，再决定最小实现：

1. 在冻结普通构建上增加可关闭的单调时钟分段记录，只保存阶段、时长、IPC/SQL/stat 次数，不保存提示词、文件内容或凭据。
2. 分解 preload→主进程入口→Agent 准备/会话→经典事件与 `turn.start`/`turn.step` 链→provider 发请求→首段响应→发布保护→preload 首文。用父子 span 区分等待、CPU 和重叠阶段，不能把并发耗时简单相加。
3. 诊断对比关闭、1/4/8 个 Hook，0/4 个 Pane，短/长会话历史；诊断样本不代替最终正式验收，也不能把单次 GC CPU 采样当成根因。
4. 仅对已证实的重复计算、只读查询或分配建立失败回归，提出最小改动方案，再由两人评审后实现。禁止缓存允许权限、减少撤权检查、跳过 `host.publish` 或文件指纹、改变 Hook 顺序、吞并首帧来美化 TTFT。
5. 使用原 8 Hook＋4 Pane、50/50 交替样本、两组各 300 秒 CPU 和原门槛复测，保存全部失败；保持一个物理请求及完整同序输出，并回归取消、撤权、重载和模型切换。
6. 内存另行比较相同历史容量下的 GC 后快照及对象保留路径，区分应用、调试器和测量对象；不能用本轮 200 次交互或 TTFT 数据关闭两小时堆增长问题。
