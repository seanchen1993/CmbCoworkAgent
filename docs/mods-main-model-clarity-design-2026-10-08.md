## 当前问题和这次目的

1.5.7 的公开界面首次使用验收已经通过，但截图暴露了一个容易误解的地方：
用户选择的组合使用模型 B，上方提示 B，输入框底部却仍显示可以选择的模型 A。
这会让人以为组合没有生效，或以为在底部换模型就能改变当前组合和流程。

已核对，截图对应的真实请求是 A、B、B：普通检视命令使用最初的组合 A，
重新保存并应用组合 B 后，两步文本检视和汇报都使用 B。
这个问题是展示没有分清模型的用途，当前证据没有显示请求错误地发给 A。

这次把模型提示和入口讲清楚，并修正关闭 Mods 时恢复原手动模型的行为。
项目开关关闭时，保留已保存组合但暂停它的影响；开启后再次生效。
普通聊天的原模型设置与流程每步的模型选择分别保留，当前方案没有增加附加功能。

## 用户会看到的变化

| 当前用法 | 输入框底部怎么显示 | 点击后的用途 |
| --- | --- | --- |
| 普通聊天，组合没有指定默认模型 | 原聊天模型，保留现有可选模型及智能路由操作。 | 按原方式选择普通聊天模型。 |
| 普通聊天，组合指定模型 B | 当前组合模型：B。说明这是组合的默认选择。 | 打开右侧组合配置，查看当前组合，并沿公开入口修改。 |
| 执行流程 | 模型按步骤设置。 | 打开右侧流程页，查看这次选择的流程及设置入口。 |

“当前组合模型：B”不表示所有组件都只能调用 B。
组件可以明确指定其他模型，流程也可以为不同步骤选择不同模型；这些原有能力保持。
实际运行中的模型和结果，仍以对应执行记录及真实请求为准。

组合和流程模式也保留一个独立、可以直接点击的“原聊天模型与智能路由”入口，
打开原模型列表和全局智能路由开关。不能因为展示 B 或“按步骤设置”，
就隐藏用户开启、关闭智能路由的唯一入口。列表说明它调整普通聊天的基础选择，
不会替换当前组合默认或流程步骤模型；模型配置和路由的操作权限仍沿原有规则。

原聊天模型 A 和智能路由开关继续保留。移除组合覆盖后，普通聊天恢复原来的选择和操作。
如果之前开启了智能路由，移除组合后仍保持开启，不强制改成手动选择 A。
这个场景的真实请求继续由原路由规则决定，不能只凭恢复 A 的标签认定请求一定发给 A。
组合没有指定默认模型时，也继续使用原聊天模型选择器。
Mods 关闭、没有组合、其他未接通组合的会话和入口，沿原有模型交互运行。

## 怎么从界面修改

### 修改组合模型

“当前组合模型：B”是一个查看和配置入口，不再打开一个看似影响当前任务的 A 选择列表。
点击它调用当前已有的侧栏入口，打开“Claw 工作台 → 配置”。
这里显示当前已应用的组合名称、模型及流程副本，点击已有“编辑我的 Claw”。

进入“我的 Claw”后，在“已保存组合”点击要修改的组合名称，修改“主助手默认模型”。
依次点击“保存能力组合 → 应用到当前对话 → 确认应用”，后续任务才采用新配置。
保存模板不会立刻更新正在使用的副本，运行中也不能直接换掉已应用组合。

当前“编辑我的 Claw”只负责打开页面，尚不负责自动选中某个组合。
本次保留这个真实行为，在入口说明中明确提示选择组合名称；不虚构自动跳转。
如果已保存模板与当前副本不同，必须核对后再应用，不能暗中恢复或覆盖副本。

### 修改流程里的模型

“模型按步骤设置”点击后，调用当前已有入口打开“Claw 工作台 → 运行”。
这里能核对当前选择的流程名称、版本，以及它是已应用组合的副本还是独立模板。
再点击已有“编辑流程”，进入“DIY 流程”。

编辑页当前不会自动定位到已应用副本，也不能直接编辑正在执行的那份副本。
用户需在“已保存流程”选择对应模板，核对名称和版本，再配置 Agent 或 Skill 步骤的模型。
模板可以比已应用副本更新；保存新版后，回“我的 Claw”重新选择流程新版，
保存组合并确认应用，才会改变后续使用的副本。
独立选择模板的运行继续按它自己的公开选择方式使用。

不把“编辑流程”宣称为当前任务即时换模型。
运行中可以查看，修改和应用仍受现有运行、审批及版本限制约束。

### 调整原聊天模型和智能路由

没有组合覆盖时保留现有模型选择入口。
组合覆盖或流程模式下，点击输入框底部独立的“原聊天模型与智能路由”，
仍可打开原模型列表、路由开关及原聊天模型配置。
列表中的路由结果称为“普通聊天的路由候选”，不把它称为当前组合实际使用的模型。
例如候选是 C、组合默认是 B，主要提示仍是 B；只说明普通聊天候选 C，
当前根任务真实请求 B。手动修改基础选择是用户主动操作，不会自动修改组合或步骤。

## 名称和简短说明

主要位置显示用户在模型配置里填写的名称，避免直接显示 `custom:` 等内部标记。
输入框上方的组合提示改为明确的默认用途，例如“组合默认：模型 B”，
不使用容易被理解成整条流程唯一模型的文字。
侧栏的主模型和角色模型也使用同一名称显示方法。

名称来自应用已有的模型列表，不为显示名称额外读取流程组件目录或连接外部服务。
已取得的列表能找到模型时，显示其名称；密钥配置元数据不满足时，标记“未配置密钥”。
名称目录不是模型服务的健康检查。找到名称或 `available: true`，不代表真实接口已经连通，
也不代表客户模型会正确回答；本次不为显示名称发起模型请求或连接测试。

目前共享缓存只公开模型快照或 `null`，正在读取的请求是私有变量，
没有可直接复用的公开“读取中/读取失败”状态。
评估后，本次不扩充全局缓存状态，采用更窄且诚实的显示规则：

| 已知信息 | 显示方式 |
| --- | --- |
| 快照为 `null` | 显示去前缀的引用及“名称尚未取得”；不能推断正在读取或已经缺失。 |
| 已有成功快照，找到引用 | 显示已取得的名称；名称来自最近成功取得的配置，不承诺是此刻最新配置。 |
| 已有成功快照，未找到引用 | 提示“名称未找到（按已取得列表）”；成功空列表同理，不能当作读取中。 |
| ModelSwitcher 自己发起或加入的读取失败 | 保留旧名称，显示“上次名称读取失败，可重试”；没有旧快照仍显示尚未取得。 |

旧快照可能在缓存失效或外部刷新失败后保留。因此列表缺项不能宣称模型已删除，
也不能当作发送资格或服务可用性的判断；当前绑定仍显示 B，不静默切换模型。
“未配置密钥”只描述已取得的配置元数据，不承诺最新凭据状态。
现有缓存没有失败通知，本次不宣称识别 App 单独刷新时的失败。
ModelSwitcher 只显示自己捕获的失败；上方和侧栏只显示已取得的名称及中性状态。
必要的后备名称沿原模型界面的去前缀方式处理，不伪造一个存在或可用的模型。
内部完整引用仍由原保存和审计记录保留，不改成显示名称来持久化。

组合 B 的名称未找到或密钥尚未配置时，仍保留公开的配置修复入口，不能只禁用按钮。
点击“原聊天模型与智能路由”，选择独立的“编辑组合模型配置”，
通过现有 `CustomModelDialog` 打开已确认匹配的 B 配置；另一个“编辑原聊天模型配置”
保留原基础模型用途，不能混成一个入口。已有 B 可以补齐配置，
不存在的 B 当前会打开新建表单，不会自动恢复原引用。
新建成功后若得到新的模型引用，需要按“我的 Claw”公开步骤选中它、保存并确认应用。
配置修复入口不替用户把组合 B 改成新模型，也不写入原聊天选择。
运行中或只有草稿时，同样不得因配置保存自动应用组合。

简短说明建议：

- 原聊天模型：“未指定组合模型的普通聊天使用这里的选择。”
- 当前组合模型：“组合默认使用这个模型；修改后需要保存并确认应用。”
- 模型按步骤设置：“步骤可以各用不同模型，查看右侧流程设置。”

说明应放在当前控件或其打开的侧栏里，少量文字即可，不增加重复的警告区。
默认视图不把模型 A 和 B 同时都当成“当前使用模型”展示。

## 切换对话和模式时，旧窗口不能改动新对话

用户正在打开模型列表或编辑配置时，如果切换了对话、聊天/流程模式，
或当前已应用组合版本、组合默认引用发生变化，关闭旧模型列表和旧配置窗口。
以后若再次打开窗口，就是一次新的操作，旧窗口的延迟结果不能选中新范围的模型，
也不能关闭新打开的窗口。此限制同样覆盖移除组合、关闭 Mods 和会话只读状态变化。

用户已点击保存而开始执行的全局模型配置保存，仍可能完成。
关闭窗口不等于撤回这次保存，不能向用户宣称配置已经回滚。
该次保存的后续回调必须经过范围检查；过期时不改变新对话、组合副本或当前发送模式。
全局配置变化仍通过现有模型变更通知更新共享名称目录，不能靠旧窗口回调补写新对话。
应用全局默认模型不属于这里的会话范围键：原配置保存会先更新它，再通知保存完成，
不能因此把正常的自身保存回调误判为过期。组合默认引用变化仍必须让旧窗口失效。

## 实现范围和保持项

实现限定为三个现有界面文件和一个名称辅助函数，不扩共享缓存状态：

1. `ChatContainer.tsx`：把当前是普通聊天、组合默认覆盖还是流程模式传给模型控件。
   使用已应用副本及当前发送模式，不读取正在编辑的草稿来决定显示。
2. `ModelSwitcher.tsx`：无组合覆盖时保留原选择器；组合覆盖及流程模式显示对应配置入口。
   组合 B 的提示优先于旧智能路由结果，但不改路由开关、原聊天 A 或基础模型元数据。
   保留独立可达的原模型/智能路由入口，并在其列表中提供 B 的配置修复入口。
   用范围和打开次数隔离窗口及回调，捕获本控件读取的拒绝，保留原基础模型恢复规则。
3. `ClawSidebar.tsx`：上方提示及配置侧栏使用友好名称，准确区分组合默认和流程步骤模型。
   未找到名称时提示上述公开修复路径，不自行挂载另一套模型编辑器或路由开关。
4. 一个名称辅助函数：统一名称和短状态文案，本身不发请求、不修改选择。

`ModelSwitcher` 的初读、窗口正常关闭后的刷新和公开重试都捕获自己调用的
`loadModels()` 拒绝，保留原失败 Promise，不伪造成功或空列表。
名称辅助函数和侧栏不新增读取，重试只复用原 `loadModels(true)`，遵守已有请求去重。
不改 `App.tsx`、`ScheduledPanel.tsx`、`AddHookDialog.tsx`、store 或缓存公共契约；
也不把本控件的捕获声称为这些原有调用点的失败处理已经完成。
原则上不改 `CustomModelDialog.tsx` 的全局保存流程：父级按打开会话隔离组件实例，
并给保存、关闭回调加范围检查。如果实施证明该边界不足，先回到方案复审再扩文件。

没有后端路由、模型凭据、插件 SDK、流程调度或持久化格式变更。
不因展示或模式切换自动修改应用默认模型；用户在原配置窗口主动保存的全局设置保留。
不改变插件明确指定其他模型的请求。
不在前端推测每一步最终实际用的是哪个模型：尤其 Agent 角色、插件内部调用和运行时规则
可能提供更具体的选择，流程入口只提示“按步骤设置”。

不能为了让数字或界面一致，调用隐藏的模型选择操作把原聊天模型 A 改成 B。
也不使用不存在的页面路由、组合自动定位或流程副本编辑接口。

### 名称快照和局部失败的具体约束

- 使用原 `readModelCatalogCache` 与稳定的 `subscribeModelCatalog`，不返回新造的
  每次不同的订阅快照，不增加目录订阅源，也不修改缓存失效代次和在途请求去重。
  已成功取得的缓存快照优先提供名称与密钥元数据，避免 store 尚未同步或旧请求回写
  导致当前缓存的名称被反向覆盖；没有快照时 appStore 的名称仅作“尚未确认”后备。
- 缓存 `null` 只显示中性未知；缓存成功空数组显示名称未找到，二者都不表示 loading。
  缓存旧快照只描述已取得信息。失效、刷新失败和最新删除无法仅从旧快照区分，
  因此本次不使用“模型已删除”“当前服务不可用”“配置已确认最新”等断言。
- 本控件的局部读取状态最多保存一次操作的 pending 标记和一条通用失败提示，
  不公开为全局 catalog 状态；重试 pending 仅用于防止用户重复提交，并说明该次重试。
  每次原有初读或主动刷新捕获范围代次及单调读取序号，`then / catch / finally`
  仅在仍挂载、范围及序号都匹配时修改该控件的局部状态。不能让旧失败污染新对话，
  或让旧 `finally` 清掉新重试状态。
- 自己的 Promise 成功后才清掉本次失败提示；自己的失败保留名称并标“上次读取失败”。
  不因切换路由导致快照对象变了就伪称重试成功。外部独立刷新没有公开失败事件，
  不冒充可以观测它；也不承诺已捕获其他原有调用者各自派生 Promise 的拒绝。
  现有订阅仍可更新名称，不能为捕获外部错误额外再发一次目录请求。
- 公开重试只使用原强制刷新并捕获拒绝，保留共享请求行为。
  不重载流程组件目录、不调用 MCP、不发推理请求，不改基础选择或已应用副本。
- 不以名称目录或配置 `available` 字段证明 endpoint 可用；接口是否使用正确模型，
  仍以实际受控请求和既有客户环境验证为准。

### 旧模型引用的名称兼容

主进程 `src/main/models/registry.ts:353` 支持旧 `custom:<model 名>` 及无前缀引用，
名称辅助函数不能仅按完整 ID 查找，未命中就提示缺项。
只对显示名称做有限匹配，先 trim 引用，按以下优先级读取已有目录：

1. 精确完整 ID 优先；`builtin:<id>` 只接受 builtin ID，不外推成 builtin model 别名。
2. `custom:<值>` 先匹配 custom ID，再匹配 custom 的 `model` 字段。
3. 无前缀值先匹配 custom ID，再匹配 custom `model`，最后按原解析规则匹配 ID/model。
   不按用户显示 `name`、模糊子串或大小写猜测，不跨 source 解析带前缀引用。

目录 ID 含 source 前缀时，旧 ID 匹配仅比较对应 source 去掉前缀后的 ID。
ID 与同名 `model` 碰撞仍遵守 ID 优先，custom 与 builtin 碰撞遵守上述 custom 优先。
如果同一优先级有多个候选，当前目录可能把全局默认项排到了最前面，
不能假装知道原 registry 收集顺序；显示去前缀引用和“名称尚未确认”，不报缺失，
不任选其中一个名称。这个保守后备不改变主进程的真实解析或实际请求。

修复入口对唯一匹配的旧引用用匹配到的完整目录 ID 定位编辑表单，
不改保存的组合引用；多候选或未匹配时要求用户在配置窗口核对或新建，不能自动编辑
某个猜出的条目。新建或重选组合仍需用户公开保存、确认应用。

### 模型窗口的范围和代次检查

`ChatContainer` 传入真实发送模式、已应用副本的 `bindingRevision` 和组合默认引用。
范围键至少包含 `threadId / 发送模式 / bindingRevision / 组合默认引用`，
并包含影响操作权限的 Mods 启用及只读状态。默认引用变化包括组合 B→C 或 B→空，
不能仅看组合名称。范围变化时推进单调代次；A→B→A 仍是新范围，不能误接旧回调。
不包含应用全局默认引用或普通路由结果：它们不是此弹窗所绑定的发送范围，
尤其 `handleSave` 自身的 `setDefault` 通知可能先于 `onModelSaved` 抵达。
若会话、发送模式及已应用组合都没变，正常保存后的原聊天选择不能因此被吞掉。

1. 渲染时更新当前范围 ref，立即让旧 token 失效；随后关闭弹层并清掉旧目标。
   不能只依靠 effect 延后关窗，因为 effect 执行前旧事件仍可能抵达。
2. 打开模型列表和打开配置窗口时，分别捕获不可变的范围 token 与本次打开代次。
   同范围关闭再打开也推进打开代次。配置窗口按这次 token 设置组件 `key`，
   旧实例的本地异步状态不进入新实例，不复用旧 `dialogModelId`。
3. 模型行选择、路由开关、从列表打开配置和配置修复入口，在任何写入前检查
   已挂载、当前范围相同、本次打开代次相同；模型选择还要求此次入口用途是原聊天选择。
   在组合/流程模式从独立入口主动调整基础模型，仍只改变基础选择，不改组合或步骤。
   使用捕获该对话的原 `setCurrentModel`，不能先取新对话动作再补做检查。
4. 向 `CustomModelDialog` 传入的 `onModelSaved`、`onOpenChange` 闭包捕获该次 token。
   保存和删除的异步续回调抵达时再次检查 token；过期回调不得选择模型、
   清新窗口目标或关闭新窗口。原聊天配置入口且范围未变时保留原保存后选择行为；
   组合配置修复窗口始终不写原聊天选择，不因保存而应用组合。
5. 不在旧回调内启动针对新范围的目录刷新。已开始的全局配置保存允许完成，
   必要的全局名称更新沿原 `models.onChanged`；本控件发起的刷新均捕获拒绝。
   不能假称关窗取消了已经授权的 `upsertCustomConfig / updateBuiltinConfig / setDefault`。

当前 `CustomModelDialog.handleSave` 会先保存全局配置、更新应用默认值、重读配置，
然后调用保存和关闭回调；`handleDelete` 也可能在等待之后触发选择回调。
这正是必须在回调抵达点检查、隔离旧组件实例的原因，不能只检查打开窗口时的 thread。
