# 创造者与运行时能力对齐检查

结论：尚不能宣称完全对齐。方法目录、事件声明、试用准入已经逐项检查；UI 构造路径还存在未闭环差异。
检查对象为 `codex/mods-v2` 当前源码，不是已下载的安装包，也不是对上游产品最新版本的比较。

## 已核对及本轮修正

| 层次 | 结果 |
| --- | --- |
| SDK 目录与作者声明 | 运行时目录的 100 个方法均可定向查询到声明 |
| 真实试用准入 | 上述 100 个方法都进入真实试用能力范围；具体目标、权限和宿主限制继续生效 |
| 事件目录 | 127 个标记为 bounded 的事件均在真实试用范围；补齐 `model.classify` 后，均可查询到作者声明 |
| 界面挂载位置 | 14 个聊天接点加 Pane、Placed 可发现，包含新 ChatHeader |
| MCP、子会话、开发工作台 | 有精确目录查询及既有条件说明；查询不会启动服务或授予权限 |
| 简版创作指引 | 原来只列 22 个常用方法和 6 类事件，系统指引又要求以这张表判断范围，容易误导模型 |

本轮将简版列表明确命名为示例，增加从实际目录计算的计数和完整目录查询指引；系统指引要求先查 SDK、事件及当前目标，再判断“不支持”。不将整份 SDK 塞进每轮上下文，返回继续分页且保持单页限制。

`model.classify` 的底层事件已实现，但作者声明生成时被跳过。现补充真实参数与 `OperationResult<string | null>` 返回类型，并验证有效 Hook 可编译、伪造结果结构被拒绝。

新增逐项回归：每个 SDK 方法必须有声明及真实试用准入；每个 bounded 事件必须有声明及真实试用准入；定向查询结果不超过 8000 字符预算。

这些结果证明静态发现、作者声明和准入目录之间的覆盖，不等同于所有参数组合、所有宿主环境或所有业务需求都已经端到端验收。

## 仍需补齐的 UI 差异

1. `authoring-declarations.ts` 的 `UiElements` 声明了 `TextInput`，而 `guest-ui.ts` 的实际构造器只有 `Input`，没有该别名。当前应使用 `Input`；作者声明仍需修正或实现一致别名并测试。
2. `List`、`Table`、`Tree`、`Chart`、`Log`、`Form` 出现在基础 `uiElements` 和作者类型中，但 `FUNCTION_UI_RESOLVE_CONSTRUCTORS`、`nativeTable` 及 `UiResolveConstructors` 仍只列 10 个基础构造器。不能据此保证它们经过构造器组合链后仍可使用。
3. 上述复杂控件的若干作者参数仍是宽泛 `JsonObject`，运行时校验则有明确字段和数量约束。应补充精确参数声明，避免编译通过后才报界面参数错误。

这些是源码核对发现的差异，本轮未修改构造器协议、回调归属或权限链。下一步应统一构造器清单，补充精确参数与 Form 回调归属测试，再用创造者实际生成“表单＋报告＋顶部状态＋侧栏”的通用工作台验收。不能靠删掉底层已有控件掩盖差异。

## 保留的明确边界

- 固定位置属于当前聊天区域，不是任意 DOM/CSS 注入，也不覆盖可信审批和窗口导航。
- MCP 连接、子会话控制、进程和文件访问等仍依赖当前会话、真实来源及原生权限。
- 某些接口是受限桌面适配或受信任策略专用接口；在 SDK 清单中不表示普通插件在任意上下文都能执行。
- 本轮没有新增音频、媒体附件等多模态能力，没有改变存量项目模式流程。
