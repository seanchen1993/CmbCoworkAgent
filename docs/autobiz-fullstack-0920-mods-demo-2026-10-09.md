# 用 Autobiz fullstack 0920 分支体验 Mods

日期：2026 年 10 月 9 日。配合 DevClaw **1.5.9 主版本候选**。

这次使用的是 Autobiz 的 **`dev_autobiz_fullstack_0920`** 分支，提交 **`504e327d2f9a4d9e30e9f541c4432accf8000ad5`**，原插件版本 **`1.0.87`**。不是之前的 `dev_agents_inject / 1.0.79` 示例。

改造方式是：**完整保留这个分支的原插件能力，增量加入可选择的 Mods 组件**。你可以先只用状态和看板，再加入文件检视，也可以把它的真实文件交给另一个插件检视、第三个组件汇报；还可为不同 Agent 步骤选择不同模型。

原 Autobiz 仓库没有改动。演示在独立副本进行，原测试和业务脚本保留。普通 Mods 演示与原插件的完整业务工作流分开，避免把能展示、能检视说成整套 Biz／Dev／Ops 已验收。

## 3. 安装、开启和授权

1. 打开 DevClaw 1.5.9，配置一个自己可用的模型；创建本地会话，项目目录选择上面的源码副本。
2. 点击左下 **“自定义设置 → Function Mods”**，依次上传三个 ZIP。
3. 开启 **“启用 Mods 功能（应用级）”** 与 **“启用项目 Mods”**，核对“作用目录”。
4. 核对各来源的用途、版本和能力，在对应卡片 **“授权以上能力”**。安装本身不会执行任务。
5. 机器需要可用的 Python。状态查询会调用安装包里该分支原有的 `read_state_json.py`，**可能出现“批准插件运行本机命令”原生弹窗**。核对命令是本包读取脚本、当前目录是所选源码项目，再批准本次命令；拒绝时查询不会继续。

这条状态入口采用原分支的规范化读取，不让模型直接读 `state.json`、日志或内部锁文件，也不调用会修写状态的 `inspect_state.py`。它只是查询，不推进阶段。

## 4. 第一次组合：只选状态，再加看板

### 先只有状态

1. 打开 **“我的 Claw”**，填写名称，例如 **“Autobiz 0920 只读助手”**，添加本次 Autobiz 来源。
2. 把组件的 **“启用范围”** 改成 **“指定组件”**。初次会保留全部选择，请取消其他组件，只保留 **状态组件**。
3. 保存能力组合，点击 **“应用到当前对话 → 确认应用”**。
4. 回到“聊天”，分别输入并选择命令：

   ```text
   /autobiz-fullstack-info
   /autobiz-fullstack-status
   ```

第一条核对来源分支、提交和版本；第二条读取项目实际 Feature 记录。这里应看到 `mods-demo` 的初始记录。没有跳到 Code／Review，也没有测试或阶段通过的结论。

此时看板、检视和准备输入组件未选，对应入口不应注册。不是只把名字从菜单藏起来。

### 加入看板

1. 回到组合，加入看板组件。看板依赖状态，保留状态组件；缺依赖时按页面提示 **“加入所需依赖”**。
2. 保存并重新确认应用，发送：

   ```text
   /autobiz-fullstack-board
   ```

3. 到右侧 **“Claw 工作台 → 插件与结果”** 看面板，选择／查看演示 Feature，按需刷新。

这个看板显示原读取脚本返回的记录，包括阶段、checkpoint，以及原入口确实返回的选定节点。**当前演示 Feature 是精简路线的初始 `specs_in_progress / Specs`；原入口没有返回 `workflowNodes`，看板不会补造三项节点。** 它没有执行动态流程的语义验收，不能把记录中的阶段名称当成该阶段已通过，也不使用旧版固定七种模板猜结果。

你感受到的 DIY 是：一个完整业务插件保留原资产，但本次对话只加载你选择的新增能力；再加一项，才出现对应交互。

## 5. 第二次组合：加入模型检视

在组合里再选择 **单文件模型检视组件**，设置已配置的组合默认模型，保存并确认应用。然后发送：

```text
/autobiz-fullstack-review tests/test_project_status_invalid_checkpoint.py
```

它读取源码副本中这个真实文件，再请求当前默认模型检视。文件内容不会由演示生成器替换；这次请求会产生模型用量。

它只做单文件检视，没有执行这个测试，也没有检查整个项目。结果不能称为“测试通过”。本示例要求文件非空且不超过 4000 字符，较大的任务用 Agent 读取相关文件检视。

恢复到只有状态／看板的组合并重新应用后，检视入口不再参与当前组合。改变模板后仅保存、不确认应用，当前对话仍使用旧副本。

## 6. 第三次组合：三个不同插件串起来

目标是：**Autobiz 提供真实文件和 Feature 背景 → 独立 Review 检视 → 汇报组件整理本次结果 → 你确认**。

### 先选能力

在“我的 Claw”选择：

- 本次 Autobiz 的 **跨插件检视输入组件**；状态／看板可按你是否需要保留。
- `review-agent` 整包。
- `component-review-kit` 的 **“汇报整理”**。切为指定组件后，取消不需要的检视与示例说明；汇报本身没有这些依赖。

设置组合默认模型，保存并应用。所用来源都要完成当前项目授权。

### 再安排四个步骤

打开 **“DIY 流程”**，创建流程，用“添加步骤”和步骤卡片配置：

| 顺序 | 类型／执行者 | 配置 |
| --- | --- | --- |
| 1 | 插件动作：本次 Autobiz 的准备输入 | 选择 **“Autobiz：准备真实单文件检视输入”**，填写 Feature `mods-demo` 和文件 `tests/test_project_status_invalid_checkpoint.py`。 |
| 2 | 插件动作：独立 Review | 选择 **“独立 Review：检视前一步文件”**。“接收前置步骤输出”选择第一步，取 **完整输出对象**，不只取 `source` 字符串。 |
| 3 | 插件动作：汇报整理 | 选择 kit 的汇报动作。“接收前置步骤输出”选择 **“本次执行结果（有效检视与测试证据）”**，输入字段采用 `text`。 |
| 4 | 人工确认 | 写明核对文件、检视意见、未执行测试，再由你决定是否结束。 |

第一步常量输入对应下面对象；用参数表单填写也可以：

```json
{
  "feature": "mods-demo",
  "path": "tests/test_project_status_invalid_checkpoint.py"
}
```

**不要把第二步返回的 `review` 字符串直接传给 kit 的 `{text}` 输入。** 两个插件的格式不同，第三步用现成“本次执行结果”方式，由宿主汇总有效记录。它也会如实标明没有项目测试，不把模型说“没问题”升级为测试证据。

保存流程。回“我的 Claw”，在 **“组合的显式流程”** 选择这个保存版本，保存能力组合，再 **“应用到当前对话 → 确认应用”**。

### 在对话触发

在右侧“运行”核对当前流程，把发送方式切到 **“执行流程”**，发送：

> 检视本次指定的 Autobiz 文件，结合 mods-demo 的真实初始记录，整理有依据的问题和未检查项。不要修改文件，不执行项目测试，不推进阶段，最后等我确认。

看第一步真实提供者、第二步实际模型结果、第三步汇报和第四步等待确认。若原生脚本执行需要审批，先处理该审批；最后成果确认再点击 **“同意并继续”** 或 **“拒绝并停止”**。

保存和应用不会开始任务。也可以在 DIY 页面点 **“运行已保存版本”**，它会立即采用该版本保存的目标执行。

## 7. 换模型、换步骤，才是自己的组合

同一个分支还可以配置两个只读 Agent 步骤：

| 步骤 | 任务 | 模型 |
| --- | --- | --- |
| 核对用例 | 实际读取上述测试文件，解释它在检查什么，不执行或修改。 | 已配置模型 A。 |
| 独立检视 | 实际读取同一文件，检查边界和回归风险，不凭前一模型的结论判断。 | 已配置模型 B。 |
| 确认 | 看两步结果，明确未执行的项目检查。 | 你。 |

打开 Agent 步骤卡片，把 **“模型选择方式”** 改成 **“固定型号”**，再从 **“模型”** 选择 A 或 B。也可采用 Claw 模型角色。查看本次实际调用，不只看模型候选名称和回复措辞。

这演示的是模型分工。若你把第一步改成实现需求，仍要遵守原业务阶段、工作流和工具权限；不能在正在执行的 Autobiz Code 阶段用普通流程跳过它的 Review／UTest 协议。

插件动作不一定都有这个选模控件。本包单文件检视跟随默认；独立 Review 动作另外支持作者声明的 `config.model` 参数，仍受组合允许模型范围约束。想最直观地分别选 A／B，用上述 Agent 步骤即可。

## 8. 测试和原业务模式怎样看

源码副本有 `.cmb/project-checks.json`，其主流程单元检查执行 `tests` 根目录中 unittest 可发现的 `test_*.py`。不自动安装依赖，不自动把其他脚本也算进来。

这条分支另外有非包子目录的集成用例、带自己入口的工作流脚本、fixture 风格函数和 Node 工作流结果测试，必须另列记录。单个 DIY 单元检查通过不能代表整个分支通过。

原 Plugin 的完整项目／Feature 模式仍依赖原角色、状态、知识／工具环境、项目绑定和业务协议。新包保留这些原资产和看板配置，但普通源码副本的四步 Mods 演示不是完整业务项目验收，也不会自动取得公司知识库或外部 MCP 凭据。

**不要为这条分支勾选宿主旧固定来源的 Autobiz validator 或自动阶段推进。** 当前宿主那条高级链仍用旧提交，本次没有把它冒充为新分支验证器。你可以使用本次检视与普通项目测试主流程；要交付原完整业务阶段，继续原 Plugin 模式并核对真实环境。

## 9. 停止、修改与重新使用

- 修改组件或模型后：保存组合，再确认应用；会话正在执行时先结束或取消。
- 修改流程后：保存流程，重新选新版，保存组合并重新应用。
- 取消整条流程：运行详情 **“取消运行”**。关闭侧栏或刷新不是取消。
- 恢复旧聊天设置：**“我的 Claw → 恢复原配置 → 确认应用”**。
- 更新插件代码后：重新上传、核对授权并应用，旧批准不能代替批准新代码。
- 取消不保证已发生的文件／外部操作回滚；本次只读演示没有业务阶段提交。

## 11. 开发人员怎样重新生成

在 DevClaw 开发工程执行，先拉取指定分支，输出目录必须是新目录：

```powershell
git -C C:/ai/autobiz_kanban fetch origin dev_autobiz_fullstack_0920
node scripts/package-autobiz-fullstack-mods.mjs C:/ai/autobiz_kanban output/autobiz-fullstack-0920-new
```

专用脚本解析目标远程分支的实际提交并写入来源；不检查出分支、不覆盖原工作区，也不把全部功能套成旧版七种工作流。

入口结构变化、原包已有新的 Function／Mods 声明或输出目录已存在时会拒绝，先复核再生成，避免覆盖原功能或旧证据。这不是任意插件通用转换器。

一般 Mods 概念、保存／应用／运行区别与旧插件改造路线见[完整使用说明](devclaw-mods-user-guide-2026-10-09.md)。本次设计及边界见[改造方案](autobiz-fullstack-0920-mods-plan-2026-10-09.md)。
