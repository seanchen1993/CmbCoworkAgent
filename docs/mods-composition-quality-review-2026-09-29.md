## 1. 阻断门槛与具体实现路径

### Q1：侧栏生命周期不能成为任务生命周期

`App.tsx` 当前只在 `!rightPanelCollapsed` 时挂载 `RightPanel`。`use-chat-flow.ts` 持有订阅、异步读取序号、操作锁与运行快照。如果把这个 Hook 直接挪进侧栏，关闭侧栏就会销毁观察者；再次打开会重建操作状态。宿主任务可能仍在运行，界面却失去审批和运行提醒。

实现要求：控制器保留在稳定会话作用域，侧栏仅投影视图；通过现有状态桥或单一 portal 显示。控制器需以 threadId + workspace + generation 隔离迟到响应，不能把线程 A 的运行结果回写到线程 B。不要为了保持状态同时在输入区、侧栏各挂一套 Hook。

`FunctionPanes`、`ModCommandJobs`、`FunctionCompletionEvidence` 由 `withModsChatScope` 包装，依赖 `ChatContainer` 中的上下文。跨 React 兄弟树搬迁时必须显式桥接正确会话上下文；使用 portal 可保留原上下文。否则新侧栏会静默空白。

`FunctionPanes` 还包含 focusAck、paneAct、命令式滚动和 Client ResizeObserver。必须定义“收起侧栏”和“关闭插件面板”的区别：前者只隐藏投影，后者才执行 pane close。隐藏内容不可获焦、不可响应键盘或重复发送 resize/mount 事件。采用保持挂载的容器时同时处理 `hidden`/`inert` 与焦点归还，不能只用 opacity 遮住交互。

验收：反复切换 Claw/文件/Git、折叠/恢复 20 次，活动运行身份不变，启动和审批请求不重复，事件监听数量回到稳定基线。运行中切 A→B→A，A 可恢复真实状态；隐藏的插件不能夺走 B 输入框焦点。

### Q2：审批、阻断与错误不能藏到关闭的侧栏

现有 `FlowRunView` 的待审批正文和按钮会随完整视图搬迁。底部应保留一个紧凑状态条，明确“等待你确认”“检查阻止完成”“运行失败”，提供查看详情和必要的取消入口；流式文字变化不可频繁触发 alert。

审批操作必须绑定用户当前看到的 runId + nonce/成果版本，继续复用宿主校验。不能将 UI 回调携带的旧 nonce 丢弃后改用后来收到的新 nonce，造成用户对旧成果的点击批准新成果。打开详情不自动审批，关闭详情不拒绝任务。

验收：侧栏关闭时产生审批，入口可见且可键盘到达；审批双击只提交一次；界面显示成果 A、宿主已推进成果 B 时拒绝旧审批；拒绝、取消、撤权、基础设施失败均不展示“成功”。

### Q3：单输入框必须保留清晰的执行意图

当前 `ChatFlowControls` 有独立目标 textarea，并明确普通聊天不运行所选流程。精简为单输入框不能把“已选择流程”直接等同于“所有后续消息都启动流程”。

实现要求：输入区提供显式模式“聊天 / 执行流程”，发送按钮相应标明动作。选择流程、保存版本、应用到对话都不能发起任务。普通聊天模式保持 slash、@ 文件、Skill、队列、原生审批及附件等原有语义；流程模式只接收真实支持的数据，未支持附件时明确提示且保留草稿，不能静默丢失。

继续复用 `startChatFlow` 与普通发送的共享 preparation lock；快速切模式、双击、Enter 与按钮竞争不得双发。失败保留当前草稿；成功清空仅当输入仍等于发起时的文本。模式切换不得吞掉后来键入的内容。

验收：保存/应用后执行次数为 0；选中流程后普通模式发送仍是聊天；切流程模式后一次发送产生一个 run；stale revision/无权限/无模型时不运行且草稿保留；流式任务期间的队列和取消仍遵守原约束。

### Q4：显示配置与真实运行分开

不能把“选了 Review 插件”或“模型 B”当作其确实执行过的证据。配置页展示下一次使用的绑定；运行页根据快照与实际请求记录展示提供者、组件、最终模型以及覆盖原因。缺失数据用“尚未执行/未记录”，不要补造成功卡片。

`native-host.ts` 已有节点 modelId > 角色模型 > 默认模型，`tests/mods-flow-e2e.spec.ts` 已对 PLAN/REPAIR 请求的 model 字段断言。新角色绑定应进入宿主冻结计划和实际执行，不得只增加 renderer 下拉框。未配置或被撤权模型必须失败，不可默默用默认模型补上。

验收：独立安装插件 A 和 B，一次组合运行实际留下不同可验证结果，并将 A 的输出传入 B；实现/检视模型请求分别命中 A/B 受控传输；修改模板后既有运行与另一对话不改变。

## 4. 性能与代码检视要求

先记录当前同机基线。建议预算：Mods 关闭时新增 guest 数为 0；普通发送和流式首段延迟相对基线 p95 增量不超过 10% 或 20ms 中较大者；30 次侧栏开关后监听回到基线；稳定空闲时无新增固定间隔轮询。阈值应在跑改后数据前冻结。30 样本只适合作为本机工程回归信号，不包装为统计意义上的全面性能证明。

目录扫描不能随每次输入、每个流式 token 或每次切页签触发；按来源版本缓存，撤权/升级失效。状态摘要与长证据列表分离订阅，避免 token 流使整个目录和审批树重渲染。长输出有滚动与数量边界。

代码检视优先看：IPC 参数与 scope 双重校验；旧引用变更后的恢复失败；快照不包含凭据；调用者/提供者身份链不被 UI 伪造；强制规则不能通过组件选择关闭；App/RightPanel 的 Harness 分支不受普通 Claw 状态误影响。

提交前完成定向单测、browser fixture、Electron 主链 E2E、typecheck、lint、build 和仓库要求的全量测试。失败需区分本次回归和可复现既有失败并列出证据，不用“部分通过”替代未完成验收。真实在线模型未执行时明确说明受控传输范围。

# 最终组合 E2E 发现的模型水合回归（2026-09-29）

真实 Electron 在“流程等待审批 + 同项目另一线程保存了已删除的模型引用”时，首次刷新出现 React #185。组件栈最后落在聊天 ScrollArea；进一步的真实组件隔离复现证明根因是 `ModelSwitcher` 的两个 effect：水合反复恢复旧 metadata 模型，缺失模型降级又选择有效模型；异步 metadata 写回之前二者发生同步往返，最终触发最大更新深度。

修复仅对模型水合增加来源幂等门控，来源由线程、路由模式和 metadata 模型组成，在恢复前记录。新 metadata 和切换线程仍重新恢复；本地降级或手动选择不会被同一份旧 metadata 夺回。没有替换 ScrollArea、虚拟列表、滚动恢复或底部锁定实现。

验证证据：

- 新增 `tests/model-switcher-hydration-browser.spec.ts`，使用真实 ModelSwitcher 和 Radix ScrollArea，故意延迟 metadata 回写。修复前稳定报 Maximum update depth exceeded；修复后通过失效模型降级、手动选择、新 metadata、A→B→A 恢复检查。
- 定向 ESLint 无错误，模型缓存 3 项单测通过，thread-context-performance 契约通过。
- 架构 agent 独立复核通过门控时机、加载与 action 守卫、来源身份和测试有效性。最终真实 Electron 重跑由集成负责人执行，不能以组件级通过代替全链结果。

最终结算：修复后的生产 Electron 组合测试 11 组通过、`pageErrors: []`，保留失效持久模型与等待审批刷新场景；旧 Flow 9 组、传统 Plugin/Harness 7 组通过。两个动态验收发现的问题已闭环，截图和性能边界见交付记录。
