# 原生项目插件的创作、组合与执行

适用分支：`codex/mods-v2`。应用版本固定为 `2.0.0`，具体能力以构建摘要和验收记录区分。
本文说明原生组合路径；旧 `1.0.3`、`1.0.4` AutoBiz 插件的兼容路径见
[历史转换说明](creator-plugin-workflow.md)。两种路径的状态所有者不同，不能混用。

**当前仍在开发验收中。接口实现、候选生成、安装成功与整轮业务通过是不同结论。**
当前原生 AutoBiz 保留的是已迁移的业务基线，并不代表旧插件所有 Hooks、前端场景、远程知识同步及外部发布均已等价迁移。

## 用户怎么使用

1. 在本地聊天切换到“创造者模式”，直接描述新插件的目标。已有插件可导入作者源码，或让助手读取已经存在的项目草稿。
2. 说明业务步骤、输入输出和验收样例；修改已有插件时，说明要替换什么、保留什么。例如“把质量复核改为来源追溯复核，保留前后的资料整理和报告交付”。
3. 缺少依赖时，助手准备原生复用方案。核对来源与权限后确认；安装与授权不会代替实际执行。
4. 助手生成新候选后，在原创作会话打开试用卡，选择隔离工作区，只填写插件声明的必填配置；需要本机知识或目录时，再绑定相应资源，然后开始试用。
5. 在项目模式查看阶段、产物和原生检查。需要批准命令或接受业务成果时，处理对应原生提示。
6. 整轮通过后回到创作工作区保存为独立插件。安装后通过“开始使用”进入对应项目入口；导出 ZIP 不会安装到另一台电脑。

已有项目不会因为安装新插件而自动改用新流程。对候选的后续修改会产生新版本，旧检查收据不能证明新候选已经通过。
新电脑需要重新绑定本机目录、敏感配置和权限；这些值不会随插件导出。

### 替换或优化中间的一个环节

独立项目也使用同一套机制。本地已用真实模型验证“资料整理 → 质量复核 → 报告交付”：
先从空白原生模板生成插件，再在同一会话把中间环节换成“来源追溯复核”，
保留前后技能与产物契约。运行发现报告改写了要求逐字引用的复核摘要后，
继续对话修改交付技能，再次试用、保存，并从普通项目入口在全新目录完成三阶段。
最终核对了实际文件、当前输入读取、来源正文引文、摘要衔接和原生检查记录。
这一路径没有依赖 AutoBiz 的脚本或内核。

可以依次这样表达需求：

1. “制作一个资料整理项目插件，分为整理资料、质量复核、报告交付。报告必须使用本次复核结果。”
2. “中间的复核不够好，改成来源追溯复核，逐条引用资料原文；保留前后环节和已有配置。”
3. “报告改写了需要原样引用的摘要，请修改交付环节，试用后核对这个问题，再保存新插件。”

以上是操作表达示例；实际验收还提供了明确的样例资料和产物字段，不能据此保证任意含糊需求都能一次生成正确结果。
结构检查通过说明声明的规则已满足，内容是否达到目标仍需实际样例和业务检查。

可以在创造者会话中提出具体修改，例如：

> 把 AutoBiz 的“行为规格”替换为“验收用例设计”。新步骤读取需求和 PRD，
> 按正常、异常和边界情况生成可执行的验收场景。继续输出下游需要的
> SPECS.bundle.json，保留设计、实施计划、代码交付等后续步骤，以及知识库、
> Hooks 和用户配置。先生成候选并试用，通过后另存为我的插件。

这类修改涉及该步骤的 Skill、组合声明和输入输出检查规则。只调整写作方式、分析重点等
内容时，可以保留步骤身份、顺序及契约；替换为另一业务环节时，再更新相应声明。
若产物格式、输出路径或业务条件改变，则必须同时调整下游输入与校验 Mod，不能只改步骤名称。

候选试用应确认新 Skill 的正文确实被加载、本次产物通过原生校验、下一步读取的是
本次生成的产物，并且原有知识和 Hooks 仍参与执行。保存后还应在普通项目模式新建
项目运行新插件，验证交付后的依赖和配置。模型回复“已替换”和安装成功均不等于这些验证通过。

安装新插件不会自动替换已有项目正在使用的版本。已有项目需要明确的迁移或阶段恢复，
不能将旧产物和旧检查直接视为新流程的通过证据。业务效果是否变好，还需要使用实际
需求样例比较替换前后的结果；受控模型的链路测试只能证明执行、衔接和校验机制有效。

本地开发验证中，已将原生 AutoBiz 的第三步 `specs` 替换为 `acceptance`，
经原创作会话试用、保存后，在普通项目模式从第一步独立完成全部 8 个阶段。
新技能的实际读取、规格产物的下游读取、14 条阶段检查及 11 次写前 Hook 均有原生记录，
Code 阶段执行了原多工作树流程、编译和测试。候选由真实模型生成，业务执行使用受控输出；
该结果证明这份候选的替换与交付链路，不证明任意旧插件已自动迁移或业务质量必然提升。
此样例验证的是 Host 明确选择阶段技能的路径；技能的普通自动发现还要求完整的
`name` 和 `description` 元数据，不能只凭阶段运行成功就断言所有调用入口都可用。
创造者现已在新候选编译、检查和准备试用前核对这两个字段，缺失时返回对应作者文件和
字段的诊断，供助手补齐后重试。修改后的候选检查失败会保留上一份已准备版本，
并明确阻止使用新候选，不会把旧版本通过的结果沿用到新版本。

### 插件流程、项目和聊天的关系

插件版本声明可用步骤、顺序、输入输出和检查规则。查看这些定义无需先创建项目、绑定聊天或启用插件。
在“我已添加”的插件管理中选择“查看流程定义”，即可查看当前安装版本；长流程的技能路径和检查声明收在步骤详情中。
部分旧插件提供多种流程模板或按需求选择步骤，此时只能展示它实际声明的模板和节点，不能把动态流程误显示为固定顺序。

具体项目保存该次任务的配置、执行进度、产物和运行记录。聊天承载任务沟通和执行，不决定插件的流程定义。
同一个插件可以创建多个项目，各项目独立记录进度；切换聊天不会改写插件中的阶段声明。

创造者用于生成或修改插件。普通使用者仍从项目模式选择插件、新建项目、执行任务；无需先进入创造者或手动组装步骤。
在“我已添加”中，已启用的项目插件也可通过“去使用”直接进入原新建项目入口，无需预先创建聊天。
从保存卡点击“开始使用”时，项目插件的知识目录和参数在目标项目中配置，
不会要求先给创作聊天填写一份相同配置；创建项目不会自动授权执行。
从新插件创建项目后，默认操作是“打开项目”，“调整步骤”是兼容流程的可选操作，不是开始任务的必经环节。

聊天插件的“开始使用”先核对实际来源和所需配置，首次确认统一完成该来源的启用与使用设置。
同一来源和范围已经就绪时直接展示使用入口；必填配置在同一表单补齐，不重复要求一次同义的启用确认。
全局插件管理的启停会影响使用该插件的其他聊天，实际写文件、执行命令或接受业务成果仍按对应操作确认。

业务验收需要实际测试目标和断言。平台可以组装执行与检查能力，但不能从“加 E2E”推导出完整业务预期，或用模型回复代替测试结果。

## 各层分别负责什么

| 层次 | 负责内容 | 不应承担的内容 |
| --- | --- | --- |
| 插件作者源 | 阶段、输入输出、配置、知识、所需执行和检查能力 | 自行批准权限、修改宿主阶段记录 |
| Function Mod | 可复用的业务执行、校验、知识选择和界面扩展 | 用另一份进度文件取代 Host 的真实阶段状态 |
| workflow | 长任务、子 agent、工作树、合并及真实运行记录 | 仅凭模型文字生成成功证据 |
| Host | 固定候选和输入，运行原检查，记录操作收据，满足条件后提交阶段推进 | 猜测缺失的业务规则或把未知结果当成功 |
| 创造者 | 理解目标，复用或生成能力，修改作者源，根据诊断修复候选 | 编辑生成的锁文件、代替用户审批 |

例如“这一步完成了”，由 Mod 返回可核对的业务检查结果，Host 再检查当前操作、输入、产物及必要批准，最后正式推进。
业务规则可以由插件调整，提交记录与并发边界仍由公共 Host 管理。

## 作者需要维护哪些文件

| 文件 | 用途 |
| --- | --- |
| `composition/source.json` | 唯一原生组合作者源，声明模块顺序、输入输出、检查、配置、知识与资源 |
| `modules/<阶段>/SKILL.md` | 该阶段的业务目标、产物和执行说明，不直接写 Host 进度 |
| `workflows/*.workflow.js` | 需要后台执行时使用的真实 workflow 脚本，必须列入 resources |
| 独立能力包的 `mods/manifest.json`、`mods/main.ts` | 声明并实现公开执行或校验动作，单独检查、安装和授权 |
| `hooks/hooks.json` 及脚本 | 保留仍需在原时点执行的必需工具约束 |
| 知识资源及 context action | 通过明确的配置绑定读取实际知识，而不是把开发机路径写死 |
| `tests/project-contract.json` | 作者产物的静态正反例，不执行真实 Skill、业务动作或模型 |

编译生成的 `devclaw.project-runtime.json`、`devclaw.project-actions.lock.json` 和 `skills/native-*` 是运行产物，不是普通修改入口。
来源身份由当前实际安装及授权目录解析，不能手填虚构的 UUID、摘要或锁记录。

## 修改组合声明不必重写整份文件

现有 `project_patch` 支持 `sourcePatch`。固定修改目标是 `composition/source.json`，并与 `files` 一次原子保存：

```json
{
  "action": "project_patch",
  "id": "实际草稿 ID",
  "revision": 2,
  "sourceDigest": "读取草稿取得的完整摘要",
  "sourcePatch": [
    { "op": "add", "path": "/resources/-", "value": "workflows/verify.workflow.js" }
  ],
  "files": [
    { "path": "workflows/verify.workflow.js", "text": "已核对的实际脚本全文" }
  ]
}
```

这只是资源差量示例，不构成可执行阶段。新增阶段仍须提交真实模块、输入、输出和检查；脚本也必须是实际有效实现。

- 只支持 `add`、`replace`、`remove`、`test`，不支持任意文件目标、`move` 或 `copy`。
- 追加阶段使用 `/modules/-`。替换阶段先 `test` 目标模块 ID，再修改对应位置，避免错改另一个阶段。
- 只修改声明时可以省略 `files`；不能同时用差量和全文修改 `composition/source.json`。
- 新增资源必须在同一次保存中声明路径并提供文件。遗漏的原文件自动保留，不必重新复制知识、Hooks 或旧 workflow。
- 版本和摘要不匹配、指针非法、声明不合法或资源缺失时，整次保存拒绝，不产生部分版本。
- 每次最多 16 个操作；单值最多 16 KiB，差量整体最多 32 KiB。原源码包、资源和运行输入限制继续有效。

读取分页文件时，应按 `nextCursor` 拼接完整内容后再判断是否有缺陷，不能把截断当成脚本缺少结尾。

### 当前文本候选的资源边界

创造者的单个文本候选最多 64 个文件，单文件最多 64 KiB，UTF-8 路径与内容合计最多
256 KiB。这是当前平台用于解析、检查、保存和传递文本候选的内部资源限制，
不表示整个业务项目、所有插件或工作区代码受同一体积限制，也不表示模型费用或 Token 额度。

当前作者源和编译后的完整候选共用这套校验；作者源合规并不自动保证展开后的候选仍合规。
文件数越限诊断给出实际文件数；累计字节越限诊断的 `observedBytes` 只是首次超过上限时的累计值，
不是完整包的最终总量。不能因生成包超限就认定作者输入不合法，或删除必需知识、Hooks 和检查。
平台生成元数据的表示应避免无语义冗余；作者输入与生成产物的边界仍须分别审查，
不能把一次紧凑序列化修复表述为任意规模均已支持。

## 依赖如何接入

先通过 `project_actions(query=...)` 查询当前已安装且授权的真实公开动作。满足契约的已有依赖可以直接复用。
`project_actions(id)` 主要用于检查该草稿已经声明的需求，不等于搜索所有新增能力。

缺少能力时，通过 `catalog(project-dependencies)` 发现真实作者源码，再调用 `dependency_prepare(sourceId)`。
宿主固定全部源文件，沿原保存、检查和复用服务准备精确方案；这个操作不安装、不授权、不运行项目。
原工具批次完成后，宿主核对同轮真实复核计划，再正常结束制作轮。用户运行中追加的消息先由原队列处理，不能被交接跳过。

安装、授权仍由原生卡片确认，并等原运行物理结束后应用。确认完成后重新读取动作目录，编译器使用实际 provider 生成锁。
未知安装结果必须先核对，不能反复点击安装或让模型新建另一份计划绕开未知状态。

能力包安装不会自动把伴随 Skill 或 workflow 放进项目。项目实际使用的伴随文件仍须进入同一作者候选并声明资源。
如果已有能力不满足业务契约，应明确缺项，选择扩展独立 Mod；不应为无关的机械接线再生成一层业务包装。

## 用户参数如何进入执行和检查

需要区分三种数据来源：

| 来源 | 含义 | 谁负责提供 |
| --- | --- | --- |
| `check.config` | 随插件版本固定的动作配置 | 插件作者 |
| 原生 `userConfig` | 用户在当前项目填写或使用默认值的参数 | 原生配置界面和配置存储 |
| 动作输入或测试回执 | 本次执行实际提交、执行或返回的数据 | 当前执行及原始回执所有者 |

`configuration.userConfig` 使用原生字段声明，每个字段须提供 `type`、`title`、`description`。
数字字段的上下界是 `min` 和 `max`。产物 `json-schema` 检查中的 `minimum`、`maximum`
不能直接用于用户配置字段。`project_read` 会给出最小有效示例；声明错误的诊断定位到
相对 `userConfig` 的字段路径，只返回固定原因和允许属性，不返回配置值。

声明了表单字段，并不意味着任意 Mod 都能读取全部项目配置。普通检查可通过
`check.configurationKeys` 选择该插件已声明的公开字段，由 Host 将实际解析值放入
`input.configuration`。选择不存在的字段、敏感字段、文件或目录字段均会拒绝；未声明此选择器的旧检查保持原语义。
值不写入动作锁，也不从模型回答或报告中补齐。配置变化会使原输入和旧检查收据失效。

workflow 没有隐式读取全部配置的权限。Host 将当前阶段检查选择的字段放入原生保留的
`Required stage configuration` 任务材料，内容为 `stageId` 和 `configuration`。
Skill 从这份实际阶段材料取得参数，再作为 workflow 参数传入。
校验 Mod 将实际运行参数与 Host 独立提供的配置比较，不能由模型决定“预期配置”。
已有知识提供器继续负责知识选择，不需要为转发无关参数修改其脚本或已批准来源。
知识目录、凭据和本机路径继续走原有受控绑定，不进入这条公开字段投影。

例如 E2E 测试：用户选择测试文件和被测文件，workflow 实际执行；校验 Mod 既核对原始运行回执，
也核对运行的是否正是配置中的测试。仅证明“某些测试通过”，不足以证明本项目要求的测试通过。
配置入口不存在或业务信息不足时，应明确报缺项，不能生成一份自报成功的报告代替。

## 追加和替换步骤怎样保证衔接

追加步骤至少需要明确：消费哪些前序产物、输出什么、由谁执行、如何检查、缺少哪些配置。
运行只读取声明的输入子集，不会因为排在第九步就自动读取所有八个前序产物。

替换中间步骤时有两种情况：

- 保留原输出契约、产物 ID 和路径，可以改变生成方式，后续消费者继续使用原合同。
- 改变输出语义，必须显式修改相应消费者和检查。平台可以诊断不匹配，不能替作者猜测兼容关系。

缺文件、业务检查失败、未知执行结果、过期回执、来源变化或未完成必要批准，均不能推进。
已知业务失败与清理未确认不同；后者不能作为安全重试的完成结果。

## 原 AutoBiz 各部分如何迁移

| 原机制 | 原生路径 | 迁移限制 |
| --- | --- | --- |
| Skill 调脚本读取、更新进度 | Host 提供项目阶段状态，按真实检查收据事务推进 | 不自动迁移已有旧项目进度，不与旧 checkpoint writer 同时管理同一个项目 |
| `board_config.json` 的流程和配置约定 | 组合作者源、原生配置声明及显式知识绑定 | 原环境变量替换、远程同步等行为须逐项映射，不能仅复制 JSON 宣称等价 |
| 产物业务检查脚本 | 独立 rules Mod 的公开检查动作，必要时保留原函数实现 | 代码保留不自动证明触发时点和外部效果等价 |
| 知识提示与组织材料 | knowledge Mod 的 context action，读取已绑定目录及部署单元 | 缺材料或配置时应报告，不以空提示代替有效知识 |
| 写前秘密扫描 | 当前原生包的必需 PreToolUse Hook | 普通 Mod 不能吞掉或绕过这项约束 |
| Code 多工作树执行 | 原 workflow 和 Git 资源接口，Host 等待真实结算及通知续接 | 当前原生 AutoBiz Code 明确受限于已支持的后端场景 |

完整迁移范围应查包内 `knowledge/configuration-mapping.json` 和实际兼容性声明。
当前发布准备及归档不等于外部流水线、发布或部署完成。

## 怎么判断真的成功

| 看到的结果 | 可以证明 | 不能证明 |
| --- | --- | --- |
| 保存或编译通过 | 当前源码和声明通过相应静态检查 | Skill、命令或浏览器已经执行 |
| 依赖安装授权完成 | 指定来源在指定范围具备使用条件 | 整个项目已经通过 |
| 项目契约正反例通过 | 文件和声明边界按测试预期工作 | 真实业务动作或模型效果符合目标 |
| 原 Host 阶段收据通过 | 该候选、该操作、该输入的原检查通过 | 新候选、另一个项目或换名包自动通过 |
| 原试用 journey 完成 | 对应试用的全部阶段及必要接受已经完成 | 任意旧插件均已无损转换 |

同一旅程应覆盖“真实对话生成 → 原生确认 → 试用 → 原检查 → 保存 → 开始使用”。
直接安装候选后创建普通项目的测试有价值，但不能单独证明原创作会话的试用与交付流程。
受控模型业务执行与自由模型创作也应分别标注。

## 对用户和开发者的实际影响

用户主要描述业务变化、填写必要配置、确认实际操作和检查成果。内部来源身份、候选保存、依赖准备及状态提交由公共能力处理。

开发者主要维护业务模块、输入输出和验收规则。新增同类步骤应通过插件差量实现，不应每次发布一个平台特例。
真正尚未开放的公共能力需要平台补齐；业务规则和场景差异应留在插件。

收益来自减少重复实现、隐式上下文和返工。是否节省 Token、减少耗时或提高业务质量，需要相同任务与模型条件下的实际对比，不能仅凭使用 Mods 就给出百分比保证。
