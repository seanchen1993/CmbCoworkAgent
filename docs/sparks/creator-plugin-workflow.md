# 插件创造、转换、组合与使用说明

本文适用于 Mods-v2 更新后的应用源码与安装包；当前设置入口与任务模板版本为 `1.5.12`，
包含 `1.5.11` 的说明与示例更新及 `1.5.10` 的聊天性能修复，
插件状态扩展的功能基线为 `1.5.9` 的 `c32a29b13`。请按
[Actions 包内验收记录](../mods-v2-actions-package-validation.md)确认实际产物。
相同版本号的
早期构建不代表能力相同：本轮 AutoBiz 修复插件需要同时更新应用，旧 R42 等构建不包含
新的受审协议，出现来源预检失败时应安装匹配的新构建，不能绕过检查。
应使用完整安装包或完整解压目录；本轮还新增 `app.asar.unpacked` 内的内置状态扩展
源码，单独替换 `app.asar` 无法完整更新这些资源和生成入口。

当前状态扩展插件为 `autobiz-function-state-mods-20261021@1.0.4`，见
[状态 Mod 的安装与使用](#新增状态扩展由可执行-mod-决定推进)。`1.0.3` 是保留原推进方式的
兼容基线，两者的执行入口与验证证据分别说明。

普通用户在当前本地聊天直接切换“创造者模式”，描述要制作或改造的功能即可。
只有查看候选、试用、验收和保存时才打开“创作工作区”；不需要先配置聊天任务模板或
常用搭配。当前版本支持受控的首次模块化与独立插件交付，未知 legacy 协议仍需作者适配，
不能保证任意插件一句话转换后就可靠运行。

### 统一的使用设置与项目入口

“自定义设置 → 基础功能 → 灵件与使用设置”是统一入口，默认展示“我已添加”。聊天工作台
也提供同名按钮，无须进入“高级特性”。尚未开启时，在当前聊天的设置区明确点击
“启用应用和当前项目灵件”，再按所选插件卡片完成启用、参数与准确源码版本授权。
开启不会代替源码授权，也不会自动开始业务任务。项目目录开关由使用同一目录的聊天
共用；开启应用总开关还会恢复其他已经批准、满足使用条件的灵件。

插件的启用、应用与项目目录的灵件开关、聊天绑定的组合分别有不同作用。安装插件不
等于这些条件全部完成，聊天绑定组合也不等于已经创建该插件的项目。既有固定项目
流程可沿原入口使用；依赖必需 Function Mod 的项目仍须完成其灵件启用与权限检查。
查看“已安装插件的项目流程”时，先核对当前项目目录及项目绑定的准确插件版本。
创建新项目和进入已有项目仍经过原生配置、版本和权限检查，不能靠切换聊天绕过。

在“我已添加”的项目插件卡片点击“查看项目流程”，可在同页查看步骤，不必先进入
高级搭配管理。没有当前目录可用项目时，页面会区分其他目录已有绑定、插件停用或
卸载、兼容性及读取失败，并提供打开已有项目、管理插件或新建项目的原生入口。
项目记录版本与当前安装版本不同只作为诊断；进入后仍核对当前安装源码，不表示保存了
旧版本代码，也不自动迁移项目。同版本替换来源后，旧的流程预览会退役并重新读取。

建议按任务阅读：[创建和使用](#可照做的创造和使用流程)、[首次转换范围](#当前版本能否在应用内完成原始插件转换)、
[人工 Host 示例](#人工示例制作通用-host-业务-mods-来源)、[精确 AutoBiz 转换](#人工示例精确转换本次原始-autobiz-zip)、
[保存插件](#如何保存为自己的插件)、[异常核对](#安装或导出异常后如何继续)、
[阶段调试](#按阶段修改与隔离调试)。首次接触时先阅读操作流程，无须先阅读后面的源码修复依据。

| 处理方式 | 用户可以期待的结果 | 必须保留的边界 |
| --- | --- | --- |
| 助手可分析并修改 | 生成候选、补声明、按失败记录修改源码、重新准备检查 | 新版本必须重新验证，模型文字不是通过证据 |
| 需要用户确认 | 创建试用、确认精确源码和权限、安装导出、人工业务批准 | 不继承旧批准，不重复执行未知结果 |
| 需要作者或适配维护者处理 | 未识别状态机、未知 Hook 语义、外部系统恢复、受审脚本协议演进 | 保留业务门禁，补协议和回归，不伪造旧指纹 |

## 先区分组装契约、运行时扩展与原业务脚本

### 平台扩展机制与插件业务逻辑的边界

Mods 通过事件处理函数和扩展 API 开放应用能力：插件使用 `on` 观察、改写或接管事件，使用获准的工具、文件、进程和存储接口实现业务逻辑。平台已提供真实 Function Mod 隔离运行时、工具注册及 `engine.create` 跨 Mod 扩展。

插件可以自行定义状态转换规则，由 Function Mod 作出显式动作决定，再调用插件自己的检查与持久写入器。知识目录、产物格式、业务门禁和状态归属由插件契约明确声明，不能仅靠界面显示或模型回复推进。增加业务场景应优先复用公共接口和插件适配器。

平台现有接口不等于对任意业务状态提供统一所有权、跨文件原子事务或不可旁路写入控制。这些保证须有相应协议、实现和验证证据，不能从一个状态 Mod 示例推导为通用能力。

存储语义也不能混用：`$.state` 是会话内状态，其版本比较不保证重启持久化；`$.store`
提供插件持久存储，但不能由此推导出多条记录或多个文件的原子事务。既有平台能力动作
提供请求记录、版本检查和未知结果保护，也不会自动将 `state.json` 与 `STATE.md` 合成
一个跨资源事务。AutoBiz 的业务状态仍须由插件中的一个明确写入器维护；模型回复
“完成”、Mod 缓存和界面显示不能替代其真实检查与写入结果。

本应用中，业务 Mod 和可执行 Function Mod 处在不同层次。判断 Mods 带来了什么能力，
需要同时看“如何生成插件”和“插件运行时由谁执行、谁保存状态”。

| 对象 | 实际作用 | 当前边界 |
| --- | --- | --- |
| 业务 Mod 源码目录及组合声明 | 构建时契约：声明模块、依赖、阶段、配置、资源和产物约束；平台组装器核对依赖闭包与流程配置，生成完整的独立插件 | 声明需要对应真实资源和受支持的执行协议，分组或重新打包本身不会产生新的执行能力 |
| 可执行 Function Mod | 运行时脚本：在隔离运行时中，通过已开放的 SDK 注册界面、工具和行为扩展 | 可编程范围取决于平台已提供的公共接口及本次批准，不能访问任意宿主内部能力 |
| AutoBiz 的 Skill、Hooks 和 Python 脚本 | 继续承担业务产物、门禁及兼容存储；新状态 Mod 决定显式状态动作，再调用原检查与写入器 | 旧 Skill 和 CLI 保留兼容路径，不把新增入口表述为全部旧入口已接管 |

兼容基线及新包保留的旧入口，其主要执行关系如下：

```text
业务 Mod 契约 → 平台组装器 → 完整 AutoBiz 插件
                                 ↓
                       Skill → 原 Hooks／业务脚本
                                 ↓
                    update_checkpoint.py／state_store.py
                                 ↓
                    工作目录 .autobizdevops/state.json
```

原始插件也能够调用脚本、保存状态。此次改造的实际收益在于：将可独立复用的业务部分
及其依赖和约束显式声明，由公共组装、检查和交付接口生成新的插件；需要新增运行时
行为时，再通过 Function Mod 使用已开放接口实现扩展。因此，不能仅凭目录拆分或
生成 ZIP 就认定已经充分实现了可编程扩展，也不能由此推定相同流程的模型效果更好或
必然节省多少 token。

本页链接的最终 r8 包在业务组合中增加了知识扩展，**没有交付 worktree 进度面板**。
它保留七个主阶段及原约束下可选的详细设计阶段；能够组合这些模块不等于已经支持
任意新增、删除或重排 AutoBiz 状态机。新增阶段仍需补齐相邻输入输出、Hooks、状态
推进和验收语义，再验证完整流程。

## 新增状态扩展：由可执行 Mod 决定推进

本轮新增独立插件为 `autobiz-function-state-mods-20261021@1.0.4`：
[安装 ZIP](../../output/deliveries/autobiz-function-state-20261021-root-r7/autobiz-function-state-mods-20261021.zip)、
[可继续组合的 Mods 源码](../../output/deliveries/autobiz-function-state-20261021-root-r7/Mods-source)、
[组装与原资源差异报告](../../output/deliveries/autobiz-function-state-20261021-root-r7/function-state-conversion.json)、
[真实运行验证报告](../../output/deliveries/autobiz-function-state-20261021-root-r7/runtime-verification.json)。
以上 r8 是保留原执行路径的兼容基线，本节 r7 输出目录中的新包才包含状态工具。
两个插件具有独立名称；安装新包后应从原项目模式选择新插件创建独立项目，不能将现有
旧插件项目视为已经自动升级。

新包在原业务 Mods 与知识扩展之外，增加 `autobiz.state-machine` 常驻组件。该组件通过现有 Function Mods
接口注册工具和命令，在 JavaScript 中判断允许的状态边，再调用插件自己的 Python
校验与写入实现；没有新增平台专用状态机 API，也没有替换原受审业务内核。

```text
用户明确请求 → 已注册状态工具 → JavaScript 业务图决策
                                   ↓
                         原 Python 校验与产物凭据
                                   ↓
                    设计完成的精确原生确认（如适用）
                                   ↓
                      原校验复核＋准备提交与文件锁
                                   ↓
                       state.json／STATE.md＋操作记录
```

Mod 可以独立收紧允许动作、增加前置检查或调整交互入口，并随业务组件一起复用和交付；
修改 Mod 不需要修改应用主程序。原 Python 仍会拒绝违反其业务契约的转换，因此放宽
JavaScript 图不会自动突破原业务约束。这是可执行业务策略的扩展入口，不是任意状态机
均可直接运行的通用业务 DSL。

| 操作 | 原业务 Skill 兼容路径 | 新状态 Mod 显式路径 |
| --- | --- | --- |
| 读取当前阶段 | Skill 调用原读取脚本 | `state_read` 返回真实 checkpoint 与 stateDigest |
| 判断能否推进 | 原脚本按业务契约检查 | Mod 的 JavaScript 先选择固定业务图中的合法边，再调用原 Python 门禁 |
| 预检 | 依原流程运行检查 | `state_preflight` 真正执行原产物与生命周期检查，不写状态 |
| 提交 | 原 Skill 调用 checkpoint 脚本 | 用户明确目标后，`state_advance` 以原状态摘要和请求键提交；仍需原生命令权限 |
| 丢失回复 | 需核对原执行结果 | `state_reconcile` 按原请求键只读核对持久记录和物理文件，不重复执行 |

原始业务模块、知识配置、16 条 Hooks 声明和脚本资源继续保留，新增组件与它们一起进入
业务 catalog、依赖闭包、完整插件和资源锁。原 Skill 仍保留兼容 CLI，因此这次增加了
真实可执行的状态控制入口，**尚未将所有旧入口全面迁移到 Mod**。原 Hooks 按旧命令匹配
的条件分支，也不能只凭文件保留就认定已在新动作上触发；应分别核对实际执行记录。
新 Mod 在设计完成的原校验通过后，通过现有原生提问确认精确 Feature、转换与状态摘要；
取消或非指定确认选项不提交。Code 完成时，插件明确调用原前端性能检查规则，按原 Plan
及交付记录绑定真实 Git 仓库和变更范围；只有已锁定的 API-only 范围可记录不适用。
这两项是新动作对原业务门禁语义的衔接，不声称新动作触发了旧 CLI 的同一个条件 Hook。

安装并明确启用新插件、选择状态组件且完成原生批准后，在其真实项目工作目录中使用：

1. 执行 `/autobiz-state-read <feature>`，读取该 Feature 的真实 checkpoint 和 stateDigest。
2. 执行 `/autobiz-state-check <feature> <下一checkpoint>`。缺产物或检查失败时先修复业务
   产物，再预检；模型回复“完成”不作为检查凭据。
3. 明确同意推进后，执行 `/autobiz-state-advance <feature> <下一checkpoint> <刚读取的stateDigest> <本次requestKey>`。
   只有原脚本返回 `status=committed` 才表示本次提交已确认，随后重新读取状态。
4. 中断或回复丢失时，执行 `/autobiz-state-reconcile <feature> <原requestKey>`。
   `unknown` 不自动重放，也不能通过更换请求键绕过同一 Feature 的未知操作。

助手也可以调用本插件注册的同名 `state_read`、`state_preflight`、`state_advance` 和
`state_reconcile` 工具；辅助 Skill `autobiz-mod-state-control` 说明参数和处理顺序。
制作新组合时选择 `autobiz.state-machine` 组件，保留所需业务阶段和知识组件，再生成、
检查并另名保存完整插件，无须修改应用主程序或手工修改平台指纹。

本版受控提交使用 Windows 本地 NTFS 文件锁；只读检查能运行不代表其他系统也能提交。
新状态动作支持固定七主阶段；详细设计分支的开启仍须使用原兼容流程，不能由新增
状态工具自行选择启用。任意新增节点、重排状态机、初始化、新建 Feature 和恢复操作
仍需相应业务适配。归档产物的物理移动与 checkpoint 推进不构成
统一原子事务。此扩展没有宣称宿主统一权威状态、自动可信阶段终态、绝对文件隔离，
也没有据此证明模型效果或 token 消耗改善。新扩展的运行证据须使用其自身精确包摘要，
不能沿用 r8 的完整流程报告作为新入口已通过的证明。

最终 r7 包已通过真实 QuickJS 到 Python 的七主阶段完整流程：12 次合法提交、6 次缺产物
拒绝、重复提交及只读对账、原五角色 workflow、Git worktree、Maven、Review、UTest、
E2E 和归档。设计确认由受控原生问答测试驱动；另一专项验证等待确认时修改设计产物，
即使用原工具同步了合法设计锁，也会因批准输入摘要变化而拒绝提交。
完整记录核对了 16 条原 Hooks 声明的保留和 15 条旧 Hook 的实际执行；旧设计条件 Hook
未伪称命中，其业务确认由新 Mod 原生问答承接。模型与批准使用确定性测试样例，不代表
生产模型质量或用户已经在安装包中完成业务验收。

## 平台内置生成与自动转换如何使用这套机制

在原聊天切换创造者模式后，可以描述：

> 将现有插件的状态推进改为可执行 Mod。保留知识、配置、Hooks、产物检查和唯一写入器，
> 先说明原状态图和待保留的门禁，再生成候选并试用；不要只拆目录或生成组合声明。

系统通过以下工具链准备和交付，用户不需要手工填写工具参数：

1. **检查原插件。** `mod_business inspect_raw` 返回精确源码身份和 `stateControl` 审计，
   列出状态脚本、Hooks、配置、知识及可执行扩展候选路径。静态检查不推断未知业务边，
   也不把存在组合声明或 Function 文件当作状态迁移已完成。既有 Host 状态继续归 Host。
2. **生成可执行候选。** 通用 `mod_authoring scaffold(kind:state-extension)` 生成真实
   Function Mod、机器可读迁移计划、写入器绑定说明及未执行测试样例；随后使用同一
   `save/check/request_trial` 原生链。默认返回 `hold`，确认原图后也只返回推进建议；
   尚未绑定原写入器与原校验时，明确显示“状态未迁移”，不会返回虚假的提交成功。
3. **复用已有完整实现。** 对已适配的 AutoBiz 内核，`mod_business example` 的
   `autobiz-state-machine` 提供实际八个源码资源、业务扩展声明和辅助 Skill。
   助手使用现有 `save` 保存独立扩展草稿，再 `preview` 与原业务和知识模块组合，
   `request_trial` 请求原生试用。模板面向 `autobiz.original-234-kernel@1.0.3`；
   原始 ZIP、其他内核或未完成首次模块化的来源，须先核对兼容适配，不能改版本号冒充。
4. **执行与保存。** 精确源码检查和用户批准后，实际执行原业务正反例，核对状态、知识
   和产物。原写入器、人工确认、动作副作用或条件 Hook 的迁移缺项必须先修复，
   再通过原生 `request_review` 安装或导出完整插件。纯函数试用通过不等于业务验收通过。

原生 Mod 制作页也提供“状态决策骨架（未迁移）”模板。它不是自动完成任意旧状态机迁移的
按钮。候选中的 `references/state-migration-plan.json` 记录待确认业务图、写入器绑定及
执行状态；`tests/state-decision-cases.json` 是测试输入，不是已通过报告。

本次平台更新补齐发现、生成、试用和原生交付的通路。业务状态规则、AutoBiz 的条件 Hook
适配及兼容提交代码留在插件中；没有为 AutoBiz 增加平台状态机或专用 SDK。

## 首次使用与再次查看指引

在创造者模式中，聊天模式栏和创作工作区保留“使用指引”，分别介绍应用入口和工作区操作。

在已有工作目录的普通本地聊天中，首次进入创造者模式、聊天切换完成且没有其他可见
对话框或导览时，会自动显示应用图标指引。点击“下一步”按当前实际可用的锚点，依次定位
左上导航图标、自定义设置、创造者模式、原聊天输入框和任务进展。创作工作区入口实际
出现后，指引才在输入框之后加入该锚点：没有候选时为五个控件，具备工作区入口时为六个。
登录、未选聊天、没有目录、普通模式或其他页面不会触发这次首次展示，也不消耗展示预算。
以后点击聊天模式栏的“使用指引”，可从第一步重看应用图标位置。

首次打开可操作的创作工作区时，会显示独立的七步工作区说明框。点击“下一步”依次
定位工作区概览、原创作聊天入口、运行试用、验收、阶段调试、保存和 Mod 组件设置；
需要时展开对应区域。没有候选或阶段快照时，说明会提示前置条件，不会生成虚假的
执行结果。工作区内的“使用指引”可重新打开这套工作区说明。

两种指引都支持“上一步”“跳过指引”“关闭使用指引”和 Esc。完成、跳过或关闭后
不再自动打扰；进入创造者模式后，仍可从各自入口手动重开。所有手动指引入口仅在创造者
模式提供，不会在普通聊天模式中启动。Esc 只关闭说明框，保留当前页面。旧版整页
示例的已读状态不会屏蔽这两份指引。灵件、搭配和聊天任务模板页保留手动打开的“任务示例
演练”，用于查看业务示例，与真实控件定位指引分开。

引导只负责定位与展开，不会替用户切换创造者权限、填写或发送消息、创建或运行试用、
批准工具、安装或导出插件。被其他导览遮挡或暂不可操作的页面不消耗首次展示；关闭后
解除引导高亮。工作区指引会还原由它临时展开的折叠区域。

在同一应用窗口中，从搭配配置返回原聊天进入创造者模式，再回到同一聊天和目录，
未保存的组合编辑会临时保留。重新打开时仍会读取当前权限和目录，不会恢复旧授权。
切账号、删除聊天或改变目录后不能沿用原草稿。临时缓存有数量和大小限制，仅在当前
页面运行期间保留，重新加载窗口或重启不会恢复；长流程编辑应先显式保存，超出保留
范围时按页面提示保存后再离开。

从搭配或聊天任务模板页的“任务示例演练”进入创造者模式失败时，当前页会显示原因；聊天或
项目发生变化时，按提示重新选择目标聊天后再操作。缺少普通本地聊天等前置条件时，
页面会明确说明，不自动重试，也不会用旧授权继续。Windows 上原始路径与宿主规范
路径表示同一目录时，可正常进入；真正换目录、会话身份变化和撤权仍会阻断。

本轮统一修复开启、模式切换、复用批准、试用批准、停止及提升保存六个入口的路径
比较。新增路径边界用例在旧实现为 4 失败、2 通过，修复后对应服务文件 39/39 通过；
创造者路由五个浏览器向量覆盖成功交接、搭配／聊天任务模板页错误可见及不适用范围，保留
原聊天和页面草稿。这些是专项证据，R35 的全量／分段结果仍仅属于其原源码快照；
后续主进程窄增量在 `development-service.ts`，最新生产包及 CI 的最终结果须另行记录，
不能从较早包或本页操作说明推定通过。详见[验证记录与未完成边界](../mods-v2-actions-package-validation.md)。

## 从哪里开始

- 制作新功能：在普通聊天进入创造者模式，描述目标、输入和希望得到的产物。
- 改造已有业务 Mods：指定已安装的来源插件，说明要保留、增加或调整的模块。
- 首次拆分原始插件：说明“把插件 X 拆为可组合 Mods，保留知识、配置、Hooks 和检查”。
  助手先检查原始源码，展示迁移方案，由用户确认创建独立源码候选，再继续组合。

首次模块化不会修改原插件。能够识别的 Host 阶段可生成迁移候选；共享 Skill 使用独立
别名时保持原资源的相对目录。不能证明原 Hook、上下文或执行语义可保留时，必须先完成
映射。原始文件仍在不等于行为已经保持，不能删除校验或改执行标签来消除诊断。

## 三步工作区

| 页面 | 用户操作 | 可以确认的结果 |
| --- | --- | --- |
| 制作 | 在原聊天描述、修改；核对首次模块化方案 | 候选源码与明确的来源版本已准备 |
| 试用 | 填写目标并开始试用，在同一页执行、查看阶段结果和处理待确认事项 | 当前候选实际运行及检查结果 |
| 保存插件 | 填写新插件标识，点击保存；也可仅导出 ZIP | 独立插件已安装或文件已导出 |

创建项目、模型回复“完成”、单次会话结束、包检查通过和安装成功分别属于不同事实。
整轮通过要求原执行链完成、各阶段检查凭据完整、必需产物有检查、人工批准已处理、来源
与候选仍匹配。缺收据、记录不完整或来源失效时显示待核对，不将其补成成功。

## 试用时如何操作

1. 在“试用”页核对候选版本与本次目标，按提示创建隔离试用。
2. 在同一工作区查看原项目的阶段操作。需要时确认源码、工具和人工审批，再推进阶段。
3. 在同一“试用”页查看结果，展开“查看结果”可看各阶段的检查与产物。
4. 效果不符合预期时，填写反馈，提交回原创造者聊天；助手读取实际试用记录后修改候选。
   新候选需要重新检查并确认。受支持的 Host 文件阶段可按下面的快照入口局部调试；
   其他情况从起点试用，旧执行不自动重放。

切换阶段保留原执行器的会话隔离，并通过原项目、运行、阶段与候选版本关联回制作聊天。
人工工具确认仍通过原生入口处理。关闭工作区或试用窗口后可回原聊天继续输入。

## 如何判断成功

- **整轮试用已通过**：原生阶段检查与推进证据完整，且属于当前候选；仍须判断业务效果。
- **检查通过，待确认推进**：当前阶段完成检查，尚需在原项目执行原有推进或人工确认。
- **未通过**：查看具体检查和产物，在原聊天描述修改要求。
- **待核对／历史版本**：缺真实收据、未知执行结果、来源失效或候选已修改；不自动重跑。

Host 使用原检查回执；插件拥有状态的流程使用受审适配器和原 Hook/checkpoint 收据。
未提供受支持校验契约的插件必须补齐契约，不能仅依据其日志或模型文本显示整轮通过。
展示的是当时校验过的产物证据，不代表状态页持续重读、重新验证所有磁盘文件。

## 如何保存为自己的插件

创作工作区只分为“描述需求 → 试用 → 保存插件”。试用结果与运行操作放在同一页。
Host 候选在“保存插件”页填写独立的新插件标识，例如 `my-data-review`，点击“保存插件”即可安装。
版本默认 `1.0.0`，需要修改时展开“版本设置”。只需分享时，点击“仅导出 ZIP”。
系统自动完成源码冻结和检查，无需先点准备、再点安装。新名称不能覆盖已安装的同名插件，原插件与试用数据保留。

业务 Mods 组装候选通过原确认卡保存并安装独立插件，也可导出插件包。原同名更新包继续
使用原 ZIP 更新入口。保存尚未完成验收的源码不等于验收通过，改名后的新包也没有因此
自动重跑。导出不会自动复制宿主保存的本机目录绑定、账户配置或批准；源码中的默认值
及硬编码路径仍需作者审查可移植性，其他环境须重新配置和授权。

## 按阶段修改与隔离调试

在“试用”页展开“按阶段修改与隔离调试”。高级入口位于“组件与高级设置 → 高级：独立项目试用”。先选择阶段进入快照，再把修改要求发送回原聊天。
助手保存新候选后，刷新、准备并确认隔离分支，在新分支的原生阶段操作区进行新的批准和
启动。可选择仅调试该阶段，或重新执行并验证后续阶段。

原项目和原产物保留；新分支只恢复阶段进入时的受控工作区文件，不继承原批准或通过
结果。单阶段通过不等于整轮验收通过。结果未知时先核对；重启不会自动恢复调试执行
授权。没有进入快照的旧运行不能从当前产物反推历史输入。

选中分支后可在独立历史卡结束该分支并保留文件与结果；正在运行或结果未知时禁止结束。
结束单阶段分支不会将已经通过的原生检查改为失败，也不会将其升级为整轮验收通过。

也可在“灵件与使用设置 → 挑选使用 → 挑一个小帮手”使用“阶段调试工作台”Mod，在原创作会话通过自己的
侧栏和 Pane 选择快照、候选、准备方案，再前往原生复核。Mod 只提出建议；原生重新读取
参数后，用户仍需再次准备、勾选确认并创建。所选分支可手动比较阶段输入和当前文件摘要。

重启后可在工作区点击“重新进入创造者模式”，再读取已保存的创作与调试记录，新控制会话
不会恢复旧分支执行权限。局部通过不计为整轮通过。可以提前保存、安装或导出未验收源码，
这些操作不代表通过；正式使用前应对当前候选完成整轮验收。

Host 分支允许目标及后续未被上游共享的 Skill 正文修改，保留原检查与依赖。原生配置、
知识及上下文冻结后重新绑定到私有分支；敏感配置重新加密保存，不传给上下文脚本。
兼容 `devclaw.stage-recovery.json` 的 Hooks 和脚本 provider 可在新批准后继续运行，
行为共享 Mods、MCP、公开动作及未适配 workflow 仍明确阻断，不能删减业务语义换取通过。
Windows 命令使用受限执行与所属进程组；文件隔离不保证阻断所有网络访问，外部系统副作用
不会随文件快照恢复。首次试用的脚本 provider 与恢复分支一样，需要每阶段精确策略确认。

## 插件拥有状态时如何恢复阶段

在已结束试用的“插件阶段恢复”中，点击“检查阶段恢复条件”，从原生流程选择起点。
规划会实际运行插件脚本：先核对精确插件、适配器及输入版本，再勾选规划确认并生成方案。
查看受影响产物和诊断后，另行确认创建恢复后的独立试用。此操作不启动业务；新试用需要
核对配置、知识、上下文和源码权限，再明确启动。原项目不被回退，恢复成功不计为业务通过。

插件必须显式声明 `devclaw.stage-recovery-adapter.json`，组装插件通过扩展的
`stageRecoveryAdapter` 将声明和脚本纳入资源投影与锁文件。平台调用统一规划、应用、
验证协议，由插件实现自己的 checkpoint 和产物规则。AutoBiz 适配器调用原
`rollback_stage.py`，保留原 Hooks 与产物校验；没有声明的旧包不会被平台按名称自动适配。
当前副本恢复不处理 Git 回退、活跃 worktree 或外部仓库重绑定，这些情况会明确阻断。

响应丢失或重启后，点击“读取已保存的恢复记录”。“只核对恢复执行记录”不运行脚本。
仅当原生物理记录确认原恢复命令真实成功，才可另行批准只读验证和接管；不会重复执行
恢复命令，不采信用户声明的成功，也不凭恢复成功将业务阶段改成通过。

## 安装或导出异常后如何继续

在原保存卡点击“核对实际交付结果”，系统检查精确安装身份与实际导出文件。核实成功后
直接显示相应结果；确认没有执行后才允许重新准备和确认。发现冲突文件时，先保留并处理
冲突，再重新核对。结果未明时不重复安装或导出，历史候选结果不能代表当前候选。

在创造者交付卡安装成功后点击“开始使用”，直接核对新插件的配置、知识、依赖和入口。
新插件默认未启用时，先明确点击“启用新插件”；启用不会继承运行批准。聊天插件展示
经过授权的真实命令、面板或可调用技能；项目插件打开已定位模板或插件的创建表单。
填写并确认前不会创建项目或启动流程，换电脑仍须重新绑定本机目录与批准。

实现协议及边界见 [Hooks 与上下文恢复协议](../stage-recovery-hooks-context-protocol-2026-10-21.md)。

## 当前版本能否在应用内完成原始插件转换

应用内已提供原始插件检查、首次模块化方案、独立源码候选、业务 Mods 组合、试用及插件
交付入口。创造者可读取受支持的来源，通过原生工具准备转换方案；确认后生成独立候选，
继续试用、反馈修改和保存。安装 ZIP、识别到阶段列表、生成源码和通过整轮业务验收是
不同结果，不能用其中一项替代后续验证。

当前不能保证任意原始插件都能一句话自动转换。需要分别判断以下条件：

| 来源情况 | 当前处理方式 | 必须核对的内容 |
| --- | --- | --- |
| 已声明业务 Mods 的插件 | 读取目录并选择、增删和组合模块 | 依赖、原 Hook、产物契约及所选模块是否闭合 |
| 可识别的 Host 阶段插件 | 检查原始源码，准备首次模块化候选 | 阶段 Skill、配置、上下文及检查映射是否完整 |
| 拥有自身状态机的受审业务插件 | 保留其原执行器，由适配器连接原生试用与验收 | 精确来源版本、执行闭包、原 checkpoint 和校验协议 |
| 未识别的自有状态机、外部动作或未知脚本协议 | 先补作者声明、适配及回归，再重新检查 | 不得靠删除 Hook、改标签或伪造通过收据消除阻断 |

“受审”不是按插件名称放行。它绑定已检查的代码和资源摘要、模块定义及执行协议。
同名插件更新脚本后不能继续借用旧版本的审查身份。适配器负责解释插件自己的业务规则；
平台提供候选、权限、隔离、配置、知识绑定、结果核对和交付等公用能力。

创造者可以分析失败记录、修改受控候选、提出适配或修复方案，再提交原检查；模型建议
本身没有通过效力。原始插件缺陷、未知外部副作用和不能证明保留的语义仍需作者处理。
确认源码、批准脚本和接受业务结果属于不同操作，先前批准不会自动转移到新候选。

## 可照做的创造和使用流程

“聊天任务模板”为下一条任务选用 Flow 编排，提供“只读检视”“检视并测试”和“失败修复复测”。
模板可保存修订、执行历史与审批，可引用已授权插件的技能、动作并执行适用 Hooks；项目流程
中的公开动作、上下文和检查也复用同一 Flow 底座。插件是版本化的能力与资源交付包，不一定
包含流程；项目插件还声明或适配长期阶段状态、配置知识和产物合同，详见[总览中的“聊天任务模板与插件的关系”](README.md)。

点击“选用并返回聊天”后，实际发送消息才开始执行；需要测试的模板先只读核对项目测试入口，
缺失时不会选用。例如“检视并测试”执行检视、原生测试、汇报和人工确认，不自动推进 AutoBiz
阶段。手工参数位于“高级特性 → 聊天任务模板”的高级区域。制作或转换插件从创造者模式
开始即可；已有项目流程直接从项目入口使用，无须在模板或搭配管理中重复配置。

### 一句话创建新插件

1. 选择有本地工作目录的聊天，进入“创造者模式”。描述业务目标、输入、输出和成功标准，
   例如：“制作一个数仓字段审查插件，读取我指定的 DDL，检查命名、主键和字段注释，生成
   可定位到表和字段的报告；先展示检查规则，不自动修改数据库。”
2. 助手先判断需要聊天功能、界面面板还是项目阶段；核对方案中的模块、配置和权限。
   不要仅写“做好一点”，应指定至少一个正常样例和一个应拒绝的样例。
3. 确认创建独立候选。在创作工作区“试用”页填写本次目标，补齐必填配置和知识绑定，
   阅读并确认本次执行需要的权限，再明确开始试用。
4. 在“验收”页检查实际产物、原生检查及待确认项。效果不符合要求时，使用反馈入口，
   例如：“第二阶段漏掉复合主键，请保留现有规则，增加此反例并重验。”
5. 助手修改候选后重新检查；按当前支持范围创建新的试用或阶段调试分支。旧版本的成功
   不会自动成为新版本的通过结果。
6. 在“保存”页填写独立名称、版本，准备并确认安装，或导出 ZIP。安装后点击“开始使用”，
   根据原生诊断补齐配置，进入系统已定位的真实聊天入口或项目创建表单。

### 从原始插件转换并继续组合

1. 先通过原插件安装入口安装来源 ZIP。在“灵件与使用设置 → 我已添加”中确认准确的来源名称
   和版本；原文件及工作数据应保留。不要用旧版本或同名目录代替待转换来源。
2. 在创造者聊天明确来源和保留要求，例如：“检查已安装的 AutoBiz 1.0.87，把阶段拆成
   可组合 Mods。保留 board_config 的环境变量替换、外部知识、所有 Hooks、workflow
   和阶段产物校验；不能保留的部分先列出，不要删除检查。”
3. 阅读检查结果和迁移方案。系统要求源码确认时，核对资源、模块和诊断，再创建独立候选。
   未识别协议应停留在待适配状态；不要要求助手把错误改成成功。
4. 先验证等价的完整流程，再添加自己的 Mod。例如新增“代码执行进度面板”，应使用实际
   workflow/worktree 观测事实；新增数仓步骤则同时声明输入产物、输出和检查规则。
   “能选到步骤”不等于上下游已衔接。
5. 重新试用组合版本，至少验证正常链路、缺少前置产物、知识未绑定和必需检查失败四种
   情况。增加步骤后重新检查依赖和产物来源，不能沿用旧组合的整轮验收。
6. 以新名称和版本保存、安装或导出。原插件、转换候选、组合后的独立插件各有自己的身份，
   更新其中一个不会自动替换另一个。

### 作者手动适配的最小工作

作者应先检查插件元数据、阶段定义、原 Skill、Hooks、配置 Schema、环境变量及知识来源，
画清阶段输入输出和状态所有权，再添加模块目录、依赖和资源声明。拥有原状态机的插件须
保留原命令入口及其真实检查，提供平台可验证的适配协议；恢复功能另需显式声明统一的
`stageRecoveryAdapter`。这些文件属于插件源码，需要连同完整资源通过锁包和校验。

手动修复应产生新的候选或包版本，并记录改了哪些脚本、为什么修改、保留了哪些门禁及
反向测试。不要直接编辑安装缓存或应用的 `app.asar` 作为插件适配；不要伪造旧源码摘要，
也不要把原始源码与已修复版本统称为“原字节保持不变”。

### 换电脑后的配置

1. 安装相同应用版本和已导出的独立插件 ZIP，核对名称、版本和来源。
2. 手动安装 ZIP 后从原项目模式选择该插件，重新检查依赖及运行环境；保留创造者交付记录
   时也可使用该卡的“开始使用”。缺失 Python、Git、Java/Maven 或命令环境时，
   按实际诊断补齐。是否需要这些工具由插件声明和真实执行路径决定。
3. 重新选择本机知识目录和项目位置，填写必填普通配置和敏感配置。原电脑的绝对路径、
   加密凭据、知识目录绑定及执行批准不会因复制插件 ZIP 自动有效。
4. 重新预检并明确批准，再用本机样例试用。外部知识被原 ZIP 引用但未打包时，必须获得
   对应知识资源或改用用户明确选择的新知识；不能把空知识或空目录当作等价迁移。

### 人工示例：制作通用 Host 业务 Mods 来源

可直接参考仓库内的[供应商准入来源](../../examples/vendor-onboarding-mods/README.md)。
这是独立的 `host-linear-v1` 场景，不使用 AutoBiz 的状态机或受审内核表。其完整目录为：

```text
  board_core/board_config.json
```

其中，[插件元数据](../../examples/vendor-onboarding-mods/plugin.json)标识来源；
[业务 Mods 目录](../../examples/vendor-onboarding-mods/mods/business/manifest.json)声明
内核、模块、资源、必需依赖及各阶段的 `host` 检查；两个 Skill 分别形成主体资料和准入报告。
`vendor.settings` 为可组合的配置扩展，知识规则作为显式资源保留。`board_config.json`
在此是示例资源，不决定 Host 状态所有权，不能靠增加同名文件把 Host 改成 AutoBiz。

作者可以复制这个来源到自己的新目录，保留受检契约，修改业务 Skill、规则和 JSON Schema。
增加必需产物时，同时声明对应检查并把检查 ID 绑定到该阶段；增加模块时，声明依赖及全部
资源，不能只增加菜单标题。普通 Host 业务声明无需修改平台的 AutoBiz 审查指纹表。

`action="modularization_schema"`；返回过长时按原 `nextCursor` 分页读取。它包含当前
原生 JSON Schema 和适配规则。对应实现为
[目录 Schema](../../src/main/plugins/business-mod-catalog-schema.ts)及
[原始插件模块化](../../src/main/plugins/plugin-modularization.ts)。不要使用旧文档猜字段，
不要把 JSON Schema 里的属性名替换成界面文案。

在应用内验证和交付的真实操作为：

1. 选择带目录的本地聊天，打开“灵件与使用设置”，进入“从 Mods 组装新插件”。
2. 点击“导入 Mods 源码目录”，选择上述来源根目录，即包含 `plugin.json` 的这一层，
   不选择 `skills` 子目录。来源区会显示其执行方式和可选模块。
3. 选择主体资料、准入报告及配置扩展，填写新的插件名称与版本。依赖应被保留；多个来源
   必须属于相容的内核身份，不能把互不兼容的流程直接强行拼接。
4. 点击“预览新插件”，检查实际步骤、自动补齐的依赖、资源列表和诊断。预览失败时修改
   来源，重新导入和预览；预览通过不代表业务运行通过。
5. 点击“生成独立插件”，再点击“检查插件包”。手工组装页面可继续“安装新插件”或
   “导出 ZIP”；包检查的绿色状态不代表业务试用通过。需要安装前隔离试用时，应走前面的
   创造者候选流程，不能把手工组装页面当作已经运行试用。
6. 手工组装安装后明确点击“启用新插件”，再进入“项目模式 → 新建项目”选择该插件，按实际配置和权限创建、执行并验收。
   原生插件与兼容插件使用同一入口，由系统选择相应的运行服务。
   保存后点击“开始使用”，系统核对并启用该版本，直接打开已选好插件的项目创建入口。必需配置会就地显示；不会自动创建项目或启动阶段。

### 人工示例：精确转换本次原始 AutoBiz ZIP

本仓库另提供了[该版本专用作者脚本](../../scripts/prepare-autobiz-original-mods-delivery.ts)。
它不是通用 legacy 转换器，只接受本节指定 SHA-256 的原始 ZIP，并在独立目录中生成模块

Node 22 和已安装依赖，在仓库根目录执行：


输出目录必须不存在；执行失败后也应保留该目录作诊断，重新选择新目录，脚本拒绝覆盖。
本轮受审修复协议为 `1.0.3`，不能随意换脚本版本或把其他 ZIP 改名后强行处理。
输出的 `Mods-source` 可由“导入 Mods 源码目录”继续组合；`complete-plugin` 是组装包的
源码，ZIP 可通过原安装入口确认安装。`conversion-verification.json` 区分转换检查与
业务运行，生成成功不会把 `businessStagesExecuted` 自动标记为成功。

陌生 legacy 来源需要作者或适配维护者先确认其状态协议、资源闭包、上下文和外部副作用，

Host 插件去修改应用、平台指纹表或 `app.asar`。

应用内首次模块化确认是只增补资源的转换，不覆盖原始脚本；普通业务 Mod 草稿也不能
替换受审内核。本次 AutoBiz 的四个原脚本修复由上面的版本专用作者脚本完成，不能表述为
原 ZIP 在聊天中已经被自动修复。使用原始未修复基线时，生成候选不代表原插件缺陷已消除。
