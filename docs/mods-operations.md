# Mods 部署与恢复

## 部署规则

`resources/mods-policy.json` 随应用构建进入资源目录，仅支持 `cmb.baseline/v1` 固定策略。
`required: true` 强制对项目工具执行和输出应用策略；关闭普通 Mods 不会关闭该策略。
`denyTools` 接受规范工具 ID 的精确匹配，`redactLiterals` 接受需要隐藏的固定字符串。
修改部署规则后须重新构建并重启应用。项目文件和插件清单不能声明受管权限。

策略运行在独立 utilityProcess 的 QuickJS 中，不开放 SDK I/O；原始输出不能在策略失败时回退发布。
宿主预检会抑制超限、不完整及不支持的非文本内容，过滤常见凭据字段和令牌。
审计中的 `baseline-v1` 表示完成基线检查，其余规则表示该次 VM 检查命中；重复发布已脱敏内容时可能不再命中。
基线是有限规则集，不保证识别所有个人信息或业务秘密。部署方应明确配置自己的固定敏感标记。

应用安装目录和部署资源必须由组织的软件分发权限保护。本机制不防止能改写整个应用的本机管理员。
当前没有组织签名、在线策略下发或策略编辑器；不要把普通插件当作组织策略的来源。

## 审计与未知结果

项目 Mods 设置中的“项目执行记录与核查”显示工作区范围内的调用。
执行状态与发布状态相互独立：工具可能已经成功，但输出被策略拒绝发布。
原始参数和最终参数只保存 SHA-256 摘要，控制库不保存这些参数的明文。
插件状态和卡片是已检查的业务数据，备份仍应按项目数据妥善保管。

崩溃时尚未结算的调用重启后记为 `unknown`，不会自动重放。
先到文件系统或外部系统确认结果，再点“已核实成功/未成功”；原始执行事实保持不变。
核查结论只能记录一次且不能跨工作区写入。不得用“再跑一次”推断未知写操作的结果。

## 备份与恢复

使用界面的“备份授权与记录”生成 SQLite 一致性快照，包含当前 WAL 的已提交数据。
快照目标必须是新的或空文件。不要在应用运行时仅复制主 `.sqlite` 文件。

控制库位于应用数据目录的 `mods-control.sqlite`，旁边有 `.initialized` 标记。
控制库丢失、损坏、版本不支持或部署策略不合法时，应用仍显示恢复提示，但工具入口停止执行。
不要删除标记、清空控制库或静默创建替代库，这可能遗失未知调用与已消费动作的证据。

管理员恢复步骤：

1. 完全退出应用并确认所有应用进程已结束。
2. 保全原控制库、`-wal`、`-shm`、初始化标记和部署策略；在原目录外另存证据副本。
3. 核实备份时间、来源、SQLite 完整性和应用版本。旧备份不能证明备份后没有发生外部写入；先核查这段时间的操作。
4. 将损坏库及其 WAL/SHM 移入保全目录，再将已核实的完整备份放到原控制库路径，保留初始化标记。
5. 使用兼容当前 schema 的应用重启，核对授权和未知操作后继续。不要在恢复过程中重新提交原操作。

自动恢复只重建隔离运行时，不自动恢复旧控制库、不重放命令。
回退普通功能可关闭“启用项目 Mods”；必需策略只可通过组织重新发布部署配置调整。
降级应用前先备份控制库并检查 schema 兼容性，不能用不理解现有记录的旧版本继续工作。
