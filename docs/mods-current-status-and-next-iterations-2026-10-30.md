# Mods 当前完成情况、能力边界与后续迭代说明

核对日期：2026 年 10 月 30 日。对象：DevClaw 的通用 Mods、创造者、项目运行机制、新版 AutoBiz Lean 和工作树变更查看能力。

## 一、当前结论

目前已经形成可运行的核心架构：平台提供受控执行、真实状态提交、产物检查和界面扩展接口；Mods 实现可替换的知识、规则、执行与展示能力；插件通过声明组合这些能力；创造者负责发现、生成、修改、验证和交付。

新版 AutoBiz 已经以这套机制跑通限定范围的五阶段业务链，包含实际 Git、编译、测试、失败修复和成果接受。独立工作树 Diff Mod 也已实现，能够复用平台通用接口。重构已超出“包装旧脚本、增加一层入口”的范围。

但是，当前还不能宣布“任意旧插件自动转换成功”“普通大型项目全面适用”“真实模型下质量不降且总 token 明显下降”，也不能宣布当前工作区代码已经完成整仓全绿和发布验收。下一阶段应集中解决真实项目覆盖、创作入口简化、复杂恢复及完整效果评测，而不是继续增加 AutoBiz 专属平台分支。

### 2. 如何理解完成状态

- **已实现并验证**：存在实现和对应运行证据，但只在列出的范围内成立。
- **已有实现、需当前版本复验**：代码已存在，也有历史验收；本轮没有重新执行全部真实用户路径。
- **部分完成**：核心链路可用，但适用范围或使用体验有明确缺口。
- **待补齐**：仍需要新增协议、实现或验证。
- **保留边界**：属于必要的权限、来源、大小或失败保护，不能通过删检查来“补齐”。

本文不使用一个总完成百分比。不同模块的代码完成、业务覆盖和发布准备程度并不相同。

## 二、整体架构已经完成了什么

### 1. 平台公共底座

| 能力 | 已完成的内容 | 实际作用及边界 |
| --- | --- | --- |
| Mods 执行与扩展 | 受控运行、工具与模型调用、文件能力、事件、Mod 状态及界面接入 | 作者可以扩展应用；并不意味着任意脚本无需声明就能获得全部权限 |
| 项目状态提交 | Host 管理输入、检查、批准和阶段完成事实 | 模型或插件返回 `passed: true` 不能直接替代真实成果接受 |
| 依赖与资源绑定 | 编译时绑定实际提供器身份、规则动作和声明资源摘要 | 替换 Mod 或 workflow 后必须重新编译验证，不能沿用旧源码的批准 |
| 原始需求来源 | 按声明向检查提供项目身份、原始请求及字节摘要证据 | 基线能核对真实来源；不代表系统已经理解并证明全部业务语义 |
| 上游变化失效 | 声明的输入变化会使旧检查、批准和阶段操作失效 | 防止用户改了上一步、下游仍拿旧结果继续推进 |
| 阶段分支来源保护 | 原生快照与读取窗口校验，拒绝创建过程中替换、删除上游文件 | 保证分支拿到真实来源；尚不等于所有业务基线支持跨项目继承 |
| 技能前后扩展 | 已有 `PreSkillUse`、`PostSkillUse` 等事件接入 | 可以接入检查与观测；关键业务门禁仍须进入可靠的执行及提交链 |
| 查询型界面 | Mod 可发起受范围限制的读取并展示结果 | 只读交互不必伪装成一次业务执行；查询不能取得写入或执行权限 |
| Git 读取 | 目录引用、基准固定、变更列表分页、按文件读取有界 Diff | 为不同插件共用；当前以固定基准到工作区的累计变更为主 |

相关实现集中在 [Mods 运行时](../src/main/mods/v2/)、[项目运行时](../src/main/harness-board/project-runtime/)、[组合编译器](../src/main/plugins/native-composition.ts) 和 [Git 检查服务](../src/main/services/mods-git-inspection.ts)。

这些能力的分工基本合理：平台维护可信事实和通用接口，插件决定业务要求。应继续守住这一边界，避免把阶段名称、业务文档格式或具体测试框架写成平台条件分支。

### 2. 创造者、保存和再次使用

| 能力 | 当前情况 | 仍需注意 |
| --- | --- | --- |
| 独立 Mod 创建与修改 | 已有真实模型、真实桌面创建、修改、保存及新会话复用记录 | 最新重构后的同版本完整体验仍需再验收 |
| 多个 Mods 组合 | 已验证文本处理与检查等独立能力组合 | 输入输出不兼容时需要适配，不是把名字放一起就能组合 |
| 非 AutoBiz 项目插件 | 已验证资料报告插件的创建、修改、项目试用和普通项目入口使用 | 证明能力不局限于 AutoBiz，但不代表所有插件类型已覆盖 |
| 业务校验 Mod | 已有引用、摘要衔接等可复用检查，能够作为阶段门禁 | 精确匹配和结构校验不能代替事实正确性与完整业务验收 |
| 依赖发现 | 可发现 source-set 中的提供器，返回真实来源及准备方式 | 大型 rules 提供器还不能走普通单 Mod 一键准备 |
| 能力声明 | 已有机器可读支持条件与诊断 | 需要持续统一工具、UI、文档的条件描述，不能将高级工具存在解释为普遍支持 |
| 未知结果对账 | 安装、导出已有核对入口和持久状态处理 | 冲突或证据不足时仍可能保持 unknown；不能伪装为成功或直接重复执行 |
| 保存后使用 | 已有安装后进入普通项目使用路径的实现和验收 | 应对当前插件种类、缺配置和环境缺失继续做同版本 UI 验收 |
| 连续创作 | 已有续作、版本历史、比较和归档 | 当前比较不是完整语义 Diff；影响分析不是所有项目、会话与外部副本的全量扫描 |

安装、导出对账不是待从零开发的功能。当前实现会核对候选、安装身份或导出文件摘要，并区分已完成、未执行、冲突和未知；核对本身不授予新的执行权限。见 [交付对账实现](../src/main/mods/devtools/creator-project-delivery.ts)。

连续创作也已经有实现。当前保留修订、活动草稿及历史容量边界；续作不能继承旧内容的批准，归档不能抹去尚未核实的执行结果。下一步应完善发现、比较和影响提示，而不是再造一套创作系统。见 [创作会话实现](../src/main/mods/devtools/project-authoring-session.ts)。

### 3. 新版 AutoBiz Lean

新版采用五个主阶段：**需求基线 → 需求定义 → 实现方案 → 编码验证 → 交付归档**。这五步是当前参考插件的声明，不是平台规定所有插件必须具有的阶段。

| 部分 | 已完成的变化 | 带来的效果 |
| --- | --- | --- |
| 需求基线 | 独立保存原始需求、来源和确认后的验收要求 | 后续摘要不能悄悄替代原始目标 |
| 知识 Mod | 显式阶段标签、知识根和部署单元绑定；保留未标注知识与相关 AGENTS | 减少不必要正文，同时避免凭模型判断丢掉全局约束 |
| 规则 Mod | 业务裁决集中到一个提供器；消费明确产物角色 | 更换业务规则不再需要同时修改交付层的一份隐藏副本 |
| 执行与证据 Mod | 声明完整执行、测试输入与结果契约 | 可替换执行框架，同时保留真实命令、测试统计和文件摘要 |
| workflow | 保留批次、工作树、实际测试和有限生产代码修复 | 运行事实由执行系统产生，模型负责实现内容 |
| 上下游衔接 | 声明输入、角色、知识映射及全部依赖失效 | 前插、后接和替换有明确检查位置 |
| 子任务上下文 | 补齐批次及最终测试所需的传递依赖、决策正文和验收关联 | 减少上下文不能以丢失前置决策为代价 |
| 交付 | 核对原始执行证据，归档基线及上游产物 | 不把编写了报告等同于实际测试成功或远程发布成功 |

源码入口为 [AutoBiz Lean](../resources/native-compositions/autobiz-lean/README.md)。它与旧版实现并存，不直接读取或写入旧状态机，也没有完成旧检查点到新五阶段的自动迁移。

部分确定性业务规则继续复用只读 Python helper；这是一项有意保留的复用。当前成果是减少重复状态查询、重复材料准备和业务规则副本，并非“消灭所有 Python”或“任何能力都必须重写成 JavaScript”。

### 4. 工作树查看 Diff

独立 [worktree-changes Mod](../resources/native-compositions/worktree-changes/README.md) 已可读取 workflow 的工作树，或由用户选择有权限的仓库及基准，展示变更清单和按文件加载的 Diff。

平台只提供通用 Git 读取、目录引用和查询界面能力。展示样式、筛选和业务组合放在 Mod 中，因此其他插件也可以使用，不需要新增 AutoBiz 专属页面。

当前是只读、手动刷新模式。暂未覆盖完整 IDE 操作、所有 Git 比较模式、工作树删除后的历史对象访问及自动刷新。这些属于后续扩展，不影响当前读取变更的核心闭环。

| 多个 Mods 组合 | 独立转换、检查组合成功与失败用例 | 任意输入输出自动兼容 |
| 创建并修改非 AutoBiz 插件 | 报告项目流程及中间检查修改已验证 | 只有 AutoBiz 之外一个案例就足以证明所有业务通用 |
| AutoBiz 五阶段完成 | 3 条真实 Host 全链通过 | 模型内容与用户决定由受控测试提供，不是 3 个真实用户项目自然完成 |
| 替换业务规则 | 英文规则替换后完成全链及附加检查 | 修改产物结构后无需适配消费方 |
| 前插需求转换 | `convert → baseline → definition → e2e` 前缀组合通过，覆盖知识映射及输入失效 | 该用例不是“前插后再跑全部五阶段编码交付”的单次完整验收 |
| 后接独立检查 | 五阶段后接引用、摘要检查，先失败再修订完成 | 附加检查不等于浏览器应用 E2E；代码 workflow 的实际测试另行验证 |
| 更换执行框架 | 独立 Python doctest 提供器实际编译、测试及证据核对通过 | 第三框架已经完成五阶段 Host 全链，或任意框架名称都可直接使用 |
| 失败后的修复 | Node 真实测试失败，仅修生产代码，原测试重跑及最终检查通过 | 可以自动修改断言让测试变绿 |
| 测试本身有问题 | `test_bug` 路径保留失败并停止自动推进 | 已支持无需人工判断的任意测试修复 |
| 中段调试 | 通用阶段分支及来源保护已实现并测试 | Lean 基线可直接继承到新项目身份；当前这条路径仍受限 |
| 旧插件自动转换 | 有源码检查、资源保留、迁移准备与诊断能力 | 任意隐含环境变量、脚本副作用、旧状态与 Hooks 都能自动等价转换 |

这里最需要补的是“同一个当前候选版本、普通用户真实入口、真实模型”的完整验收。确定性联调负责证明状态、证据与失败边界，真实模型体验负责证明模型能正确使用工具并完成创作；两者不能互相替代。

## 四、仍需补齐的实现与产品缺口

### 1. 普通项目规模与执行栈覆盖：优先级高

默认 Code 实现仍以 `backend_only` 为范围。Node 路线有生产文件和测试数量边界；当前每仓最多 8 个生产 JS 模块、每次最多 4 个测试文件及 8 个被测文件。Java 路线使用受约束的根工程 Maven compile 和 Python unittest。独立 doctest 证明了提供器可替换，但不是大项目适配的完成证明。

这些边界有助于防止虚假测试、遗漏源码和无限执行；同时也意味着当前默认插件不能直接承担多数大型、前后端混合项目。TS、TSX、JSX、Vue 等不能直接套用默认 Node 适配器。

下一步应由插件执行提供器支持代表性项目的原生构建与测试入口，声明实际覆盖清单、测试统计、跳过项及源码摘要。只有确实缺少通用执行或证据接口时才改平台。不能简单提高所有全局上限，也不能把没覆盖的文件记为已验证。

### 2. 大型 Mod 准备与配置仍不够简单：优先级高

AutoBiz rules 当前超过单 Mod 创作源码预算，目录会明确提示 `native-source-set-required`。用户可以导入完整 source-set，再选择 rules 依赖，但这会建立集合快照和项目草稿，步骤明显多于“复用一个规则 Mod”。

应补通用的大型依赖准备方案，或者将确定性资源与可执行入口合理拆分；让创造者直接解释适用入口、预检结果和下一步动作。不能静默扩大预算或隐藏失败。

知识绑定仍涉及绝对目录，`selectedDeployUnits` 当前采用 JSON 字符串配置。对普通用户，应提供结构化选择、路径预检、知识覆盖预览和缺项定位。换电脑时重新绑定本地资源，不能导出本机授权或凭据。

### 3. 复杂阶段恢复：已有基础，但业务闭环未覆盖全部场景

通用阶段快照、来源保护和受限调试已有实现。Lean 的需求基线另外绑定原项目身份，新调试分支具有新的项目身份，因此不能直接从中段继承原基线。

需要新增通用的分支来源协议，明确源项目、基线摘要、允许继承的事实、重新检查项和新分支批准范围。插件基于协议决定哪些业务基线可以继承。不得通过手工修改已接受基线的项目 ID 或关闭来源校验来实现。

对于配置、知识、Hooks、工作树及外部动作，应按资源类别声明恢复方式。文件可恢复不等于外部发布、数据库写入或跨仓合并可自动回滚。恢复能力应逐类准入，不能统一声称“任意步骤随时退回”。

### 4. 旧插件转换的语义保留与迁移诊断

当前有原始插件模块化基础，但脚本里隐含的知识加载、环境变量替换、前后 Hooks、产物路径和副作用仍需显式识别。自动转换应先输出职责与依赖清单，再逐项映射成知识、规则、执行、观测或兼容适配器。

应补可复用的转换验收清单：哪些原始行为保留、哪些改写、哪些无法自动判断、哪些需作者确认，并用同一输入对照原版与新版产物及失败行为。不能以“编译成功”代替“业务等价”。

新版 Lean 的重构路线与旧项目无损迁移是两件事。当前不读取旧状态机是清晰的架构选择；存量项目继续完成、另存新项目、迁移部分已确认产物应分别设计，不应混成一个入口。

### 5. 连续创作与影响分析的覆盖范围

续作、历史、比较、归档已存在。后续重点是把文本差异提升为可理解的影响说明：改了哪些阶段输入、哪些校验、哪些知识绑定，哪些成功记录需要作废。

目前依赖影响提示覆盖显式安装依赖及当前创作上下文，不能代表全部历史项目、其他会话、动态调用与外部导出副本。应先建立可靠的引用索引，再扩大范围；无法确定的影响应标为未知，而不是“没有影响”。

### 6. 通用项目读取和知识缓存

已有项目和上下文接口，但还需核对完整项目/Feature 投影的统一覆盖，避免插件为了读取状态重新启动脚本、拼接多个来源。平台应提供已有事实的只读投影，业务知识筛选仍由提供器决定。

知识提供器目前会重新列举所选目录以避免遗漏新文件；尚不能当作已经完成通用增量索引和版本化缓存。后续缓存必须包含来源、配置、阶段、输入和权限版本；失败、取消、unknown 不缓存成成功，展示缓存不替代最终门禁。

### 7. Git 的后续公共能力

当前累计变更查看已可用。其他比较模式、IDE 跳转、低频刷新、完整大文件查看和工作树删除后的历史访问，可在实际需要时补齐。

其中历史访问必须有独立授权和仓库来源校验，不能让过期目录引用继续读取任意仓库。此类功能应供独立插件复用，不写入 AutoBiz 分支判断。

## 五、效果、性能与 token：已经证明什么

### 1. 上下文材料确实减少，但不是总 token 结论

同一固定样例中，编译后的 Skill、知识正文和必读契约合计从 **89,485 降至 33,595 UTF-8 字节，减少约 62.46%**；该测量范围内的材料操作从 **50 次降至 33 次**。

这一结果已经包含新增需求基线和必读契约。历史的 25,211 字节、71.8% 等评审前数值不能继续作为当前结果。

测量不包含 Host 消息封装、产物正文、workflow、子代理提示、工具返回、修复重试及真实模型 token。因此，目前可以说“固定准备材料明显减少”，不能说“总 token、费用或总耗时下降 62.46%”。

### 2. Harness 的提升已经体现为可执行约束

当前改进包括原始目标留存、上游变化失效、真实检查提供器绑定、真实执行证据、失败来源区分及阶段提交控制。它们可以降低遗漏要求、沿用旧结果和伪造成功的风险。

但结构完整不自动等于业务正确。还应增加外部固定验收样例、错误实现反例和独立评价，验证模型是否为了过检查而遗漏未形式化的目标。规则需要支持变化，同时不能由同一次生成随意降低自己的验收标准。

### 3. 性能已做修复和局部验证，不能宣布全面根治

本轮包含操作范围内快照复用、原生流式调度优化、按需读取工作树 Diff 等改进。聊天性能 9 个脚本通过，400 条混合高度消息的浏览器拖动测试中可见空白帧为 0；此前也保留了真实桌面和 2,000 条持久消息记录。

这些结果证明对应路径有改善，但还缺当前最终候选上的多轮同条件对照，尤其是大型仓库、长工具输出、持续流式响应与拖动同时发生时的体验。真实桌面历史记录和浏览器用例应分别报告，不能互相冒充。

完整性能验收应同时记录首个有效响应时间、阶段总耗时、滚动/拖动帧延迟、可见空白持续时间、主进程阻塞、内存和 Git 查询耗时。完整成本验收需汇总父代理、子代理、工具带回内容、重试和缓存命中，服务不提供的用量标注未知。

以下使用 R0—R5 表示本报告建议，避免与旧方案的 P0—P6、S6 混淆。阶段按可验收的交付划分，不按新增接口数量衡量进度。

| 阶段 | 主要工作 | 归属 | 完成标准 |
| --- | --- | --- | --- |
| R0：固定现状与最终联验 | 整理当前改动，区分历史清理；固定候选；执行整仓及三条真实创作流程 | 集成与测试 | 同一候选的失败都有明确处理；创建、组合、非 AutoBiz 项目修改可保存并再次使用 |
| R1：让现有能力更容易用 | 大型依赖准备、结构化配置、知识绑定预检、缺项与恢复入口收敛 | 创造者、通用配置、插件声明 | 普通用户不需手写 JSON 或猜 source-set 流程；异常能在原入口恢复 |

| R3：复杂恢复与迁移 | 通用分支来源、知识/配置/Hook 恢复声明、旧项目迁移范围 | 平台协议与插件适配共同完成 | 修改中间步骤后正确继承允许的事实，重验失效结果；不可恢复副作用明确阻断 |
| R4：性能及成本证据 | 项目投影、版本化知识缓存、真实长会话回归、完整用量与质量对照 | 平台性能、知识提供器、测试 | 相同业务输入和验收下报告质量、延迟、用量；不以漏读和弱化测试换取变快 |

R0 应先完成，后续可以并行但需控制共享文件冲突。建议分为公共协议、插件执行与业务、创造者与配置、独立验收四个职责；主集成统一冻结版本和验收口径。性能基线应从 R0 开始记录，R4 再完成系统性优化与对照。

不建议同时扩展所有框架、所有旧插件和所有 Git 功能。应先确定代表性工作负载，让功能边界、测试和用户入口一致，再按独立案例扩大覆盖。

## 八、判断后续开发方向是否正确的标准

1. **同样的业务目标仍能完成。** 原始需求、知识、必要 Hooks、配置和产物验收不能因为减少上下文而丢失。
2. **修改一项能力不要求修改整套系统。** 规则、知识、执行或界面替换应通过契约完成；契约改变时明确指出受影响消费方。
3. **平台增量具有独立复用对象。** 新能力至少用第二个独立场景验证，平台不识别 AutoBiz 阶段名或专属文档。
4. **创造者减少作者操作，而不是掩盖不确定性。** 自动发现和生成可以更主动；缺配置、未知执行结果、语义不兼容必须具体说明和恢复。
5. **效果与成本一起验收。** 固定验收条件下衡量成功率、业务质量、修改成本、总用量和延迟，不只计算提示词长度。
6. **不再重复建设。** 已有 Host、workflow、审批、安装及状态机制继续复用；Mods 不维护另一套与平台冲突的完成事实。

按这些标准，当前架构方向可以继续推进；尚未解决的主要矛盾是“受控样例已闭环”到“普通用户、实际规模项目稳定使用”的距离。下一步优先填平这段距离，比继续增加外围功能更有价值。

### 2. 是否侵入项目模式

**平台项目模式底层有修改，不能称为零侵入；没有将所有旧插件强制改成 Lean，也没有要求用户采用固定五阶段。**

当前项目目录同时识别旧 board 协议与新 Host 协议。旧项目按其原安装身份和协议读取；新模板进入统一项目入口。发现同名新插件不会自动将旧项目切到新协议。具体逻辑见 [项目目录读取](../src/main/harness-board/catalog-reader.ts)。

本轮底层变化可分为两类：

| 类别 | 变化 | 影响范围 |
| --- | --- | --- |
| 显式选择的新能力 | `contextArtifactIds` 控制初始阅读；`requestProvenance` 请求原始目标来源；提供器及资源绑定 | 只在声明时采用；未声明的旧清单保留相应默认行为 |
| Host 公共行为调整 | 启动下一阶段前重新检查已接受的上游产物；持久化分支输入基线；操作内快照复用 | 使用 Host 协议的其他项目也会受到影响，不只 AutoBiz Lean |

其中最明显的行为变化是：已有 Host 项目若直接修改了已接受的上游文件，再继续下一阶段，可能被 `EVIDENCE_STALE` 阻断。正确方式是通过声明的修订阶段或适配后的调试流程重新检查，不能静默将修改后的文件视为原来已经接受的结果。

这属于可靠性加强，但对以前依赖“手改上游文件后直接继续”的插件是实际兼容影响，应说明并提供恢复路径。不能仅因为新字段可选，就推断全部旧行为完全不变。

### 3. 对不同存量插件的判断

| 存量情况 | 当前判断 | 需要保留或补验的内容 |
| --- | --- | --- |
| 原始 board/Skill/CLI 插件，未转换 | 保留旧协议路径，不自动交给新 Host 接管 | 原始 AutoBiz 的首次提问、选项续接、知识注入、Hooks 和 CLI 推进仍需真实完整回归 |
| 已使用 Host 的旧组合插件 | 可继续解析未声明新字段的清单，但会经过公共 Host 校验 | 已接受产物变化、历史项目恢复和旧调试分支重点复验 |
| 纯 Skill、聊天扩展插件 | 不要求转为项目插件或安装 Lean 提供器 | 共享模型、Mods 运行时和启用入口仍属于回归范围 |
| 用同一安装身份直接替换旧协议包为新协议包 | 不保证旧项目可以继续；代码会阻止将新 Host 包误当旧 board 包 | 应并存安装或走明确迁移，不能同名覆盖后自动认领旧状态 |
| 旧阶段调试分支 | 新建分支具有输入基线；历史分支可能缺少新增持久证据 | 缺证据时可能阻断；需专门制定兼容读取或重新建分支的恢复方案 |
| 将旧项目直接改成 Lean | 目前没有自动迁移闭环 | 旧状态、批准、工作树与产物不能直接冒充新五阶段事实 |

数据库增加 `host_branch_inputs` 表属于增量结构；它不删除旧项目，但仅仅能打开数据库，不足以证明旧项目和旧分支都能继续执行。

此前已做统一入口中 Host/legacy 并存、同名绑定隔离、纯 Skill 启用与普通项目使用等回归。本次进一步核对了可选字段默认值、Host 共享校验以及旧附件身份。现有测试包含同名 Host 不劫持旧项目、安装 UUID 优先、非法新协议不回退冒充旧协议等场景。
