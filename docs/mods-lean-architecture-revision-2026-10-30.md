# Mods 轻量插件架构：独立评审后的修订方案

日期：2026-10-30。范围：`codex/mods-v2`，应用版本保持 `2.0.0`。本轮不打包、不触发 GitHub Actions。

## 1. 评审结论与目标

三位未继承开发对话的评审者分别检查架构职责、组合扩展和上下文与业务效果。结论一致：公共 Host、声明式组合、Mods 提供器的分层可以保留；当前样例还不能证明能力可以独立替换，也不能证明端到端 token 下降或业务效果等价。

最初代码评审未通过。本文修订方案随后由三位评审者分别通过：职责与可信身份、组合扩展、需求基线与业务效果。第三项意见要求明确自动 `test_bug` 阻断边界，已纳入 §3.4。核心整改现已实现并完成主要联合路径验证；当前证据和未覆盖范围见 [详细说明](./mods-lean-plugin-explained-2026-10-30.md)。方案批准本身不替代代码或业务验收。

目标是保持原有业务约束、知识、Hooks 和执行证据，用更少的重复材料与操作完成任务；知识、业务规则、执行与证据能力可以在明确契约下替换。AutoBiz 是复杂实例，平台不得识别 AutoBiz 的包名、阶段名称或业务文档格式。

## 2. 职责与可信边界

| 层次 | 负责内容 | 不承担的内容 |
| --- | --- | --- |
| 平台 Host | 项目状态、原始任务、依赖失效、固定安装身份、受控执行、原始回执、所有必需检查通过后提交状态 | 不判断某企业的需求、设计或交付清单是否业务合格 |
| 组合声明 | 阶段顺序、输入输出、角色映射、知识策略、规则绑定、执行提供器和资源 | 不通过模型填写成功标记跳过检查 |
| 知识 Mod | 根据显式配置选择材料，保留来源、摘要和最近 AGENTS 边界 | 不默默丢弃未标注知识或猜测业务相关性 |
| 规则 Mod | 需求、规格、设计及交付文档的业务验收 | 不拥有项目状态写入权，不复制执行引擎 |
| 执行与证据 Mod | 执行契约、实际编译测试、输入与运行证据核验、原字节归档约束 | 不再复制另一份完整业务规则；测试通过不自动等于业务完整 |
| Skill / workflow | Skill 描述阶段工作；workflow 编排受控动作、子代理和工作树 | 不维护另一套持久项目状态，不自报身份或批准 |

“独立替换”指替换一个契约单元后重新编译、安装和确认，通过原生检查继续使用。它不意味着任意脚本无需适配即可运行，也不意味着更换依赖后旧批准和旧成功回执仍然有效。

## 3. 必须修正的问题

### 3.1 业务规则只保留一个裁决来源

初评时 delivery 内置完整 rules 副本，导致更换规则 Mod 后仍受旧规则限制。修订为：

1. 编译器从真实已安装 action catalog 解析其他已声明检查的提供器身份，固定到检查配置。不得接受模型自报的 UUID、摘要或来源身份。
2. Code 证据检查验证原 workflow 的 `solution-check` 成功回执，核对固定的规则提供器、动作、同一运行、完整输出和相同输入摘要。
3. Delivery 文档合格与执行证据合格由 Host 的两个必需检查共同约束。交付证据检查保留它消费字段的结构、文件稳定性、归档原字节、执行与 Git 证据验证，不重新运行整套需求与设计业务规则。
4. 输入、配置、规则提供器或 workflow 变化后必须重新验证；不存在“拿旧成功证明新内容”的通道。

只扩展通用编译绑定，不新增 AutoBiz 专用接口或另一套回执存储。已有包未声明新字段时保持原行为；新包缺少所需可信绑定时拒绝执行。

具体编译字段为 `bindCheckProviderIdentities: { rulesProvider: { checkId: "solution.business", actionId: "solution.inspect" } }` 和 `bindResourceDigests: { workflowSha256: "workflows/lean-code.workflow.js" }`。两遍解析先获得所有检查的真实提供器，再解析关联动作；`solution.verify` 与 `solution.inspect` 必须属于同一安装 ID、包名和源码摘要，且后者确实在 catalog 中唯一导出。资源摘要仅从明确声明的实际资源字节生成。不存在、歧义、跨摘要、非动作检查和配置键覆盖均拒绝。前向引用只引用身份，不引入检查执行依赖或递归。

### 3.2 消除组合拓扑的隐含硬编码

检查配置显式声明其消费的产物角色。检查器只处理所需的已声明子集；Host 继续追踪全部输入，新增前置产物不能为绕过检查而从依赖图删除。重复角色、缺失必需角色、输入不在声明内、契约不匹配须拒绝。

知识 Mod 使用作者声明的阶段映射。插入需求转换或追加 E2E 时由创造者更新映射和输入输出，不再修改知识代码中的固定阶段列表。未知映射给出具体配置缺项；未标注知识和最近 AGENTS 仍保留。

执行框架白名单归执行与证据 Mod。workflow 只消费已锁定提供器的版本化执行契约，不在项目 workflow 中先封死 Node 或 Java 名称。执行器与其证据校验仍作为完整替换单元，不能任意拼接不兼容的 runner 和检查器。

移除 delivery 的样例包名判断，保留原生安装 ID、包名、摘要和动作的精确绑定。workflow 身份从声明资源的真实字节生成并固定，避免作者在多个包手写同一 SHA；来源校验不能取消。

### 3.3 恢复需求基线与必要上下文

不能把当前可写 `Definition.requirements` 同时当作验收基线。增加通用、显式选择启用的原始请求来源注入：由 Host 从持久项目 goal 生成来源类型、项目身份、UTF-8 字节数及 SHA-256 摘要，纳入已有输入指纹与大小限制，拒绝插件或模型覆盖。正文保存在需求基线产物中，规则 Mod 将其与 Host 摘要逐字节核对；检查参数不再重复携带整份正文，也不提高全局大小上限。独立需求基线阶段复用既有 `resultApproval: "human"` 确认并成为 Definition 的固定上游输入。原请求摘要只能证明来源，不能证明模型提炼完整；确认后的清单才是后续完整性对照基线。

默认流程由四步调整为五步：确认需求基线、需求与验收定义、方案、代码、交付。普通用户确认一次提炼结果，无需手写基线文件。新要求走显式修订与下游失效；不能在修复 Definition 时同时修改已确认清单。没有明确原始请求的新导入任务应提示补齐，不凭空制造已确认记录。

批次上下文按引用生成依赖集合：本批规格、依赖批次规格、实际引用的决策正文、来源定位及设计约束。缺失引用阻断，不因减少材料而省略。能够可靠选取时传子集；无法安全细分时保留必要原文并说明原因。

### 3.4 区分运行成功与业务合格

真实测试数量、源码摘要和成功退出只能证明某次真实执行，不能独立证明所有业务场景已经覆盖。增加明确的场景到用例映射、独立审查与固定外部业务验收样例；关键断言使用有代表性的行为变异验证。

对 `test_bug` 路径，原命令不变不足以保证断言不弱化。本轮保留 `source_bug` 有界自动修复；遇到 `test_bug` 保留原失败证据并停止自动改测试，明确提示需要审查测试变更后重新运行。不得让同一自动流程修改失败断言后仅凭通过结果继续。未来恢复自动测试修复，须增加绑定原失败、修改前后测试摘要及验收要求的真实批准；独立模型审查或用例数量不变不足以代替该批准。恒真测试、缺失场景、未使用生产代码、删除失败断言须有负例。

这些机制提高可核验性，不宣称能自动证明任意程序的业务正确性。不能以模型审查意见代替原生运行记录，也不能把模型意见当作确定性证明。

原失败运行保持失败及原始证据，人工审查后的修订进入新运行，不回写旧运行成功，也不重放不明副作用。恒真或弱化反例由固定外部业务验收样例与代表性变异揭示，不宣称通用静态检查能够识别所有无效测试。

### 3.5 创造者可发现和复用能力

依赖目录支持读取通用 source-set 声明中的提供器，不依赖 `providers/*` 的目录猜测，不只暴露整个 AutoBiz 包。目录发现仅返回惰性元数据；实际准备时核对真实源码和摘要，继续使用原生安装确认与权限流程。

知识读取可通过显式绑定的部署单元子根或材料索引缩小候选范围，先确定相关路径再读正文。索引必须有明确覆盖约定；不能因为索引过期而静默遗漏新资料。无索引路径保留原有语义，不能对未读取文件宣称“完整检索”。

## 4. 验收要求

| 场景 | 必须证明的效果 |
| --- | --- |
| 替换规则 Mod | 新规则接受的合法文档不被 delivery 的旧业务副本再次否决；冒充身份、旧摘要和失败回执仍被拒绝 |
| 执行提供器换名与替换 | 正确重新绑定后可运行；相同名字不同摘要或未经锁定的提供器不能继承旧证据 |
| 前插需求转换 | 输入产物保留真实依赖，转换结果参与验收；删除依赖或同时删掉基线要求不能通过 |
| 末尾追加 E2E | 无需增加平台阶段名特例，知识映射、执行和门禁可接通 |
| 非 AutoBiz 组合 | 独立创建一个简单业务流程并复用通用提供器，平台不增加业务分支 |
| 第三个实际测试框架 | 完整替换执行与证据提供器，workflow 不改实现，执行实际命令和测试；换名称或返回 mock 统计不算通过 |
| workflow 身份生成 | 修改资源后重新编译自动取得新 SHA；旧运行、编译后篡改及模型自填 SHA 拒绝 |
| 单提供器发现复用 | 冷目录能发现 source-set 中一项提供器并在另一业务中安装使用，无需导入整套 AutoBiz |
| 修改技能、步骤或产物 | 影响范围可识别，旧回执和下游结果不能冒充新结果 |
| 多批次与决策引用 | 子代理能拿到所依赖规格、决策和来源；引用不存在时明确阻断 |
| 测试修复与业务验收 | source_bug 正常修复可过；恒真测试、场景遗漏、断言弱化负例不可自动认定成功 |
| 知识与 Hooks | 原配置、知识来源、未标注材料和 Hooks 边界保留；相关缺失有明确诊断 |
| 性能与费用 | 对比实际主/子代理材料、工具返回、重试和延迟；输入字节缩减不替代总 token 或业务质量结论 |

先运行模块边界测试，再进行真实 Host、workflow、Git、编译及测试的联合验证。规则替换必须实际改变一条业务政策；前插必须验证新增输入变化会使下游失效；后接 E2E 必须失败一次并阻断。可使用受控模型输出检验确定性链路，但必须标注，不能据此声称真实模型创作质量已通过。现有 worktree diff 和长会话性能成果保留并回归。

## 5. 实施顺序与复审门槛

1. 三位评审者确认可信身份、输入基线、组合契约及验收边界；记录异议及解决方式。
2. 形成面向使用者和插件开发者的通俗说明，清楚区分现状、计划和验证证据。
3. 并行开发：公共可信绑定；需求与业务契约；知识、发现与可组合性。文件所有权明确，交叉接口先约定。
4. 主代理整合执行 workflow 与上下文依赖，运行新增反例及跨模块测试。
5. 独立复审实现，完成 Host 与桌面回归。未通过项明确保留，不用“方案已通过”代替“实现已完成”。

修订后的固定样例准备材料从 89,485 降至 37,705 UTF-8 字节，范围内操作从 50 降至 33 次。字节减少约 57.86%，仅包含编译后 Skill、知识正文与必读契约；不含产物、workflow、子代理、工具返回、重试和 Host 消息封装。评审前 25,211 字节的记录已过时。没有端到端 token 和同模型业务质量对照证据之前，不作费用降低百分比或效果不降低的量化承诺。
