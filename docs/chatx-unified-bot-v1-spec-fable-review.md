## 1. 核心决定

第一版的硬约束是：**桌面（Electron）现有行为零改动；IM 端允许缺少并发类高级功能。**

这条决定影响 spec 的 §3、§11、§19、§21，需要写回。它的作用不是推迟最难的一块，而是把其中风险最高的部分移出 V1 范围。

依据：§11.2 现在要求共享核心“拥有全局唯一 per-thread active-run registry”，并要求“桌面 stop/replace 一个 IM 正在执行的 Thread 时，原 IM event 得到精确 cancelled”。后半句是真正逼迫改动桌面 stop/steer/coordinator 所有权的来源，也是桌面主路径回归风险的集中地。产品上既然接受 IM 少做并发功能，这半句可以退出 V1。

一个必须先说清的边界：本原则不恢复 IM 直接拼装裸 `createAgentRuntime()`。IM 仍走共享无状态准备层与 `invokeThreadTurn()`，仍不得直接 `createAgentRuntime()`。被裁掉的只是 IM 侧的富并发所有权功能，不是共享核心本身。这不构成“第二套远程执行语义”，因为 IM 用的是同一套准备层和同一把运行租约，只是没有实现富并发那部分。

## 2. 需要写回 spec 的修改

### 2.1 V1 执行模型：桌面核心不动 + 一把运行租约

用下列结构替换 §11.2 现在的单一 registry 表述：

1. 桌面 stateful 核心（active-run、stop、replace、steer、coordinator、goal 现态）保持现状，不抽取、不改写。
2. 共享核心只包含无状态准备层（见 2.4），桌面继续是它的唯一调用方。
3. 新增一把 per-thread 本地运行租约，作为“该 Thread 是否正在执行”的单一真相。桌面和 IM 在创建 Runtime 前都必须先取得该 Thread 的租约，结束后释放。
4. 并发规则单向：IM 让位桌面；桌面不操作不属于自己的 run。

“桌面行为不变”在这个模型下是可证明的：当 IM 没有在某 Thread 上执行时，该 Thread 的运行租约始终可得，桌面路径与现状逐字节一致。运行租约只在“IM 正在该 Thread 执行”这一新增场景里生效，而该场景在旧结构中根本不存在，本来就必须有安全处理，否则两个 Runtime 并写同一 Thread 会损坏 checkpoint 和消息历史。

补充术语，避免与网关租约混淆：

- **网关设备租约**（§13.1 的 `lease`）：某设备在当前 `deviceEpoch` 下代表该 conversation 行动的授权；
- **本地运行租约**（本节新增）：同一 Thread 上桌面与 IM 之间的单 owner 互锁。

二者是不同机制，spec 需要分别命名。

### 2.2 §11.2 拆分为两条交付边界

- **V1 必须（数据完整性，不是功能）：** 同一 Thread 任一时刻只有一个 Runtime owner。桌面与 IM 通过本地运行租约达成，IM 让位桌面，任一路径都不得在已被占用的 Thread 上创建第二个 Runtime owner。
- **Post-V1（非 V1 门槛）：** 桌面 stop/replace 一个 IM 正在执行的 Thread 时让 IM event 得到精确 cancelled；IM 对桌面 run 的 steer/replace；桌面与 IM 在同一 Thread 上的并发协作。

请在 spec 里明确：“单 owner”是不可退让的正确性底线，不属于可裁剪的高级功能；被裁掉的是双向取消与 steer。

### 2.3 §3.2 增补一条 allowed difference

§3.1 现在把“工具沙箱、审批与取消机制”列为桌面/IM 必须等效项。在 2.1 的模型下这是过度承诺，需要在 §3.2 增补：

> IM run 在并发上从属于桌面。V1 不保证桌面能即时取消一个 IM 正在执行的 run，也不保证 IM 能抢占或 steer 桌面 run。单轮内部的沙箱、审批门控和自身 `/停止` 语义仍与桌面等效。

被降级的只是跨路径并发取消，不是单轮内部语义。

### 2.4 §11.4 / §19 / §21 重新界定共享核心与分期

§11.4 现在把“完整共享（含 active-run 所有权统一）”写成正式上线门槛。在桌面零改动原则下，这不再是 V1 门槛，改为：

- V1 的共享核心 = 无状态准备层：Harness context、prompt 准备、模型路由与 Trace、Runtime options 组装、transport-neutral event sink。桌面继续是唯一调用方。
- V1 的并发机制 = 本地运行租约。
- 完整行为对等（桌面/IM 的 stop/steer/replace 逐项等效、对比测试）= post-V1 增强，不是上线门槛。

配套修改：

- §11.4 步骤 4“将现有 IPC handler 收敛为薄 Adapter”限定为：收敛到无状态准备层之上，保留桌面 active-run/stop/steer/coordinator 所有权。步骤 6 的对比测试中，并发取消相关项归入 post-V1。
- §11.4 末句“Fable 提出的窄共享单元是中间步骤”改为：无状态准备层抽取加本地运行租约就是 V1 在执行所有权维度的目标形态；IM 不复制桌面富并发所有权，不等于保留第二套执行语义。
- §19 阶段 0A 的“Desktop Adapter 改用共享核心，桌面行为必须保持不变”限定为：0A 只把桌面接到无状态准备层，不移动 active-run/stop/steer/coordinator 所有权。
- §19 阶段 1 需要明确桌面对收件箱 Thread 的交互边界。建议 V1 定为“桌面只看不发”：桌面可以查看、镜像流、审批，但不在一个 IM 正在执行的收件箱 Thread 上发起新 Turn。这样第一个端到端闭环不触发跨路径并发，运行租约的作用点推迟到阶段 2 的 Feature Thread。
- §21 PR-B 范围相应收窄为只抽取无状态准备层，不含 active-run 所有权；本地运行租约作为独立小项（可并入 PR-D 或单列）。

### 2.5 一处需要下代码确认

桌面现有的“忙”路径是否假设正在执行的 run 属于自己（例如直接 steer 或注入）。如果是，需要加一条窄守卫：只对自己 own 的 run 执行 steer/replace，遇到不属于自己的 run 按忙处理。这是本原则唯一可能落到桌面侧的改动，且只会让桌面更保守，不改变桌面独立执行时的任何成功路径，因为独立执行时租约中没有他方 run。

## 3. 其余待收口的发现

以下与桌面原则无关，是上一轮口头评审已提出、尚未写入 spec 的项，请一并补入。

### 3.1 [P1] 本地执行必须由网关设备租约门控

§13.1 的入站事件带 `lease{id,expiresAt}` 和 `deviceEpoch`，但 spec 没有任何一条要求客户端在**执行前**校验它们。§13.4 只约束网关侧对 ACK/回复的接受，§15.2 只撤销旧设备的租约和下行权限，都没禁止旧设备本地执行。

后果：设备 A（epoch 5）本地队列里已投递一个 Feature 事件，用户从设备 B 接管（epoch→6，撤销 A）。A 若在断网状态下继续消费本地队列，会在本地跑完副作用（Feature 模式带自动提交，等于 git commit），跑完才发现 ACK 被拒。同一任务在两台设备各执行一次外部副作用。

补入规则（建议进 §12.4 或 §13）：客户端启动 Runtime 前必须持有未过期的网关设备租约且 `deviceEpoch` 经网关确认为当前；断连、租约过期或 epoch 落后时挂起执行，不得开跑。

### 3.2 [P1] 分段回复缺少大小与条数策略

§8.2 允许收件箱写方案这类长输出，§10.5/§13.3/§16.2 有分段，但全文没有定义单段上限、最大段数和超限行为。API 参考里平台文本上限是 3000 字。

补入（建议进 §13.3）：单段上限对齐平台限制；定义超限策略，例如截断并附“完整结果见桌面”指引，或明确的多段续发上界。

### 3.3 [P1] `/重试 <事件短码>` 需要把短码发到 IM

§10.1 靠事件短码重试，但 §6.5 只保证 outcome_unknown 在桌面 Thread 和状态页可见。纯 IM 用户拿不到短码就无法 `/重试`。

补入（§10.1 或 §12.4）：IM 侧的 outcome_unknown / failed 回复正文必须携带对应事件短码。

### 3.4 [范围] 后端网关是承重交付，不是 app 侧内部项

spec 以 app 侧为主，但整套设计依赖一个独立后端网关（§5 第一层、§13 协议、§16.3 数据、§18 阻塞项）。网关承担平台凭据托管、招乎上行接入（webhook/Kafka，非现有 WSS 中继）、OpenID→principalId 映射、设备路由与接管、顺序与去重、下行幂等。这是净新增基础设施，当前 chatx.ts 的中继不承担这些职责。

§18 把它压成阻塞项清单，低估了交付比重和风险，身份映射来源、顺序保证、平台是否支持下行幂等这些难点全是未决项。建议：

- 在 spec 里把网关列为与 app 侧并列的交付物，而不是外部阻塞项里的一行；
- PR-C（Mock Gateway）可以让 app 侧先跑，但进入联调前必须先敲定网关归属、部署边界（单企业/多企业）和 §18 的七项契约；
- 如网关另有规格，§13 应引用它并声明契约冻结点。

### 3.5 [P2] 补全项

- **纯 IM 用户的审批死路：** §8.2 收件箱外部写“等待桌面审批或被策略禁用”。纯 IM 用户永远不开桌面时，这类 Turn 每次在 TTL 后被取消。建议收件箱 V1 默认走策略禁用而非等桌面审批，别让纯 IM 路径走进死胡同；Feature 模式仍可要求桌面审批，那是刻意的安全边界。
- **首条消息、零设备在线：** 此时 route 未建，§15.1 的离线处理默认已有 pin 设备。需要补网关此刻的行为（挂起重投或回“无在线设备”）。
- **received-ACK 顺序与持久化耦合：** §13.4 严格按 seq 首投加上 §12.3 第 6 条 flush 失败不发 ACK，意味着一次落盘卡顿会扣住 received-ACK，从而在网关把后续 `/停止`、`/收件箱` 一并堵住。V1 可接受，但应作为已知限制写明。
- **传输澄清：** §16.2 的 gateway-client “WSS” 是客户端↔网关的自选传输，与 §18.4 平台上行是 webhook/Kafka 不冲突。加一句区分，免得被读成矛盾。

## 4. 已正确吸收，请勿回退

以下是 spec 相对上一轮评审已经改对的地方，应用本次修改时请保留：

- flush 纪律铺到 received/executing/waiting_desktop/completed/切换五个点，并有可注入失败的 flush 测试（§12.3、§20.4 第 24 条）；§12.5 明确不承诺 exactly-once。
- 三层版本栅栏收敛为单层 `deviceEpoch`；§7.1 明确不使用 routeVersion/targetRef/bindingVersion。
- 运行中允许切换，靠 snapshot 加前缀加串行队列保证归属（§10.4）。
- 审批 TTL 恢复，桌面无限等待不动（§11.5、§14.3）。
- 四条安全规则在位：不可信输入标记、`request_user_input` 仅桌面、错误回复脱敏、IM 文本不能当审批。

第 2 节的修改与“运行中允许切换”不冲突：切换针对的是一个 conversation 内 activeTarget 指针，运行租约针对的是一个 Thread 的执行 owner，两者正交。
