## 一、结论与首期交付目标

建议采用 **“App 先行、共享服务端承载协作、本地 Runtime 首发、云端 Runtime 后接”** 的路线。服务端先做模块化单体，不按产品概念拆成大量微服务；通过契约隔离模块，后续再按负载与安全边界拆分部署。

DevClaw Bot 的定位是：**服务 AutoBizDevOps 的 Biz—Dev 阶段，让业务人员、开发人员与专业 AI 伙伴围绕同一项需求持续协作，把需求澄清、技术评估、原型返讲、范围确认和开发交接连起来。**

对标 Grok Bot 的长期身份、协作交接、持续上下文和主动工作能力，结合此前讨论的 Waker/Group 形态，形成三个核心模块：

| 核心模块 | 用户能感知的能力 | 首期边界 |
| --- | --- | --- |
| 伙伴与团队：Bot / Group | 配置领域专家，组成 AI 协作团队，接受任务、交接和反馈 | 伙伴独立于一次会话、招乎群和执行机器；先支持明确分工与有界交接 |
| 工作模式：AutoBizDevOps | 在需求、原型、项目三种已有模式间传递经过确认的成果 | 衔接现有能力，不另造一套研发流程引擎；不把“模型已回答”当作“业务已确认” |
| Runtime | 在授权仓库与工作区执行，产出文档、原型、代码和验证结果 | 首期复用本地执行；统一契约预留常驻节点、云端隔离执行 |

身份权限、共享任务与成果、知识记忆、事件调度、招乎接入和存储为这三个模块提供基础能力，不作为六个独立产品另行铺开。

### 首期必须完成的最小用户旅程

1. 开发负责人在 App 创建“支付领域专家”，绑定经授权的领域资料、仓库引用、可用技能与维护人，再与需求分析伙伴组成“支付需求协作团队”。
2. 业务人员在 App 提交需求材料；招乎群入口接通后，同样可以通过 `@DevClaw + 任务编号` 提交或补充。
3. 需求伙伴生成问题清单和 PRD 草稿；业务直接修改，系统保存新的成果版本，不覆盖旧版本。
4. 领域专家读取获准使用的系统上下文，给出可行性、影响范围、风险和待确认事项；由指定人员确认允许向业务及招乎群展示的结论。
5. 需要时进入原型模式，基于指定 PRD 版本生成原型、收集标注并返讲；业务确认需求范围，研发确认技术评估与开发交接。
6. 开发人员点击“进入项目开发”，把已确认的 PRD、原型、评估和验收标准交给现有项目模式；过程与结果回到同一任务。

验收重点不是“群里能聊几句”，而是 **同一任务、明确责任人、可追溯成果版本、真实执行、人工确认、可靠交接**。

### 首期不做

- 不强制建设独立 Web；业务人员首期需具备 App 访问条件，否则应将最小 Web 审阅页提前纳入排期。
- 不建设通用桌面视觉教学、手机端、自主生产发布或全功能多智能体市场。
- 不把任意招乎群成员视为代码仓库授权人，不允许 AI 代替业务确认需求范围。
- 不承诺电脑离线后继续执行；首期只保证共享服务仍能记录任务并显示“等待执行节点”。
- 不迁移全量个人聊天、个人记忆、凭据或本地工作目录；只提供明确授权的导入与绑定。

### 2.3 不应被“合并成功”掩盖的阻塞项

1. **真实凭据不得进入对话。** 需求模式的 `RequirementConversationView.tsx` 当前把获取到的发布 Token 拼进 queued message。接入真实账号或共享成果前，必须改为凭据引用和受控发布工具；聊天、模型上下文、记忆、日志、ES 都不得保存令牌。
2. **需求到原型并未完整接通。** `DesignView.tsx` 的 `onEnterDesign` 仍记录 selection 并留有 TODO；需要明确消费 PRD/功能点及版本，不能把已有选择界面算成完整能力。
3. **有专家列表，不等于长期伙伴。** 当前 `ExpertAgentEntry` 是能力配置，尚无团队服务端生命周期与共享权限。
4. **本地租约不是分布式租约。** `thread-run-lease.ts` 使用进程内 Map；不能承担服务端多实例和远程节点恢复。
5. **IM 与项目记忆不能直接打开开关。** IM 收件箱明确关闭记忆，项目模式还有环境开关；需要先完成作用域与权限设计。
6. **Java 网关目前是文档与契约基础。** 本仓库未发现可直接启动的 Java 网关工程。Mock、SQL 和开发规格不等于生产网关已部署；需与现有网关负责人核对外部仓库和实际进度。
7. **来源分支夹带较大的辅助目录。** 包含 `playwright-main/` 及 `.playwright-mcp/` 历史材料。本次保留完整合并历史；发布前单独做来源、许可证、敏感信息和产物范围检查，不默认进入生产包。

## 三、总体架构与模块边界

### 3.1 部署与依赖

首期保持三个部署单元：现有 DevClaw App、本次新增伙伴协作服务、招乎网关。网关若已有独立工程则继续独立；若尚未落地，可共用基础设施，但不得混合业务与平台凭据边界。

| 模块 | 负责 | 依赖 | 不负责 |
| --- | --- | --- | --- |
| App 伙伴工作台 | Bot/Group 管理、任务、成果审阅、模式入口、执行节点状态 | 伙伴服务 API、已有需求/原型/项目 UI | 权限最终判定、跨端业务真相、直接访问数据库 |
| Bot / Group 服务 | 伙伴定义、配置版本、团队成员、职责分配、协作策略 | 身份权限、知识引用、任务 | 创建虚拟机、持有所有伙伴的共享登录态 |
| 工作模式服务 | 模式定义、阶段输入输出、成果交接、确认门禁 | Bot/Group、任务/成果、Runtime 调度、项目桥接 | 重复实现现有项目模式的内部阶段策略 |
| Runtime 控制模块 | 节点注册、能力匹配、派发、租约、取消、恢复与事件接收 | 身份权限、任务、工作区准备、凭据引用 | 决定业务范围、生成最终业务确认 |
| DesktopRuntimeProvider | 将执行契约适配到现有 AgentRunService、返回事件/产物 | 本地 Runtime、工具、沙箱、工作区 | 成为团队状态唯一存储或替请求者提升权限 |
| 任务与成果基础 | Task、Stage、Run、成果版本、审批、活动记录、幂等命令 | MySQL、S3、Outbox | 用聊天摘要替代正式成果 |
| 知识记忆基础 | 来源管理、权限过滤、检索、提炼建议、纠正与删除 | MySQL、S3、ES、模型能力 | 自动分享私人记忆或把推断作为确认事实 |
| 招乎群适配 | 验签、身份映射、群绑定、附件入口、任务编号、回执 | 现有网关、伙伴 API、权限与投递队列 | 长期任务真相、直接调用本地 IPC |
| Routine / 协作调度 | 持久触发、伙伴交接、优先级、限额、通知策略 | 任务、Runtime 控制、MySQL Outbox | 无限自我唤醒或越过人工确认 |

关键依赖顺序：身份与契约先于共享任务；共享任务与成果先于工作模式交接；Runtime 契约先于远程执行；群权限先于招乎群开放；记忆权限先于跨任务自动积累。

### 3.2 技术栈建议及待冻结项

- 桌面与 Runtime 延续现有 TypeScript / Electron，首期不迁移模型执行内核。
- 2026-10-02 用户已确认 **JDK 8、MySQL 5.7**，伙伴服务端按 **Java 模块化单体** 推进；现有桌面/Runtime 仍为 TypeScript。F05 的 Node 开发替身和编排不是生产服务端技术栈。详细决定、环境证据和待确认项见 `devclaw-bot-delivery/tasks/F04.md`。
- 已有网关规格写明 JDK 8、内部增强 Spring Boot 2.7.2、MySQL 5.7。**这不代表新资源也只能用这些版本，更不建议把相应公共旧发行版直接暴露到外网。** P0 需冻结安全维护来源、内部 BOM 和资源版本；外网使用批准的维护版本，并以契约与数据库兼容测试验证可迁回内网。
- S3 指兼容的对象存储能力，具体产品、签名方式、版本化、加密和生命周期支持需实测。ES 先做全文检索，不预设向量检索插件或商业功能可用。
- 首期不新增 Redis、Kafka、向量数据库作为硬依赖；以 MySQL 事务、Inbox/Outbox 和短周期拉取支撑试点，达到容量瓶颈后再替换队列适配器。

### 3.3 关键对象不要混在一起

| 对象 | 定义与关系 | 生命周期 |
| --- | --- | --- |
| BotTemplate / Bot | 模板描述职责；Bot 是有归属、版本与记忆策略的伙伴实例 | 跨任务存在；复制模板不复制私有会话、记忆或凭据 |
| Group | 多个 AI 伙伴组成的协作团队；另有明确的人类管理员和参与权限 | 独立于招乎群；一个 Group 可承接多项 Task |
| Task / Stage | 一次业务需求及其澄清、评估、原型、确认、开发交接阶段 | 围绕同一需求持续跟踪 |
| Thread | 某阶段的执行对话；通过映射关联现有 DevClaw Thread | 一项 Task 可有多个阶段 Thread；不把整个 Group 永久绑定一条 Thread |
| Run / Attempt | 一次执行及某次实际派发尝试 | 记录配置快照、输入成果版本、授权与租约 |
| ArtifactVersion | 文档、原型、评估、开发交接包、验证报告等的不可变版本 | 修改生成新版本；审批必须绑定版本 |
| Workspace / RuntimeNode | 授权仓库和执行目录的准备结果 / 承接执行的节点 | 不等同于 Bot，也不因前端页面切换而重建 |
| ImBinding | 外部招乎群与 Group 的访问入口映射 | 首期每个群最多一个有效 Group 绑定，可解绑；不改变 Group 身份 |

`Feature` 可继续作为项目模式桥接中的内部字段，不再作为伙伴产品层必须理解的对象。界面只呈现伙伴、团队、任务、阶段、成果与执行环境。

## 四、接口先行：首轮需要冻结的契约

下列是设计草案。P0 将其落为 OpenAPI / JSON Schema / fixtures，再从同一版本生成 Java 与 TypeScript 类型。不要只维护两份手写 DTO。

### 4.1 业务 API

统一前缀 `/api/bot/v1`；认证主体来自已验证身份，不接受请求体自报的 `actorId` 作为可信身份。所有写操作带 `commandId`；修改现有对象带 `expectedVersion`。

| API 草案 | 输入要点 | 输出与语义 |
| --- | --- | --- |
| `POST /bots`、`POST /bots/{id}/versions` | 名称、职责、知识/仓库引用、Skill 白名单、记忆策略 | 稳定 `botId` 和版本；发布配置不改变在途 Run 的快照 |
| `POST /groups`、`PUT /groups/{id}/members` | 伙伴与职责、人类管理/参与角色、协作限额 | Group 版本；同名不等同于同一身份 |
| `POST /tasks`、`POST /tasks/{id}/messages` | Group、输入成果、目标、任务编号、指定伙伴 | Task、消息与活动；消息不直接等于一次获准写代码的 Run |
| `POST /tasks/{id}/stage-transitions` | 目标阶段、输入版本、确认记录、`expectedVersion` | 校验阶段前置条件，返回新阶段或冲突 |
| `POST /uploads`、`POST /uploads/{id}/complete` | 文件元数据、用途、长度/校验信息 | 受限上传会话；验证和入库成功后才产生可引用成果 |
| `POST /artifacts/{id}/versions` | 基础版本、内容引用、修改说明 | 新版本；并发修改返回冲突，不以最后写入覆盖前者 |
| `POST /approvals/{id}/decisions` | 决定、意见、准确版本和审批版本 | 幂等确认；过期、撤权、版本变化均不能继续沿用 |
| `POST /tasks/{id}/handoffs` | 目标伙伴、输入版本、预期输出、截止/预算 | 持久交接；接收成功与执行完成是不同事件 |
| `POST /runs`、`POST /runs/{id}/cancel` | 工作模式、伙伴快照、输入引用、执行策略 | 接受后返回 Run；取消先进入请求取消，不立即声称已停止 |
| `GET /tasks/{id}`、`GET /events?after=...` | 对象 ID 或增量游标 | 当前快照及可靠增量；游标过期要求重新同步 |
| `POST /im-bindings`、`DELETE /im-bindings/{id}` | 平台群身份、Group、可见性策略 | 双端权限校验后的绑定；不是群里发一句文字就绑定 |

共同错误码至少包括 `FORBIDDEN`、`VERSION_CONFLICT`、`INPUT_CHANGED`、`APPROVAL_REQUIRED`、`NODE_OFFLINE`、`CAPABILITY_UNAVAILABLE`、`OUTCOME_UNKNOWN`。重放相同命令返回原结果；相同 `commandId` 配不同载荷拒绝。

### 4.2 Runtime 契约

独立于 IM V1，新建 Bot Runtime 协议及能力协商。建议执行代理由本地主动建立出站 WSS；业务 API 走 HTTPS，事件可通过 WSS 或可恢复的流式接口传递。

首版契约至少包含：

```text
RuntimeProvider
  describeCapabilities()                 // 支持的工作模式、工具、环境和恢复能力
  prepareWorkspace(workspaceSpec)         // 仓库版本、工作区隔离、材料挂载
  start(runSpec, lease)                    // 返回 accepted，不代表完成
  cancel(runId, attemptId, fence)          // 幂等取消，保留已发生副作用证据
  inspect(runId, attemptId)                // 重连时核对实际执行状态
  resume(runId, checkpointRef, lease)      // 仅节点声明支持时允许
  subscribe(afterEventSeq)                // 可恢复事件，不依赖 UI 是否在线
```

`RunSpec` 应固定 `schemaVersion`、`runId`、`attemptId`、`taskId`、`stageId`、`botVersion`、`modeVersion`、`contextManifestRef`、`inputArtifactVersions`、`workspaceSpec`、`grantRef`、`credentialRefs`、`budget`、`deadline`。

执行租约包含 `leaseId`、单调递增 `fence`、过期时间和授权版本。事件包含 `eventId`、Run/Attempt、序号、类型和结构化载荷。展示层不得以最后一段 Token 或 Promise resolve 推断执行成功。

初期 `DesktopRuntimeProvider` 适配 `AgentRunService` 与现有本地运行工厂，保留既有本地 Thread 互斥；服务端租约叠加于其外侧。后续 `HostedRuntimeProvider` 使用同一协议，但不能假定 Electron 代码已经可在无窗口 Linux 进程运行。

**权限有效范围取交集**：请求主体或已批准的服务身份授权、Bot 配置上限、Group/Task 资源授权、工作模式能力、执行节点能力、当前审批。Scheduler、伙伴转交和重试都不能改变这条规则。

### 4.3 工作模式与交接契约

| 工作模式/阶段 | 输入 | 正式输出 | 人工门禁与边界 |
| --- | --- | --- | --- |
| 需求模式 | 原始需求、补充材料、问题回答 | PRD、未决问题、规则、验收标准 | 业务负责人确认；现有“只处理需求、不写应用代码”的约束继续保留 |
| 技术评估阶段 | 指定 PRD 版本、授权仓库快照、系统资料 | 可行性、影响范围、依赖与风险 | 由领域专家使用受控只读能力执行，不偷偷解除需求模式的 Git/编码限制 |
| 原型模式 | 已指定版本的需求、功能点、设计约束 | 原型版本、标注记录、返讲意见 | 标注绑定目标版本；失效标注不可直接应用到新版 |
| 范围确认/开发交接 | PRD、原型、技术评估、未决项 | `DevelopmentHandoff` | 业务确认范围，研发确认评估与接收；未决项需显式接受或阻断 |
| 项目模式 | 正式交接包、仓库/分支、现有项目配置 | 开发与验证成果、风险、阶段状态 | 复用现有项目门禁；首期不由伙伴功能自动生产发布 |

`DevelopmentHandoff` 固定需求/原型/评估的成果版本、仓库 revision、验收标准、已确认排除项、开放问题及两类责任人的确认记录。项目模式返回内部项目/特性/Thread 引用。重复确认不得重复创建项目会话。

### 4.4 群里没有回复串，如何避免串任务

- 每项 Task 有短编号，例如 `T-1024`。群回复含任务编号、阶段、待确认人和 App 内任务链接。
- `@DevClaw T-1024 补充……` 明确路由；平台提供引用消息关系时可作为辅助，但不能假定招乎支持 Slack 式任务回复串。
- 同一招乎群存在多个任务而用户未指明时，先让用户选择；不采用“全群最近一条任务”作为隐式写操作目标。
- 首期只响应明确提及、任务指令、已有交接或已授权 Routine，不默认监听并存储所有群聊。
- 群里只播报阶段摘要、成果和待决事项；完整 Agent 内部讨论留在任务活动记录中。
- 绑定 Group 不等于向每个群成员公开所有历史成果。敏感内容保留在鉴权 App；群回执仅包含允许公开的信息。

### 4.5 与既有 IM 的兼容

已有 `contracts/schema`、`contracts/fixtures/v1`、`im-gateway-contract.ts` 继续作为单聊 V1 的依据，不借新增群能力静默修改含义。

群能力使用显式的新协议版本或独立入口，例如 `contracts/im-group/v2`；通过适配器把平台消息转换为伙伴任务命令。新 Bot Runtime 协议独立于“一名用户一条活动桌面连接”的 V1 会话模型。节点身份、请求人、群成员身份和业务授权版本分别建模。

## 五、MySQL、S3、ES 的职责与一致性

### 5.1 数据分工

| 资源 | 存放内容 | 不存放/不承担 |
| --- | --- | --- |
| MySQL | Bot/Group、成员与授权、Task/Stage/Run、成果元数据与版本、审批、节点租约、触发记录、Inbox/Outbox、审计索引 | 大附件、工作目录镜像；不得明文保存长效凭据 |
| S3 兼容存储 | 需求原件、PRD、原型包、验证报告、获准导出的检查点/追踪大文件 | 权限真相、运行状态、全量个人工作区和 `.env` 等秘密文件 |
| ES | 获准文档片段、记忆检索索引、任务/成果搜索投影 | 审批真相、任务队列、锁、唯一记忆原件 |
| 本地 SQLite/文件 | 桌面执行缓存、现有会话/检查点、未同步暂存 | 共享任务的唯一权威记录 |

ES 是异步、可重建的投影，搜索不可用不应阻止任务创建、审批或按 ID 查看成果。其检索可见性具有近实时特性，不宜作为“写入已经成为正式成果”的依据。[Elastic 官方说明](https://www.elastic.co/docs/manage-data/data-store/near-real-time-search)

### 5.2 最小逻辑数据模型

表名前缀暂用 `dc_bot_`，与已有 `chatx_gw_*` 分开。以下是逻辑集合，可在评审后合并部分物理表，不要求全部在第一周完成。

| 集合 | 核心约束 |
| --- | --- |
| `bot`、`bot_version`、`group`、`group_bot`、`group_member` | 组织/空间归属、维护人、不可变配置版本；人和 Bot 成员类型分开 |
| `task`、`stage`、`task_message`、`thread_binding` | Task 状态版本；Thread 使用节点/Provider 与本地 ID 的组合映射，不能全局猜测唯一 |
| `run`、`run_attempt`、`runtime_node`、`run_event` | 尝试次数、能力、心跳、租约与 fence；事件唯一键、顺序与缺口检测 |
| `artifact`、`artifact_version`、`upload_session` | 元数据与 Blob 分离；唯一版本、内容校验、上传完成状态 |
| `approval`、`approval_decision`、`resource_grant` | 决定关联具体成果/操作及版本；撤权与过期可校验 |
| `knowledge_source`、`memory_item`、`memory_revision` | 来源、可见范围、置信/确认状态、修改与删除记录 |
| `handoff`、`routine`、`trigger_receipt` | 交接与触发去重，来源链、轮数、优先级和预算 |
| `command_inbox`、`event_outbox`、`audit_event`、`im_binding` | 命令载荷摘要与原结果、投递状态、审计、平台绑定 |

业务表统一带归属、创建/更新者、UTC 时间和版本。唯一键应覆盖归属与幂等范围；授权查询必须显式限定空间，不凭对象 ID 本身表示权限。

### 5.3 MySQL 事务与派发

创建 Task/Run、记录命令处理结果与写入 Outbox 在同一数据库事务中完成。独立派发器领取消息并发送，消费者以稳定 ID 去重。服务重启后继续派发，而不是让 App 重发整项任务。

考虑已有 MySQL 5.7 方案，首期设计不依赖 `SKIP LOCKED`。采用受限候选查询、预期状态/版本条件更新、受影响行数判定和 DB 时间；短事务领取后释放，不能在持锁事务内调用模型或远程节点。具体隔离级别、索引、死锁重试和迁移方式需在目标版本压测。若选较新版本，可通过适配层优化领取方式，不改变投递语义。

Outbox 保证可重试投递，不承诺任意外部动作“恰好一次”。数据库派发幂等不等于 Git 推送、发布接口或招乎发送天然幂等。

### 5.4 S3 上传与成果提交

1. 服务端鉴权后创建 `upload_session`，分配随机暂存 key、用途、大小上限和有效期。
2. 客户端或 Worker 上传到暂存区；不得自行选择其他团队的 key。
3. 服务端验证类型、实际长度、内容校验和安全策略。大文件解析和扫描在受限进程中执行，限制压缩展开与解析资源。
4. 将经过验证的**准确对象版本**固定到不可变成果区，再以事务提交 `artifact_version` 和索引 Outbox。支持对象版本 ID 时固定版本；不支持时用服务端受控流式写入/复制并校验，不能只做一次 HEAD 就相信文件之后不变。
5. 数据库提交失败产生孤立对象，按审计与保留策略清理；不得把不完整上传显示为正式成果。

S3 预签名 URL 是短期 bearer 访问能力，不是应用权限。上传 URL 有效期内可被再次使用，相同 key 可能被覆盖，因此“随机 key + complete 回调”不足以保证正式成果不可变。[AWS 官方说明](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html)

敏感成果优先经鉴权下载代理；若使用短期下载 URL，需明确到期/撤销限制，不把链接当作可立即收回的授权，也不将敏感直链发进招乎群。S3 兼容产品的实际语义必须在内网验证。

### 5.5 检索与记忆

- 权威记忆保存在 MySQL/受控对象内容中；ES 只存可重建片段与来源引用。
- 查询先按当前主体、团队和资源授权过滤；返回片段前再次校验权威授权/删除状态，避免索引延迟造成撤权后泄漏。
- 第一阶段只纳入显式配置知识和人工确认记忆；第二阶段开放自动提炼“候选记忆”，经规则和确认后发布。
- 显式记忆、模型推断、过期信息分开显示；删除保留抑制标记，避免下一轮整理从旧对话再次写回。
- 每次 Run 固定 Context Manifest：来源 ID、版本、授权版本、用途与引用；正式确认内容从成果服务读，不依赖搜索摘要。
- 撤权后拒绝新检索与下载，通知在途任务停止新增使用、清理缓存并审计影响；已向外部显示的信息无法仅靠删除索引追回。

## 六、运行可靠性、安全与人工控制

### 6.1 状态分离

- Task 状态：草稿、进行中、等待业务确认、等待研发确认、已交接、完成、取消；状态迁移受模式定义和人工权限约束。
- Run 状态：排队、等待节点、启动中、执行中、等待人工、请求取消、成功、失败、已取消、结果未知。
- Delivery 状态：待投递、已接收、已送达、失败、结果未知；Run 成功而群通知失败时，只重发回执，不重跑开发。
- 阶段成果变化会使对应审批失效或要求重新确认。已经开始开发后发生范围变更，应创建变更记录及影响分析，不偷偷替换已批准输入。

### 6.2 恢复规则

| 故障/并发情形 | 必须的行为 |
| --- | --- |
| 多个请求重复创建/确认 | 命令去重与版本 CAS；只产生一次阶段迁移和 Run |
| 派发成功但 ACK 丢失 | 相同 Run/Attempt 重试投递或 inspect；Worker 不重复启动 |
| 本地节点离线 | 未开始任务等待节点；在途任务检查租约和实际进程，不直接宣称失败或换节点重跑 |
| 租约失效，旧节点仍执行 | 控制端拒收过期 fence 的写入；Worker 停止新增工具副作用并取消工作；无法确认停止时进入结果未知 |
| 修改代码或调用外部接口后失联 | 记录副作用回执并对账；无可靠幂等/检查点时人工接管，不自动重放 |
| 两个任务写同一工作区 | 独立任务工作区优先；无法隔离时资源级写锁，不只按 Thread 互斥 |
| 审批过期/成员撤权/版本变化 | 恢复前重新校验主体、资源、成果版本和审批；拒绝旧链接继续执行 |
| ES 不可用 | 检索降级或标识延迟；正式成果和任务状态仍从权威存储可读 |
| S3 不可用 | 上传失败或等待，保留可恢复状态；不生成虚假已完成成果 |

### 6.3 三种确认必须分开

1. **业务确认**：这是不是正确的需求范围与验收标准。
2. **技术确认**：评估是否可行、风险是否接受、交接是否完整。
3. **工具授权**：是否允许访问某仓库、写文件、执行命令或调用发布接口。

前两项不能推导第三项，工具执行授权也不能替代业务签字。机器人、Group Leader 或模型自评不能扩大权限。

### 6.4 敏感信息与安全底线

- 发布 Token 改为 `credentialRef`；App 仅通过主进程受控入口操作，Worker 按用途取短效凭据，服务端使用批准的凭据适配器。真实秘密不进入 RunSpec、聊天、Trace 明文和搜索。
- 普通研发资料与“可向业务展示的技术结论”分别授权。业务无源码权限时，不自动借用开发者凭据给其开放源码；可由获准技术伙伴执行，再由责任人确认共享结论。
- 仓库与路径由服务端授权引用解析，本地路径只在相应节点内解析；服务端不保存可任意读取的客户端绝对路径指令。
- 文档、群消息和仓库内容是输入数据，不是提升权限的指令。模式与工具白名单在执行边界强制生效，不能只依赖提示词。
- 交互 HTML 预览与静态标注保持两个隔离模式：前者只允许脚本的 opaque origin，后者禁止脚本但允许父页面读取标注 DOM。不得合并 `allow-scripts` 与 `allow-same-origin`。
- 第一版不共享浏览器登录态或个人凭据给整个 Group。不同 Bot 窗口也不构成租户隔离。
- 伙伴主动工作有任务预算、频率上限、停止按钮、负责人和安静时段。无新进展不刷群；需要确认、失败或有正式成果时通知。

## 七、外网开发环境与迁入内网

### 7.1 外网开发拓扑

新增 `deploy/dev/` 环境描述与 `services/bot-control/` 工程骨架，**这是后续 P0/P1 工作，不是本次已部署内容**。

建议开发环境包含：伙伴服务、MySQL、私有 S3 兼容对象存储、可选 ES、开发身份服务、招乎模拟器；另以两台 App 或两个隔离测试客户端模拟业务与研发，至少一个本地执行节点。使用专用测试仓库、虚构需求材料和假凭据。

若部署到团队外网测试机，只开放经认证的 HTTPS/WSS 入口；MySQL、ES、对象存储管理端口在私有网络内，不直接暴露公网。即使暂用 Docker Compose，也需固定镜像版本/摘要、非默认密码、私有 bucket、资源限额和持久卷。

### 7.2 环境适配点

| 能力 | 外网开发 | 内网接入 |
| --- | --- | --- |
| 身份 | 仅在 dev profile 可启用的固定测试主体/模拟身份提供者 | 企业登录、JWT 验签、主体与招乎身份映射 |
| 招乎 | 按冻结 fixtures 的模拟 webhook、群成员、附件和回执 | 平台正式接口、签名、权限、频率限制、实际错误码 |
| 模型 | 批准的开发模型或确定性假模型 | 内部模型网关；不得把内网资料发往外网模型 |
| MySQL | 与目标版本兼容的批准发行版、同一迁移脚本 | 已有数据库资源、账号、备份与变更流程 |
| S3 | 批准的兼容实现或测试 bucket | 内网 endpoint、证书、签名、加密、版本化与策略 |
| ES | 可暂关闭；开启时使用目标能力子集 | 实际版本、分析器、权限、索引配额 |
| 仓库/发布 | 测试 Git 与模拟发布系统 | 经授权的内部 Git、需求平台与工具连接器 |

内网配置缺失时必须启动失败或明确禁用相关能力，禁止自动回退到模拟身份、外网模型或测试 endpoint。密钥只给部署系统，不提交到仓库。

### 7.3 迁移顺序

先冻结版本与网络边界 → 在外网完成合同测试与断网恢复 → 固定镜像和依赖清单 → 内网部署空库/私有 bucket → 企业身份及只读资料联调 → 两组试点隔离验证 → 再开放受控写代码与发布适配。

只迁移代码、数据库迁移、契约、脱敏 fixtures 和经批准的配置模板，不默认把外网聊天、记忆、凭据、真实仓库镜像整体导入内网。数据库迁移采用增量兼容方式，先扩展再切流，破坏性收缩另行审批；备份必须验证可恢复。

| --- | --- | --- | --- |
| C01 | Group 职责、指定伙伴响应、持久 handoff | B02、R01 | 需求伙伴交接领域专家；重启不丢交接；有轮数和预算上限 |
| M02 | 技术评估适配与仓库上下文授权 | C01、权限与工作区准备 | 只读评估；展示来源和仓库 revision；无权限不读源码 |
| M03 | 接通需求 selection 到设计会话 | M01、B03 | 生成的原型明确引用 PRD 版本；不再只打印 selection |
| M04 | 原型标注、并发修改、版本失效处理 | M03 | 旧版标注不能误改新版；维持 HTML 双模式隔离 |
| M05 | 业务/技术两类确认与 DevelopmentHandoff | M02/M04 | 版本改变使确认失效；确认后可人工发起项目交接 |
| M06 | 项目模式桥接和阶段结果回传 | M05、现有项目/插件契约 | 同一交接重复提交只创建一次；开发结果回到同一 Task |

P2 演示：同一需求经历澄清、评估、原型、返讲、确认，再进入现有项目模式。首期项目状态以已有项目系统为准，伙伴服务保存投影和关联，不与其争夺同一阶段的控制权。

### P3：招乎群、受控记忆与主动跟进（约 2 周）

| ID | 开发项 | 依赖 | 交付与验收 |
| --- | --- | --- | --- |
| I01 | 群协议、附件、身份映射与绑定 | F04、B01、招乎正式契约 | 群管理员与 Group 管理权限均验证；旧单聊 V1 回归通过 |
| I02 | 任务编号路由、澄清选择、回执与审批适配 | I01、M05/M06 | 两任务并行不串线；无回复串也可用；过期审批被拒绝 |
| K01 | 显式知识/记忆、范围与来源 | B03、M02 | 专家有持续背景；私人、任务、团队信息互不越界 |
| K02 | ES 异步索引、ACL 过滤、删除与重建 | K01 | 索引落后不泄露撤权资料；ES 关闭仍可查看任务和正式成果 |
| A01 | Routine、持久触发、提醒与伙伴唤醒 | B02、C01、I02 | 澄清待办提醒和开发结果跟进；相同触发只执行一次逻辑动作 |
| A02 | 候选记忆审阅、修正、删除及抑制回写 | K01/K02 | 用户能解释“记住了什么、来自哪里、谁能看、如何撤销” |

Routine 首批只做“待澄清提醒、明确资料变更后的复核建议、研发验证完成回传”。首期不承诺所有文件系统或外部系统事件自动接入；每种事件源单独定义来源校验、去重和权限。

### P4：内网试点与稳定性验收（约 1–2 周）

| ID | 开发项 | 依赖 | 交付与验收 |
| --- | --- | --- | --- |
| Q01 | 企业身份、正式招乎、S3/MySQL/ES 适配联调 | P1–P3、环境审批 | 不存在 dev fallback；资源最小权限和网络审计通过 |
| Q02 | 故障注入、权限负向测试、备份恢复、容量评测 | Q01 | 执行本节后附验收矩阵；没有未定级的安全阻塞项 |
| Q03 | 试点与产品评估 | Q02 | 建议 1–2 个领域、至少 2 个独立团队，真实需求小样本受控验证 |

预计约 8–9 周形成可评估的内网试点；若按 3 人投入，某些任务可并行，但安全门禁和外部接口联调不能通过并行省略。单人实施应重新估算，不能沿用这一日历时间。

### P5：常驻/云端 Runtime（独立里程碑，约 3–5 周起）

- 抽离 Electron/BrowserWindow、个人登录态和本地路径假设，构建可无 UI 启动的执行 Worker。
- 实现 HostedRuntimeProvider、受控仓库拉取、每任务工作区/沙箱、资源和网络策略、短效凭据、日志与产物回传。
- 明确检查点格式和可恢复版本；先实现同 Provider 恢复，不承诺不同架构/工具版本间任意迁移。
- 加入租户隔离、工作区清理、节点回收、费用/配额、常驻服务调度和运维告警。
- 验收“关闭个人电脑后任务仍执行、等待人工可恢复、异常不重复副作用”；通过后才宣传全天候伙伴。

如果领导把“电脑关机后继续工作”列为首版硬要求，必须将 P5 最小常驻执行能力前移，并相应减少 P3 的自动记忆/主动场景范围；不能只改一个产品文案来兑现。

## 九、代码组织、提交拆分和验收

### 9.1 建议新增目录（尚未创建实现）

```text
contracts/bot/v1/               OpenAPI、Runtime Schema、fixture、兼容说明
contracts/im-group/v2/          群接入契约；不覆盖既有 V1
services/bot-control/           模块化服务端：伙伴/团队、模式、任务、调度及基础设施适配
src/shared/bot/                生成类型与少量桌面适配类型
src/main/services/bot/         API 客户端、同步、DesktopRuntimeProvider、工作区/凭据适配
src/main/ipc/bot.ts            App 到服务端/主进程的窄接口，不承载核心业务状态机
src/renderer/src/components/bot/  伙伴、团队、任务、成果与待确认界面
deploy/dev/                    开发环境、假身份/假招乎、示例配置
tests/bot/                     契约、幂等、隔离、恢复、模式交接与 E2E
```

数据库迁移归服务端工程；知识解析/索引通过后台任务接口执行，耗时解析不阻塞 HTTP 请求。ES、S3、身份、招乎均用适配接口隔离，单元测试使用确定性假实现，集成测试必须覆盖真实兼容资源。

服务端开发者负责 B01–B03、C01 和持久调度；桌面/Runtime 开发者负责 R01、项目模式桥接与节点恢复；工作模式/前端开发者负责 U01、M01/M03/M04 及审阅体验。I01–I02 需网关负责人参与，K01–K02 由服务端与 Runtime 共同交付。每个任务仅设一名交付负责人，接口两侧互相验收；上述分配在 P0 按实际团队调整。

建议每个任务 ID 一个可审阅的小变更：契约及 fixtures → 服务端实现 → Desktop Adapter → UI → 场景 E2E。接口破坏变更需版本升级及迁移说明；不在巨大 `ipc/agent.ts` 里继续堆协作产品逻辑。

分别设置伙伴功能、群接入、Routine 和 Hosted Runtime 的服务端开关，按试点 Group 灰度。回滚时先停止接收新任务和触发，再排空或人工处置在途 Run；不得直接回滚数据库并重放不确定任务。原单聊 V1 与个人工作模式保留独立回退路径。

### 9.2 发布前验收矩阵

| 类别 | 最小验收条件 |
| --- | --- |
| 原有能力回归 | 类型检查、Electron 构建、IM V1、桌面基线、需求/原型、预览隔离全部通过；新增功能关闭时原流程可用 |
| 多人协作 | 两用户同改 PRD 不覆盖；审批绑定准确版本；撤权后不能继续确认/下载/检索 |
| 多伙伴 | 明确分工、交接有回执、重启不丢；互相唤醒达到限额时停止，不无限讨论 |
| 任务路由 | 同群多任务、迟到回复、重复消息、引用失效、无任务编号均不串任务 |
| 执行可靠性 | 断线重连、ACK 丢失、节点重启、租约过期、取消竞态、结果未知处理均有自动用例 |
| 成果一致性 | S3 上传中/超限/替换/损坏/DB 回滚不会形成已确认成果；正式版本不可被重用上传链接改写 |
| 权限与秘密 | 伪造身份/群成员、跨空间 ID、资料提示注入、旧授权恢复都被拒绝；凭据扫描通过 |
| 检索与记忆 | ES 延迟/删除/重建不越权；模型候选与已确认记忆可区分、可纠正 |
| 模式交接 | 输入版本可追溯；需求变更触发重确认；项目模式接收幂等且结果回传 |
| 运维 | 空环境安装、升级回滚、DB/S3 恢复、审计导出、禁用单一伙伴/团队/节点均有操作手册 |

性能门槛先作为测试目标：在 P0 冻结的数据量、机器和并发条件下，普通元数据 API 的 P95 目标不超过 500ms；不含模型生成、附件解析和大文件传输。需要分别记录节点在线时派发延迟、人工等待、模型耗时和投递延迟，不能用一项总耗时掩盖瓶颈。数值在基线压测后调整并留档，不作为未经验证的现有性能声明。

产品指标先采集基线，再比较试点：需求首次有效反馈时间、澄清往返次数、确认后需求变更率、技术评估耗时、交接缺漏率、人工返工率。技术指标包括 Run 成功/未知率、重复副作用、恢复耗时、待确认积压、投递成功率及 Token/执行资源消耗。不能只汇报消息数或 Agent 数量。
