# 用两个插件和不同模型 DIY 一个 Claw

现在还可加入不同插件的 Skill 与 MCP 服务，并作为原生流程步骤执行；当前完整操作与存量插件改造见 [使用与迁移指南](mods-compatibility-impact-and-plugin-migration-2026-09-29.md)，节点说明见 [原生步骤交付](mods-native-step-delivery-2026-09-29.md)。下文的两插件流程示例继续适用。

本说明对应开发目录 `C:\ai\CmbCoworkAgent-mods-v2`、分支 `codex/mods-v2`，不是 UAT。
这次增加的是可执行的跨插件动作组合、对话独立绑定和右侧 Claw 工作台。

## 先理解三个操作

| 操作 | 效果 |
| --- | --- |
| 保存能力组合 | 保存一份模板，不影响已经应用的对话 |
| 应用到当前对话 | 给这个普通本地对话绑定插件、模型、流程副本，不立即执行 |
| 输入框选择“执行流程”并发送目标 | 按已绑定流程执行，并在右侧显示步骤与确认 |

输入框选择“聊天”时，仍然正常聊天；绑定的默认模型和匹配事件的 Hooks 会参与。
命令型能力仍通过 `/命令` 触发。选中一个流程不会自动把聊天切成执行流程。
“带运行摘要追问”会切回聊天，方便解释刚才的结果。

## 1. 安装两个真实插件

本次生成的导入包：

- `output/mods-composition-delivery/autobiz/AutobizDevOps_Plugin_Kanban_Mods.zip`
- `output/mods-composition-delivery/Review_Agent_Mods.zip`

打开应用的“自定义 → Mods”，上传这两个 ZIP，核对源码和权限并授权，开启 Function Mods。
如果已装旧版，同名插件更新后需要重新核对并批准新的源码摘要；旧组合中的摘要不会自动替换。
请使用本开发目录运行 `npm run dev`，避免打开仍未包含本轮修改的旧安装包。

Autobiz 包保留上游 Skills、Python 门禁与 MCP，同时加入 Function Mods。来源固定为
`autobiz_kanban` 的 `8db1ec937d6ed3d271cb9dc540310d6633c91e70`；本次没有拉取并声称它是上游最新版。
Review 是另一个独立安装的插件，不是 Autobiz 内部换了一个显示名称。

## 2. 选择体验项目

先用随包生成的演示项目，避免影响正在开发的业务：

`C:\ai\CmbCoworkAgent-mods-v2\output\mods-composition-delivery\autobiz\demo-project`

在应用中为此目录创建**普通本地对话**。这份项目含合成业务数据：Feature 为 `order-export`，
检视文件为 `src/export-orders.ts`。它用于演示接线，不代表真实业务的 Python 门禁已通过。
交付的这个目录已单独初始化 Git，仅提交合成演示文件，避免把外层工程的修改纳入成果检查。
如果自己重新运行打包脚本生成示例，请把示例作为独立 Git 项目初始化后再体验。

也可以使用自己的 Autobiz 项目，但要换成真实 Feature ID 和真实文件路径。此示例只支持非空、
不超过 4000 字符的单文件，不接受动态 workflow.d 覆盖，遇到这些情况会明确拒绝。

## 3. 拼装两个插件的步骤

进入“自定义 → DIY 流程”，新建流程，名称填“Autobiz 跨插件检视”，所属 Mods 选择 Autobiz。
“所属 Mods”是流程授权来源，后面的动作可以来自其他已授权插件。
删除不需要的默认步骤，只保留或新建下面三步：

| 顺序 | 组件与选项 | 填写内容 |
| --- | --- | --- |
| 1 | 插件动作：Autobiz：准备单文件检视输入 | 动作输入 `{"feature":"order-export","path":"src/export-orders.ts"}`，动作配置 `{}` |
| 2 | 插件动作：独立 Review：检视前一步文件 | 接收前置步骤输出选第 1 步，字段路径留空，动作输入 `{}`，动作配置先用 `{}` |
| 3 | 人工确认 | 提示填“查看单文件检视意见；本例未运行测试，也不推进业务阶段。” |

保存流程。第 1 步读取文件与真实状态，第 2 步接收结构化输出、调用宿主模型并等待结果，
第 3 步请你确认。流程末尾还有宿主最终成果确认，这是结束执行的确认，不等于 Autobiz 阶段推进。

模型设置先配置至少一个可用模型。本例会产生实际模型用量。
若需要第二步用不同模型，在其“动作配置”填 `{"model":"实际模型引用"}`，并在下一步把同一个模型
加入 Claw 的“检视角色”。模型引用可从模型配置取得，不能把示例文字直接照抄，也不要填 API Key。
也可先完成第 4 步，再打开右侧“配置”页，复制角色下面展示的 `custom:…` 或 `builtin:…` 引用，
回到流程编辑器填入 Review 的动作配置，保存后重新选择流程副本并应用。
这里的 `config.model` 是 Review 插件定义的参数；它与 Agent 节点的“Claw 模型角色”是两种入口。

## 4. 保存并应用自己的 Claw

进入“我的 Claw”：

1. 新建组合“我的 Autobiz 研发助手”。
2. 同时勾选 Autobiz 和 review-agent 两个能力来源。
3. 选择“主助手默认模型”。需要不同模型时，给“实现角色”和“检视角色”分别选择 A、B。
4. 在“组合的显式流程”选择刚保存的流程。
5. 点击“保存能力组合”，再点击该组合的“应用到当前对话”。
6. 点击“回到聊天使用”。

应用时会检查流程涉及的插件是否都在组合中、摘要是否仍被授权、模型是否可用。
不能只勾选 Autobiz，却让流程调用未纳入组合的 Review。

这里保存的是流程副本。后来编辑 DIY 流程不会偷偷改变已应用的对话；要采用新版本，请在组合里重新选择
该流程、保存、再应用。其他对话可以绑定不同组合。正在执行任务的当前对话不能切换组合。

## 5. 在同一个输入框真正使用

回到对话后，选择输入框上方的“执行流程”，输入：

> 检视订单导出文件，关注边界情况；保留当前业务阶段，等我确认。

发送后打开右上角“Claw”。右侧工作台提供“运行 / 配置 / 插件与结果”三个标签。
检查第 1 步的输入来源、第 2 步的执行插件和输出，再处理人工确认。关闭侧栏不会取消任务；
需要停止时用明确的取消操作。宽窗口可以拖动侧栏边界调整宽度，窄窗口使用抽屉。

成功的可观察证据是：Autobiz 输出真实路径和状态；Review 的 `output.review` 包含检视内容；
执行记录中的两步提供者不同。回答措辞是否变化不是验证 DIY 成功的标准。

切回“聊天”，再输入“解释刚才的检视结果”就是普通聊天；不会再次跑这条流程。

## 还可以怎样组合

- 在流程前面加一个 Agent 任务，模型角色填 `implementation`，由 Claw 的实现角色模型处理。
- 后面加一个 Agent 任务，模型角色填 `review`，由检视模型处理；显式指定节点模型时优先用节点模型。
- 插入“真实检查”节点执行现有测试门禁，失败时配置有限次数的修复步骤；测试结果不能靠模型说通过。
- 在另一个对话应用另一份组合，比较选择的插件和模型。相同项目的显式流程仍互斥执行，避免同时改同一目录。

## 本轮边界

可组合动作必须由插件明确导出 `claw.actions`；未导出的任意内部函数和 Hooks 不会自动变成节点。
启用一个插件仍会注册其正常 Hooks，选择其中某个动作不代表该插件的其他 Hooks 都被卸载。
参数暂为 JSON 表单，前步输出支持对象和 JSON Pointer；还不是任意表达式或自动类型连线编辑器。
Agent 模型角色已统一绑定；插件动作如何使用模型由该动作的参数契约定义。

Skill、MCP、loop、存储、沙箱尚未全部纳入同一个可替换服务组合。本轮没有把它们画成可选卡片后就宣称已经接通。
传统 Plugin 项目模式和 Harness 继续走原有入口，本轮的 Claw 对话绑定不应用到这些会话。
这份单文件检视示例不运行测试、不修改源码、不提交、不推进 Feature 阶段，不能作为完整研发交付证明。
