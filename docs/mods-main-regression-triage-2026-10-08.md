# 主版本完整回归的失败复核

工作只在开发分支 `codex/mods-v2`。1.5.8 候选保持原样，不覆盖首次失败。

## 已知事实

1.5.8 的上手流程、模型启停链路、旧 Plugin 项目模式及原聊天执行链路均实际通过，
结果各自经过两人复核。这些检查使用本机受控模型服务，不代替客户模型或安装验收。

当前源码的完整 `npm test` 首轮退出 1：1,059 个文件中 1,026 通过、29 失败、4 跳过；
10,516 项测试中 10,404 通过、103 失败、9 跳过，另有 3 个未处理错误。
总耗时约 424 秒，源码摘要前后相同。后续独立测试命令因 `&&` 未执行。

这台机器有 16 个逻辑核，本轮使用默认调度。此前约 40 分钟的全量执行明确限定了单工作进程。
许多新失败直接报 5 秒、15 秒或 30 秒超时，但也出现预算取消、目录占用、
解析守卫异常和运行时释放断言。不能把这些错误都归因于并发，也不能据局部通过称全量通过。

## 复核方法

先对首轮失败的完整文件复查，使用此前的单工作进程设置。
保持原测试源码、全部用例、断言、等待时限、真实外部进程和文件工作量；不按个别用例筛选。
记录首轮与复查的退出码和源码摘要，结果分别保存。

单进程下通过的项目，只能说明其对调度敏感。仍失败的项目需要进一步定位实际行为和资源归属。
目录占用不能靠增加删除重试或等待时间关闭；运行时释放异常也不能仅靠一次复查通过关闭。
如果需要修复生产代码或测试夹具，先形成明确的小方案、双人评审，再实现和回归。

之后再用同样的单进程设置执行完整 `npm test`。即使该轮通过，也不能改写默认调度首败，
更不能冒称本次优化了产品运行性能。完整测试若仍失败，单独执行被短路的存量模块测试并记录。

声音、新服务连接及成本较高的边缘能力保持后移。Git 目录占用目前没有确认原生句柄归属，
不为取得绿色结果而引入尚未完成评审的大型观察器或修改生产 Git 行为。
