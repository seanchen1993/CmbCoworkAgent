## 3. 数据来源与实际字段契约

### 3.1 索引及用途

| 实际索引 | 本期用途 |
| --- | --- |
| `devclaw_project_info` | 项目事实、组织和日期筛选、功能点、累计开发报工、关联特性编号 |
| `devclaw_feature_info` | 仅为项目明细批量补充特性名称，不参与两项新增耗时计算 |
| `devclaw_gitee_push_info` | 组织月度总入库行数及 devagent 三个来源的入库行数 |
| `devclaw_event` | Harness 快照、代码生成和采纳事件 |
| `devclaw_trace` | 现有项目累计 Token 及其他算力指标 |

复用现有 ES 连接、认证和索引配置入口。项目索引沿用 `VITE_ES_INDEX_PROJECT_INFO`；特性、月度索引分别支持 `VITE_ES_INDEX_FEATURE_INFO`、`VITE_ES_INDEX_GITEE_PUSH_INFO`，未配置时使用上表中的实际索引名。不增加字段别名、双读、历史回退或兼容迁移。

### 3.2 项目事实 `devclaw_project_info`

每个企业项目一条当前事实，文档 `_id=prjCode`。

| 字段 | 含义及来源 |
| --- | --- |
| `prjCode` | keyword，企业项目编号；来自 `PUBLIC_PROJECT`，关联前只 trim，不改大小写 |
| `prjName` | text，项目名称 |
| `teamName`、`roomName` | keyword，项目归属团队、室 |
| `groupName`、`prjDeptCode` | 保留项目原始组织信息，不做组维度统计 |
| `status`、`phaseStatus`、`type` | 原有状态、阶段和类型 |
| `createDate` | 项目立项时间 |
| `firstStStartDate`、`firstStEndDate` | 首次 ST 发起、结束时间，分别保留 |
| `firstUatStartDate`、`firstUatEndDate` | 首次 UAT 发起、结束时间，分别保留 |
| `firstOnlineDate` | 首次上线时间，上线判断及吞吐率过滤依据 |
| `endDate` | 原有项目结项时间，不作为本期默认日期口径 |
| `approvedDate` | 项目关联特性中最早的有效审批日期，由 Java 按项目归并取最小值 |
| `featureCodes` | keyword 数组，项目关联产品特性编号；trim、去重，关系只在这里保存 |
| `devWorkHours` | 非负数，累计开发报工小时；取 `PUBLIC_PROJECT.devCenterWorkhour` |
| `notAdjustFuns` | scaled_float，功能点；沿用原功能点接口，不使用 `evaluateFp` 替代 |
| `bugNum` | long，缺陷数；现有上游 null 按 0 写入的规则保留 |
| `kenanIssueCount` | long，非功能问题总数，保留现有口径 |
| `kenanIssueCategoryCount` | nested，`category/count`；保留类别统计及明细 |
| `pm` | 来自 `PUBLIC_PROJECT.pm`，本期不做个人指标 |
| `syncBatchNo`、`syncedAt` | 同步批次、时间，说明数据新鲜度，不作为业务筛选日期 |

项目固定保留 `createDate >= 2026-06-01 00:00:00` 的全部数据，不按近六个月滚动删除。统计及关联只覆盖已保存项目，不自动扩大到保留起点以前，也不宣称完整历史。

报工只取开发报工，不使用 `workhour`、`planWorkhour` 或 `testCenterWorkhour` 替代。缺失为 null，明确的 0 保留真实零；不把缺失一概转换为 0。一个字段缺失只影响依赖该字段的指标，不移除项目总数和其他有效指标。

提供过的项目 mapping 为 `dynamic:false`，最新样例 `_source` 已包含新增字段。客户端通过只读 field_caps 检查 `featureCodes` 为可查询的 keyword、`devWorkHours` 为可查询的数值，缺少 mapping 时明确报错，不能把 `_source` 存在当作已可查询、聚合的证明；客户端不自动修改 mapping。

### 3.3 特性事实 `devclaw_feature_info`

产品特性是产品部门提出的完整需求，与 Harness Board 的本地特性区分。项目与产品特性是多对多关系，多数实际关系为一对一。

| 字段 | 含义 |
| --- | --- |
| `featureCode` | 企业特性编号，每特性一条，文档 ID 使用该编号 |
| `featureName` | 特性名称，明细直接展示 |
| `approvedDate` | 该特性自己的审批日期 |
| `syncBatchNo`、`syncedAt` | 同步元数据 |

关系接口 `PUBLIC_FEATURE_PROJECT_RELATION` 以 `featureCode + prjCode` 为业务主键。同一特性在不同关系记录中的审批日期由上游保证一致。项目中的 `approvedDate` 继续取所有关联特性的最早有效日期。

两项新增耗时按项目计算，不读取特性索引的审批日期，不按特性去重或跨项目取最早、最晚时间。此索引本期仅用于按当前页去重特性编号批量补充名称。

不复制项目日期、报工、组织或 `prjCodes/projectCodes` 反向列表到特性文档。关联关系只保存一份，通过项目索引的 `featureCodes` 可批量反查项目。名称读取失败仍显示编号，并说明名称暂不可用，不影响指标。

### 3.4 月度事实 `devclaw_gitee_push_info`

以下是内网实际索引和 mapping，客户端按此读取：

| 字段 | 实际类型 | 含义 |
| --- | --- | --- |
| `timeRange` | keyword | 自然月，例如 `2026-10` |
| `orgLevel` | keyword | `team` 或 `room` |
| `teamName`、`roomName` | keyword | 团队、室；团队记录可缺少 roomName |
| `totalPushedLines` | long | 组织当月全部入库行数，共同分母 |
| `devagentIdePushedLines` | long | devagent IDE 入库行数 |
| `devagentCloudPushedLines` | long | devagent-cloud 入库行数 |
| `devagentCliPushedLines` | long | devagent-cli 入库行数 |
| `updatedBy` | keyword | 维护人 |
| `updatedAt` | date | 格式 `yyyy-MM-dd HH:mm:ss||epoch_millis` |

实际月度 mapping 为 `dynamic:true`。`es_index_time` 等附加字段不参与指标。每组织每月一条，不按来源拆文档。

Java 月度接口按组织接收 `metrics`，允许键 `total`、`devagent`、`devagent-cloud`、`devagent-cli`，分别映射到四个行数字段。总量和来源可分开填报，未提交保留原值，明确提交 0 才表示零；`metrics.devagent` 对应 `devagentIdePushedLines`。APP 不参与填报，DevClaw 行数不人工维护。

全部室时使用团队记录，条件为：

```json
{
  "bool": {
    "filter": [
      { "term": { "orgLevel": "team" } },
      { "term": { "teamName": "零售客户经营开发团队" } },
      { "term": { "timeRange": "2026-10" } }
    ]
  }
}
```

具体室使用 `orgLevel=room`、相同 `teamName`、所选 `roomName` 和月份。不使用 `orgLvl`、`groupName` 代替实际字段。

## 4. 统一智能化分类

### 4.1 项目

研发效能所有智能化／CMBDevClaw 项目判定使用同一规则。从事件索引读取 `eventName=harness.project.snapshot`，要求：

```text
properties.projectFromLean = true
properties.projectCode 非空
properties.projectId 非空
properties.isTestProject 不为 true
properties.manuallyMarkedTestProject 不为 true
```

任一测试标记为 true 都排除。复用项目运营概览中已有测试项目范围解析，按 Harness 项目 ID 排除快照、代码、trace，不仅检查可能不带标记的历史事件。

构建完整映射：

```text
Set<企业项目编号> devclawPrjCodes
Map<企业项目编号, Harness项目编号集合> eligibleHarnessIdsByPrjCode
Map<企业项目编号, 插件信息集合> eligiblePluginsByPrjCode
```

快照 `properties.projectId` 是 Harness 项目编号，`properties.projectCode` 与事实 `prjCode` 关联。任一有效 Harness 项目命中即可判为智能化；样本中其余企业项目为常规项目。

同一企业项目有测试与正常 Harness 项目时，只使用正常关联分类和汇总代码、Token。排除的是测试 Harness 项目，不自动删除企业项目事实；仅有关联测试 Harness 项目的企业项目不会被判为智能化。

分类映射不按页面周期、当前所选室提前裁剪，避免跨室、跨周期误分类。映射只留主进程；权限仍限制可返回的事实，不向渲染层暴露其他室明细或全量编号集合。

### 4.2 特性

先按组织、项目周期取得样本项目，收集 `featureCodes` 去重，得到候选特性。再批量反查候选特性全部已保存关联项目：任一项目智能化，该候选特性即智能化，否则为非智能化。

- 周期和组织决定候选集合，不能统计完全未关联周期样本项目的特性。
- 分类可以受其他室、周期外已保存关联项目影响，但它们不能凭空增加候选特性。
- 不要求全部关联项目上线，不依赖特性状态。
- 团队特性数量必须重新去重，不能相加各室结果。

Tips：特性根据全部已保存关联项目统一判定。只要任一关联项目智能化，该特性即为智能化；本室项目未使用 DevClaw，也可能因其他室关联项目使用 DevClaw而计入智能化特性。

## 5. 组织、时间和筛选范围

### 5.1 组织

当前团队为“零售客户经营开发团队”，支持多选室、全部室，不支持组。

| 数据 | 团队／室归属字段 |
| --- | --- |
| 项目指标 | 项目 `teamName`、`roomName` |
| DevClaw 代码指标 | 事件 `upperOrgLv2`、`upperOrgLv1`，沿用运营面板逻辑 |
| 月度代码指标 | 月度 `teamName`、`roomName`，以及 `orgLevel` |

全部室表示整个团队，不等同于对任意团队取消过滤。多选室在该团队内取并集，并与权限取交集。项目所属室和代码上报人所属室是不同归属，不擅自把代码组织改为项目所属室。

### 5.2 开发完成与项目日期选项

```text
developmentCompletedAt = firstStStartDate
                         缺失时取 firstUatStartDate
```

有 ST 就取 ST，不比较早晚；两者都缺失时为空。此日期同时用于周期筛选和审批到开发完成耗时，不使用流程结束时间。

| 展示名称 | 条件 |
| --- | --- |
| 开发完成，默认 | developmentCompletedAt 落入所选周期 |
| 立项时间 | createDate 落入所选周期 |

开发完成过滤为两支 OR：ST 发起命中；或 ST 发起不存在且 UAT 发起命中。ST 存在但在范围外时，不能让范围内 UAT 分支命中。

沿用 Dashboard 的传入时间参数，主进程转 GMT+8 边界。项目日期为首日零点到末日次日零点，左闭右开；2026-10-01 至 2026-10-31 对应 `[2026-10-01 00:00:00, 2026-11-01 00:00:00)`。不扩大修改其他面板的时间传输格式。

### 5.3 每项指标的时间范围

| 指标 | 时间选样本 | 受项目日期选项影响 |
| --- | --- | --- |
| 应用研发智能化特性占比 | 周期内立项／开发完成项目关联的候选特性 | 是 |
| 月人均产出功能点 | 周期内立项／开发完成项目 | 是 |
| 特性审批完成到开发完成耗时 | 周期内立项／开发完成项目 | 是 |
| 特性审批完成到立项完成耗时 | 周期内立项／开发完成项目 | 是 |

### 5.4 其他现有筛选

| 筛选 | 作用范围 |
| --- | --- |
| 项目阶段、功能点区间 | 项目对比、相关趋势及明细；吞吐率仍按上线日期 |
| 插件、累计 Token 区间 | 项目对比、相关趋势及明细，只收窄智能化一侧 |
| 开发方式、项目编号／名称搜索、分页、排序 | 仅明细，不改变总体 |
| 当前室多选 | 页面适用指标；导出组织范围另按第 11 节 |

顶部特性占比按组织、周期计算，不受下方项目高级筛选影响。两个 AI 代码指标不受项目阶段、功能点、插件、累计 Token 等项目条件影响。界面明确作用范围，不传组筛选。

插件复用项目运营概览：有效快照按插件名去重，任一有效 Harness 项目匹配即可命中企业项目；命中后累计代码、Token 使用该企业项目全部有效 Harness 关联。常规侧不受插件、Token 条件影响，显示样本不对称 Tips。明细选择常规时清空并禁用这两个筛选，主进程也拒绝语义矛盾组合。

## 6. 指标计算与有效样本

### 6.1 应用研发智能化特性占比

```text
特性总数 = 候选featureCode集合大小
智能化特性数 = 候选中智能化特性的数量
占比 = 智能化特性数 / 特性总数
```

总数为 0 时比例 null，计数可显示真实 0。概览同时显示占比和“智能化特性数／特性总数”，不使用关系记录条数。

### 6.2 AI 代码入库占比

```text
devagent IDE 占比 = devagentIdePushedLines / totalPushedLines
devagent-cloud 占比 = devagentCloudPushedLines / totalPushedLines
devagent-cli 占比 = devagentCliPushedLines / totalPushedLines
DevClaw 占比 = pushedAdoptedLines / totalPushedLines
累计占比 = 四渠道入库行数之和 / totalPushedLines
```

DevClaw 分子直接复用运营面板“入库采纳率”的 `pushedAdoptedLines`，限定精益、非测试范围，沿用事件字段完整性检查、组织和周期条件。

当前采纳查询按 `properties.generatedAt` 过滤周期，再要求 `properties.pushed=true`，汇总 `properties.adoptedLineCount`。不要额外按 `pushedAt` 重算，不叠加项目立项、开发完成、上线时间。

仅统计范围覆盖完整自然月时显示，例如 2026-10。本月从月初至当前时间的范围暂不支持；近 30 天或其他非自然月范围隐藏，不请求该指标，不另设月份选择器。

组织汇总：

- 全部室直接使用团队月度记录，不相加所有室，不混入室记录。
- 单室用该室记录；多室汇总所选室分子、分母后相除，不平均百分比。
- 所选任一室缺少总量或该来源数据时，该来源组合结果 null，不只算已有室后标为完整结果。
- 分母为 0 时 null；明确来源 0 可产生有效 0%，缺失不能补零。
- 累计将四渠道入库行数直接相加，再除以同一组织总入库行数；任一渠道缺失时，累计行数及比例为 null，不显示部分渠道合计。

本期不处理行数定义对齐、跨来源重叠和重复 Push 修正，不归一化四来源总和。使用独立条形，不画合计 100% 的堆叠图。

### 6.3 AI代码入库率

```text
AI代码入库率 = pushedAdoptionRate
             = pushedAdoptedLines / pushedEffectiveGeneratedLines
```

复用正式标为“入库采纳率”的现有计算，限定精益且排除两个测试标记。不是 `inclusivePushedAdoptionRate`（总量入库采纳率），不使用月度组织总行数作分母。

可使用任意受支持时间范围。组织和事件周期与第 6.2 节 DevClaw 分子相同。复用公式与查询，不直接取未施加精益、非测试过滤的页面结果。分母为 0 则 null。

### 6.4 月人均产出功能点

```text
某组开发人月 = SUM(有效项目devWorkHours) / 152.25
某组指标 = SUM(同批有效项目notAdjustFuns) / 某组开发人月
```

项目按 `prjCode` 去重，智能化／常规分别计算。按所选组织、项目日期和周期选样本，不额外要求上线。功能点与工时均为有效非负数，分子、分母同一批样本；缺失不补零。真实零值保留，组内总工时为 0 时结果 null。不先计算每个项目比值再平均。

Tips：统计所选项目的累计功能点与累计开发投入，1 人月＝7 小时×21.75 天＝152.25 小时，不表示周期内实际发生的报工产出。

### 6.5 月人均特性吞吐率

```text
样本 = 所选组织内 firstOnlineDate 落入周期的项目
某组特性数 = 本组有效样本项目关联featureCode去重数量
某组开发人月 = SUM(本组有效样本项目devWorkHours) / 152.25
某组指标 = 某组特性数 / 某组开发人月
```

- 独立按首次上线时间选样本，不叠加立项／开发完成条件。
- 项目按编号去重、智能化／常规分组；报工每项目只加一次，不因多个特性重复累加，不分摊工时。
- 不要求特性全部关联项目都上线，不依据特性状态。
- 分子分母使用同批关联完整且报工有效的样本；未知报工不视为 0，总工时为 0 则 null。
- 同一特性可以进入两组，项目报工不跨组重复；两组特性数不能相加为总体，需再次去重。

Tips：本指标按项目首次上线时间筛选，与所选立项／开发完成口径不同。特性在组内去重，项目累计开发报工每个项目只加一次，按 152.25 小时折算人月，不分摊报工。

### 6.6 特性审批完成到开发完成耗时

```text
项目耗时 = workdays(项目approvedDate, developmentCompletedAt)
某组指标 = AVG(本组有效项目耗时)
```

项目是统计单位，智能化／常规分别计算。`approvedDate` 是该项目关联特性最早审批日期。多特性项目只计算一次，同一特性关联多个项目时各项目分别计算，不跨项目取最早或最晚。

按所选项目日期口径选样本；有效起止日期且终点不早于起点才能参与均值，不要求上线。

### 6.7 特性审批完成到立项完成耗时

```text
项目耗时 = workdays(项目approvedDate, createDate)
某组指标 = AVG(本组有效项目耗时)
```

样本、审批最小值、项目去重、分组及有效日期与上一项相同。正式名称虽然含“特性”，统计单位仍为项目，不按特性编号统计等待时间。

### 6.8 已有指标

| 指标 | 公式／有效样本 |
| --- | --- |
| 平均缺陷数 | 有效项目 AVG(bugNum) |
| 平均非功能问题数 | 沿用 kenanIssueCount 均值及现有类别统计 |
| 平均功能点 | 有功能点结算值的项目均值 |
| 平均缺陷密度 | 同批有效项目 SUM(bugNum)×100/SUM(notAdjustFuns)，功能点大于 0，不平均项目密度 |
| 平均发起 ST 耗时 | AVG(workdays(createDate, firstStStartDate)) |
| 平均发起 UAT 耗时 | AVG(workdays(createDate, firstUatStartDate)) |
| 平均特性上线耗时 | AVG(workdays(项目approvedDate, firstOnlineDate))，仍为项目级 |
| 平均代码行数 | 命中智能化项目累计已 Push 采纳行数总和／命中项目数；无采纳行项目按 0 |
| 平均输入／输出 Token | 命中智能化项目累计 Token 总和／命中项目数；无 trace 项目按 0 |
| 平均单行代码消耗 Token | 同批有正采纳行数的项目，分别 SUM(输入/输出Token)/SUM(采纳行)，不平均项目比值 |

如沿用千行代码缺陷率字段，口径为同批有效项目 `SUM(bugNum)×1000/SUM(pushedAdoptedLines)`；缺陷及采纳行均有效且采纳行大于 0，常规项目无遥测关联时 null。不据此额外增加未确认的新指标行。

每项指标返回有效样本数。字段缺失只退出依赖它的指标，不退出其他有效指标或项目总数。

## 7. 工作日计算

全部已有、新增耗时及其趋势、明细、排序、导出使用同一函数，不能混用自然日。

```text
workdays(start,end)
= [start,end)在各工作日日历日内覆盖的毫秒数之和 / 86400000
```

- 按 GMT+8 切分日期。普通周一至周五工作、周末休息，再应用国务院年度放假和调休上班例外。
- 内置 2026、2027 年，运行时不联网，不调用内网节假日 API。
- 保留小数，计算不提前舍入，显示统一格式化。同工作日 09:00～16:00 为 7/24≈0.2917 工作日，不按 7 小时折算一天。
- start=end 为有效 0；日期缺失、非法或倒置为 null。
- 区间涉及未配置年份时不回退自然日，说明日历覆盖不足。
- 不修改原始日期，不给累计报工重复扣节假日；7 小时只用于人月换算。

官方来源：[2026 年通知政府转载页](https://www.beijing.gov.cn/zhengce/zhengcefagui/202511/t20251104_4258873.html)、[2027 年通知人社部网站转载页](https://chinajob.mohrss.gov.cn/h5/c/2026-11-09/635850.shtml)。放假及调休上班日期都要整理进内置数据，覆盖周末、补班和跨年测试。

## 8. 查询与完整性

### 8.1 批量查询路径

1. 校验权限、参数，确定团队／室及 GMT+8 边界。
2. 完整获取精益非测试快照映射，同一请求复用测试排除范围和分类结果。
3. 取得必要项目轻量字段，区分普通日期样本、上线日期吞吐率样本。
4. 特性覆盖先取得周期候选编号，再批量反查全部已保存关联项目，精确去重分类。
5. 汇总项目指标、工作日耗时；现有代码和 Token 在 ES 聚合后按企业项目合并。
6. 明细返回当前页，特性名称按页批量补齐，不逐项目、逐特性发请求。
7. 自然月查询月度记录，复用代码统计分子；非自然月不请求月度占比。

主进程完成查询和计算，渲染层不直接访问 ES。使用 Set/Map 归并，不把项目—特性展开结果直接用于报工求和。

### 8.2 不允许截断后统计

- 不允许用 10,000 条截断快照或候选项目继续分类、总体、趋势、导出。
- 复用完整分页方式，按能力使用 composite/search_after，terms 批量及分桶遵守 ES、请求体和响应大小限制。
- 超时、分片失败、分页未完成必须报告，不把部分结果当完整成功，不以“可能误分类”提示代替正确统计。
- 代码事件和 trace 使用 ES 聚合，不拉取全部事件明细；完整取回项目聚合结果。
- 轻量事实可为统计、工作日排序或派生筛选完整分页读取，前端明细只接收当前页。
- 特性数量精确去重，不依赖近似 cardinality。团队不能相加各室特性数、比例或均值。

### 8.3 项目累计遥测与顶部代码指标分开

项目对比、明细的代码和 Token 使用所选企业项目的当前累计值：

- 关联该企业项目全部有效 Harness 项目。
- code_adopt 要求采纳计数字段完整、pushed=true，按 properties.harnessProjectId 聚合。
- trace 按 harnessProjectId 汇总输入、输出 Token。
- 不加生成事件时间、trace startedAt，不额外加上报人的室；项目归属已在事实样本筛选。
- 查询成功但某智能化项目无事件为 0；整体查询失败为不可用，常规项目无关联为 null。

顶部两个 AI 代码指标按事件组织和生成时间，不复用这条无时间过滤的累计查询。

### 8.4 缓存、排序与失败

快照可复用现有短时缓存，但需区分测试排除范围，避免被标记测试后仍长时间参与统计。复用已有刷新、取消机制，不引入新的锁或排队。

各区域独立 loading/error。月度失败不遮项目对比，名称失败不影响数字，代码失败不伪装全为常规或零。旧请求不能覆盖新筛选；展示旧值时标明更新／失败状态。

明细保持 20/50/100 分页、表头排序、默认上线耗时倒序和项目编号稳定次序。工作日排序使用同一算法；应用层排序、累计 Token 派生筛选需要完整候选集合后分页，不只排序当前页，不截断。null 始终排末尾。

沿用查询名、目标索引和 DSL 日志，不新增整批事实文档或凭据日志。通过真实数据验证耗时、内存、项目及关系数量后再评估物化，不声称已有数据证明固定性能目标。

组织固定全团队和各室，不跟随当前只选了哪些室。时间、项目日期及适用高级筛选沿用页面；吞吐率和代码仍按各自时间条件。

团队固定“零售客户经营开发团队”。各室从该团队项目事实 roomName、月度室记录及现有组织选项补齐，不仅依赖 trace 活跃室，避免漏掉没有 DevClaw 使用的室。

遵守权限：无全团队读取权限明确说明，不扩大权限或把本室伪装团队。必需查询失败不提示完整导出成功；正常指标缺失保留说明。

### 11.2 两个Sheet

第一Sheet名称：`团队指标`。

| 室名称 | 指标 | 智能化项目 | 常规项目 | 总体 | 单位 | 时间口径 | 口径说明 |

- 对比指标填智能化／常规两列，特性占比、代码入库率及四来源占比填总体。

- 数字与单位分列，百分比按0～100数值输出，单位`%`，例如22.47；不把`22.47%`当作文本数值。耗时单位工作日，产出单位功能点／人月、特性／人月。

### 11.3 汇总要求

团队和每个室分别用完整样本计算：团队特性重新去重；比例汇总原始分子分母；平均耗时按有效项目而非各室均值平均；团队月度用team记录，各室用room记录，不混合层级。

同次导出复用分类、轻量事实和聚合，避免每单元格单独请求。开始导出时固定参数，页面随后修改筛选不能把不同周期混入同一文件。
