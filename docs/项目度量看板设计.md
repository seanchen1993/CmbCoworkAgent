# 项目度量看板设计

## 1. 阅读说明与交付边界

本文档分为两个可以独立开发、独立验收的部分：

| 部分                       | 开发环境         | 责任                                                          |
| -------------------------- | ---------------- | ------------------------------------------------------------- |
| 第一部分：项目事实索引建设 | 企业内网         | 调用三个外部批量接口、按项目聚合补全、创建并写入项目事实索引  |
| 第二部分：DevClaw 看板开发 | DevClaw 代码环境 | 只读项目事实索引和现有 event 索引，计算指标并实现研发效能页面 |

两个部分之间只通过 ES 索引 `devclaw_project_info` 的字段契约衔接：

```text
企业内网 Java 服务 ──写入──▶ devclaw_project_info ◀──只读── DevClaw
```

DevClaw 侧不需要知道企业内网接口地址、鉴权方式或分页实现，也不修改项目事实数据。企业内网写入程序不查询 `devclaw_event`，不负责判断项目是否由 DevClaw 开发。

### 1.1 共同指标定义

| 指标     | 项目级口径                                     | DevClaw/非 DevClaw 总体口径                         |
| -------- | ---------------------------------------------- | --------------------------------------------------- |
| 缺陷数   | 项目有效缺陷数量                               | `AVG(项目缺陷数)`                                   |
| 功能点   | 项目功能点                                     | `AVG(项目功能点)`                                   |
| 缺陷密度 | `缺陷数 × 100 ÷ 功能点`                        | 有效项目的 `SUM(缺陷数) × 100 ÷ SUM(功能点)`        |
| 缺陷率   | `缺陷数 × 1000 ÷ DevClaw 累计已 Push 采纳行数` | DevClaw：有效项目汇总后计算；非 DevClaw：暂不可统计 |
| 提测时间 | `ST 测试开始时间 - 立项时间`                   | 有效项目的项目级时间差均值                          |
| 交付天数 | `首次上线时间 - 特性审批通过时间`              | 有效项目的项目级时间差均值                          |

### 1.2 共同设计约束

- 项目事实索引只保存原始项目事实和同步元数据。
- 不保存 `is_devclaw`、`projectFromLean` 或 `harnessProjectId`。
- 不保存 `defectDensityPer100Fp`、`testLeadDays`、`deliveryDays` 等确定性派生指标。
- 不保存 DevClaw 已 Push 采纳行数或 Token。
- 一个外部项目在事实索引中只有一条当前事实文档。
- 通常 `null` 表示数据未知或未采集，0 表示已采集且值确实为 0；`bugNum` 是已确认的例外，上游接口返回 `null` 时按 0 写入。

## 第一部分：企业内网——项目事实索引建设

### 2. 内网部分目标

企业内网开发一个独立 Java 批处理程序，负责：

1. 完整分页拉取特性基本信息，建立本批次权威项目集合。
2. 完整分页拉取特性实施情况和项目功能点信息，在内存中按项目编号补全事实。
3. 校验三个数据源的分页完整性、关联质量和字段质量。
4. 将完整项目事实按批次写入 ES 索引 `devclaw_project_info`。

内网程序不负责：

- 查询 `devclaw_event` 或 `devclaw_trace`。
- 判断项目是否为 DevClaw 项目。
- 计算并存储缺陷密度、缺陷率、提测天数和交付天数。
- 提供 DevClaw 看板查询接口。

### 3. 上游接口与字段契约

#### 3.1 特性基本信息（主接口）

```text
POST {base_url}/LV01.41/APP_N01/PUBLIC_PROJECT/V1
请求：{ "page": 1 }
单页上限：500
```

该接口的完整结果是事实索引的主表和权威项目集合。只有主接口中存在的 `prjCode` 才写入事实索引。

| 字段               | 含义                  | 写入规则                               |
| ------------------ | --------------------- | -------------------------------------- |
| `prjCode`          | 项目稳定唯一编号      | 必填，作为 ES `_id`                    |
| `prjName`          | 项目名称              | 原值写入                               |
| `status`           | 项目状态              | 原值写入                               |
| `phaseStatus`      | 阶段状态              | 原值写入                               |
| `type`             | 项目类型              | 原值写入                               |
| `createDate`       | 立项时间              | 原值解析为 GMT+8 日期时间              |
| `firstOnlineDate`  | 首次实施/首次上线时间 | 原值解析为 GMT+8 日期时间              |
| `bugNum`           | 项目缺陷数量          | `null` 按 0 写入，非空值必须大于等于 0 |
| `centerName`       | 中心                  | 原值写入                               |
| `teamName`         | 团队                  | 原值写入                               |
| `roomName`         | 室                    | 原值写入                               |
| `groupName`        | 组                    | 原值写入                               |
| `prjDeptCode`      | 项目部门编号          | 按标识符字符串写入                     |
| `firstStStartDate` | 首次 ST 开始时间      | 原值解析为 GMT+8 日期时间              |
| `firstStEndDate`   | 首次 ST 结束时间      | 原值解析为 GMT+8 日期时间              |

`page`、`rowNum`、`num`、`totalNum` 等分页元数据不进入项目事实文档。
补充：分页拉取全量数据，但是仅保留createDate 距离当前日期 6 个月以内的数据写入 MAP和 es index。

#### 3.2 特性实施情况（补充接口）

```text
POST {base_url}/LV01.41/APP_N01/PUBLIC_FEATURE_PROJECT_RELATION/V1
请求：{ "start": "2026-01-01", "end": "2026-08-31", "page": 1 }
```

| 字段           | 含义             | 写入规则                                |
| -------------- | ---------------- | --------------------------------------- |
| `prjCode`      | 项目编号         | 只补全主项目 Map 中已存在的项目         |
| `approvedDate` | 特性审批通过时间 | 与项目一对一，原值解析为 GMT+8 日期时间 |

同步程序应使用覆盖全部主项目的时间范围分页拉取；当单次范围过大时，可以按月拆分时间窗口，但所有窗口仍属于同一个同步批次。若同一批次返回同一 `prjCode` 多条不同的 `approvedDate`，任意选一条。

#### 3.3 项目功能点信息（补充接口）

```text
POST {baseUrl}/dashboard/source-knot
请求：{ "pageNum": 1, "pageSize": 500 }
```

| 字段            | 含义       | 写入规则                                 |
| --------------- | ---------- | ---------------------------------------- |
| `projectNo`     | 项目编号   | 关联时映射到主接口 `prjCode`，不单独写入 |
| `notAdjustFuns` | 目标功能点 | 写入同名事实字段，允许为 `null`          |

#### 3.4 项目编号规范

主接口 `prjCode`、实施接口 `prjCode`、功能点接口 `projectNo` 和 DevClaw snapshot 的 `properties.projectCode` 必须表示同一业务编号。所有接口值进入关联逻辑前统一执行 `trim`；不做其他处理

### 5. 全量聚合与批量写入

#### 5.1 推荐批次流程

```text
申请单实例同步锁并生成 syncBatchNo
                  │
                  ▼
完整分页拉取主接口
写入 Map<prjCode, ProjectFactBuilder>
                  │
                  ▼
完整分页拉取实施接口
只更新 Map 中已有项目的 approvedDate
                  │
                  ▼
完整分页拉取功能点接口
只更新 Map 中已有项目的 notAdjustFuns
                  │
                  ▼
三个接口完整性和关联质量校验
                  │
                  ▼
遍历 Map，每 500 条执行一次 Bulk index
                  │
                  ▼
全部写入成功后清理非当前批次的旧项目文档
```

执行步骤：

2. 使用 GMT+8 的 `yyyyMMdd-HHmmss` 生成本批次 `syncBatchNo`，初始化 `new HashMap<>(32768)`。
3. 顺序拉取主接口全部分页。每页校验成功后立即写入 Map，同一页的原始响应不再保留；`bugNum=null` 转换为 0。
4. 主接口完整成功后，顺序拉取实施接口全部分页。用 `prjCode` 更新同一个 Map；不在 Map 中的编号只记录孤儿数据告警，不创建项目。
5. 实施接口完整成功后，顺序拉取功能点接口全部分页。用 `projectNo` 更新 Map 中对应项目的 `notAdjustFuns`；不在 Map 中的编号同样只告警。
6. 三个接口全部完成且总数、页数和字段校验通过后，遍历 Map 构造完整 ES 文档。
7. 每构造 500 条即执行一次 Bulk `index`，发送后清空批次 List；不创建另一个包含 20,000 条文档或 JSON 字符串的完整 List。
8. Bulk 部分失败时只重试失败文档。`_id=prjCode` 且每次写入完整最终文档，因此重试幂等，并能清除上一批次遗留的补充字段。
9. 全部项目写入成功后，删除 `syncBatchNo` 不等于当前批次的旧文档。任一 Bulk 最终失败时禁止执行旧文档清理。

三个接口不需要让同一页的项目编号彼此对应。关联发生在完整主项目 Map 上：主接口先定义项目集合，后两个接口无论分页顺序如何，都按项目编号更新对应 Builder。

#### 5.2 20,000 个项目的容量设计

当前预计约 20,000 个项目，主接口每页最多 500 条，约 40 页；ES 每批 500 条，也约 40 个 Bulk 请求。该规模继续采用单 Map 内存聚合，不引入暂存表或暂存索引。

内存中只长期保留：

```text
Map<String, ProjectFactBuilder> projectMap
```

不保留三个接口的完整原始 List，也不保留完整 Bulk 请求 List。按每个 Builder 约 2～10 KB 的保守估算，20,000 个项目约占 40～200 MB；Java 堆 512 MB 通常可运行，建议配置 1 GB 并以压测结果为准。

Bulk 参数建议：

| 参数           | 建议值                               |
| -------------- | ------------------------------------ |
| 单批文档数     | 默认 500，可在 500～1,000 之间压测   |
| 单个请求体     | 不超过约 5～10 MB                    |
| 并发 Bulk 请求 | 1～2                                 |
| Bulk 失败重试  | 仅重试失败项，指数退避并设置最大次数 |

主要耗时预计来自外部接口分页和 ES Bulk 网络往返，而不是 Map 查找。只有项目增长到几十万以上、单项目文档明显变大、可用堆低于约 256 MB，或必须并发运行多个全量任务时，再评估暂存表、暂存索引或磁盘 KV。

#### 5.3 为什么不按接口分页直接更新 ES

分页直接更新会让同一项目被主信息、审批时间、功能点分别写入多次，并带来以下维护成本：

- 需要区分“补充接口尚未拉取”和“本批次字段确实为空”。
- 补充字段从有值变为空时，局部 `_update` 容易保留上一批次旧值。
- 外部分页失败后，索引会长期保留难以识别的部分状态。
- 写入次数和失败恢复状态明显增加。

因此本期固定采用“全部拉取到单 Map、校验完成、完整文档分批覆盖”的方式。这里的“全部拉取”是保存 20,000 个项目 Builder，不是保存所有分页响应。

#### 5.4 批次完整性

开始 Bulk 写入前必须确认：

- 三个接口的所有分页均获取成功。
- 每个接口实际拉取数量与其 `total`、`totalNum` 或分页对象中的 `total` 一致。
- 项目编号已按约定完成 `trim` 和大小写规范化。
- 主接口不存在空 `prjCode` 或同编号冲突记录。
- 不存在负数 `bugNum` 或 `notAdjustFuns`。
- 后两个接口中的未知项目编号已记录数量和样例告警。
- 实施接口不存在同一项目多个不同 `approvedDate`。
- 当前批次号晚于已成功写入的批次，避免旧批次覆盖新数据。

任一源数据检查失败时，整批不写入。写入阶段开始后若部分 Bulk 失败，可接受查询短暂读到新旧批次混合数据，但必须保留失败项并重试；所有 Bulk 成功前不得清理旧项目。

#### 5.5 实现骨架

```java
Map<String, ProjectFactBuilder> projectMap = new HashMap<>(32768);

fetchAllProjectPages(page -> {
    for (ProjectRecord item : page.getData()) {
        String prjCode = normalize(item.getPrjCode());
        projectMap.put(prjCode, ProjectFactBuilder.fromMain(item, syncBatchNo));
    }
});

fetchAllRelationPages(page -> {
    for (FeatureRelation item : page.getData()) {
        ProjectFactBuilder fact = projectMap.get(normalize(item.getPrjCode()));
        if (fact != null) fact.setApprovedDate(item.getApprovedDate());
    }
});

fetchAllFunctionPointPages(page -> {
    for (FunctionPoint item : page.getData()) {
        ProjectFactBuilder fact = projectMap.get(normalize(item.getProjectNo()));
        if (fact != null) fact.setNotAdjustFuns(item.getNotAdjustFuns());
    }
});

List<BulkOperation> batch = new ArrayList<>(500);
for (ProjectFactBuilder fact : projectMap.values()) {
    batch.add(indexOperation(fact.build()));
    if (batch.size() == 500) {
        bulkWithRetry(batch);
        batch.clear();
    }
}
if (!batch.isEmpty()) bulkWithRetry(batch);
deleteDocumentsNotInBatch(syncBatchNo);
```

示例省略了分页总数校验、重复编号检测、日期解析错误收集、锁续期和失败告警，这些均为生产实现必需项。

### 6. 内网程序验收标准

1. `prjCode` 作为 ES `_id`，重复执行同一批次不会产生重复项目。
2. 主接口 `bugNum=null` 的项目在事实索引中写为 `bugNum=0`。
3. 后两个接口只能补全主接口中存在的项目，不能额外创建项目事实。
4. 任一接口分页失败或总数不一致时，不开始本批次 Bulk 写入。
5. 20,000 项目压测时不持有三个原始结果集或完整 ES 请求集，堆内存保持在配置上限内。
6. Bulk 重试不会产生重复项目，也不会累加 `bugNum`。
7. 补充字段从有值变为 `null` 时，完整文档覆盖可以清除旧值。
8. 只有全部 Bulk 成功后才清理不属于当前 `syncBatchNo` 的旧项目。
9. 索引不存在 DevClaw 分类、代码行数和派生指标字段。
10. 每条文档包含 `syncBatchNo` 和 `syncedAt`，可以追溯最近成功批次。

### 7. 内网向 DevClaw 侧交付内容

企业内网开发完成后，仅需向 DevClaw 开发侧提供：

1. 已创建并有只读权限的索引名 `devclaw_project_info`。
2. 最终 Mapping。
3. 字段字典和 `null`/0 语义，特别是 `bugNum=null` 按 0 的约定。
4. 一组脱敏项目事实样例。
5. 最近同步时间和预期同步频率。
6. `prjCode` 与 snapshot `properties.projectCode` 一致性的抽样验证结果。

不需要向外网代码或 Codex 提供企业内网接口地址、Token、接口完整响应或 Java 写入程序源码。

## 第二部分：DevClaw——事实索引读取、指标统计与页面开发

### 8. DevClaw 部分目标

DevClaw 只读以下数据源：

| 数据源                                        | 用途                                       |
| --------------------------------------------- | ------------------------------------------ |
| `devclaw_project_info`                        | 项目缺陷、功能点、组织和里程碑原始事实     |
| `devclaw_event` 的 `harness.project.snapshot` | 获取 DevClaw 项目编号和 harness 项目映射   |
| `devclaw_event` 的 `code_gen`                 | 获取 DevClaw 生成代码行数                  |
| `devclaw_trace`                               | 获取 DevClaw 项目的输入 Token 和输出 Token |

在运营面板“研发效能” Tab 新增：

1. DevClaw 与非 DevClaw 总体对比。
2. 项目明细和筛选。

### 9. DevClaw 项目判定

项目事实索引不保存 `is_devclaw`。每次查询或短时缓存刷新时，从 snapshot 获取：

```text
DevClaw 项目编号集合 =
  DISTINCT properties.projectCode
  WHERE eventName = harness.project.snapshot
    AND properties.projectFromLean = true
    AND properties.projectCode 非空
```

同时构造：

```text
devclawPrjCodes: Set<prjCode>
leanHarnessProjectIdsByPrjCode: Map<prjCode, harnessProjectId[]>
leanHarnessProjectsByPrjCode:
  Map<prjCode, Array<{ harnessProjectId, adapterName, adapterVersion }>>
```

分类规则：

```text
事实 prjCode 在 devclawPrjCodes 中 → DevClaw
事实 prjCode 不在集合中            → 非 DevClaw
```

一个外部项目(prjCode)对应多个 harness 项目时，只要任一当前 snapshot 的 `projectFromLean=true`，该外部项目即为 DevClaw。代码行数只汇总该外部项目下 `projectFromLean=true` 的 harness 项目；同一外部项目下 `projectFromLean=false` 的 harness 项目不进入分母。

snapshot 查询不应用项目室筛选。项目所属室统一以事实索引的 `roomName` 为准，避免 snapshot 上报人的组织影响项目归属。顶部室筛选仍传递现有 `upperOrgLv1` 枚举值；该字典与事实索引 `roomName` 一致，DevClaw 项目度量查询将其直接用于过滤 `roomName`。

建议 snapshot 映射在主进程内缓存 5 分钟，不返回渲染层，也不写入事实索引。

### 10. 统一查询范围

#### 10.1 日期筛选

项目指标按立项时间统计：

```text
createDate >= from
AND createDate < to
```

例如选择 `2026-08-01` 至 `2026-08-31`：

```text
from = 2026-08-01 00:00:00
to   = 2026-09-01 00:00:00
```

项目度量 IPC 在主进程将现有 Dashboard ISO `TimeRange` 转换为 GMT+8 日历日边界，再生成 `createDate` 左闭右开查询。不得直接复用现有针对事件时间的 `lte: range.to` 查询构造器。

事实索引只保留立项时间距当前日期六个月以内的项目。UI 应将项目质量与交付模块的可查日期限制在该范围内，并提示“项目事实数据仅保留近六个月立项项目”；不得把超出保留期后的空结果解读为该期间项目数为 0。

#### 10.2 室筛选

运营面板顶部选择的室名称直接过滤：

```json
{
  "terms": {
    "roomName": ["研发一室", "研发二室"]
  }
}
```

日期和室条件同时作用于总体对比和项目明细。

日期条件只决定哪些项目进入统计样本，不用于截断这些项目的 `bugNum`、`code_gen` 事件或 trace Token。完整时间口径见第 13.2 节。

#### 10.3 其他筛选口径

| 筛选          | 总体对比 | 项目明细 | 实现                                                                                 |
| ------------- | -------- | -------- | ------------------------------------------------------------------------------------ |
| 项目阶段      | 生效     | 生效     | 事实索引 `terms phaseStatus`                                                         |
| 功能点区间    | 生效     | 生效     | 事实索引 `range notAdjustFuns`；启用区间时自动排除 `null`                            |
| DevClaw 插件  | 生效     | 生效     | snapshot `properties.adapterName` 精确匹配，只收窄 DevClaw 项目集                    |
| 开发方式      | 不生效   | 生效     | 明细可选全部、DevClaw、非 DevClaw；总体始终保留两组对比                              |
| 项目编号/名称 | 不生效   | 生效     | 项目编号使用 `wildcard *keyword*` 包含查询，项目名称使用 `match_phrase` 全文短语查询 |
| 室/组搜索     | 不生效   | 生效     | `roomName`、`groupName` 使用 `wildcard *keyword*` 包含查询；与顶部室筛选叠加         |

插件选项和筛选逻辑直接参考“项目运营概览 → 项目列表 → 全部插件”：

1. 选项来自当前 `harness.project.snapshot` 中 `properties.projectFromLean=true` 且非空 `properties.adapterName` 的去重值，按插件名合并不同版本。
2. 选中插件后，用 `term properties.adapterName` 匹配 lean harness 项目，再通过 `projectCode` 得到对应外部项目编号集合。
3. 一个外部项目对应多个 lean harness 项目时，任一当前 harness 项目匹配所选插件，该外部项目即命中。
4. 插件筛选只收窄 DevClaw 一侧；非 DevClaw 侧仍使用其他事实条件下的全量非 DevClaw 项目。因此两侧样本不对称，UI 必须展示口径 Tips。
5. 明细选择“非 DevClaw”时禁用插件筛选，或自动清空已选插件，避免产生必然为空的条件组合。
6. 插件只用于筛选外部项目；项目命中后，其缺陷率和 Token 仍汇总该外部项目下全部 lean harness 项目，不再只保留绑定所选插件的 harness 项目数据。

### 11. 指标有效样本规则

项目仍然属于 DevClaw 或非 DevClaw 分组，但字段缺失时只退出依赖该字段的指标：

| 指标           | 有效条件                                            | 不满足时                                     |
| -------------- | --------------------------------------------------- | -------------------------------------------- |
| 平均缺陷数     | `bugNum` 非 `null`                                  | 不进入缺陷数均值；按当前接口契约通常不会为空 |
| 平均功能点     | `notAdjustFuns` 非 `null`                           | 不进入功能点均值                             |
| 缺陷密度       | `bugNum` 非 `null` 且 `notAdjustFuns 非 null且 > 0` | 不进入密度的分子和分母                       |
| DevClaw 缺陷率 | `bugNum` 非 `null` 且项目生成行数大于 0             | 不进入缺陷率的分子和分母                     |
| 提测时间       | 立项和 ST 时间均存在，且 ST 不早于立项              | 不进入提测时间均值                           |
| 交付天数       | 审批和首次上线时间均存在，且上线不早于审批          | 不进入交付天数均值                           |

示例：

```text
bugNum = 10
notAdjustFuns = null
```

该项目的 10 个缺陷进入缺陷数统计，但项目不进入缺陷密度；如果时间字段完整，仍进入提测和交付周期统计。

总体接口必须同时返回：

```text
projectCount
bugSampleCount
functionPointSampleCount
defectDensitySampleCount
defectRateSampleCount
testLeadSampleCount
deliverySampleCount
```

### 13. DevClaw 缺陷率

#### 13.1 数据关联

“全部 DevClaw 项目”特指经过页面日期、室等事实条件过滤后命中的全部 DevClaw 项目，不是事实索引中的所有历史 DevClaw 项目，也不是项目明细当前页。

为保证分子、分母属于同一批有效项目：

1. 从事实索引取得日期、室条件下命中的 DevClaw `prjCode` 和非空 `bugNum`。
2. 总体对比必须覆盖上述全部命中项目，不能只取项目明细当前页，也不能只查询一个独立的 `SUM(bugNum)`。
3. 根据 `leanHarnessProjectIdsByPrjCode` 得到这些项目下 `projectFromLean=true` 的全部 harnessProjectId。
4. 查询 `code_adopt`，要求采纳计数字段完整且 `properties.pushed=true`，由 ES 按 `properties.harnessProjectId` 汇总 `properties.adoptedLineCount`；请求使用 `size=0`，不把代码事件明细返回应用层。
5. 应用层将多个 lean harness 项目的已 Push 采纳行数按 `prjCode` 再次汇总。
6. 只保留 `bugNum` 非空且项目已 Push 采纳行数大于 0 的项目作为缺陷率有效样本。
7. 使用同一批有效项目的缺陷数之和与已 Push 采纳行数之和计算总体缺陷率。

```text
DevClaw 总体缺陷率 =
  SUM(有效项目 bugNum) × 1000
  / SUM(同一批项目 pushedAdoptedLines)
```

不能分别计算“全部命中项目的缺陷总数”和“全部命中项目的代码总行数”后直接相除。某个项目可能有 `bugNum`，但没有有效的已 Push 采纳行数；该项目仍进入缺陷数指标，但必须同时退出缺陷率的分子和分母。

项目明细缺陷率按项目计算：

```text
项目缺陷率 = bugNum × 1000 / pushedAdoptedLines
```

一个外部项目关联多个 lean harness 项目时：

```text
pushedAdoptedLines(prjCode) = SUM(pushedAdoptedLines of lean harnessProjectId[])
```

代码行数查询示例：

```json
POST devclaw_event/_search
{
  "size": 0,
  "query": {
    "bool": {
      "filter": [
        { "term": { "eventName": "code_adopt" } },
        { "exists": { "field": "properties.adoptedLineCount" } },
        { "exists": { "field": "properties.generatedLineCount" } },
        { "exists": { "field": "properties.effectiveGeneratedLineCount" } },
        { "term": { "properties.pushed": true } },
        {
          "terms": {
            "properties.harnessProjectId": ["H001", "H002"]
          }
        }
      ]
    }
  },
  "aggs": {
    "by_harness_project": {
      "terms": {
        "field": "properties.harnessProjectId",
        "size": 10000
      },
      "aggs": {
        "pushed_adopted_lines": {
          "sum": { "field": "properties.adoptedLineCount" }
        }
      }
    }
  }
}
```

该请求复用“项目运营概览 → 已 Push 采纳行数”的事件与字段口径。ES 扫描并聚合符合条件的事件，应用层只接收每个 harness 项目的聚合结果，不拉取全部 `code_adopt` 原始事件。

#### 13.2 时间口径

本期采用“项目样本按页面日期筛选，指标事实使用当前值”的口径：

| 数据         | 时间口径                                                                                        |
| ------------ | ----------------------------------------------------------------------------------------------- |
| 项目样本     | 按事实索引 `createDate` 落入页面日期范围筛选，并叠加室等条件                                    |
| 缺陷数       | 取项目事实索引最近一次成功同步的当前 `bugNum`                                                   |
| 代码行数     | 取命中项目下 lean harness 项目截至本次查询时的累计已 Push 采纳行数                              |
| Token        | 取命中项目下 lean harness 项目截至本次查询时的累计 trace Token                                  |
| 页面日期范围 | 只用于选择项目样本；不用于过滤 `code_adopt` 或 trace，也不把代码行数和 Token 截断到首次上线时间 |

因此，查询历史立项区间时，结果仍可能随着项目后续新增缺陷、代码被采纳并 Push、继续产生 trace Token 以及事实索引下一次同步而变化。这是当前“当前事实 + 累计事件”架构的预期行为，不代表查询错误。

若未来要求“截至首次上线时”的稳定历史缺陷率，需要同时具备首次上线时点的缺陷快照和代码行数快照；仅依靠当前事实索引和累计 `code_adopt` 事件无法精确还原。

非 DevClaw 项目没有可关联的 `code_adopt` 数据，因此缺陷率返回 `null`，页面显示 `—`。

#### 13.3 DevClaw Token 统计

Token 统计复用“项目运营概览”打开“仅精益项目”时的 trace 聚合口径：

1. 根据事实筛选和可选插件筛选得到本次命中的 DevClaw `prjCode`。
2. 通过 `leanHarnessProjectIdsByPrjCode` 取得这些项目下全部 lean `harnessProjectId`。
3. 查询 `devclaw_trace`，使用 `terms harnessProjectId` 圈定项目，求和 `totalInputTokens` 和 `totalOutputTokens`。
4. 不添加 `startedAt` 时间过滤；页面日期只决定项目样本，不截断 Token。
5. 不叠加 trace 上报人的 `upperOrgLv1` 过滤；室筛选已在事实索引 `roomName` 上完成，trace 只按已确定的 harness 项目集合聚合。
6. 总体对比的平均输入/输出 Token = 命中 DevClaw 项目的 Token 总和 ÷ 命中 DevClaw 项目数；没有命中 trace 的 DevClaw 项目按 0 计入。非 DevClaw 无 trace 关联，返回 `null`。
7. 普通排序下，项目明细只查询当前页 DevClaw 项目；按代码行数或单行 Token 排序时，查询最多 10,000 个符合条件的项目。ES 按 `harnessProjectId` 分桶求和，应用层再按 `prjCode` 合并。
8. Token 查询成功但某个 DevClaw 项目没有命中 trace 时，该项目输入/输出 Token 为 0；只有 Token 查询整体失败时才返回 `null` 并显示暂不可用。
9. 平均代码行数 = 命中 DevClaw 项目的累计已 Push 采纳行数之和 ÷ 命中 DevClaw 项目数；没有采纳行的项目按 0 计入。
10. 平均单行代码消耗 Token 使用加权口径：只保留已 Push 采纳行数大于 0 的项目，分别计算 `SUM(输入 Token) / SUM(已 Push 采纳行数)` 和 `SUM(输出 Token) / SUM(已 Push 采纳行数)`。

总体 Token 查询示例：

```json
POST devclaw_trace/_search
{
  "size": 0,
  "query": {
    "bool": {
      "filter": [
        { "exists": { "field": "harnessProjectId" } },
        { "terms": { "harnessProjectId": ["H001", "H002"] } }
      ]
    }
  },
  "aggs": {
    "total_input_tokens": { "sum": { "field": "totalInputTokens" } },
    "total_output_tokens": { "sum": { "field": "totalOutputTokens" } }
  }
}
```

该逻辑复用现有字段、权限入口和 ES 查询工具，但不能直接复用现有 `projectModeTraceFilters(range, ...)`，因为其会强制添加 `startedAt` 时间条件。

### 14. 项目明细查询

#### 14.1 筛选

| 筛选项               | 实现                                                                                         |
| -------------------- | -------------------------------------------------------------------------------------------- |
| 日期                 | `createDate` 左闭右开 range                                                                  |
| 室                   | `terms roomName`                                                                             |
| 项目阶段             | `terms phaseStatus`                                                                          |
| 功能点区间           | `range notAdjustFuns`                                                                        |
| 开发方式：全部       | 不增加项目编号条件，返回后标记开发方式                                                       |
| 开发方式：DevClaw    | `terms prjCode = devclawPrjCodes`                                                            |
| 开发方式：非 DevClaw | `must_not terms prjCode = devclawPrjCodes`                                                   |
| DevClaw 插件         | 先按 snapshot `properties.adapterName` 得到命中 `prjCode`，再用 `terms prjCode` 过滤事实索引 |
| 项目编号/名称搜索    | 项目编号使用 `wildcard *keyword*`，项目名称使用 `match_phrase`；两者为 OR                    |
| 室/组搜索            | `roomName`、`groupName` 分别使用 `wildcard *keyword*`；两者为 OR                             |

当前 mapping 中 `prjCode`、`roomName`、`groupName` 为 `keyword`，可以直接进行包含搜索；`prjName` 为 `text`，支持全文短语匹配，但不保证严格的任意字符串子串语义。本期不调整索引 mapping；若后续要求项目名称严格逐字符包含，需要增加可搜索的 keyword/ngram 子字段并重建或回填数据。

#### 14.2 派生指标

当前页项目返回后，在主进程按原始事实计算：

```text
defectDensityPer100Fp = bugNum × 100 / notAdjustFuns
testLeadDays = (firstStStartDate - createDate) / 86400秒
deliveryDays = (firstOnlineDate - approvedDate) / 86400秒
pushedAdoptedLines = SUM(code_adopt.properties.adoptedLineCount WHERE pushed = true)
inputTokensPerAdoptedLine = totalInputTokens / pushedAdoptedLines
outputTokensPerAdoptedLine = totalOutputTokens / pushedAdoptedLines
tokensPerAdoptedLine = (totalInputTokens + totalOutputTokens) / pushedAdoptedLines
```

字段为空、分母小于等于 0 或时间倒置时，对应派生指标为 `null`。`tokensPerAdoptedLine` 只用于“单行代码消耗 Token 数”列排序，单元格分别展示输入和输出 Token/行。

普通排序时，当前页 DevClaw 项目再按第 13 节查询并合并代码行数、输入 Token 和输出 Token。非 DevClaw 的代码行数、缺陷率和 Token 保持 `null`。

#### 14.3 分页和排序

- ES 服务端分页，默认每页 20 条，可选 20、50、100。
- 默认按 `firstOnlineDate` 倒序、`prjCode` 升序。
- 支持按 `firstOnlineDate`、`bugNum`、`notAdjustFuns`、`pushedAdoptedLines` 和 `tokensPerAdoptedLine` 排序。
- 排序交互复用“项目运营概览 → 项目列表”：不单独提供排序下拉框，直接点击对应表头，在“降序 → 升序 → 默认排序”之间切换，并显示排序箭头。
- 代码行数和单行 Token 是跨索引派生指标，复用“项目运营概览”指标排序路径：先查询最多 10,000 个符合事实条件的项目，汇总这些项目的已 Push 采纳行数和 Token，在应用层按完整命中集合排序后再分页；`null` 始终排在末尾。单行 Token 按输入与输出 Token/行之和排序。
- 查询时派生的缺陷密度、缺陷率和两个周期暂不支持全局排序。
- 前 10,000 条可使用 `from/size`；需要深分页时改为 `search_after`。

所有项目度量 ES 查询在主进程执行前使用 `console.log` 输出查询名称、目标索引和完整 DSL，用于联调和问题排查。命中 snapshot 缓存时不会产生新的 ES 查询，因此也不会重复打印 snapshot DSL。

### 16. DevClaw 性能、安全和失败处理

#### 16.1 性能目标

| 项目              | 目标                             |
| ----------------- | -------------------------------- |
| 总体对比          | 典型日期和室范围下 p95 小于 1 秒 |
| 项目明细          | p95 小于 500 ms                  |
| snapshot 映射缓存 | 5 分钟                           |
| 明细查询          | 服务端分页，禁止全量回传         |

两个周期使用 runtime fields 在命中文档上计算。先以真实数据压测；只有它们成为明确瓶颈时，才评估物化整数秒数字段。

#### 16.2 权限与输入安全

- 沿用研发效能 Tab 的访问控制。
- 室权限最终作用于事实索引 `roomName`。
- snapshot 项目编号集合只存在于主进程，不返回渲染层。
- 限制日期范围、分页大小和排序字段。
- 项目名称 wildcard 搜索必须转义 ES 特殊字符。
- 日志不输出完整项目编号集合和项目事实文档。

#### 16.3 失败场景

| 场景                        | 处理                                                                              |
| --------------------------- | --------------------------------------------------------------------------------- |
| 事实索引不可用              | 新模块独立报错，现有研发效能指标不受影响                                          |
| snapshot 查询失败           | 不把全部项目降级为非 DevClaw；总体对比不可用                                      |
| snapshot `projectCode` 缺失 | 不参与关联并记录数据质量告警                                                      |
| DevClaw 编号超过上限        | 使用截断后集合继续查询，返回 `truncated=true`，页面展示结果不完整及可能误分类提示 |
| code_adopt 查询失败         | 其他指标正常展示，代码行数、缺陷率和单行 Token 显示暂不可用                       |
| trace Token 查询失败        | 其他指标正常展示，输入/输出 Token 显示暂不可用                                    |
| 功能点为空或不大于 0        | 对应缺陷密度为 `null`                                                             |
| 时间缺失或倒置              | 对应周期为 `null`，不进入均值                                                     |

### 17. DevClaw 部分验收标准

1. DevClaw 分类完全来自 snapshot 的 `projectFromLean` 和 `projectCode`。
2. 查询和 UI 不依赖事实索引中的 `is_devclaw` 字段。
3. 非 DevClaw 项目通过排除 DevClaw 编号集合统计，不枚举非 DevClaw 编号。
4. `bugNum` 有值而 `notAdjustFuns=null` 的项目进入缺陷数统计，但不进入缺陷密度。
5. 任一字段为空时，项目只退出依赖该字段的指标，不退出其他有效指标和项目总数。
6. 缺陷密度的分子、分母来自同一批有效项目。
7. DevClaw 总体缺陷率覆盖公共筛选条件下命中的全部 DevClaw 项目，而不是项目明细当前页。
8. DevClaw 缺陷率的缺陷数、代码行数来自同一批有效项目；没有有效代码行数的项目同时退出分子和分母，但不退出缺陷数指标。
9. `code_adopt` 的已 Push 采纳行数在 ES 内聚合，应用层不拉取全部代码事件明细。
10. 一个外部项目关联多个 harness 项目时，只汇总其中 `projectFromLean=true` 的 harness 项目代码行数。
11. 非 DevClaw 缺陷率显示 `—`。
12. 提测时间和交付天数查询时计算，事实索引中不存在派生天数字段。
13. 日期和室筛选同时作用于总体对比和项目明细，日期统一按 `createDate` 过滤。
14. 页面日期范围不用于过滤 `code_adopt`；代码行数为截至查询时的累计已 Push 采纳行数。
15. Token 复用现有“仅精益项目”的 trace 字段和 `harnessProjectId` 关联逻辑，但不使用页面日期过滤 trace。
16. 插件选项和筛选逻辑与“项目运营概览 → 项目列表 → 全部插件”一致。
17. 选择插件后只收窄 DevClaw 侧，非 DevClaw 侧不受插件条件影响，页面展示样本不对称 Tips。
18. 项目阶段、功能点区间、日期和室筛选同时作用于总体对比和明细。
19. 总体对比所有指标旁均展示第 15.3 节规定样式的口径 Tips。
20. 超过关联上限时允许直接截断，但接口必须返回 `truncated=true`，页面必须提示结果可能不完整或误分类。
21. 代码行数与“项目运营概览 → 已 Push 采纳行数”使用相同事件过滤和字段口径，并作为每千行代码缺陷数的分母。
22. 代码行数和单行 Token 支持完整命中集合上的应用层排序；单行 Token 按输入与输出 Token/行之和排序。
23. 项目度量每次实际执行 ES 查询前打印查询名称、索引和完整 DSL。
24. 平均输入/输出 Token 使用命中 DevClaw 项目数作为分母，没有 trace 的 DevClaw 项目按 0 计入。
25. 平均代码行数使用命中 DevClaw 项目数作为分母，没有已 Push 采纳行的项目按 0 计入。
26. 平均单行代码消耗 Token 分输入、输出展示，按有效项目的 Token 总和 ÷ 已 Push 采纳行数总和加权计算。

### 18. ADR-001：使用独立 ES 原始事实索引，查询时完成 DevClaw 关联

#### 状态

已接受。

#### 背景

外部项目数据只能在企业内网获取并由独立 Java 服务写入；DevClaw 分类和代码生成事件已经存在于 `devclaw_event`。当前阶段要求两边保持独立，不同步分类和代码行数。

#### 决策

企业内网建设直接索引 `devclaw_project_info`，只写原始项目事实。DevClaw 只读该索引，通过事实 `prjCode` 与 snapshot `properties.projectCode`、`code_adopt` 做应用层关联，并在查询时计算缺陷密度、缺陷率、单行 Token 和两个周期。

#### 正向影响

- 企业内网写入程序和 DevClaw 页面可以独立开发、独立部署。
- 不需要把企业内网接口或凭据暴露给 DevClaw 开发环境。
- 不需要维护 `is_devclaw` 和代码行数同步任务。
- 原始事实更新后无需同步更新派生指标。
- 非 DevClaw 项目数量较多时仍只传递 DevClaw 编号集合。

#### 负向影响

- ES 不支持普通跨索引 join，DevClaw 主进程需要应用层关联。
- 查询性能受 DevClaw 项目编号数量影响。
- 两个周期的 runtime fields 带来少量查询开销。
- 当前分类只能表达查询时状态，不能还原历史分类。
- 非 DevClaw 缺陷率暂不可计算。

#### 备选方案

1. MySQL 事实表：在分类不落事实表时仍需跨服务传递项目编号，并增加内网查询 API；本期不采用。
2. 将 `is_devclaw` 写入事实索引：查询更简单，但违反当前数据源独立约束；作为规模超过关联上限后的演进方案。
3. 保存派生指标：查询更快，但增加一致性和口径变更成本；第一版不采用。

### 19. ADR-002：20,000 个项目采用单 Map 聚合后分批覆盖写入 ES

#### 状态

已接受。

#### 背景

三个外部接口分别分页，页内项目编号不保证对应；主接口是权威项目集合，补充接口只负责提供审批时间和功能点。预计项目总量约 20,000 条，可以接受 Bulk 写入期间短暂读到新旧批次混合数据，更重视实现简单、失败可恢复和避免旧字段残留。

#### 决策

同步任务先完整拉取主接口并构造 `Map<prjCode, ProjectFactBuilder>`，再串行完整拉取两个补充接口并更新同一个 Map。三个接口全部校验成功后，遍历 Map，以每批 500 条的 Bulk `index` 完整覆盖事实文档；只保留一个项目 Map 和一个当前 Bulk List。

#### 正向影响

- 三个接口分页无需对齐，关联逻辑集中在项目编号 Map。
- 每个项目只执行一次最终写入，数据语义和重试逻辑简单。
- 完整文档覆盖可以清除补充字段上一批次的旧值。
- 20,000 条约 40 个主接口分页和 40 个 ES Bulk，请求数量可控。
- 不需要引入暂存 MySQL 表、暂存 ES 索引或额外消息链路。

#### 负向影响

- 同步期间需要常驻保存约 20,000 个 Builder，预计占用约 40～200 MB 堆内存。
- 直接写物理索引时，约 40 个 Bulk 完成前可能查询到新旧批次混合数据。
- 任一补充接口失败会阻止本批次发布，即使主接口已经拉取完成。

#### 备选方案

1. 每拉取一页直接更新 ES：写入次数更多，局部更新容易保留旧值，失败恢复复杂；本期不采用。
2. 三个接口结果全部保存为 List 后一次写入：额外占用堆内存且没有收益；本期不采用。
3. 使用暂存表或暂存索引：适合几十万以上项目或严格原子切换场景，对当前规模过度设计；本期不采用。
