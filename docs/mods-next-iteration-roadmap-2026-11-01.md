# 后续迭代：先贯通，再补能力，最后集中验收

依据 2026-11-01 用户补充调整。后续开发顺序以本文为准；能力审计中的历史优先级随此更新。应用仍为 2.0.0，原项目模式的创建、配置、需求和执行页面继续沿用。

## 第一阶段：贯通现有页面与能力

本阶段按 [具体方案](mods-continuity-phase1-plan-2026-11-01.md) 完成已识别断点的修复，两个独立 medium agent 回检通过；范围和局限见 [验收记录](mods-continuity-phase1-verification-2026-11-01.md)。集中真实模型全流程验收仍按第三阶段安排。

先解决“能力已经有，但用户找不到、用不上、走不下去”的问题，不先扩建一套入口。

逐条检查这些完整路径：

1. 普通聊天与创造者切换→描述需求→准备当前候选→试用→修改→重新准备→保存→再次使用。
2. 导入 ZIP→主插件和依赖归属→必要配置和汇总授权→对应的聊天或原项目入口。
3. 项目插件→原项目创建/配置→需求管理→执行→待确认/停止→产物和会话→完成。
4. 已有页面、侧栏、工具栏及交互面板→入口可发现→打开和操作→状态反馈→关闭/返回原任务。
5. 开发文件夹导入→列出需要安装/配置的组件→生成候选→保存及使用。与普通自然语言创建、ZIP 安装分清适用对象。

每条路径采用同一检查标准：用户知道现在是什么、为什么需要此操作、会产生什么结果、下一步在哪里；失败、等待、取消、修改后失效和重启恢复都有明确去向。当前聊天和旧记录保留，不能自动重放未知操作或把旧版通过记录当作新版通过。

文案统一处理：去掉“作者源码”“高级开发”等没有用途解释的入口表达；开发者必需的文件名留在对应的开发者说明里。普通用户的主路径默认在对话中完成，技术选项按需展开。只改措辞而没有接通操作不算完成。

第一阶段已把该入口改为“导入开发文件夹（开发者）”，解释谁需要、选什么和下一步；明确 ZIP 应到插件管理上传，并修正交付卡的位置说明。最终贯通范围与局限以本节上方的验收记录为准。

## 第二阶段：补齐重要的通用底层 Mods 能力

本轮已按 [具体方案](mods-capabilities-phase2-plan-2026-11-01.md) 实施，并经两个全新 medium agent 回检；范围、证据和剩余适配边界见 [验证记录](mods-capabilities-phase2-verification-2026-11-01.md)。新增聊天卡片、MCP 独立连接与子任务查看沿通用宿主实现，原项目流程不变。MCP 新主动连接先开放 stdio，HTTP/SSE 保留原已配置调用链；不把未完成的远程主动连接、Placed 滚动或完整输入重定向写成已支持。

先核对已有实现和真实缺口，能沿用的宿主服务继续沿用。每个新增能力都同时接通创造者可发现的契约、SDK、权限、实际执行、状态及用户入口。

| 优先项 | 要完成的实际闭环 |
| --- | --- |
| 页面与交互界面 | 声明页面/入口→生成→可发现并打开→交互反馈→关闭/返回；补齐现有页面扩展的断点，再评审必要的聊天内交互卡片，避免只增加声明或样式 |
| MCP | 发现和选择服务→必要配置/授权→真实连接→调用→断开、失败及撤权；认证由宿主管理，插件不能获取原始凭证或任意绕过连接策略 |
| 子会话/子 agent | 创建任务→明确允许的模型、工具和范围→查看进度→取消或完成→取回结果→进入子会话查看并返回；保持父子归属、输入目标和账号隔离 |

`Placed`、通知等按它们对上述闭环的作用安排，不能以同名空函数或错误别名冒充支持。具体能力进入开发前再做契约和实现评审；复杂业务规则、企业接口及多仓库策略仍由插件开发者实现，不给 AutoBiz 添加平台分支。

暂不纳入附件媒体、图片、音频、视频及多模态接入。不把这些项目夹带进 MCP、页面或子会话的交付范围。

## 第三阶段：集中验收并整理开发者底座

前两阶段完成后，再集中执行真实界面和模型验收。开发过程中仍做必要的窄回归，避免缺陷累积；不把全面验收提前当作下一轮的主工作，也不反复跑整套业务实现。

- 用聊天 Mod、通用页面/MCP/子会话需求、非 AutoBiz 项目和 AutoBiz 派生需求验证同一套通用路径。
- 覆盖从零创建、派生、组合调整、试用、保存和正式入口衔接；验证配置不足、取消、失效、重启及未知结果的去向。
- 检查 128K 配置下的上下文使用与连续创作，区分用户配置、真实模型限制和平台故障。
- 集中多 agent 回检与必要的真实模型验收；Git/审批环境问题单列，不把受控结果写成真实业务通过。
- 在能力和入口稳定后整理 SDK/能力目录、适用范围、兼容性说明、少量通用脚手架及完整示例。示例说明如何调用公共能力，不固化业务流程。

最终交付标准：普通用户可以沿一条连贯路径完成创作和使用；开发者可以据公开契约组合页面、工具、MCP 和子会话；平台负责通用机制，复杂个性化留在插件中。
