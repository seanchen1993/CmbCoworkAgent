# 研发效能各室指标口径

## 公共口径

### 组织和日期筛选

| 条件 | DDL 表和字段 | 规则 |
| --- | --- | --- |
| 项目所属团队 | `project_info.teamName` | 固定为「零售客户经营开发团队」。 |
| 项目所属室 | `project_info.roomName` | 组织效能导出覆盖团队各室。计算某室的项目类指标时，取 `roomName` 等于该室名称的项目。 |
| 立项日期门槛 | `project_info.createDate` | 只纳入 `2026-06-01 00:00:00` 及以后立项的项目。这个门槛与所选统计周期同时生效。 |
| 统计周期：按开发完成（本文默认） | `project_info.firstStStartDate`、`project_info.firstUatStartDate` | 优先取首次 ST 发起日期，缺少 ST 日期才取首次 UAT 发起日期。两者都缺失时，项目无法按开发完成日期入选。 |
| 统计周期：按立项 | `project_info.createDate` | 选择「按立项」时，用立项日期判断项目是否落在统计周期内。 |

时间按 GMT+8 解释，起止日期均覆盖整天。SQL 使用「开始日零点及以后、结束日次日零点以前」表示。例如，选择 2026 年 10 月，范围是 `[2026-10-01 00:00:00, 2026-11-01 00:00:00)`。一个 5 月立项、10 月开发完成的项目虽然符合 10 月的开发完成日期条件，但未达到立项日期门槛。

项目类指标使用下文 DDL 的 `project_info` 表。月人均特性吞吐率用 `project_info.firstOnlineDate` 筛选周期，仍保留立项日期门槛。平均特性上线耗时沿用普通项目周期，首次上线日期只用来计算耗时。

代码类指标按代码上报的组织归属统计。CMBDevClaw 代码事件来自运营看板项目模式埋点，按下文 `project_mode_code_event.upperOrgLv2` 限定团队、按 `upperOrgLv1` 归室、按 `generatedAt` 筛选周期。代码事件使用所选起止时间，两端均包含。组织月度填报按 `devclaw_gitee_push_info.teamName`、`orgLevel = 'room'`、`roomName` 和 `timeRange` 取数。

### 项目类型与分组

`developmentMode` 表示精益项目的研发类型，用于区分智能化和常规项目。

- **智能化（`devclaw`）**：该精益项目在运营面板的项目模式中有非测试项目记录。
- **常规（`non_devclaw`）**：该精益项目在运营面板的项目模式中没有非测试项目记录。

研发类型的判定不受本次所选室和统计周期限制。

对按项目类型展示的指标，**一组就是同一次统计中的「一个室 × 一种项目类型」**。例如，「A 室的智能化项目」和「A 室的常规项目」是两组。每项指标在各组内分别筛选有效项目，分子和分母使用同一批有效项目。SQL 用 `:room_name` 固定到一个室，再按 `developmentMode` 分组。

### 数据表和关联

`project_info`（精益项目）、`feature_info`（特性）和 `project_feature`（项目与特性关联）的数据都来自 DAAS 平台。时间按 GMT+8 的 `YYYY-MM-DD HH:mm:ss` 表示，缺失值存为 `NULL`。

```sql
CREATE TABLE project_info (
    prjCode           TEXT PRIMARY KEY NOT NULL, -- 精益项目编号
    prjName           TEXT,                      -- 项目名称
    teamName          TEXT,                      -- 所属团队
    roomName          TEXT,                      -- 所属室
    createDate        TEXT,                      -- 立项日期
    firstStStartDate  TEXT,                      -- 首次 ST 发起日期
    firstUatStartDate TEXT,                      -- 首次 UAT 发起日期
    firstOnlineDate   TEXT,                      -- 首次上线日期
    approvedDate      TEXT,                      -- 项目关联特性中最早的审批完成日期
    notAdjustFuns     NUMERIC,                   -- 功能点
    bugNum            INTEGER,                   -- 缺陷数
    devWorkHours      NUMERIC                    -- 项目累计开发报工小时
);

CREATE TABLE feature_info (
    featureCode  TEXT PRIMARY KEY NOT NULL, -- 企业特性编号
    featureName  TEXT,                      -- 特性名称
    approvedDate TEXT                       -- 该特性自己的审批完成日期
);

-- SQL 辅助表：将 featureCodes 数组展开，每个项目与特性的组合占一行。
CREATE TABLE project_feature (
    prjCode     TEXT NOT NULL REFERENCES project_info (prjCode),
    featureCode TEXT NOT NULL,
    PRIMARY KEY (prjCode, featureCode)
);
```

### 运营看板项目模式埋点

以下两张参考表把埋点的字段展开成普通列。项目快照按 CMBDevClaw 项目编号取一条项目关联；两种测试标记各自汇总，只要同一项目的任一快照标记为真，就记为 `1`。代码事件表每行对应一条代码采纳埋点，`generatedAt` 对应埋点的代码生成时间，统一为 GMT+8。

```sql
CREATE TABLE project_mode_snapshot (
    harnessProjectId   TEXT PRIMARY KEY NOT NULL, -- CMBDevClaw 项目编号
    leanProjectCode    TEXT,                      -- 绑定的精益项目编号
    fromLean          INTEGER,                   -- 是否来源于精益，1 表示是
    testProject       INTEGER,                   -- 测试项目标记
    manuallyMarkedTest INTEGER                   -- 人工测试标记
);

CREATE TABLE project_mode_code_event (
    eventName                   TEXT,    -- 事件名称
    harnessProjectId            TEXT,    -- CMBDevClaw 项目编号
    upperOrgLv2                 TEXT,    -- 代码上报所属团队
    upperOrgLv1                 TEXT,    -- 代码上报所属室
    generatedAt                 TEXT,    -- 代码生成时间
    pushed                      INTEGER, -- 已 Push 时为 1
    adoptedLineCount            INTEGER, -- 采纳行数
    generatedLineCount          INTEGER, -- 生成行数
    effectiveGeneratedLineCount INTEGER  -- 有效生成行数
);
```

项目类型和代码统计共用以下精益项目关联。

```sql
WITH eligible_project_links AS (
    SELECT harnessProjectId, TRIM(leanProjectCode) AS prjCode
    FROM project_mode_snapshot
    WHERE fromLean = 1
      AND TRIM(harnessProjectId) <> ''
      AND TRIM(leanProjectCode) <> ''
      AND COALESCE(testProject, 0) <> 1
      AND COALESCE(manuallyMarkedTest, 0) <> 1
)
```

### 如何阅读导出结果

「各室指标」给出结果、分子、分母和有效样本数。「项目依据」每个精益项目一行，覆盖多个指标的有效样本。核对某项指标时，只取对该指标有效的记录。依据列里的 `—` 表示缺失或不参与该项计算，`0` 是有效零值。

### 公共计算规则

- **开发人月**按 21.75 个工作日、每天 7 小时折算，每人月共 **152.25 小时**。日期用来选择项目，功能点与开发报工取入选项目的累计值。
- **项目耗时**按 GMT+8 的 2026、2027 年工作日日历计算，包含调休。计入起止时间之间落在工作日内的实际时段，每累计 24 小时记一个工作日，保留小数。起止日期缺失、无效、超出日历覆盖范围，或结束日期跨日早于开始日期时，无有效耗时。同日时间倒置按 0 计。
- **汇总**先按指标选出同一批有效样本，再加总分子和分母。无有效样本或分母为 0 时，结果显示 `—`。SQL 中用 `NULL` 表示此结果。

### 项目指标共用 SQL

项目指标按室和统计周期取数。`:room_name` 为室名称，`:start_at` 为开始日零点，`:end_before` 为结束日次日零点。

SQL 示例按开发完成日期筛选。按立项日期统计时，`projects_in_scope` 的日期条件改用 `createDate`。

```sql
, project_modes(developmentMode) AS (
    VALUES ('devclaw'), ('non_devclaw')
),
retained_projects AS (
    SELECT p.*,
           CASE WHEN EXISTS (
               SELECT 1 FROM eligible_project_links AS l WHERE l.prjCode = p.prjCode
           ) THEN 'devclaw' ELSE 'non_devclaw' END AS developmentMode
    FROM project_info AS p
    WHERE p.createDate >= '2026-06-01 00:00:00'
),
project_scope AS (
    SELECT p.*,
           COALESCE(p.firstStStartDate, p.firstUatStartDate) AS developmentCompletedAt
    FROM retained_projects AS p
    WHERE p.teamName = '零售客户经营开发团队'
      AND p.roomName = :room_name
),
projects_in_scope AS (
    SELECT *
    FROM project_scope
    WHERE developmentCompletedAt >= :start_at
      AND developmentCompletedAt < :end_before
),
```

## 月人均产出功能点

这个指标表示所选项目每投入一个开发人月，产出了多少功能点。按项目类型分别计算。

### 参与计算的项目

对于所选室的一种项目类型，从 `projects_in_scope` 中选出功能点（`notAdjustFuns`）和累计开发报工小时（`devWorkHours`）都有有效值的项目。两项都可以为 0。这批项目同时用于加总功能点和报工小时。

### 计算公式

```text
功能点合计 = 本室、本项目类型下，有效项目的功能点之和
开发人月   = 这同一批有效项目的累计开发报工小时之和 ÷ 152.25
月人均产出功能点 = 功能点合计 ÷ 开发人月
```

例如，同一室同一类型的两个有效项目合计 314.72 个功能点、369.25 小时开发报工，结果为 `314.72 × 152.25 ÷ 369.25 ≈ 129.77 功能点/人月`。

### 参考 SQL

```sql
valid_projects AS (
    SELECT prjCode, developmentMode, notAdjustFuns, devWorkHours
    FROM projects_in_scope
    WHERE notAdjustFuns >= 0
      AND devWorkHours >= 0
),
totals AS (
    SELECT
        developmentMode,
        COUNT(*) AS valid_project_count,
        SUM(notAdjustFuns) AS total_function_points,
        SUM(devWorkHours) AS total_dev_hours
    FROM valid_projects
    GROUP BY developmentMode
)
SELECT
    :room_name AS roomName,
    m.developmentMode,
    COALESCE(t.valid_project_count, 0) AS valid_project_count,
    COALESCE(t.total_function_points, 0) AS total_function_points,
    COALESCE(t.total_dev_hours, 0) AS total_dev_hours,
    t.total_function_points * 152.25 / NULLIF(t.total_dev_hours, 0)
        AS function_points_per_person_month
FROM project_modes AS m
LEFT JOIN totals AS t ON t.developmentMode = m.developmentMode;
```

### 在 Excel 中核对

在「项目依据」按「项目所属团队」「项目所属室」「项目类型」找到对应组。只取「功能点」和「开发报工小时（功能点产出）」都为数值的行。分别求和后，用功能点合计乘以 152.25，再除以开发报工小时合计。以「各室指标」中同一室、同一项目类型的「有效样本项目数」「分子」「分母」「结果」核对。分母列记录的是开发报工**小时**，公式再将它折算为人月。

## 精益项目与特性的多对多关系

一个精益项目可以关联多个特性，一个特性也可以关联多个精益项目。`project_feature` 用「精益项目编号（`prjCode`）+ 特性编号（`featureCode`）」标识一条关联，同一对编号只保留一条。统计时按指标决定用哪个编号去重：

| 统计内容 | 编号处理 |
| --- | --- |
| 特性数量 | 按 `featureCode` 去重。特性吞吐率在每个「室 × 项目类型」内去重，智能化特性占比在每个室内去重。特性有编号即可参与，名称缺失不影响计数。 |
| 项目的报工、功能点和耗时 | 按 `prjCode` 计算，每个精益项目只累计一次。涉及特性审批的耗时，用该项目关联特性中最早的审批完成时间（`project_info.approvedDate`）作为起点。 |

例如，同一室同一项目类型内，项目 P1 关联 F1、F2，项目 P2 关联 F1。若两个项目都入选吞吐率样本，分子是 **2 个特性**，分母使用 **P1 和 P2 各自的报工小时**。

## 月人均特性吞吐率

统计入选项目每投入一个开发人月，首次上线项目关联了多少个不同的特性。智能化和常规项目分别计算。

### 参与计算的项目

从 `project_scope` 中选出 `firstOnlineDate` 在周期内、开发报工有效且至少关联一个特性的项目。

### 计算公式

`组内去重特性数 × 152.25 ÷ 同组有效项目累计开发报工小时合计`。

### 参考 SQL

```sql
valid_projects AS (
    SELECT p.prjCode, p.developmentMode, p.devWorkHours
    FROM project_scope AS p
    WHERE p.firstOnlineDate >= :start_at
      AND p.firstOnlineDate < :end_before
      AND p.devWorkHours >= 0
      AND EXISTS (SELECT 1 FROM project_feature AS f WHERE f.prjCode = p.prjCode)
),
project_totals AS (
    SELECT developmentMode, COUNT(*) AS valid_project_count, SUM(devWorkHours) AS total_dev_hours
    FROM valid_projects
    GROUP BY developmentMode
),
feature_totals AS (
    SELECT p.developmentMode, COUNT(DISTINCT f.featureCode) AS feature_count
    FROM valid_projects AS p
    JOIN project_feature AS f ON f.prjCode = p.prjCode
    GROUP BY p.developmentMode
)
SELECT m.developmentMode,
       COALESCE(p.valid_project_count, 0) AS valid_project_count,
       COALESCE(f.feature_count, 0) AS feature_count,
       COALESCE(p.total_dev_hours, 0) AS total_dev_hours,
       f.feature_count * 152.25 / NULLIF(p.total_dev_hours, 0) AS features_per_person_month
FROM project_modes AS m
LEFT JOIN project_totals AS p ON p.developmentMode = m.developmentMode
LEFT JOIN feature_totals AS f ON f.developmentMode = m.developmentMode;
```

### 在 Excel 中核对

在「特性依据」按统计层级「室」和统计组织筛选，对该项目类型的「对月人均特性吞吐率分子贡献」列求和；在「项目依据」按项目所属室和项目类型，对「开发报工小时（特性吞吐）」求和。

## 缺陷与功能点

这三项均从 `projects_in_scope` 选样本，按项目类型分别汇总。

| 指标 | 有效样本 | 计算公式 | Excel「项目依据」核对列 |
| --- | --- | --- | --- |
| 平均缺陷数 | 缺陷数 `bugNum` 有效，包含明确的 0。 | 缺陷数合计 ÷ 有效项目数。 | 缺陷数 |
| 平均功能点 | 结算功能点 `notAdjustFuns` 有效，包含明确的 0。 | 功能点合计 ÷ 有效项目数。 | 功能点 |
| 平均缺陷密度 | 同时有有效缺陷数和大于 0 的功能点。 | 同批项目缺陷数合计 × 100 ÷ 功能点合计，单位为个/百功能点。 | 缺陷数、功能点，两列要在同一行满足条件。 |

### 参考 SQL

三个 `WHERE` 分别对应三项指标的有效样本。每个样本行给出该项目对分子和分母的贡献。

```sql
metrics(metric) AS (
    VALUES ('平均缺陷数'), ('平均功能点'), ('平均缺陷密度')
),
valid_samples(metric, developmentMode, numerator, denominator) AS (
    SELECT '平均缺陷数', developmentMode, bugNum, 1
    FROM projects_in_scope
    WHERE bugNum >= 0
    UNION ALL
    SELECT '平均功能点', developmentMode, notAdjustFuns, 1
    FROM projects_in_scope
    WHERE notAdjustFuns >= 0
    UNION ALL
    SELECT '平均缺陷密度', developmentMode, bugNum, notAdjustFuns
    FROM projects_in_scope
    WHERE bugNum >= 0 AND notAdjustFuns > 0
),
totals AS (
    SELECT metric, developmentMode, COUNT(*) AS valid_project_count,
           SUM(numerator) AS numerator, SUM(denominator) AS denominator
    FROM valid_samples
    GROUP BY metric, developmentMode
)
SELECT i.metric, m.developmentMode,
       COALESCE(t.valid_project_count, 0) AS valid_project_count,
       COALESCE(t.numerator, 0) AS numerator,
       COALESCE(t.denominator, 0) AS denominator,
       t.numerator * CASE WHEN i.metric = '平均缺陷密度' THEN 100.0 ELSE 1.0 END
           / NULLIF(t.denominator, 0) AS result
FROM metrics AS i
CROSS JOIN project_modes AS m
LEFT JOIN totals AS t ON t.metric = i.metric AND t.developmentMode = m.developmentMode;
```

## 项目耗时

以下五项都从 `projects_in_scope` 取项目。表里的起止字段用来计算**该项目的耗时**，有效耗时之和除以有效项目数，再按项目类型分别展示。

| 指标 | 起点（`project_info`） | 终点（`project_info`） | Excel「项目依据」核对列 |
| --- | --- | --- | --- |
| 特性审批完成到开发完成耗时 | `approvedDate` | 首次 ST 发起，缺失时取首次 UAT 发起，即 SQL 中的 `developmentCompletedAt`。 | 特性审批完成到开发完成耗时 |
| 特性审批完成到立项完成耗时 | `approvedDate` | `createDate` | 特性审批完成到立项完成耗时 |
| 平均发起 ST 耗时 | `createDate` | `firstStStartDate` | 立项至首次 ST 发起耗时 |
| 平均发起 UAT 耗时 | `createDate` | `firstUatStartDate` | 立项至首次 UAT 发起耗时 |
| 平均特性上线耗时 | `approvedDate` | `firstOnlineDate` | 特性审批至首次上线耗时 |

### 参考 SQL

`working_days(start_at, end_at)` 根据精益项目的起止时间和公共部分的工作日日历计算耗时。用 SQLite 运行时，注册与 [项目耗时函数](../src/shared/project-metric-calendar.ts) 等价的函数。

```sql
metrics(metric) AS (
    VALUES ('特性审批完成到开发完成耗时'), ('特性审批完成到立项完成耗时'),
           ('平均发起 ST 耗时'), ('平均发起 UAT 耗时'), ('平均特性上线耗时')
),
project_durations AS (
    SELECT i.metric, p.developmentMode,
           CASE i.metric
               WHEN '特性审批完成到开发完成耗时'
                   THEN working_days(p.approvedDate, p.developmentCompletedAt)
               WHEN '特性审批完成到立项完成耗时'
                   THEN working_days(p.approvedDate, p.createDate)
               WHEN '平均发起 ST 耗时'
                   THEN working_days(p.createDate, p.firstStStartDate)
               WHEN '平均发起 UAT 耗时'
                   THEN working_days(p.createDate, p.firstUatStartDate)
               WHEN '平均特性上线耗时'
                   THEN working_days(p.approvedDate, p.firstOnlineDate)
           END AS days
    FROM projects_in_scope AS p
    CROSS JOIN metrics AS i
),
totals AS (
    SELECT metric, developmentMode, COUNT(*) AS valid_project_count,
           SUM(days) AS total_working_days, AVG(days) AS average_working_days
    FROM project_durations
    WHERE days IS NOT NULL
    GROUP BY metric, developmentMode
)
SELECT i.metric, m.developmentMode,
       COALESCE(t.valid_project_count, 0) AS valid_project_count,
       COALESCE(t.total_working_days, 0) AS total_working_days,
       t.average_working_days
FROM metrics AS i
CROSS JOIN project_modes AS m
LEFT JOIN totals AS t ON t.metric = i.metric AND t.developmentMode = m.developmentMode;
```

## 应用研发智能化特性占比

统计本室周期内项目关联的特性中，有多少属于智能化特性。每个室出一项总体结果。

### 有效样本和计算公式

1. 从 `projects_in_scope` 找到关联特性，按 `featureCode` 去重，得到分母。
2. 对每个候选特性，检查其**全部已保存的关联项目**。只要有一个项目属于智能化，特性就进入分子。判定可使用其他室、其他团队或周期外的已保存项目，这些项目不会扩大本室的候选特性集合。
3. `智能化候选特性数 × 100 ÷ 全部候选特性数`。

### 参考 SQL

```sql
candidate_features AS (
    SELECT DISTINCT f.featureCode
    FROM projects_in_scope AS p
    JOIN project_feature AS f ON f.prjCode = p.prjCode
),
classified_features AS (
    SELECT c.featureCode,
           EXISTS (
               SELECT 1
               FROM project_feature AS f
               JOIN retained_projects AS p ON p.prjCode = f.prjCode
               WHERE f.featureCode = c.featureCode
                 AND p.developmentMode = 'devclaw'
           ) AS is_intelligent
    FROM candidate_features AS c
)
SELECT COUNT(*) AS feature_count,
       COALESCE(SUM(is_intelligent), 0) AS intelligent_feature_count,
       SUM(is_intelligent) * 100.0 / NULLIF(COUNT(*), 0) AS intelligent_feature_pct
FROM classified_features;
```

### 在 Excel 中核对

从「特性依据」筛出统计层级「室」和目标统计组织，分别加总「对应用研发智能化特性占比分子贡献」和「对应用研发智能化特性占比分母贡献」。两列已经标出每个室每个特性应计数的那一行。

## 代码类指标共用数据

CMBDevClaw 的两个指标共用同一批已 Push 的采纳事件。取 `project_mode_code_event` 中三项行数都有值的已 Push 采纳事件，再通过 CMBDevClaw 项目编号关联到合格的精益项目。按上报室和代码生成时间筛选，项目的立项和开发完成日期不参与筛选。

`:room_name` 为代码上报所属室，`:code_from` 和 `:code_to` 为代码生成时间的统计起止时间，均按 GMT+8。

```sql
, code_by_harness_project AS (
    SELECT l.prjCode,
           MAX(0, SUM(e.adoptedLineCount)) AS pushed_lines,
           MAX(0, SUM(e.effectiveGeneratedLineCount)) AS effective_lines
    FROM project_mode_code_event AS e
    JOIN eligible_project_links AS l ON l.harnessProjectId = e.harnessProjectId
    WHERE e.upperOrgLv2 = '零售客户经营开发团队'
      AND e.upperOrgLv1 = :room_name
      AND e.generatedAt >= :code_from
      AND e.generatedAt <= :code_to
      AND e.eventName = 'code_adopt'
      AND e.pushed = 1
      AND e.adoptedLineCount IS NOT NULL
      AND e.generatedLineCount IS NOT NULL
      AND e.effectiveGeneratedLineCount IS NOT NULL
    GROUP BY l.prjCode, e.harnessProjectId
),
devclaw_totals AS (
    SELECT COALESCE(SUM(pushed_lines), 0) AS pushed_lines,
           COALESCE(SUM(effective_lines), 0) AS effective_lines,
           COUNT(DISTINCT prjCode) AS valid_project_count
    FROM code_by_harness_project
)
```

先按 CMBDevClaw 项目分别汇总行数，负的汇总值按 0 计，再汇总到室。有效样本项目数按精益项目编号去重。

## AI 代码入库率

衡量已 Push 的 AI 生成代码中，实际采纳了多少。可按任意受支持的统计周期计算，每室一个总体结果。

### 计算公式与参考 SQL

`已 Push 采纳行数合计 × 100 ÷ 同批事件的已 Push 有效生成行数合计`。

```sql
SELECT valid_project_count, pushed_lines AS numerator, effective_lines AS denominator,
       pushed_lines * 100.0 / NULLIF(effective_lines, 0) AS ai_adoption_pct
FROM devclaw_totals;
```

在 Excel「代码入库依据」取本室的 CMBDevClaw 行，加总「入库代码行数」和「对应已Push有效生成行数」。

## 代码入库情况

这组指标包含四个渠道的入库占比，以及累计 AI 入库代码占比（硅碳比）。只在所选周期恰好覆盖一个或连续多个完整自然月时展示。例如 7 月 1 日至 9 月 30 日可以汇总，7 月 1 日至 10 月 30 日含不完整月份，整组隐藏。

### 月度填报数据源

组织总入库行数和三个 devagent 渠道来自月度填报表 `devclaw_gitee_push_info`。每条填报记录对应一个组织和一个月份，`timeRange` 格式为 `YYYY-MM`。各室指标只取 `orgLevel = 'room'` 的记录。同一团队、同一室、同一月份只允许一条室级填报；缺失或无效的行数在 SQL 示例中记为 `NULL`。

```sql
CREATE TABLE devclaw_gitee_push_info (
    orgLevel                 TEXT NOT NULL, -- 组织层级，team 或 room
    teamName                 TEXT NOT NULL, -- 团队名称
    roomName                 TEXT,          -- 室名称
    timeRange                TEXT NOT NULL, -- 填报月份，例如 2026-07
    totalPushedLines         INTEGER,       -- 组织总入库行数
    devagentIdePushedLines   INTEGER,       -- IDE 入库行数
    devagentCloudPushedLines INTEGER,       -- Cloud 入库行数
    devagentCliPushedLines   INTEGER,       -- CLI 入库行数
    UNIQUE (orgLevel, teamName, roomName, timeRange)
);
```

### 有效数据和计算公式

分母是本室各月的**组织总入库行数之和**。各渠道的分子如下，均先累计行数再除以分母。所需月份有缺失或分母为零时，对应占比显示 `—`。明确填报为 0 的渠道在分母大于 0 时占比为 0%；埋点查询成功且本室没有符合条件的 CMBDevClaw 事件时，该渠道按 0 行计算。

| 导出行 | 分子 |
| --- | --- |
| devagent-ide | 该室各月填报的 IDE 入库行数之和。 |
| devagent-cloud | 该室各月填报的 Cloud 入库行数之和。 |
| devagent-cli | 该室各月填报的 CLI 入库行数之和。 |
| CMBDevClaw | 同一统计周期的已 Push 采纳行数。 |
| 累计 AI 入库代码占比（硅碳比） | 四个渠道入库行数之和，要求四个渠道与组织总量齐全。 |

### 参考 SQL

以 **2026 年 7 月 1 日至 9 月 30 日**为例，月度填报取 7、8、9 月，CMBDevClaw 埋点也按同一周期统计。每个行数字段须三个月都有有效值才求和。

```sql
, months(timeRange) AS (
    VALUES ('2026-07'), ('2026-08'), ('2026-09')
),
monthly_totals AS (
    SELECT
        CASE WHEN COUNT(p.totalPushedLines) = COUNT(*) THEN SUM(p.totalPushedLines) END AS total,
        CASE WHEN COUNT(p.devagentIdePushedLines) = COUNT(*) THEN SUM(p.devagentIdePushedLines) END AS ide,
        CASE WHEN COUNT(p.devagentCloudPushedLines) = COUNT(*) THEN SUM(p.devagentCloudPushedLines) END AS cloud,
        CASE WHEN COUNT(p.devagentCliPushedLines) = COUNT(*) THEN SUM(p.devagentCliPushedLines) END AS cli
    FROM months AS m
    LEFT JOIN devclaw_gitee_push_info AS p
      ON p.timeRange = m.timeRange
     AND p.orgLevel = 'room'
     AND p.teamName = '零售客户经营开发团队'
     AND p.roomName = :room_name
),
report_rows(source, numerator, denominator) AS (
    SELECT 'devagent-ide', ide, total FROM monthly_totals
    UNION ALL
    SELECT 'devagent-cloud', cloud, total FROM monthly_totals
    UNION ALL
    SELECT 'devagent-cli', cli, total FROM monthly_totals
    UNION ALL
    SELECT 'CMBDevClaw', d.pushed_lines, m.total
    FROM monthly_totals AS m CROSS JOIN devclaw_totals AS d
    UNION ALL
    SELECT '累计 AI 入库代码占比（硅碳比）',
           CASE WHEN m.total IS NOT NULL THEN m.ide + m.cloud + m.cli + d.pushed_lines END,
           m.total
    FROM monthly_totals AS m CROSS JOIN devclaw_totals AS d
)
SELECT source, numerator, denominator,
       numerator * 100.0 / NULLIF(denominator, 0) AS pushed_pct
FROM report_rows;
```

### 在 Excel 中核对

在「代码入库依据」筛选本室、「统计层级」为「室」。按自然月加总「组织累计入库」行，作为所有渠道的共同分母。三个 devagent 渠道分别按月加总。CMBDevClaw 使用整个统计周期的精益项目汇总行。最后核对「各室指标」中各行的分子、分母和结果。
