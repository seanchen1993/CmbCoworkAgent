# Webhook 最新状态契约

普通事件例程仍按每次事件执行，`Idempotency-Key` 只用于同一请求的持久去重。只有在例程编辑器选择“只处理对象的最新状态”，并保存“来源批次”后，才会启用本文的版本约束。此模式适用于订单、工单、构建等对象状态更新；通知、支付流水等每一条都有独立意义的事件应保留普通模式。

## 接入格式

沿用例程 Webhook 窗口提供的本机 POST 地址和 `Authorization: Bearer <密钥>`。每次交付提供 `Idempotency-Key`，重试保持原标识和正文。例程示例配置：

```json
{
  "kind": "event",
  "topic": "order.updated",
  "eventPolicy": { "mode": "latest-state", "sourceEpoch": "orders-v1" }
}
```

请求正文示例：

```json
{
  "entityKey": "order-123",
  "sourceEpoch": "orders-v1",
  "sequence": 42,
  "payload": { "status": "approved", "amount": "8750.75" }
}
```

- `entityKey`：例程范围内稳定的业务对象标识，1～160 字符，字母、数字、下划线、点、冒号或连字符。
- `sourceEpoch`：与例程配置精确匹配的来源批次，使用相同字符范围。源系统重建序号时由用户编辑例程确认新批次；入站事件不能自行切换批次。重新使用旧批次仍受此前高水位约束。
- `sequence`：同一对象、同一批次的递增非负安全整数，最大 9,007,199,254,740,991。它必须由可信源系统生成，不能采用接收时间猜测业务顺序。
- `payload`：本次实际业务资料，仍按不可信输入处理，不能扩大工具或审批权限。

同版本、同内容返回原任务，不再次派发；同版本不同内容返回 409。低于已接收高水位的事件返回 `accepted: true, disposition: "stale", runIds: []`，保留已忽略的回执。相同请求重试返回此前确认结果，即使高水位已继续推进。缺失/非整数版本返回 400，来源批次不符返回 409。

`emitEvent` 的内部类型同步支持可选 `version: {entityKey, sourceEpoch, sequence}`。普通例程继续逐事件执行。最新状态例程要求版本，因此不能通过“运行一次”绕过接入契约。例程编辑器、保存重试记录、模型例程工具和后台能力声明均保留该配置。

## 执行保证

版本记录、高水位、任务创建、旧任务停止以及持久接收回执在原 SQLite 事务中提交。提交失败不会留下半个新任务或提前推进高水位。

已接受新状态后，旧根任务及其跨 Bot、工作流子任务停止新派发，待处理审批被取消。审批已经通过也不等于还能执行：原 `beginEffect` 入口再次检查版本。运行循环及后台服务的原有授权检查也包含来源版本。

已开始的动作保留原 lease 和效果回执结算路径。新状态不会越过同对象旧任务或子任务中仍在进行、等待人工核对或结果未知的动作。重启后保留这些约束；人工只能在核对完全部未知结果后结束旧版本，不能把过期版本恢复为有效工作。不同对象相互不因此新增阻塞，同一 Bot 原有串行约束仍生效。

状态检查从运行根身份出发，使用活动任务和未决效果索引；不扫描完整任务历史来判定派发权限。版本记录不保存业务正文。每例程最多保留 100,000 个版本身份，达到上限会明确拒绝新版本，已有请求/版本重试仍可确认；不会通过删除旧高水位来悄悄放行迟到事件。

## 外部系统的原子性边界

Host 能阻止旧版本的新操作，并在已经发出的动作结果不明时阻塞后继。它不能撤回已经送达第三方的请求，也不能替任意网站、Shell 或连接器实现目标系统的原子条件更新。

修改外部状态时，连接器应重新读取目标版本，并在最终写入使用目标系统的 CAS / ETag / `If-Match`。Host 的 `versionForRun` 提供当前根任务继承的来源版本；目标版本和来源序号属于不同概念，不能混用。更新失败应返回明确冲突，重新读取后重新审批；响应丢失则保留未知效果，核对目标后再处理下一状态。受控 HTTP 版本对象测试验证该链路，不能据此宣称所有外部系统已具有原子防覆盖能力。

当前实现为 schema74。测试使用隔离 SQLite、实际 HTTP、原审批和效果回执；没有修改用户运行数据库。正式 provider 接入、当前冻结 App 和真实模型的 CJ04 全流程仍须单独验收。
