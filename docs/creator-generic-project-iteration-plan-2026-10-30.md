## 目标与边界

在 codex/mods-v2、应用 2.0.0 上，复用已有原生组合、作者草稿、编译、试用、交付和版本机制，完成可理解、可修改的项目插件创作路径。平台不识别 AutoBiz 名称、阶段或业务规则。已有未相关输出删除和本地报告保持原样，不提交推送，不构建安装包、不触发 Actions。

用户再次确认的边界：不同用户的业务阶段与产物由插件声明；创造者通过现有声明工具灵活调整组装。平台抽取草稿、契约、权限、运行和验证等通用机制，复杂行业规则、企业接口和执行策略交由插件开发者实现。AutoBiz 仅为参考样例，不能成为默认流程。当前结构调整沿已有对话工具，正文编辑不演变成新的流程设计器。

本轮支持：现有 native-modular 模板创建；受支持的已安装原生组合派生；查看阶段输入输出和检查；直接编辑阶段 Skill 正文或让创造者修改；保存不可变草稿修订；重新编译与从头试用；沿已有确认流程保存并从普通项目入口使用。

本轮不做：旧 AutoBiz 自动转换或全功能等价迁移、运行中项目迁移、中段恢复和原地回退、外部效果补偿、通用可视化流程设计器、新执行框架、全局语义影响分析、自动修改验收门禁。

## 现有基础与实施项

1. **基础模板与来源**：以已有 AutoBiz Lean 作者源作为受限研发参考脚手架，保留基线/定义/方案/编码/交付及其规则，不重写。核验作者源可编译、保留源码、可派生，明确后端/执行器/配置依赖边界。以不依赖 AutoBiz 的 native-modular/报告流程验证同一作者能力。新建和派生沿现有工具和入口；不建第二套导入安装机制。旧插件内容变化只形成新源码候选，不自动修改原生模板或既有项目。

2. **通用阶段提示词编辑**：在现有创作工作区加入阶段列表/详情与正文编辑入口。Host 从实际草稿 composition/source.json.modules[].skill 定位作者 Skill，返回必要的阶段、输入、输出、检查和可编辑正文；不能把生成的 skills/native-* 当作者源。保持 YAML frontmatter、其他资源、检查、依赖及配置原样。共享 Skill 文件应明确显示受影响阶段；本轮可拒绝直接编辑共享文件并引导对话修改，不能暗中更改多个阶段。缺源码/不支持格式明确只读。

3. **保存与并发**：复用作者会话 patch/save 与现有 scope、revision、sourceDigest 校验。来自 UI 的编辑只允许替换实际阶段正文，不能提交任意路径、生成文件或整包源码。校验会话仍为创造者、草稿身份仍有效；模型并发修改时拒绝过期保存，保留用户未保存文字。保存创建新修订，不修改旧试用和已安装插件。达到版本预算返回现有续作指引，不能放大预算或自动丢历史。用户须显式保存；离开/刷新不静默丢弃未保存编辑。

4. **自然语言修改与流程提示**：编辑页可将准确草稿/阶段信息交给既有创造者对话入口；同样编辑作者源。界面区分“草稿已保存”“编译/文件检查”“真实试用”“已安装”；只展示原事实，不新建成功状态机。保存后提示重新编译并从头试用；使用既有动作/回调完成衔接，旧成功不得成为新版本成功。现有试用未知/运行中依旧需结算，不绕过原生确认。

5. **回归与文档**：新增必要的 Host/IPC/renderer 测试，验证两个不同业务来源使用相同逻辑。维护简短使用说明和本轮验收记录，明确真实 UI/真实模型/受控夹具分别证明什么。真实模型验证若环境或现有结算缺陷阻塞，记录阻塞，不以受控测试替代通过，不为赶进度添加 AutoBiz 特例。

## 代码组织原则

- 阶段投影与正文变更使用小型可测试纯函数，作者会话持久化/授权仍走现有机制。
- IPC 只增加直接编辑确实需要的窄接口，复用原身份检查；不暴露任意文件写入 API。
- React 组件可复用现有 API/创作面板、按钮与错误反馈；避免进一步膨胀核心运行时。
- 模板业务改动仅在 resources/native-compositions 与相关测试，不修改平台使其识别具体模板。
- 实施前核对 origin/uat-without-mods 是否已合入，必要同步先保存既有工作；同步与评审结果保持可追踪。

## 验收要求

1. 从真实原生声明解析阶段列表、作者正文及输入输出/检查；AutoBiz Lean 与非 AutoBiz 均适用。
2. 手工编辑仅改变选定正文，完整保留 frontmatter、校验和其他文件；原版本不变；新版本编译与产物检查正常。
3. revision/digest/scope 冲突、非法阶段、共享资源、损坏声明、版本预算、运行中/未知试用均有准确处理，不绕过权限或旧成功失效。
4. 浏览器覆盖读取、修改、保存、并发冲突保留文字、取消/离开、AI 修改入口和试用衔接；保留截图。
5. 复验现有创建/原生派生/连续创作/交付及非 AutoBiz 项目链；AutoBiz 保留现有检查强度与范围声明。
6. 先跑窄测试，再 Node/Web typecheck、改动文件 lint 和 npm test；全量失败逐项记录，禁止拼接历史结果冒充最新全绿。

## 评审门槛

评审 A：架构通用性、源码来源、权限与版本、插件职责边界。评审 B：用户路径、最小工作量、可测试性、交付口径。两位分别给出“通过”或阻断项；逐项修订后必须再次得到两者明确通过。实现后再次请求代码评审。
