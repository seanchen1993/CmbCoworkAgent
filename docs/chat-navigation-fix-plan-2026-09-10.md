# 会话切换与搜索定位修复方案

日期：2026-09-10。工作分支：`codex/fix-thread-switch-search`。

状态更新：方案已实施，二次检视的 3 项问题已修复；功能、性能及检视结果见 [修复验证报告](chat-navigation-fix-validation-2026-09-10.md)。本文保留实施前设计，最终范围与验证边界以报告为准。原复现数据见 [二次检视记录](chat-navigation-review-2026-09-10.md)。

## 1. 修复目标与依据

保留已验证有效的虚拟列表首屏优化，修复搜索自动展开、完成态尾部丢失及多块索引预算失效，并验证不会重新阻塞共享界面线程。

| 已复现问题 | 根因 | 必须达到的结果 |
| --- | --- | --- |
| 搜索 524,008 字符的格式化回答，出现 1,239 ms 长任务 | 搜索模拟点击所有“展开全文”按钮，单行挂载约 3.9 万个元素 | 搜索不触发全文渲染，定位成本受目标上下文大小约束 |
| 300,026 字符回答中的尾部关键词在完成后消失 | 流式首尾预览切换为完成态前 256 Ki 字符 | 同一内容完成前后保留既有首尾覆盖 |
| 32 块共 1,024 万字符，投影约 332 ms | 每块独立分配 256 Ki 额度，最终截断发生在解析和拼接之后 | 进入投影前执行整条消息共享预算，重计算移出 renderer 主线程 |

另一个需要随修复解决的契约问题：`scanDurableChatSearch` 用历史命中数量减去本地命中数量，`mergeChatSearchResults` 再拼出全局 `occurrenceIndex`。本地覆盖首尾两个不连续区域时，数量不能表示位置。例如全文按顺序命中 A、B、C，本地只有 A、C，不能认为历史补充项位于 C 后面。仅修正文案、删除自动展开或提高字符上限，都不足以保证定位正确。

## 3. 内容预算与搜索覆盖

### 3.1 预算在解析前生效

对一次消息索引使用共享预算对象，先检查块元数据、选取源范围，再进行 Markdown 投影。不允许先 `flatMap/map/join` 全部正文，也不允许先进行完整大小写转换、全文哈希或格式清理后才截断。

建议初始硬限制如下；这些是实施目标，不是本轮已经测得的结果：

| 项目 | 初始限制与约束 |
| --- | --- |
| 单消息选取的源文本 | 合计不超过 256 Ki 个 UTF-16 code unit，所有正文块共享 |
| 单消息保留的投影文本 | 合计不超过 256 Ki 个 UTF-16 code unit；工具摘要计入预算 |
| 块和片段 | 检查至多 128 个候选内容块，另设片段数量上限；不能无界遍历整个数组 |
| 本地历史缓存 | 沿用最多 500 条、4 Mi 字符语料；新坐标和辅助数据另计内存额度 |
| 单个搜索上下文 | 最多 4 Ki 字符，只保留一个活动上下文 |
| Worker 传输 | 单批正文和元数据合计不超过 64 KiB 序列化字节，限制队列积压 |
| 历史检索 | 保留现有每次 512 KiB 扫描、128 KiB 响应预算；新增坐标也必须计入 |
| 命中结果 | 保留界面总量上限 1,000，生成坐标时就停止，不能先生成所有结果 |

字符额度与字节额度必须分开计数。中间副本、规范化文本、位置映射、Worker 在途消息都纳入内存核算；最终字符串长度合规不能作为临时分配合规的证据。映射优先使用片段或连续区间，不为每个字符创建对象。

用户输入的附件标记、Goal、内部通知、思考内容和工具详情有不同可见性规则。先识别语义边界，再选取可见范围；不能截取隐藏标记的中部后把它当普通正文。无法在预算内确认可见性的片段，标记覆盖不完整，不从原始隐藏内容补回。

### 3.2 完成态保留首尾覆盖

单条超长回答优先保留现有预览的首部约 8 Ki、尾部约 48 Ki 源范围，以及当前活动命中所在片段，再分配剩余中段预算。边界采用预览函数实际返回范围，避免重复和遗漏。未超过预算时覆盖全部可见正文。

流式结束只改变消息状态，不应让其已索引且仍存在的尾部关键词消失。命中位置保留原始块序号和源范围，不按裁切后数组重新编号。

对于任意多块、任意长度输入，硬预算与无限全文覆盖无法同时保证。超过预算的消息必须保留明确的 `coverage` 和 `truncated` 状态，并在界面显示搜索范围尚不完整；不能把局部“未匹配”表述为整条消息“无结果”。优先覆盖预算内的可见首尾，超出块数或总量限制的范围如实记录。

## 4. 命中身份、去重与精确定位

搜索文档从单个拼接字符串调整为有界片段。每个片段至少携带：消息 ID、内容来源种类、原始块标识、源范围、投影版本、内容快照标识和投影文本。命中携带片段身份及其投影文本中的起止偏移；展示序号由最终排序产生，不承担定位职责。

具体要求：

1. 本地与历史使用相同的确定性投影规则。内容和片段范围相同，坐标才能直接合并；排序按消息顺序、块顺序和片段内位置完成。
2. 删除 `requestedOccurrences - localOccurrenceCount`、`occurrenceOffset` 这类推断。数量仅用于展示统计，去重必须比较已经确认属于同一快照、同一位置的命中。
3. 活跃流内容与持久化内容可能不同。不同快照或不同裁切范围不能直接合并。驻留消息以当前可见投影为准；历史命中在目标分页加载后重新验证，过期项重新匹配或失效，不跳到另一处相同关键词。
4. 不能假设 Markdown 源字符偏移等于 DOM 偏移。大小写转换也可能改变字符串长度；规范化过程必须保留到原投影的偏移关系。不得顺便引入未经测试的空白折叠或新的匹配语义。
5. 已挂载片段建立有界 TextNode 映射，支持查询跨越粗体、链接等多个文本节点。生成 Range 后验证文本与查询一致，再执行滚动。
6. 首尾片段合并时保留间隔信息，禁止拼接后产生跨越被省略中段的虚假命中。真正连续的可见文本跨片段查询需要有界重叠及去重测试。
7. 片段边界改变或旧 Range 的节点断开后重新解析当前目标。无法验证对应关系时，显示该命中的有界上下文，不按 DOM 中“第几个同名词”猜测。

现有主进程已按历史加载的可见内容检索，应继续保持这一边界。不能为了补回 renderer 驻留超长回答的尾部，改为直接搜索数据库隐藏原文；驻留尾部由本地搜索计划保留。

## 5. 用有限上下文揭示折叠命中

删除 `prepareChatContentForSearchHighlight` 中对 `[data-chat-search-expand-markdown]` 的遍历点击。首尾预览已有的命中直接定位。

中段未挂载时，在目标消息的折叠区域展示一个最多 4 Ki 字符的只读搜索上下文。上下文来自与命中一致的投影文本，包含前后文并高亮目标；初版使用纯文本，避免截断 Markdown 围栏、表格后产生错误解析，也避免再次启动大段语法高亮。用户仍可显式点击“展开全文”查看完整格式。

通过受控参数沿 `ChatContainer → ChatMessageVirtualList → MessageBubble → StreamingMarkdown` 传递目标，仅传给匹配的正文块。组件 memo 比较器必须包含该参数；一次目标切换最多引起旧目标和新目标行的额外更新，不把每次导航广播成全部消息重渲染。

关闭搜索、切换会话或更换命中时释放旧上下文。展示状态独立于正文，不改变复制、编辑、分叉所使用的原始消息，也不进入模型上下文或持久化。

导航流程为：确认当前请求 → 必要时加载历史窗口 → 虚拟列表挂载目标行 → 必要时挂载上下文 → 校验 Range → 滚动。保留首轮修复中的最新回调引用、失效请求保护和精确 Range 滚动。

DOM 变化或尺寸变化才重新收集范围，避免最多 60 帧反复扫描整条消息。滚轮、触摸、键盘及滚动条的用户滚动意图统一取消待完成导航；程序触发的滚动不能误取消自身。旧查询、旧会话、旧内容版本的异步回调不得抢回滚动位置。

## 6. 索引移出界面线程，限制额外成本

即使每条只有 256 Ki，连续处理 500 条或 4 Mi 语料仍可能形成长任务。因此采用按需启动的搜索 Worker，负责可见性投影、规范化和匹配；renderer 只读取有界块元数据、切取有界源片段、传输小批次及应用结果。

关闭搜索时不建立索引。稳定历史复用缓存，只更新变化消息及流式尾部；输出结束只更新对应消息，不能因 `isLoading` 改变使所有稳定文档失效。首次语料构建采用小批次逐步产出结果，不同步建立全部文档再一次性发送。

每个请求包含会话、查询及内容版本。合并积压的流式更新，始终优先处理最新状态；取消消息只能在 Worker 获得调度时生效，所以单个工作单元也要有界并主动让出执行。切换会话后丢弃旧结果并释放或淘汰旧缓存，避免不断增长的常驻 Worker、消息数组和索引副本。

Worker 失败时保留有界的可见区域结果及不完整状态，不同步回退到全文扫描。不能把原始 1,024 万字符消息整体 structured clone 给 Worker，或在 UI 线程做完重投影后再交给 Worker 匹配。

历史检索仍处于主进程，新增坐标构造必须在扫描和响应预算内增量完成。保留分页之间的让出执行；性能回归同时观测主进程 IPC 延迟，避免只是把阻塞移到主进程。

## 7. 验证与合并门槛

### 功能回归

先把二次检视的 3 个复现转成可失败的自动化回归，再实施业务修复。补充以下边界：

- 相同关键词分别位于首部、折叠中段和尾部；连续上一个/下一个，顺序、数量和 Range 都正确。
- 流式到完成态、重复关键词、原始数组块序号、多段 Markdown、跨内联节点、中文、emoji 和大小写长度变化。
- 覆盖缺口不能生成跨间隔命中；超限结果正确标记范围不完整。
- 历史命中加载、重复 ordinal、空结果但有下一页、末页、过期请求、快速切换会话、取消导航。
- 用户附件、Goal、Hook、思考内容、折叠工具摘要的可见性；隐藏原始内容不能出现在搜索上下文。
- 复制、编辑、分叉、工具审批、手动展开、向上加载历史、滚动恢复及流式跟随。
- 新坐标加入后的 IPC 字节上限、单条超大结果、密集重复关键词和坐标截断；页游标必须推进，截断不能伪装成完整结果。

测试放在相应 shared/lib 旁的 `*.test.ts`，扩展现有 `chat-search-overlay.test.ts`、`thread-message-search.test.ts`、IPC 契约和滚动回归套件；浏览器与 Electron 场景扩展 `tests/chat-navigation-browser.spec.ts` 和 `tests/chat-navigation-e2e.spec.ts`。

### 性能及 E2E

使用真实 Markdown 组件和 Virtuoso，覆盖 1/80/100/101/128 条消息、512 Ki 字符高节点密度 Markdown、1 Mi 字符单条回答、32 块共约 10 Mi 字符、长代码和表格。不能仅用连续 x/y 字符代表长回答渲染成本。

固定机器、Node/Electron 版本和前台窗口条件，对基线、当前版本、修复版本各采样至少 20 次。记录中位数、P95、最大值和原始数据；冷索引构建时间与索引就绪后的导航延迟分开报告。

硬门槛：搜索不触发全文渲染；目标上下文、解析输入、返回文本、传输、坐标和缓存均不突破预算；关闭搜索没有新增索引工作；不会重新出现 Virtuoso 接管前的全量 Markdown 挂载。

性能门槛：压力场景不得出现由新搜索逻辑造成的 renderer 超过 50 ms 长任务；UI 每批准备/应用结果以 8 ms 为目标；会话切换和输入响应 P95 相对同条件对照不得退化超过 10%。临界波动需加样本确认，不能仅挑最快值证明通过。Worker CPU、主进程 IPC、GC 和内存一起记录，连续开关搜索及切换会话后不出现持续增长。

Electron E2E 在 A 会话持续输出时切换到 B 搜索并返回 A，同时覆盖文件/Git 面板交互、工具审批显示和输入响应。测量使用页面事件标记、MutationObserver、PerformanceObserver 和实际绘制时点，避免把测试框架的等待退避当作用户延迟。保存首尾和折叠命中截图，以及长任务原始记录。

完成窄测试后运行 `npm test`、`npm run typecheck`、`npm run lint`、`npm run build`。已有全仓失败逐项与基线对照；未知来源的失败必须查清，不能统一归为存量问题。变更文件不得新增 lint/typecheck 错误，相关测试、浏览器测试和 Electron E2E 必须通过。

### 代码检视重点

检查预算是否真的早于解析和分配、是否存在无界的 `map/join/hash/normalize`、片段及快照是否可比较、memo 是否吞掉定位更新、取消能否覆盖所有异步阶段、缓存是否随会话释放、IPC 新字段是否漏计字节，以及搜索上下文是否意外参与其他消息操作。

## 8. 实施顺序与交付

1. 固化 3 项回归及“本地 A/C、历史 A/B/C”的坐标合并用例，保留当前失败证据。
2. 实现共享预算、片段及坐标契约，并同步主进程、本地匹配和历史合并；用单测证明覆盖与身份正确。
3. 接入有限上下文和精确 Range 导航，修正行 memo、取消与生命周期；通过真实浏览器回归。
4. 接入按需 Worker 和增量缓存，验证 UI 准备阶段也受预算约束；完成性能对照。
5. 完成全量检查、Electron E2E、跨模块回归及最终代码检视，更新报告后再判断是否满足合并条件。

按上述顺序组织可审查的小提交；涉及同一返回契约的两端和测试一起变更。全部阶段通过前不把中间版本作为完整修复交付。第一轮已验证的虚拟列表首屏优化保留；新的搜索路径出现问题时应以完整契约为单位回退，避免主进程和 renderer 各留半套定位协议。
